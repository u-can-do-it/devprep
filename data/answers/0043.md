## Hints

- Which component type can use `useState`, `onClick` or `window`, and which can query a database directly?
- Does the code of a Server Component ever get sent to the browser?
- Can you pass a function or a `Date` as a prop from a Server to a Client Component?

## Answer

**Server Components (RSC)** run only on the server (at build or request time). They can be `async`, access databases, the filesystem and secrets, and their code and dependencies are **never shipped to the client**. They cannot use state, effects, event handlers or browser APIs. React serializes their output into the **RSC payload**, which the client merges into the tree.

**Client Components** are marked with `'use client'` at the top of a file. They are pre-rendered to HTML on the server too, then **hydrated** in the browser, so they can use hooks, events and browser APIs. Their JS is in the bundle.

`'use client'` marks a **boundary**: that module and everything it imports become client code. So push it to the **leaves** (a `LikeButton`, not the whole page).

**What can cross the boundary (Server → Client props):** only **serializable** values — primitives, plain objects/arrays, `Date`, `Map`/`Set`, typed arrays, Promises (read them with `use()`), JSX elements, and **Server Actions**. Not allowed: regular functions, class instances, or anything with methods.

**Composition pattern** — a Client Component can't *import* a Server Component, but it can receive one as `children`:

```tsx
// Server Component
<ClientTabs>
  <ServerProductList /> {/* rendered on the server, passed as a slot */}
</ClientTabs>
```

**Pitfalls:**

- Leaking secrets: anything passed as a prop ends up in the payload. Use the `server-only` package to guard server modules.
- Context providers must be Client Components; wrap them and render `{children}`.
- Server Components re-render on navigation/refresh, not on client state changes.

**Follow-up:** "Server Components" ≠ SSR — SSR produces HTML, RSC produces a serialized component tree; Next.js uses both.
