## Hints

- What happens if a user types `' OR '1'='1` into a login form that builds SQL by string concatenation?
- How can the database tell the difference between your SQL code and the user's data?
- Which parts of a query can't be parameterized, and how do you handle them?

## Answer

**SQL injection** happens when untrusted input is concatenated into a SQL string, so the input becomes part of the **code** instead of being treated as **data**.

```python
# Vulnerable
email = request.args["email"]
cur.execute(f"SELECT * FROM users WHERE email = '{email}'")
# email = "' OR '1'='1" -> returns every user
# email = "'; DROP TABLE users; --" -> potentially destructive
```

Consequences: data leaks, authentication bypass, data modification, sometimes remote code execution.

**Fix: parameterized queries (prepared statements).** The SQL text and the values are sent separately, so the database never parses values as SQL:

```python
cur.execute("SELECT * FROM users WHERE email = %s", (email,))
```

```js
await pool.query("SELECT * FROM users WHERE email = $1", [email]);
```

ORMs and query builders (SQLAlchemy, Prisma, Drizzle) parameterize by default – but their **raw query** escape hatches (`text()`, `$queryRawUnsafe`) can reintroduce the bug.

**Things you can't parameterize** – table/column names, `ORDER BY` direction – must be validated against an **allowlist**:

```python
sort = {"name": "name", "date": "created_at"}.get(request.args.get("sort"), "created_at")
```

**Defense in depth:**

- Least-privilege DB users (the app user shouldn't be able to `DROP TABLE`).
- Input validation (types, lengths) and generic error messages.
- Escaping functions are a fragile last resort, not a primary defense.

**Follow-up:** Is a NoSQL database immune? (No – e.g. MongoDB operator injection with `{"$ne": null}` in JSON bodies.)
