## Hints

- What is the difference between "the model was asked to answer in JSON" and "the API guarantees the output matches a schema"?
- After the model returns JSON, who validates it and what do you do when validation fails?
- What should never be computed by the model inside the JSON (ids, prices, totals)?

## Answer

Most product features don't want prose from an LLM; they want a **typed value**: extracted fields, a classification, a list of suggested tags, a plan for the next step. Getting that reliably is a layered problem.

**Levels of guarantee:**

1. **Prompt only** ("reply with JSON like `{...}`"): works most of the time, fails with Markdown fences, trailing commentary, invented fields, or a refusal in plain text. Acceptable for prototypes.
2. **JSON mode**: the provider guarantees syntactically valid JSON but not your shape.
3. **Schema-constrained output**: you pass a JSON Schema and the API constrains decoding so the result matches it. Two forms: a dedicated **structured output** parameter (Anthropic's `output_config.format`, OpenAI's `response_format` with a JSON schema) or **tool calling** with `strict: true`, where the "tool" is just a typed return value (#479). This is the production default.
4. **Validate anyway** with Zod or Pydantic (#182, #443): schemas express more than JSON Schema can (cross-field rules, ranges, enums tied to your database), SDKs can silently truncate when `max_tokens` is hit, and you want one place that throws a typed error.

**TypeScript with the Anthropic SDK:** the Zod schema is both the constraint and the validator.

```ts
import Anthropic from '@anthropic-ai/sdk';
import { zodOutputFormat } from '@anthropic-ai/sdk/helpers/zod';
import { z } from 'zod';

const Ticket = z.object({
  category: z.enum(['bug', 'billing', 'feature', 'other']),
  priority: z.enum(['low', 'medium', 'high']),
  summary: z.string().max(200),
  customer_ids_mentioned: z.array(z.string()),
});

const res = await client.messages.parse({
  model: 'claude-opus-5-5',
  max_tokens: 1024,
  messages: [{ role: 'user', content: `Classify this support email:\n\n${email}` }],
  output_config: { format: zodOutputFormat(Ticket) },
});
if (res.stop_reason === 'refusal' || !res.parsed_output) throw new LlmOutputError(res);
const ticket = res.parsed_output;           // typed as z.infer<typeof Ticket>
```

**Python with Pydantic:** `client.messages.parse(..., output_format=Ticket)` returns `response.parsed_output` as a validated model instance; the same `Ticket` class is reused by FastAPI for the response body (#79).

**Design the schema for the model, not for your database:**

- Flat, few fields, descriptive names and `description`s; enums instead of free text wherever a fixed set exists. Deeply nested, recursive or huge schemas degrade accuracy and cost tokens.
- Let the model extract and classify, **not compute**: totals, ids, dates in your own format, prices and permissions are derived in code from what it extracted (#481 for why you never let it decide authorization).
- Allow "I don't know": a `confidence` field or `null`able fields beat forced guesses. Ask for the quote or evidence the answer is based on when you'll show it to users.
- Version the schema like an API contract and keep examples in an eval set (#482), because changing a field description changes behaviour.

**Failure handling:** on a validation error, retry once with the error message appended ("field `priority` must be one of..."), then fall back (queue for a human, default value, or a visible error). Check `stop_reason`: `max_tokens` means truncated JSON, `refusal` means no output at all. Log the raw response with the request id for debugging. Keep temperature low for extraction tasks.

**Streaming:** structured output can be streamed, but partial JSON is not parseable until the end; for UI feedback stream a text field first or render progressively with a tolerant parser (#477).

**Follow-up:** the model keeps putting a long explanation into `summary`. What do you change first? (The field description and a `max` length in the schema, then an example in the prompt; constraints in the schema beat instructions in prose.)
