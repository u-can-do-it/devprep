## Hints

- Does a `CancellationToken` stop a running method by itself, or does the method have to cooperate?
- Who owns the `CancellationTokenSource`, and who only receives the token?
- Where does ASP.NET Core get a token that fires when the client disconnects, and how would you combine it with a timeout?

## Answer

**Cancellation is cooperative.** Nothing aborts your code. The owner of a `CancellationTokenSource` (CTS) calls `Cancel()`; everyone who received its `CancellationToken` checks it or passes it on to APIs that check it. By convention, cancelled work throws `OperationCanceledException` (`TaskCanceledException` derives from it).

| Type | Who uses it | What it does |
|---|---|---|
| `CancellationTokenSource` | the code that decides to cancel | `Cancel()`, `CancelAfter(timeout)`, must be disposed |
| `CancellationToken` | the code doing the work | `IsCancellationRequested`, `ThrowIfCancellationRequested()`, `Register(callback)` |

**Using a token in your code**

```csharp
public async Task ProcessAsync(IEnumerable<Order> orders, CancellationToken ct)
{
    foreach (var order in orders)
    {
        ct.ThrowIfCancellationRequested();                 // CPU loop: check between iterations
        await _db.SaveAsync(order, ct);                    // I/O: pass it down, the driver cancels the call
    }
}
```

- Accept `CancellationToken ct = default` as the **last parameter** of async methods and pass it to every async call inside.
- Don't swallow `OperationCanceledException` in a generic `catch (Exception)`; let it propagate or catch it explicitly.
- Cancellation is a request, not a guarantee: an operation may still complete if it was already past the point of no return.

**In ASP.NET Core**

The framework gives you `HttpContext.RequestAborted`, which fires when the client disconnects. Minimal APIs and controllers bind a `CancellationToken` parameter to it automatically:

```csharp
app.MapGet("/reports/{id}", async (int id, ReportService svc, CancellationToken ct) =>
    await svc.BuildAsync(id, ct));                         // stops the DB query if the user closes the tab
```

Be careful with writes: cancelling halfway through a non-transactional sequence of changes can leave inconsistent data. For work that must finish, pass `CancellationToken.None` (or a shutdown token) instead of the request token.

**Timeouts**

Link the incoming token with a timeout, so the operation stops when either fires:

```csharp
using var cts = CancellationTokenSource.CreateLinkedTokenSource(ct);
cts.CancelAfter(TimeSpan.FromSeconds(5));
try
{
    return await _pricing.GetQuoteAsync(sku, cts.Token);
}
catch (OperationCanceledException) when (!ct.IsCancellationRequested)
{
    throw new TimeoutException("Pricing service did not answer in 5 s");   // our timeout, not the client
}
```

The exception filter tells "the caller cancelled" apart from "our timeout fired". Other options: `task.WaitAsync(timeout, ct)` (stops *waiting*, not the work itself), `HttpClient.Timeout` or a resilience pipeline (#590), and ASP.NET Core's request timeouts middleware (`AddRequestTimeouts`, `[RequestTimeout]`).

**Background services** get a `stoppingToken` in `ExecuteAsync` that fires on shutdown (#595).

**Follow-up:** why dispose a `CancellationTokenSource`? (It may own a timer from `CancelAfter`, and linked sources register callbacks on their parent tokens. Not disposing a linked CTS created per request keeps those registrations alive on a long-lived parent token and leaks memory.)
