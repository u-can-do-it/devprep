## Hints

- What should happen to the first half of a money transfer if the second half fails?
- How can a database promise data survives a crash right after `COMMIT`?
- Is the "C" in ACID the same as the "C" in CAP?

## Answer

ACID describes the guarantees of a database **transaction** – a group of statements treated as one unit.

- **Atomicity** – all or nothing. If any statement fails or you `ROLLBACK`, every change in the transaction is undone. Implemented with undo information / MVCC row versions and the write-ahead log.
- **Consistency** – a transaction moves the database from one valid state to another: constraints (`PRIMARY KEY`, `FOREIGN KEY`, `CHECK`, `UNIQUE`) are enforced, so invalid data is rejected. Business invariants not expressed as constraints are the application's job.
- **Isolation** – concurrent transactions don't see each other's half-finished work. How strictly is configurable via isolation levels (Read Committed, Repeatable Read, Serializable), implemented with MVCC snapshots and locks.
- **Durability** – once `COMMIT` returns, the data survives a crash. The DB writes changes to a **write-ahead log (WAL)** and `fsync`s it before acknowledging; data files are updated later and replayed from the log on recovery.

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;  -- both updates or neither
```

Pitfalls:

- ACID's "C" (constraints hold) is unrelated to CAP's "C" (linearizable reads across replicas).
- Durability can be weakened for speed (e.g. `synchronous_commit = off` in PostgreSQL, async replicas).
- Many NoSQL stores offer ACID only per document/item, or in limited multi-item transactions.

**Follow-up:** Contrast ACID with BASE (Basically Available, Soft state, Eventually consistent).
