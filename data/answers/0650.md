## Hints

- Should the frontend send "user X changed field Y" to an audit endpoint after saving? Why not?
- The history says `countryId: 17 → 23`. What does a compliance officer need to see instead, and what if country 17 has since been renamed?
- A record has 4,000 history entries. How do you show and filter them?
- Who may see the audit log, and what about sensitive fields such as a PESEL number in a diff?
- Two users edit the same record at the same time. How does that relate to the audit trail?

## Answer

> The backend records audit events. The frontend only displays them, because a client can't be trusted to report its own changes. An event says who did what to which entity, when and from where, with old and new values per field, and ideally a reason and a request or correlation id. The UI has two views: a per-record timeline ("History" tab) and a global audit log (a server-side grid filtered by date, user, entity and action). Diffs need readable labels: field names, formatted values, and dictionary ids turned into the label valid at that time. Audit is read-only, permission-controlled, with sensitive values masked and times shown with their time zone.

**Who writes the audit trail.** The server, in the same transaction as the change: an explicit audit table written by the application or domain events, database triggers, SQL Server temporal (system-versioned) tables, or change data capture. Imports, API integrations and batch jobs must be audited the same way as UI edits. Record the **source** (UI, import #651, API, system job).

**An audit event**

```ts
type AuditEvent = {
  id: string;
  occurredAt: string;                 // UTC ISO timestamp
  actor: { id: string; displayName: string };   // name snapshot: people get renamed or leave
  action: 'create' | 'update' | 'delete' | 'restore' | 'approve' | 'export';
  entity: { type: 'customer'; id: string; label: string };
  changes: { field: string; old: unknown; new: unknown; oldLabel?: string; newLabel?: string }[];
  reason?: string;                    // required for some actions, e.g. overriding a risk score
  source: 'ui' | 'import' | 'api' | 'job';
  correlationId: string;              // ties together everything one request changed
};
```

No-op saves shouldn't create events. Changes to several related records in one action share a `correlationId`, so the UI can group them.

**Per-record timeline**

- Newest first, grouped by event: "Anna Nowak, 14 Nov 2026 10:42 (CET), via Import #381".
- Each change as **Field: old → new**, with field labels from the same config as the edit form, so names match what users see.
- Values formatted by type: dates and money (#630), booleans as Yes/No, enums and dictionary ids as labels (#652). Store the label snapshot in the event (`oldLabel`/`newLabel`) or resolve ids against the dictionary *as of that date*. Otherwise renaming a dictionary entry rewrites history.
- Long text: an inline word diff (the `diff` library). Lists: "added: …, removed: …" rather than two JSON blobs.
- Paginate or load more (`useInfiniteQuery`). Filter by field ("show only changes to the limit") and by user.
- Useful extras: "view the record as it was on…" (a point-in-time snapshot) and "compare version 12 with 15".

**Global audit log.** A server-side grid (#646): columns for time, user, action, entity (linked to the record), changed fields and source. Filters for a date range (required, so nobody loads ten years by accident), user, entity type and action. Export for auditors, itself audited (an "export" event). Filters belong in the URL so an investigation can be shared (#503).

**Implementation notes**

- One `FieldFormatter` registry per entity (`{ limit: { label: 'Credit limit', format: money } }`), shared by the form, the grid and the history view.
- Unknown fields (added later or removed) fall back to the raw key and value instead of crashing; old events must keep rendering after the model changes.
- Time: store UTC, show the user's local time with a time zone label, and the exact ISO timestamp in a tooltip.
- Unit-test the formatter and diff rendering with fixtures. Snapshot tests are fine for this one.

**Permissions and privacy**

- Viewing the audit log is its own permission. The backend filters events to the records the user may see (#622). Hiding a tab in the UI isn't access control (#522).
- Mask sensitive values in diffs (PESEL, account numbers): "changed" without old and new values, unless the user has a stronger permission.
- No edit or delete actions in the UI. Immutability is enforced in the backend and database (append-only table, restricted grants). Retention follows the regulation, not convenience.
- Some regulations also require auditing **reads** of sensitive records. That's a backend concern, but the UI may need to show it.

**Concurrency.** Use optimistic locking (a `version` or ETag sent with each save). If the record changed since the user opened it, the API returns `409 Conflict`. The UI then shows who changed what using the same history data ("Jan Kowalski changed the limit 2 minutes ago") and lets the user reload or reapply. This prevents silent lost updates, which an audit trail would otherwise faithfully record.

**Follow-up:** "Temporal tables or an explicit audit table?" Temporal tables capture every row version automatically, but they don't know *who* or *why* without extra columns, and they're per table rather than per business action. An explicit, application-written audit event carries business meaning (action, reason, correlation). Many systems use both: temporal tables as a safety net, events for the UI.
