## Hints

- Which parts of the request determine whether two users get the same cached copy?
- What should happen to cached pages right after you publish an edit to an article?
- Why would a CDN cache a response for an hour while the browser only caches it for a minute?

## Answer

A CDN runs caches in many points of presence (PoPs) near users. On a request it builds a **cache key**, serves a stored copy on a hit, and otherwise forwards to the origin (often through an **origin shield** tier, so the origin sees one request per region instead of one per PoP).

**Cache key** – by default host + path + query string. Tune it:

- Ignore irrelevant query params (`utm_*`, `fbclid`) to raise hit ratio.
- Include only the headers that really change the response (`Accept-Language`, device class). `Vary: Cookie` or `Vary: Authorization` usually destroys the hit ratio.
- Normalize (lowercase, sorted params) to avoid duplicate entries.

**Controlling TTLs separately per layer:**

```http
Cache-Control: public, max-age=60
CDN-Cache-Control: max-age=3600, stale-while-revalidate=86400
Cache-Tag: product-42, category-shoes
```

`s-maxage` or targeted headers like `CDN-Cache-Control` (RFC 9213) let the CDN keep content longer than browsers, because you **can purge the CDN but not users' browsers**.

**Invalidation options:**

- **Versioned URLs** for assets – never purge, just reference a new file.
- **Purge by URL** – simple, but you must know every affected URL.
- **Purge by tag / surrogate key** – tag responses with entity ids, then purge `product-42` on update; all pages showing that product are invalidated together (Fastly, Cloudflare, Akamai support this).
- Short TTL + `stale-while-revalidate` when exact freshness isn't critical.

**Dynamic content:** cache anonymous HTML/API responses at the edge with short TTLs; serve the personalized parts separately (client fetch or edge composition). Use `stale-if-error` to keep serving during origin outages.

Pitfalls: caching `Set-Cookie` responses, caching error pages for long, and forgetting that cache keys must include anything that changes the content – or users see each other's data.
