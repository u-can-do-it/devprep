## Hints

- Can you filter on `COUNT(*)` before the rows have been grouped?
- Why can't you reference a `SELECT` alias inside `WHERE`?
- Which clause would you use to drop rows early so less data gets grouped?

## Answer

`WHERE` filters **individual rows before grouping**; `HAVING` filters **groups after aggregation**. That's why aggregates like `SUM()` or `COUNT()` are allowed in `HAVING` but not in `WHERE`.

```sql
SELECT customer_id, SUM(total) AS revenue
FROM orders
WHERE status = 'paid'              -- row filter
  AND created_at >= '2026-01-01'
GROUP BY customer_id
HAVING SUM(total) > 1000           -- group filter
ORDER BY revenue DESC
LIMIT 10;
```

**Logical evaluation order** (the engine may physically reorder, but the result must match this):

1. `FROM` / `JOIN` – build the row set
2. `WHERE` – filter rows
3. `GROUP BY` – form groups
4. `HAVING` – filter groups
5. `SELECT` – compute expressions, window functions, aliases
6. `DISTINCT`
7. `ORDER BY`
8. `LIMIT` / `OFFSET`

Consequences:

- A column alias from `SELECT` can't be used in `WHERE` (it doesn't exist yet), but it can be used in `ORDER BY`.
- Window functions are computed in step 5, so you can't filter on them in `WHERE` – wrap the query in a CTE or subquery.
- Put non-aggregate conditions in `WHERE`, not `HAVING`: filtering early means fewer rows to group and lets the planner use indexes.
