## Hints

- Why can a bundler remove unused exports from ES modules but not from `require()` calls?
- What does `"sideEffects": false` in a package's `package.json` promise?
- You import one icon. Why might all 2,000 icons end up in the bundle?

## Answer

**Tree shaking** is dead-code elimination for modules: the bundler includes only the exports that are actually imported and drops the rest.

It works because **ES module** imports and exports are **static**: `import { debounce } from 'lodash-es'` can be analysed at build time without running code. Then the minifier removes code that's never referenced.

**What prevents it:**

- **CommonJS:** `require()` and `module.exports` are dynamic, so the bundler must keep the whole module. `import { debounce } from 'lodash'` pulls in all of lodash; `lodash-es` or `lodash/debounce` doesn't.
- **Side effects:** if a module might do something on import (patch a prototype, register a global, import CSS), the bundler must keep it even if nothing is used. Libraries declare `"sideEffects": false` (or a list like `["*.css"]`) in `package.json` to say it's safe to drop unused files.
- **Top-level code that looks impure:** `export const x = createThing()` is kept unless marked `/*#__PURE__*/`.
- **Barrel files** (`index.ts` re-exporting everything) without `sideEffects: false` drag in whole folders, and they also slow down dev servers and tests.
- **Dynamic access** such as `import * as icons` followed by `icons[name]`: the bundler can't know which ones you use.
- Transpiling ESM to CommonJS too early (Babel `modules: 'commonjs'`, an old library build).

**Finding out what makes a bundle big:**

- **Visualise it:** `rollup-plugin-visualizer` (Vite), `webpack-bundle-analyzer`, `@next/bundle-analyzer`, or `source-map-explorer` on the output.
- **Chrome DevTools → Coverage** shows how much of each downloaded file actually runs on a page.
- Check package cost before adding a dependency (pkg-size, bundlephobia), and look for **duplicate versions** of the same library (`npm ls react`, `pnpm why`).
- Lighthouse's "Reduce unused JavaScript" audit.
- **Guard it in CI** with a size budget (`size-limit`, bundler warnings) so regressions fail the pull request.

**Common fixes:** replace heavy libraries (moment → `date-fns` or `Intl`), import per-module, **lazy-load** routes and heavy widgets (charts, editors, maps) with `import()`, move work to the server (Server Components ship no JS for server-only code), and drop polyfills for browsers you no longer support.

**Follow-up:** a library is ESM and marks `sideEffects: false`, but importing one function still adds 80 KB. What would you investigate?
