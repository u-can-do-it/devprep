## Hints

- What does `z.infer<typeof schema>` give you, and how are the input and output types different once you use `.transform()` or `z.coerce`?
- `parse` or `safeParse`: which one do you use in a form, and which in an API handler?
- How do you validate that `endDate` is after `startDate`, and attach the error to the right field?
- The server says "this NIP number already exists". How does that message end up under the right input?
- Where does the schema live so that the React form and the Fastify/tRPC endpoint use the same one?

## Answer

> TypeScript types disappear at run time, so form and API input still has to be validated. A Zod schema gives you both a runtime validator and a type, and in a full-stack app the same schema validates the React Hook Form and the server request. Input and output types differ when the schema coerces or transforms values. `parse` throws, while `safeParse` returns a result. Map server errors back with `setError` so they show under the right field. Only the server can check things like uniqueness and permissions.

TypeScript types disappear at runtime (#182), so input from forms and APIs must be validated. **Zod** describes the shape once and gives you both a **runtime validator** and a **TypeScript type**. In a full-stack TypeScript app the same schema validates the form in React and the request on the server.

**Schema in a shared library** (`libs/shared/schemas`, #616):

```ts
import { z } from 'zod';

export const offerItemSchema = z.object({
  name: z.string().trim().min(1, 'Required'),
  quantity: z.coerce.number().int().positive(),               // inputs give strings; coerce to number
  unitPrice: z.string().regex(/^\d+(\.\d{1,2})?$/, 'Max 2 decimals'),   // keep money as a string, not float (#630)
});

export const offerSchema = z.object({
  clientId: z.string().uuid(),
  nip: z.string().regex(/^\d{10}$/, 'NIP has 10 digits'),
  validFrom: z.coerce.date(),
  validTo: z.coerce.date(),
  items: z.array(offerItemSchema).min(1, 'Add at least one item'),
  notes: z.string().max(2000).optional(),
}).refine((o) => o.validTo > o.validFrom, { message: 'Must be after the start date', path: ['validTo'] });

export type OfferInput = z.input<typeof offerSchema>;     // what the form holds (strings for numbers/dates)
export type Offer = z.output<typeof offerSchema>;         // what the server gets after parsing (= z.infer)
```

**Core API:**

- `schema.parse(x)` returns typed data or **throws** a `ZodError`; `safeParse(x)` returns `{ success, data | error }` without throwing. Use `safeParse` where you branch on the result, `parse` where an error handler maps the exception to a 400.
- Objects **strip unknown keys** by default (good against mass assignment, #372); `z.strictObject` / `.strict()` rejects them instead.
- `refine` for one rule, `superRefine` for several issues with custom paths; `z.discriminatedUnion('type', [...])` for "company vs private person" forms (#27).
- `transform` changes the output type (trim, parse, normalize), which is why input and output types differ.
- `.extend()`, `.pick()`, `.omit()`, `.partial()` to derive "create", "update" (`partial`) and "filter" schemas from one base.
- Zod 4 is faster and smaller, adds top-level formats like `z.email()`, and `z.flattenError(err)` / `z.treeifyError(err)` to turn errors into field maps.

**React Hook Form with the schema:**

```tsx
const form = useForm<OfferInput, unknown, Offer>({
  resolver: zodResolver(offerSchema),
  defaultValues: { items: [{ name: '', quantity: 1, unitPrice: '' }], notes: '' },   // always set defaults
  mode: 'onBlur',
});
const { fields, append, remove } = useFieldArray({ control: form.control, name: 'items' });

const onSubmit = form.handleSubmit(async (offer) => {       // `offer` is the parsed output type
  try {
    await createOffer.mutateAsync(offer);
  } catch (e) {
    for (const [field, msg] of Object.entries(fieldErrorsFrom(e))) form.setError(field as any, { message: msg });
    if (!hasFieldErrors(e)) form.setError('root.server', { message: 'Could not save, try again' });
  }
});

<input {...form.register('nip')} aria-invalid={!!form.formState.errors.nip} />
{form.formState.errors.nip && <p role="alert">{form.formState.errors.nip.message}</p>}
<button disabled={form.formState.isSubmitting}>Save</button>
```

- RHF keeps inputs **uncontrolled** (`register`), so typing doesn't re-render the whole form (#36, #213). Wrap third-party controlled inputs (date pickers, comboboxes) in `<Controller>`.
- `useFieldArray` handles dynamic rows like offer items; use `field.id` as the key, not the index (#32).
- Show server-side errors with `setError`: field errors under fields, others under `root`. Make errors accessible (#287).
- `reset(data)` after loading an entity for editing; `formState.isDirty` to warn about unsaved changes.

**On the server, the same schema:**

```ts
// tRPC (#617)
create: protectedProcedure.input(offerSchema).mutation(({ input }) => ...)
// Fastify with fastify-type-provider-zod (#618)
app.post('/offers', { schema: { body: offerSchema } }, async (req) => create(req.body))
```

Return validation errors in a predictable shape (field path → message, e.g. in Problem Details, #353) so the frontend can map them back with `setError`.

**What only the server can check:** uniqueness (the NIP exists), permissions, references to other records, and anything depending on current data. Client validation is for UX; the server is the authority (#48).

**Follow-up:** the form has a number input, and an empty field turns into `0` instead of "Required". Why, and how do you fix it? (`z.coerce.number()` calls `Number('')`, which is `0`. Convert empty strings to `undefined` before converting the rest: `z.preprocess((v) => (v === '' || v == null ? undefined : Number(v)), z.number({ error: 'Required' }))`, or use a number field component that stores `undefined` for empty input.)
