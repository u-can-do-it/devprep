## Hints

- Where should a database URL live so the same build can run in staging and production?
- What happens to files written to local disk when a container is replaced?
- Why should an app write logs to stdout instead of managing log files?

## Answer

The **Twelve-Factor App** is a set of principles (from Heroku, now community-maintained) for building apps that deploy and scale cleanly on cloud platforms. In short:

1. **Codebase:** one repo per app, many deploys.
2. **Dependencies:** declared explicitly (lockfiles), never assumed on the host.
3. **Config:** stored in the environment, separate from code.
4. **Backing services** (DB, cache, queue): attached resources, swappable through config.
5. **Build, release, run:** strictly separated stages. A release is build + config.
6. **Processes:** stateless, share-nothing. State lives in backing services.
7. **Port binding:** the app is self-contained and exports HTTP on a port.
8. **Concurrency:** scale out by running more processes.
9. **Disposability:** fast startup and graceful shutdown on `SIGTERM`.
10. **Dev/prod parity:** keep environments as similar as possible.
11. **Logs:** event streams to stdout. The platform collects them.
12. **Admin processes:** one-off tasks (migrations) run with the same code and config.

**Still most important today** (containers, Kubernetes, serverless all assume them):
- **Config in the environment** (plus a secret manager): build once, promote the same artifact.
- **Stateless processes:** no in-memory sessions or local uploads. Use Redis or object storage, so any instance can serve any request and autoscaling works.
- **Disposability:** handle `SIGTERM`, drain connections, keep startup fast.
- **Logs to stdout** in structured form.
- **Dev/prod parity** through Docker Compose and the same database engine locally.

**Where it has aged:** it predates observability (traces, metrics), secret managers, and modern concerns like OIDC or workload identity, so treat it as a foundation rather than a complete checklist.
