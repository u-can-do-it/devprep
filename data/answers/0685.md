## Hints

- How many times will iOS show the system permission dialog for the camera?
- What must be in `Info.plist` before you may ask for the camera at all?
- The user denied the permission last week. What can the app do now?

## Answer

> A permission has two parts. You declare it in the native project (a usage description on iOS, a manifest entry on Android), and you ask for it at runtime when the feature is used. The system dialog is a scarce resource: iOS shows it once, and Android stops showing it after the user refuses twice. So explain first, ask in context, and handle three results: granted, denied but askable, and blocked, where the only path is the Settings app.

**1. Declare**

- **iOS:** a purpose string in `Info.plist`, such as `NSCameraUsageDescription`. Without it the app crashes when it asks, and a vague text ("needs camera") gets the app rejected in review.
- **Android:** `<uses-permission>` in the manifest.
- With Expo, both come from config plugins in `app.json` (#676). Remove permissions that libraries add but you don't use.

**2. Ask at runtime**

```tsx
function Scanner() {
  const [permission, requestPermission] = useCameraPermissions();

  if (!permission) return null;                              // still loading
  if (permission.granted) return <CameraView style={{ flex: 1 }} />;

  if (permission.canAskAgain) {
    // Our own screen first; the system dialog appears only after the user taps "Continue"
    return <Explain text="Scan the QR code on your ticket" onContinue={requestPermission} />;
  }

  return (
    <Blocked
      text="Camera access is turned off for this app."
      onOpenSettings={() => Linking.openSettings()}
    />
  );
}
```

**States**

| State | Meaning | What to do |
|---|---|---|
| Undetermined | never asked | explain, then ask |
| Granted | allowed | use the feature |
| Denied, can ask again | Android, after the first refusal | explain better, ask once more |
| Blocked | iOS after any refusal; Android after the second | offer a button to Settings, or an alternative |
| Limited | partial access | work with what you got |

**Partial access**

- **Photos:** the user can share only selected photos.
- **Location:** approximate instead of precise, and "while using the app" instead of "always". Background location is a separate, later request, and the stores ask you to justify it (#704).
- **One-time grants:** "only this time" expires when the app closes.

**Good practice**

- **Ask in context,** at the moment the user starts the feature. Never show a wall of dialogs at first launch.
- **Pre-prompt:** show your own explanation before the system dialog, so the one real dialog isn't wasted on a confused "Don't allow".
- **Don't block the app.** A refused permission disables one feature. Offer another way: type the code instead of scanning it, enter the address by hand.
- **Check again when the app returns to the foreground.** The user can change permissions in Settings at any time.
- **Ask for less.** The system photo picker and document picker need no permission, because the user picks the files. Use them instead of full library access where you can.

**Notifications** follow the same model on iOS and on Android 13 and later (#683).

**Testing**

Reset by uninstalling the app, or in the simulator's settings. Test the full matrix: first ask, refusal, block, and enabling it later from Settings while the app is in the background.

**Libraries**

Expo modules each expose their own permission hooks and methods. `react-native-permissions` gives one API for all of them in apps without Expo modules.

**Follow-up:** your analytics show that 60% of users refuse the location prompt on first launch. What do you change? (Move the request to the moment location is needed, add a pre-prompt that explains the benefit, ask for "while using" only, and let the user type a city instead.)
