## Hints

- If you switched from PostgreSQL to another database, how much of your business logic would need to change?
- In which direction should source-code dependencies point: domain to infrastructure, or the reverse?
- How would you unit-test a "place order" use case without starting a database or HTTP server?

## Answer

> When business rules live inside controllers and ORM code, they're hard to test and hard to change. Hexagonal and clean architecture keep the core business logic as plain code that knows nothing about frameworks or databases. The core defines interfaces, called ports, for what it needs, and adapters at the edges implement them, like a Postgres repository or an HTTP controller. Dependencies always point inward, toward the core. This makes testing with fakes easy, but it adds indirection that simple CRUD services often don't need.

**Hexagonal architecture (ports and adapters)** and **clean architecture** share one core idea: **keep business logic independent of frameworks, databases and delivery mechanisms.**

- **Domain / application core:** entities, business rules, use cases. Plain code with no Express, FastAPI, ORM or HTTP types.
- **Ports:** interfaces the core defines for what it needs (`OrderRepository`, `PaymentGateway`) or what it offers (`PlaceOrder` use case).
- **Adapters:** implementations at the edges. **Driving adapters** call the core (HTTP controllers, CLI, queue consumers). **Driven adapters** are called by it (Postgres repository, Stripe client, email sender).
- **Dependency rule:** dependencies point **inward**. Infrastructure depends on the core, never the reverse (dependency inversion).

```ts
// core: port + use case
export interface OrderRepository {
  save(order: Order): Promise<void>;
}

export class PlaceOrder {
  constructor(private repo: OrderRepository, private payments: PaymentGateway) {}
  async execute(cmd: PlaceOrderCommand) {
    const order = Order.create(cmd);          // business rules
    await this.payments.charge(order.total);
    await this.repo.save(order);
  }
}

// adapter (infrastructure)
export class PgOrderRepository implements OrderRepository { /* SQL here */ }
```

**What it solves:**
- **Testability:** use cases are tested with in-memory fakes. Fast and deterministic.
- **Replaceability:** swap a DB, payment provider or framework by writing a new adapter.
- **Clarity:** business rules aren't scattered across controllers and ORM hooks.

**Trade-offs:** more interfaces, mapping and indirection. For simple CRUD services it's often overkill. Apply it where domain logic is rich. It pairs naturally with DDD (domain model, bounded contexts).
