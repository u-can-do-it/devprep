## Hints

- If every micro-frontend is an npm package installed by the host, can teams still deploy independently?
- Which approach gives the strongest isolation, and what does it cost in UX and accessibility?
- What's the simplest split that needs no runtime integration at all?

## Answer

Composition is about **where and when** the pieces are put together: at build time, on the server or edge, or in the browser.

| approach | independent deploy | isolation | performance and SEO | complexity |
|---|---|---|---|---|
| Build-time (npm packages) | no | low | best: one optimized bundle | low |
| Route-level (reverse proxy) | yes | high | good, but a full reload between apps | low |
| Server or edge (SSI, ESI, fragments) | yes | medium | good: HTML is ready for SEO | medium to high |
| Runtime (Module Federation, single-spa) | yes | low to medium | good with shared deps | high |
| Iframes | yes | very high | poor: duplicated loads, weak SEO | low to medium |
| Web Components | yes | medium (shadow DOM) | depends on how frameworks are bundled | medium |

**Build-time:** each part is published as a package and the host installs it. You get type safety, deduplication and one bundle. But every change requires a host release in lockstep, so it's really a modular monolith with extra publishing steps.

**Route-level (link-based):** a reverse proxy or CDN sends `/checkout/*` to the checkout app and `/account/*` to the account app. Navigation between them is a full page load. Isolation is strong and coupling is minimal. Shared chrome (header, footer) comes from a package or a server fragment. **Next.js Multi-Zones** is this pattern. It's often the right first step.

**Server or edge composition:** a layout server or CDN assembles HTML fragments from several services: SSI in nginx, **ESI** at the CDN, edge workers, or libraries such as Podium or Tailor. You get fast first paint and good SEO. The costs: each fragment hydrates separately, caching and timeouts per fragment, and coordinating shared assets.

**Client-side runtime:**

- **Module Federation:** loads remote modules and shares dependencies at runtime. Fine-grained (a single component), works best when every part uses the same framework.
- **single-spa:** an orchestrator that mounts and unmounts apps (`bootstrap`/`mount`/`unmount` lifecycles) by route. Framework-agnostic, usually with **import maps**.
- **Native ES modules plus import maps:** no bundler-specific runtime, but you manage sharing yourself.

**Iframes:** the strongest isolation (JS, CSS, security origin), useful for third-party or legacy embeds. Downsides: sizing, modals can't escape the frame, deep linking and history are awkward, accessibility and SEO suffer, communication only through `postMessage`, and every frame loads its own runtime.

**Web Components:** each part is a custom element. The contract is framework-neutral: attributes and properties go in, DOM events come out. Shadow DOM isolates styles. Downsides: SSR needs declarative shadow DOM, every component may bundle its own framework, and the frameworks' interop differs (React 19 finally passes properties and listens to custom events properly).

```html
<mfe-cart-widget user-id="42"></mfe-cart-widget>
<script>
  document.querySelector('mfe-cart-widget')
    .addEventListener('cart:checkout', (e) => navigate('/checkout', e.detail));
</script>
```

**How to choose:** start with a **route-level split**. Add runtime composition only where several teams really need to render into the same page. Use iframes for untrusted or legacy content. Use server composition when SEO and first paint matter more than in-page interactivity.
