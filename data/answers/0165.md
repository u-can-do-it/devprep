## Hints

- What happens at runtime when code outside the class tries to read a `#field`?
- What is left of TypeScript's `private` keyword in the emitted JavaScript?
- How do you check whether an object has a given private field?

## Answer

**`#private` fields and methods** are a JavaScript language feature (ES2022). The engine enforces them: outside the class body they can't be read or written, not even through reflection.

```js
class Account {
  #balance = 0;
  static #count = 0;
  static { /* static initialization block */ }

  deposit(n) { this.#validate(n); this.#balance += n; }
  #validate(n) { if (n <= 0) throw new RangeError('positive only'); }
  static isAccount(obj) { return #balance in obj; } // brand check
}
const a = new Account();
a.#balance;      // SyntaxError: can't even be written outside the class
a['#balance'];   // undefined: it's not a normal property
```

**TypeScript `private`** is checked **only at compile time**. After compilation it's an ordinary public property, so `(obj as any).secret` or `obj['secret']` works, and it shows up in `Object.keys` and `JSON.stringify`.

| | `#field` | TS `private` |
|---|---|---|
| Enforced | at runtime | at compile time only |
| Visible to `Object.keys` / JSON | no | yes |
| Accessible from subclasses | no | no (`protected` allows it) |
| Works with `Proxy` | no: method calls on the proxy throw a TypeError | yes |
| Testing / debugging | harder | easier |

**When to use which:** use `#private` for real encapsulation in libraries or security-sensitive state. TS `private`/`protected` is fine for app code where team convention is enough, and when tools (mocks, proxies, ORMs, serializers) need to reach the property.

**Gotchas:**

- Private fields are per class. A subclass can't access its parent's `#fields`.
- `Proxy` wrappers break `#field` access, which affects some reactive libraries.
- Class fields are initialized after `super()` returns, so a parent constructor can't see the subclass's fields.
