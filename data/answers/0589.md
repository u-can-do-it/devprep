## Hints

- With `$"Order {id} failed"`, what can a log backend search on later, and what happens if the level is disabled?
- How would you attach an order id to every log line written while one request is processed?
- How do logs, metrics and traces connect to each other in OpenTelemetry?

## Answer

**`ILogger<T>`**

Inject `ILogger<T>`; `T` becomes the **category** (the full class name), which you can filter on in configuration. Providers (console, OpenTelemetry, Serilog and others) decide where logs go.

```csharp
public sealed class OrderService(ILogger<OrderService> log)
{
    public void Ship(int orderId, string carrier) =>
        log.LogInformation("Shipping order {OrderId} with {Carrier}", orderId, carrier);
}
```

**Message templates, not string interpolation**

```csharp
log.LogInformation($"Shipping order {orderId}");          // bad
log.LogInformation("Shipping order {OrderId}", orderId);  // good
```

- The template keeps `OrderId` as a **structured property**, so you can query `OrderId = 42` in Seq, Elastic or Application Insights. Interpolation produces one flat string.
- Interpolation builds the string even when the level is disabled; the template is only formatted if the log is written.
- Placeholders are matched by **position**, not name. Analyzers (CA2254) warn about non-constant templates.

For hot paths, use the **`[LoggerMessage]` source generator**: it creates a strongly typed method with no boxing and an `IsEnabled` check.

```csharp
public static partial class Log
{
    [LoggerMessage(Level = LogLevel.Warning, Message = "Payment {PaymentId} declined: {Reason}")]
    public static partial void PaymentDeclined(this ILogger logger, string paymentId, string reason);
}
```

**Log levels**

`Trace` < `Debug` < `Information` < `Warning` < `Error` < `Critical`. Set them per category in `appsettings.json`:

```json
{ "Logging": { "LogLevel": { "Default": "Information", "Microsoft.AspNetCore": "Warning" } } }
```

Use `Error` for failures someone must look at and `Warning` for degraded but handled situations. Log an exception by passing it as the first argument (`LogError(ex, "...")`) so the stack trace is kept as a field.

**Scopes**

A scope adds properties to every log line inside it (needs a provider with scopes enabled):

```csharp
using (log.BeginScope(new Dictionary<string, object> { ["OrderId"] = orderId }))
{
    log.LogInformation("Reserving stock");   // includes OrderId
    await payments.ChargeAsync(...);          // logs in called services too
}
```

ASP.NET Core already adds a request scope with `RequestId` and the trace id.

**OpenTelemetry**

- **Traces:** ASP.NET Core, `HttpClient` and many database drivers create `Activity` spans automatically; the trace context is propagated in the `traceparent` header across services.
- **Metrics:** built-in `System.Diagnostics.Metrics` instruments (request duration, active requests, GC, thread pool) plus your own `Meter` counters.
- **Logs:** the OpenTelemetry logging provider exports `ILogger` output and attaches the current `TraceId` and `SpanId`, so you can jump from a log line to its trace.

```csharp
builder.Services.AddOpenTelemetry()
    .WithTracing(t => t.AddAspNetCoreInstrumentation().AddHttpClientInstrumentation())
    .WithMetrics(m => m.AddAspNetCoreInstrumentation().AddRuntimeInstrumentation())
    .UseOtlpExporter();   // to a collector, Grafana, Jaeger, Datadog...
builder.Logging.AddOpenTelemetry(o => o.IncludeScopes = true);
```

**Never log** passwords, tokens, full card numbers or personal data in plain text; the `Microsoft.Extensions.Compliance.Redaction` package can redact classified fields.

**Follow-up:** logging made a hot endpoint 15% slower. What do you check? (Debug-level calls with interpolation or expensive arguments evaluated anyway, too many logs per request, synchronous console output; use templates or `[LoggerMessage]`, raise levels, and use async/batched exporters.)
