## Hints

- Can you hold a single ACID transaction across the order service's DB, the payment provider and the inventory service?
- If step 3 of 4 fails, how do you undo steps 1 and 2 when they've already committed?
- Should one coordinator drive the flow, or should each service react to the previous one's events?

## Answer

With a database per service, there's no shared ACID transaction. **Two-phase commit (2PC)** exists but is a poor fit: it blocks on a coordinator, needs every participant to support it (Stripe doesn't), and hurts availability.

A **saga** splits the business transaction into a sequence of **local transactions**, each committing in its own service. If a step fails, previously completed steps are undone with **compensating actions**: semantic undos, not rollbacks.

Example, placing an order:

| Step | Action | Compensation |
|---|---|---|
| 1 | Order: create `PENDING` | mark `CANCELLED` |
| 2 | Inventory: reserve items | release reservation |
| 3 | Payment: charge card | refund |
| 4 | Order: mark `CONFIRMED` | — |

**Two styles:**
- **Choreography:** services react to each other's events (`OrderCreated` triggers a stock reservation, which emits `StockReserved`, and so on). Loosely coupled and simple for 2–3 steps, but the flow becomes implicit and hard to follow or debug as it grows.
- **Orchestration:** a central orchestrator (a state machine) tells each service what to do and handles failures. The flow is explicit, observable and testable. Durable workflow engines such as **Temporal**, AWS Step Functions or Restate persist saga state and handle retries and timeouts.

```ts
// Temporal-style orchestration (simplified)
export async function placeOrder(order: Order) {
  await reserveStock(order);
  try {
    await chargeCard(order);
  } catch (err) {
    await releaseStock(order);   // compensation
    throw err;
  }
  await confirmOrder(order);
}
```

**Design requirements:**
- every step and compensation must be **idempotent** (they'll be retried),
- reliable messaging (**transactional outbox**) so state changes and events don't diverge,
- design for **lack of isolation**: other requests can see intermediate states. Use explicit states (`PENDING`), semantic locks, and reorder steps so the hard-to-compensate ones (sending an email, shipping) come last,
- some actions can't be compensated, so make them the final "pivot" step or confirm before executing.

**Follow-up:** "Why not just use one database?" Often that *is* the right answer. Sagas are the cost of splitting data across services.
