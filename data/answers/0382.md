## Hints

- Which layer cares about MAC addresses, which about IP addresses, and which about ports?
- Where would you put HTTP, TLS, TCP and Ethernet?
- What can a load balancer see if it only reads TCP, compared with one that reads HTTP?

## Answer

Both are **layered models**: each layer offers a service to the one above and wraps (encapsulates) its data in its own header.

**OSI (7 layers, conceptual):**

| # | Layer | Examples |
|---|---|---|
| 7 | Application | HTTP, DNS, SMTP |
| 6 | Presentation | encoding, compression, encryption (TLS is often placed here) |
| 5 | Session | session setup/teardown |
| 4 | Transport | TCP, UDP (ports, reliability) |
| 3 | Network | IP, ICMP, routing |
| 2 | Data link | Ethernet, Wi-Fi, MAC addresses, switches |
| 1 | Physical | cables, radio, signals |

**TCP/IP (4 layers, what the internet actually uses):** Application (OSI 5–7) / Transport (4) / Internet (3) / Link (1–2).

An HTTP request is wrapped like this: HTTP message, inside a TLS record, inside a TCP segment (ports), inside an IP packet (addresses), inside an Ethernet/Wi-Fi frame.

**Why "L4" and "L7" still matter:** the OSI numbers became shorthand for what a component can see and do:

- **L3/L4 devices** (firewalls, NAT, AWS NLB) see IPs and ports. They are fast and protocol-agnostic but can't route by URL or header.
- **L7 devices** (reverse proxies, ALB, API gateways, WAFs) understand HTTP: route by path/host, rewrite headers, terminate TLS, cache, and block malicious payloads.

Also useful for debugging: work up the stack. Is DNS resolving? Is the IP reachable (`ping`, `traceroute`)? Is the port open (`nc -vz host 443`)? Does TLS succeed (`openssl s_client`)? What does HTTP return (`curl -v`)?

**Follow-up:** Where does QUIC fit? It runs over UDP but provides transport features (streams, reliability, encryption) itself, which blurs the classic layers.
