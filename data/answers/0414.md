## Hints

- What can you do when you're halfway through a change and need to switch branches for an urgent fix?
- Are untracked (new) files stashed by default?
- What's the difference between getting stashed changes back with `pop` and with `apply`?

## Answer

`git stash` saves your uncommitted changes (staged and unstaged) on a stack and resets your working directory to a clean `HEAD`. You can then switch branches, pull, or test something, and restore the changes later.

```bash
git stash push -m "wip: filter UI"   # save changes with a description
git stash push -u                     # also include untracked files
git stash list                        # stash@{0}, stash@{1}, ...
git stash show -p stash@{0}           # inspect a stash
git stash pop                         # apply the latest and remove it
git stash apply stash@{1}             # apply but keep it on the stack
git stash drop stash@{1}              # delete one
git stash branch fix-filters          # new branch from the stash's base commit
```

**Typical uses:**
- an urgent hotfix comes in while you're mid-feature,
- `git pull` refuses because local changes would be overwritten,
- you want to quickly check whether a bug exists without your changes.

**Gotchas:**
- Untracked files are **not** stashed unless you pass `-u` (and ignored files need `-a`).
- `pop` can conflict. If it does, the stash is **kept**, so resolve the conflict and then drop it.
- Stashes are local and easy to forget. For longer interruptions, a WIP commit on the branch or a second working tree (`git worktree add ../hotfix main`) is often clearer.

**Follow-up:** "I dropped a stash by mistake. Can I get it back?" Usually yes. Its commit is unreachable but still exists for a while, so `git fsck --unreachable | grep commit` can find it.
