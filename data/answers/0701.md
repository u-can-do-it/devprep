## Hints

- Why can't you stay on the same React Native version for three years?
- Which dependencies are most likely to block an upgrade: pure JS ones, or ones with native code?
- If the `ios/` and `android/` folders are generated, what is left to merge by hand?

## Answer

> Upgrade regularly and in small steps, because the stores, Xcode, Android and your libraries all move forward. Read the release notes, go one version at a time, update the libraries with native code together with the framework, rebuild from clean, and run a full regression on both platforms in release builds. What breaks is mostly native: build tooling versions, libraries that haven't caught up, and removed or changed APIs. Generated native projects make the framework's own changes nearly free.

**Why you must upgrade**

- **Store rules:** Google Play requires a recent target API level, and Apple requires builds made with a recent Xcode and SDK.
- **New OS versions** change behaviour (edge-to-edge on Android, new lifecycle rules on iOS).
- **Libraries** drop support for old React Native versions, so staying behind blocks bug fixes and security patches.
- **Support window:** only the latest few React Native versions get fixes, and releases come every couple of months. An Expo SDK is supported for a limited time too.

**The process**

1. **Read** the release notes and breaking changes for every version you cross.
2. **One step at a time:** one React Native minor, or one Expo SDK. Skipping versions stacks breaking changes on top of each other.
3. **Check dependencies first.** For each library with native code, find the version that supports the target (changelogs, reactnative.directory). This step decides whether the upgrade is possible now.
4. **Upgrade:**

```bash
npx expo install expo@latest --fix
```

```bash
npx expo-doctor
```

   - **Expo with CNG:** bump the SDK, let `expo install --fix` align library versions, and regenerate the native projects (#676).
   - **Bare project:** use the **Upgrade Helper**, which shows the diff of the app template between two versions (Gradle files, Podfile, `AppDelegate`, `MainApplication`), and apply it to your native files by hand.
5. **Clean build:** reinstall pods, clear Gradle and Metro caches, rebuild both apps.
6. **Fix** compile errors, type errors, failing tests and warnings about deprecated APIs.
7. **Regression test** in release builds on real devices: start, navigation, forms and keyboard, lists, push, deep links, payments, and anything with a native library.
8. **Ship** through internal testing and a staged rollout, and watch crash rates (#687).

**What usually breaks**

| Area | Examples |
|---|---|
| Build tooling | required Xcode, Gradle, Android Gradle Plugin, Kotlin, Node and minimum OS versions change |
| Native libraries | not yet updated, or abandoned; they block everything |
| Removed APIs | `InteractionManager` removed; core `SafeAreaView` deprecated; deep imports from `react-native/Libraries/...` |
| Types | the stricter TypeScript API surfaces errors that were hidden |
| Architecture | libraries that never supported the New Architecture stop working (#693) |
| Behaviour | edge-to-edge layout (#679), keyboard handling, text rendering, the iOS scene lifecycle |
| React | a new React major: removed legacy APIs, stricter effects |
| Patches | `patch-package` patches no longer apply |
| Tests and tooling | Jest presets and mocks, Metro and Babel config |

**Over-the-air updates:** a new React Native version is a new native runtime. It needs a store release, and updates can't cross that line (#699).

**Reducing the pain**

- Upgrade every release or two. Three small upgrades are much cheaper than one big jump.
- Keep the list of native dependencies short, and prefer well-maintained ones. Review every new native dependency as a long-term commitment.
- Avoid forks and patches. When you must patch, open an upstream pull request and track it.
- Don't edit generated native files. Use config plugins.
- Let a bot (Renovate, Dependabot) open update pull requests, with CI building both platforms.
- Have end-to-end smoke tests, so regression testing isn't all manual (#686).
- Give the upgrade an owner and time in the plan. It is product work, not spare-time work.

**Follow-up:** one unmaintained library with native code blocks the upgrade, and the app depends on it. What are the options? (Find a maintained replacement, use a community fork, patch it and upstream the fix, wrap or rewrite the small part you use as your own module (#700), or remove the feature. Decide by how much of the library you really use.)
