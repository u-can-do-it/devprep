## Hints

- Which layer is closest to the user, and which is closest to the database?
- What is the cost of serving data that's slightly out of date, and who decides if it's acceptable?
- Which is faster: a lookup in process memory or a network call to Redis?

## Answer

**Caching** stores the result of expensive work (a DB query, a computation, a network response) closer to where it's needed, so repeated requests are faster and cheaper. The trade-off is **staleness** and extra complexity around **invalidation**.

**Layers, from user to database:**

1. **Browser cache** – HTTP caching via `Cache-Control`/`ETag`; service workers for offline.
2. **Client-side data cache** – TanStack Query, SWR, Apollo/Relay normalized caches keep API responses in memory.
3. **CDN / edge** – caches static assets and cacheable responses close to users (Cloudflare, CloudFront, Fastly).
4. **Reverse proxy** – Nginx/Varnish in front of app servers.
5. **Application cache**
   - **In-process** (a `Map`/LRU, `functools.lru_cache`) – fastest, but per instance and lost on restart.
   - **Distributed** (Redis/Valkey, Memcached) – shared by all instances.
   - Framework caches like Next.js's `'use cache'` data and route caches.
6. **Database** – its own buffer pool keeps hot pages in RAM; materialized views precompute expensive queries.

```python
from functools import lru_cache

@lru_cache(maxsize=1024)
def exchange_rate(currency: str) -> float:
    return fetch_rate_from_api(currency)   # pure-ish, expensive call
```

**What to cache:** data read often and changed rarely, expensive to compute, and acceptable if slightly stale. **What not to cache** (or cache carefully): per-user sensitive data in shared caches, rapidly changing data like stock levels at checkout.

Measure it: track **hit ratio**, latency, and memory; a cache with a low hit rate only adds complexity.
