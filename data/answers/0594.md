## Hints

- Before attaching any tool, which numbers tell you whether the problem is CPU, the GC, the thread pool or a dependency?
- Latency grows, CPU stays low and the thread pool queue keeps growing. What is the app probably doing?
- How do you tell memory that grows and gets collected from memory that only grows, and how do you find what holds it?

## Answer

Go from cheap to expensive: **metrics → traces → dumps**, with a hypothesis at each step.

**1. Narrow it down with what you already have**

Request duration per endpoint, dependency timings (database, HTTP), container CPU and memory, error rates (OpenTelemetry, #589). Is everything slow or one endpoint? Does it line up with a slow dependency, a deploy or a traffic spike?

**2. Live runtime counters**

```bash
dotnet tool install -g dotnet-counters
dotnet-counters monitor -p <pid> --counters System.Runtime,Microsoft.AspNetCore.Hosting
```

In Kubernetes, run the tools from a sidecar or debug container that shares `/tmp` (the diagnostic port), or use `dotnet-monitor`.

| What you see | Likely cause |
|---|---|
| Low CPU, high latency, thread pool queue length growing, thread count creeping up | **thread pool starvation**: blocking calls (`.Result`, `.Wait()`, sync I/O) |
| High % time in GC, many gen 2 GCs, high allocation rate | allocation-heavy code, large buffers on the LOH (#591) |
| GC heap keeps growing even after gen 2 GCs | managed leak: something holds references |
| Process memory grows, GC heap flat | native leak: undisposed native resources or a native library |
| High CPU | hot code: take a CPU trace |
| High exception count | exceptions used for control flow |

**3. Thread pool starvation**

The pool adds threads only gradually. If requests block threads waiting for I/O (sync-over-async, #574), new requests queue up even though the CPU is idle. Confirm with a stack snapshot: many threads parked in `Task.Wait`, `GetResult` or `Monitor.Wait`.

```bash
dotnet-stack report -p <pid>
```

The fix is async all the way down. Raising `ThreadPool.SetMinThreads` only buys time.

**4. CPU: take a trace**

```bash
dotnet-trace collect -p <pid> --duration 00:00:30 --format Speedscope
```

Open it in speedscope, PerfView or Visual Studio and look for the widest stacks: serialization, regex, LINQ in hot loops, logging, lock contention.

**5. Memory: compare heaps over time**

```bash
dotnet-gcdump collect -p <pid>        # heap graph only, small; open in Visual Studio or PerfView
dotnet-dump collect -p <pid>          # full dump
dotnet-dump analyze <dump-file>
> dumpheap -stat                      # types by count and total size
> dumpheap -mt <method-table>         # instances of one type
> gcroot <address>                    # the chain of references keeping it alive
```

Take two snapshots some minutes apart and compare which types grow. Usual suspects: static or singleton caches without eviction, an `IMemoryCache` without a size limit (#598), event handlers on long-lived objects (#576), captive dependencies (#581), timers. Collecting a gcdump forces a full GC (a pause), and full dumps contain secrets and personal data, so treat them as sensitive.

**6. Benchmark the fix**

```csharp
[MemoryDiagnoser]                          // adds allocated bytes per operation
public class ParseBenchmarks
{
    private const string Line = "2026-10-29;42;ok";

    [Benchmark(Baseline = true)]
    public int Split() => int.Parse(Line.Split(';')[1]);

    [Benchmark]
    public int Span()
    {
        ReadOnlySpan<char> s = Line;
        ReadOnlySpan<char> rest = s[(s.IndexOf(';') + 1)..];
        return int.Parse(rest[..rest.IndexOf(';')]);
    }
}
// BenchmarkRunner.Run<ParseBenchmarks>();  run in Release, without a debugger
```

BenchmarkDotNet handles warm-up, JIT tiering and statistics; a `Stopwatch` loop doesn't. A microbenchmark only proves the function is faster: confirm under a load test and with the same production counters before and after.

**Follow-up:** latency is bad only for the first minutes after each deploy. Why? (Cold start: the JIT starts with unoptimized tier-0 code (#604), caches and connection pools are empty, the thread pool is still ramping up. Mitigate with ReadyToRun, warm-up before the readiness probe passes, and pre-filled caches.)
