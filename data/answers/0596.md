## Hints

- Two users edit the same appointment at once. What does the second `SaveChanges` do by default, and what changes with a concurrency token?
- How many SQL statements does loading 10,000 rows, changing them and calling `SaveChanges` produce, compared with `ExecuteUpdate`?
- Is `FromSql($"... {input}")` injectable? What about `FromSqlRaw`?

## Answer

**1. Optimistic concurrency**

By default the **last write wins**: the second save silently overwrites the first. A **concurrency token** is added to the `WHERE` clause of every `UPDATE` and `DELETE`. If the row changed in the meantime, zero rows match and EF throws `DbUpdateConcurrencyException`.

```csharp
public class Appointment
{
    public int Id { get; set; }
    public DateTime StartsAt { get; set; }
    [Timestamp] public byte[] RowVersion { get; set; } = [];    // SQL Server rowversion, set by the database
}

try
{
    appointment.StartsAt = newStart;
    await db.SaveChangesAsync(ct);    // UPDATE ... WHERE Id = @id AND RowVersion = @originalVersion
}
catch (DbUpdateConcurrencyException ex)
{
    var entry = ex.Entries.Single();
    var current = await entry.GetDatabaseValuesAsync(ct);      // null if the row was deleted
    // return 409 Conflict with the current values, or merge and retry
}
```

- On PostgreSQL with Npgsql, map a `uint` property with `IsRowVersion()` to the `xmin` system column, or keep your own token (`[ConcurrencyCheck]` on a `Guid` you change on every save).
- In an API, the token has to come **from the client**: send it out (a field or an `ETag`), and on update set `entry.Property(a => a.RowVersion).OriginalValue = dto.RowVersion`. Otherwise you only compare against the row you loaded a millisecond ago and miss the other user's edit.
- For hot rows where conflicts are the norm, lock pessimistically (`SELECT ... FOR UPDATE` in a transaction), and let **unique or exclusion constraints** be the final guard against things like double bookings.

**2. Transactions**

One `SaveChanges` call already runs in a transaction. You need an explicit one when several saves or raw SQL must succeed or fail together:

```csharp
var strategy = db.Database.CreateExecutionStrategy();    // required when retry on failure is enabled
await strategy.ExecuteAsync(async () =>
{
    await using var tx = await db.Database.BeginTransactionAsync(ct);
    db.Orders.Add(order);
    await db.SaveChangesAsync(ct);                       // order gets its id
    db.OutboxMessages.Add(OutboxMessage.For(new OrderPlaced(order.Id)));
    await db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);                            // disposing without commit rolls back
});
```

Keep transactions short: no HTTP calls or user input waits inside them.

**3. Bulk changes**

Loading entities and calling `SaveChanges` means one `SELECT` plus one `UPDATE` per row (batched, but still per row). `ExecuteUpdate` and `ExecuteDelete` (EF Core 7+) send **one statement**:

```csharp
await db.Sessions
    .Where(s => s.ExpiresAt < DateTime.UtcNow)
    .ExecuteDeleteAsync(ct);                             // DELETE FROM sessions WHERE ...

await db.Products
    .Where(p => p.CategoryId == categoryId)
    .ExecuteUpdateAsync(s => s.SetProperty(p => p.Price, p => p.Price * 1.1m), ct);
```

They run immediately and bypass the change tracker: entities already loaded in the context are now stale, and `SaveChanges` interceptors, EF-side cascades and concurrency checks don't apply. For inserting very many rows, use the provider's bulk API (`SqlBulkCopy`, Npgsql binary `COPY`) or a bulk extension library.

**4. Raw SQL and injection**

| API | Parameters |
|---|---|
| `FromSql($"...")`, `ExecuteSql($"...")`, `SqlQuery<T>($"...")` | interpolated values become `DbParameter`s: safe |
| `FromSqlRaw(sql, args)`, `ExecuteSqlRaw` | the string is sent as-is: safe only with `{0}` placeholders and separate arguments |

```csharp
var users = await db.Users
    .FromSql($"SELECT * FROM users WHERE email = {email}")    // parameterized
    .ToListAsync(ct);

// db.Users.FromSqlRaw("SELECT * FROM users WHERE email = '" + email + "'")   // SQL injection
```

`FromSql` takes a `FormattableString`, so a pre-built `string` won't compile, which is the point. Identifiers (column names, sort direction) can't be parameters: map them from a whitelist.

**5. When Dapper (or `SqlQuery<T>`) fits better**

Complex hand-written SQL, reporting queries and read models mapped straight to DTOs, where change tracking adds nothing. A common split is EF Core for writes (tracking, concurrency, migrations) and Dapper or `SqlQuery<T>` for heavy reads (#597). `AsNoTracking()` with a projection already gets EF close to Dapper for most reads.

**Follow-up:** two requests book the last free slot at the same moment. How do you prevent a double booking? (Check-then-insert isn't enough. Put a unique or exclusion constraint on the slot and turn the `DbUpdateException` into a 409, or use a concurrency token on the slot row, or lock it with `SELECT ... FOR UPDATE` inside a transaction.)
