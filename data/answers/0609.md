## Hints

- `DateTime.Now` on a server in Frankfurt and on a laptop in Warsaw: are they the same instant, and how would the type tell you?
- "Every Monday at 09:00 Warsaw time": can you store that as UTC?
- How do you unit-test code that does something after 30 days without waiting?

## Answer

**Four questions, four types**

| Question | Type | Example |
|---|---|---|
| When did it happen? (an instant) | `DateTimeOffset`, or `DateTime` with `Kind = Utc` | `2026-10-29T10:15:00+01:00` |
| Which calendar day or clock time, no zone? | `DateOnly`, `TimeOnly` (.NET 6) | birthday, opening hours |
| 09:00 in Warsaw? (local time in a zone) | local `DateTime` + IANA zone id | appointments, recurring schedules |
| How long? | `TimeSpan` | `TimeSpan.FromMinutes(30)` |

**`DateTime` and the `Kind` trap.** A `DateTime` is ticks plus a `Kind` flag: `Utc`, `Local` or `Unspecified`. The flag is easy to lose, and **comparisons ignore it**: a Utc and a Local value for the same instant compare as different, and `ToUniversalTime()` on an `Unspecified` value assumes the machine's local zone, so the result depends on where the code runs. `DateTime.Now` and `TimeZoneInfo.Local` differ per machine, and are usually UTC inside a container.

```csharp
var utc   = DateTime.UtcNow;                            // Kind = Utc
var local = utc.ToLocalTime();                          // Kind = Local, the same instant
Console.WriteLine(utc == local);                        // False: different ticks, Kind ignored

var parsed = DateTime.Parse("2026-10-29T10:15:00");     // Kind = Unspecified
parsed.ToUniversalTime();                               // treats it as the server's local time: wrong on most servers
```

**`DateTimeOffset`** is a `DateTime` plus the UTC offset, so it always names an exact instant; equality and ordering compare the instant, and `.UtcDateTime`/`.ToOffset(...)` convert. Prefer it for timestamps (`CreatedAt`, tokens, logs) and anything that crosses machines. An offset is **not** a time zone: `+02:00` is Warsaw in summer and Cairo all year, and it can't tell you next month's offset.

**Time zones.** `TimeZoneInfo.FindSystemTimeZoneById` accepts IANA ids (`"Europe/Warsaw"`) and Windows ids (`"Central European Standard Time"`) on every OS since .NET 6, converting between them with ICU. Store and send **IANA** ids. Containers need the `tzdata` package (Alpine and chiseled images may lack it) and ICU; with `InvariantGlobalization` the id conversion stops working.

```csharp
var warsaw  = TimeZoneInfo.FindSystemTimeZoneById("Europe/Warsaw");
var instant = new DateTimeOffset(2026, 3, 29, 0, 30, 0, TimeSpan.Zero);           // 00:30 UTC
var wall    = TimeZoneInfo.ConvertTime(instant, warsaw);                           // 01:30 +01:00
warsaw.IsInvalidTime(new DateTime(2026, 3, 29, 2, 30, 0));                         // True: clocks jump 02:00 → 03:00
warsaw.IsAmbiguousTime(new DateTime(2026, 10, 25, 2, 30, 0));                      // True: 02:30 happens twice
```

**Storing times**

- **Instants:** PostgreSQL `timestamptz` (stored as UTC). Npgsql 6+ maps it to `DateTime` with `Kind = Utc` or `DateTimeOffset` with offset zero and **throws** when you write a Local or Unspecified `DateTime`, which flushes out every `DateTime.Now` in the code. SQL Server `datetime2` has no zone, so store UTC by convention, or use `datetimeoffset`.
- **Local schedules** ("every Monday 09:00 Warsaw"): store the local time plus the zone id and compute the instant when you need it. Converting to UTC up front gives the wrong hour after the clocks change and breaks when DST rules change. A booked appointment (#553) is typically stored as the instant **plus** the zone it was booked in, so it can be shown in the patient's and the doctor's local time.
- **Dates without a time:** `DateOnly` ↔ `date`. A birthday as midnight `DateTime` shifts by a day when it crosses a zone.
- **JSON:** ISO 8601 with `Z` or an offset (#607). An `Unspecified` `DateTime` serializes without either, and the client has to guess.

**Testable time: `TimeProvider` (.NET 8)**

Don't call `DateTime.UtcNow` inside logic. Inject `TimeProvider`, register `TimeProvider.System`, and use `FakeTimeProvider` from `Microsoft.Extensions.TimeProvider.Testing` in tests (#588):

```csharp
public sealed class TrialService(TimeProvider clock)
{
    public bool IsExpired(Account a) => clock.GetUtcNow() > a.TrialStartedAt.AddDays(30);
}

var time = new FakeTimeProvider(new DateTimeOffset(2026, 1, 1, 0, 0, 0, TimeSpan.Zero));
var svc  = new TrialService(time);
time.Advance(TimeSpan.FromDays(31));
Assert.True(svc.IsExpired(account));
```

`TimeProvider` also backs timers, `Task.Delay(delay, timeProvider)` and `PeriodicTimer` (#595), so a test can fast-forward a background loop instead of sleeping.

**Durations:** measure with `Stopwatch` or `TimeProvider.GetTimestamp()`/`GetElapsedTime()`, not by subtracting two `DateTime.Now` values, which jump when the clock is adjusted.

**Follow-up:** `DateTime.Parse("10/11/2026")` gives different dates on different machines. Why? (It uses the current culture: 10 November in Poland, 11 October in the US. Parse data with `ParseExact` and an explicit format or `CultureInfo.InvariantCulture`, and exchange ISO 8601 (`2026-11-10`) between systems.)
