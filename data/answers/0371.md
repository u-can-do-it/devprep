## Hints

- If you're logged in and change `/invoices/1041` to `/invoices/1042` in the URL, what should happen?
- Does using UUIDs instead of sequential IDs fix the problem?
- Where in the code should the "does this user own this object?" check live so nobody forgets it?

## Answer

**IDOR (Insecure Direct Object Reference)**, called **BOLA (Broken Object Level Authorization)** in the OWASP API Top 10, happens when an endpoint takes an object ID from the client and returns or modifies the object **without checking the caller is allowed to access that specific object**. The user is authenticated, but authorization is missing. Broken access control is #1 in the OWASP Top 10.

```http
GET /api/invoices/1042
Authorization: Bearer <token for user A>   -> returns user B's invoice
```

Prevention:

- **Check ownership/permission on every request**, server-side, for every object, including updates, deletes, nested resources (`/orgs/7/projects/9`) and bulk endpoints.
- **Scope queries to the caller**, so "not yours" naturally becomes "not found":

```python
invoice = await db.scalar(
    select(Invoice).where(Invoice.id == invoice_id, Invoice.org_id == user.org_id)
)
if invoice is None:
    raise HTTPException(404)
```

- **Centralize authorization** in a policy layer, dependency or middleware (`can(user, "read", invoice)`) instead of ad-hoc `if` checks. Multi-tenant apps can add database **row-level security** (Postgres RLS) as a safety net.
- **Deny by default**: new endpoints should need an explicit policy.
- **Test it**: automated tests that log in as user A and try to access user B's resources, for every endpoint.

**Random IDs (UUIDv4) are not a fix.** They make guessing harder, but IDs leak through URLs, logs and shared links. Defense in depth only.

**Follow-up:** Return 404 or 403 for someone else's object? 404 avoids confirming the resource exists; 403 is fine when existence isn't sensitive.
