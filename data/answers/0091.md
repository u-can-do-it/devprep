## Hints

- What does "stateless" mean for how a server handles each request?
- How are things on the server identified and manipulated in a RESTful API?
- Why would responses need to say whether they can be cached?

## Answer

REST (Representational State Transfer) is an architectural style described by Roy Fielding. It is defined by a set of constraints:

- **Client–server** – UI concerns are separated from data storage, so both sides evolve independently.
- **Stateless** – every request carries everything needed to process it (auth token, params). The server keeps no session state between requests, which makes horizontal scaling easy.
- **Cacheable** – responses declare whether they can be cached (`Cache-Control`, `ETag`), reducing load and latency.
- **Uniform interface** – resources are identified by URIs (`/users/42`), manipulated through representations (JSON), use standard methods (`GET`, `POST`, `PUT`, `DELETE`), and messages are self-descriptive (`Content-Type`, status codes). HATEOAS (links to next actions) is also part of this, though rarely implemented fully.
- **Layered system** – clients can't tell if they talk to the origin or a proxy, load balancer or CDN.
- **Code on demand** (optional) – the server may send executable code, e.g. JavaScript.

```http
GET /orders/123 HTTP/1.1
Accept: application/json
Authorization: Bearer eyJ...
```

In practice, most "REST APIs" are resource-oriented HTTP + JSON APIs that follow the first constraints but skip HATEOAS.

**Follow-up:** "Is your API really RESTful?" – be honest that most APIs sit at level 2 of the Richardson Maturity Model (resources + HTTP verbs) and explain why that's usually enough.
