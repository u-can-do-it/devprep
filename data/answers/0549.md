## Hints

- What's the difference between the first explanation that fits and one you've actually confirmed?
- What changed right before the problem started: a deploy, a config or flag, traffic, data, a dependency?
- The problem hits only some requests. Which dimensions would you slice the data by to find what they have in common?

## Answer

Treat it like an experiment: **observe, hypothesise, predict, test**, with telemetry as your evidence. The order matters.

**1. Mitigate first, investigate second.** If patients can't join consultations, roll back, turn off the flag or scale up before hunting the root cause. Keep evidence (traces, a heap dump, logs) before restarting things.

**2. Describe the symptom precisely.** Not "the API is slow" but "about 3% of `POST /appointments` return 504 since 14:10, only on the mobile app, p50 unchanged". Who is affected, since when, how much.

**3. Ask what changed.** Deploys (tag telemetry with `version` so you can compare), config and feature flags, infrastructure (node pool upgrade, autoscaling), traffic shape (a new B2B client, a marketing push), data (a table crossed a size where the plan changed), and third parties (status pages, their latency in your spans).

**4. Slice and correlate.** In an APM tool such as Datadog:

- Filter traces by error or by latency above p99 and **compare slow traces with fast ones**: which span grows?
- Break the metric down by tag: endpoint, version, pod, node, region, client version, tenant. A problem on one pod points to the host; on one tenant, to data; on one version, to code.
- Jump from a trace to its logs via the trace ID, and to infrastructure metrics for the same pod and minute (CPU throttling, GC pauses, memory, connection pool wait).
- Use database monitoring for query samples, lock waits and plan changes.

**5. Write down several hypotheses** and, for each, a prediction that would **disprove** it. "If the connection pool is exhausted, pool wait time spikes at the same minutes and only on the busiest pods." Check the cheapest ones first, and change one thing at a time.

**6. Don't stop at the first explanation that fits.** A confirmed root cause explains **all** the symptoms: why now and not last week, why only these requests, why it recovers. Correlation in time isn't causation (two deploys happened that afternoon). Reproduce it (replay the request, a production-sized dataset in staging, a load test) and confirm that the fix moves the metric.

**7. Add instrumentation when the data isn't there:** extra spans, log fields, a temporary debug flag for one tenant. Deploy, wait for the next occurrence.

**Usual suspects for "hard" production bugs:** lock contention and deadlocks (#337), connection pool exhaustion (#338), N+1 queries at scale, retry storms, mismatched timeouts (the client gives up before the server), event loop blocking and GC pauses (#65, #69, #306), CPU throttling from Kubernetes limits (#555), DNS, clock skew, cache stampedes (#90), race conditions (#552), and one huge tenant.

**Example:** intermittent 504s on booking. First fit: "the database is slow". But traces show slow requests spend 30 s waiting on `SELECT ... FOR UPDATE` on a slot row, and only between 14:00 and 14:30. Database monitoring shows a transaction holding that lock for 40 s. The cause: a code path that calls an SMS provider **inside** the transaction, and the provider was slow that afternoon. Fix: send the SMS after commit through the outbox (#484), and add a lock-wait alert.

**AI agents help, with care:** an agent with read-only access to logs and traces (an MCP server, #542) can search faster than you, but it jumps to plausible explanations just like people. Ask it for evidence (links to traces and queries) for every claim.

**Afterwards:** a blameless postmortem, fixes for root cause and contributing factors, and a new alert, test or guardrail so it can't come back silently (#440).

**Follow-up:** the error rate rose after a deploy, but rolling back didn't fix it. What now? (Something else changed too: data or messages written by the new version, a migration that wasn't rolled back, a poisoned cache, a config change, or an external dependency. Or the deploy was a coincidence.)
