## Hints

- How much of a typical full OS does your Node or Python app actually need at runtime?
- What could an attacker do if they got code execution inside a container running as root?
- How would you find out that a library inside your image has a known CVE?

## Answer

Hardening means shrinking the attack surface and limiting the damage if the container is compromised.

**1. Minimal, trusted base images**
- Prefer `-slim`, distroless, or hardened images (e.g. Chainguard, Docker Hardened Images). Fewer packages mean fewer CVEs, and having no shell makes post-exploitation harder.
- Pin versions, ideally by **digest** (`node:22-slim@sha256:...`), and rebuild regularly to pick up patches. Renovate or Dependabot can automate the bumps.

**2. Don't run as root**

```dockerfile
FROM node:22-slim AS runtime
WORKDIR /app
COPY --from=build --chown=node:node /app/dist ./dist
USER node
CMD ["node", "dist/server.js"]
```

**3. Restrict the runtime**
- Read-only root filesystem, `--cap-drop=ALL`, `no-new-privileges`, resource limits.
- In Kubernetes: `securityContext` with `runAsNonRoot: true`, `readOnlyRootFilesystem: true`, `allowPrivilegeEscalation: false`.
- Never mount the Docker socket into an app container.

**4. Scan and attest in CI**
- Scan images with Trivy, Grype or Docker Scout, and fail the build on critical, fixable CVEs.
- Generate an SBOM and sign images (cosign) so the cluster runs only verified images.

**5. Keep secrets and build tools out**: multi-stage builds, `.dockerignore`, BuildKit secret mounts.

**Pitfall:** scanning once and forgetting. New CVEs are published against images that haven't changed, so scan registries continuously.
