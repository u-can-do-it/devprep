## Hints

- What information does a client developer need to fix a bad request, and what must never be shown?
- Is the HTTP status code alone enough for a client to react programmatically?
- How would you report several invalid fields in one response?

## Answer

Good error responses are **consistent**, **machine-readable**, and **safe**:

1. The correct **status code** (`400` malformed, `401` unauthenticated, `403` forbidden, `404`, `409` conflict, `422` validation failed, `429` rate limited, `5xx` server faults).
2. A **stable error code/type** clients can branch on – never make them parse human messages.
3. A human-readable message, plus field-level details for validation.
4. A **correlation/trace id** so support can find the logs.
5. No stack traces, SQL or internal hostnames.

**RFC 9457 Problem Details** (which replaced RFC 7807) standardizes this with the media type `application/problem+json`:

```http
HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://api.example.com/problems/validation-error",
  "title": "Your request is not valid.",
  "status": 422,
  "detail": "2 fields failed validation.",
  "instance": "/orders/requests/7f3c",
  "errors": [
    { "pointer": "#/items/0/quantity", "detail": "must be greater than 0" },
    { "pointer": "#/email", "detail": "must be a valid email address" }
  ],
  "traceId": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01"
}
```

- `type` – a URI identifying the problem type (can link to docs); `title` is its short summary.
- `status`, `detail` (this occurrence), `instance` (this occurrence's id).
- **Extension members** like `errors` or `traceId` are allowed.

Frameworks help: ASP.NET Core and Spring have built-in support; in FastAPI or Express you add a global exception handler that maps domain errors to problem documents in one place.

Pitfalls: returning `200` with `{"success": false}`, different error shapes per endpoint, and leaking whether an account exists (e.g. on login or password reset).
