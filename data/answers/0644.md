## Hints

- In `mode: 'uncontrolled'`, why does every input need `key={form.key('email')}`, and why doesn't `form.values` update on each keystroke?
- A `NumberInput` gives you `number | ''`. What does that mean for your Zod schema's input type?
- How do you validate on blur for one field but on submit for the rest?
- The API answers `422` with `{ "errors": { "items.2.amount": "…" } }`. How do those errors end up under the right input?
- How do you warn about unsaved changes, and what does `form.initialize` solve for edit forms that load data asynchronously?

## Answer

> `useForm` keeps values, errors and touched/dirty state. In uncontrolled mode (the default to choose in Mantine 7+) inputs hold their own value and the component doesn't re-render on every keystroke, so you spread `getInputProps` and pass `key={form.key(path)}`, and read values with `getValues()`. Plug in a Zod schema through a resolver, so one schema defines both the TypeScript type and the rules. Lists use `insertListItem`/`removeListItem` with paths like `items.0.name`. Choose validation timing with `validateInputOnBlur`, map server errors with `setErrors`, and use `isDirty()` to warn about unsaved changes.

**Basic form with a Zod schema**

```tsx
import { useForm } from '@mantine/form';
import { zodResolver } from 'mantine-form-zod-resolver';   // newer Mantine versions also accept Standard Schema
import { z } from 'zod';

const schema = z.object({
  name: z.string().trim().min(1, 'Required'),
  email: z.string().email('Invalid e-mail'),
  limit: z.coerce.number().positive('Must be positive'),      // NumberInput may give '' or a string
  validFrom: z.string().min(1, 'Required'),
  validTo: z.string().optional(),
}).refine((v) => !v.validTo || v.validTo >= v.validFrom, {
  path: ['validTo'], message: 'Must be after the start date',   // cross-field rule shown under validTo
});

type FormValues = z.input<typeof schema>;    // what the inputs hold
type Payload = z.output<typeof schema>;      // what you send to the API

function CustomerForm({ onSave }: { onSave: (p: Payload) => Promise<void> }) {
  const form = useForm<FormValues>({
    mode: 'uncontrolled',
    initialValues: { name: '', email: '', limit: '', validFrom: '', validTo: '' },
    validate: zodResolver(schema),
    validateInputOnBlur: ['email'],          // or true for every field
  });

  return (
    <form onSubmit={form.onSubmit(async (values) => onSave(schema.parse(values)))}>
      <TextInput label="Name" key={form.key('name')} {...form.getInputProps('name')} />
      <TextInput label="E-mail" key={form.key('email')} {...form.getInputProps('email')} />
      <NumberInput label="Limit" key={form.key('limit')} {...form.getInputProps('limit')} />
      <Button type="submit" loading={form.submitting}>Save</Button>
    </form>
  );
}
```

- `getInputProps(path)` returns `defaultValue` or `value`, `onChange`, `error`, `onFocus` and `onBlur`, so Mantine inputs show errors without extra wiring. Checkboxes need `getInputProps('agree', { type: 'checkbox' })`.
- **Controlled vs uncontrolled:** in controlled mode every keystroke re-renders the component holding `useForm`, which is noticeable in big forms. In uncontrolled mode `form.key(path)` changes when values are set programmatically (`setValues`, `reset`), which remounts the input with the new value. That's why the `key` is required. To react to a value, use `form.watch('country', ({ value }) => …)` or `getValues()`, not `form.values`.
- **Input vs output types:** the form holds what inputs produce (strings, `''`, `null` from a cleared `Select`). The schema converts it to what the API expects. Keep that split explicit with `z.input`/`z.output` (#625), or use `transformValues` in `useForm`.

**Validation timing.** By default validation runs on submit and an error clears when the field changes. `validateInputOnBlur` and `validateInputOnChange` (both accept `true` or a list of paths) give earlier feedback. Validate on blur for format checks, never on each keystroke for an empty field the user hasn't reached yet. Async checks ("is this code taken?") belong in the submit handler or a debounced query, not in the synchronous resolver.

**List fields**

```tsx
form.insertListItem('items', { id: crypto.randomUUID(), name: '', amount: '' });
form.removeListItem('items', index);
form.reorderListItem('items', { from, to });

{form.getValues().items.map((item, i) => (
  <Group key={item.id}>                                        {/* a stable id, not the index */}
    <TextInput key={form.key(`items.${i}.name`)} {...form.getInputProps(`items.${i}.name`)} />
  </Group>
))}
```

Zod paths become dot paths (`items.2.amount`), so errors land on the right row automatically.

**Server-side errors.** Client validation is a convenience. The backend validates again and is the authority.

```ts
try {
  await onSave(payload);
} catch (e) {
  if (isAxiosError(e) && e.response?.status === 422) {
    form.setErrors(e.response.data.errors);        // { 'items.2.amount': 'Exceeds limit', email: 'Taken' }
    return;
  }
  throw e;                                        // let the global handler show a toast
}
```

Agree with the backend on the error shape: field paths in the same dot notation, plus a form-level message for errors that don't belong to a field.

**Edit forms and dirty state**

- Load data, then call `form.initialize(data)`. It sets values and initial values once, so the form isn't dirty after loading, and a refetch won't overwrite what the user is typing. Alternatively render the form only after the data arrives and pass it as `initialValues`.
- `form.isDirty()` compares with the initial values. Use it to disable Save and to warn on navigation (`beforeunload` in the browser). After a successful save, `form.resetDirty()` makes the saved values the new baseline.
- `form.isTouched(path)`, `form.reset()` and `form.setFieldValue(path, v)` cover the rest.
- Big forms split across components share one form with `createFormContext<FormValues>()`.

**Follow-up:** "Why not React Hook Form?" It's also uncontrolled and has a larger ecosystem. The Mantine one integrates with Mantine inputs without `Controller` wrappers (#639) and matches the rest of the UI library. Either way the Zod schema, the server-error mapping and the dirty-state handling are the same ideas.
