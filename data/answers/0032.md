## Hints

- Comparing two arbitrary trees optimally is O(n³) — what shortcuts does React take instead?
- What happens when the element type at a position changes from `<div>` to `<span>`?
- If you insert an item at the start of a list keyed by index, which component instances get reused?

## Answer

> After each render, React compares the new element tree with the previous one and changes only the parts of the DOM that differ. This is reconciliation. If an element's type changes, React throws away that whole subtree and its state. If the type stays the same, it keeps the node and updates the props. In lists, React matches old and new items by `key`, so a stable unique key like a database id keeps each item's state attached to the right row. Index keys break when items are added, removed or reordered.

On each render React builds a new element tree and **diffs** it against the previous one (reconciliation), then commits only the needed DOM changes. To keep it O(n), React uses two heuristics:

- **Different type → replace.** If an element changes type (`<div>` → `<section>`, or `ComponentA` → `ComponentB`), React unmounts the whole subtree, destroying its state, and mounts a new one.
- **Same type → update.** React keeps the instance/DOM node and updates only changed props, then recurses into children.

For lists of children, React matches old and new items by **`key`**. A stable, unique key (like a database id) lets React move, insert and remove items correctly while preserving each item's state and DOM node.

```jsx
{todos.map(t => <TodoRow key={t.id} todo={t} />)}
```

**Why index keys are a problem:** if you prepend, delete or reorder, indexes shift, so React pairs the wrong state with the wrong item — e.g. an input's typed text or a checkbox stays at position 0 while the data moves. They also cause unnecessary re-renders. Index keys are only acceptable for static lists that never reorder.

Never generate keys with `Math.random()` during render — every render gets new keys, so everything remounts.

**Follow-up:** changing a `key` on purpose is a handy way to **reset** a component's state (e.g. `<Form key={userId} />`).
