## Hints

- You have 25 dictionaries (countries, currencies, document types, risk categories…). Do you build 25 CRUD screens?
- How long should dictionary data be cached on the client, and when must the cache be invalidated?
- A currency is deactivated. Should it disappear from existing records, from the edit form's options, or both?
- Mantine's `Select` needs `{ value, label }` with string values. What do you store in the record?
- The user changes the country. What should happen to the already selected region?

## Answer

> Dictionaries (reference data) are small, rarely changing lists that the rest of the app references by id or code. Build one generic, config-driven dictionary module (grid, form, schema and permissions per dictionary) instead of a screen per list. Cache them for a long time with TanStack Query and invalidate them when an admin edits one. Expose them through a `useDictionary` hook that gives both `options` and an id→label lookup. Records store codes or ids, never labels. Entries are deactivated or given validity dates rather than deleted: they stay visible on old records but disappear from options for new ones. Dependent dictionaries reset the child value when the parent changes.

**One generic module.** Most dictionaries share the same shape (code, name, active flag, validity dates, sometimes a few extra fields), so describe each one with config:

```ts
type DictionaryConfig<T extends DictionaryEntry> = {
  key: 'countries' | 'currencies' | 'riskCategories';
  title: string;
  schema: z.ZodType<T>;                     // form validation (#644), also used by imports (#651)
  columns: ColDef<T>[];                     // grid columns (#645)
  fields: FieldConfig<T>[];                 // which inputs the edit form renders
  permissions: { view: Permission; edit: Permission };
};

// app/(admin)/dictionaries/[key]/page.tsx renders <DictionaryPage config={dictionaries[key]} />
```

One page, one generic grid with search and an "include inactive" toggle, and one generic form drawer. A new dictionary is a config entry plus a backend endpoint. Dictionaries that really are special (hierarchies, rich rules) get their own screens.

**Caching and the hook**

```ts
export const dictionaryQuery = (key: DictionaryKey) => queryOptions({
  queryKey: ['dictionary', key],
  queryFn: ({ signal }) => http.get<DictionaryEntry[]>(`/dictionaries/${key}`, { signal }).then((r) => r.data),
  staleTime: 60 * 60_000,                                  // reference data changes rarely
});

export function useDictionary(key: DictionaryKey, opts: { includeInactive?: boolean; at?: string } = {}) {
  const { data = [] } = useQuery(dictionaryQuery(key));
  return useMemo(() => {
    const byId = new Map(data.map((e) => [e.id, e]));
    const options = data
      .filter((e) => opts.includeInactive || isActive(e, opts.at))
      .map((e) => ({ value: String(e.id), label: e.name }));
    return { options, label: (id?: string | number | null) => (id == null ? '' : byId.get(Number(id))?.name ?? `#${id}`) };
  }, [data, opts.includeInactive, opts.at]);
}
```

- After an admin saves an entry: `queryClient.invalidateQueries({ queryKey: ['dictionary', key] })`. Other users get the change when their `staleTime` passes.
- Prefetch the dictionaries every screen needs on the server or at login (#635), so selects and grids don't flash raw ids.
- Large dictionaries (thousands of entries, such as institutions or postcodes) shouldn't be downloaded whole. Use a searchable select with server search, debounced (#502), and fetch labels for the ids on screen.

**Using them in the UI**

```tsx
const currencies = useDictionary('currencies');                      // only active ones as options

<Select label="Currency" data={currencies.options} searchable {...form.getInputProps('currencyId')} />

// in a grid column: show the label, sort and filter by it
{ field: 'currencyId', headerName: 'Currency', valueGetter: (p) => currencies.label(p.data?.currencyId) }
```

Mantine's `Select` works with **string** values. Convert at the boundary (in the form's input/output types) if the API uses numbers.

**Store codes, not labels.** Records hold `currencyId` or `currencyCode: 'PLN'`. Labels change, get translated, and are resolved at display time. Prefer stable codes over database ids when the value travels to other systems or appears in imports.

**Inactive and time-limited entries**

- Never hard-delete an entry that records point to. Use `active: false` or `validFrom`/`validTo`.
- **Options** for new or edited records show only entries active now, or at the record's effective date (`at`).
- **Display** of existing records resolves any entry, including inactive ones. If an old record still holds an inactive value, the edit form shows it as "EUR-old (inactive)" so saving doesn't silently clear it, and validation decides whether it may stay.
- Validity periods matter in compliance: a risk category valid until 2025 must still be shown correctly on 2024 reports, and history views resolve labels as of the event date (#650).

**Dependent dictionaries**

```tsx
const regions = useQuery({ ...regionsQuery(countryId), enabled: !!countryId });

form.watch('countryId', () => form.setFieldValue('regionId', null));   // a region from another country is invalid
```

Disable the child select until the parent is chosen, and validate the pair on the backend too.

**Admin side**

- Edits require their own permission, and every change is audited (who, old → new, reason; #650).
- Optimistic locking prevents two admins overwriting each other (`409` on a stale version).
- Bulk changes go through the same import flow as other data (#651), with the same schema.
- Translations: store a label per language, or translation keys, and choose the label in the hook based on the current locale.

**Follow-up:** "Why not hard-code small dictionaries as TypeScript enums?" Do it for lists that change only together with code (order statuses that drive logic). Use database dictionaries for lists that business users maintain (document types, risk categories), because a change shouldn't require a deployment.
