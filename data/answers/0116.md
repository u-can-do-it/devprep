## Hints

- Why shouldn't an access token travel through the browser's URL bar?
- If a public client (SPA, mobile app) can't keep a client secret, how can the server be sure the code is redeemed by the same client that started the flow?
- What does OAuth not tell you that a login system needs to know?

## Answer

**OAuth 2.0** is an **authorization delegation** framework: a client gets an access token to call an API on the user's behalf. **OpenID Connect (OIDC)** adds **authentication** on top: who the user is.

**Authorization code flow with PKCE:**

1. Client generates a random `code_verifier` and derives `code_challenge = BASE64URL(SHA256(code_verifier))`, plus a random `state` (and `nonce` for OIDC).
2. Redirect the user to the authorization server:

```http
GET /authorize?response_type=code
  &client_id=web-app
  &redirect_uri=https://app.example.com/callback
  &scope=openid profile email orders:read
  &state=xyz&nonce=abc
  &code_challenge=E9Melhoa...&code_challenge_method=S256
```

3. User authenticates and consents. The server redirects back with a short-lived, single-use `code` and `state`.
4. Client checks `state` (CSRF protection), then exchanges the code over a back channel:

```http
POST /token
grant_type=authorization_code&code=...&redirect_uri=...
&client_id=web-app&code_verifier=dBjftJeZ...
```

5. The server verifies `SHA256(code_verifier)` matches the stored challenge, then returns an `access_token`, optional `refresh_token`, and with OIDC an **`id_token`**.

**Why PKCE:** an intercepted code (malicious app with the same redirect scheme, logs, referrers) is useless without the verifier. OAuth 2.1 makes PKCE mandatory for all clients, including confidential ones, and drops the implicit and password grants.

**What OIDC adds:**

- **`id_token`** – a JWT about the authentication event (`sub`, `iss`, `aud`, `exp`, `nonce`, `auth_time`). The client must validate signature (via JWKS), issuer, audience, expiry and nonce.
- `/userinfo` endpoint, discovery (`/.well-known/openid-configuration`), standard scopes.

**Key distinctions:**

- `id_token` is for the **client** (who logged in); `access_token` is for the **API** (what may be done). Never send an id_token to an API as authorization.
- Validate `aud` on access tokens in resource servers.

**Architecture for browser apps:** prefer a **BFF** – the backend is a confidential client, does the code exchange, stores tokens server-side and gives the browser an `HttpOnly` session cookie. Refresh tokens, if used in public clients, must rotate with reuse detection.
