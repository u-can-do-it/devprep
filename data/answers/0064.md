## Hints

- Which of these shares memory with the main thread and which runs separate processes?
- Is your problem CPU-bound work inside one request, or scaling an HTTP server across cores?
- What if you need to run a non-JavaScript program, like `ffmpeg`?

## Answer

All three get work off the single JS thread, but for different problems:

**`worker_threads`** – extra V8 isolates inside the **same process**. Each has its own event loop and heap, communicates via `postMessage`, and can share memory with `SharedArrayBuffer` / transfer `ArrayBuffer`s with zero copy. Best for **CPU-heavy JS** (image processing, parsing, hashing) without blocking the main loop. Use a pool (e.g. Piscina) since spawning a worker costs ~ms and memory.

```js
import { Worker } from 'node:worker_threads';
const w = new Worker(new URL('./hash.js', import.meta.url), { workerData: buf });
w.on('message', (result) => console.log(result));
```

**`cluster`** – forks **multiple copies of your whole server process**, sharing one listening port; the primary distributes connections. Good for using all CPU cores for I/O-bound HTTP traffic. Processes don't share memory (sessions/caches must be external, e.g. Redis). In containers it's usually replaced by running N replicas behind a load balancer, or PM2.

**`child_process`** (`spawn`, `exec`, `fork`) – runs **any external program** or a separate Node script with full isolation. Use for shell tools (`ffmpeg`, `git`), or isolating crash-prone code. Communicate via stdio or IPC (`fork`). Highest overhead; beware shell injection with `exec`.

Rule of thumb: CPU work in-process → workers; scale a server across cores → cluster/replicas; external binaries or strong isolation → child_process.
