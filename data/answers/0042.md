## Hints

- When is the HTML generated in each case — at build time, on each request, or periodically?
- What does the user see while a slow database query is running in each strategy?
- How fresh does a blog post need to be compared with a shopping cart?

## Answer

They differ in **when HTML is produced**:

- **SSG (Static Site Generation)** — HTML built at **build time**, served from a CDN. Fastest and cheapest, but data is only as fresh as the last deploy. Use for docs, marketing pages, blogs. In the App Router a route is static when it uses no request-time data; `generateStaticParams` pre-builds dynamic segments.
- **SSR (Server-Side Rendering)** — HTML rendered **on every request**. Always fresh and can personalize (cookies, headers), but slower TTFB and more server load. Use for dashboards, per-user pages, search results. Triggered by reading `cookies()`, `headers()`, `searchParams` or uncached data.
- **ISR (Incremental Static Regeneration)** — static pages that **regenerate in the background** after a time window or on demand. Users get cached HTML instantly; the next request after expiry triggers a rebuild (stale-while-revalidate). Use for product catalogs and news.

```ts
export const revalidate = 3600; // time-based ISR for this route
// or on demand, after a mutation:
revalidatePath('/products');
```

- **Streaming** — send HTML **in chunks** as it becomes ready. The shell (layout, nav) arrives immediately and slow parts wrapped in `<Suspense>` (or `loading.tsx`) stream in later. It improves TTFB and perceived performance and combines with SSR.

```tsx
<Suspense fallback={<ReviewsSkeleton />}>
  <Reviews productId={id} />
</Suspense>
```

**Modern Next.js** mixes these per route or even per component: **Partial Prerendering** (part of Cache Components in Next.js 16) serves a static shell from the CDN and streams the dynamic holes in the same response.

**Follow-up:** the biggest pitfall is accidentally making a whole route dynamic by reading cookies in a shared layout.
