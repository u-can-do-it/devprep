## Hints

- In each model, who patches the operating system, and who scales the servers?
- Which of these would you pick for a cron job that runs for five seconds once an hour?
- What do you gain and lose as you move from IaaS toward SaaS?

## Answer

These models differ in **how much the provider manages** and how much you manage:

| Model | You manage | Provider manages | Examples |
|---|---|---|---|
| **IaaS** | OS, runtime, app, scaling | hardware, network, virtualization | AWS EC2, GCP Compute Engine, Hetzner VMs |
| **PaaS** | your app and its config | OS, runtime, scaling, deploys | Heroku, Render, Fly.io, Cloud Run, App Service |
| **FaaS** (serverless functions) | individual functions | everything else, scales to zero | AWS Lambda, Cloud Run functions, Cloudflare Workers |
| **SaaS** | just usage and data | the whole application | Gmail, Slack, Auth0, Stripe |

The trade-off: going toward SaaS gives you **less operational work and faster delivery**, but **less control, more vendor lock-in**, and sometimes higher cost at scale. IaaS gives full control (custom kernels, special software) at the price of patching, monitoring and scaling yourself.

**For a typical web app** (frontend + API + Postgres) at a startup, a good default is:
- frontend on a platform like Vercel, Netlify or Cloudflare,
- API in containers on a PaaS or container service (Cloud Run, ECS Fargate, Fly.io),
- a **managed database** (RDS, Cloud SQL, Neon, Supabase),
- FaaS for event-driven bits (webhooks, image processing, scheduled jobs),
- SaaS for undifferentiated work: auth, email, payments, error tracking.

Move toward IaaS or Kubernetes when cost, compliance, or special requirements justify the extra operational load.

**Follow-up:** "What is CaaS?" Containers-as-a-Service (ECS, Cloud Run, managed Kubernetes) sits between IaaS and PaaS: you ship an image, the provider runs it.
