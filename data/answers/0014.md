## Hints

- Which one loads synchronously and which one can be analyzed before the code runs?
- Can `require()` load an ES module? Can `import` load CommonJS?
- Why does static structure matter for tree-shaking?

## Answer

| | CommonJS (CJS) | ES Modules (ESM) |
|---|---|---|
| Syntax | `require()`, `module.exports` | `import` / `export` |
| Loading | synchronous, at runtime | asynchronous; the module graph is parsed before any code runs |
| Structure | dynamic (`require` can appear anywhere) | static top-level declarations, plus `import()` for dynamic loading |
| Exports | a **copy** of the `module.exports` value | **live bindings** (importers see later updates) |
| `this` / globals | `__dirname`, `__filename`, `require` | `import.meta.url`, `import.meta.dirname` (Node 20.11+) |
| Top-level `await` | no | yes |
| Strict mode | opt-in | always |

```js
// CJS
const { readFile } = require('node:fs/promises');
module.exports = { parse };

// ESM
import { readFile } from 'node:fs/promises';
export function parse() {}
const mod = await import('./heavy.js'); // dynamic, code-split
```

**Why ESM matters:**

- It is the standard, so the same module works in browsers and Node.
- Bundlers can **tree-shake** unused exports because imports are static.
- It supports top-level `await`.

**Interop in Node:**

- The module system is chosen by the file extension (`.mjs`/`.cjs`) or by `"type": "module"` in `package.json`.
- ESM can `import` CJS. The default export is `module.exports`.
- CJS can load ESM with `await import()`. Since Node 22.12, `require(esm)` also works for ES modules that don't use top-level `await`.
- Packages often publish both formats using the `"exports"` field with `import`/`require` conditions. That can lead to the "dual package hazard", where two copies of the module's state exist.

**Follow-up:** circular dependencies behave differently. CJS returns a partially filled `exports` object. ESM throws a TDZ error if a binding is used before it is initialized.
