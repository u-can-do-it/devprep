## Hints

- Will a function that expects `{ name: string }` accept a value of an unrelated class that also has `name`?
- Why does an object literal with an extra property cause an error, while the same object stored in a variable doesn't?
- How could you stop someone from passing a `UserId` where an `OrderId` is expected if both are strings?

## Answer

**Structural typing** means compatibility depends on **shape**, not on the type's name or where it was declared. If `A` has every member that `B` requires, then `A` is assignable to `B`, even if they are unrelated. This is "static duck typing", and it matches how JS objects work.

```ts
interface Point { x: number; y: number }
class Vector { constructor(public x: number, public y: number, public z = 0) {} }

const p: Point = new Vector(1, 2); // OK: Vector has x and y (z is extra)
```

**Excess property checks** are an exception for **fresh object literals**. Writing extra properties directly in a literal is an error, because it's probably a typo:

```ts
const a: Point = { x: 1, y: 2, z: 3 };  // error: 'z' does not exist
const tmp = { x: 1, y: 2, z: 3 };
const b: Point = tmp;                    // OK: not a fresh literal
```

**Consequences:**

- Mocks and test doubles are easy to write, and there's no need for explicit `implements`.
- `{}` and `object` accept nearly anything.
- Values with the same shape but **different meanings** (IDs, currencies, units) can be mixed up silently.
- Classes with `private` or `#private` members are effectively nominal. Two classes with the same private field are not compatible.

**Branded (nominal) types** fix the "same shape, different meaning" problem:

```ts
type Brand<T, B extends string> = T & { readonly __brand: B };
type UserId = Brand<string, 'UserId'>;
type OrderId = Brand<string, 'OrderId'>;

const toUserId = (s: string): UserId => s as UserId; // validate here, cast once

function getUser(id: UserId) { /* ... */ }
getUser(toUserId('u_1'));   // OK
// getUser('u_1');          // error
// getUser(orderId);        // error
```

Brands exist only at compile time and add zero runtime cost. A `declare const brand: unique symbol` key makes the brand impossible to fake by hand. Zod's `.brand()` combines runtime validation with branding.

**Follow-up:** function parameter variance. Under `strictFunctionTypes`, parameters are checked contravariantly, but method-style declarations remain bivariant.
