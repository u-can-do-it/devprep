## Hints

- What type does `args` have inside the function, and what about `kwargs`?
- What do `*` and `**` do when used in a function *call* instead of a definition?
- What does a bare `*` in a parameter list force callers to do?

## Answer

> Some functions need to accept a variable number of arguments. In a function definition, `*args` collects extra positional arguments into a tuple, and `**kwargs` collects extra keyword arguments into a dict. In a function call, the stars do the opposite: they unpack a list or a dict into arguments. This is how decorators and wrappers forward everything to the function they wrap. The names are only a convention, the stars are what matter. Don't overuse `**kwargs`, because it hides the real API from type checkers and IDEs.

In a function **definition**:

- `*args` collects extra **positional** arguments into a **tuple**.
- `**kwargs` collects extra **keyword** arguments into a **dict**.

The names are just convention; the stars matter.

```python
def log(message, *args, **kwargs):
    print(message, args, kwargs)

log("hi", 1, 2, level="info")
# hi (1, 2) {'level': 'info'}
```

In a function **call**, the stars do the opposite: they **unpack** an iterable or a mapping into arguments.

```python
nums = [1, 2, 3]
opts = {"sep": "-", "end": "!\n"}
print(*nums, **opts)   # 1-2-3!
```

Parameter order: positional, `*args`, keyword-only, `**kwargs`. Related syntax:

```python
def connect(host, /, port=5432, *, timeout=10): ...
# host is positional-only (/), timeout is keyword-only (*)
```

Common uses: wrapper functions and decorators that forward everything (`func(*args, **kwargs)`), flexible APIs, merging dicts (`{**a, **b}`), and passing config dicts to constructors.

Pitfall: overusing `**kwargs` hides the real API from type checkers and IDEs; prefer explicit parameters, or type them with `Unpack[TypedDict]`.
