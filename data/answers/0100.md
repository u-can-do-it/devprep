## Hints

- Should the schema mirror your database tables or what clients need?
- What happens to the rest of the response if a non-null field's resolver throws?
- How do you change a schema without breaking existing clients?

## Answer

> A GraphQL schema is a long-lived contract with clients, so design it around the domain and UI use cases, not your database tables. Use clear names, one `input` per mutation, cursor-based connections for lists, and evolve with `@deprecated` instead of versions. Nullability needs care: if a non-null field fails, the `null` spreads up to the nearest nullable parent and can wipe out a big part of the response. Make inputs strict, but outputs non-null only when truly guaranteed.

**Design principles:**

- **Client/domain-driven, not DB-driven.** Model the business domain and the use cases of the UI, not table structure. Hide internal IDs and join tables.
- **Consistent naming**: `camelCase` fields, `PascalCase` types, verb-first mutations (`createOrder`, `cancelOrder`) rather than generic `updateOrder` with a status flag.
- **Mutations** take one `input` type and return a payload type (room to add fields, errors).
- **Pagination** with Relay-style connections (`edges`, `node`, `pageInfo`, cursors) for lists that can grow.
- **Errors as data** for expected failures (`union CreateUserResult = User | EmailTaken`), reserving `errors` for unexpected ones.
- **Evolve, don't version**: add fields, mark old ones `@deprecated(reason: "...")`, track field usage before removal.

**Nullability:**

In GraphQL fields are nullable by default; `!` makes them non-null. If a non-null field resolves to `null` or throws, the null **propagates to the nearest nullable parent**, potentially wiping out a big chunk of the response.

```graphql
type Query {
  me: User            # nullable: not logged in, or error -> just null
}
type User {
  id: ID!             # always present
  name: String!
  avatarUrl: String   # optional / may fail independently
  orders(first: Int!): OrderConnection!
}
```

Guidelines:

- Make **arguments and input fields** non-null when required – that's a safe, strong contract.
- Make **output fields** non-null only when they're truly guaranteed (IDs, required columns). Fields backed by other services should usually stay nullable so partial failures degrade gracefully.
- Changing nullable → non-null on output is safe; the reverse is breaking for clients.

**Follow-up:** Mention newer work on semantic/"error-aware" nullability (`@semanticNonNull`, client-side error handling) that aims to fix this trade-off.
