## Hints

- If a toolbar has 10 buttons, how many Tab presses should it take to get past it?
- Which item gets `tabindex="0"` and which get `-1`?
- What's the alternative to moving DOM focus between the items?

## Answer

A **composite widget** (tabs, menu, listbox, toolbar, radio group, grid, tree) should be **a single Tab stop**. **Tab** moves into and out of the widget, and **arrow keys** move between its items. Otherwise a keyboard user has to press Tab through every item.

**Roving tabindex:** only the current item has `tabIndex={0}` and all the others have `-1`. On an arrow key you update the current index and call `.focus()` on the new item. Tabbing back into the widget returns to the last active item.

```tsx
function Tabs({ tabs }: { tabs: { id: string; label: string; content: React.ReactNode }[] }) {
  const [selected, setSelected] = useState(0);
  const refs = useRef<(HTMLButtonElement | null)[]>([]);
  const id = useId();

  function onKeyDown(e: React.KeyboardEvent) {
    const last = tabs.length - 1;
    const moves: Record<string, number> = {
      ArrowRight: selected === last ? 0 : selected + 1,
      ArrowLeft: selected === 0 ? last : selected - 1,
      Home: 0,
      End: last,
    };
    const next = moves[e.key];
    if (next === undefined) return;
    e.preventDefault();
    setSelected(next);             // automatic activation: moving focus also selects the tab
    refs.current[next]?.focus();
  }

  return (
    <>
      <div role="tablist" aria-label="Account sections" onKeyDown={onKeyDown}>
        {tabs.map((t, i) => (
          <button
            key={t.id}
            ref={(el) => { refs.current[i] = el; }}
            role="tab"
            id={`${id}-tab-${i}`}
            aria-selected={i === selected}
            aria-controls={`${id}-panel-${i}`}
            tabIndex={i === selected ? 0 : -1}
            onClick={() => setSelected(i)}
          >
            {t.label}
          </button>
        ))}
      </div>
      {tabs.map((t, i) => (
        <div key={t.id} role="tabpanel" id={`${id}-panel-${i}`} aria-labelledby={`${id}-tab-${i}`}
             hidden={i !== selected} tabIndex={0}>
          {t.content}
        </div>
      ))}
    </>
  );
}
```

**The alternative is `aria-activedescendant`.** DOM focus stays on the container or input, and the attribute points at the id of the active item. Use it when focus must stay in a text input, as in a combobox (#502). Roving tabindex is simpler and more robust for most other widgets.

**Expected keys per pattern** (from the WAI-ARIA Authoring Practices):

| Widget | Keys |
|---|---|
| Tabs | ←/→, Home/End. Automatic activation, or manual activation with Enter/Space when panels are expensive to load |
| Menu button | Enter/Space/↓ opens. ↑/↓ moves, typing a letter jumps to an item, Esc closes and **returns focus to the button** |
| Listbox | ↑/↓, Home/End, type-ahead, Shift+arrow for multi-select |
| Radio group | arrows move and select. Native `<input type="radio">` already does this |
| Grid / data grid | arrows move between cells in 2D, Enter edits a cell |

**Related WCAG criteria:** 2.1.1 Keyboard, 2.1.2 No Keyboard Trap, 2.4.3 Focus Order, 2.4.7 Focus Visible (style `:focus-visible`, never just `outline: none`), and 2.4.11 Focus Not Obscured (new in 2.2: sticky headers mustn't cover the focused item).

**In practice:** use a library that implements these patterns (React Aria, Radix, the design system's components) and test them with a keyboard only and a screen reader. Hand-roll a widget only when you have to, and follow the APG pattern exactly.
