## Hints

- How do you find out that the provider renamed a field your service depends on, before production?
- Who knows best which parts of an API response are actually used?
- Why aren't full end-to-end tests across ten microservices a good answer?

## Answer

**Contract testing** checks that two services (consumer and provider, e.g. a frontend and an API, or two microservices) agree on the **shape of their interaction** (requests, responses, messages) **without running both together**. It fills the gap between fast but isolated unit tests with mocks (which can drift from reality) and slow, flaky cross-service E2E environments.

**Consumer-driven contracts (Pact):**

1. The **consumer** writes tests against a Pact mock provider, stating what it sends and the minimum it needs back. This generates a **contract** (pact file).

```ts
await provider
  .given('order 42 exists')
  .uponReceiving('a request for order 42')
  .withRequest({ method: 'GET', path: '/orders/42' })
  .willRespondWith({
    status: 200,
    body: { id: like(42), status: like('shipped'), total: decimal(19.99) },
  })
  .executeTest(async (mock) => {
    const order = await getOrder(mock.url, 42);
    expect(order.status).toBe('shipped');
  });
```

2. The contract is published to a **broker** (Pact Broker / PactFlow).
3. The **provider** verifies it in its CI: it replays the requests against the real service (with **provider states** set up via hooks) and checks the responses satisfy the contract.
4. Before deploying either side, **`can-i-deploy`** checks the broker: is this version compatible with what's running in that environment?

**Benefits:** the provider knows exactly which fields consumers use, so removing an unused field is safe and renaming a used one fails the build. Feedback comes in minutes, and each service is tested independently.

**When it's worth it:** several teams own services that talk over HTTP or messaging and deploy independently. Less useful when one team owns both sides and deploys them together, or for public APIs with unknown consumers (use **schema-based** contracts: OpenAPI validation, GraphQL schema checks, Protobuf breaking-change detection with `buf`).

**Pitfall:** contracts should express what the consumer **needs** (matchers), not snapshots of full responses, or they become brittle.
