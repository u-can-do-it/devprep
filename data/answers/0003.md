## Hints

- What does the engine do with declarations before it runs a scope's code?
- Why does using a `var` before its declaration give `undefined`, while `let` throws?
- Are function declarations and function expressions hoisted the same way?

## Answer

**Hoisting:** before running a scope, the engine sets up bindings for every declaration in it. So it behaves *as if* the declarations had been moved to the top. How each binding starts out depends on the kind of declaration:

- **`var`:** hoisted and initialized to `undefined`.
- **Function declarations:** hoisted together with their body, so you can call them before the line where they are defined.
- **`let`, `const`, `class`:** hoisted but **not initialized**. They sit in the **Temporal Dead Zone** from the start of the block until the line that declares them. Any access in that zone throws a `ReferenceError`.
- **Function expressions and arrow functions** follow the rules of the variable that holds them.

```js
console.log(a); // undefined
var a = 1;

console.log(b); // ReferenceError: Cannot access 'b' before initialization
let b = 2;

greet();        // works
function greet() {}

hi();           // TypeError: hi is not a function (hi is undefined)
var hi = () => {};
```

The TDZ is based on **time, not position in the code**:

```js
function log() { return x; } // fine to reference here
log();      // ReferenceError: x is still in the TDZ
let x = 1;
log();      // 1
```

The TDZ also proves that `let` is hoisted. In the example below the inner `x` shadows the outer one from the start of the block:

```js
let x = 'outer';
{ console.log(x); let x = 'inner'; } // ReferenceError, not 'outer'
```

**Follow-up:** `typeof undeclaredVar` returns `'undefined'`, but `typeof` on a variable in its TDZ throws.
