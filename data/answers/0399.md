## Hints

- How does the API know the database is actually ready, not just started?
- How do you get code changes into a running container without rebuilding every time?
- How would you keep optional services (e.g. a mail catcher) from always starting?

## Answer

A good Compose setup lets a new developer run the whole stack with one command: `docker compose up`.

```yaml
# compose.yaml (the top-level "version:" key is obsolete)
services:
  api:
    build: { context: ./api, target: dev }
    ports: ["8000:8000"]
    env_file: .env
    depends_on:
      db:
        condition: service_healthy
    develop:
      watch:
        - action: sync
          path: ./api/src
          target: /app/src
        - action: rebuild
          path: ./api/package.json
  db:
    image: postgres:17
    environment: { POSTGRES_PASSWORD: dev }
    volumes: [pgdata:/var/lib/postgresql/data]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      retries: 10
  mailpit:
    image: axllent/mailpit
    profiles: [mail]
volumes:
  pgdata:
```

Key points:

- **`depends_on` + `condition: service_healthy`** waits for the healthcheck. A plain `depends_on` only waits for the container to *start*, not for Postgres to accept connections.
- **Live reload:** bind mounts or `docker compose watch` (sync files, rebuild on dependency changes).
- **Named volumes** keep DB data between restarts. `docker compose down -v` resets it.
- **Profiles** for optional services: `docker compose --profile mail up`.
- **`compose.override.yaml`** or multiple `-f` files for per-developer or CI variations. A `target: dev` stage in a multi-stage Dockerfile keeps dev tooling out of production images.

**Pitfall:** keeping real secrets in `compose.yaml`. Use a git-ignored `.env` file and commit a `.env.example`.
