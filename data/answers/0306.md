## Hints

- If one request does 200 ms of synchronous work, what happens to every other request queued behind it?
- What shared resources besides the main thread can become a queue (thread pool, connection pools, sockets)?
- Which measurements tell the event loop apart from slow downstream calls?

## Answer

Good averages with bad tails usually mean **queueing**: some requests wait behind something shared. Measure before guessing.

**1. Is the event loop blocked?**

```js
import { monitorEventLoopDelay, performance } from 'node:perf_hooks';
const h = monitorEventLoopDelay({ resolution: 20 });
h.enable();
setInterval(() => {
  metrics.gauge('eventloop.p99_ms', h.percentile(99) / 1e6);
  metrics.gauge('eventloop.utilization', performance.eventLoopUtilization().utilization);
  h.reset();
}, 10_000);
```

If loop delay spikes line up with the latency spikes, profile CPU: `node --cpu-prof`, the Chrome DevTools inspector, or flame graphs from production (Datadog/Pyroscope continuous profiling). Typical culprits: `JSON.parse`/`stringify` of huge payloads, sync crypto (`bcrypt` sync, `pbkdf2Sync`), catastrophic regex backtracking, big sorts and maps, sync `fs`, and template rendering.

Fixes: paginate or stream, move CPU work to **worker threads** or a separate service, use async crypto, and fix the regex.

**2. Is it GC?** Check `--trace-gc` or the GC metrics. Large heaps with many short-lived objects cause long pauses. Reduce allocations, cache less, or tune `--max-old-space-size`.

**3. Is it a pool?**

- **libuv thread pool** (4 threads by default) is shared by `fs`, `dns.lookup`, async crypto and zlib. Raise `UV_THREADPOOL_SIZE`, or cache DNS.
- **DB pool too small**, or one slow query holding connections. Check acquire wait time.
- **Outbound HTTP**: no keep-alive, socket limits, missing timeouts. Use an undici `Agent` with keep-alive and set timeouts.

**4. Is it downstream?** Distributed traces show which span dominates slow requests. Add timeouts, retries with jitter, hedging, or caching.

**5. Infrastructure**: CPU throttling from container limits (check cgroup `throttled_time`), noisy neighbors, cold starts, and uneven load balancing.

**Follow-up:** Why does a CPU limit of 0.5 cores in Kubernetes cause p99 spikes even at low average CPU? (CFS quota throttling pauses the whole process for the rest of each period.)
