## Hints

- `fetch` resolves on a 500. What does TanStack Query consider a successful query?
- Why is a toast in `QueryCache({ onError })` better than one in every component's error branch?
- Should a 404 or 403 be retried three times?
- User A logs out and user B logs in on the same tab. What is still in the cache?
- You open a v4 codebase and see `cacheTime`, `isLoading` and `useQuery(key, fn, options)`. What changes in v5?

## Answer

> In a big app, the hard part with TanStack Query is that everyone fetches, caches and handles errors the same way. Wrap `fetch` in one API function that throws on HTTP errors, because `fetch` doesn't. Keep keys and fetchers together in `queryOptions` factories per resource. Handle errors once in the `QueryCache`, don't retry 4xx responses, send 401s to sign-in, and call `queryClient.clear()` on logout. In legacy code, v5 changed the API to a single object, renamed `cacheTime` to `gcTime` and removed `onSuccess` from `useQuery`.

Basics (keys, `staleTime`, invalidation, optimistic updates) are in #530. In a large app the hard part is **consistency**: every team member should fetch, cache and handle errors the same way.

**1. An API layer that throws.** `fetch` doesn't reject on HTTP errors (#513), so a query function that only calls `res.json()` turns a 500 into "success". Wrap it once:

```ts
export class HttpError extends Error {
  constructor(public status: number, public body: unknown) { super(`HTTP ${status}`); }
}

export async function api<T>(path: string, init?: RequestInit): Promise<T> {
  const res = await fetch(`/api${path}`, { ...init, headers: { 'Content-Type': 'application/json', ...init?.headers } });
  if (!res.ok) throw new HttpError(res.status, await res.json().catch(() => null));
  return res.status === 204 ? (undefined as T) : res.json();
}
```

TanStack Query passes an `AbortSignal` to the query function. Forward it to `fetch` so unmounted or superseded queries are cancelled.

**2. `queryOptions` and key factories per resource** (v5): key, fetcher and options live together, and the same object is used by `useQuery`, `useSuspenseQuery`, `prefetchQuery` and a typed `getQueryData`.

```ts
export const orderKeys = {
  all: ['orders'] as const,
  list: (f: OrderFilters) => [...orderKeys.all, 'list', f] as const,
  detail: (id: string) => [...orderKeys.all, 'detail', id] as const,
};

export const orderQueries = {
  list: (f: OrderFilters) => queryOptions({
    queryKey: orderKeys.list(f),
    queryFn: ({ signal }) => api<Page<Order>>(`/orders?${toSearch(f)}`, { signal }),
    placeholderData: keepPreviousData,
  }),
  detail: (id: string) => queryOptions({
    queryKey: orderKeys.detail(id),
    queryFn: ({ signal }) => api<Order>(`/orders/${id}`, { signal }),
  }),
};
// components: useQuery(orderQueries.detail(id)); after a mutation: invalidateQueries({ queryKey: orderKeys.all })
```

Thin custom hooks (`useOrder(id)`) on top are fine; avoid hooks that hide which key they use.

**3. Global defaults and error handling**

```ts
const queryClient = new QueryClient({
  queryCache: new QueryCache({
    onError: (error, query) => {
      if (error instanceof HttpError && error.status === 401) return signIn();   // session expired
      if (query.meta?.silent) return;
      toast.error(messageFor(error));                                             // once per query, not per component
    },
  }),
  mutationCache: new MutationCache({ onError: (e) => toast.error(messageFor(e)) }),
  defaultOptions: {
    queries: {
      staleTime: 30_000,
      retry: (count, e) => !(e instanceof HttpError && e.status < 500) && count < 2,   // don't retry 4xx
      refetchOnWindowFocus: true,
    },
  },
});
```

- **Error boundaries:** `throwOnError: true` (or a function such as `(e) => e.status >= 500`) rethrows into the nearest error boundary. Combine it with `QueryErrorResetBoundary` so "Try again" retries the query.
- **Mutations:** `mutate` handles errors through callbacks; `mutateAsync` returns a promise you must `catch`. Invalidate in `onSuccess`/`onSettled`, or centrally via `meta: { invalidates: [orderKeys.all] }` in `MutationCache`.
- **Logout:** call `queryClient.clear()` so the next user never sees the previous user's cached data.
- **Devtools** (`@tanstack/react-query-devtools`) in development: the fastest way to learn which keys an unfamiliar app uses (#640).

**4. v4 → v5 (what you'll see in legacy code)**

| v4 | v5 |
|---|---|
| `useQuery(key, fn, opts)` overloads | Single object: `useQuery({ queryKey, queryFn, ... })` |
| `cacheTime` | `gcTime` |
| `status: 'loading'`, `isLoading` | `status: 'pending'`, `isPending` (`isLoading` = `isPending && isFetching`) |
| `keepPreviousData: true` | `placeholderData: keepPreviousData` |
| `useErrorBoundary` | `throwOnError` |
| `onSuccess`/`onError`/`onSettled` on `useQuery` | Removed. Use `QueryCache` callbacks, or derive state in render. (Still available on `useMutation`.) |
| `suspense: true` | `useSuspenseQuery` |
| `<Hydrate>` | `<HydrationBoundary>` |
| `useInfiniteQuery` without initial param | `initialPageParam` required |

Requires React 18+. There's an official codemod. Even older code may use `react-query` v3 (package renamed to `@tanstack/react-query` in v4, where keys also had to become arrays).

**Follow-up:** "Why did they remove `onSuccess` from `useQuery`?" It ran once per observer and not when data came from the cache, so people used it to sync server data into `useState`, which caused bugs. Derive values in render or use `select` instead.
