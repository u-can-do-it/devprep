## Hints

- Is state tied to the component function, or to its position in the rendered tree?
- What happens to a child's state if the parent renders `<Form />` and later renders `<Form />` again in the same spot with different props?
- Which special prop tells React that two elements are different "things"?

## Answer

React stores state **by position in the tree**, not in the component itself. On each render it compares the new tree with the previous one:

- **Same component type at the same position:** state is **kept**, even if props change.
- **Different type at that position** (for example `<Form>` replaced by `<p>`), or the component is removed: state is **destroyed**, including the whole subtree.

That's why this classic bug happens: switching the chat recipient keeps the old draft message:

```jsx
<Chat contact={selected} />   // same position, same type → draft persists
```

**Ways to reset:**

1. **Change the `key`.** A new key means a new identity, so React remounts the component with fresh state:

   ```jsx
   <Chat key={selected.id} contact={selected} />
   ```

2. **Render at different positions**, for example `{isA ? <Counter key="a" /> : <Counter key="b" />}` or two separate conditional branches.
3. **Lift the state up** and reset it from the parent, if the parent needs control anyway.

**Avoid** resetting state with a `useEffect` that watches a prop. It renders stale state first and then corrects it.

**The opposite need, keeping state while hidden:** React 19.2's `<Activity mode="hidden">` hides a subtree and unmounts its effects but **preserves its state**. That suits tabs or a back-navigation cache. You can also store the state higher up.

**Pitfall:** defining a component *inside* another component's body creates a new type on every render, so its state resets each time. Always define components at module level.
