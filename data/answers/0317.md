## Hints

- Why shouldn't you `pip install` packages into the system Python?
- What does `requirements.txt` without pins fail to guarantee, and what fixes it?
- Which single file describes a modern Python project's metadata, dependencies and tool config?

## Answer

**Virtual environments** isolate each project's interpreter and packages, so projects with conflicting versions don't break each other or the OS Python.

```bash
python -m venv .venv && source .venv/bin/activate   # built-in
pip install -r requirements.txt
```

**`pyproject.toml`** is the standard project file. It declares metadata, dependencies, the build backend and tool settings (ruff, pytest, mypy).

```toml
[project]
name = "orders-api"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = ["fastapi>=0.115", "sqlalchemy>=2.0"]

[dependency-groups]
dev = ["pytest", "ruff", "mypy"]
```

You need both **declared ranges** (`pyproject.toml`) and a **lockfile** with exact versions and hashes of the whole tree, for reproducible installs.

Tools:

- **pip + venv**: built in and minimal. For locking, use `pip-tools` (`pip-compile`) or `pip freeze`, which is crude.
- **Poetry**: an all-in-one dependency manager, lockfile, build and publish tool. Mature and widely used.
- **uv** (Astral, written in Rust): very fast. It manages Python versions, venvs, `uv.lock`, scripts and tools (`uvx`). It has become the default choice for many new projects.

```bash
uv init && uv add fastapi && uv add --dev pytest
uv sync --locked      # CI: install exactly the lockfile
uv run pytest
```

Practices: commit the lockfile, pin the Python version (`.python-version`), separate dev dependencies, install with the frozen lockfile in Docker and CI, and scan with `pip-audit`. The standard `pylock.toml` format (PEP 751) aims to make lockfiles portable between tools.

**Follow-up:** Library vs application: should a library pin exact versions? (No. Libraries declare compatible ranges; applications lock.)
