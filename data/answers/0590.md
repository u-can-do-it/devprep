## Hints

- `HttpClient` is `IDisposable`, so `using var client = new HttpClient()` looks right. What happens to the TCP connection after it's disposed?
- If you keep one static `HttpClient` forever instead, what happens when the DNS record of the target changes?
- Which requests are safe to retry automatically, and what makes retries dangerous during an outage?

## Answer

**The two classic problems**

1. **Socket exhaustion.** Creating and disposing an `HttpClient` per request closes its connection pool. Closed sockets stay in `TIME_WAIT` for a while, so under load you run out of ports (`SocketException`), and every request pays for a new TCP and TLS handshake.
2. **Stale DNS.** A single static `HttpClient` reuses pooled connections forever, so it never notices that the service moved to a new IP (blue-green deploys, failover).

The fix is to reuse connections but recycle them periodically. With a plain singleton client you can do that on the handler:

```csharp
private static readonly HttpClient Client = new(new SocketsHttpHandler
{
    PooledConnectionLifetime = TimeSpan.FromMinutes(2)   // reconnect, re-resolve DNS
});
```

**`IHttpClientFactory`**

In ASP.NET Core, let the factory manage handlers: it pools and recycles them, integrates with DI, logging and configuration, and lets you add a pipeline of `DelegatingHandler`s.

```csharp
builder.Services.AddHttpClient<GitHubClient>(c =>      // typed client
{
    c.BaseAddress = new Uri("https://api.github.com/");
    c.DefaultRequestHeaders.UserAgent.ParseAdd("my-app");
})
.AddHttpMessageHandler<AuthHeaderHandler>()            // e.g. adds a bearer token
.AddStandardResilienceHandler();                       // retries, timeouts, circuit breaker

public sealed class GitHubClient(HttpClient http)
{
    public Task<Repo?> GetRepoAsync(string name, CancellationToken ct) =>
        http.GetFromJsonAsync<Repo>($"repos/{name}", ct);
}
```

| Style | How |
|---|---|
| Basic | inject `IHttpClientFactory`, call `CreateClient()` |
| Named | `AddHttpClient("github", ...)`, `CreateClient("github")` |
| Typed | a class that takes `HttpClient` in its constructor; the clearest option |

Typed clients are registered as **transient**. Don't capture one in a singleton, or you're back to never recycling the handler.

**Resilience**

`Microsoft.Extensions.Http.Resilience` (built on Polly v8) adds `AddStandardResilienceHandler()`, which stacks:

- a **rate limiter** (concurrency),
- a **total request timeout** across all attempts,
- **retries** with exponential backoff and jitter, for transient errors (5xx, 408, 429, network failures),
- a **circuit breaker** that stops calling a failing dependency for a while so it can recover and your threads aren't stuck waiting,
- a **per-attempt timeout**.

Things to get right:

- **Only retry idempotent requests** (GET, PUT, DELETE), or POSTs that carry an idempotency key. A retried payment POST can charge twice.
- Respect `Retry-After` on 429 and 503.
- Pass the `CancellationToken` so a cancelled request stops retrying (#575).
- Without limits, retries multiply load on a struggling service (a retry storm); backoff, jitter and the circuit breaker exist to prevent that.

**Follow-up:** with retries added, which timeout limits how long a caller waits? (The resilience handler runs inside the `HttpClient`, so `HttpClient.Timeout`, 100 seconds by default, caps the whole call including retries; the pipeline's per-attempt and total timeouts apply inside that. Set the total timeout deliberately and keep `HttpClient.Timeout` at least as long, so it doesn't cut retries short.)
