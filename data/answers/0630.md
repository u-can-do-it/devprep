## Hints

- Which PostgreSQL type would you use for an invoice amount, and what does the `pg` driver or Prisma give you back in JavaScript?
- Split 100.00 PLN into three equal instalments. Where does the extra grosz go?
- `timestamp` vs `timestamptz` vs `date`: which one for "approved at", and which one for "invoice due date"?
- Why does `new Date('2026-11-05')` sometimes display as November 4th?
- What happens to a `Date` or a `Decimal` when it goes through `JSON.stringify` to the frontend?

## Answer

Billing and project management ("rozliczenia") mean amounts, VAT, deadlines and schedules. Floating point and time zones cause most of the bugs.

### Money

**Never use `number` (float) for money arithmetic:** `0.1 + 0.2 !== 0.3` (#153), and errors accumulate across invoice lines.

**Storage in PostgreSQL:**

- `numeric(14, 2)` (exact decimal) for amounts, or `bigint` in **minor units** (grosze: 123.45 PLN = 12345).
- Always store the **currency** next to the amount. For conversions, store the exchange rate, its date and source (e.g. the NBP table) with the transaction instead of looking it up again later.
- Avoid the Postgres `money` type: it depends on the `lc_monetary` setting and holds no currency.

**In TypeScript:**

- The `pg` driver returns `numeric` and `bigint` as **strings** (to avoid precision loss); Prisma returns `Prisma.Decimal` (decimal.js) for `Decimal` columns.
- Either do arithmetic with a decimal library (`decimal.js`, `big.js`, Dinero.js) or in **integer minor units** (exact up to `Number.MAX_SAFE_INTEGER` grosze, about 90 trillion PLN; use `bigint` beyond that).
- **Over the wire,** send amounts as strings (`"1234.50"`) or minor-unit integers, never floats. `superjson` in tRPC (#617) keeps `Decimal` typed; with plain JSON, validate and convert at the boundary (#625).
- **Rounding:** decide the mode explicitly. Commercial rounding (half-up) is usual on Polish invoices; banker's rounding (half-to-even, the default for .NET `Math.Round` and Python's `round`, #608) is different. Decide whether VAT is computed per line or on the net total of each VAT rate (Polish invoices normally use the total per rate; confirm with accounting), document it and use it consistently, because the two can differ by a grosz.
- **Allocation:** split 100.00 into 3 → 33.34 + 33.33 + 33.33. Distribute the remainder explicitly so the parts add up to the total.
- **Display** with `Intl.NumberFormat('pl-PL', { style: 'currency', currency: 'PLN' })`, which gives `1 234,50 zł`.

```ts
const toGrosze = (s: string) => { const [z, g = ''] = s.split('.'); return Number(z) * 100 + Number(g.padEnd(2, '0')); };   // assumes validated non-negative "123.45"
const allocate = (total: number, parts: number) =>
  Array.from({ length: parts }, (_, i) => Math.floor(total / parts) + (i < total % parts ? 1 : 0));
allocate(10000, 3); // [3334, 3333, 3333]
```

### Dates and times

**Two different kinds of value:**

- An **instant** (when something happened): `approvedAt`, `createdAt`. Store as **`timestamptz`**. Postgres stores it in UTC and converts on input/output, and JS `Date` is also an instant.
- A **calendar date** with no time of day: invoice issue date, due date, contract end, leave days. Store as **`date`**, and pass it around as a `"YYYY-MM-DD"` string or a `Temporal.PlainDate`, **not** as a `Date` at midnight.
- (A **wall-clock time in a zone**, like "every day at 8:00 Warsaw time": store the local time and the IANA zone, `Europe/Warsaw`.)

`timestamp` without time zone stores a wall-clock value without a zone; the same row means different instants depending on who reads it. Avoid it for events.

**Classic off-by-one bugs:**

- `new Date('2026-11-05')` (date only) is parsed as **UTC** midnight, while `new Date('2026-11-05T00:00')` is **local** midnight. Displaying the first one in a UTC-5 browser shows November 4th.
- `node-postgres` parses `date` columns into a `Date` at **local** midnight of the server, and Prisma maps `@db.Date` to UTC midnight. Either way a date can shift by a day when the server and client zones differ. Return dates as strings (`pg.types.setTypeParser(1082, (v) => v)`) or format them carefully.
- `toISOString()` always prints UTC, so `new Date(2026, 10, 5).toISOString()` in Warsaw is `2026-11-04T23:00:00.000Z`.

**Practices:**

- Run servers and databases in **UTC** (`TZ=UTC`); convert to `Europe/Warsaw` only for display (`Intl.DateTimeFormat('pl-PL', { timeZone: 'Europe/Warsaw' })`) and for business rules that are defined in local time.
- **DST:** "remind at 8:00 every day" must be scheduled in the zone (`timeZone: 'Europe/Warsaw'`, #626), not as a fixed UTC hour, or it moves by an hour twice a year. Adding "1 day" is not always 24 hours.
- **Deadlines** such as "payment within 14 days" or "approve within 3 business days" need a calendar of working days and Polish public holidays, not `+ 14 * 86400000`.
- Use a date library for arithmetic and zones (date-fns with `@date-fns/tz`, Luxon, Day.js), or the **Temporal** API where available (#172): `Temporal.PlainDate` for dates, `Temporal.ZonedDateTime` for zone-aware times.
- **JSON** turns `Date` into an ISO string; the client gets a string, not a `Date`. Parse it at the boundary (`z.coerce.date()`, or `superjson`).

**Follow-up:** an invoice has 3 lines with 23% VAT. Summing per-line VAT gives 69.01 PLN, while computing VAT on the net total gives 69.00. Which one is right? (Ask accounting rather than guess: Polish rules normally compute VAT on the net total of each rate, which gives 69.00 here. Whatever the method, apply it everywhere and store the computed VAT amounts instead of recalculating them later, so a code change doesn't alter issued invoices.)
