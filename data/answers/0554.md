## Hints

- A producer publishes to an exchange, not to a queue. What decides which queues get the message?
- When is a message removed from a queue, and what happens to it if the consumer crashes halfway through?
- A message fails every time it's processed. How do you stop it from blocking the queue or spinning forever?

## Answer

**Model (AMQP 0-9-1):** producers publish to an **exchange** with a **routing key**; **bindings** route the message to **queues**; consumers read from queues.

| Exchange type | Routes to | Example |
|---|---|---|
| `direct` | queues bound with exactly that key | `pdf.generate` |
| `topic` | key patterns: `*` one word, `#` zero or more | `appointment.*.cancelled`, `appointment.#` |
| `fanout` | every bound queue | broadcast a config change |
| `headers` | header matches | rarely needed |

**Queue types:** **quorum** queues (Raft-replicated, the default choice for anything you can't lose; classic mirrored queues were removed in RabbitMQ 4.0), classic queues for transient data, and **streams** (an append-only, replayable log, closer to Kafka, #424).

**Not losing messages**

- **Publisher confirms:** the broker acknowledges once the message is safely stored; without them a publish can vanish on a broker restart. Mark messages persistent and use durable queues.
- **Publishing after a DB commit:** a crash between commit and publish loses the event, so use the transactional outbox (#484).
- **Manual consumer acks:** ack only after processing. Unacked messages are redelivered when the consumer's channel closes, so delivery is **at least once** and consumers must be **idempotent** (dedupe by message id in the same transaction as the side effect, or make the operation naturally idempotent).

**Flow control:** `prefetch` limits unacked messages per consumer. Without it the broker pushes everything to the first consumer and memory explodes; with it, work spreads fairly. Scale consumers on queue depth.

**Retries and poison messages:** `nack` with `requeue=true` redelivers immediately, which hot-loops on a message that always fails. Prefer **delayed retries** through a TTL queue that dead-letters back, then a parking-lot queue for manual inspection. Quorum queues also have a `delivery-limit` that dead-letters (or drops) a message after too many redeliveries. Use one retry queue per delay: per-message TTLs in one queue only expire at the head.

```ts
import amqp from 'amqplib';

const MAX_ATTEMPTS = 5;
const conn = await amqp.connect(process.env.AMQP_URL!);
const ch = await conn.createConfirmChannel();

await ch.assertExchange('appointments', 'topic', { durable: true });
await ch.assertQueue('notifications', { durable: true, arguments: { 'x-queue-type': 'quorum' } });
await ch.bindQueue('notifications', 'appointments', 'appointment.booked');
await ch.assertQueue('notifications.retry', {
  durable: true,
  arguments: {
    'x-message-ttl': 30_000,                         // wait 30 s...
    'x-dead-letter-exchange': '',                    // ...then go back to the work queue
    'x-dead-letter-routing-key': 'notifications',
  },
});
await ch.assertQueue('notifications.parking', { durable: true });

await ch.prefetch(10);
await ch.consume('notifications', async (msg) => {
  if (!msg) return;                                  // the broker cancelled the consumer
  const attempt = Number(msg.properties.headers?.attempt ?? 1);
  try {
    const event = JSON.parse(msg.content.toString());
    await processOnce(event.id, () => scheduleReminders(event));   // idempotent
    ch.ack(msg);
  } catch (err) {
    const target = attempt >= MAX_ATTEMPTS ? 'notifications.parking' : 'notifications.retry';
    ch.sendToQueue(target, msg.content, {
      persistent: true,
      messageId: msg.properties.messageId,
      headers: { ...msg.properties.headers, attempt: attempt + 1, lastError: String(err) },
    });
    await ch.waitForConfirms();                      // republish safely, then drop the original
    ch.ack(msg);
  }
});
```

A crash between the republish and the ack can deliver the message twice, which the idempotent consumer absorbs.

**Ordering:** a queue is FIFO, but several consumers, `prefetch > 1` and retries reorder processing. For per-entity order use **single active consumer**, a consistent-hash exchange that partitions by key, or design handlers to tolerate reordering (versions, timestamps).

**Operations:** one long-lived connection per process with channels per consumer (never a connection per message); handle reconnects (amqplib doesn't reconnect by itself, so use a wrapper such as `amqp-connection-manager`); monitor queue depth, unacked count, consumer utilisation and parking-lot size, and alert on the age of the oldest message.

**RabbitMQ vs Kafka (#424):** RabbitMQ for task distribution and flexible routing with per-message acks; Kafka for high-volume event streams that many consumers replay.

**Follow-up:** a consumer calls an SMS provider that is down for an hour. What happens to the queue, and how would you design for it? (Retries with growing delays, a circuit breaker that pauses consuming, alerts on depth and age, and messages that are still valid when they're finally processed: check the appointment wasn't cancelled.)
