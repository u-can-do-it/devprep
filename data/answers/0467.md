## Hints

- When you change the "orders" feature, how many top-level folders do you have to touch?
- What should one feature be allowed to import from another?
- How do you stop a rule like "shared code never imports from features" from eroding over time?

## Answer

Small apps can group files **by type** (`components/`, `hooks/`, `services/`). In a large app that scatters every feature across the whole tree, so the usual answer is to group **by feature** (or domain) and set clear dependency rules.

```
src/
  app/                    # bootstrapping: routes, providers, global styles, error boundaries
  features/
    orders/
      api/                # requests, query hooks, DTO → model mapping
      components/
      hooks/
      model/              # types, slices, pure business logic
      index.ts            # the feature's public API
    checkout/
  shared/
    ui/                   # design-system components, no business logic
    lib/                  # generic utilities (dates, formatting, http client)
    config/
```

**Rules that make it scale:**

- **Colocation:** code that changes together lives together, including tests, stories and styles next to the component.
- **Public API per feature:** other code imports from `features/orders`, never from `features/orders/components/OrderRow`. Internals can change freely.
- **One-way dependencies:** `app → features → shared`. `shared` never imports from features, and features don't reach into each other's internals; if two features need the same thing, move it down to `shared` or into an `entities` layer. **Feature-Sliced Design** formalises this with layers (`app`, `pages`, `widgets`, `features`, `entities`, `shared`).
- **Enforce it with tooling**, not code review: `eslint-plugin-boundaries`, `import/no-restricted-paths`, dependency-cruiser, or Nx module boundary rules.
- **A typed API layer** inside each feature: components never call `fetch` directly, and DTOs are mapped to UI models at the edge, so a backend change touches one place.
- **State close to where it's used:** server state in a query cache, URL state in the URL, local state in components, and a global store only for truly shared client state.
- **Be careful with barrel files:** one `index.ts` per feature is useful, but barrels everywhere slow builds and tests and hurt tree shaking.

**At larger scale:** split into packages in a **monorepo** (pnpm workspaces with Turborepo or Nx): `@acme/ui`, `@acme/api-client`, and apps that consume them. That gives build caching, affected-only CI and explicit dependencies. Micro-frontends are the next step only when team autonomy and independent deployment require it.

**Signs the structure is failing:** circular imports, "utils" folders with 3,000 lines, changes that touch ten folders, and nobody knowing where new code should go. Write the conventions down in the README or an ADR.
