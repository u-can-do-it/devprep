## Hints

- What's the fastest way to stop the bleeding, and is it always the right one?
- What makes a rollback impossible or dangerous?
- Which mechanisms let you "turn off" a change without a deploy at all?

## Answer

> When a deploy breaks production, the first job is to restore service, not to find the root cause. Rolling back to the previous artifact is usually fastest, but only if the old version still works with the current database schema and data. Roll forward with a small fix when a rollback would break things, for example after a migration that isn't backward compatible. Feature flags, canary releases and expand/contract migrations reduce how often you face this choice. Practise rollbacks so they're routine.

**First priority: restore service, then find the root cause.**

**Roll back** (redeploy the previous known-good artifact) when:
- the issue clearly started with this deploy,
- the previous version is still **compatible with the current state**: database schema, message formats, external contracts.

It's usually the fastest and safest option, *if* you build once and keep immutable, versioned artifacts (`api:1.4.2`), so rolling back is just pointing the deployment at the old tag (`kubectl rollout undo`, re-promoting the previous release, or swapping back in blue-green).

**Roll forward** (ship a fix) when:
- a rollback would break things: a non-backward-compatible migration already ran, data was written in a new format, or a partner already depends on a new API,
- the fix is tiny, well understood, and the pipeline is fast.

**Even better: avoid needing either.**
- **Feature flags / kill switches:** turn the feature off in seconds without a deploy.
- **Canary releases with automatic rollback** on error-rate or latency SLO breaches (Argo Rollouts, Flagger, cloud deploy tools).
- **Expand/contract migrations** so the previous version always works with the schema.

**During the incident:** declare it, assign an incident lead, communicate status, prefer the most reversible action, and don't debug in production while users are hurting.

**Afterwards:** a blameless postmortem. Why did tests, canary and monitoring not catch it? Add the missing test, alert or guardrail.

**Pitfall:** a rollback that has never been practised. Rehearse it so it's one well-known command, not improvisation at 2 a.m.
