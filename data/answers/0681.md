## Hints

- Is AsyncStorage encrypted?
- Where does the operating system itself keep passwords and keys?
- What do you need when the data is 50,000 records that you filter and sort offline?

## Answer

> Pick storage by the kind of data. Small non-sensitive settings go to a key-value store: AsyncStorage (async, simple) or MMKV (synchronous and much faster). Secrets such as refresh tokens go to the system keystore through SecureStore or Keychain. Large structured data that you query goes to SQLite. Files go to the file system. None of these replaces the server as the source of truth, and nothing on a rooted device is fully safe.

| Storage | Model | Encrypted | Use for |
|---|---|---|---|
| AsyncStorage | async key-value, strings | no | settings, flags, small caches |
| MMKV | sync key-value, via JSI | optional | the same, plus persisted state that must be ready at first render |
| SecureStore / Keychain | key-value, small values | yes, by the OS | tokens, keys, credentials |
| SQLite (`expo-sqlite`, `op-sqlite`) | relational database | optional (SQLCipher) | large or relational data, offline-first (#696) |
| File system | files | no (app sandbox) | downloads, photos, documents, exports |

**AsyncStorage**

- Simple and everywhere. Values are strings, so you `JSON.stringify`.
- Asynchronous: on startup the first render happens before stored values are read, so you need a loading state.
- Not encrypted. Never put tokens or personal data here. This is the mobile equivalent of putting a token in `localStorage`.

**MMKV**

- Calls are synchronous through JSI (#693) and very fast.
- Good as the storage for Zustand `persist` or a persisted TanStack Query cache, because the state is there at the first render.
- Supports encryption, but the encryption key must itself live in the keystore.

**Secure storage**

```ts
import * as SecureStore from 'expo-secure-store';

await SecureStore.setItemAsync('refreshToken', token, {
  keychainAccessible: SecureStore.WHEN_UNLOCKED_THIS_DEVICE_ONLY,
});
const token = await SecureStore.getItemAsync('refreshToken');
```

- iOS stores the value in the Keychain. Android encrypts it with a key held in the Android Keystore, which can be hardware-backed.
- Meant for small values. Keep them to a couple of kilobytes; for a large secret, store an encryption key here and the encrypted data elsewhere.
- `requireAuthentication: true` makes the OS release the value only after Face ID or a fingerprint (#697).
- On iOS, Keychain items can survive an app uninstall. Clear them on first launch after install if that matters.

**SQLite**

- Real queries, indexes and transactions, on the device.
- Use it with a typed layer (Drizzle ORM, or a sync library such as WatermelonDB or PowerSync).
- Plan schema migrations from day one. Users skip versions, so migrations must run in order from any old version.

**File system**

- A **document** directory for user data that must persist, and a **cache** directory that the OS may clear when space is low.
- Store the path in your database, not the file contents.

**Rules**

- **Tokens:** access token in memory, refresh token in secure storage.
- **Never store:** passwords, card numbers, or more personal data than the feature needs.
- **Backups:** the OS may back up app data to the cloud. Exclude sensitive files, and use the "this device only" keychain options.
- **Logout:** clear every store, including caches and the query cache.
- **Server state:** a persisted cache is a copy for fast start and offline reading, not the truth (#212).

**Follow-up:** the app persists a Zustand store to AsyncStorage, and after an update some users crash on launch. What happened? (The persisted shape no longer matches the code. Version the persisted state, write a migration, and fall back to defaults when the data is invalid.)
