## Hints

- When a Client Component calls a function marked `'use server'`, what actually travels over the network?
- Is a Server Action reachable only from the button you wired it to?
- What do you have to check inside the action that you'd also check in a REST endpoint?

## Answer

A **Server Action** is an async function marked with `'use server'` that runs on the server but can be called from the client — passed to `<form action>`, a button's `formAction`, or invoked from an event handler. Next.js compiles it into an **HTTP POST endpoint** with an opaque action ID; the client sends serialized arguments and receives the result (plus an updated RSC payload if you revalidate).

```ts
'use server';
import { z } from 'zod';

const Schema = z.object({ title: z.string().min(1).max(200) });

export async function createPost(formData: FormData) {
  const session = await auth();                 // 1. authenticate
  if (!session) throw new Error('Unauthorized');
  const { title } = Schema.parse({ title: formData.get('title') }); // 2. validate
  await db.post.create({ data: { title, authorId: session.userId } }); // 3. authorize via owner
  revalidatePath('/posts');
}
```

**Benefits:** no hand-written API routes, works with progressive enhancement (forms submit before JS loads), integrates with `useActionState`, `useOptimistic` and cache revalidation.

**Security concerns** — treat every action as a **public API endpoint**:

- **Anyone can call it** with any arguments, not just your UI. Hiding the button is not authorization.
- **Always authenticate and authorize inside the action** — don't rely on middleware/proxy or the page having checked it.
- **Validate input** (Zod, Valibot); TypeScript types are erased at runtime.
- **IDOR:** never trust IDs from the client without checking ownership.
- **Closures:** variables captured from a Server Component are sent to the client encrypted, but don't capture secrets — pass IDs, re-fetch on the server.
- **CSRF:** Next.js only accepts POST and compares `Origin` with `Host`; configure `serverActions.allowedOrigins` behind proxies.
- Return minimal data and safe error messages; add rate limiting for expensive actions.

**Follow-up:** keep actions thin by delegating to a data-access layer that enforces auth in one place.
