## Hints

- Does the App Router have a built-in `i18n` config like the Pages Router had?
- Where in the URL would the locale live, and which file would read it?
- How do you decide which language to show someone visiting `/` for the first time?

## Answer

The App Router has **no built-in i18n routing**. The `i18n` key in `next.config` belongs to the Pages Router. Instead, you put the locale in the URL yourself:

```text
app/
  [lang]/
    layout.tsx      -> <html lang={lang}>
    page.tsx
    products/[id]/page.tsx
proxy.ts            -> detects locale, redirects / to /en or /pl
```

**1. Locale segment and static params:**

```tsx
// app/[lang]/layout.tsx
export function generateStaticParams() {
  return [{ lang: 'en' }, { lang: 'pl' }, { lang: 'de' }];
}

export default async function Layout({ children, params }: LayoutProps<'/[lang]'>) {
  const { lang } = await params;
  return <html lang={lang}><body>{children}</body></html>;
}
```

**2. Locale detection in `proxy.ts`:** if the path has no locale, read a `NEXT_LOCALE` cookie or the `Accept-Language` header (negotiate with a library such as `@formatjs/intl-localematcher`) and redirect to `/pl/...`. Respect the user's explicit choice over the header.

**3. Translations loaded on the server:** keep dictionaries in a `server-only` module and load just the current locale with a dynamic `import()`. Server Components render translated text, so **dictionaries don't ship to the browser**. Pass only the strings a Client Component needs.

**4. SEO:** set `alternates.languages` (hreflang) and canonical URLs in `generateMetadata`, and translate titles and descriptions.

**5. Formatting:** use `Intl.DateTimeFormat`, `Intl.NumberFormat` and ICU plurals instead of string concatenation.

In practice many teams use **`next-intl`**, which packages the proxy, routing helpers, typed messages, and Server/Client Component APIs.

**Pitfalls:** unvalidated `lang` params (call `notFound()` for unsupported locales); hydration mismatches when server and client format dates differently; and translating slugs, which needs a mapping per locale.

**Follow-up:** subpath (`/pl`), subdomain (`pl.example.com`) or separate-domain strategies all work with proxy rewrites. Subpaths are simplest for SEO and hosting.
