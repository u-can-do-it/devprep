## Hints

- What goes wrong if a customer's address is copied onto every order row and then changes?
- What does it mean for a column to depend on only part of a composite key?
- Which costs grow when every read needs five joins?

## Answer

**Normalization** organizes tables so each fact is stored **once**, preventing update, insert and delete anomalies.

- **1NF** – atomic values, no repeating groups. Not `tags = 'a,b,c'` or `phone1, phone2, phone3`; use a separate table.
- **2NF** – 1NF + every non-key column depends on the **whole** primary key. In `order_items(order_id, product_id, qty, product_name)`, `product_name` depends only on `product_id` → move it to `products`.
- **3NF** – 2NF + no **transitive** dependencies: non-key columns depend only on the key. In `employees(id, dept_id, dept_name)`, `dept_name` depends on `dept_id` → move it to `departments`.

Rule of thumb: "every column depends on the key, the whole key, and nothing but the key". (BCNF tightens 3NF further; rarely asked in detail.)

**Denormalization** deliberately duplicates data to make reads cheaper:

- Cached aggregates: `posts.comment_count` instead of `COUNT(*)` on every page view.
- Snapshot data that *should* not change: copy price and shipping address onto the order at purchase time (that's correct modelling, not just optimization).
- Read models / materialized views for dashboards and reporting.
- Document databases and analytics warehouses (star schemas) are denormalized by design.

```sql
CREATE MATERIALIZED VIEW daily_revenue AS
SELECT date_trunc('day', created_at) AS day, SUM(total) AS revenue
FROM orders GROUP BY 1;
-- REFRESH MATERIALIZED VIEW CONCURRENTLY daily_revenue;  (needs a unique index)
```

The cost: you must keep copies in sync (triggers, application code, events), and they can drift. Start normalized; denormalize where measurements show a hot read path.
