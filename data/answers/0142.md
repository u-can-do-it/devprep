## Hints

- What do you limit by — user, API key, IP, endpoint — and where does the check run?
- How do fixed window, sliding window, and token bucket algorithms differ at the window boundaries?
- With 50 API servers, where does the shared counter live, and how do you avoid a race between "read" and "increment"?

## Answer

**Requirements:** limit requests per client key (API key/user, IP as fallback) with per-plan rules, e.g. 100 req/min with bursts. Low added latency (< few ms), works across many gateway instances, and returns `429 Too Many Requests` with `Retry-After` and `RateLimit-*` headers.

**Algorithms:**

- **Fixed window counter:** simple, but allows 2x bursts at window boundaries.
- **Sliding window log:** exact, but stores every timestamp — memory heavy.
- **Sliding window counter:** weighted blend of current and previous window; good accuracy, cheap.
- **Token bucket:** tokens refill at rate r up to capacity b; each request consumes one. Naturally allows controlled bursts — the most common choice.
- **Leaky bucket:** smooths output to a constant rate (a queue).

**Distributed design:** enforce in the API gateway/middleware. State lives in **Redis** (sharded by key), and the check-and-decrement must be **atomic** — a Lua script or a single atomic command — to avoid races.

```lua
-- token bucket: KEYS[1]=bucket, ARGV: rate, capacity, now_ms
local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local rate, cap, now = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
local tokens = tonumber(b[1]) or cap
local ts = tonumber(b[2]) or now
tokens = math.min(cap, tokens + (now - ts) / 1000 * rate)
local allowed = tokens >= 1
if allowed then tokens = tokens - 1 end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(cap / rate * 1000))
return allowed and 1 or 0
```

**Tradeoffs to discuss:**

- **Latency vs accuracy:** a Redis round-trip per request; at very high scale use local in-memory buckets that sync periodically (slightly over-admits).
- **Failure mode:** if Redis is down — fail open (availability) or fail closed (protection)? Usually fail open with a local fallback limit.
- **Multi-region:** per-region limits or async-replicated counters; global exactness is expensive.
- Layering: coarse IP limits at the CDN/WAF for DDoS, fine-grained per-key limits in the gateway, separate quotas for expensive endpoints.
- Use server time in the script (`redis.call('TIME')`) if app server clocks may drift.

**Follow-up:** "How would you let enterprise customers change limits without a deploy?" — rules in a config store, cached in gateways and refreshed on change.
