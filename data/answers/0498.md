## Hints

- What did the prompt ask for exactly, including the implicit requirements?
- How do you check that the code works, not just that it looks right?
- How do you rank problems so the reader knows what matters most?
- Would someone else reach the same score from your comments alone?

## Answer

This is the core task in AI training and code evaluation work (Alignerr, Outlier, DataAnnotation, in-house eval teams). The goal is a **judgement that is correct, specific and consistent**, written so that a researcher can turn it into training data.

**1. Read the prompt before the answer.** List the explicit requirements (language, framework, function signature, output format) and the implicit ones (handles empty input, no `any`, idiomatic for the stated version). Note anything ambiguous: a good answer should ask or state its assumption.

**2. Verify, don't eyeball.** Run the code or at least type-check it. Try the edge cases: empty, `null`, large input, concurrency, error paths. Check that every API and option actually exists in the stated version.

**3. Score against the usual rubric dimensions:**

| dimension | question |
|---|---|
| Instruction following | Did it do what was asked, in the requested format and constraints? |
| Correctness | Does it compile and behave correctly, including edge cases? |
| Type safety / quality | Casts, `any`, wrong generics, missing narrowing, readability, idioms |
| Completeness | Is anything missing (imports, error handling, tests asked for)? |
| Explanation | Is the prose accurate, concise, and consistent with the code? |
| Honesty and safety | No invented APIs, no false claims ("this is fully tested"), no insecure patterns |

**4. Rank problems by severity:**

- **Critical:** wrong result, doesn't compile, security hole, ignores the main instruction
- **Major:** misses an important edge case, unsafe types at a boundary, outdated API
- **Minor:** style, naming, verbosity

One critical issue outweighs any number of minor ones. Don't punish style when the answer is correct, and don't reward a well-written explanation of wrong code.

**5. Write the feedback:**

1. One-line verdict ("Doesn't meet the requirement: the generic constraint makes the function unusable with nested keys.")
2. Issues from most to least severe, each with **where** (line or snippet), **why** it matters, and **the fix**
3. What the answer did well, briefly, if it affects the score
4. Make sure the score matches the comments

Bad: "Types could be better." Good: "Line 4 casts `res.json()` to `User` with `as`; a 404 body would be accepted as a user. Validate with a schema or a type guard."

**6. Side-by-side comparisons (A vs B):** decide on the most important difference first, state it, then justify the strength of the preference. "B is slightly better" and "B is much better" mean different things to the people training the model.

**7. Rewrites / ideal answers:** when asked to write the ideal response, write what an expert would actually ship: minimal, correct, typed, with a short explanation of trade-offs. No filler.
