## Hints

- Who is the real owner of "the list of orders": your component or the database?
- What happens to cached API data when another user or tab changes it?
- How much code does correct caching, deduplication, retries and refetch-on-focus take if you write it with `useEffect` and `useState`?

## Answer

**Client state** is owned by the browser and is synchronous: whether a modal is open, form drafts, the selected tab, theme. Your app is the source of truth.

**Server state** is a **cached snapshot of data owned elsewhere**. It's async, shared, and can become **stale** without your app knowing. It needs:

- caching and **deduplicating** identical requests
- background **refetching** (on focus, reconnect, interval) and stale-while-revalidate
- **invalidation** after mutations
- retries, pagination, infinite scroll, prefetching
- loading and error states, optimistic updates and rollback

Storing it in Redux or Context with hand-written `useEffect` fetching means building all of that yourself, usually with race-condition bugs.

**TanStack Query** (or SWR, RTK Query, Apollo for GraphQL) handles it with a cache keyed by query keys:

```tsx
const { data, isPending, error } = useQuery({
  queryKey: ['orders', userId],
  queryFn: () => fetchOrders(userId),
  staleTime: 30_000,
});

const qc = useQueryClient();
const cancel = useMutation({
  mutationFn: cancelOrder,
  onSuccess: () => qc.invalidateQueries({ queryKey: ['orders', userId] }),
});
```

**Typical 2026 split:**

- server state → TanStack Query, or Server Components / framework loaders
- shared client state → Zustand, Jotai, or Redux Toolkit (often small once server state moves out)
- local UI state → `useState`/`useReducer`
- shareable view state (filters, pagination) → URL search params

**Follow-up:** once you separate server state, the "global store" usually shrinks dramatically. That's the main argument against putting everything in Redux.
