## Hints

- Which TypeScript features silence the compiler instead of satisfying it?
- Where does `any` enter a program without anyone writing the word `any`?
- How many times should a generic type parameter appear in a signature to be useful?
- What happens when the model doesn't know which version of a library you use?

## Answer

AI-generated TypeScript usually compiles. The problems are in places where it **compiles because the type checker was switched off locally**, or where types say more than the runtime guarantees.

**1. Assertions instead of proof**

```ts
const config = loadConfig() as Config;     // hides missing or misspelled fields
const user = data as unknown as User;      // double cast: "trust me" with extra steps
const el = document.getElementById('app')!; // crashes if the element is missing
// @ts-ignore                                // hides the error and every future one
```

Prefer `satisfies` for literals, type guards or schema validation for data, and an explicit `if (!el) throw ...` for `!`. If an `@ts-...` comment is really needed, use `@ts-expect-error` with a reason.

**2. `any` leaking in silently**

`res.json()`, `JSON.parse`, `catch (e)` without `useUnknownInCatchVariables`, untyped third-party code, and `Function` / `object` / `{}` types. Annotating the result (`const u: User = await res.json()`) is still an unchecked cast.

**3. Generics that don't do anything, or are wrongly constrained**

```ts
function first<T>(arr: any[]): T { return arr[0]; }         // T is only a return-type cast
function get<T, K extends string>(o: T, k: K) { return o[k]; } // error: K must be keyof T
function get2<T, K extends keyof T>(o: T, k: K): T[K] { return o[k]; } // correct
```

Rule of thumb: a type parameter should appear **at least twice**, otherwise it's a hidden cast or unnecessary.

**4. Types that are too wide or don't narrow**

`status: string` instead of `'idle' | 'loading' | 'error'`; optional fields everywhere instead of a discriminated union; a `switch` over a union with no `never` exhaustiveness check; `arr[0].name` without `noUncheckedIndexedAccess`.

**5. Outdated or invented APIs**

`React.FC` with implicit `children` (removed in React 18 types), `forwardRef` where React 19 accepts `ref` as a prop, utility types that don't exist (`ValueOf<T>`), options for the wrong library version. Check against the versions in `package.json`.

**6. Async typing mistakes**

`Promise<void>` that forgets to `await`, `forEach(async ...)` that nobody waits for, `Promise.all` results typed by hand instead of inferred, missing `AbortSignal` handling.

**How to review quickly:**

1. Run `tsc --noEmit` with `strict` (and ideally `noUncheckedIndexedAccess`), plus ESLint with `@typescript-eslint` rules such as `no-explicit-any`, `no-non-null-assertion`, `no-unsafe-*` and `switch-exhaustiveness-check`.
2. Search the diff for `as `, `any`, `!`, `@ts-`, `Function`, `object`.
3. For each generic, ask "what does this parameter connect?"
4. Find the **trust boundaries** (network, storage, user input, `postMessage`) and check that there's runtime validation there.
5. Write one test or type test for the tricky case (`expectTypeOf`, `// @ts-expect-error` lines) instead of trusting the explanation.
