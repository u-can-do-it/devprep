## Hints

- If you pass a token through `ARG` or `ENV`, can someone recover it from the final image?
- Should the same image run in staging and production? What differs between them?
- Where can an environment variable leak once the container is running?

## Answer

**Principle:** build one image and inject environment-specific config at **runtime**. Secrets must never be baked into layers.

**Build time** (e.g. a private npm token to install packages):
- `ARG`/`ENV` values are visible in `docker history` and image metadata, so they're **not** safe for secrets.
- Use BuildKit **secret mounts**, which exist only for that `RUN` step and are never stored in a layer:

```dockerfile
# syntax=docker/dockerfile:1
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci
```
```bash
docker build --secret id=npmrc,src=$HOME/.npmrc -t api .
```

**Runtime:**
- **Non-secret config** goes in environment variables (12-factor): `-e`, `env_file`, Kubernetes ConfigMaps.
- **Secrets** come from a secret manager (AWS Secrets Manager, GCP Secret Manager, Vault) or orchestrator secrets (Kubernetes Secrets, ideally encrypted at rest or synced via External Secrets / CSI driver). Mounting them as **files** (`/run/secrets/db_password`) is often safer than env vars.

Why files can be better than env vars: env vars are inherited by child processes, show up in `docker inspect` and crash dumps, and are easy to log by accident (`console.log(process.env)`).

**Also:** validate config at startup and fail fast on missing values, rotate secrets without rebuilding images, and give each service only the secrets it needs.

**Pitfall:** `COPY . .` with a `.env` in the context. Add it to `.dockerignore`.
