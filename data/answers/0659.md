## Hints

- When three agents finish at the same time, what becomes the bottleneck?
- Two agents work in the same checkout. What do they share besides the files?
- Which tasks split cleanly, and which only look independent?

## Answer

> Parallel agents pay off for independent, well-specified tasks with automated checks: chores, migrations by module, test coverage, trying two approaches. They don't help with tightly coupled changes, because your review, not typing, is the bottleneck. Give each agent its own git worktree and branch, or a cloud sandbox, so they can't overwrite each other. Split the work by files, land shared contracts first, and limit work in progress to what you can actually review.

**When it pays off**

- **Good:** tasks that don't touch the same files and can be verified by tests or CI: dependency upgrades, a codemod per package, adding tests to untested modules, fixing a list of lint errors, one bug each with a reproduction. Also running **two approaches** to the same problem and keeping the better one, and research in parallel (several subagents read different parts of the system).
- **Bad:** one feature cut into pieces that share types, state or a schema; anything that needs your design decisions along the way; tasks without a feedback loop, where each agent needs you watching.

Writing was never the slow part. With four agents you get four diffs to **review**, and review doesn't parallelise. Unreviewed agent output is inventory, not progress.

**Ways to run agents in parallel**

| Form | Isolation | Good for |
|---|---|---|
| Subagents inside one session | separate context, same working tree | searching, analysis, review; avoid parallel writes to the same files |
| Several local sessions in git worktrees | separate directory and branch each | two to four tasks you steer yourself |
| Background or cloud agents | a sandbox per task, result is a PR | well-specified chores you review later |
| Orchestrated workflow | a script or lead agent fans out to workers | a large migration over many modules |

**Git worktrees** give each agent its own checkout of the same repository:

```bash
git worktree add ../shop-export -b feat/export
git worktree add ../shop-deps   -b chore/deps
cd ../shop-export && pnpm install    # each worktree needs its own node_modules
git worktree list
git worktree remove ../shop-deps     # after the branch is merged
```

One branch can be checked out in only one worktree. Claude Code can create one for a session (`claude --worktree export`).

**What agents share even with separate worktrees**

- **Ports:** two dev servers on 3000. Take the port from an environment variable.
- **The database and other services:** a migration from one agent breaks the other's tests. Use a database per worktree (a schema or container name based on the branch).
- **Untracked files:** `.env` and local config aren't in a new worktree; copy or generate them in a setup script.
- **Caches, Docker container names, and machine resources** such as CPU during test runs.

**Avoiding conflicts**

- **Split by ownership:** one writer per set of files. If two tasks need the same file, they aren't parallel.
- **Contract first:** land shared types, the API schema or the migration on `main`, then fan out work that depends on it.
- **Small PRs, merged quickly, rebased often.** Long-lived agent branches conflict like long-lived human branches.
- **The same instructions for all:** the brief, `CLAUDE.md` and skills, so five agents don't produce five styles (#541).

**Keeping review manageable**

- Limit work in progress to what you can review the same day.
- Require **evidence** in every result: tests run, output shown, a screenshot for UI.
- Let CI do the first pass, and review by risk (#545).
- Count the cost: tokens grow with the number of agents, and failed runs are paid for too (#662).

**Follow-up:** two agents each produced a correct PR, and the PRs conflict in a shared file. What does that tell you about how you split the work? (The file was a shared contract. Land that part first, or give both tasks to one agent in sequence.)
