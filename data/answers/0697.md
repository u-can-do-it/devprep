## Hints

- Can a mobile app keep a client secret?
- If the login page is shown inside your app's WebView, what could your app read?
- Does a successful Face ID check prove anything to your server?

## Answer

> A mobile app is a public client: it can't keep a secret, so it uses the Authorization Code flow with PKCE (#116). The login page opens in the system browser, not in a WebView, and returns to the app through a redirect link. The refresh token goes to the Keychain or Keystore, and the access token stays in memory. Refresh with rotation, and make sure only one refresh runs at a time. Biometrics unlock the stored token on the device. They don't replace server authentication.

**The flow**

1. The app creates a random `code_verifier` and its hash, the `code_challenge`.
2. It opens the identity provider's authorize URL in the **system browser** (`ASWebAuthenticationSession` on iOS, Custom Tabs on Android), with the challenge and a `state` value.
3. The user signs in there: password manager, passkeys, MFA and an existing SSO session all work.
4. The provider redirects to the app (`https://example.com/auth/callback` as a verified link, or `com.example.app:/callback`) with a one-time code.
5. The app exchanges the code plus the `code_verifier` for tokens. No client secret is involved.

Libraries: `expo-auth-session` or `react-native-app-auth`. Don't write the flow by hand.

**Why not a WebView**

- The app hosts the page, so it could read the password. Users can't tell a real login page from a fake one inside an app.
- No shared browser session, so no SSO, and password managers and passkeys work poorly.
- Google and other providers block sign-in from embedded WebViews.
- The standard for native apps (RFC 8252) says to use the system browser.

A first-party app with its own backend and no external identity provider often has a native email and password form that calls its own API. That is acceptable. The rule is about not collecting another provider's credentials in your UI.

**Why PKCE**

Another app can register the same custom URL scheme and receive the redirect (#684). Without the `code_verifier`, which never left your app, the stolen code is useless.

**Token storage**

| Token | Where | Why |
|---|---|---|
| Access token (minutes) | memory | short-lived; refetched after restart |
| Refresh token (days or weeks) | Keychain / Keystore through SecureStore | encrypted by the OS (#681) |
| Anything | not AsyncStorage, not logs, not crash reports | plain text |

**Refresh**

- Refresh shortly before expiry, or on a 401, then repeat the failed request once.
- **Single flight:** when five requests fail at once, one refresh runs and the others wait for it. With refresh token rotation, parallel refreshes invalidate each other and log the user out.
- If the refresh fails with an auth error, the session is over: clear state and show sign-in. If it fails because of the network, keep the session and retry later.
- After the app returns to the foreground, check the token before the first request (#682).

**Logout**

Revoke the refresh token on the server, delete it from secure storage, clear the query cache and local databases, unregister the push token (#683), and reset navigation to the sign-in screens (#674).

**Biometrics**

```ts
await SecureStore.setItemAsync('refreshToken', token, { requireAuthentication: true });
// Reading it later shows the Face ID / fingerprint prompt
```

- This is **local unlock**: the OS releases the stored token only to the device owner. The server still authenticates the token.
- Don't implement it as `if (await authenticate()) showApp()`. That check is easy to bypass on a compromised device. Tie the secret itself to the biometric check, as above.
- Offer a fallback (device passcode or a full login), and expect the stored item to become invalid when the user changes their enrolled biometrics.
- **Passkeys** are different: a real cryptographic login that the server verifies.

**Other points**

- If the app offers third-party social login, App Store rules also require an equivalent privacy-focused option such as Sign in with Apple.
- Hide sensitive screens in the app switcher, and require re-authentication for dangerous actions.

**Follow-up:** after adding refresh token rotation, some users are logged out randomly. Why? (Two refreshes ran in parallel, or a refresh response was lost and the app retried with the old token, and the server treated the reuse as theft. Use single-flight refresh, and a short grace period for the previous token on the server.)
