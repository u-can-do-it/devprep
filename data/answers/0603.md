## Hints

- What does the compiler turn an `async` method into, and what happens at an `await` whose task is already complete?
- Who decides on which thread the code after an `await` runs, and what does `ConfigureAwait(false)` change?
- If a `ValueTask` can be backed by a reusable object, what happens when you await it a second time after that object was reused?

## Answer

`async`/`await` is a compiler feature on top of a small runtime contract: **awaitables**, **method builders** and **schedulers**.

**1. The state machine**

The compiler rewrites an `async` method into a struct that implements `IAsyncStateMachine` (a class in Debug builds). Locals that live across an `await` become fields, and the body becomes a `MoveNext()` method with a `switch` on a `state` field. The method itself creates the struct, calls `builder.Start()` (which runs `MoveNext` **synchronously** until the first incomplete await) and returns `builder.Task`.

```csharp
// Roughly what `var data = await ReadAsync(); return Parse(data);` becomes
void MoveNext()
{
    TaskAwaiter<string> awaiter;
    if (state == 0) { awaiter = _awaiter; state = -1; goto resume; }

    awaiter = ReadAsync().GetAwaiter();
    if (!awaiter.IsCompleted)                       // fast path: already done → no suspension, no allocation
    {
        state = 0; _awaiter = awaiter;
        builder.AwaitUnsafeOnCompleted(ref awaiter, ref this);   // boxes `this` to the heap (once) and registers MoveNext as the continuation
        return;
    }
resume:
    try { builder.SetResult(Parse(awaiter.GetResult())); }       // GetResult rethrows with the original stack trace
    catch (Exception ex) { builder.SetException(ex); }
}
```

Key consequences: a method that completes synchronously costs almost nothing (and with `ValueTask<T>` allocates nothing); the first real suspension allocates the boxed state machine; exceptions are stored on the task and rethrown by `await` through `ExceptionDispatchInfo`, so you see the first exception with its original stack, while `Task.Wait()` wraps them in `AggregateException`.

**2. Where the continuation runs**

When the awaited task completes, the awaiter decides how to resume:

| Situation | Continuation runs on |
|---|---|
| `SynchronizationContext.Current` is set (WPF/WinForms UI thread, old ASP.NET) | posted back to that context, e.g. the UI thread |
| a non-default `TaskScheduler.Current` | queued to that scheduler |
| neither (ASP.NET Core, console apps, thread pool code) | usually inline on the thread that completed the task, or a thread pool thread |
| `ConfigureAwait(false)` | ignores the context and scheduler |

`ExecutionContext` (and so `AsyncLocal<T>`, `Activity.Current`, culture) **always** flows, whatever `ConfigureAwait` says. The classic deadlock is `.Result` on a thread that owns a single-threaded context: the continuation is posted to the blocked thread, which waits for the continuation. ASP.NET Core has no `SynchronizationContext`, so it doesn't deadlock that way, but blocking still starves the thread pool (#594). Library code should still use `ConfigureAwait(false)` because it can't know its caller.

**3. The thread pool**

Worker threads take work from per-thread local queues (LIFO for the owner, other threads steal from them) and a global FIFO queue. The pool keeps at least `Environment.ProcessorCount` threads and adds more with a **hill-climbing** algorithm that measures throughput as it changes the thread count, plus starvation detection. Both inject threads **slowly**, which is why a burst of sync-over-async calls can leave requests queued for seconds. Awaited I/O doesn't occupy a thread at all: sockets complete through IOCP on Windows and epoll/kqueue on Linux/macOS, and only the continuation is queued.

**4. `ValueTask` and `IValueTaskSource`**

`ValueTask<T>` is a struct holding one of: a result, a `Task<T>`, or an `IValueTaskSource<T>` plus a `short` token. The third form lets a long-lived object (for example a socket's receive operation, or your own type built on `ManualResetValueTaskSourceCore<T>`) be **reset and reused** for the next operation, so a hot path allocates nothing.

That is why a `ValueTask` may be consumed **only once**: after the first await the source may already be serving another operation. Awaiting again, awaiting concurrently, or calling `.Result` before completion can return another operation's result or throw (the token check catches some, not all, misuse).

```csharp
ValueTask<int> vt = stream.ReadAsync(buffer, ct);
int n = await vt;                 // ✅ once
// await vt;                      // ❌ undefined: the source may be reused
Task<int> t = stream.ReadAsync(buffer, ct).AsTask();   // need to await it twice or store it? convert to a Task first
```

You can also pool the state machine boxes of your own `async ValueTask` methods with `[AsyncMethodBuilder(typeof(PoolingAsyncValueTaskMethodBuilder<>))]`, but measure first: pooling trades allocation for contention and retained memory.

**Follow-up:** why does `async void` crash the process when it throws? (There's no task to store the exception on, so it's rethrown on the captured `SynchronizationContext` or the thread pool, where nobody can catch it.)
