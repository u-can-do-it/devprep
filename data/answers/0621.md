## Hints

- Which states can a document be in, and which transitions are allowed from each one? Who may trigger each transition?
- How do you model "invoices above 50,000 PLN need the director too" without hard-coding it in `if` statements?
- Two managers click "Approve" at the same second. What must not happen?
- An approver is on holiday for two weeks. What does the system do?
- How do you send the notification email without sending it for a transaction that was rolled back?

## Answer

Approval workflows ("obiegi akceptacji") are the bread and butter of internal systems: cost invoices, offers, purchase orders, leave requests, contract changes. In an interview, walk through it like a small system design (#538): requirements, data model, the state machine, concurrency, notifications and audit.

**1. Clarify requirements with the business** (#491, #557): who approves what, is it sequential or parallel, what happens on rejection (back to the author or end), thresholds by amount or department, deadlines and escalation, delegation (substitutes), can an approved document be edited, what must be auditable.

**2. Model the process as a state machine,** not as scattered booleans (`isApproved`, `isSent`):

```
DRAFT --submit--> PENDING_APPROVAL --approve (last step)--> APPROVED
                     |   \--approve (more steps)--> PENDING_APPROVAL (next step)
                     \--reject--> REJECTED --revise--> DRAFT
DRAFT/PENDING --cancel--> CANCELLED
```

```ts
const transitions = {
  DRAFT:            { submit: 'PENDING_APPROVAL', cancel: 'CANCELLED' },
  PENDING_APPROVAL: { approve: 'PENDING_APPROVAL' /* or APPROVED */, reject: 'REJECTED', cancel: 'CANCELLED' },
  REJECTED:         { revise: 'DRAFT' },
} as const;
```

One function `applyTransition(doc, action, user)` checks that the transition is allowed, that the user may perform it, runs side effects and records history. A discriminated union (#27) or a library like XState helps when it grows.

**3. Data model (PostgreSQL):**

```
documents          id, type, status, amount, department_id, author_id, current_step, version
approval_steps     id, document_id, step_no, approver_id | role, decision (PENDING/APPROVED/REJECTED),
                   decided_by, decided_at, comment, due_at
approval_rules     document_type, min_amount, department_id, step_no, approver_role   ← configurable
delegations        user_id, substitute_id, valid_from, valid_to
document_events    id, document_id, action, from_status, to_status, actor_id, payload jsonb, created_at  ← audit
```

- On **submit**, resolve the rules into concrete `approval_steps` for this document (a snapshot). Changing the rules later doesn't change documents already in flight.
- **Parallel approval** (any one of three, or all three) is a step with several rows and a policy (`ANY`/`ALL`).
- **Delegation:** when listing "my approvals", include documents assigned to users who delegated to me for today; record `decided_by` (the substitute) separately from the assigned approver.

**4. Concurrency and integrity:**

- Use **optimistic locking** (`WHERE id = $1 AND version = $2`, #337, #620) or `SELECT ... FOR UPDATE` on the document so two clicks don't both advance the step or approve twice.
- Make actions **idempotent**: approving an already approved step returns the current state, not an error or a duplicate event.
- Status changes and the event row are written **in one transaction**.
- Lock editing: once submitted, the document content is read-only, or editing it resets the approval.

**5. Authorization** (#379, #524, #622): "can approve" is not just a role. The user must be the current step's approver (or their substitute), must not be the author (segregation of duties), and the document must be in the right state. Check it on the server for every action; the UI only hides buttons.

**6. Notifications:**

- Triggered by events: "waiting for your approval", "rejected with comment", "approved", reminders before `due_at`, escalation after it.
- Write the notification (or a domain event) **in the same transaction** as the state change and deliver it from a worker: the outbox pattern (#484) with a job queue (#535). Then a rollback can't send a ghost email, and a mail outage doesn't fail the approval.
- Channels: in-app list (a `notifications` table with `read_at`), email, Teams via Microsoft Graph (#624). Let users pick digests to avoid spam.
- Reminders and escalations: a scheduled job that queries steps with `due_at < now()` and no decision.

**7. Audit and history:** the `document_events` table is append-only: who did what, when, from which state, with which comment. The UI shows it as a timeline. For field-level history ("who changed the amount"), store diffs in the event payload or use a trigger-based history table.

**8. Testing:** unit-test the transition function exhaustively (every state × action × role); integration-test the concurrency case with two parallel requests against a real database (#628).

**Follow-up:** the board wants to change the threshold from 50,000 to 30,000 PLN. What happens to the 40 invoices currently waiting? (Nothing, because steps were snapshotted at submit time. If they want it retroactive, that's an explicit migration they decide on, not a side effect of editing a rule.)
