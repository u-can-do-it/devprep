## Hints

- Should a user's feed be computed when they open the app, or precomputed when someone posts — and what breaks for a celebrity with 50M followers?
- How do you paginate a feed that keeps changing while the user scrolls?
- Which parts of notification delivery must be reliable, and which can be best-effort?

## Answer

**Requirements:** users follow others; a home feed shows recent posts (chronological or ranked); notifications for likes, comments, follows via in-app, push, and email. Assume ~100M DAU, read-heavy, feed load < 200 ms, eventual consistency acceptable.

**Feed generation:**

- **Fan-out on write (push):** when a user posts, a worker appends the post ID to each follower's feed cache (e.g. a Redis list/sorted set capped at ~1,000 IDs). Reads are fast, but celebrities cause massive write amplification.
- **Fan-out on read (pull):** at read time, fetch recent posts from everyone you follow and merge. Cheap writes, expensive reads.
- **Hybrid (standard answer):** push for normal users; for accounts above a follower threshold, pull their posts at read time and merge them in. Skip fan-out to inactive users.

**Data flow:** Post service writes to the DB → publishes `PostCreated` to Kafka → fan-out workers update feed caches. Feed service reads post IDs, hydrates them from the post cache (batch get), applies ranking, and filters blocked or deleted content.

**Pagination:** cursor-based (`?cursor=<last_post_id_or_score>`), never offset, so new posts don't cause duplicates or skips.

**Ranking:** start chronological; later a ranking service scores candidates (affinity, recency, engagement) — two-stage: candidate generation, then ranking.

**Notifications:**

- Events (like, comment, follow) → queue → notification service, which applies user preferences, dedupes, and **aggregates** ("Ann and 12 others liked your post").
- Store in a per-user notifications table (unread counts in cache) for the in-app inbox.
- Delivery channels through separate queues: real-time via WebSocket/SSE gateway, push via APNs/FCM, email via provider — each with retries, backoff, and dead-letter queues.
- Idempotency keys to avoid duplicate pushes; rate-limit and respect quiet hours.

**Scaling and reliability:** shard feed caches by user ID; rebuild a cold or evicted feed from the DB on demand; multi-region with async replication. Monitor fan-out lag and delivery success rates.

**Follow-up:** "How do you handle a deleted post already fanned out?" — filter at read time (tombstones) instead of trying to remove it from millions of feeds.
