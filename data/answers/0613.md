## Hints

- Resizing 1,000 images and fetching 1,000 URLs: which needs more threads, and which needs none while it waits?
- If you start 10,000 `HttpClient` calls in a loop and `WhenAll` them, what breaks first?
- Three of ten tasks fail. How many exceptions does `await Task.WhenAll(tasks)` throw?

## Answer

**Two different things**

| | Asynchrony | Parallelism |
|---|---|---|
| Goal | don't hold a thread while **waiting** (I/O, timers) | finish **CPU work** sooner on several cores |
| Costs while running | nothing while waiting: the OS signals completion (#603) | one thread per core, at best |
| Tools | `async`/`await`, `Task.WhenAll` over I/O calls | `Parallel.For`/`ForEach`, PLINQ, `Task.Run` |
| Scales to | thousands of concurrent operations | `Environment.ProcessorCount` |

I/O-bound work (database, HTTP, files) is **async**: await the real async API, never wrap it in `Task.Run` (#574). CPU-bound work (image resizing, compression, big in-memory calculations) is **parallel**: split it over cores. Many jobs are both: fetch 100 reports (async, concurrent), then render them (parallel).

**CPU-bound: `Parallel` and PLINQ**

```csharp
Parallel.ForEach(images, new ParallelOptions { MaxDegreeOfParallelism = Environment.ProcessorCount }, Resize);

var totals = orders.AsParallel().WithDegreeOfParallelism(4).Select(ComputeTotal).ToList();   // PLINQ; AsOrdered() keeps order
```

`Parallel.For`/`ForEach` and PLINQ partition the work over thread pool threads and **block the caller** until done. On a web server that takes threads from other requests, so reserve them for real CPU work, cap the degree of parallelism and don't nest them. `Task.Run` moves one unit of CPU work off the current thread: right in a UI app (keep the UI thread free) or to run two independent computations at once; in ASP.NET Core it only swaps one pool thread for another.

**I/O-bound fan-out: concurrency with a limit**

```csharp
// unbounded: 10,000 requests in flight; exhausts the connection pool, trips rate limits, times out
var users = await Task.WhenAll(ids.Select(id => client.GetUserAsync(id, ct)));

// bounded (.NET 6+): at most 16 in flight, async body, cancellation built in
var results = new ConcurrentBag<User>();
await Parallel.ForEachAsync(ids, new ParallelOptions { MaxDegreeOfParallelism = 16, CancellationToken = ct },
    async (id, token) => results.Add(await client.GetUserAsync(id, token)));
```

`Parallel.ForEachAsync` is the usual answer. The manual version is a `SemaphoreSlim(16)` with `WaitAsync`/`Release` around each call (#592); `Channel<T>` with N consumers fits when producers and consumers run at different speeds (#600). Collect results into a thread-safe collection or an array indexed by position, never a shared `List<T>` (#592).

**Starting tasks: two traps**

- `foreach (var id in ids) await ProcessAsync(id);` is **sequential**. Start them, then await: `var tasks = ids.Select(ProcessAsync).ToList(); await Task.WhenAll(tasks);`
- `ids.ForEach(async id => await ProcessAsync(id))`, or a `Select(async …)` nobody awaits, fires and forgets: the lambda becomes `async void` or the tasks are dropped, exceptions vanish and the method returns before the work is done (#574).

**How `Task.WhenAll` reports failures**

It waits for **all** tasks even after one fails and doesn't cancel the others (link a `CancellationTokenSource` and cancel it in `catch` if you want that). `await`ing it throws **only the first** exception; the full set is on the task:

```csharp
var all = Task.WhenAll(tasks);
try { await all; }
catch
{
    var failures = all.Exception!.InnerExceptions;       // AggregateException with every failure
    log.LogError("{Failed} of {Total} items failed", failures.Count, tasks.Count);
    throw;
}
```

Related: `Task.WhenAny` for "first one wins" (for timeouts prefer `task.WaitAsync(timeout, ct)`, #575) and `Task.WhenEach` (.NET 9) to handle results as each task completes.

**Threads directly** (`new Thread`, `TaskCreationOptions.LongRunning`) are for the rare dedicated loop that shouldn't occupy a pool thread; application code almost never needs them.

**Sizing:** `Environment.ProcessorCount` honours container CPU limits (a pod limited to 2 CPUs sees 2), so CPU parallelism adapts on its own. I/O concurrency limits should come from the dependency (connection pool size, the other service's rate limit), not from the CPU count.

**Follow-up:** `Parallel.ForEach(orders, async o => await db.SaveChangesAsync())` compiles. What's wrong? (The lambda is `async void`, so `ForEach` returns before any save finishes and exceptions crash the process; and one `DbContext` is used from many threads at once (#585). Use `Parallel.ForEachAsync` with a scope per item (#581), or a bounded channel.)
