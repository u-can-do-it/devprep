## Hints

- Who signs the app that users download from Google Play: you or Google?
- You published version 2.3.0 and it has a serious bug. Can you roll back like a web deploy?
- How long after your release do users still run the previous version?

## Answer

> A release is a signed native binary with an increased build number, uploaded to each store, tested through TestFlight or a Play testing track, reviewed, and rolled out in stages. You can't roll back a store release, and users update slowly, so you protect yourself with staged rollouts, feature flags, over-the-air fixes and a backward-compatible API. Automate building, signing and uploading with EAS or fastlane, so that a release is one command or one merge.

**Signing**

- **Android:** you sign the upload with an **upload key**. Google re-signs with the app signing key it holds (Play App Signing). The format is an **AAB**, from which Play generates optimised APKs per device.
- **iOS:** a **distribution certificate** and a **provisioning profile** tied to the bundle id and capabilities such as push.
- EAS creates and stores these for you. With fastlane, `match` keeps them in an encrypted repository. Never commit keystores or put them in chat.

**Version numbers**

| | Shown to users | Must increase with every upload |
|---|---|---|
| Android | `versionName` (2.3.0) | `versionCode` (integer) |
| iOS | `CFBundleShortVersionString` (2.3.0) | `CFBundleVersion` (build number) |

Let the build system increment the build number automatically.

**Testing channels**

- **TestFlight:** internal testers get builds within minutes. External testers need a short beta review.
- **Google Play:** internal testing, closed testing, open testing, then production.
- Internal distribution builds (ad hoc, APK) for QA and stakeholders.

**Review**

- Apple reviews every version, usually within a day or two, and may reject: missing demo credentials, a broken flow, unclear permission texts, payment rule violations.
- Google also reviews, with more automation.
- Plan for review time, and don't release on a Friday evening.
- Keep store metadata current: screenshots, the privacy labels and data safety form, the account deletion option, and the required target API level on Android.

**Rollout**

- **Staged rollout** on Play (1%, 10%, 50%, 100%) and **phased release** on iOS (seven days). Watch the crash-free rate (#687) and halt if it drops.
- **No rollback.** You can stop a rollout, but users who already updated keep the build. The fix is a new version, or an over-the-air update for JS-only bugs (#699).
- **Feature flags** let you ship code turned off and enable it remotely (#123).
- **Forced update:** the backend returns a minimum supported version, and old apps show an "update required" screen. Build this before you need it.

**Old versions stay alive**

Many users don't update for weeks or months. So the API must stay compatible with old app versions, breaking changes need versioning, and you should track which versions are still active before removing an endpoint.

**Environments**

- Separate app variants for development, staging and production, with different bundle ids, names and icons, so they install side by side.
- Configuration is baked in at build time. Values in the bundle are public (`EXPO_PUBLIC_*`), so no secrets (#698).

**Automation**

```bash
eas build --platform all --profile production --auto-submit
```

- **EAS:** build profiles in `eas.json`, cloud builds, managed credentials, submit to both stores, and workflows for CI.
- **fastlane:** the same steps scripted on your own CI. iOS builds need macOS runners.
- A typical pipeline: merge to `main` builds and ships to internal testers; a tag or release branch builds the store version, uploads it, and starts a staged rollout.

**Follow-up:** a critical bug is found in production on a Saturday. What are your options, fastest first? (Turn the feature off with a flag; ship an over-the-air update if the bug is in JS; halt the staged rollout; submit a fixed build and ask Apple for an expedited review.)
