## Hints

- The `account` object is only present on one call of the `jwt` callback. Which one, and what do you copy out of it?
- Who should attach the `Authorization: Bearer` header: the browser or the Next.js server?
- Two requests notice an expired access token at the same moment and both refresh it. What does Keycloak do with the second refresh if rotation with reuse detection is on?
- A Server Component calls `auth()` and the token gets refreshed. Where does the new token go?
- The user clicks "Log out", then "Log in" and is signed in again without a password prompt. Why?

## Answer

> When a Next.js app signs users in through Keycloak and calls backend APIs for them, the access token should never reach browser JavaScript. Store it in the encrypted JWT in the `jwt` callback, and have server code add it to API calls. Refresh it in the same callback when it expires, keeping in mind that parallel refreshes can race. Augment the session types once instead of casting everywhere. On logout, also end the Keycloak session, or the next sign-in succeeds silently.

**Setup.** Register a confidential client in Keycloak (standard flow, redirect URI `https://app.example.com/api/auth/callback/keycloak`) and configure the provider with `issuer = https://sso.example.com/realms/<realm>`. Auth.js discovers the endpoints from `/.well-known/openid-configuration`.

**1. Keep tokens server-side.** Copy them from `account` into the encrypted JWT at sign-in. Don't copy `access_token` into the session unless the browser really has to call APIs directly.

```ts
// auth.ts (v5; v4 is the same inside authOptions.callbacks)
callbacks: {
  async jwt({ token, account, profile }) {
    if (account) {                                   // first sign-in only
      return {
        ...token,
        access_token: account.access_token,
        refresh_token: account.refresh_token,
        expires_at: account.expires_at,              // seconds since epoch
        id_token: account.id_token,                  // needed for logout
        roles: (profile as any)?.realm_access?.roles ?? [],
      };
    }
    if (Date.now() < (token.expires_at - 30) * 1000) return token;   // still valid (30 s margin)
    return refreshAccessToken(token);
  },
  session({ session, token }) {
    session.user.roles = token.roles;
    session.error = token.error;                     // let the UI react to a failed refresh
    return session;
  },
},
```

**2. Refresh token rotation.**

```ts
async function refreshAccessToken(token: JWT): Promise<JWT> {
  try {
    const res = await fetch(`${process.env.AUTH_KEYCLOAK_ISSUER}/protocol/openid-connect/token`, {
      method: 'POST',
      headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
      body: new URLSearchParams({
        grant_type: 'refresh_token',
        refresh_token: token.refresh_token!,
        client_id: process.env.AUTH_KEYCLOAK_ID!,
        client_secret: process.env.AUTH_KEYCLOAK_SECRET!,
      }),
    });
    const data = await res.json();
    if (!res.ok) throw data;
    return {
      ...token,
      access_token: data.access_token,
      expires_at: Math.floor(Date.now() / 1000) + data.expires_in,
      refresh_token: data.refresh_token ?? token.refresh_token,   // keep the old one if not rotated
      error: undefined,
    };
  } catch {
    return { ...token, error: 'RefreshTokenError' };
  }
}
```

On the client, `if (session?.error === 'RefreshTokenError') signIn('keycloak')`.

**Known pitfalls:**

- **Races.** Parallel requests can refresh with the same refresh token. With rotation and reuse detection the second one fails and the user is kicked out. Mitigations: refresh slightly early in one place (the proxy runs before page requests), deduplicate in-flight refreshes per user, or allow a short reuse window on the IdP.
- **Server Components can't set cookies.** A token refreshed while `auth()` runs in a Server Component is used for that render but not saved. Let `proxy.ts`/middleware (which can write the cookie) or Route Handlers do the refresh.
- **Cookie size.** Access, refresh and ID tokens with many roles can exceed 4 KB. Auth.js splits the cookie into chunks, but proxies may reject large headers (#633). Store fewer claims, or switch to database sessions.

**3. Calling backend APIs.** The browser calls your Next.js server (Route Handler, Server Action or Server Component), which adds the token:

```ts
// app/api/orders/route.ts
import { getToken } from 'next-auth/jwt';

export async function GET(req: NextRequest) {
  const token = await getToken({ req, secret: process.env.AUTH_SECRET });
  if (!token || token.error) return new Response(null, { status: 401 });
  return fetch(`${process.env.ORDERS_URL}/orders`, {
    headers: { Authorization: `Bearer ${token.access_token}` },
    signal: AbortSignal.timeout(5000),
  });
}
```

Gotcha: on HTTPS the cookie is named `__Secure-authjs.session-token` (`__Secure-next-auth.session-token` in v4); if `getToken` returns `null` in production only, pass `secureCookie: true`.

The token never reaches browser JavaScript, and the backend still validates it (signature, `iss`, `aud`, expiry, roles). Roles in the session are only for showing or hiding UI.

**4. Typing.** Augment the types once instead of casting everywhere:

```ts
// types/next-auth.d.ts
import type { DefaultSession } from 'next-auth';
declare module 'next-auth' {
  interface Session { error?: 'RefreshTokenError'; user: { roles: string[] } & DefaultSession['user'] }
}
declare module 'next-auth/jwt' {
  interface JWT { access_token: string; refresh_token?: string; expires_at: number; id_token?: string; roles: string[]; error?: 'RefreshTokenError' }
}
```

**5. Federated logout.** `signOut()` only deletes the app's cookie. The Keycloak SSO session is still alive, so the next sign-in succeeds silently. Also end the IdP session: redirect to `…/protocol/openid-connect/logout?id_token_hint=<id_token>&post_logout_redirect_uri=<app URL>` (via a Route Handler that reads `id_token` from the JWT), or call it from the `signOut` event. Register the post-logout URI in Keycloak.

**Follow-up:** with a central telecom IdP you may also get **back-channel logout**: the IdP calls your app when the user logs out elsewhere. That needs database sessions (or a deny-list), because a stateless JWT can't be revoked.
