## Hints

- How does the frontend get the types of the API without code generation?
- What is the difference between a query, a mutation and a procedure middleware in tRPC?
- Where do input validation and authorization happen in a tRPC procedure?
- Why can't a mobile app written in Swift or an external partner use your tRPC API comfortably?

## Answer

> When the frontend and backend are both TypeScript, keeping their types in sync by hand is error-prone. tRPC lets the React client call server procedures like local functions, with types inferred from the router: rename a field on the server and the frontend fails to compile. Zod schemas still validate input at run time, and middleware builds reusable protected procedures. It fits an internal app where frontend and API ship together. For public APIs or many different clients, REST or GraphQL fits better.

**tRPC** lets a TypeScript client call server functions as if they were local, with **end-to-end types inferred from the router**. There is no schema file or code generation step: the client imports the router's *type* (`import type { AppRouter }`), and TypeScript does the rest. Under the hood it is plain HTTP and JSON (queries are `GET`, mutations are `POST`, optionally batched).

**Server (with Fastify):**

```ts
import { initTRPC, TRPCError } from '@trpc/server';
import superjson from 'superjson';
import { z } from 'zod';

type Context = { user: { id: string; roles: string[] } | null; db: PrismaClient };
const t = initTRPC.context<Context>().create({ transformer: superjson }); // Dates and Decimals survive JSON

const isAuthed = t.middleware(({ ctx, next }) => {
  if (!ctx.user) throw new TRPCError({ code: 'UNAUTHORIZED' });
  return next({ ctx: { ...ctx, user: ctx.user } });            // narrows ctx.user to non-null
});
const protectedProcedure = t.procedure.use(isAuthed);

export const appRouter = t.router({
  offer: t.router({
    list: protectedProcedure
      .input(z.object({ status: z.enum(['draft', 'sent', 'won']).optional(), cursor: z.string().nullish() }))
      .query(({ ctx, input }) => ctx.db.offer.findMany({ where: { ownerId: ctx.user.id, status: input.status }, take: 20 })),
    approve: protectedProcedure
      .input(z.object({ id: z.string().uuid() }))
      .mutation(async ({ ctx, input }) => {
        const offer = await ctx.db.offer.findUnique({ where: { id: input.id } });
        if (!offer) throw new TRPCError({ code: 'NOT_FOUND' });
        if (!canApprove(ctx.user, offer)) throw new TRPCError({ code: 'FORBIDDEN' });   // object-level check (#371)
        return ctx.db.offer.update({ where: { id: input.id }, data: { status: 'approved' } });
      }),
  }),
});
export type AppRouter = typeof appRouter;

// fastify
server.register(fastifyTRPCPlugin, { prefix: '/trpc', trpcOptions: { router: appRouter, createContext } });
```

**Client (React with TanStack Query, #530):**

```tsx
const trpc = createTRPCReact<AppRouter>();               // or the newer queryOptions-based integration
const { data } = trpc.offer.list.useQuery({ status: 'sent' });   // data is typed from the Prisma return type
const approve = trpc.offer.approve.useMutation({
  onSuccess: () => utils.offer.list.invalidate(),
});
```

Rename a field on the server and the frontend fails to compile. That is the main selling point.

**Key points to mention:**

- **Validation:** `.input(zodSchema)` parses at runtime; never trust the client just because it is typed. Output validation (`.output()`) is optional and useful when returning data from external sources.
- **Auth:** reusable procedures (`publicProcedure`, `protectedProcedure`, `adminProcedure`) built from middleware. Object-level checks still belong inside the procedure or a policy layer.
- **Errors:** `TRPCError` codes map to HTTP statuses (`BAD_REQUEST` 400, `UNAUTHORIZED` 401, `FORBIDDEN` 403, `NOT_FOUND` 404). Use an `errorFormatter` to return Zod field errors to forms (#625), and don't leak stack traces in production.
- **Transformers:** plain JSON turns `Date` into a string and `Prisma.Decimal` into a string or object. `superjson` keeps them typed (#630).
- **Don't return Prisma models blindly:** select the fields the client needs, or internal columns leak (#372).

**tRPC vs REST vs GraphQL (#97):**

| | tRPC | REST + OpenAPI | GraphQL |
|---|---|---|---|
| best for | one TS frontend + one TS backend, same repo | public APIs, many clients, any language | many clients with different data needs |
| contract | inferred TS types | OpenAPI spec | schema |
| HTTP caching | queries are `GET`, so possible | natural | hard (#364) |
| coupling | tight (that is the point) | loose | medium |

Rule of thumb: tRPC for an internal app in a monorepo where frontend and API ship together (#616). If partners, mobile teams or other systems need the API, expose REST (tRPC can generate OpenAPI with `trpc-to-openapi`) or keep a separate REST layer for integrations.

**Follow-up:** you deploy the API before the frontend, and a procedure's input gained a required field. What breaks, and how do you roll such changes out? (Old clients send the old shape and get `BAD_REQUEST`. Add the field as optional first, deploy both, then tighten; the same expand/contract idea as database migrations, #340.)
