## Hints

- Can a tool decide whether an image's alt text actually describes the image?
- What can you learn by putting the mouse away and using only the keyboard?
- Where in your development process should checks run so regressions don't ship?

## Answer

Use a **layered** approach. Automated tools reliably catch only a **portion** of WCAG issues, commonly estimated at around a third. The rest needs human judgment.

**1. Automated (fast, on every change)**

- **Linting:** `eslint-plugin-jsx-a11y` catches missing alt text, invalid ARIA and click handlers on non-interactive elements.
- **Component tests:** Testing Library queries such as `getByRole('button', { name: 'Save' })`. If the test can't find it by role and name, neither can a screen reader.
- **axe-core** in unit, Storybook or E2E tests (`@axe-core/playwright`, the Storybook a11y addon), plus Lighthouse in CI.

```ts
import AxeBuilder from '@axe-core/playwright';

test('checkout has no detectable a11y violations', async ({ page }) => {
  await page.goto('/checkout');
  const results = await new AxeBuilder({ page }).withTags(['wcag2a', 'wcag2aa', 'wcag22aa']).analyze();
  expect(results.violations).toEqual([]);
});
```

What tools catch well: contrast, missing labels or alt, invalid ARIA, duplicate ids, landmark and heading problems, missing `lang`.

**What they can't judge:** whether alt text or labels are **meaningful**, logical focus order, keyboard traps, whether custom widgets actually work with assistive technology, whether announcements make sense, cognitive clarity, and dynamic states (a menu that is only broken when open).

**2. Manual checks (per feature)**

- **Keyboard only:** Tab through everything. Is focus visible, is the order logical, does Escape close things, are there any traps?
- **Zoom** to 200% and 400% (reflow at 320 CSS px) and **increase text spacing**.
- Turn on **reduced motion**, **forced colors** / high contrast, and dark mode.
- Inspect the **accessibility tree** in DevTools for names and roles.

**3. Screen reader testing (key flows)**

Common pairings: **NVDA + Firefox/Chrome** and **JAWS + Chrome** on Windows, **VoiceOver + Safari** on macOS and iOS, **TalkBack + Chrome** on Android. Learn the basics: navigate by headings, landmarks and form fields, and listen to what is announced on state changes.

**4. Real users and audits**

Usability testing with disabled users, and periodic expert audits against WCAG 2.2 AA, especially before a legal compliance statement.

**Process tips:** shift left (accessible design-system components, annotated designs), add an a11y item to the definition of done, and track issues like any other bug.

**Follow-up:** "Lighthouse 100" doesn't mean accessible. It just means no automatically detectable failures.
