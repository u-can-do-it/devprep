## Hints

- How is `await foreach` over an `IAsyncEnumerable<T>` different from awaiting a `Task<List<T>>`, both for memory and for time to the first item?
- What should happen when the producer writes faster than the consumer reads: grow a queue forever, block, or drop items?
- How does a consumer learn that there will be no more items, and how does an error in the producer reach it?

## Answer

Both tools deal with **data that arrives over time**. `IAsyncEnumerable<T>` is a pull-based async sequence for one consumer. `Channel<T>` is an async queue that decouples producers from consumers, usually running concurrently.

**1. `IAsyncEnumerable<T>`**

An async iterator: each `MoveNextAsync` can await I/O before yielding the next item. The caller processes items as they arrive instead of waiting for the whole list.

```csharp
public async IAsyncEnumerable<Event> ReadEventsAsync(
    string path, [EnumeratorCancellation] CancellationToken ct = default)
{
    using var reader = new StreamReader(path);
    while (await reader.ReadLineAsync(ct) is { } line)
        yield return JsonSerializer.Deserialize<Event>(line)!;
}

await foreach (var e in ReadEventsAsync("events.jsonl").WithCancellation(ct))
    await HandleAsync(e, ct);
```

- `[EnumeratorCancellation]` connects the token passed with `WithCancellation` to the iterator's parameter.
- Like `IEnumerable<T>`, it's lazy and runs again on each enumeration.
- EF Core: `db.Orders.AsAsyncEnumerable()` streams rows without buffering them all into a list.
- ASP.NET Core: an endpoint returning `IAsyncEnumerable<T>` is serialized by System.Text.Json item by item, so a large result doesn't sit in memory first.

**2. `Channel<T>`**

A thread-safe queue with an async API: writers call `WriteAsync`, readers call `ReadAsync` or `ReadAllAsync()` (which returns an `IAsyncEnumerable<T>`).

```csharp
var channel = Channel.CreateBounded<Event>(new BoundedChannelOptions(capacity: 1_000)
{
    FullMode = BoundedChannelFullMode.Wait,   // writers wait when full: back-pressure
    SingleReader = false,
    SingleWriter = false,
});

// producer
async Task ProduceAsync(CancellationToken ct)
{
    try
    {
        await foreach (var e in ReadEventsAsync("events.jsonl", ct))
            await channel.Writer.WriteAsync(e, ct);   // suspends while the channel is full
        channel.Writer.Complete();                    // no more items
    }
    catch (Exception ex) { channel.Writer.Complete(ex); } // readers see the exception
}

// several consumers in parallel
var consumers = Enumerable.Range(0, 4).Select(_ => Task.Run(async () =>
{
    await foreach (var e in channel.Reader.ReadAllAsync(ct))
        await HandleAsync(e, ct);
}));

await Task.WhenAll([ProduceAsync(ct), .. consumers]);
```

**3. Back-pressure: bounded vs unbounded**

| Option | When the channel is full | Use for |
|---|---|---|
| `CreateUnbounded` | never full, memory grows | only when the producer is naturally limited |
| `Wait` | `WriteAsync` waits; `TryWrite` returns `false` | pipelines where nothing may be lost |
| `DropOldest` / `DropNewest` | an item already in the channel is discarded | telemetry, latest-value-wins updates |
| `DropWrite` | the new item is discarded | best-effort work |

Back-pressure only works if it propagates: if the producer is an HTTP endpoint, waiting on a full channel slows the request, and at some point you should reject with `429` or `503` instead of holding connections (`TryWrite` + an error response).

**4. Building a pipeline**

- Chain stages with one channel between each (parse → enrich → batch → write), each stage with its own degree of parallelism.
- Batch for I/O: read up to N items or until a timeout, then write them in one database call (#606).
- Order: with several consumers, items finish out of order. Partition by key (one channel per partition) if per-key order matters.
- Shutdown: complete the writer, let consumers drain, and respect the host's shutdown token in a `BackgroundService` (#595).
- In-process channels lose everything on a crash. If items must survive a restart, use a durable broker or an outbox.

Alternatives: `Parallel.ForEachAsync` for "process this collection with N workers", TPL Dataflow for richer pipelines with linking and batching blocks built in.

**Follow-up:** your API pushes jobs into an unbounded channel read by a background service, and under a traffic spike the pod is OOM-killed. What do you change? (Make it bounded, decide what a full queue means for the caller — wait, reject with 429/503 or drop — and monitor the queue length. For work that must not be lost, move it to a durable queue.)
