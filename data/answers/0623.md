## Hints

- Full sync every night or incremental changes? What do you need from the source system to do incremental sync?
- How do you match a record from the external system with your own row, and what happens when the same change arrives twice?
- The external API allows 10 requests per second and fails 2% of the time. How does your sync behave?
- How do you find out that the two systems have drifted apart even though no job failed?

## Answer

> Internal apps constantly import and export data from systems like an ERP, HR or Microsoft Graph, and syncs fail, repeat and drift. Agree on who owns each field and which direction data flows. Then fetch changes incrementally with a saved cursor, and upsert by a unique external id, so re-running a page is harmless. Deletes need tombstones or a periodic full comparison. Handle rate limits with backoff, log bad rows instead of stopping, and run a regular reconciliation to catch silent drift.

Internal systems constantly exchange data: employees from HR or Entra ID (#624), projects and invoices from the ERP or accounting software, documents from SharePoint, exchange rates, CRM contacts. Interviewers want to hear that you design for **failure, duplicates and drift**, not just "call the API and save".

**1. Decide the basics with the business:**

- **Source of truth** per field. If the ERP owns the invoice amount, your app never edits it; it may own the approval status.
- **Direction:** one-way import, one-way export, or two-way (much harder: conflicts).
- **Freshness:** is nightly fine, every 5 minutes, or near real-time?
- **Volume** and the API's limits.

**2. Pick a mechanism:**

| | how | when |
|---|---|---|
| full snapshot | fetch everything, compare, upsert | small datasets, or as a periodic reconciliation |
| incremental by timestamp/cursor | `?modifiedSince=` or a delta token; store the last cursor | most APIs (Microsoft Graph delta queries, many ERPs) |
| webhooks / events | the source pushes changes | near real-time; still needs a periodic catch-up because webhooks get lost (#357) |
| CDC / DB replication | read the source's change log (Debezium) | you own both databases |
| file drops | CSV/XLSX on SFTP or SharePoint | legacy systems; validate hard (#629) |

**3. Make the import idempotent:**

```ts
for await (const page of fetchChangedSince(cursor)) {           // paginate, don't load everything into memory
  for (const ext of page.items) {
    const data = mapExternalProject(ext);                           // validate with Zod (#625), skip and report invalid rows
    await db.project.upsert({
      where: { source_externalId: { source: 'erp', externalId: ext.id } },   // unique key on (source, external_id)
      create: { ...data, source: 'erp', externalId: ext.id },
      update: data,
    });
  }
  await db.syncState.update({ where: { name: 'erp-projects' }, data: { cursor: page.nextCursor } });   // commit progress per page
}
```

- Store the **external id** with a unique constraint; never match on names.
- **Upserts** make reprocessing the same page harmless, so a crash mid-run just restarts from the last saved cursor.
- Advance the cursor **after** the page is saved. Use an overlap window (re-read the last few minutes) when the source's timestamps aren't strictly ordered.
- **Deletes:** incremental APIs often don't report them. Use tombstones from the API, or a periodic full id comparison that marks missing records as inactive (soft delete) rather than hard-deleting.

**4. Resilience:**

- Run sync as a **background job** with a lock so only one instance runs at a time (#535).
- **Retries with exponential backoff and jitter** for 5xx/timeouts; respect `429` and `Retry-After` (#521); don't retry 4xx validation errors.
- **Timeouts** on every call (#300), and a circuit breaker if the source is down for long.
- **Rate limiting** on your side (a token bucket or the queue's limiter) to stay under the provider's quota.
- **Poison records:** one bad row must not stop the whole sync. Log it with the external id, store it in an errors table, continue.

**5. Exporting / two-way sync:**

- Send changes through an **outbox** (#484) so a local transaction and the "to be sent" record commit together, with an idempotency key the target can dedupe on (#356).
- **Conflicts:** last-writer-wins by timestamp is simple but loses data; better to split ownership by field, or flag conflicts for a human.
- Avoid **ping-pong loops**: an update you pushed comes back as a change from the other side. Track the origin or the version you last sent.

**6. Observability and reconciliation:**

- Record each run: started, finished, records read/created/updated/failed, cursor. Alert when a sync hasn't succeeded for N hours, not only when it throws.
- A periodic **reconciliation** report (counts and checksums per month, e.g. total invoiced amount) catches silent drift.
- Give business users a "last synced at" timestamp and a way to see failed records; they'll find mismatches before you do.

**Follow-up:** the ERP fixes a bug and re-sends 200,000 changed records at once. What happens to your app? (The job pages through them under the rate limit, upserts are idempotent, and the API stays responsive because the work runs in a worker with bounded concurrency and its own database pool.)
