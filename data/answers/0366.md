## Hints

- Which of the three can be reversed, and what (if anything) do you need to reverse it?
- Which one would you use to check that a downloaded file wasn't modified?
- Is a JWT payload secret just because it looks unreadable?

## Answer

They solve different problems and are often confused:

- **Encoding** transforms data into another representation for **compatibility**, not secrecy. Anyone can reverse it with no key. Examples: Base64, URL encoding, UTF-8, HTML entities.
- **Encryption** transforms data so only someone with the **key** can read it. It is reversible by design. Examples: AES-GCM (symmetric), RSA/ECDH-based schemes (asymmetric). Use it for confidentiality: data in transit (TLS) and at rest (encrypted DB columns, disk encryption).
- **Hashing** is a **one-way** function producing a fixed-size digest. You can't get the input back; you can only recompute and compare. Examples: SHA-256 for integrity checks, HMAC-SHA256 for message authentication (hash + secret key), and slow password hashes like Argon2id or bcrypt for passwords.

```js
Buffer.from('admin:secret').toString('base64'); // encoding: trivially reversible
crypto.createHash('sha256').update(file).digest('hex'); // hashing: integrity check
crypto.createHmac('sha256', key).update(body).digest('hex'); // HMAC: webhook signature
```

Classic mistakes:

- Treating Base64 as protection (HTTP Basic auth headers, JWT payloads are only base64url-**encoded**, anyone can read them).
- "Encrypting" passwords: if you can decrypt them, so can an attacker who steals the key. Passwords must be hashed with a slow, salted algorithm.
- Using a plain fast hash where you need a keyed one (signing webhooks needs HMAC, not `sha256(body)`).

**Follow-up:** Why compare HMACs with a constant-time function (`crypto.timingSafeEqual`, `hmac.compare_digest`)? To avoid timing attacks that leak how many bytes matched.
