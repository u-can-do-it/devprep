## Hints

- Which problem do replicas solve: too many reads, too many writes, or too much data?
- What does a user see if they write to the primary and immediately read from a lagging replica?
- How would you query or move data that spans several shards?

## Answer

**Replication** copies the same data to multiple nodes.

- **Leader–follower (primary–replica):** all writes go to the primary; replicas apply its log (WAL/binlog) and serve reads. Scales **reads** and provides failover.
- Usually **asynchronous** → **replication lag**. Problems: a user updates their profile and the next page (read from a replica) shows old data. Fixes: read-your-writes routing (read from primary for N seconds after a write, or pin to the primary for that session), wait for the replica to reach the write's LSN, or use synchronous replicas for critical paths.
- Failover can lose the last async writes; split-brain must be prevented by proper leader election (Patroni, managed services).
- Multi-leader / leaderless (Cassandra, DynamoDB) accept writes on many nodes and need conflict resolution.

**Sharding (partitioning)** splits data across nodes, each holding a subset. Scales **writes and storage**.

- **Shard key choice is everything:** high cardinality, even distribution, and most queries should include it (e.g. `tenant_id` in SaaS).
- **Strategies:** hash (even spread, no range scans), range (efficient ranges, risk of hot spots on recent data), directory/lookup service (flexible, extra hop).
- **Problems:** cross-shard queries become scatter-gather; cross-shard joins and transactions are hard (avoid, or use sagas / 2PC); unique constraints and global secondary indexes need extra machinery; **resharding** is painful – mitigate with many logical shards mapped to fewer physical nodes, or consistent hashing; hot tenants may need dedicated shards.

```text
shard = hash(tenant_id) % 1024        -> logical shard
logical shard 0-255  -> db-node-a
logical shard 256-511 -> db-node-b ...  (move logical shards, not rows)
```

**Order of operations in practice:** optimize queries and indexes → vertical scaling → caching → read replicas → partition tables within one node → shard (or adopt Citus, Vitess, or a distributed SQL database like CockroachDB/Spanner/Aurora Limitless) only when writes or data size truly exceed one node.
