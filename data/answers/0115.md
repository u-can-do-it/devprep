## Hints

- Where does the session state live in each approach, and what does the server need to look up per request?
- How do you log out a user immediately if their token is self-contained?
- Which browser storage can JavaScript read, and why does that matter if you have an XSS bug?

## Answer

**Server-side sessions**

The server stores session data (in Redis/DB) and gives the browser an opaque session ID in a cookie.

- Easy **revocation** (delete the session), small cookie, data stays private.
- Requires a shared session store across instances (a lookup per request).

**JWT (stateless tokens)**

A signed token containing claims (`sub`, `exp`, `scope`) that any service can verify with a key, no lookup needed.

- Good for **distributed systems/microservices** and third-party APIs; works across domains and for mobile clients.
- **Hard to revoke** before `exp` – needs short lifetimes, refresh tokens, or a denylist (which reintroduces state).
- Payload is only encoded, not encrypted – don't put secrets in it. Validate `alg` (never accept `none`), `exp`, `iss`, `aud`.

**Where to store tokens in a browser:**

- **`localStorage`/`sessionStorage`** – readable by any JS, so any XSS can steal the token and use it elsewhere. Avoid for long-lived tokens.
- **In memory** – lost on reload; needs a refresh mechanism.
- **`HttpOnly`, `Secure`, `SameSite` cookie** – JS can't read it; recommended. Requires CSRF protection.

```http
Set-Cookie: __Host-session=...; HttpOnly; Secure; SameSite=Lax; Path=/
```

**Common recommendation:**

- For a first-party web app, plain **cookie-based sessions** are usually simplest and safest.
- If you use OAuth/OIDC tokens, use a **Backend-for-Frontend (BFF)**: the server holds access/refresh tokens and the browser only gets a session cookie.
- Short-lived access tokens (5–15 min) + rotating refresh tokens with reuse detection.

**Follow-up:** "JWTs are stateless so they scale better" – is that true? Usually session lookups in Redis are cheap; revocation and security matter more.
