## Hints

- What is the difference between a WebView inside your app and opening the system browser from your app?
- The page and the app run in different JavaScript engines. What can they send each other?
- A message arrives in `onMessage`. How do you know which page sent it?

## Answer

> A WebView is a browser view embedded in a screen. Use it for content that already exists as a web page and isn't worth rebuilding: help articles, legal texts, a payment step, a legacy flow. Don't build the whole app from WebViews, and don't use one for third-party login. The page and the app exchange string messages through `postMessage` and injected JavaScript. Treat every message and every navigation as untrusted: restrict the allowed origins and validate what you receive.

**When it fits, and when it doesn't**

| Good use | Poor use |
|---|---|
| CMS content, terms, FAQs | the main screens of the app (slow start, non-native feel, store rejection risk) |
| a hosted payment or 3-D Secure page | OAuth login with Google or other providers: use the system browser (#697) |
| a complex web widget: a rich text editor, a chart, a map embed | anything that needs to be fast on scroll or work offline |
| a legacy web flow during a migration | storing secrets or tokens in page context |

**Three related tools**

- **`react-native-webview`:** a web view (`WKWebView`, Android System WebView) inside your layout. Your app controls it and can talk to the page.
- **The system browser** (`expo-web-browser`: `SFSafariViewController`, Custom Tabs): a browser sheet above your app. It shares cookies and password managers with the real browser, and your app can't read the page. Right for login and for external links.
- **Expo DOM components** (`'use dom'`): render a React web component inside a WebView, with props and callbacks bridged for you. Useful for reusing a web component in a native app.

**Communication**

```tsx
// In the web page
window.ReactNativeWebView.postMessage(JSON.stringify({ type: 'checkout:done', orderId: '42' }));
```

```tsx
// In the app
const ALLOWED = 'https://pay.example.com';

<WebView
  ref={webRef}
  source={{ uri: `${ALLOWED}/checkout?session=${sessionId}` }}
  originWhitelist={[ALLOWED]}
  onShouldStartLoadWithRequest={(req) => {
    if (req.url.startsWith(ALLOWED)) return true;
    Linking.openURL(req.url);          // external links leave the WebView
    return false;
  }}
  onMessage={(event) => {
    if (!event.nativeEvent.url.startsWith(ALLOWED)) return;
    const msg = Message.safeParse(JSON.parse(event.nativeEvent.data));   // zod schema
    if (msg.success && msg.data.type === 'checkout:done') onDone(msg.data.orderId);
  }}
/>

// App to page
webRef.current?.injectJavaScript(`window.onAppEvent(${JSON.stringify({ theme: 'dark' })}); true;`);
```

- Messages are strings. Define a small typed protocol with a `type` field and validate it.
- `injectedJavaScriptBeforeContentLoaded` runs a script before the page's own scripts, for setup.

**Security**

- **Origin:** load only origins you control. Block other navigation with `originWhitelist` and `onShouldStartLoadWithRequest`, or a compromised or redirected page gets your bridge.
- **Messages are untrusted input.** Any script on the page, including a third-party analytics script or an XSS payload, can call `postMessage`. Never act on a message without checking its origin and shape, and never let a message trigger something privileged without the user's confirmation.
- **Don't inject secrets** (tokens, personal data) into a page you don't fully control. For an authenticated page, pass a short-lived, single-use session code in the URL and exchange it on the server.
- **User HTML:** `source={{ html }}` with unsanitised content is XSS. Sanitise it, or turn JavaScript off for that view.
- **Files and mixed content:** keep file access off and HTTPS only.

**Performance and UX**

- A WebView starts a separate browser process: slow first load and more memory. Show a loading state, and avoid several on one screen.
- Scrolling, the keyboard, text selection and the back gesture behave like the web, not like the app. Handle Android back to go back inside the page first.
- The page needs its own error and offline handling (`onError`, `onHttpError`).

**Follow-up:** the web checkout page must know who the user is, and the app holds the access token. How do you pass identity safely? (Ask your backend for a one-time, short-lived checkout session bound to the user, open the page with that session id, and let the server set its own session. Don't inject the app's token.)
