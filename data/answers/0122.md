## Hints

- Which steps of the pipeline do the same work on every run even when nothing relevant changed?
- Which jobs don't depend on each other and could run at the same time?
- What should fail first: the cheap checks or the slow ones?

## Answer

> A CI pipeline is only useful if it gives feedback in minutes, and it tends to slow down as the codebase grows. Run cheap checks first (lint, types, unit tests) and stop on the first failure. Run independent jobs in parallel and shard big test suites. Cache dependencies with a key based on the lockfile hash, and cache build outputs too. In monorepos, run only what changed. Build the artifact once and promote the same one through environments.

A fast pipeline gives feedback in minutes. Key techniques:

- **Fail fast:** order stages cheapest-first — lint, type-check, unit tests, then integration and E2E. Stop on first failure.
- **Parallelize:** run independent jobs concurrently and shard large test suites across runners.
- **Cache dependencies:** key the cache on the lockfile hash so it's reused until dependencies change.
- **Cache build outputs:** Docker layer caching, Turborepo/Nx remote caches, compiler caches.
- **Only run what changed:** path filters or affected-project detection in monorepos.
- **Build once, promote the artifact:** the same image goes to staging and production; don't rebuild per environment.

```yaml
- uses: actions/cache@v4
  with:
    path: ~/.npm
    key: npm-${{ runner.os }}-${{ hashFiles('package-lock.json') }}
- run: npm ci
- run: npx vitest run --shard=${{ matrix.shard }}/4
```

Also keep pipelines reproducible (pinned tool versions, hermetic builds), keep secrets in the CI secret store, and track pipeline duration and flakiness as metrics.

**Pitfall:** over-aggressive caching that hides real failures (stale cache keys). Always include the lockfile or config hash in the key.
