## Hints

- How many queries run if you load 100 posts and then access `post.author` inside a loop?
- How could you fetch all the related rows in one or two queries instead?
- How would you notice this problem in logs or monitoring before users do?

## Answer

The **N+1 problem**: you run **1 query** to fetch a list of N items, then **N more queries** to fetch related data for each item, usually triggered by lazy loading in an ORM. Each query is fast, but round-trips add up and the database gets hammered.

```python
posts = session.scalars(select(Post).limit(100)).all()  # 1 query
for post in posts:
    print(post.author.name)   # lazy load: +1 query per post = 101 total
```

**Fixes:**

- **Eager loading** in the ORM:
  - a JOIN (`joinedload`, Prisma `include`, Django `select_related`) for many-to-one;
  - a second `WHERE id IN (...)` query (`selectinload`, Django `prefetch_related`) for one-to-many, which avoids row duplication.

```python
from sqlalchemy.orm import selectinload
posts = session.scalars(
    select(Post).options(selectinload(Post.author)).limit(100)
).all()  # 2 queries total
```

- **Write the JOIN yourself** in SQL and select only the needed columns.
- **Batching** in GraphQL/resolver-style code with **DataLoader**, which collects the ids requested in one tick and issues a single `IN` query.

```sql
SELECT p.id, p.title, a.name AS author
FROM posts p JOIN authors a ON a.id = p.author_id
ORDER BY p.created_at DESC LIMIT 100;
```

**Detection:** SQL query logging (`echo=True`), APM traces showing many identical queries per request, Django Debug Toolbar, or tests asserting query counts. Some ORMs can make lazy loading raise (`lazy="raise"` in SQLAlchemy).

Pitfall: over-eager loading of large relations can be just as bad; load what the endpoint needs.
