## Hints

- What happens to an HTTP request that takes four minutes behind a load balancer with a 60-second timeout?
- Which status code says "I've accepted this, but it isn't done yet"?
- How does the client find out the job has finished, and what if it retries the original request?

## Answer

Don't keep a request open for minutes: proxies time out, clients retry (duplicating work), and server resources stay pinned. Use the **asynchronous request–reply** pattern.

**1. Accept and return immediately**

```http
POST /reports
Idempotency-Key: 6d1c...
{ "type": "sales", "from": "2026-01-01", "to": "2026-09-30" }

HTTP/1.1 202 Accepted
Location: /operations/op_81f2
Retry-After: 5
{ "id": "op_81f2", "status": "pending" }
```

The API stores a job record and enqueues work (SQS, a Postgres-backed queue, Celery, BullMQ, Temporal). An **idempotency key** prevents duplicates if the client retries the `POST`.

**2. Let the client check status**

```http
GET /operations/op_81f2

200 OK
{ "id": "op_81f2", "status": "running", "progress": 0.6 }

200 OK
{ "id": "op_81f2", "status": "succeeded",
  "result": { "href": "/reports/rep_33a9" } }
```

Some APIs answer the finished status with `303 See Other` pointing at the result. On failure return `"status": "failed"` with a problem-details error – the status endpoint itself still returns `200`.

**3. Notification options instead of (or in addition to) polling**

- **Webhooks** for server-to-server integrations.
- **Server-Sent Events / WebSockets** for a UI waiting live.
- Email/notification with a download link for very long jobs.

**Design details:**

- Polling with `Retry-After` and backoff; rate-limit the status endpoint.
- Allow cancellation: `POST /operations/op_81f2/cancel` or `DELETE`.
- Expire job records and results (with a TTL documented in the API).
- Workers must be idempotent and retry-safe; record progress so a crashed worker can resume.
- Results like files go to object storage, delivered via a signed URL.

**Follow-up:** How does this pattern change if the operation must be exactly-once (e.g. payouts)?
