## Hints

- Why might firing 1,000 requests at once with `Promise.all` be a bad idea?
- How can a fixed number of "workers" pull the next item from a shared index?
- How do you keep results in input order when tasks finish out of order?

## Answer

**Why limit concurrency:** API rate limits, connection pools, memory, and not overwhelming the server or the browser's connection limit. `Promise.all(items.map(fn))` starts everything at once.

**Worker-pool approach:** start `limit` async workers. Each one keeps taking the next index until the items run out. JavaScript is single-threaded, so `next++` can't race.

```js
async function mapWithLimit(items, limit, fn) {
  const results = new Array(items.length);
  let next = 0;

  async function worker() {
    while (next < items.length) {
      const i = next++;
      results[i] = await fn(items[i], i);   // store by index keeps the order
    }
  }

  const workers = Array.from({ length: Math.min(limit, items.length) }, worker);
  await Promise.all(workers);
  return results;
}

const users = await mapWithLimit(ids, 5, (id) => fetch(`/api/users/${id}`).then((r) => r.json()));
```

**Things to discuss:**

- **Errors:** as written, the first rejection rejects the whole call, but the other workers keep going. Options: an `AbortSignal` to stop them, or collect `{ status, value | reason }` per item like `allSettled`.
- **Retries:** wrap `fn` with retry and exponential backoff plus jitter for errors that are worth retrying (429, 5xx).
- **Streaming input:** for unbounded sources, use a semaphore (`acquire`/`release`) instead of a pre-built list.
- **Libraries:** `p-limit` or `p-map` in production. Interviewers want to see that you understand the mechanism.

An alternative is a **semaphore** design: a counter plus a queue of waiting resolvers. Each task `await`s `acquire()` before running and calls `release()` in `finally`, which wakes the next waiting task.

**Follow-up:** "How would you add a per-task timeout?" Pass `AbortSignal.timeout(ms)` into each `fn` call.
