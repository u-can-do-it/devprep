## Hints

- When you call `.Where(x => x.Price > 10)` on each of them, is the lambda compiled into a delegate or into an expression tree?
- When does the code inside a `yield return` method actually run?
- If you call `.ToList()` before `.Where(...)` on a `DbSet`, how many rows does the database send back?

## Answer

**`IEnumerable<T>`: in-memory, pull-based iteration.** LINQ operators (`System.Linq.Enumerable`) take **delegates** (`Func<T, bool>`) and run your C# code over each item.

**`IQueryable<T>`: a query to be translated.** Operators (`System.Linq.Queryable`) take **expression trees** (`Expression<Func<T, bool>>`), data that describes the lambda. A provider (EF Core) translates the whole tree into SQL when you enumerate it.

| | `IEnumerable<T>` | `IQueryable<T>` |
|---|---|---|
| Lambdas become | compiled delegates | expression trees |
| Runs | in your process, item by item | in the data source, as SQL |
| Can call | any C# method | only what the provider can translate |
| Where filtering happens | after the data is loaded | in the database |

`IQueryable<T>` extends `IEnumerable<T>`, so the **static type** decides which overload you get. A method that returns `IEnumerable<Order>` from a `DbSet` silently switches every later operator to in-memory LINQ.

**Why the position of `.ToList()` matters**

```csharp
// 1. Good: one SQL query with WHERE, ORDER BY and LIMIT
var top = await db.Orders
    .Where(o => o.CustomerId == id)
    .OrderByDescending(o => o.CreatedAt)
    .Take(10)
    .ToListAsync(ct);

// 2. Bad: SELECT * FROM Orders, then filtering 2 million rows in memory
var top2 = db.Orders.ToList()
    .Where(o => o.CustomerId == id)
    .OrderByDescending(o => o.CreatedAt)
    .Take(10);

// 3. Same trap, hidden: AsEnumerable() (or an IEnumerable<T> parameter) ends the SQL part
var top3 = db.Orders.AsEnumerable().Where(o => o.CustomerId == id);
```

Materialize (`ToListAsync`, `FirstOrDefaultAsync`, `CountAsync`) **after** filtering, sorting, paging and projecting (`Select` only the columns you need). Moving to memory on purpose is fine when the remaining step can't be translated, e.g. a call to your own C# method, but only after the database has cut the data down. EF Core throws when it can't translate a part of the query instead of silently running it in memory (except in the final `Select`).

**`yield return`: lazy iterators**

The compiler turns a method with `yield return` into a state machine that implements `IEnumerable<T>`. Nothing runs until someone enumerates it, and each `MoveNext()` runs up to the next `yield`:

```csharp
static IEnumerable<int> ReadIds(string path)
{
    Console.WriteLine("opening");                       // runs on the first MoveNext, not when called
    foreach (var line in File.ReadLines(path))
        if (int.TryParse(line, out var id))
            yield return id;                           // one item at a time; the file is never fully in memory
}

var ids = ReadIds("ids.txt");                          // prints nothing yet
foreach (var id in ids.Take(3)) { }                    // reads only until it has 3 ids, then disposes the iterator
```

Consequences:

- **Deferred execution:** argument validation inside an iterator also runs late. Put checks in a non-iterator wrapper method (or a local function) so they throw immediately.
- **Multiple enumeration:** enumerating twice runs the whole thing twice (reads the file again, or sends the SQL query again). Call `.ToList()` once if you need the results more than once.
- `yield break` ends the sequence; `finally` blocks run when the consumer stops early, because `foreach` disposes the enumerator.
- `IAsyncEnumerable<T>` with `await foreach` is the async version (#600).

**Follow-up:** your repository returns `IQueryable<Order>`. Good or bad? (Callers can compose filters and paging into the SQL, but the query shape leaks out of the data layer: any caller can write something untranslatable or very slow, and it's hard to know which SQL runs. Many teams return `IQueryable` only inside the data layer and expose materialized results or specific query methods.)
