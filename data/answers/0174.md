## Hints

- How can an engine make a dynamically typed language fast? What does it guess about your code?
- How does V8 find the offset of `obj.x` without a hash lookup every time?
- What happens when an optimized function suddenly receives an object of a different shape?

## Answer

**The pipeline.** V8 parses source to an AST and compiles it to bytecode that the **Ignition** interpreter runs. While running, it collects **type feedback**. Code that runs often moves up through tiers: **Sparkplug** (a fast baseline compiler), **Maglev** (a mid-tier optimizer) and **TurboFan** (the top-tier optimizer). The optimizing tiers **speculate** from the feedback, for example "`x` is always a small integer", and generate machine code guarded by cheap checks.

**Hidden classes (Maps, or shapes).** Objects created with the same properties in the same order share a hidden class that records property offsets. Adding properties in a different order, or deleting them, creates new shapes.

**Inline caches (ICs).** Each property access site remembers the shapes it has seen:

- **Monomorphic** (one shape): very fast, a direct offset load.
- **Polymorphic** (2–4 shapes): a small check per shape.
- **Megamorphic** (many shapes): falls back to slow generic lookups.

**Deoptimization.** When a speculation fails (a string shows up where only integers were seen), V8 throws away the optimized code and falls back to the interpreter. Repeated deopts can stop a function from being optimized at all.

**Patterns that help:**

```js
class Point { constructor(x, y) { this.x = x; this.y = y; } } // same shape every time
// avoid: adding properties later in different orders
// avoid: delete obj.prop  → set to undefined, or use a Map for dynamic keys
```

- Keep arrays **homogeneous and packed**: no holes, and don't mix integers, floats and objects ("elements kinds").
- Keep hot functions **monomorphic**: always call them with the same types and shapes.
- Avoid `arguments` tricks and `eval`/`with` in hot code.

**Senior perspective:** these are micro-optimizations. Algorithm choice, fewer allocations, DOM work and network usually matter far more. Profile first (DevTools Performance panel, `node --cpu-prof`, `--trace-deopt`) and only reshape code in proven hot paths. Engines change often, so trust benchmarks over folklore.
