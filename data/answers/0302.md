## Hints

- How would a logger deep inside your code know which request it's running for, without passing `req` everywhere?
- Why can't you store "the current request" in a module-level variable in Node?
- How is this similar to thread-local storage in other languages?

## Answer

`AsyncLocalStorage` (from `node:async_hooks`) stores a value that **follows the async execution context**. Everything started inside `als.run(store, fn)`, including callbacks, promises and timers created there, sees the same store via `als.getStore()`. Concurrent requests each get their own store.

A module-level variable doesn't work because many requests interleave on one thread. The next `await` might resume a different request.

```js
import { AsyncLocalStorage } from 'node:async_hooks';
import { randomUUID } from 'node:crypto';
import pino from 'pino';

const als = new AsyncLocalStorage();
const baseLogger = pino();

export const log = () => als.getStore()?.logger ?? baseLogger;

app.use((req, res, next) => {
  const requestId = req.headers['x-request-id'] ?? randomUUID();
  res.setHeader('x-request-id', requestId);
  als.run({ requestId, logger: baseLogger.child({ requestId }) }, next);
});

// anywhere deeper, no req passed around
export async function chargeCard(order) {
  log().info({ orderId: order.id }, 'charging card');
}
```

Typical uses: request/correlation IDs in logs, tracing (OpenTelemetry uses it internally), the current user or tenant, and per-request DB transactions.

Caveats:

- Keep the store small and treat it as **read-mostly**. Hidden context makes code harder to follow, so don't use it for business data you could pass explicitly.
- Context can be lost through libraries that queue callbacks themselves (old connection pools, custom thenables). `AsyncResource.bind()` fixes that.
- Since Node 24 it's built on `AsyncContextFrame`, which is faster than the older `async_hooks`-based implementation. The cost is small but not zero.
