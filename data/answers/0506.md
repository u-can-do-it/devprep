## Hints

- After `npm run build`, does your app still need Node.js to run?
- `import.meta.env.VITE_API_URL` is replaced at build time. What does that mean for one image deployed to dev, UAT and prod?
- What should happen when a user refreshes the page on `/accounts/42`?
- Which files can be cached forever, and which must never be cached?

## Answer

A built SPA is **static files**. The image only needs a web server: build with Node in one stage, and serve with nginx in a small final stage.

```dockerfile
# 1. Build
FROM node:24-alpine AS build
WORKDIR /app
RUN corepack enable
COPY package.json pnpm-lock.yaml ./
RUN pnpm install --frozen-lockfile          # cached layer until dependencies change
COPY . .
RUN pnpm build

# 2. Serve: static files only, no Node.js, runs as non-root on port 8080
FROM nginxinc/nginx-unprivileged:1.27-alpine
COPY nginx/default.conf.template /etc/nginx/templates/default.conf.template
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 8080
```

Also add a `.dockerignore` with `node_modules`, `dist`, `.git` and `.env*`.

**nginx config.** The image runs `envsubst` on `/etc/nginx/templates/*.template` at startup, and only for environment variables that are set, so nginx's own `$uri` is left alone:

```nginx
server {
  listen 8080;
  root /usr/share/nginx/html;

  # SPA fallback: /accounts/42 isn't a file, so serve index.html and let the router handle it
  location / {
    try_files $uri /index.html;
    add_header Cache-Control "no-cache";      # index.html must always be revalidated
  }

  # Vite puts hashed file names here, so they can be cached forever
  location /assets/ {
    add_header Cache-Control "public, max-age=31536000, immutable";
  }

  # Runtime config, filled in from environment variables when the container starts
  location = /config.json {
    default_type application/json;
    add_header Cache-Control "no-store";
    return 200 '{"apiUrl":"${API_URL}","environment":"${APP_ENV}"}';
  }
}
```

**Build once, deploy many.** `VITE_*` and `process.env.*` values are **inlined at build time**. Building a separate image per environment defeats the point of testing the exact artifact you ship. Instead, load the config at runtime before rendering:

```ts
// main.tsx
const config: AppConfig = await fetch('/config.json').then((r) => r.json());
createRoot(document.getElementById('root')!).render(
  <ConfigProvider value={config}><App /></ConfigProvider>,
);
```

Other options are a Kubernetes ConfigMap mounted as `config.json`, or an entrypoint script that writes `window.__CONFIG__` into a `config.js`. **No secrets go in there:** everything the browser loads is public.

**Things that commonly trip people up:**

- **OpenShift** (common in banks) runs containers with a random UID. Use an unprivileged image, listen on a port above 1024, and keep writable paths group-writable.
- In nginx, `add_header` in a `location` **replaces** the headers from the `server` block. Repeat security headers (CSP, `X-Content-Type-Options`, `frame-ancestors`) where needed, or `include` a snippet.
- Add a health endpoint for readiness and liveness probes, and serve with gzip or brotli.

**CI/CD pipeline:** install → lint → type-check → unit tests → build → image build → scan (Trivy) → push, tagged with the git SHA → deploy to dev → e2e tests → promote **the same image** to UAT and prod.

**Alternative:** many teams skip containers for SPAs and deploy `dist/` to object storage behind a CDN. Containers make sense when the platform standard is Kubernetes or OpenShift, or when the SPA sits behind the same ingress as the APIs.
