## Hints

- How would you look up data if all you had was a key?
- Which kind of store fits a social network's "friends of friends" query?
- What kind of workload produces a huge, steady stream of writes keyed by time?

## Answer

> NoSQL databases give up some relational features, like joins or a fixed schema, to get scale, flexibility or speed for specific access patterns. The main types are key-value stores for caching and sessions, document stores for JSON-like data you read as a whole, wide-column stores for huge write volumes like time series, and graph databases for relationships. The key point: you model NoSQL data around the queries you already know you'll run. Many teams still start with PostgreSQL and add these only when needed.

"NoSQL" covers several data models that trade some relational features (joins, rigid schema, multi-row transactions) for scale, flexibility or speed on specific access patterns.

- **Key-value** – a giant distributed hash map: `get(key)` / `set(key, value)`. Extremely fast, minimal querying. *Examples:* Redis/Valkey, DynamoDB (also a document store), Memcached. *Use for:* caching, sessions, feature flags, rate-limit counters.
- **Document** – JSON-like documents with nested fields, queried by any field and indexed. Flexible schema. *Examples:* MongoDB, Firestore, Couchbase. *Use for:* product catalogs, content, user profiles – aggregates you read and write as a whole.
- **Wide-column** – rows identified by a partition key, with sorted columns inside a partition; built for massive write throughput across many nodes. *Examples:* Cassandra, ScyllaDB, Bigtable. *Use for:* time series, event logs, messaging, IoT.
- **Graph** – nodes and edges as first-class citizens; traversals are cheap. *Examples:* Neo4j, Amazon Neptune. *Use for:* recommendations, fraud rings, access-control graphs, social relations.

Related specialized stores: **search engines** (Elasticsearch/OpenSearch) for full-text, **time-series** (InfluxDB, TimescaleDB), and **vector databases** (or `pgvector`) for embedding similarity search.

Key interview point: NoSQL databases are designed around **known access patterns** – you model data for the queries you'll run, rather than normalizing and querying any way later. Many teams still default to PostgreSQL (which has JSONB, full-text and vector extensions) and add a specialized store only when a workload clearly needs it.
