## Hints

- What happens if a test finishes before the promise it started has resolved?
- How can you control time in a test instead of actually waiting?
- When a test fails only sometimes, what kinds of hidden dependencies should you look for?

## Answer

**Testing async code:**

- Always `await` (or return) the promise; otherwise the test may pass before assertions run. Use `await expect(fn()).rejects.toThrow()` for errors.
- Use **fake timers** instead of real `setTimeout` waits.
- In UI tests, wait for a condition (`findByText`, Playwright's auto-waiting `expect(...).toBeVisible()`), never a fixed `sleep`.
- Mock the network at the boundary (e.g. MSW) for deterministic responses.

```ts
test('retries after 1s', async () => {
  vi.useFakeTimers();
  const p = fetchWithRetry(flakyFn);
  await vi.advanceTimersByTimeAsync(1000);
  await expect(p).resolves.toEqual({ ok: true });
  vi.useRealTimers();
});
```

**Common causes of flaky tests:**

- race conditions and fixed sleeps,
- shared state between tests (DB rows, globals, module-level caches) and order dependence,
- real time, time zones, randomness,
- real network or third-party services,
- resource limits in CI (slower machines, parallel workers).

**Handling flakiness as a team:**

1. Detect it — track failure rates; rerun-on-failure only as a signal, not a fix.
2. Quarantine flaky tests out of the blocking path, with an owner and a deadline.
3. Fix the root cause: isolate data per test, inject clocks and random seeds, replace sleeps with condition waits.
4. Reproduce with repeated runs or random ordering.

**Pitfall:** permanent auto-retries hide real race conditions that may also exist in production code.
