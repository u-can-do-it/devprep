## Hints

- What does an agent know about your build commands, conventions and "don't touch this" areas on its first turn?
- Which instructions should be advice the model may ignore, and which must be enforced by the harness?
- How do you keep context files from going stale, and how do you know they help?

## Answer

Agents start every session knowing nothing about your repo except what they can read. "Agent-ready" means: **the right context, loaded at the right time, plus enforced rules and fast feedback**. Examples use Claude Code; Cursor, Codex and Copilot have equivalents.

**1. Context files (advice the model reads)**

- **`CLAUDE.md`** at the root (loaded at session start, together with parent directories and the user's `~/.claude/CLAUDE.md`): what the system is, how to build, test and lint, architecture in a few lines, conventions that differ from the defaults, and traps ("money is in cents", "never edit generated files in `src/gen`").
- **Nested `CLAUDE.md`** files in subdirectories load only when the agent works with files there, so module-specific rules don't cost context elsewhere. `.claude/rules/*.md` with `paths:` frontmatter does the same per glob.
- **`AGENTS.md`** is the cross-tool convention (Codex, Cursor, Copilot and others read it). Keep one source of truth and import it into `CLAUDE.md` with `@AGENTS.md` instead of duplicating.
- `@path` imports pull in existing docs (`@docs/architecture.md`) instead of copying them.

What to write: commands the agent can run, **verification steps**, decisions with their reasons, and pointers to good examples ("new endpoints follow `src/modules/booking`"). What not to write: things a linter or type checker already enforces, long generic style guides, anything outdated. Short and specific beats long: every line costs tokens in every session and competes for attention.

**2. Skills and subagents (procedures loaded on demand)**

- A **skill** is `.claude/skills/<name>/SKILL.md` with a `description` and step-by-step instructions, plus optional scripts and templates. Only the name and description sit in context; the body loads when it's relevant or invoked as `/name`. Good candidates: "add a database migration", "release", "debug a failing CI job", "write an MCP tool". (Older `.claude/commands/*.md` files work the same way.)
- **Subagents** (`.claude/agents/*.md`) get their own context, tool allowlist and model: a read-only reviewer, a test writer, an explorer that searches the codebase and returns only conclusions.

**3. Enforcement (rules the model can't ignore)**

- **Permissions** in `.claude/settings.json`, committed for the team: `allow` safe commands, `ask` for risky ones, `deny` what must never happen.

  ```json
  {
    "permissions": {
      "allow": ["Bash(npm run test *)", "Bash(npm run lint)", "Bash(git diff *)"],
      "deny": ["Read(./.env)", "Read(./secrets/**)", "Bash(git push *)", "Bash(rm -rf *)"]
    }
  }
  ```

- **Hooks** run your scripts on events: `PreToolUse` can block a call (exit code 2, and the reason goes back to the model), `PostToolUse` can format or lint every edited file, `Stop` can refuse to finish until tests pass, `SessionStart` can inject fresh context (current branch, open incident).

  ```json
  {
    "hooks": {
      "PostToolUse": [{
        "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write" }]
      }]
    }
  }
  ```

- **Sandboxing** for shell commands, and the usual guardrails that apply to humans too: branch protection, required review, CI (#543, #525).

**4. Fast, deterministic feedback.** Agents are as good as their feedback loop: one command for tests of a single file, fast type checking, a seed script for a local database, clear error messages. Investment in developer experience pays twice.

**5. Tools for your systems.** Project MCP servers in `.mcp.json` (shared with the team) give agents read access to logs, tickets and schemas (#542).

**Keeping it alive:** treat these files as code (reviewed in PRs, with owners). When an agent makes the same mistake twice, add a rule or, better, a check that enforces it. Prune rules that no longer apply. Test changes on real tasks: did the agent need fewer corrections? (#543)

**Follow-up:** the agent keeps writing raw SQL in a module that must use the repository layer, despite a line in `CLAUDE.md`. What do you do? (Move the rule closer: a nested `CLAUDE.md` or a path rule with an example; then enforce it with a lint rule or a hook so it can't be ignored.)
