## Hints

- In ASP.NET Core, what does "scoped" correspond to: a thread, a request, or something else?
- If a singleton takes a scoped `DbContext` in its constructor, how long does that `DbContext` live?
- A `BackgroundService` is a singleton. How does it get a fresh `DbContext` for each job?

## Answer

**Dependency injection (DI)**: classes declare what they need in their constructor, and a container builds them. ASP.NET Core has a built-in container (`Microsoft.Extensions.DependencyInjection`). You register services on `builder.Services`, and the framework resolves controllers, endpoint parameters, middleware and hosted services from it.

```csharp
builder.Services.AddSingleton<IClock, SystemClock>();
builder.Services.AddScoped<IOrderRepository, OrderRepository>();
builder.Services.AddTransient<IPriceCalculator, PriceCalculator>();
builder.Services.AddDbContext<AppDbContext>(o => o.UseNpgsql(connString));   // scoped by default
```

**Lifetimes**

| Lifetime | One instance per | Typical use | Watch out for |
|---|---|---|---|
| **Transient** | every resolution | lightweight, stateless services | disposable transients resolved from the root live until the app stops |
| **Scoped** | scope; in ASP.NET Core, **one HTTP request** | `DbContext`, unit of work, current user context | must not be resolved from the root provider |
| **Singleton** | application | caches, configuration, `HttpClient` factories, clocks | must be **thread-safe**; must not hold scoped services |

The container disposes the `IDisposable` instances it created when their scope ends (singletons at shutdown). It doesn't dispose instances you created yourself and registered with `AddSingleton(instance)`.

**Captive dependency**

A service can only depend on services that live **at least as long** as it does. A singleton that takes a scoped service in its constructor "captures" it: the first request's `DbContext` is reused by every request on every thread, which breaks change tracking, isn't thread-safe and keeps the connection or stale data around.

```csharp
public class PriceCache(AppDbContext db) { }    // registered as singleton: captures one DbContext forever
```

In Development, the host enables **scope validation** (`ValidateScopes`), which throws when a singleton depends on a scoped service or a scoped service is resolved from the root provider, and `ValidateOnBuild`, which checks every registration can be built at startup. Neither is on in Production by default, so make sure your Development runs and tests exercise the real registrations.

**Using scoped services from a singleton or background service**

Inject `IServiceScopeFactory` and create a scope per unit of work:

```csharp
public class OutboxPublisher(IServiceScopeFactory scopes, ILogger<OutboxPublisher> log) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await using (var scope = scopes.CreateAsyncScope())                 // one scope per batch
            {
                var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
                // ... read and publish pending messages
            }                                                                   // DbContext disposed here
            await Task.Delay(TimeSpan.FromSeconds(5), stoppingToken);
        }
    }
}
```

Alternatives: `IDbContextFactory<T>` (`AddDbContextFactory`) when a singleton needs short-lived `DbContext`s.

**Other things worth knowing**

- Registering several implementations of one interface: resolving `IEnumerable<INotifier>` gives all of them; resolving `INotifier` gives the **last** registered. `TryAdd*` registers only if nothing is registered yet (used by libraries).
- **Keyed services** (.NET 8+): `AddKeyedSingleton<ICache, RedisCache>("redis")` and `[FromKeyedServices("redis")]`.
- Avoid the **service locator** pattern (injecting `IServiceProvider` and calling `GetService` everywhere): it hides dependencies and moves errors to runtime. A scope factory in a background service is the accepted exception.
- Constructor injection with **primary constructors** (C# 12), as above, keeps classes short.

**Follow-up:** how would you decorate a registered service (e.g. add caching around `IProductRepository`)? (The built-in container has no decorator support; register the inner type, then `AddScoped<IProductRepository>(sp => new CachedProductRepository(sp.GetRequiredService<ProductRepository>(), ...))`, or use Scrutor's `Decorate`, or keyed services for the inner implementation.)
