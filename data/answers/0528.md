## Hints

- Who checks that a function returning `x is User` actually verified the shape of `x`?
- Why does `values.filter(Boolean)` not remove `null` from the array's type?
- What is the difference between a function that returns a boolean and one that `asserts` something?

## Answer

Built-in narrowing (`typeof`, `instanceof`, `in`, equality on a discriminant, truthiness, #27) covers most cases. When it doesn't, you write your own narrowing functions. TypeScript **trusts them completely**, which is both the point and the danger.

**Type predicate (`x is T`)**: a function returning a boolean whose signature tells the compiler what a `true` result means.

```ts
type User = { id: string; email: string };

function isUser(x: unknown): x is User {
  return typeof x === 'object' && x !== null && 'id' in x && 'email' in x
    && typeof (x as User).id === 'string' && typeof (x as User).email === 'string';
}

const data: unknown = await res.json();
if (isUser(data)) data.email.toLowerCase();                     // narrowed

const users = mixed.filter(isUser);                             // User[], not unknown[]
const present = values.filter((v): v is string => v != null);   // (string | null)[] -> string[]
```

Since TypeScript 5.5 the compiler **infers** predicates for simple arrow functions, so `values.filter((v) => v != null)` narrows on its own. `filter(Boolean)` still does not: `Boolean`'s signature is not a predicate.

**Assertion function (`asserts x is T` or `asserts cond`)**: returns nothing, throws on failure, and the code after the call is narrowed. Good for invariants and for fail-fast validation at boundaries.

```ts
function assertUser(x: unknown): asserts x is User {
  if (!isUser(x)) throw new TypeError('Expected a User');
}
function assert(cond: unknown, msg?: string): asserts cond {
  if (!cond) throw new Error(msg ?? 'Assertion failed');
}

assertUser(data);
data.id;                        // User from here on
assert(user.role === 'admin');  // user.role is 'admin' below
```

Pitfall: an assertion function must be called through a name with an **explicit type annotation** (a declared function or a typed `const`), otherwise TypeScript reports "Assertions require every name in the call target to be declared with an explicit type annotation".

**Why they are unsafe:** the body is not checked against the predicate. `function isUser(x: unknown): x is User { return true; }` compiles. A guard that checks `'id' in x` but forgets `email` lies to the whole codebase, and errors appear far away from the lie. Compare with narrowing on a discriminated union, which the compiler verifies.

**Making them safe:**

- Keep guards small and test them with wrong inputs like any other function.
- At real boundaries (API responses, `JSON.parse`, `localStorage`, form data) derive the guard from a schema: `UserSchema.safeParse(x).success` or `z.infer` plus `schema.parse`, so the check and the type cannot drift (#182, #443).
- Prefer discriminated unions over predicate functions inside your own code: add a `kind` field and let `switch` narrow.
- Don't write a guard that just casts (`return (x as User).id !== undefined`) and don't widen the parameter to `any`.
- `satisfies` is not a guard: it checks a literal at compile time and narrows nothing at runtime (#29).

**Follow-up:** why can't a type predicate return `false` for a value and still narrow the `else` branch to something useful? (It does: in the `else` branch the type is `Exclude<Input, T>`, which is why `isString(x): x is string` on `string | number` leaves `number`. For a predicate on `unknown` the `else` branch stays `unknown`.)
