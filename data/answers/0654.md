## Hints

- How does your script learn which tool is about to run and with which arguments?
- Your policy script fails with exit code 1. Does the tool call go ahead?
- You block `Edit` and `Write` on `.env`. Which other tool can still read or overwrite that file?

## Answer

> A hook is a handler the harness runs when a lifecycle event fires. You register it in `settings.json` under an event name, with a matcher that picks the tools. The handler gets the event as JSON on stdin and answers with an exit code or with JSON on stdout: exit 0 lets the action continue, exit 2 blocks it and sends stderr back to the model. `PreToolUse` runs before a tool call and can stop it; `PostToolUse` runs after it and can only react.

**Events worth knowing** (there are about thirty)

| Event | Fires | Can block? | Typical use |
|---|---|---|---|
| `SessionStart` | session starts or resumes | no | inject context: branch, ticket, open incident |
| `UserPromptSubmit` | you send a prompt | yes | add context, reject prompts containing secrets |
| `PreToolUse` | before a tool call | yes | block commands and paths, rewrite the input |
| `PostToolUse` | after a tool call succeeded | no, it already ran | format, lint, send errors back to the model |
| `Stop` | the agent is about to finish its turn | yes, it keeps working | refuse to stop while type checks fail |
| `SubagentStop` | a subagent finishes | yes | the same for subagents |
| `PreCompact` | before the context is compacted | yes | save state, add instructions for the summary |
| `Notification` | the agent waits for you | no | desktop or Slack notification |
| `SessionEnd` | session ends | no | cleanup, logging |

**Configuration** has three levels: event, matcher group, handlers.

```json
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Edit|Write",
      "hooks": [{ "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/protect-files.sh" }]
    }],
    "PostToolUse": [{
      "matcher": "Edit|Write",
      "hooks": [{ "type": "command", "command": "f=$(jq -r '.tool_input.file_path') && npx prettier --write --ignore-unknown \"$f\"" }]
    }]
  }
}
```

- **Where:** `~/.claude/settings.json` (you, all projects), `.claude/settings.json` (the project, committed), `.claude/settings.local.json` (you, this project), managed policy settings, plugins, and the frontmatter of a skill or subagent. Entries from all levels are merged.
- **Matcher:** for tool events it matches the tool name. `Bash` is an exact name, `Edit|Write` a list, anything with other characters is a regular expression (`mcp__github__.*`). Empty or `*` matches everything. Some events have no matcher (`UserPromptSubmit`, `Stop`), others match something else (`SessionStart` matches `startup`, `resume`, `clear`, `compact`).
- **Handler types:** `command` (a shell command, the usual choice), `http` (POSTs the event to a URL), `mcp_tool`, `prompt` (a single model call that decides) and `agent` (a subagent with tools, experimental).
- Matching hooks for one event run **in parallel**; a command hook has a long default timeout (minutes), which you can lower with `timeout`.

**Input:** JSON on stdin with common fields (`session_id`, `transcript_path`, `cwd`, `permission_mode`, `hook_event_name`) and event-specific ones. For `PreToolUse`: `tool_name`, `tool_input` (for `Bash` the `command`, for `Edit` the `file_path`) and `tool_use_id`. `PostToolUse` adds `tool_response`. The environment has `CLAUDE_PROJECT_DIR`.

**Output**

| Exit code | Meaning |
|---|---|
| 0 | success. Stdout is parsed as JSON if it is one JSON object. For `SessionStart` and `UserPromptSubmit`, plain stdout is added to the model's context |
| 2 | **blocking error.** Stderr goes to the model as the reason. `PreToolUse` cancels the call; `PostToolUse` can't undo it but the model sees the message; `Stop` makes the agent continue |
| anything else | **non-blocking** error: a notice is shown and the action goes ahead |

A policy script that crashes with exit 1 therefore **does not block**. Enforcement must exit 2 or return a decision as JSON:

```json
{ "hookSpecificOutput": { "hookEventName": "PreToolUse", "permissionDecision": "deny", "permissionDecisionReason": "Edits to .env are not allowed" } }
```

`permissionDecision` is `allow`, `deny` or `ask`; when several hooks answer, `deny` wins. `updatedInput` replaces the tool input, and `additionalContext` adds text for the model. `PostToolUse` and `Stop` use `{ "decision": "block", "reason": "..." }`.

**The blocking script**

```bash
#!/bin/bash
# .claude/hooks/protect-files.sh
file=$(jq -r '.tool_input.file_path // empty')

case "$file" in
  *.env|*.env.*|*/secrets/*)
    echo "Blocked: $file is protected. Ask the user to change it." >&2
    exit 2 ;;
esac
exit 0
```

The message matters: it is what the model reads, so say what was blocked and what to do next.

**Limits and pitfalls**

- This hook covers `Edit` and `Write` only. The agent can still run `cat .env` or `echo X > .env` through `Bash`. Use **permission deny rules** (`Read(./.env)`) and a sandbox for hard boundaries, and hooks for checks that need logic. Parsing shell commands with a regular expression is easy to get around.
- A `Stop` hook that always blocks loops. Make it pass when the work is done; the harness also caps consecutive continuations.
- Hooks run on every matching call, so keep them fast: format one file, not the repository.
- Command hooks run **with your user's permissions**. A hook in a cloned repository is someone else's code on your machine; project hooks wait for the workspace trust prompt, and they should be reviewed in pull requests like any script.
- Quote shell variables and use absolute paths (`$CLAUDE_PROJECT_DIR`), because the working directory can change during a session.
