## Hints

- The session lives in an HttpOnly cookie on the Next.js domain. Can browser JavaScript attach a bearer token to a call to `orders.internal`?
- One of five services behind a dashboard times out. What should the user see?
- `NEXT_PUBLIC_API_URL` is set at build time. What happens when the same image is deployed to test and production?
- The build server has no internet access. Which parts of a Next.js build try to download something?

## Answer

**How the frontend reaches the services**

| Option | Pros | Cons |
|---|---|---|
| **Browser → each service** | Simple, no extra hop | CORS on every service; the browser needs a token for each (so tokens live in JS); internal topology exposed; many round trips |
| **Browser → API gateway → services** (Kong, NGINX, Apigee…) | One entry point; TLS, rate limiting and token validation in one place | The gateway is generic: no aggregation shaped for this UI |
| **Browser → Next.js as a BFF → services** (#421) | Tokens stay server-side (#632); responses aggregated and trimmed for the screen; same origin, so no CORS | Next.js becomes a critical runtime service: it needs scaling, timeouts and monitoring |

With NextAuth the BFF option is natural: Route Handlers, Server Actions or Server Components read the token from the session cookie and call the services. That is usually behind a gateway, which still handles cross-cutting concerns. Next.js `rewrites` can proxy a path, but they can't add a per-user `Authorization` header; use a Route Handler (`app/api/[...path]/route.ts`) for that.

**Token propagation**

- **Forward the user's access token**: simplest. Each service validates signature, issuer, **audience** and scopes or roles. Watch out when the token's audience doesn't include the downstream service.
- **Token exchange** (RFC 8693, supported by Keycloak): swap the user token for one scoped to a specific service.
- **Service credentials** (client credentials grant) plus the user ID in a header, only between trusted services, never from the browser.

**Partial failures and resilience**

- **Timeouts on every call** (`AbortSignal.timeout(3000)`). Without them a slow service holds Node connections and requests pile up.
- **Retry only idempotent requests**, with backoff; a circuit breaker for a service that's down.
- **Degrade per section.** Separate queries and an error boundary for each widget: if billing fails, the profile and services widgets still render with a "try again" for billing. In Server Components, `Promise.allSettled` instead of `Promise.all`.
- **Correlation IDs**: create or forward `x-request-id` (or W3C `traceparent`) on every call and log it (#302, #412), so one user complaint can be traced across services.

**Contracts between independently deployed services**

- Generate typed clients from each service's OpenAPI spec (`openapi-typescript` + `openapi-fetch`, or Orval, which can also generate TanStack Query hooks). Regenerate in CI and fail the build when the spec breaks the frontend.
- Validate responses at the boundary (Zod) for services that change without telling you, and use consumer-driven contract tests where teams are separate (#392).
- Use API versioning and deprecation windows (#96).

**Configuration per environment** (dev, test, pre-prod, prod; on-premise vs private cloud)

- `NEXT_PUBLIC_*` values are **inlined into the JavaScript bundle at build time**, which breaks "build once, deploy many". One Docker image should run everywhere, so:
  - Service URLs are **server-side env vars** read at request time (Route Handlers, dynamic Server Components). The browser only talks to the same origin.
  - The few values the browser needs (feature flags, a public Sentry DSN) are passed from the root layout as props, or served by an `/api/config` endpoint, not baked in at build time.
- Internal service addresses (`http://orders.billing.svc.cluster.local`) differ from public ones, so keep the two clearly named.

**On-premise realities**

- An internal certificate authority (`NODE_EXTRA_CA_CERTS`), egress proxies, firewall rules that block the pod → IdP or pod → service call, split-horizon DNS, and possibly mTLS through a service mesh. These are often why "works locally, fails on the cluster".
- Offline builds: a private npm registry (Nexus, Artifactory); `next/font/google` downloads fonts at build time, so use `next/font/local`; set `NEXT_TELEMETRY_DISABLED=1`; make sure `sharp` for `next/image` is in the image.
- Several replicas: shared auth secret, shared cache handler if you rely on Next.js caching, graceful shutdown (#250, #301).
- Local development without the whole platform: MSW or WireMock for missing services, docker-compose for the ones you own, or a dev environment over VPN.

**Follow-up:** "Who owns the BFF?" The frontend team. It exists to serve this UI. If other clients start using it, it's turning into a general API and should move behind the gateway with its own owners.
