## Hints

- You save an order to Postgres and then publish `OrderCreated` to Kafka. What if the process crashes between the two?
- Can you put a database write and a Kafka publish in one transaction?
- If the relay publishes an event and crashes before marking it sent, what do consumers see?

## Answer

**The dual-write problem:** a service often has to **update its database and publish an event**. Two separate systems can't be committed atomically:

```ts
await db.insert(orders).values(order);                 // 1. committed
await producer.send({ topic: 'orders', messages });     // 2. crash or broker down → event lost forever
```

Swap the order and you can publish an event for an order that was never saved. Distributed transactions (2PC) across a database and a broker are slow and usually unsupported.

**Transactional outbox:** write the event into an **`outbox` table in the same database transaction** as the business change. Both commit or neither does. A separate **relay** then publishes outbox rows to the broker.

```ts
await db.transaction(async (tx) => {
  const [created] = await tx.insert(orders).values(order).returning();
  await tx.insert(outbox).values({
    id: crypto.randomUUID(),            // event id, used by consumers to deduplicate
    aggregateId: created.id,             // becomes the Kafka key → ordering per order
    type: 'OrderCreated',
    payload: created,
  });
});
```

**The relay**, one of two kinds:

- **Polling publisher:** a worker reads unpublished rows in order, publishes them, and marks them sent. With several workers, use `SELECT … FOR UPDATE SKIP LOCKED` so they don't take the same rows.

```sql
SELECT * FROM outbox WHERE published_at IS NULL
ORDER BY created_at LIMIT 100
FOR UPDATE SKIP LOCKED;
```

- **Change data capture (CDC):** Debezium reads the database's write-ahead log (Postgres logical replication) and streams new outbox rows to Kafka. Lower latency, no polling load, but more infrastructure.

**Consequences you must design for:**

- **At-least-once delivery:** if the relay publishes and crashes before marking the row, it publishes again. Consumers must be **idempotent** (deduplicate by event id; the receiving side of this is sometimes called the *inbox pattern*).
- **Ordering:** publish with the aggregate id as the message key so events for one order stay in order. Global ordering across aggregates isn't guaranteed.
- **Cleanup:** delete or archive published rows so the table doesn't grow forever.
- **Monitoring:** alert on outbox lag (oldest unpublished row age).
- **Event schema:** version the payload; it's a public contract.

**Related patterns:** the saga pattern uses the outbox to reliably emit each step's events; CQRS read models are often fed by these events.
