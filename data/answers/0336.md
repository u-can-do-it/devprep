## Hints

- How does a CTE improve readability compared with nested subqueries?
- What two parts does every recursive query need, and what stops it?
- What happens if the data contains a cycle?

## Answer

A **Common Table Expression** (`WITH name AS (...)`) is a named, query-scoped result set. It makes complex queries readable by splitting them into steps, and lets you reference the same intermediate result more than once.

```sql
WITH paid AS (
  SELECT customer_id, SUM(total) AS spent
  FROM orders WHERE status = 'paid'
  GROUP BY customer_id
)
SELECT c.name, p.spent
FROM customers c JOIN paid p ON p.customer_id = c.id
WHERE p.spent > 1000;
```

**Recursive CTEs** walk trees and graphs: org charts, category trees, comment threads, bill of materials. They have an **anchor** member (starting rows) and a **recursive** member that joins back to the CTE, combined with `UNION ALL`. Recursion stops when the recursive step returns no new rows.

```sql
WITH RECURSIVE subordinates AS (
  SELECT id, manager_id, name, 1 AS depth
  FROM employees WHERE id = 42                 -- anchor
  UNION ALL
  SELECT e.id, e.manager_id, e.name, s.depth + 1
  FROM employees e
  JOIN subordinates s ON e.manager_id = s.id   -- recursive step
  WHERE s.depth < 20                           -- safety limit
)
SELECT * FROM subordinates;
```

Notes:

- **Cycles** cause infinite loops; guard with a depth limit, track a path array, or use PostgreSQL 14+'s `CYCLE` clause.
- **Performance:** since PostgreSQL 12, simple CTEs are inlined into the main query and optimized like subqueries; use `AS MATERIALIZED` to force computing once (or `NOT MATERIALIZED` to force inlining).
- CTEs can also wrap data-modifying statements (`WITH moved AS (DELETE ... RETURNING *) INSERT ...`).

**Follow-up:** For deep, read-heavy trees, compare adjacency lists with materialized paths (`ltree`) or closure tables.
