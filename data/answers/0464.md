## Hints

- A user reports "the page is blank". What would you want to know before you open the code?
- Your production bundle is minified. How do you get a readable stack trace?
- Lighthouse on your laptop is fast. Is the app fast for real users on mid-range Android phones?

## Answer

Server logs can't see what happens in the browser, so frontends need their own monitoring. It covers three things: **errors**, **performance** and **user impact**.

**1. Error tracking (Sentry, Datadog RUM, Bugsnag)**

- Capture uncaught errors and unhandled rejections automatically, plus errors caught by React **error boundaries** (`Sentry.ErrorBoundary`, or `captureException` in your boundary) and failed API calls you choose to report.
- **Source maps:** upload them to the error tracker at build time (bundler plugin, with debug IDs or release names) so stack traces show your original TypeScript. Don't serve them publicly if you don't want to expose the source.
- **Context:** release version, environment, route, browser, a user id (not personal data), and **breadcrumbs** such as clicks, navigation and network calls before the error. Session Replay shows what the user did, with inputs masked.
- **Privacy:** scrub PII in `beforeSend`, mask replays, respect consent.
- **Noise control:** group and deduplicate, ignore browser-extension errors and known third-party noise, set alert thresholds such as "new issue in this release" or an error-rate spike. Tie issues to the release that introduced them.

**2. Performance and real-user monitoring (RUM)**

- Measure **Core Web Vitals in the field** (LCP, INP, CLS) with the `web-vitals` library or the RUM tool, segmented by route, device and country. Lab tests like Lighthouse don't represent real devices and networks.
- Track long tasks, slow API calls, JS bundle size per release (a CI budget with `size-limit`), and custom timings (`performance.mark`/`measure`) for key interactions such as "search results shown".
- **Distributed tracing:** propagate trace headers (`traceparent`) from the browser so a slow page links to the slow backend span (Sentry, Datadog or OpenTelemetry).

**3. Product health**

- Error-free session rate, crash rate per release, and funnel drop-offs, linked to deploys and feature flags so you can roll back or switch off a flag quickly.
- Uptime and synthetic checks: scripted Playwright journeys against production every few minutes.

**Gotchas:** ad blockers block monitoring endpoints, so use a **tunnel** through your own domain; your CSP must allow the endpoint; sample high-volume events and replays to control cost; and minified "Script error." messages from cross-origin scripts need `crossorigin` attributes and CORS headers.

**Follow-up:** after a release, the error rate doubles but only on Safari. Walk through how you'd find the cause.
