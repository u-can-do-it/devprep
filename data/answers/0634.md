## Hints

- Which data-fetching function runs on every request, which one at build time, and which one also runs in the browser?
- What goes into `_app` and what into `_document`, and why can't `_document` have click handlers?
- Can `pages/` and `app/` live in one project? What happens when a user navigates between them?
- What replaces `useRouter().query` in the App Router?

## Answer

Many production apps, including older self-service portals, still run on the **Pages Router**. You need to read it fluently even if new code goes into `app/`.

**Data fetching (per page, exported from the page file):**

| Function | Runs | Use for |
|---|---|---|
| `getServerSideProps(ctx)` | On the server, **every request** (`ctx.req`, `ctx.res`, `params`, `query`) | Per-user or always-fresh pages; auth checks with `getServerSession(ctx.req, ctx.res, authOptions)` |
| `getStaticProps` (+ `revalidate`) | At build time; with `revalidate: 60` regenerated in the background (**ISR**) | Marketing pages, catalogues |
| `getStaticPaths` | At build time, for dynamic static routes | `fallback: false` (404), `true` (render a fallback, then data), `'blocking'` (SSR the first request) |
| `getInitialProps` | Server on first load, **browser on client navigation** | Legacy. In `_app` it disables Automatic Static Optimization for the whole app |

All of them can return `{ props }`, `{ redirect: { destination, permanent } }` or `{ notFound: true }`. Props are serialized to JSON in the HTML (`__NEXT_DATA__`), so `Date` objects fail and secrets leak if you return them.

**Special files:**

- `pages/_app.tsx`: wraps every page. Global CSS, providers (`SessionProvider`, `QueryClientProvider`, MUI `ThemeProvider`), persistent layout via a `getLayout` pattern.
- `pages/_document.tsx`: renders `<html>` and `<body>` **on the server only**, once. Use it for `lang`, and for the Emotion/MUI style collection in `getInitialProps`. No state, no event handlers, because it is never hydrated.
- `pages/api/*.ts`: API routes with Node-style `(req, res)` handlers. Often this is where the BFF and the NextAuth handler (`pages/api/auth/[...nextauth].ts`) live.
- `next/router`'s `useRouter()`: `router.query`, `router.push`, shallow routing. On statically optimized pages `router.query` is empty during the first render; wait for `router.isReady`.
- `next/head` for titles and meta tags.

**Incremental migration to the App Router**

`pages/` and `app/` can coexist. A route must exist in only one of them, and navigating **between** the two routers is a full page load, so migrate whole sections at a time.

1. Upgrade Next.js and React first, keeping `pages/` working.
2. Add `app/layout.tsx` (it replaces `_app` and `_document`) and a `'use client'` `providers.tsx` with the same providers.
3. Move a low-risk route. Translate the data fetching:
   - `getServerSideProps` → an `async` Server Component that fetches directly (dynamic rendering).
   - `getStaticProps` + `revalidate` → cached fetches or `'use cache'` with a revalidate setting (#44).
   - `getStaticPaths` → `generateStaticParams`.
   - `next/head` → `metadata` / `generateMetadata`.
4. Switch the hooks: `useRouter` from `next/navigation` has no `query`; use `useParams`, `useSearchParams` and `usePathname`.
5. Keep API routes as they are, or move them to `route.ts` Route Handlers. Both work.
6. Auth: NextAuth v4 works in both routers (`getServerSession(authOptions)` in Server Components). The v5 `auth()` replaces it everywhere.
7. Delete `pages/` routes once their replacements are tested. Characterization tests (#640) on the main flows make this safe.

**Follow-up:** "Would you migrate at all?" Only with a reason: you need streaming or nested layouts, the Pages Router blocks a feature, or the version you're on is losing security support. A working Pages Router app with a stable team can stay where it is.
