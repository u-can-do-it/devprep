## Hints

- Does a component re-render when any part of the store changes, or only the part it reads?
- Where does a Zustand store live, and why is that a problem when the same code runs on the server for many users?
- What does Redux Toolkit give a large team that a 50-line Zustand store doesn't?

## Answer

All three solve "state that many components share" (#37), but with different models. Server data belongs in TanStack Query or SWR regardless (#212, #530); these libraries are for **client state**: UI state, drafts, selections, auth session, multi-step flows.

**Zustand: one store, selectors, no provider.** A store is a hook created from a `create()` call; components read a slice with a selector and re-render only when that slice changes (`Object.is`). Actions are plain functions on the store. Middleware adds `persist`, `devtools`, `immer`, `subscribeWithSelector`.

```ts
const useCart = create<CartState>()((set, get) => ({
  items: [],
  add: (item) => set((s) => ({ items: [...s.items, item] })),
  total: () => get().items.reduce((sum, i) => sum + i.price, 0),
}));

const count = useCart((s) => s.items.length);                  // re-renders only when length changes
const { add, items } = useCart(useShallow((s) => ({ add: s.add, items: s.items })));
```

Pitfall: a selector that returns a **new object or array** each call (`(s) => ({ a: s.a, b: s.b })` or `s.items.filter(...)`) re-renders on every store update and, with `useSyncExternalStore`, can throw "maximum update depth exceeded". Use `useShallow` or select primitives.

**Jotai: atoms, bottom-up.** State is split into atoms; derived atoms compute from others and components subscribe to exactly the atoms they use. Async atoms integrate with Suspense. Feels like `useState` that can be shared, with no store shape to design up front.

```ts
const filterAtom = atom('');
const visibleAtom = atom((get) => get(itemsAtom).filter((i) => i.name.includes(get(filterAtom))));
const [filter, setFilter] = useAtom(filterAtom);
```

**Redux Toolkit: one store, slices, reducers, devtools, conventions.** `createSlice` generates actions and reducers (Immer makes "mutations" safe), `configureStore` wires devtools and middleware, `useSelector` + `createSelector` read memoized slices (#450, #452). RTK Query covers server state inside the same ecosystem, and listener middleware handles side effects. More ceremony, but every feature looks the same, which is what a large team needs; time-travel debugging and serializable actions are a real benefit in complex flows (editors, checkout, dashboards with undo).

**Re-render granularity:** Zustand and RTK depend on **selectors** (you choose what to subscribe to; a bad selector over-renders). Jotai depends on **atom boundaries** (you choose how finely to split state). Context has neither: every consumer re-renders on any change (#217).

**Choosing:**

- Small or mid-size app, a few global concerns (auth, theme, cart, toast queue): **Zustand**. Minimal code, easy to test (call the store outside React), no provider.
- State that is naturally a graph of small, derived values (forms, canvases, spreadsheets), or you want Suspense-driven async: **Jotai**.
- Large team, complex synchronous business logic, need for strict structure, audit trail or time travel, or existing Redux code: **Redux Toolkit**.
- Already using TanStack Query plus URL state and a bit of `useState`: maybe **nothing**. Add a library when prop drilling (#198) or Context re-renders become a measured problem.

**SSR pitfall:** a store created at module scope is a **singleton per server process**. In Next.js or any SSR, create the store per request (Zustand `createStore` in a provider, Jotai `<Provider>`, RTK `makeStore()`), otherwise user A's state can leak into user B's HTML (#244).

**Follow-up:** how would you migrate a Context-based global state to Zustand without a big-bang rewrite? (Wrap the store in the same Context-shaped hook API, move one slice at a time, keep the old provider until no consumer is left.)
