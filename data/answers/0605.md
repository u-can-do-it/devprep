## Hints

- Who is allowed to reorder your reads and writes: the C# compiler, the JIT, the CPU? Why does code that works on x64 sometimes break on ARM?
- What does `volatile` guarantee, and what doesn't it (think `count++`)?
- Two threads update two different fields and both get slower. What do the fields have in common?

## Answer

A memory model says which values a thread may see when another thread writes without a lock. In single-threaded code every optimization preserves program order; across threads, **the compiler, the JIT and the CPU may all reorder** reads and writes.

**1. What can go wrong**

```csharp
class Worker
{
    private bool _stop;                       // not volatile
    public void Run() { while (!_stop) { /* work */ } }   // the JIT may read _stop once and loop forever
    public void Stop() => _stop = true;
}
```

```csharp
_data = Compute();          // 1
_ready = true;              // 2: another thread may see _ready == true but stale _data on ARM64
```

x86/x64 is strongly ordered (it only reorders a store with a later load), so many bugs never show there. **ARM64** (Graviton, Apple silicon, Ampere) is weakly ordered and exposes them. The .NET memory model is documented in the dotnet/runtime repository; code it doesn't guarantee is a bug even if it passes tests on x64.

**2. The tools and what each guarantees**

| Tool | Guarantee |
|---|---|
| plain read/write of `int`, `bool`, a reference, or anything up to pointer size (aligned) | **atomic** (no torn values), but no ordering or freshness |
| `long`/`double` on a 32-bit process | **not** atomic: use `Interlocked.Read` or `Volatile` |
| `volatile` field / `Volatile.Read` / `Volatile.Write` | read = **acquire** (later accesses can't move before it), write = **release** (earlier accesses can't move after it); the JIT can't cache the value in a register |
| `Interlocked.*` (`Increment`, `Exchange`, `CompareExchange`) | atomic read-modify-write and a **full fence** |
| `lock` / `Monitor` | mutual exclusion; entering acquires, exiting releases |
| `Interlocked.MemoryBarrier()` | full fence, rarely needed directly |

`volatile` fixes both examples above (`_ready` written last with release, read with acquire). It does **not** make `_count++` atomic (that's read, add, write) and does not stop a store followed by a load from being reordered, so Dekker-style "set my flag, check yours" needs full fences.

**3. Compare-and-swap loops**

Lock-free updates follow one pattern: read, compute, publish only if nobody changed it meanwhile, otherwise retry.

```csharp
static void UpdateMax(ref int max, int value)
{
    int current = Volatile.Read(ref max);
    while (value > current)
    {
        int seen = Interlocked.CompareExchange(ref max, value, current);   // write only if max == current
        if (seen == current) return;   // we won
        current = seen;                // someone else changed it, retry against the new value
    }
}
```

The most useful lock-free pattern in application code is the **immutable snapshot swap**: readers read a reference to an immutable object with no locks, a writer builds a new object and swaps the reference.

```csharp
private ImmutableDictionary<string, Route> _routes = ImmutableDictionary<string, Route>.Empty;
public Route? Find(string key) => Volatile.Read(ref _routes).GetValueOrDefault(key);     // lock-free read
public void Set(string k, Route r) => ImmutableInterlocked.Update(ref _routes, d => d.SetItem(k, r)); // CAS loop inside
```

Because the GC doesn't reuse memory that's still referenced, the classic **ABA problem** of C/C++ lock-free structures mostly doesn't affect reference CAS in .NET, but it still can with integer indexes or pooled objects.

**4. False sharing**

CPUs move memory between cores in **cache lines** (64 bytes on x64, 128 on some ARM chips; adjacent-line prefetching makes 128 a safe padding). Two counters in the same line, each written by a different core, make that line bounce between caches: the code is correct but scales negatively.

```csharp
[StructLayout(LayoutKind.Explicit, Size = 128)]
struct PaddedCounter { [FieldOffset(0)] public long Value; }   // one counter per cache line
private readonly PaddedCounter[] _perCore = new PaddedCounter[Environment.ProcessorCount];
```

`ConcurrentQueue<T>` pads its head and tail indexes for exactly this reason. Spotting it needs hardware counters (`perf c2c` on Linux, VTune) or a benchmark that gets slower as you add threads.

**5. When it's worth it**

Almost never in business code. An uncontended `lock` costs tens of nanoseconds, and `ConcurrentDictionary`, `Channel<T>` (#600), `Lazy<T>` and `Interlocked.Increment` for counters cover most needs (#592). Lock-free code is worth it for: very hot shared counters or statistics, read-mostly configuration (snapshot swap), and library-level structures that profiling shows are contended. Write it only with a benchmark proving the lock is the bottleneck, a stress test on ARM64, and a comment explaining every fence.

**Follow-up:** is double-checked locking safe in .NET? (Only if the field is `volatile` or read with `Volatile.Read`, so the object's constructor writes are visible before the reference. In practice use `Lazy<T>` or `LazyInitializer.EnsureInitialized`.)
