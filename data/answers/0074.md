## Hints

- Can two threads execute Python bytecode at the same time in standard CPython?
- Is the work waiting on the network/disk, or burning CPU?
- What changed with the free-threaded build in Python 3.13+?

## Answer

The **Global Interpreter Lock** is a mutex in CPython that lets only **one thread execute Python bytecode at a time**. It simplifies memory management (reference counting) but means threads don't give parallel speed-ups for pure-Python CPU work. The GIL **is released during blocking I/O** and by many C extensions (NumPy, hashing, compression), so threads still help there.

Choosing a model:

- **threading** – I/O-bound work with blocking libraries (`requests`, sync DB drivers). Simple, shared memory, but needs locks for shared state. Use `ThreadPoolExecutor`.
- **multiprocessing** / `ProcessPoolExecutor` – **CPU-bound** pure-Python work. Separate processes, each with its own interpreter and GIL, so true parallelism. Costs: process startup, memory, and pickling data between processes.
- **asyncio** – lots of concurrent **I/O** (thousands of sockets) in one thread using cooperative `async`/`await`. Very cheap per task, but every library in the path must be async, and one blocking call stalls everything.

```python
import asyncio
from concurrent.futures import ProcessPoolExecutor

async def main(images):
    loop = asyncio.get_running_loop()
    with ProcessPoolExecutor() as pool:
        return await asyncio.gather(*(loop.run_in_executor(pool, resize, img) for img in images))
```

Combining them is common: asyncio for I/O, `asyncio.to_thread` for a blocking call, a process pool for CPU work.

**Current state:** PEP 703 introduced an optional **free-threaded build** (`python3.13t`), still experimental in 3.13 and officially supported (but not default) since 3.14. Ecosystem support is growing; the default CPython still has the GIL.

**Follow-up:** Does the GIL make your multithreaded code thread-safe? (No: `count += 1` is not atomic.)
