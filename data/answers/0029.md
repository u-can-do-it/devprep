## Hints

- When you annotate `const config: Config = {...}`, what happens to the specific literal types of the values?
- Which of the three can hide a real type error?
- How can you check an object against a type and still keep its precise inferred type?

## Answer

`satisfies` (TS 4.9+) **checks** that an expression matches a type **without changing** the type that gets inferred for it. You get validation and precise inference at the same time.

Compare the three options:

```ts
type Route = { path: string; method: 'GET' | 'POST' };
type Routes = Record<string, Route>;

// 1. Annotation: checked, but the type is widened to Routes
const r1: Routes = { home: { path: '/', method: 'GET' } };
r1.home;     // Route (possibly undefined with noUncheckedIndexedAccess)
r1.typo;     // no error: any string key is allowed

// 2. Assertion: you tell the compiler to trust you; real mistakes can slip through
const r2 = { path: '/login' } as Route; // no error, although `method` is missing

// 3. satisfies: checked, and the precise type is kept
const r3 = {
  home:  { path: '/',      method: 'GET' },
  login: { path: '/login', method: 'POST' },
} satisfies Routes;
r3.login.method;  // 'POST' (a literal type, not the full union)
r3.typo;          // error: property 'typo' does not exist
```

**Typical uses:**

- **Config objects and lookup tables**, where you want key autocomplete and literal values but still want to validate the shape.
- **Exhaustive maps:** `const labels = { idle: '...', loading: '...' } satisfies Record<Status, string>` fails to compile if a status is missing or extra.
- Combined with `as const`: `[...] as const satisfies readonly Item[]` gives deeply readonly literals that are also checked.
- Framework exports, for example `export default { ... } satisfies Config` in Next.js, Vite or Tailwind configs.

**Which to use:**

- **Annotation:** when you *want* the wider type, such as a variable that will be reassigned, or a public API boundary.
- **`satisfies`:** for constant data whose exact shape you want to keep.
- **`as`:** only when you really know more than the compiler (for example after validation), never to silence errors.

**Follow-up:** `satisfies` doesn't change runtime behavior. Like all TypeScript types, it is erased at compile time.
