## Hints

- How many threads execute your JavaScript code in a Node process?
- What happens to all other incoming requests while one request runs a 2-second synchronous loop?
- How could you move heavy work elsewhere or split it into smaller pieces?

## Answer

Node executes JavaScript on **one main thread**. While a callback is running, the event loop can't do anything else: no new requests, no timers, no I/O callbacks. Any long **synchronous** work therefore "blocks the event loop" and raises latency for *every* client, not just the one that triggered it.

Common culprits:

- CPU-heavy code: big `JSON.parse`/`JSON.stringify`, sorting huge arrays, image or crypto work.
- Sync APIs: `fs.readFileSync`, `crypto.pbkdf2Sync`, `zlib.gzipSync` in request handlers.
- Catastrophic regex backtracking (ReDoS) on user input.
- Infinite or very large loops.

```js
app.get('/report', (req, res) => {
  const data = fs.readFileSync('huge.json'); // blocks everyone
  res.json(heavyCompute(data));              // blocks everyone
});
```

How to avoid it:

- Use async APIs (`fs/promises`, async `crypto`).
- Offload CPU-bound work to **worker threads** or a separate service/queue.
- Chunk long work and yield with `setImmediate` between chunks.
- Stream large payloads instead of buffering them.
- Validate input sizes and avoid vulnerable regexes.

Detect it with `perf_hooks.monitorEventLoopDelay()`, APM event-loop-lag metrics, or `node --cpu-prof`.

**Follow-up:** Does `async`/`await` alone make CPU-heavy code non-blocking? (No – it only helps when awaiting real async I/O.)
