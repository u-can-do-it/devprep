## Hints

- Can you query DynamoDB by an attribute that isn't part of any key?
- What happens if 90% of traffic targets the same partition key value?
- Why do people design DynamoDB tables starting from a list of access patterns?

## Answer

Every DynamoDB item has a **primary key**: a **partition key** (hashed to pick a physical partition) and an optional **sort key** (orders items within that partition). Efficient reads are `GetItem` (exact key) and `Query` (one partition key, optional sort-key condition like `begins_with` or `BETWEEN`). `Scan` reads the whole table and should be avoided in request paths.

**Design process – access patterns first:**

1. List every query the app needs ("orders for a customer, newest first", "order by id").
2. Choose keys so each pattern is a `GetItem` or a `Query`.
3. Add **Global Secondary Indexes** (different partition/sort key, eventually consistent) for remaining patterns.

```text
PK                SK                        attributes
CUSTOMER#42       PROFILE                   name, email
CUSTOMER#42       ORDER#2026-10-01#9001     total, status
CUSTOMER#42       ORDER#2026-10-03#9017     total, status
```

`Query PK = "CUSTOMER#42" AND begins_with(SK, "ORDER#")` returns orders sorted by date. Storing several entity types in one table like this is **single-table design** – fewer round trips, but harder to evolve and explore; many teams use a few tables instead.

**Hot partitions:** throughput is limited per partition (roughly 3,000 read units and 1,000 write units per second). If keys are skewed – a celebrity user, a `status = "active"` key, a date key for "today" – one partition throttles while others idle. Adaptive capacity helps, but design matters:

- Pick **high-cardinality**, evenly accessed partition keys (user id, order id).
- **Write sharding**: append a random or computed suffix (`EVENTS#2026-10-04#7`) and fan out reads across suffixes.
- Cache hot reads (DAX or Redis).

Other limits: items max 400 KB; GSIs are eventually consistent; transactions exist (up to 100 items) but cost more.
