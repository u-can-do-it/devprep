## Hints

- Who is responsible for provisioning and patching servers in a serverless model?
- What has to happen before a function can handle a request if no instance is warm?
- How does the cost model compare for spiky versus steady, high traffic?

## Answer

Serverless (AWS Lambda, Cloud Run functions, Vercel/Cloudflare functions) means the provider runs your code on demand and bills per invocation/duration.

**Pros:**

- No server management; automatic scaling, including to zero.
- Pay only for actual usage — great for spiky or low traffic, cron jobs, webhooks, event processing.
- Fast to ship small services.

**Cons:**

- **Cold starts:** when no warm instance exists, the platform must allocate a sandbox, load the runtime and your code, and run initialization. This can add from tens of milliseconds to several seconds (worse with big bundles, JVM, or VPC networking).
- Execution time and memory limits; not suited to long-running jobs or WebSockets (without extra services).
- Statelessness — every invocation may hit a fresh instance; database connections can be exhausted (use a pooler/proxy).
- Vendor lock-in, harder local debugging, and cost can exceed containers at sustained high load.

**Reducing cold starts:**

- keep bundles small and lazy-load heavy dependencies,
- initialize clients outside the handler so warm invocations reuse them,
- use provisioned concurrency / min instances for latency-critical paths,
- consider edge runtimes (V8 isolates) which start much faster.

```js
const db = createPool(process.env.DATABASE_URL); // reused across warm invocations

export const handler = async (event) => {
  const rows = await db.query('SELECT 1');
  return { statusCode: 200, body: JSON.stringify(rows) };
};
```
