## Hints

- Sales people should see only their own offers, managers their department's, the board everything. Where does that filter live so that a new endpoint can't forget it?
- What is the difference between filtering in every query, a repository or ORM extension that adds the filter, and PostgreSQL Row-Level Security?
- How does Postgres RLS know who the current user is when the app connects with one database user through a pool?
- Which places besides list endpoints leak data: exports, search, counts, file downloads, joins?

## Answer

"Data access management" in an internal system usually means **row-level permissions**: two users call the same endpoint and must see different rows. RBAC (#379) answers *what actions* a role can do; row-level access answers *which records*. Getting it wrong is IDOR (#371) at scale.

**1. Express the rule once, as a scope:**

```ts
// one function that turns a user into a Prisma `where`
export function offerScope(user: User): Prisma.OfferWhereInput {
  if (user.roles.includes('board')) return {};
  if (user.roles.includes('manager')) return { departmentId: { in: user.managedDepartmentIds } };
  return { OR: [{ ownerId: user.id }, { sharedWith: { some: { userId: user.id } } }] };
}

// every query composes it
db.offer.findMany({ where: { AND: [offerScope(user), filtersFromQuery] } });
db.offer.findFirst({ where: { AND: [offerScope(user), { id }] } });   // 404 if out of scope, not 403 (don't confirm existence)
```

Use the same scope for lists, single reads, counts, exports, search, and for updates (`updateMany({ where: { AND: [scope, { id }] } })` and check the count).

**2. Make forgetting it hard:**

- A **repository / data-access layer** (#616 `data-access` library) that takes the user (or a request context, #302) and always applies the scope. Route handlers never touch the raw client.
- A **Prisma client extension** created per request (`prisma.$extends(forUser(user))`) that injects the scope into `findMany`/`findFirst`/`count`/`update*`. Convenient, but extensions don't cover `$queryRaw` or nested relation loads automatically, so keep them as a convenience, not the only control.
- **Tests:** for each protected endpoint, a test that user B cannot read or change user A's record (#628).

**3. PostgreSQL Row-Level Security as defence in depth:**

```sql
ALTER TABLE offer ENABLE ROW LEVEL SECURITY;
ALTER TABLE offer FORCE ROW LEVEL SECURITY;              -- applies to the table owner too

CREATE POLICY offer_read ON offer FOR SELECT USING (
  owner_id = current_setting('app.user_id')::uuid
  OR department_id = ANY (string_to_array(current_setting('app.department_ids', true), ',')::uuid[])
  OR current_setting('app.is_board', true) = 'true'
);
```

The app connects as a role **without** `BYPASSRLS`, and sets the user per transaction:

```ts
await prisma.$transaction(async (tx) => {
  await tx.$executeRaw`SELECT set_config('app.user_id', ${user.id}, true)`;   // true = local to this transaction
  return tx.offer.findMany();                                                  // the database filters
});
```

- `set_config(..., true)` (like `SET LOCAL`) is scoped to the transaction, so the setting doesn't leak to the next request that gets the same pooled connection. A plain session-level `SET` with a pool is a data leak waiting to happen.
- Pros: holds even for raw SQL, reporting queries and new endpoints. Cons: every query must run inside a transaction with the setting; policies are harder to test and debug; migrations and admin jobs need a separate role; complex policies can slow queries (check `EXPLAIN`, index the columns used in policies).
- Supabase is built on exactly this pattern (`auth.uid()` in policies).

**4. Related concerns:**

- **Field-level access:** salaries visible to HR only. Use different `select`s or DTOs per role, not just row filters.
- **Files and documents:** never serve files by a guessable path. Check the scope, then stream the file or return a short-lived presigned URL (#410).
- **Caching:** a cache key without the user or scope serves one user's data to another (#351).
- **Audit:** log access to sensitive records (who viewed which contract), not only changes.
- **Sharing and exceptions:** explicit `shares` table with an expiry, so "give the accountant access to this project" doesn't require a new role.

**Follow-up:** an admin "export all offers to Excel" job runs from a worker without a user. How does it get past the scope or RLS, and how do you keep that safe? (A separate service role or an explicit `systemScope()` used only by that job, logged, and never reachable from a user request.)
