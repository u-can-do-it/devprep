## Hints

- How do you make an atomic change to a shared library and all its consumers in each model?
- If every push builds and tests every project, what happens to CI time as the repo grows?
- Who owns which folder, and how do you enforce reviews from the right team?

## Answer

**Monorepo** (many projects in one repo, e.g. web, api, shared packages):
- **Pros:** atomic cross-project changes in a single PR, one version of shared code (no publishing internal packages), consistent tooling and lint rules, easy refactoring and code discovery.
- **Cons:** CI and Git performance at scale, needs build tooling, coarser access control, and coupling can grow unnoticed.

**Polyrepo** (one repo per service or library):
- **Pros:** clear ownership and access control, independent pipelines and release cadence, small fast repos.
- **Cons:** cross-repo changes need coordinated PRs and versioned releases, dependency drift ("which version of `shared-utils` does service X use?"), duplicated config.

**How CI must change for a monorepo:**
- **Affected-only builds:** build and test only projects changed since the base commit *plus their dependents*, using the dependency graph.
- **Task caching:** local and **remote caches** keyed by input hashes, so unchanged work is never redone.
- **Parallelism** across projects, respecting the task graph.
- **Path-based ownership and triggers:** `CODEOWNERS` per folder, path filters, and separate deploy pipelines per app.

```bash
pnpm turbo run lint test build --filter="...[origin/main]"  # changed + dependents
npx nx affected -t lint test build --base=origin/main
```

**Tooling:** pnpm/npm/uv workspaces, Turborepo, Nx, Bazel or Pants at very large scale. For huge repos, use sparse checkout or partial clones.

**Choosing:** monorepo works well for a product team sharing code across a frontend and backends. Polyrepo suits independent teams or products with little shared code, or strict access boundaries.

**Pitfall:** a monorepo without boundaries becomes a distributed monolith. Enforce module boundaries (Nx tags, lint rules) and explicit package APIs.
