## Hints

- What if your page were loaded inside an invisible iframe on someone else's site?
- Which party gets to decide whether a page may be framed – the parent or the page itself?
- Which HTTP headers express that decision?

## Answer

**Clickjacking (UI redressing)** is when an attacker loads your site in a transparent or disguised `<iframe>` and tricks the user into clicking something on it – e.g. "Delete account" or "Confirm payment" – while they think they're clicking the attacker's button. The user is logged in, so the click is a real authenticated action.

**Prevention – forbid framing via response headers:**

```http
Content-Security-Policy: frame-ancestors 'self'
X-Frame-Options: DENY
```

- **`frame-ancestors`** (CSP) is the modern standard: `'none'` (never frame), `'self'`, or a list of trusted origins.
- **`X-Frame-Options`** (`DENY` / `SAMEORIGIN`) is the legacy header; still worth sending for older clients.
- Set them on every HTML response, ideally centrally (reverse proxy, framework middleware).

**Additional measures:**

- `SameSite` cookies reduce the impact – a cross-site iframe won't receive `Lax`/`Strict` cookies, so the user appears logged out.
- Require re-authentication or a confirmation step for very sensitive actions.
- JavaScript "frame-busting" scripts are unreliable and shouldn't be the main defense.

**Follow-up:** What if you legitimately need to be embedded (e.g. a widget)? Allow specific partner origins in `frame-ancestors` and keep sensitive actions out of the embeddable pages.
