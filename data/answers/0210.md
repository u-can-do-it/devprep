## Hints

- Before hooks, how could two components share "subscribe to window size" logic?
- What is "wrapper hell," and why are props from several HOCs hard to trace?
- Where do you still see `children` as a function, or `withSomething()` wrappers, today?

## Answer

Both are patterns for **reusing stateful logic** from the class-component era.

**Higher-order component (HOC):** a function that takes a component and returns a new component with extra props or behavior:

```jsx
const withUser = (Component) => (props) => {
  const user = useUser();
  return <Component {...props} user={user} />;
};
export default withUser(Profile);
```

**Render prop:** a component that calls a function prop (often `children`) with its data:

```jsx
<MousePosition>{({ x, y }) => <Cursor x={x} y={y} />}</MousePosition>
```

**Problems that hooks solve:**

- **Wrapper hell:** five HOCs create five nesting levels in DevTools.
- **Implicit props and name collisions:** where did `user` come from? Two HOCs might both inject `data`.
- **Static composition:** HOCs are applied at module level and can't easily depend on props.
- **Nesting:** render props nest deeply when you combine several.

A custom hook does the same job with plain function calls, explicit variables, and no extra tree nodes:

```jsx
function Profile() {
  const user = useUser();
  const { x, y } = useMousePosition();
  ...
}
```

**Where they still make sense:**

- **HOCs** for cross-cutting wrapping that needs to render something around the component: `withErrorBoundary`, auth gates, `memo()`.
- **Render props or slot props** when the *caller* must control rendering. Headless libraries do this (virtualized lists' `renderItem`, TanStack Table cells).

**Follow-up:** hooks share *logic*, not *state*. Two components calling `useUser()` each get their own state unless the hook reads from a shared store or Context.
