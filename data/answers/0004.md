## Hints

- When an inner function runs later, how can it still read variables of an outer function that has already returned?
- How could you make a counter whose value can't be changed from outside?
- What goes wrong with closures inside a `for (var ...)` loop?

## Answer

A **closure** is a function together with the **lexical environment** it was created in. Every JS function keeps a reference to the variables that were in scope where it was *defined*. It can read and update them even after the outer function has returned.

```js
function createCounter() {
  let count = 0;            // private state
  return {
    inc: () => ++count,
    get: () => count,
  };
}
const c = createCounter();
c.inc(); c.inc();
c.get(); // 2  (count can't be reached directly)
```

**Common uses:**

- **Data privacy / encapsulation:** the module pattern, factory functions.
- **Function factories and partial application:** `const add5 = makeAdder(5)`.
- **Callbacks and event handlers** that need context from where they were created.
- **Memoization:** a cache kept in the enclosing scope.
- React hooks depend on closures. That is also why **stale closures** happen: a callback captures the state from an old render.

**Pitfalls:**

- Closures capture **variables, not values**. With `var` in a loop, every callback shares one variable. Use `let`.
- A closure keeps everything it references alive. A long-lived closure, such as a global listener, can cause **memory leaks**.

**Follow-up:** "What is a stale closure in React and how do you fix it?" Fix it with correct dependency arrays, functional `setState` updates, or refs.
