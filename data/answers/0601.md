## Hints

- With no JIT at runtime, what can't the app do anymore that a lot of libraries rely on (think `Reflection.Emit`, serializers, DI containers)?
- How can the trimmer know which types are used when code finds them by name through reflection?
- What do you gain at startup, and what might you lose in steady-state throughput compared with a JIT that optimizes hot code?

## Answer

**1. What they are**

- **Native AOT** (`<PublishAot>true</PublishAot>`): the app is compiled ahead of time to a single native executable for one OS and CPU. There's no JIT and no IL compilation at runtime.
- **Trimming**: the linker removes code the app doesn't use from the framework and libraries. Native AOT always trims; you can also trim a normal self-contained app (`PublishTrimmed`).
- **Source generators**: Roslyn plugins that generate C# at **compile time**, replacing work that used to be done with reflection at runtime. They're what makes AOT practical.

**2. What you gain**

- **Startup** in tens of milliseconds instead of hundreds, because nothing is JIT-compiled.
- **Lower memory** (no JIT, smaller working set) and a small self-contained binary; no .NET runtime needed in the image.
- Fits serverless functions with cold starts, CLI tools, sidecars and dense container deployments.

**3. What breaks**

| Breaks or is limited | Why | Replacement |
|---|---|---|
| `Reflection.Emit`, runtime code generation, dynamic proxies | there is no JIT | source generators |
| Loading assemblies at runtime (plugins) | everything is compiled in | build-time composition |
| Reflection over types the trimmer removed | the trimmer can't see string-based lookups | annotations, source generators |
| Reflection-based JSON | System.Text.Json walks types at runtime | `JsonSerializerContext` source generation |
| MVC controllers, Razor Pages | rely on reflection | Minimal APIs (with the Request Delegate Generator) |
| Some libraries (older ORMs, AutoMapper-style mappers) | reflection and emit | check for AOT support; EF Core's AOT support is still limited |

The compiler tells you: trim and AOT analyzers emit warnings such as `IL2026` (`[RequiresUnreferencedCode]`) and `IL3050` (`[RequiresDynamicCode]`). Treat them as errors: an app that publishes with warnings may fail at runtime. Library authors set `<IsAotCompatible>true</IsAotCompatible>` to get those analyzers.

**4. A minimal AOT API**

```csharp
var builder = WebApplication.CreateSlimBuilder(args);   // fewer default features, smaller binary
builder.Services.ConfigureHttpJsonOptions(o =>
    o.SerializerOptions.TypeInfoResolverChain.Insert(0, AppJsonContext.Default));

var app = builder.Build();
app.MapGet("/todos", () => new[] { new Todo(1, "Write tests") });
app.Run();

public record Todo(int Id, string Title);

[JsonSerializable(typeof(Todo[]))]                       // serializer code generated at compile time
internal partial class AppJsonContext : JsonSerializerContext;
```

```bash
dotnet publish -c Release -r linux-x64   # PublishAot in the csproj; build on the target OS
```

**5. Source generators you'll meet even without AOT**

- `[GeneratedRegex]`: the regex is compiled to C# at build time.
- `[LoggerMessage]`: allocation-free, strongly typed log methods (#589).
- `[JsonSerializable]`: faster serialization and less startup work.
- The configuration binding generator and the Request Delegate Generator for Minimal APIs.

They help any app: less reflection, faster startup, and errors at compile time instead of runtime.

**6. When it's worth it**

- Worth it: functions and scale-to-zero services where cold start is billed or user-visible, CLIs, small focused microservices, many replicas where memory per pod matters.
- Not worth it: a large MVC or Razor app, heavy use of reflection-based libraries, or long-running services where startup doesn't matter. The JIT with dynamic PGO (#604) can produce **faster steady-state code** than AOT, because it optimizes for the actual hot paths.
- Middle ground: **ReadyToRun** precompiles IL to native code but keeps the JIT for re-optimizing, so startup improves without AOT's restrictions.

**Follow-up:** the AOT build publishes fine but a JSON endpoint returns empty objects or throws at runtime. What's the likely cause? (The type isn't in the `JsonSerializerContext`, or code takes the reflection-based path the trimmer stripped. Add the type to the context and fix every trim/AOT warning instead of suppressing it.)
