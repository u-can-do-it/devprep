## Hints

- What would a contractor need in the brief to finish the task without calling you?
- Where is the cheapest moment to catch a wrong approach: in the plan, in the diff or in production?
- Which behaviours during a session tell you the agent is off track, even before you read the code?

## Answer

Delegating a whole task means the agent goes from brief to a reviewable PR on its own, while you stay accountable for what ships (#476).

**1. Pick a task that can be delegated**

Good: well defined, verifiable by tests, types or a visible result, with a bounded blast radius (an endpoint, a migration with a backfill, a refactor across 30 files, a bug with a reproduction). Bad without close supervision: vague product decisions, security-critical logic, a redesign touching many teams' code.

**2. Write a brief, not a one-liner**

- Goal and **why** (the agent makes better choices when it knows the purpose).
- Acceptance criteria, including edge cases.
- Constraints: "don't change the public API", "no new dependencies", "follow the pattern in `modules/booking`".
- Pointers to the relevant files, tickets, logs.
- **How to verify**: the commands to run, what a passing result looks like.
- What's out of scope.

**3. Review the plan before any code.** Ask for a plan (plan mode) and check it: right layer, right data model, no unnecessary abstraction, the domain understood. Fixing a plan costs a minute; fixing 600 lines in the wrong place costs an hour.

**4. Give it a feedback loop and isolation.** Tests first or a failing reproduction, then let it iterate until tests, types and lint pass and it has checked the result itself (run the app, open the page). Work in a branch or worktree; run independent tasks in parallel agents.

**5. Review by risk.** Read the diff where it matters (data, money, auth, concurrency, migrations), run it yourself, and ask the agent to explain non-obvious decisions. A second agent with fresh context is a useful extra reviewer, not a replacement.

**Signs the agent is wrong:**

| Sign | Example |
|---|---|
| It games the checks | weakens assertions, skips or deletes tests, updates snapshots, adds `@ts-ignore`, `any` or `eslint-disable` |
| It claims success without evidence | "this should fix it" without running anything; tests "pass" but weren't run |
| It hides errors | broad `try/catch`, fallback values, `?? []` everywhere, retries around a bug |
| Scope creep | unrelated files reformatted, new dependencies, a rewrite instead of a fix |
| It loops | the same fix tried three times, flip-flopping between approaches, complexity growing with each attempt |
| Invented things | APIs, config options, CLI flags or packages that don't exist, outdated library versions |
| Special-casing | code that recognises the test input instead of fixing the logic |
| Domain errors | local time instead of UTC, floats for money, ignoring permissions |
| Confident diagnosis without data | "the bug is caused by X" with no log, trace or reproduction |
| It duplicates | writes a new helper instead of using the existing one |

**What to do when you see them:** stop early. Don't keep arguing in a long, polluted context; quality drops as the context fills up. Start a fresh session with a better brief that includes what you've learned, split the task, give it the failing evidence, or take over the hard part yourself and hand back the rest. Then fix the cause: add the missing convention or a check to the repo setup so the next session doesn't repeat it (#541).

**Know your own numbers:** how often agent PRs merge as they are, need fixes or get rewritten, and for which kinds of tasks. That tells you where delegating pays off (#543).

**Follow-up:** tell me about a time an agent produced plausible but wrong code and how you caught it (#499).
