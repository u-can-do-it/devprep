## Hints

- The dev server says "port 3000 is already in use". How do you find and stop the process?
- What do `chmod 755`, `chmod +x` and `rwxr-x---` mean?
- What is the difference between `>`, `>>`, `|` and `2>&1`?
- Why is `pnpm install` ten times slower in `/mnt/c/Users/...` than in `~/projects` under WSL?
- Your shell script fails with `/bin/bash^M: bad interpreter`. What happened?

## Answer

> Interviewers check that you can work without a GUI: search code with `grep`, follow logs with `tail -f`, find what is using a port, stop processes, and chain commands with pipes and redirection. Know basic file permissions, like `chmod +x` for scripts and `600` for SSH keys. In WSL, keep repositories in the Linux filesystem, not under `/mnt/c`, because crossing that boundary is slow and file watchers miss changes. Install your tools inside WSL, and watch out for CRLF line endings.

The job asks for "basic terminal and Linux/WSL skills". Interviewers check that you can move around, read logs, find processes and fix the usual WSL problems without a GUI.

**Everyday commands:**

| task | command |
|---|---|
| where am I, list incl. hidden | `pwd`, `ls -la` |
| search text in a project | `grep -rn "approveOffer" src/` (or `rg`) |
| find files | `find . -name "*.sql" -not -path "*/node_modules/*"` |
| read and follow logs | `less app.log`, `tail -f app.log`, `tail -n 200 app.log \| grep ERROR` |
| disk usage | `df -h` (disks), `du -sh node_modules` (folder) |
| processes | `ps aux \| grep node`, `top` / `htop` |
| what listens on a port | `ss -ltnp \| grep 3000` or `lsof -i :3000` |
| stop a process | `kill <pid>` (SIGTERM, lets it shut down gracefully, #301), `kill -9 <pid>` (SIGKILL, last resort) |
| HTTP from the shell | `curl -i http://localhost:3000/health`, `curl -s ... \| jq '.items[0]'` |
| environment | `echo $PATH`, `export NODE_ENV=production`, `env \| grep DATABASE`, `which node` |
| remote | `ssh user@host`, `scp file user@host:/tmp/`, keys in `~/.ssh/` |

**Pipes and redirection:** `|` passes stdout to the next command; `>` overwrites a file, `>>` appends; `2>` redirects stderr; `cmd > out.log 2>&1` sends both to one file; `&&` runs the next command only if the previous one succeeded (exit code 0), `||` only if it failed.

**Permissions:** each file has owner/group/others × read/write/execute. `rwxr-x---` = `750`: owner can do everything, group can read and execute, others nothing. `chmod +x deploy.sh` makes a script executable; `chown` changes the owner. SSH private keys must be `600`, or ssh refuses them. Avoid `sudo` for `npm install -g`; use a version manager (nvm, fnm, volta) installed in your home directory.

**Shell config:** `~/.bashrc` / `~/.zshrc` for aliases, `PATH` and version managers; `source ~/.bashrc` reloads it. A script starts with a shebang (`#!/usr/bin/env bash`), and `set -euo pipefail` makes it stop on errors and undefined variables.

**WSL (Windows Subsystem for Linux):**

- **WSL 2** runs a real Linux kernel in a lightweight VM. You get a normal Ubuntu (or other distro) with `apt`, and Windows can still reach its files at `\\wsl$\`.
- **Keep repositories in the Linux filesystem** (`~/projects`), not under `/mnt/c`. Crossing the Windows/Linux boundary makes file I/O slow (installs, builds, git) and file watchers (Vite HMR, `nx`, `tsc --watch`) may miss changes.
- **Line endings:** files checked out on Windows can get CRLF, and Linux then fails with `bad interpreter: ^M`. Use `git config --global core.autocrlf input` in WSL and a `.gitattributes` with `* text=auto eol=lf`.
- **Install Node, pnpm, Python and the Prisma engines inside WSL**, not on Windows, so binaries match the platform.
- **Networking:** `localhost:5173` in the Windows browser reaches a server in WSL 2 thanks to localhost forwarding. A server must listen on `0.0.0.0`, not `127.0.0.1`, to be reachable from other machines (#384).
- **Docker Desktop** uses the WSL 2 backend; `docker` works inside WSL once integration is enabled for your distro.
- **Editors:** VS Code with the WSL extension runs the editor's server inside Linux, so extensions, terminals and git use the Linux toolchain.
- Memory and CPU limits for the VM go in `%UserProfile%\.wslconfig`; `wsl --shutdown` restarts it.

**Follow-up:** a teammate on macOS says the build works for them, but on your WSL it fails with `Cannot find module './OfferForm'` while the file `offerForm.tsx` exists. Why? (macOS's default filesystem is case-insensitive and Linux is case-sensitive. Fix the import's casing, and let `forceConsistentCasingInFileNames` in `tsconfig.json` catch it.)
