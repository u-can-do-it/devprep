## Hints

- What does the GIL prevent today, and which workloads does it hurt?
- What happens when you import a C extension that hasn't declared it's safe without the GIL?
- What does a typical FastAPI or Django service mostly wait on: CPU or I/O?

## Answer

**Free-threaded Python** is a separate CPython build (`python3.13t`, `python3.14t`) where the **Global Interpreter Lock is removed** (PEP 703). Threads can run Python bytecode **in parallel on multiple cores**.

Status:

- 3.13: experimental.
- 3.14: **officially supported** (PEP 779), but still an optional build. The default `python` still has the GIL.
- You can check with `sys._is_gil_enabled()`. `PYTHON_GIL=0` or `-X gil=0` forces it off.

What changes:

- CPU-bound work in a `ThreadPoolExecutor` actually scales with cores, without the pickling and memory costs of `multiprocessing`.
- **Single-threaded code runs somewhat slower** (roughly 5–10% in 3.14, more in 3.13) because of per-object locking and the different memory allocator.
- **C extensions** must declare support (`Py_mod_gil`). Importing one that doesn't **re-enables the GIL** for the whole process, with a warning. Major libraries (NumPy, Cython-built packages) ship `cp314t` wheels, but coverage of the long tail is uneven.
- **Race conditions** that the GIL hid can now appear in your own code: unsynchronized counters, check-then-act on shared dicts, lazy initialization. Built-in containers remain internally safe, but compound operations still need `threading.Lock`.

**Should you adopt it in production now?** Usually **not by default**:

- Most web services are **I/O-bound**. asyncio or threads with the GIL already handle them well, and you scale with processes or containers.
- Adopt it when profiling shows **CPU-bound, parallelizable Python work** (data transforms, parsing, inference pre-processing) where multiprocessing overhead hurts, **and** your dependency tree supports it.
- Plan: run the test suite and load tests on the `t` build, check that the GIL stays disabled after all imports, benchmark single- and multi-threaded throughput, and roll out behind a separate image.

Related: subinterpreters (`concurrent.interpreters` in 3.14, PEP 734) give isolation-based parallelism as another option.

**Follow-up:** Does free-threading make asyncio faster? (Not on its own. The event loop still runs on one thread. You gain only by moving CPU work to threads.)
