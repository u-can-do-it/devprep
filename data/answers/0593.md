## Hints

- A `Span<T>` can point at stack memory. What would go wrong if you stored it in a field of a class or kept it across an `await`?
- How do you parse part of a string without allocating a substring?
- What must you never do after returning an array to `ArrayPool<T>`?

## Answer

They let you work on **slices of existing memory without copying or allocating**, which means less GC work (#591) on hot paths.

| Type | What it is | Where it can live | Across `await`, in fields of classes |
|---|---|---|---|
| `Span<T>`, `ReadOnlySpan<T>` | `ref struct`: a reference plus a length over an array, string, `stackalloc` or native memory | stack only | no |
| `Memory<T>`, `ReadOnlyMemory<T>` | ordinary struct over an array, string or custom memory | anywhere | yes; use `.Span` to work on it |
| `stackalloc` | a buffer in the current stack frame | current method | no |
| `ArrayPool<T>.Shared` | rents and reuses arrays | heap | yes |

**Slicing without allocating**

```csharp
// "2026-10-29" -> (2026, 10, 29) without three Substring allocations
static (int Y, int M, int D) ParseDate(ReadOnlySpan<char> s) =>
    (int.Parse(s[..4]), int.Parse(s.Slice(5, 2)), int.Parse(s[8..]));

ParseDate("2026-10-29");     // string converts implicitly to ReadOnlySpan<char>
```

Slicing is O(1) and copies nothing. Most of the BCL has span overloads: parsing, `TryFormat`, `IndexOf`, `SequenceEqual`, UTF-8 encoding, streams.

**Why `ref struct` is restricted**

A span may point to the stack or into the middle of an object. If it escaped to the heap it could outlive the stack frame it points to, and the GC only tracks such interior references on the stack. So the compiler forbids boxing a span, storing it in a field of a class or normal struct, capturing it in a lambda, and keeping it alive across an `await` or `yield` (C# 13 allows `ref struct` locals in async methods and iterators as long as they don't cross one). When you need a buffer in async code, use `Memory<T>`:

```csharp
async Task<int> ReadAsync(Stream stream, Memory<byte> buffer, CancellationToken ct)
{
    int total = 0, read;
    while (total < buffer.Length &&
           (read = await stream.ReadAsync(buffer[total..], ct)) > 0)   // Memory<T> crosses the await
        total += read;
    return total;
}
```

**`stackalloc`**

```csharp
Span<byte> buffer = length <= 256 ? stackalloc byte[256] : new byte[length];
buffer = buffer[..length];
```

The stack is small (about 1 MB per thread by default). Use `stackalloc` only for **small, bounded** sizes and never in a loop: a stack overflow kills the process and can't be caught.

**`ArrayPool<T>`**

```csharp
byte[] rented = ArrayPool<byte>.Shared.Rent(64 * 1024);    // may return a bigger array
try
{
    int n = await stream.ReadAsync(rented.AsMemory(0, 64 * 1024), ct);
    Process(rented.AsSpan(0, n));                            // use only the part you filled
}
finally
{
    ArrayPool<byte>.Shared.Return(rented);                   // clearArray: true if it held secrets
}
```

Pitfalls: the array can be **longer** than requested and still holds **old data**; using it after `Return` is a use-after-free bug, because another caller may already own it; forgetting to return it isn't a leak, you just lose the pooling. `System.IO.Pipelines` (which Kestrel uses) and `IBufferWriter<T>` build on the same ideas.

**When it's worth it:** in measured hot paths such as parsers, serializers, middleware and high-throughput pipelines (#606), confirmed with BenchmarkDotNet's `[MemoryDiagnoser]` (#594). In ordinary business code, readable code wins.

**Follow-up:** why does `Substring` allocate when `AsSpan(...)` doesn't, and when do you still need a `string`? (`Substring` copies the characters into a new object; a span is just a view. You need a string to store it or pass it to APIs that take strings. For dictionary lookups, .NET 9's `GetAlternateLookup<ReadOnlySpan<char>>()` lets you look up string keys with a span.)
