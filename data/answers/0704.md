## Hints

- What happens to your JavaScript timers a minute after the user switches to another app?
- If you schedule a periodic sync every 15 minutes, who decides when it really runs?
- Which kinds of background work does the OS let you hand over, so that it continues without your app running?

## Answer

> Mobile systems protect the battery, so an app in the background is suspended within seconds and may be killed at any time. You can't run code freely. You ask the OS for a specific kind of background work, and the OS decides when, or whether, it runs. The main kinds are: a short grace period to finish a task, periodic deferrable work, transfers handed to the OS, location updates, and wake-ups by push. Design every one as best effort, and always sync again when the app returns to the foreground.

**What happens by default**

When the app leaves the foreground, JavaScript keeps running only briefly. Timers, polling and open sockets stop. Later the OS may remove the process, and the next launch is a cold start (#682).

**The kinds of background work**

| Need | iOS | Android | From React Native |
|---|---|---|---|
| Finish what just started (save, send) | a short background task, around 30 s | short grace period, or a foreground service | usually handled by the networking or upload library |
| Periodic sync | `BGTaskScheduler`: the system picks the time | `WorkManager`: minimum 15 minutes, with constraints | `expo-background-task` with `expo-task-manager` |
| Large uploads and downloads | background `URLSession` | `WorkManager` or the download manager | background upload and download libraries |
| Location tracking | "Always" permission, background mode | background permission and a foreground service | `expo-location` with a task |
| Server-triggered work | silent push | high-priority data message | push library handler (#683) |
| Ongoing user-visible work (navigation, a call, playback) | background modes: audio, VoIP, location | foreground service with a notification | dedicated libraries |

**Periodic tasks**

```ts
import * as TaskManager from 'expo-task-manager';
import * as BackgroundTask from 'expo-background-task';

// Defined at the top level: the OS can start the app without any UI to run this
TaskManager.defineTask('sync', async () => {
  try {
    await syncPendingChanges();
    return BackgroundTask.BackgroundTaskResult.Success;
  } catch {
    return BackgroundTask.BackgroundTaskResult.Failed;
  }
});

await BackgroundTask.registerTaskAsync('sync', { minimumInterval: 60 });   // minutes; a request, not a promise
```

- The interval is a minimum. iOS learns when the user opens the app and schedules around that; an app that is rarely opened may get almost no background time.
- Nothing runs after the user force-quits the app on iOS.
- On Android, Doze mode, app standby buckets and some manufacturers' battery savers delay or block work.
- The task runs without React components. It must be short, idempotent and safe to stop halfway (#696).

**Transfers**

Hand a large upload or download to the OS instead of keeping the app alive. The system continues it while the app is suspended, retries on reconnect, and wakes the app when it finishes.

**Location**

- Background location needs the stronger permission, asked separately after "while using", and a store review justification (#685).
- Android requires a foreground service with a visible notification while tracking.
- Use the cheapest mode that works: geofences or significant-change updates use far less battery than continuous GPS.

**Push as a trigger**

A silent push can ask the app to sync, but it is throttled and not guaranteed, especially on iOS and for apps that were force-stopped. Treat it as a hint.

**Foreground services on Android**

They keep the app alive for work the user can see, with a permanent notification. Recent Android versions require a declared service type, restrict starting one from the background, and Play reviews their use.

**Design rules**

- **Best effort:** never promise the user that something will happen at an exact time in the background.
- **Foreground sync is the baseline.** Background work only makes the app fresher when it opens.
- **Prefer the server:** do scheduled work on the backend and notify the device with a push.
- **Keep tasks short and idempotent,** with a network constraint when they need the network.
- **Watch the battery.** Both stores and both systems report and punish excessive background use.

**Testing**

Scheduling can't be tested by waiting. Trigger tasks manually with the debug commands of each platform, and test on real devices from several manufacturers.

**Follow-up:** product asks for "sync every 5 minutes in the background so data is always fresh". What do you answer? (The OS doesn't allow that: the minimum is about 15 minutes on Android and unpredictable on iOS. Offer sync on open and on foreground, a push when important data changes, and periodic background sync as a bonus.)
