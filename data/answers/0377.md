## Hints

- What can an attacker do with a fake login page that looks exactly like yours, for each MFA method?
- Where does the secret live in each method, and can it be copied?
- What happens when the user loses their phone?

## Answer

> MFA adds a second factor, but methods differ a lot in strength. SMS codes are weak: SIM swaps and fake sites that relay the code beat them. TOTP apps are better, but a user can still type the code into a phishing site. Passkeys use a key pair per site and sign a challenge, and the browser binds that to the real origin. On a look-alike domain the passkey simply doesn't exist, and there's no code to hand over. The server stores only public keys.

MFA combines factors from different categories: something you **know** (password), **have** (phone, security key), or **are** (biometric). Methods differ a lot in strength:

- **SMS / email codes**: better than nothing, but weak. Vulnerable to SIM swapping, SS7 interception, and **phishing**: a fake site relays the code in real time. Current guidance (e.g. NIST) restricts SMS as an authenticator.
- **TOTP apps** (Google Authenticator, 1Password): a shared secret, provisioned via a QR code, generates a code from the current 30-second window (RFC 6238). No telecom dependency, works offline. Still **phishable**: the user can type the code into a fake site, and the shared secret is stored server-side, so it must be encrypted.
- **Push approvals**: convenient, but vulnerable to "MFA fatigue" spam unless they use number matching.
- **WebAuthn / passkeys**: the device creates a **key pair per site**. The server stores only the public key; login is a **signed challenge**.

Why passkeys resist phishing:

1. The browser includes the **origin** in the signed data, and credentials are bound to the relying party ID (e.g. `example.com`). On `examp1e.com` the passkey simply doesn't exist, and there is no code the user could hand over.
2. There's **no shared secret** on the server to steal; a DB leak exposes only public keys.
3. User verification (biometric/PIN) happens locally and never leaves the device.

Synced passkeys (iCloud Keychain, Google Password Manager, password managers) fix the "lost device" problem; device-bound security keys give higher assurance.

Implementation notes: use a maintained WebAuthn library (SimpleWebAuthn, py_webauthn), offer **recovery codes**, make account recovery as strong as login (it's a common bypass), and rate-limit code verification.

**Follow-up:** Is a passkey alone single-factor? It counts as MFA: possession of the device plus local biometric/PIN.
