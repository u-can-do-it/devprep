## Hints

- Does the data need to flow in one direction or both?
- What happens with each approach when a proxy or load balancer sits in between?
- How many open connections can your server handle, and what about reconnects?

## Answer

All three let the server push updates to the client.

**Long polling**

The client sends a request; the server holds it until there's data (or a timeout), responds, and the client immediately re-requests.

- Works everywhere over plain HTTP.
- Overhead of a new request per message, extra latency, awkward ordering. Mostly a fallback today.

**Server-Sent Events (SSE)**

One long-lived HTTP response with `Content-Type: text/event-stream`; server → client only.

```js
const es = new EventSource("/api/notifications");
es.addEventListener("order", (e) => render(JSON.parse(e.data)));
```

- Simple, plain HTTP (works with HTTP/2 multiplexing, standard auth/cookies, proxies).
- **Automatic reconnect** with `Last-Event-ID`.
- Text only, one direction. Great for notifications, live feeds, progress, and **LLM token streaming**.

**WebSockets**

An HTTP `Upgrade` turns the connection into a persistent, **full-duplex** channel (`ws://`/`wss://`).

```js
const ws = new WebSocket("wss://chat.example.com");
ws.onmessage = (e) => console.log(e.data);
ws.send(JSON.stringify({ type: "typing" }));
```

- Low latency both ways, binary support.
- You handle reconnects, heartbeats, auth and message protocol yourself; stateful connections make load balancing and scaling harder (sticky sessions, pub/sub backplane like Redis).

**Choosing:**

- Chat, multiplayer, collaborative editing → **WebSockets**
- Server → client streams (dashboards, notifications, AI responses) → **SSE**
- Restricted environments or rare updates → **long polling** (or just regular polling)

**Follow-up:** How do you scale WebSockets horizontally? (Pub/sub fan-out between instances, connection limits, graceful draining on deploy.)
