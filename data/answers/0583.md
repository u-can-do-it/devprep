## Hints

- Where do routing, binding and filters live in each style: in a class with attributes, or in a lambda registered in `Program.cs`?
- How does ASP.NET Core decide whether a parameter comes from the route, the query string, the body or DI?
- Why is `Results<Ok<T>, NotFound>` more useful than returning `IResult`?

## Answer

Both run on the same routing, middleware, auth and DI. The difference is **how you declare endpoints** and how much framework machinery sits between the request and your code.

| | Controllers | Minimal APIs |
|---|---|---|
| Declaration | classes deriving from `ControllerBase`, attributes (`[HttpGet]`, `[Route]`) | `app.MapGet(...)` lambdas or static methods, grouped with `MapGroup` |
| Cross-cutting logic | action filters, `[ApiController]` conventions | endpoint filters, route group conventions |
| Validation | automatic with `[ApiController]` (400 + ProblemDetails) | built in since .NET 10 with `AddValidation()`; before that, a filter or FluentValidation |
| Overhead | MVC pipeline, model state, more reflection | thinner, works with Native AOT (#601) |
| Good for | large existing codebases, teams used to MVC | new services, small APIs, vertical slices (#597) |

**Routing and model binding**

```csharp
var orders = app.MapGroup("/orders").RequireAuthorization();

orders.MapGet("/{id:int}", async Task<Results<Ok<OrderDto>, NotFound>> (
    int id,                       // from the route
    [FromQuery] bool? details,    // from the query string
    AppDbContext db,              // from DI (registered service)
    CancellationToken ct) =>      // bound to HttpContext.RequestAborted
{
    var order = await db.Orders.FindAsync([id], ct);
    return order is null ? TypedResults.NotFound() : TypedResults.Ok(order.ToDto());
});

orders.MapPost("/", (CreateOrder body, IOrderService svc) => ...);   // complex type → JSON body
```

Binding rules: route values and query strings for simple types, the body for complex types (only one body parameter), services from DI, and special types (`HttpContext`, `CancellationToken`, `ClaimsPrincipal`). Use `[AsParameters]` to bind a whole record of parameters.

**`TypedResults` vs `Results`**

`Results.Ok(x)` returns `IResult`, so the OpenAPI generator can't see what the endpoint returns. `TypedResults.Ok(x)` returns `Ok<T>`, and a return type of `Results<Ok<OrderDto>, NotFound>` documents every possible response, is checked by the compiler, and is easy to assert in unit tests.

**Endpoint filters**

The Minimal API equivalent of action filters: they run around the handler and can inspect arguments or short-circuit.

```csharp
orders.MapPost("/", Handler).AddEndpointFilter(async (ctx, next) =>
{
    var body = ctx.GetArgument<CreateOrder>(0);
    if (body.Quantity <= 0)
        return TypedResults.ValidationProblem(new() { ["quantity"] = ["Must be positive"] });
    return await next(ctx);
});
```

**Controllers in the same terms:** `[ApiController]` turns on attribute routing requirements, automatic 400s for invalid models, and binding inference (`[FromBody]` for complex types). `ActionResult<T>` plays the role of typed results.

**Follow-up:** a Minimal API file grows to 2,000 lines. How do you organise it? (Route groups per feature, handlers as static methods or classes in feature folders, an extension method like `app.MapOrders()` per slice; shared filters and auth on the group.)
