## Hints

- Why would you not want to read a 5 GB file into memory with `fs.readFile`?
- What should a writable stream signal when its internal buffer is full, and what should the producer do?
- What does `pipeline` give you that chained `.pipe()` calls don't?

## Answer

Streams process data **incrementally in chunks** instead of buffering everything in memory. Four types: **Readable**, **Writable**, **Duplex** (both, e.g. a TCP socket) and **Transform** (duplex that modifies data, e.g. gzip).

**Backpressure** happens when the consumer is slower than the producer. Each writable stream has a buffer with a `highWaterMark` (default 16 KiB for bytes, 16 objects in object mode). `writable.write(chunk)` returns `false` when the buffer is over that mark; the producer must stop and wait for the `'drain'` event. If you ignore the return value, memory grows unbounded.

```js
import { pipeline } from 'node:stream/promises';
import { createReadStream, createWriteStream } from 'node:fs';
import { createGzip } from 'node:zlib';

await pipeline(
  createReadStream('big.log'),
  createGzip(),
  createWriteStream('big.log.gz'),
);
```

`pipe()` and `pipeline()` handle backpressure automatically by pausing the readable. Prefer **`stream/promises` `pipeline`**: it also propagates errors and destroys all streams on failure, which plain `.pipe()` does not (a classic source of fd leaks).

Readable streams are also async iterables, so `for await (const chunk of stream)` respects backpressure naturally.

Use cases: file uploads/downloads, CSV/log processing, proxying HTTP responses, streaming DB cursors.
