## Hints

- If you store a timer ID somewhere, should changing it redraw the screen?
- What happens to a normal `let` variable inside a component on the next render?
- Is it safe to read `ref.current` during render?

## Answer

`useRef(initial)` returns a mutable object, `{ current: initial }`. React keeps the **same object** for the component's whole lifetime. Changing `.current` **does not trigger a re-render**.

| | `useState` | `useRef` |
|---|---|---|
| Survives re-renders | yes | yes |
| Changing it re-renders | yes | no |
| Value updates | on the next render (snapshot) | immediately, it's mutable |
| Use for | data that appears in the UI | data the UI doesn't depend on |

**Typical uses:**

- **DOM access:** focus an input, measure an element, call `.play()` on a video.
- **Instance values:** timer or interval IDs, an `AbortController`, a WebSocket.
- **Latest value for async callbacks:** avoids stale closures.

```jsx
function Search() {
  const inputRef = useRef(null);
  const timerRef = useRef(null);

  function onType(e) {
    clearTimeout(timerRef.current);
    timerRef.current = setTimeout(() => search(e.target.value), 300);
  }
  return <input ref={inputRef} onChange={onType} />;
}
```

A plain `let` variable would reset on every render, so it can't do this job.

**Rule:** don't read or write `ref.current` during rendering, except for one-time lazy initialization. Rendering should be pure, and the React Compiler's lint rules flag this. Read and write refs in event handlers and effects.

**Follow-up:** if the screen should change when a value changes, it belongs in state. If you store it in a ref, the UI will go stale.
