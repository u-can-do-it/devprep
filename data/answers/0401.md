## Hints

- What happens with plain Docker when a container crashes at 3 a.m., or the whole host dies?
- How do other services find a set of containers whose IPs keep changing?
- How does traffic from the internet reach the right service inside a cluster?

## Answer

**Docker** builds and runs containers on a single host. **Kubernetes** is an **orchestrator**: you declare the desired state ("3 replicas of api:v42"), and its control loops keep the cluster matching it. It provides scheduling across many nodes, self-healing, rolling updates, autoscaling, service discovery, and config/secret management. (Kubernetes runs OCI images through containerd. Docker is just one way to build them.)

Core objects a full-stack developer should know:

- **Pod:** the smallest unit. One or more containers sharing a network namespace and volumes. Pods are disposable.
- **Deployment:** manages a ReplicaSet of identical pods and handles rolling updates and rollbacks.
- **Service:** a stable virtual IP and DNS name (`api.default.svc`) that load-balances across matching pods, so clients don't track pod IPs.
- **Ingress** (or its successor, the **Gateway API**): HTTP routing from outside the cluster to Services by host or path, plus TLS termination.
- **ConfigMap / Secret:** configuration injected as env vars or files.
- **Probes:** `readinessProbe` (send traffic?), `livenessProbe` (restart?), `startupProbe` (slow boot).

```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: api }
spec:
  replicas: 3
  selector: { matchLabels: { app: api } }
  template:
    metadata: { labels: { app: api } }
    spec:
      containers:
        - name: api
          image: ghcr.io/acme/api:1.4.2
          ports: [{ containerPort: 3000 }]
          readinessProbe: { httpGet: { path: /healthz, port: 3000 } }
```

**Follow-up:** "Do you always need Kubernetes?" No. For small teams, managed platforms (Cloud Run, ECS/Fargate, Fly.io, Render) give most of the benefits with far less operational overhead.
