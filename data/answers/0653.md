## Hints

- Which of these does the model read and may ignore, and which does the harness run no matter what the model decides?
- What is in the context window at the start of a session, and what loads only when it's needed?
- "Always run the formatter after an edit": where does that rule belong, and why not in `CLAUDE.md`?

## Answer

> A skill is a folder of instructions the model loads when a task needs them; the model decides whether and how to follow it. A hook is a command the harness runs on an event such as "before a tool call"; it runs every time and can block the action. So a skill teaches the agent how to do something, and a hook guarantees that something happens. Facts go in `CLAUDE.md`, procedures in skills, rules that must hold in hooks or permissions, isolated work in subagents, and access to other systems in MCP servers.

Examples use Claude Code, where these names come from. Cursor, Codex and Copilot have their own instruction files, and several agent tools read skills in the same `SKILL.md` format, which was published as an open standard (Agent Skills).

**The two in one line each**

- **Skill:** `.claude/skills/<name>/SKILL.md` with a `description` and a body of instructions, plus optional scripts and reference files. Only the name and description sit in context. The body loads when the model judges the task matches, or when you type `/name`. It is **advice**: the model reads it and usually follows it.
- **Hook:** an entry in `settings.json` that says "on this event, for these tools, run this command". The **harness** runs it, not the model, so it runs **every time**. It gets the event as JSON on stdin and can block the action, add context or do work on the side.

```json
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Edit|Write",
      "hooks": [{ "type": "command", "command": "f=$(jq -r '.tool_input.file_path') && npx prettier --write --ignore-unknown \"$f\"" }]
    }]
  }
}
```

**Where each thing belongs**

| Mechanism | What it is | When it applies | Guaranteed? | Costs context? |
|---|---|---|---|---|
| `CLAUDE.md` | facts about the repo: commands, conventions, traps | every session, always loaded | no, advice | yes, every line, every session |
| Skill | a procedure: "add a migration", "release" | when the task matches or on `/name` | no, advice | only the description until it's used |
| Hook | a command run on a lifecycle event | every time the event fires | yes | no, unless it returns output |
| Permission rule | allow / ask / deny for tools and paths | every tool call | yes | no |
| Subagent | a separate context with its own prompt, tools and model | when the main agent delegates | n/a | no, only its summary comes back |
| MCP server | new tools and data from another system | when the model calls a tool | n/a | tool definitions do |

**How to decide**

- A **fact** the agent needs in every session ("money is in cents") goes in `CLAUDE.md`.
- A **procedure** needed sometimes goes in a skill. A section of `CLAUDE.md` that has grown into step-by-step instructions is a skill waiting to be extracted.
- Something that **must happen every time** (format, lint, never touch `.env`, don't finish while types fail) goes in a hook, a permission rule or CI. "ALWAYS run prettier" in a prompt is a request; a `PostToolUse` hook is a guarantee.
- Work that would **flood the context** (searching a large codebase, reading logs) or needs different tools goes to a subagent.
- **Access** to Jira, logs or a database is an MCP server. It adds capability, not instructions.

They combine: a skill can call MCP tools, declare its own hooks or run in a subagent, a subagent can preload skills, and a plugin packages all of them for a team.

**Common mistakes**

- Putting a hard rule in `CLAUDE.md`, watching the agent ignore it once in twenty sessions, then writing it again in capitals. Move it to a hook or a lint rule.
- Using a hook for something that needs judgement ("review the design"). Hooks are good at yes/no checks on concrete input.
- A 600-line `CLAUDE.md` full of procedures that are relevant to one task in ten.
- Ten MCP servers enabled "just in case", with their tool definitions taking context in every session.
