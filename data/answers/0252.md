## Hints

- Where would you store a small piece of element-specific information that your script or CSS needs?
- How does an attribute name like `data-user-id` look when you read it from JavaScript?
- Would you put a secret or your app's main state in markup?

## Answer

`data-*` attributes are custom, valid HTML attributes for attaching **private, element-level data** that no standard attribute covers.

```html
<button class="add" data-product-id="42" data-variant="large">Add to cart</button>
```

```js
const btn = document.querySelector('.add');
btn.dataset.productId;   // "42" (dashes become camelCase)
btn.dataset.variant = 'small';      // writes data-variant
delete btn.dataset.variant;         // removes it
btn.getAttribute('data-product-id'); // also works
```

All values are **strings**, so convert them yourself (`Number(...)`, `JSON.parse(...)`).

**Good uses:**

- **Event delegation**: one listener on a list, with the item's id read from `event.target.closest('[data-id]').dataset.id`.
- **Styling state**: `[data-state="open"] { ... }`. Headless libraries such as Radix use this pattern, and Tailwind supports it with `data-[state=open]:`.
- **CSS `attr()`** in generated content: `content: attr(data-label)`.
- **Test hooks**: `data-testid`, though querying by role or label is usually better.
- Passing small amounts of server-rendered configuration to a script.

**Bad uses:**

- **Sensitive data.** Anyone can see it in the markup.
- **Large or complex app state.** It belongs in JavaScript state or a store, and serializing it into the DOM is slow and duplicates data.
- **Replacing semantics.** `data-disabled` doesn't disable anything. Use `disabled`, or ARIA when it fits.
- **Content that matters to assistive technology.** Screen readers ignore data attributes.

**Follow-up:** in React you write `data-*` attributes as-is (`data-testid="x"`), and they pass straight through to the DOM.
