## Hints

- In which router are components Server Components by default?
- How do you fetch data for a page in each router — special exported functions or something else?
- How are layouts and loading/error states expressed in each?

## Answer

Both are file-system routers, but the **App Router** (`app/`, the default since Next.js 13.4) is built on React Server Components, while the **Pages Router** (`pages/`) is the older client-first model. They can coexist in one project during migration.

| | Pages Router | App Router |
|---|---|---|
| Default component | Client (hydrated) | **Server Component**; opt in with `'use client'` |
| Data fetching | `getServerSideProps`, `getStaticProps`, `getStaticPaths` | `async` components that `await` data directly; `generateStaticParams` |
| Layouts | `_app` / `_document`, manual per-page layouts | Nested `layout.tsx` that persist across navigations |
| Loading / errors | Manual | `loading.tsx` (Suspense), `error.tsx`, `not-found.tsx` |
| Streaming | Limited | Built in via Suspense |
| Mutations | API routes | **Server Actions** + Route Handlers (`route.ts`) |
| Metadata | `next/head` | `metadata` export / `generateMetadata` |

```tsx
// app/products/[id]/page.tsx
export default async function Page({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  const product = await db.product.find(id);
  return <h1>{product.name}</h1>;
}
```

**Why App Router:** less JavaScript shipped to the browser, colocated data fetching, nested layouts, streaming, and fine-grained caching. **Trade-offs:** a new mental model (server/client boundary), caching semantics that changed across versions, and some libraries that need `'use client'` wrappers.

Request interception lives in a root-level `middleware.ts` — renamed to `proxy.ts` in Next.js 16 — and works with both routers.

**Follow-up:** new projects should use the App Router; the Pages Router is still supported but receives few new features.
