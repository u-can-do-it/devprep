## Hints

- CI runs `yarn install` and quietly changes `yarn.lock`. Which flag makes that an error instead?
- You clone a repo and there's no `node_modules`, only `.pnp.cjs`. How do packages get resolved, and why does your editor complain?
- A transitive dependency has a vulnerability and the direct dependency hasn't released a fix. How do you force a version?
- What does the `packageManager` field in `package.json` do?
- Someone ran `npm install` in a Yarn project. What did that leave behind?

## Answer

> Yarn Classic (1.x) is frozen and only maintained. Modern Yarn ("Berry", 2+, currently 4.x) is a rewrite configured through `.yarnrc.yml`. The lockfile pins every resolved version. CI must install with `--immutable` (Berry) or `--frozen-lockfile` (Classic), so a lockfile that doesn't match `package.json` fails the build. Berry's default Plug'n'Play mode replaces `node_modules` with a resolution map and is strict about undeclared dependencies. Many teams set `nodeLinker: node-modules` for compatibility. Workspaces handle monorepos, `resolutions` forces transitive versions, `packageManager` pins the Yarn version, and `yarn why` explains why a package is installed.

**Classic vs Berry**

| | Yarn 1 (Classic) | Yarn 2+ (Berry) |
|---|---|---|
| Config | `.yarnrc` | `.yarnrc.yml` |
| CI install | `yarn install --frozen-lockfile` | `yarn install --immutable` (the default when a CI environment is detected) |
| Install strategy | `node_modules` | Plug'n'Play by default; `node-modules` or `pnpm` linkers available |
| Run a package binary once | `npx` | `yarn dlx` |
| Upgrade | `yarn upgrade` | `yarn up`, `yarn up -i` |
| `pre`/`post` script hooks | run | not run for your own scripts (`prebuild` is ignored) |

Check which one the project uses (`yarn --version`, and whether `.yarnrc.yml` and a `.yarn/` folder exist) before following any blog post.

**The lockfile**

- `yarn.lock` records the exact resolved version and checksum of every package, so all machines and CI install the same tree. Always commit it.
- Review lockfile changes in PRs. A small `package.json` change producing hundreds of changed lines deserves a question.
- Don't mix package managers: `npm install` creates `package-lock.json` and a different `node_modules` layout. Delete it and reinstall with Yarn.
- Merge conflicts in `yarn.lock`: accept either side, then run `yarn install`, which rewrites it consistently. Don't edit it by hand.

**Plug'n'Play vs `node_modules`**

- PnP writes `.pnp.cjs`, a map from package names to zip files in a cache. Node is patched to resolve through it. Installs are fast, there are no huge folders, and it's **strict**: importing a package you didn't declare fails instead of working by accident through hoisting.
- The cost is compatibility. Tools that read `node_modules` directly break, and editors need SDKs (`yarn dlx @yarnpkg/sdks vscode`) so TypeScript can resolve types.
- `nodeLinker: node-modules` in `.yarnrc.yml` gives a classic layout with Berry's CLI. It's a common choice for Next.js projects with many tools. `nodeLinker: pnpm` gives a symlinked, pnpm-style layout.
- "Zero-installs": committing `.yarn/cache` so a clone runs without installing. Some teams like it; others reject the repository growth.

**Workspaces**

```json
{
  "private": true,
  "workspaces": ["apps/*", "packages/*"]
}
```

- `yarn workspace web add @mantine/core` adds to one package. `yarn workspaces foreach -A run build` runs a script in all of them (Berry).
- Internal dependencies use `"@acme/ui": "workspace:^"`, which links to the local package and is replaced with a real version when publishing.
- For task caching and "build only what changed", add Turborepo or Nx on top (#616).

**Forcing versions and security**

```json
{
  "resolutions": {
    "semver": "7.6.3",
    "some-lib/minimist": "1.2.8"
  }
}
```

`resolutions` overrides a transitive version (npm calls it `overrides`). Remove it once the direct dependency fixes the problem, and leave a comment in the PR saying why it's there.

- `yarn why <pkg>` shows which dependency pulls a package in.
- `yarn npm audit` (Berry) or `yarn audit` (Classic) lists known vulnerabilities.
- Recent Yarn versions can refuse install scripts (`enableScripts: false`) and very recently published package versions, which reduces supply-chain risk (#303, #375).

**Pinning Yarn itself.** `"packageManager": "yarn@4.x.y"` in `package.json` tells Corepack which Yarn version to run, so everyone and CI use the same one. Corepack shipped with Node.js up to version 24. On newer Node versions install it separately (`npm i -g corepack`) and run `corepack enable`. Alternatively Berry projects commit the Yarn release under `.yarn/releases` and point `yarnPath` to it.

**CI essentials**

```bash
corepack enable
yarn install --immutable
yarn lint && yarn typecheck && yarn test && yarn build
```

Cache the Yarn cache folder (`yarn config get cacheFolder`) between runs, keyed on `yarn.lock`.

**Follow-up:** "Yarn, npm or pnpm?" All three are fine. pnpm is fast and strict with a global content-addressable store. Yarn Berry has PnP, constraints and strong workspace tooling. npm needs nothing extra. In an existing project use what the lockfile says. For a new one, the team's familiarity matters more than benchmarks.
