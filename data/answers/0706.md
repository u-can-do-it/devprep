## Hints

- With 300 screens, which code must run before the first frame?
- Most pull requests change only JavaScript. Does CI need to compile the native app for each of them?
- Forty developers merge every day. How does a change reach users without waiting for everyone else's work?

## Answer

> At this size the problems are organisational as much as technical. I would work on five areas: clear module boundaries with owners, a startup path that loads only the shell and the first screen, build pipelines that reuse native builds and run only what a change affects, a release train with feature flags and staged over-the-air updates, and a platform team that owns the shared foundation and the upgrades. Each area needs a metric and a budget, so regressions are caught by a check, not by a complaint.

**1. Structure and ownership**

- A monorepo with **feature packages by domain** (`orders`, `payments`, `profile`), each with a small public API, plus shared packages: design system, API client, navigation shell, analytics.
- **Enforced boundaries:** features can't import each other's internals; dependencies point from features to shared packages (#616).
- **CODEOWNERS** per package, and crash and performance data tagged by owning team (#687).
- A **platform team** owns the app shell, navigation, networking, auth, build, CI, release tooling and the list of allowed native dependencies.
- Typed navigation and typed API contracts, so one team's change breaks another team's build, not production.

**2. Startup**

- The shell loads providers, navigation and the first screen. Every feature loads on first use (lazy routes), so 300 screens don't run their module code at launch (#695).
- No heavy barrel files and no import-time side effects in feature packages. A lint rule helps.
- SDK initialisation is deferred and owned: each SDK has an owner and a measured cost.
- **A startup budget** (for example, the 90th percentile on a reference low-end device) on a dashboard, with an alert per release and an automated cold-start test in CI.

**3. Build and CI time**

Native compilation is the slow part, and most changes don't touch it.

- **Fingerprint the native inputs.** If the hash is unchanged, reuse the last native build and only produce a new JS bundle.
- **Development builds are distributed,** so most developers never compile native code. They install the current build and run Metro.
- **Affected-only tasks** with remote caching: lint, type-check and test only the packages a pull request touches (#419).
- Prebuilt framework binaries, Gradle and compiler caches for the remaining native builds.
- End-to-end smoke tests on the critical flows per pull request, and the full suite nightly (#686).
- Target: feedback on a JS-only pull request within about ten minutes.

**4. Release cadence**

- A **release train:** a fixed schedule (weekly or every two weeks), a branch cut, a release owner, automated builds and store submission (#688). A feature that isn't ready waits for the next train.
- **Feature flags** separate merging from releasing: code ships dark and is enabled per user group, with a remote kill switch (#123).
- **Staged rollouts** in the stores, gated on the crash-free rate.
- **Over-the-air updates** for JS fixes, also staged, tied to a fingerprint-based runtime version (#699).
- **Minimum supported version** and a forced-update screen, and an API that stays compatible with the versions still in use.
- Internal dogfooding builds every day.

**5. Quality at scale**

- Performance budgets per screen (render time, list frame rate), checked in review and in production data.
- The React Compiler and lint rules for common mistakes, instead of relying on every developer's memory.
- A shared design system, so 300 screens don't mean 300 button variants.
- Contract tests between app and backend.
- An RFC step for architecture changes and for each new native dependency.

**6. Upgrades**

- The platform team upgrades React Native or Expo every release or two (#701).
- Few native dependencies, no long-lived forks, native projects generated from config.
- Enough native expertise in-house to debug a build or a crash without waiting for a library author.

**What I would not do first**

- **Module federation or "mini-apps" with separate deployment.** Tools exist (Re.Pack with Module Federation), and super-apps use them. But all native code must still live in the host, shared dependency versions must match, and debugging gets harder. Use it only when teams truly need independent releases, after package boundaries and release trains have been tried.
- **A rewrite.** Problems of ownership and process survive a rewrite.

**How to start**

Measure first: startup percentiles, CI time per pull request, lead time from merge to users, crash-free rate by team. Pick the worst number, fix it, and keep the dashboard.

**Follow-up:** two teams need different major versions of the same library with native code. How do you resolve it? (You can't ship two native versions in one binary. Agree on one version, with the platform team scheduling the migration, or isolate one usage behind an adapter so it can move later. This is why native dependencies need central ownership.)
