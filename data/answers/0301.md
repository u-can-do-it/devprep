## Hints

- What signal does Docker or Kubernetes send before killing a container, and how long do you get?
- What happens to requests in flight and to idle keep-alive connections when you call `server.close()`?
- Why might your process never receive the signal at all when started with `npm start`?

## Answer

Goal: on shutdown, **stop accepting new work, finish in-flight work, release resources, exit**, all before the orchestrator sends `SIGKILL`. Kubernetes waits `terminationGracePeriodSeconds`, 30 seconds by default.

```js
let shuttingDown = false;
const server = app.listen(3000);

app.get('/ready', (req, res) => res.status(shuttingDown ? 503 : 200).end());

async function shutdown(signal) {
  if (shuttingDown) return;
  shuttingDown = true;
  console.info({ signal }, 'shutting down');

  const force = setTimeout(() => process.exit(1), 25_000);
  force.unref();

  server.close(async () => {          // waits for in-flight requests
    await db.end();                   // close pools, flush logs/queues
    await tracer.shutdown?.();
    process.exit(0);
  });
  server.closeIdleConnections();      // drop idle keep-alive sockets
}

process.on('SIGTERM', shutdown);
process.on('SIGINT', shutdown);
```

Details that matter:

- **Fail readiness first** so the load balancer stops routing new traffic. Endpoint removal is asynchronous, so a short delay (or a `preStop` sleep) avoids errors from late requests.
- `server.close()` stops new connections but **waits for keep-alive sockets**. Close idle ones, and use `closeAllConnections()` after a deadline.
- Stop **background consumers** too (queue workers, cron jobs) and let the current message finish or return it to the queue.
- **PID 1 and signals**: `npm start` or a shell-form `CMD` may not forward `SIGTERM`. Use `CMD ["node", "server.js"]` and `docker run --init` (or tini) so signals arrive and zombies are reaped.
- Keep a **hard timeout** shorter than the grace period so you exit cleanly instead of being killed.
