## Hints

- Does the test double just return canned data, or does it also check how it was called?
- Which kind of double contains a simplified but working implementation?
- What's the risk of verifying too many internal calls in a test?

## Answer

> Mocks, stubs and fakes are all *test doubles*: stand-ins for real dependencies in tests. A stub just returns canned answers so your code can run, and you assert on your code's output. A mock lets you check interactions, like whether `send` was called once with the right address. A fake is a simple working implementation, like an in-memory repository. Prefer fakes and checks on state, and mock only at system boundaries like network, email and time, or refactors will break your tests.

All three are **test doubles** — replacements for real dependencies.

- **Stub:** returns predefined answers so the code under test can run. You assert on the *output* of your code, not on the stub. Example: a payment gateway stub that always returns `{ status: 'ok' }`.
- **Mock:** pre-programmed with expectations, and the test verifies *interactions* — was it called, how many times, with what arguments. Example: assert that `emailService.send` was called once with the user's address.
- **Fake:** a lightweight working implementation not suitable for production — an in-memory repository, SQLite instead of Postgres, a fake clock.
- (Also: **spies** record calls on a real or stub function; **dummies** are placeholders never used.)

```ts
import { vi, test, expect } from 'vitest';

test('sends welcome email on signup', async () => {
  const users = new InMemoryUserRepo();                // fake
  const email = { send: vi.fn() };                      // mock
  const captcha = { verify: async () => true };         // stub

  await signup({ users, email, captcha }, 'ann@x.io');

  expect(await users.findByEmail('ann@x.io')).toBeTruthy();
  expect(email.send).toHaveBeenCalledWith('ann@x.io', expect.any(String));
});
```

**Guidelines:** prefer state-based assertions and fakes where possible; mock at system boundaries (network, email, payments, time). Over-mocking ties tests to implementation details, so refactors break tests even when behavior is correct.
