## Hints

- If replica A revalidates a page, how does replica B find out?
- A user's tab was loaded from build N; the next request hits a pod running build N+1. What breaks?
- What can nginx or a load balancer silently do to a streamed response?

## Answer

A single `next start` "just works". With **multiple replicas** behind a load balancer, several defaults assume one instance.

**Build and image**

- `output: 'standalone'` gives a minimal server plus only the needed `node_modules`. Copy `public/` and `.next/static` into the image yourself. Use a multi-stage Dockerfile and run as a non-root user.
- **Build once, promote the same image** through environments. Server-side env vars are read at runtime, but `NEXT_PUBLIC_*` values are inlined at build time.
- Serve `/_next/static/*` (hashed, immutable) from a CDN or with long cache headers, using `assetPrefix` if needed.

**Shared state between pods**

- **Cache:** by default each pod has its own in-memory and on-disk cache, so pods serve different versions and ISR is duplicated. Configure a shared **`cacheHandler`** (ISR and the data cache, e.g. Redis) and set `cacheMaxMemorySize: 0`. Use **`cacheHandlers`** / `'use cache: remote'` for `'use cache'` entries.
- **Tag invalidation:** `revalidateTag` on one pod only affects that pod unless the handler coordinates it (implement `refreshTags()` to sync tag state from Redis).
- **Server Actions encryption key:** each build generates a random key. All pods must share **`NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`**, or you get "Failed to find Server Action" errors.
- **Build ID:** if you build per environment, use a consistent `generateBuildId`.

**Rolling deploys**

- Set **`deploymentId`**. Clients send it, and on a mismatch Next.js does a hard reload instead of loading missing chunks or calling stale action IDs (version skew).
- Keep old static assets available for a while, or use sticky routing during rollout.
- **Graceful shutdown:** handle `SIGTERM` with a drain period so in-flight requests and `after()` callbacks finish.

**Networking**

- Put a reverse proxy in front (slowloris protection, body limits, rate limiting).
- **Disable buffering** (`X-Accel-Buffering: no` for nginx; check your ingress and LB), or streaming and PPR quietly stop working.
- Configure `serverActions.allowedOrigins` if the `Host` / `X-Forwarded-Host` seen by Next.js differs from the public origin.

**Operations**

- Image optimization uses `sharp` and is CPU and memory heavy. Size pods for it, or offload to an image CDN with a custom `loader`.
- Add a health endpoint, plus OpenTelemetry via `instrumentation.ts` and `onRequestError`.

**Follow-up:** compare this with Vercel or a verified adapter, where the cache, skew protection and streaming are handled for you. That's the operational cost you take on in exchange for control.
