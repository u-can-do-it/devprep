## Hints

- Who actually delivers a notification to the phone: your server, or Apple and Google?
- When the app is killed, can your JavaScript decide how to show an incoming notification?
- The user taps a notification while the app is not running. How does the app learn which one?

## Answer

> Your server never talks to a phone directly. The app registers with the platform's push service (APNs on iOS, FCM on Android) and gets a device token. You send that token to your backend, and the backend asks the push service to deliver a message. If the app is in the background or killed, the OS shows the notification without running your JavaScript. When the user taps it, the app reads the payload and navigates. Delivery is best effort, so the app must still fetch the truth from the API.

**The flow**

1. The app asks the user for notification permission.
2. The OS registers with APNs or FCM and returns a **device token**.
3. The app sends the token to your backend, linked to the user and the device.
4. The backend sends a message through FCM or APNs (or a service that wraps both: Expo Push, OneSignal, Firebase).
5. The OS shows the notification. A tap opens the app with the payload.

**Tokens**

- A token identifies an app install on a device. It can change, so send it to the backend on every launch and on the token-refresh event.
- One user has many devices, and one device can change users. Remove the token on logout.
- When the push service says a token is no longer registered, delete it.

**Permissions**

- iOS always needs an explicit permission. Android needs one from Android 13.
- The system dialog appears once. Ask in context ("Notify me when my order ships"), after your own explanation screen (#685).
- A denied permission is a normal state. The feature must degrade gracefully.

**App state when the message arrives**

| App state | Notification message | Data-only (silent) message |
|---|---|---|
| Foreground | delivered to your JS; you decide whether to show a banner | delivered to JS |
| Background | the OS shows it; no JS needed | may wake the app briefly; throttled |
| Killed | the OS shows it | unreliable: iOS may not deliver, Android skips force-stopped apps |

```ts
// Foreground behaviour (expo-notifications)
Notifications.setNotificationHandler({
  handleNotification: async () => ({
    shouldShowBanner: true, shouldShowList: true, shouldPlaySound: false, shouldSetBadge: false,
  }),
});
```

Silent pushes are a hint to sync, never a guarantee (#704).

**Android channels**

From Android 8 every notification belongs to a channel ("Orders", "Promotions"). The channel sets importance and sound, and the user can mute each one. Create the channels at startup. You can't change a channel's importance after it is created.

**Opening the right screen**

```ts
// Put a URL in the payload: { "data": { "url": "/orders/42" } }
function useNotificationLinks() {
  const router = useRouter();
  const last = Notifications.useLastNotificationResponse();   // also covers a cold start
  useEffect(() => {
    const url = last?.notification.request.content.data?.url;
    if (typeof url === 'string') router.push(url);
  }, [last, router]);
}
```

- Handle both cases: the app was running, and the app was started by the tap.
- Treat the payload as untrusted input, and route it through the same code as deep links, including the "user is logged out" case (#684).

**Backend side**

- Send in batches, handle errors per token, and retry with backoff.
- Collapse or deduplicate messages so that a retry doesn't notify twice.
- Don't put sensitive data in the payload. Send an id and let the app fetch the details.
- Respect user preferences and quiet hours on the server.

**Practical notes**

- iOS needs a push key or certificate from the Apple developer account. Android needs a Firebase project.
- Test on real devices with a development build. Simulators are limited.
- Images, action buttons and badge counts work, but need extra setup per platform.

**Follow-up:** a user logs out, another logs in on the same phone, and sees the first user's notifications. What went wrong? (The backend still maps the device token to the first user. Unregister the token on logout and re-register it for the new user.)
