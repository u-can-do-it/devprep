## Hints

- If `Dog` extends `Animal`, should `Dog[]` be assignable to `Animal[]`? What could go wrong if you then push a `Cat`?
- If a function expects a handler for `Animal`, can you pass one that only handles `Dog`, or the other way around?
- Why might TypeScript deliberately allow some unsound assignments?

## Answer

**Variance** describes how subtyping of a generic type follows subtyping of its type argument (here `Dog extends Animal`):

- **Covariant:** `Box<Dog>` is assignable to `Box<Animal>`. Safe for **output** positions (return values, readonly properties).
- **Contravariant:** `Handler<Animal>` is assignable to `Handler<Dog>`. Safe for **input** positions (parameters). A function that handles any animal can handle a dog.
- **Invariant:** neither direction. Required for types that are both read and written.
- **Bivariant:** both directions are allowed. Unsound, but convenient.

```ts
type Handler<T> = (x: T) => void;
const handleAnimal: Handler<Animal> = (a) => {};
const handleDog: Handler<Dog> = (d) => d.bark();

const h1: Handler<Dog> = handleAnimal;   // ok (contravariance)
const h2: Handler<Animal> = handleDog;   // error with strictFunctionTypes
```

**`strictFunctionTypes`** (part of `strict`) checks parameters of **function-type properties** contravariantly. **Method-syntax** members (`onEvent(x: T): void`) are still checked **bivariantly**. That exception exists so that types like `Array<T>`, whose methods take `T`, stay covariant and usable.

```ts
interface A { handle(x: Animal): void }       // method: bivariant (unsound)
interface B { handle: (x: Animal) => void }   // property: contravariant (sound)
```

**Known unsoundness:** arrays are covariant even though they are mutable.

```ts
const dogs: Dog[] = [];
const animals: Animal[] = dogs;  // allowed
animals.push(new Cat());         // compiles, and now dogs contains a Cat
```

**Explicit variance annotations** (TS 4.7) say how a type parameter is used:

```ts
interface Producer<out T> { get(): T }
interface Consumer<in T> { accept(v: T): void }
interface Store<in out T> { get(): T; set(v: T): void }
```

The compiler checks that the annotation matches how `T` is actually used. It can also skip expensive structural comparisons, which helps performance with deeply nested generic types. Use the annotations sparingly, mainly in libraries.

**Practical takeaways:**

- Prefer **property syntax** for callbacks in interfaces.
- Accept `readonly T[]` when you only read from an array.
- Understand that `Promise<T>` and `ReadonlyArray<T>` are covariant, while a mutable container is effectively invariant.
