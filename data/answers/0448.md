## Hints

- If both the shell and a micro-frontend run their own router, which one owns the URL?
- Why is a single global Redux store shared by every micro-frontend a trap?
- One team adds a global `button { … }` rule. How do you stop it from restyling every other team's buttons?

## Answer

The goal is to keep the parts **loosely coupled**: share as little as possible, and make whatever is shared an explicit, versioned contract.

**Routing**

- The **shell owns the top-level routes** and gives each part a path prefix: `/checkout/*` goes to checkout.
- Each part uses a **nested router** with that `basename` and only handles its own sub-routes.
- There's **one history**: everything goes through the browser History API (or a `navigate` function the shell passes in), so two routers never fight over the URL.
- Cross-part navigation uses plain links or a shell API, never imports from another part's router.
- Deep links must survive a refresh: the server returns the shell for every route.

**Shared state and communication**

- Each part **owns its state**. The **URL** and the **backend** are the main shared sources of truth.
- The shell provides a small, typed set of **cross-cutting context**: current user and a token getter, locale, theme, feature flags.
- Parts talk through **events**, not by importing each other: `CustomEvent`s on `window`, a tiny typed event bus, or `BroadcastChannel` across tabs.
- Avoid a shared global store. It couples every team's deploys to one state shape. If a state library is shared at all, it must be a singleton dependency.

```ts
// @acme/mfe-contracts: a versioned package that every part depends on
export type Events = {
  'cart:item-added': { sku: string; qty: number };
  'auth:logout': void;
};

export function emit<K extends keyof Events>(type: K, detail: Events[K]) {
  window.dispatchEvent(new CustomEvent(type, { detail }));
}

export function on<K extends keyof Events>(type: K, fn: (detail: Events[K]) => void) {
  const handler = (e: Event) => fn((e as CustomEvent<Events[K]>).detail);
  window.addEventListener(type, handler);
  return () => window.removeEventListener(type, handler);
}
```

**Styling isolation**

CSS is global by default, so any part can break the others.

- **Scope class names:** CSS Modules, or CSS-in-JS with a per-part prefix.
- **Namespaced conventions:** a per-part prefix (`.checkout-…`), or Tailwind's `prefix` option.
- **Only the shell** ships the reset, base styles and fonts. Parts must not style bare elements (`button`, `body`).
- **Cascade layers** (`@layer reset, design-system, app`) and **`@scope`** make precedence predictable.
- **Shadow DOM** (Web Components) gives hard isolation, but it also blocks theming unless you pass CSS custom properties through.

**Design-system consistency**

- A **shared design system** owned by a platform team: tokens plus components, versioned like any public API.
- **Design tokens as CSS custom properties** defined by the shell on `:root`. A theme or brand change then reaches every part without redeploying them.
- Share the component library as a **singleton** so everyone uses the same version, or accept per-part versions with upgrade deadlines.
- Catch drift with Storybook, **visual regression tests** (Chromatic, Playwright screenshots) and lint rules (no hardcoded colors, use DS components).

**Other cross-cutting concerns:** the shell handles auth and login (httpOnly cookies or a token getter, so tokens aren't copied around), a shared analytics and logging API, and an **error boundary around each part** so one crash doesn't blank the page.
