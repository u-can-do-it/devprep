## Hints

- Where did the Tailwind config move in v4?
- What happens with `className="px-4 px-2"`, and which one wins?
- How would you express a button's `variant` and `size` props as Tailwind classes without a pile of ternaries?

## Answer

**Tailwind CSS** is utility-first: small single-purpose classes (`flex`, `px-4`, `text-sm`, `hover:bg-blue-600`) composed in markup. The build scans your source files and generates **only the classes you use**, so the CSS stays small.

**What changed in v4 (2025):**

- **CSS-first configuration:** no `tailwind.config.js` by default. You import Tailwind and define the theme as CSS variables:

```css
@import "tailwindcss";

@theme {
  --color-brand-600: oklch(0.55 0.2 260);
  --font-display: "Inter", sans-serif;
  --breakpoint-3xl: 120rem;
}
/* generates bg-brand-600, font-display, 3xl:… and exposes them as CSS variables */
```

- A new, much faster engine (Oxide), **automatic content detection** (`@source` to add paths), and built-in import handling and vendor prefixing.
- Modern CSS underneath: cascade layers, `oklch` colours, container queries (`@container`, `@md:`), `@starting-style`, 3D transforms.
- Custom utilities and variants in CSS: `@utility`, `@custom-variant dark (&:where([data-theme=dark] *))`.

**Managing component variants:** a design-system component needs variant props mapped to classes. **`cva`** (class-variance-authority) does that declaratively:

```ts
import { cva, type VariantProps } from 'class-variance-authority';

export const button = cva('inline-flex items-center rounded-md font-medium focus-visible:outline-2', {
  variants: {
    variant: { primary: 'bg-brand-600 text-white hover:bg-brand-700', ghost: 'hover:bg-gray-100' },
    size: { sm: 'h-8 px-3 text-sm', md: 'h-10 px-4' },
  },
  defaultVariants: { variant: 'primary', size: 'md' },
});
export type ButtonVariants = VariantProps<typeof button>;
```

**Class conflicts:** CSS doesn't care about the order of classes in the attribute. It uses the order in the stylesheet, so `px-4 px-2` is unpredictable from the reader's point of view. **`tailwind-merge`** resolves conflicts so the last class wins. shadcn/ui's `cn()` helper combines it with `clsx` for conditionals:

```ts
export const cn = (...inputs: ClassValue[]) => twMerge(clsx(inputs));
<button className={cn(button({ variant, size }), className)} />   // consumer's px-2 overrides px-4
```

**Rules of thumb:** never build class names dynamically (`bg-${color}-500`), because the scanner can't see them; extract a **component**, not an `@apply` class, when markup repeats; and put design tokens in `@theme` so utilities and plain CSS share the same values.
