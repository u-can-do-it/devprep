## Hints

- The client-side row model holds every row in memory. Roughly where does that stop being reasonable, and what breaks first: the browser or the network?
- What does the server-side row model's `getRows` receive, and what must it call when the request succeeds or fails?
- The user ticks "select all" on 300,000 server-side rows and clicks "Archive". What should you send to the API?
- After editing one row, how do you refresh the server-side data without losing scroll position?
- "Export to Excel" with the server-side row model exports only the loaded blocks. How do you export everything the user filtered?

## Answer

> Pick the row model by data size and licence. The client-side model loads everything and is fine up to tens of thousands of rows. The infinite model (Community) loads blocks as the user scrolls, with sort and filter done on the server. The server-side model (Enterprise) adds lazy-loaded grouping, aggregation and transactions on top of that. The viewport model lets the server push updates for the visible rows. With server data, map the grid's `sortModel` and `filterModel` to a whitelisted API query, refresh with `refreshServerSide` after edits, send the selection as "all matching this filter except these ids", and generate full exports on the server from the same filter.

**Choosing a row model**

| Row model | Licence | Data lives | Good for |
|---|---|---|---|
| Client-side | Community | all rows in the browser | up to ~50–100k narrow rows that load quickly; instant sort and filter |
| Infinite | Community | blocks fetched while scrolling | large flat lists, server-side sort and filter |
| Server-side (SSRM) | Enterprise | blocks, lazy groups | huge data, grouping and aggregation on the server, pagination |
| Viewport | Enterprise | only the visible range | live data the server pushes (trading screens) |

The limit of the client-side model is usually **payload and memory**, not rendering: 200k rows × 30 columns of JSON is tens of megabytes to download, parse and keep. Permissions also matter: if the backend filters data per user (#622), sending "everything" isn't an option anyway.

**Server-side row model**

```tsx
const datasource = useMemo<IServerSideDatasource>(() => ({
  getRows: async (params) => {
    const { startRow, endRow, sortModel, filterModel } = params.request;
    try {
      const page = await queryClient.fetchQuery(
        orderQueries.page({ offset: startRow!, limit: endRow! - startRow!, sort: sortModel, filter: filterModel }),
      );                                                        // cache and deduplication from TanStack Query
      params.success({ rowData: page.items, rowCount: page.total });
    } catch {
      params.fail();                                           // grid shows the block as failed and can retry
    }
  },
}), []);

<AgGridReact
  rowModelType="serverSide"
  serverSideDatasource={datasource}
  cacheBlockSize={100}            // rows per request
  maxBlocksInCache={20}           // memory cap; older blocks are dropped
  getRowId={(p) => p.data.id}
  columnDefs={columnDefs}
/>
```

The infinite row model (Community) works the same way through `datasource.getRows` with `startRow`, `endRow`, `sortModel`, `filterModel` and `successCallback(rows, lastRow)`.

**Mapping the grid's models to the API.** `sortModel` is `[{ colId: 'amount', sort: 'desc' }]`. `filterModel` is a per-column object such as `{ status: { filterType: 'text', type: 'equals', filter: 'open' }, amount: { filterType: 'number', type: 'greaterThan', filter: 1000 } }`.

- Translate it in one place (an adapter) into the API's query format. Don't send the grid's raw JSON to the backend as a contract.
- **Whitelist** sortable and filterable columns and operators on the backend. Never build SQL from `colId`.
- Hide filter options the backend doesn't support (`filterParams: { filterOptions: ['contains', 'equals'] }`), and debounce text filters (`filterParams: { debounceMs: 400 }`).
- Make sure every sortable column is indexed, or pagination over 300k rows gets slow. Use stable ordering (add `id` as a tiebreaker) so rows don't jump between pages.
- Keep sort and filter in the URL too, if views should be shareable (#503).

**Refreshing after changes**

- An edited row: update it locally with `api.applyServerSideTransaction({ update: [row] })`, or refetch just that row and apply it.
- Data changed in ways you can't patch (a new row that sorts somewhere in the middle): `api.refreshServerSide({ purge: false })` reloads the loaded blocks in the background, keeping scroll and selection. `purge: true` clears them and shows loading rows.
- Invalidate the matching TanStack Query keys as well, or the datasource will serve the old cached page.

**Selection across server rows.** Only loaded rows exist in the browser, so "select all" can't be a list of ids. SSRM gives you a selection state like `{ selectAll: true, toggledNodes: ['17', '42'] }`. Send that **with the current filter model** to a bulk endpoint ("archive everything matching this filter except 17 and 42"). Before acting, show the count: "Archive 299,998 orders?". The backend re-applies the filter with the user's permissions. Run large bulk actions as async jobs (#651).

**Exporting the full dataset.** `exportDataAsExcel`/`exportDataAsCsv` export what the grid has loaded. For "everything I filtered", call a server endpoint with the same sort, filter and visible-column list, and stream the file or run it as a job with a download link (#651). Audit who exported what; in finance that's usually required (#650).

**Performance checklist**

- Stable `columnDefs`, callbacks and datasource (`useMemo`), and `getRowId` everywhere (#645).
- Prefer `valueFormatter` over React `cellRenderer`s. Keep renderers cheap and memoized.
- Don't turn off virtualization (`suppressRowVirtualisation`, `domLayout="autoHeight"` with many rows).
- Lots of live updates: `applyTransactionAsync` batches them. Don't push them through React state (#224).
- Measure with the browser's Performance panel before tuning `rowBuffer` or block sizes.

**Follow-up:** "Infinite scroll or pagination?" Pagination is easier to explain ("page 3 of 120"), easier to link to and easier to test. Infinite scroll suits browsing. For compliance work, where users process records and come back to a place, pagination plus a URL usually wins. Both are available on the same server-side datasource.
