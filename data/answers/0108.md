## Hints

- Where does the malicious script live in each attack type – in the database, in the URL, or only in the browser?
- What is the difference between inserting text and inserting HTML?
- If an XSS slips through anyway, what can limit the damage?

## Answer

**Cross-Site Scripting (XSS)** is when an attacker gets their JavaScript to run in your site's origin, letting them read data, act as the user, or steal tokens.

**Types:**

- **Stored** – payload is saved (comment, profile name) and served to every viewer.
- **Reflected** – payload comes from the request (e.g. `?q=<script>...`) and is echoed back in the response.
- **DOM-based** – client-side JS takes untrusted input (`location.hash`, `postMessage`) and writes it into a dangerous sink (`innerHTML`, `eval`) without the server being involved.

**Prevention:**

- **Context-aware output encoding** – escape for HTML, attributes, URLs, JS. Frameworks like React escape text by default.
- **Avoid dangerous sinks**: `innerHTML`, `dangerouslySetInnerHTML`, `eval`, `new Function`, `javascript:` URLs.
- If you must render HTML, **sanitize** with a vetted library (DOMPurify).

```jsx
// Safe: React escapes this
<p>{comment.text}</p>

// Dangerous unless sanitized
<div dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(comment.html) }} />

// Still a risk in React: user-controlled URLs
<a href={user.website}>site</a>  // validate scheme is http/https
```

**Defense in depth:**

- **Content Security Policy** with nonces to block inline/injected scripts.
- **`HttpOnly` cookies** so scripts can't read session cookies.
- **Trusted Types** to lock down DOM sinks.
- Validate input, but don't rely on input filtering alone – encode on output.

**Follow-up:** Why doesn't `HttpOnly` fully solve XSS? (The attacker's script can still make authenticated requests as the user from the page.)
