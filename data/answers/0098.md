## Hints

- How does the GraphQL engine produce a value for each field in a query?
- If a query returns 50 posts and each post has an `author` field, how many DB queries run naively?
- What if you could collect all author IDs requested in one tick and fetch them together?

## Answer

A **resolver** is a function that returns the value for one field. Its signature is `(parent, args, context, info)`. The engine walks the query tree and calls resolvers per field, per object.

**The N+1 problem:**

```ts
const resolvers = {
  Query: { posts: () => db.post.findMany({ take: 50 }) },     // 1 query
  Post:  { author: (post) => db.user.findUnique({ where: { id: post.authorId } }) }, // 50 queries
};
```

One query for the list plus N queries for each child = N+1 round trips. Nested lists make it multiply.

**DataLoader** fixes this with **batching** and **per-request caching**:

```ts
import DataLoader from "dataloader";

const createLoaders = () => ({
  userById: new DataLoader(async (ids: readonly string[]) => {
    const users = await db.user.findMany({ where: { id: { in: [...ids] } } });
    const map = new Map(users.map((u) => [u.id, u]));
    return ids.map((id) => map.get(id) ?? null); // same order as keys!
  }),
});

// context: { loaders: createLoaders() } – created per request
const Post = { author: (post, _, ctx) => ctx.loaders.userById.load(post.authorId) };
```

All `load()` calls made in the same tick of the event loop are collected and sent as one `WHERE id IN (...)` query. Duplicate IDs are deduped by the cache.

**Key rules:**

- Create loaders **per request** – a global cache leaks data between users and goes stale.
- The batch function must return results in the **same order and length** as the keys.
- Alternatives: look-ahead with `info` to build joins, or tools that compile GraphQL to SQL.

**Follow-up:** How would you detect N+1 in production? (Tracing per resolver, counting DB queries per request.)
