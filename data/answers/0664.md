## Hints

- Which kinds of data are a "never", and which depend on the tool and the contract?
- What do you need to know about a tool before client code goes into it?
- Who is accountable for code an AI tool wrote, and can you always claim copyright on it?

## Answer

> Start from the company's and the client's policy, not from what is technically possible. Secrets never go into a prompt. Personal data needs a legal basis and an approved tool, and usually should be anonymised or replaced with synthetic data. Source code may go only into tools the company or client has approved, on terms that cover training, retention and location. For generated code, you are accountable for it, licences of reproduced snippets still apply, and ownership of purely AI-generated work is legally unsettled.

**What may go in**

| Data | Rule |
|---|---|
| Secrets: API keys, tokens, passwords, private keys | never, in any tool. If one leaks, rotate it |
| Personal data (customers, patients, employees) | only in an approved tool with a data processing agreement and a legal basis; prefer anonymised or synthetic data (#556) |
| Client code under NDA | only tools the client or contract allows; some clients forbid AI tools entirely |
| Your company's proprietary code | approved tools on business terms |
| Public code and documentation | fine |
| Logs and production dumps | often contain personal data and tokens; redact first |

When there is no policy, ask before you paste. "Everyone does it" isn't an answer you want to give after an incident.

**What to check about a tool** (usually security and legal decide; you should know the questions)

- **Training:** are prompts and code used to train models? Consumer plans and business or API plans often differ, and some need an opt-out.
- **Retention:** how long are inputs and outputs stored, and is there a zero-retention option?
- **Location and subprocessors:** where is data processed, and who else gets it? This matters for GDPR and for clients with residency requirements.
- **Access and audit:** SSO, admin controls, logs, who at the vendor can read content.
- **Contract:** a data processing agreement, and whether the terms match what you promised your own clients.
- **Extensions:** every MCP server, plugin or browser extension is another party that receives data (#525).

**Shadow AI** is the common violation: a personal account or an unapproved tool used on company code because it's convenient. The risk is not only the vendor; it's that nobody knows where the data went.

**Practical safeguards**

- Keep secrets where the agent can't read them: deny rules for `.env` and key files, a secret manager instead of files, secret scanning in CI. A `.gitignore` entry doesn't stop an agent from reading a file (#654).
- Redact before sharing: IDs, emails and tokens out of logs and stack traces.
- Develop against synthetic or seeded data, not a production copy.
- Give agents read-only, non-production access to databases and internal systems.
- For highly sensitive work, a self-hosted or on-premise model may be the only acceptable option.

**The code that comes out**

- **Accountability:** the author who commits it and the reviewer who approves it, the same as for any code.
- **Licences:** a model can reproduce existing open-source code. A long, distinctive snippet under GPL in a proprietary product is a problem however it got there. Use the duplicate-detection filters where the tool has them, and treat large, unusually specific output with suspicion (#526).
- **Ownership:** in several jurisdictions, work generated without meaningful human authorship may not be protected by copyright. The law is still developing. Code you direct, edit and integrate is a stronger case than raw output.
- **Indemnity:** some vendors promise to cover IP claims on their business plans, with conditions.
- **Contracts:** a client may require you to disclose AI use, forbid it, or require that deliverables are fully assignable. Check before using AI on a client project.
- **Regulation:** if the product itself uses AI on users' data, rules such as the EU AI Act and GDPR apply to the feature, not just to your tooling.

**In an interview,** show judgement, not legal expertise: "I check the policy and the client contract first. Secrets and personal data stay out. If I'm not sure a tool is approved for this code, I ask before using it, and I'd rather describe the problem in general terms than paste the file."

**Follow-up:** you realise you pasted a stack trace containing a customer's email and an access token into a chat tool. What do you do? (Rotate the token at once, report it through the incident or data-protection process, delete the conversation if the tool allows it, and fix the cause: redaction and a policy people can follow.)
