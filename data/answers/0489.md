## Hints

- Which problems should a human reviewer look for, and which should a tool catch automatically?
- How do you phrase a comment so it's clear whether it blocks the merge?
- What do you do when you disagree with a review comment on your own code?

## Answer

Code review is about **shared ownership and quality**: catching bugs, spreading knowledge, and keeping the codebase consistent. It's not about proving who's smarter.

**As a reviewer:**

- **Automate the trivial:** formatting, lint, types and tests run in CI. Humans shouldn't argue about semicolons.
- **Focus, in order:** correctness and edge cases, security (auth checks, injection, data exposure), design and fit with the architecture, tests that actually test behaviour, readability and naming, performance where it matters. Also check the UI states and accessibility for frontend changes.
- **Understand the context first:** read the ticket and the PR description, run it locally or check the preview environment for UI changes.
- **Be specific and kind:** comment on the code, not the person; explain *why*; suggest an alternative; ask questions when unsure ("What happens if `items` is empty?").
- **Label severity** so the author knows what blocks the merge, e.g. Conventional Comments: `issue (blocking):`, `suggestion:`, `nit:`, `question:`, `praise:`.
- **Be timely:** a review within a few hours keeps the team moving; a PR that waits two days gets merged with less care.
- Approve with minor comments when they're not blocking. Move long debates to a call, then write the outcome in the PR.
- Point out good solutions too.

**As an author:**

- **Small, focused PRs** (a few hundred lines) get better reviews than 2,000-line ones. Split refactoring from behaviour changes.
- **Self-review the diff first**, write a description (what, why, how to test, screenshots for UI), and flag the risky parts.
- Don't take comments personally. If you disagree, explain your reasoning with facts; if it's a matter of taste, follow the team convention or the reviewer's preference and move on.
- Resolve every comment: change it, or reply why not.

**Team practices:** a checklist or definition of done, code owners for critical areas, pairing for complex changes, and the same review standard for AI-generated code: the author must understand and stand behind every line.

**Follow-up:** a senior colleague's PR has a design you think is wrong, and it's already been approved by someone else. What do you do?
