## Hints

- What is the difference between `[Fact]` and `[Theory]`, and how does xUnit create test class instances?
- Which dependencies would you mock, and which would you rather run for real?
- How can a test call your API through the full middleware pipeline without deploying it?

## Answer

**Frameworks**

| | xUnit | NUnit | MSTest |
|---|---|---|---|
| Test | `[Fact]` | `[Test]` | `[TestMethod]` |
| Parameterised | `[Theory]` + `[InlineData]`/`[MemberData]` | `[TestCase]` | `[DataRow]` |
| Setup | constructor (new instance per test), `IAsyncLifetime` | `[SetUp]` | `[TestInitialize]` |
| Shared setup | `IClassFixture<T>`, collection fixtures | `[OneTimeSetUp]` | `[ClassInitialize]` |

xUnit is the most common choice for new projects. Assertions: built-in `Assert`, or a fluent library (Shouldly, or AwesomeAssertions/FluentAssertions; check the licence of newer FluentAssertions versions).

**Unit tests with mocks**

```csharp
public class CheckoutTests
{
    [Fact]
    public async Task Charges_the_total_and_sends_a_receipt()
    {
        var payments = Substitute.For<IPaymentGateway>();               // NSubstitute
        payments.ChargeAsync(Arg.Any<decimal>(), Arg.Any<CancellationToken>()).Returns(ChargeResult.Ok);
        var email = Substitute.For<IEmailSender>();
        var sut = new CheckoutService(payments, email, TimeProvider.System);

        await sut.CheckoutAsync(new Cart(lines: [new("SKU1", 2, 10m)]), CancellationToken.None);

        await payments.Received(1).ChargeAsync(20m, Arg.Any<CancellationToken>());
        await email.Received(1).SendReceiptAsync(Arg.Any<Receipt>());
    }
}
```

Moq does the same with `new Mock<T>()`, `.Setup(...)` and `.Verify(...)`. Mock at the boundaries you own (interfaces for payments, email, clock); don't mock `DbContext` or `HttpClient` internals. Inject `TimeProvider` instead of calling `DateTime.UtcNow` so time is testable (`FakeTimeProvider`).

**Integration tests with `WebApplicationFactory`**

`Microsoft.AspNetCore.Mvc.Testing` boots your real `Program` in memory with a `TestServer`, so requests go through routing, middleware, auth, validation and serialisation, without a network port.

```csharp
public class OrdersApiTests(ApiFactory factory) : IClassFixture<ApiFactory>
{
    [Fact]
    public async Task Get_unknown_order_returns_404()
    {
        var client = factory.CreateClient();
        var res = await client.GetAsync("/orders/999");
        Assert.Equal(HttpStatusCode.NotFound, res.StatusCode);
    }
}

public class ApiFactory : WebApplicationFactory<Program>
{
    protected override void ConfigureWebHost(IWebHostBuilder builder) =>
        builder.ConfigureTestServices(s =>
            s.AddSingleton<IEmailSender, FakeEmailSender>());   // replace external services only
}
```

With top-level statements, add `public partial class Program;` so the test project can reference it.

**Real databases with Testcontainers**

The EF Core in-memory provider isn't a relational database: no SQL translation errors, no constraints, no transactions. Run the real engine in Docker instead:

```csharp
public class ApiFactory : WebApplicationFactory<Program>, IAsyncLifetime
{
    private readonly PostgreSqlContainer _db = new PostgreSqlBuilder().WithImage("postgres:17").Build();

    public Task InitializeAsync() => _db.StartAsync();   // xUnit v2 signatures; v3 uses ValueTask
    Task IAsyncLifetime.DisposeAsync() => _db.DisposeAsync().AsTask();   // explicit: the factory has its own DisposeAsync

    protected override void ConfigureWebHost(IWebHostBuilder builder) =>
        builder.ConfigureTestServices(services =>
        {
            services.RemoveAll<DbContextOptions<AppDbContext>>();
            services.AddDbContext<AppDbContext>(o => o.UseNpgsql(_db.GetConnectionString()));
        });   // then apply migrations once, e.g. in InitializeAsync after the container starts
}
```

Share one container per test class or collection, and reset data between tests (transactions rolled back, or Respawn to clean tables).

**Follow-up:** your integration tests pass alone but fail when run together. Why? (Shared state: tests running in parallel against the same database rows, or data left by a previous test. Isolate data per test, reset between tests, or put those classes in one xUnit collection so they run sequentially.)
