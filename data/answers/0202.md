## Hints

- How many `useState` calls and setters does a component need before the logic gets scattered?
- Where does the "what happens on each event" logic live with a reducer?
- How easy is it to unit-test a reducer compared to a component?

## Answer

> When several pieces of state change together, or many handlers update the same state, the logic gets scattered. `useReducer` moves it into one pure function, `(state, action) => newState`. Components only dispatch actions that describe what happened, and the reducer decides how state changes. That keeps related values consistent and makes transitions easy to test without rendering. Use `useState` for simple, independent values like a toggle. The reducer must stay pure: no fetching and no mutation.

`useReducer(reducer, initialState)` moves update logic into a pure function, `(state, action) => newState`. Components describe **what happened** by dispatching actions. The reducer decides **how state changes**.

Prefer `useReducer` when:

- **Several values change together** (`status`, `data`, `error` for a request) and must stay consistent.
- **The next state depends on the previous one** in many different ways.
- **Many event handlers** update the same state. Centralizing the logic removes duplication.
- You want to **test** transitions without rendering. A reducer is just a function.
- You pass updates deep down the tree. `dispatch` is stable, so it works well in Context and doesn't trigger re-renders.

```ts
type State = { status: 'idle' | 'loading' | 'error' | 'done'; items: Item[]; error?: string };
type Action =
  | { type: 'fetch' }
  | { type: 'success'; items: Item[] }
  | { type: 'failure'; error: string };

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case 'fetch':   return { ...state, status: 'loading', error: undefined };
    case 'success': return { status: 'done', items: action.items };
    case 'failure': return { ...state, status: 'error', error: action.error };
  }
}
```

A discriminated union for `Action` makes the `switch` exhaustive and type-safe.

Stick with `useState` for independent, simple values like a toggle or an input string.

**Rules:** the reducer must be pure. No fetching, no mutation, no `Date.now()`. StrictMode calls it twice to catch violations. Side effects belong in handlers or effects.

**Follow-up:** `useReducer` plus Context gives you a small Redux-like store. Move to Zustand or Redux Toolkit when you need selectors, devtools, or middleware.
