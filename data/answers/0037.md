## Hints

- If two sibling components need the same data, where is the closest place it could live?
- What re-renders when a Context value changes?
- Is server data (fetched from an API) really the same kind of state as a UI toggle?

## Answer

Start simple and escalate only when there's a real pain point.

**1. Local state** — keep state in the component that uses it.

**2. Lift state up** — when siblings need to share state, move it to their closest common parent and pass it down with props/callbacks. This is the default React answer and keeps data flow explicit.

**3. Context** — when props have to travel through many layers that don't care about them (prop drilling), or for app-wide, rarely changing values: theme, locale, current user, feature flags. Caveat: **every consumer re-renders when the value changes**, and Context has no selectors. Split contexts and memoize the value to limit this.

```jsx
const value = useMemo(() => ({ user, logout }), [user]);
<AuthContext value={value}>{children}</AuthContext> // React 19 syntax
```

**4. A state library** (Zustand, Redux Toolkit, Jotai) — when global client state changes often, many components read slices of it, or the update logic is complex. They offer **selector-based subscriptions** (only re-render on the slice you use), devtools, middleware and easier testing.

**Separate server state from client state.** Most "global state" is really cached API data — use TanStack Query, SWR, or Server Components for that, not Redux. URL state (filters, pagination) belongs in search params.

**Follow-up:** Context is a dependency-injection mechanism, not a state manager — it pairs with `useState`/`useReducer` to become one.
