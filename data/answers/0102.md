## Hints

- Before any connection can be made, how does the browser find the server's address?
- What has to be set up before the first HTTP byte is sent over HTTPS?
- Once HTML arrives, what does the browser do to turn it into pixels?

## Answer

A strong answer walks through the layers, at whatever depth the interviewer wants:

1. **URL parsing** – the browser decides if it's a URL or a search term, figures out scheme, host, port, path. HSTS preload may force `https`.
2. **Cache checks** – service worker, HTTP cache; a fresh cached response may skip the network entirely.
3. **DNS resolution** – browser cache → OS cache/hosts file → recursive resolver → root → TLD → authoritative server, returning an IP (A/AAAA record).
4. **Connection** – TCP three-way handshake (SYN, SYN-ACK, ACK), then **TLS handshake** (negotiate version/cipher, verify certificate, derive keys). With HTTP/3 this is a single QUIC handshake over UDP.
5. **HTTP request** – `GET /` with headers (`Host`, `Accept`, cookies). It may pass through CDNs, load balancers and reverse proxies.
6. **Server side** – the app routes the request, may hit caches/databases, renders the response.
7. **Response** – status, headers (`Content-Type`, `Cache-Control`, `Set-Cookie`), body. Redirects (`301`/`302`) restart parts of the process.
8. **Rendering** – parse HTML into the DOM; discover and fetch CSS, JS, images; build CSSOM; blocking scripts pause parsing (unless `defer`/`async`/modules); render tree → layout → paint → composite.
9. **After load** – JS runs, hydration (in React/Next.js apps), further API calls.

```bash
curl -v https://example.com   # shows DNS, TCP connect, TLS and HTTP stages
```

**Tip:** state the outline first, then ask which part to dive deeper into (DNS, TLS, rendering pipeline, performance). Interviewers use this question to probe breadth.

**Follow-up:** How would you make this faster? (CDN, `preconnect`/`dns-prefetch`, HTTP/2–3, caching, critical CSS, fewer render-blocking resources.)
