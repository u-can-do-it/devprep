## Hints

- How does the server push a new message to a recipient who is connected to a different server instance?
- How do you guarantee message order within a conversation, and what happens to messages for offline users?
- How would you store billions of messages so that "load the last 50 messages of chat X" is fast?

## Answer

**1. Clarify requirements:** 1:1 and group chats (cap group size, e.g. 1,000), online presence, delivery and read receipts, history sync across devices, push notifications, attachments. Scale assumption: about 50M daily active users and 2B messages per day. Non-functional needs: low latency (under ~200 ms), no lost messages, ordered within a conversation.

**2. High-level architecture**

```text
Clients <-WebSocket-> Gateway nodes (stateful connections)
                         |   ^
                         v   |  pub/sub (Redis / NATS / Kafka)
                     Chat service --> Message store (Cassandra / ScyllaDB)
                         |        --> Conversations & members (Postgres)
                         +--> Push service (APNs / FCM) for offline users
Attachments: presigned upload to object storage + CDN
```

- **Gateways** keep persistent **WebSocket** connections and a registry of `userId -> gatewayId` (in Redis, with TTL heartbeats, which also gives **presence**).
- **Send path:** client sends `{conversationId, clientMsgId, body}`. The chat service validates membership, assigns a **per-conversation sequence number**, persists the message, acks the sender, then publishes to the recipients' gateways via pub/sub. Offline recipients get a push notification.
- **Idempotency:** `clientMsgId` dedupes retries after reconnects.
- **Ordering:** sequence numbers per conversation (single writer per conversation, or a partition key in Kafka). Clients sort by sequence, not clock time.
- **Sync:** each device stores its last-seen sequence per conversation. On reconnect it requests everything after it. That's how offline delivery and multi-device sync work.

**3. Storage**
- Messages: a wide-column store partitioned by `conversation_id`, clustered by sequence descending. Fast "latest N" reads and huge write throughput. Very active conversations may need time-bucketed partitions.
- Metadata (users, conversations, membership): a relational DB.
- Receipts: store a per-member "last read sequence" instead of a row per message per user.

**4. Group fan-out:** write once, deliver to online members via pub/sub. For very large groups or channels, recipients pull instead (fan-out on read).

**5. Scaling and reliability:** gateways scale horizontally behind an L4 load balancer. Reconnect with backoff and jitter. Regional deployments. Rate limits and abuse detection. End-to-end encryption (Signal protocol) means the server stores only ciphertext, which limits server-side search.

**Follow-ups:** typing indicators (ephemeral, never persisted), search (an async index), and the trade-offs of WebSockets vs SSE plus HTTP POST.
