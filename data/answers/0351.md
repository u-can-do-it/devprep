## Hints

- If a CDN caches a response keyed only by URL, who receives the next copy of `/api/me`?
- Which parts of a "personalized" page actually differ per user?
- What must be part of the cache key when data is per user or per tenant?

## Answer

The main risk is **cross-user data leakage**: a shared cache stores one user's response and serves it to someone else. This has caused real incidents (account pages served to strangers after CDN misconfigurations).

**Rules for shared caches (CDN, proxy):**

- Mark per-user responses `Cache-Control: private` (or `no-store` for sensitive data). Default to **not cacheable** for authenticated routes and opt in explicitly.
- Never cache responses with `Set-Cookie`.
- Make sure the CDN doesn't ignore `Authorization`/cookies and strip `Cache-Control` by "cache everything" rules.

**Strategies that still give you caching:**

1. **Split public and private.** Cache the shared shell/product data publicly; fetch the small personalized part (cart count, user name) separately with `private` caching. Partial prerendering / streaming in Next.js follows the same idea.
2. **Cache by segment, not by user.** Price tier, country, language, A/B variant → a handful of variants. Put the segment in the cache key (URL or a normalized header set at the edge), not the raw cookie.
3. **App-level per-user caches** in Redis with keys that include the identity and authorization context:

```python
key = f"tenant:{tenant_id}:user:{user_id}:dashboard:v3"
await redis.set(key, payload, ex=120)
```

4. **Cache the expensive shared inputs** (catalog, permissions model, feature flags), then assemble the user-specific result cheaply per request.
5. Use `ETag` + `private, no-cache` so the browser revalidates cheaply with `304`.

**Pitfalls:**

- Cache keys missing tenant id in multi-tenant systems.
- Permission changes not invalidating cached results (include a permissions version in the key).
- Framework caches: with Next.js `'use cache'`, values read from cookies/headers must be passed in as arguments (part of the key), not read inside the cached function.
- Logging out must not leave private data in a shared device's cache – `no-store` for truly sensitive pages.
