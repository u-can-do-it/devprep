## Hints

- In the old design, how did a call from JavaScript reach native code, and could JS get the answer synchronously?
- What must happen for JS to call a C++ function directly, without turning arguments into JSON?
- Why couldn't the old renderer support React's concurrent features?

## Answer

> The old architecture connected JavaScript and native code through an asynchronous bridge that passed batched, JSON-serialised messages. It was slow for chatty communication, couldn't answer synchronously, and loaded every native module at startup. The New Architecture replaces it with JSI, a C++ interface through which JS calls native code directly. On top of JSI sit Turbo Native Modules (lazy, typed modules), Fabric (a new renderer with a shared C++ core that supports concurrent React), and Codegen (generated typed glue code). It is the default since 0.76 and the only architecture since 0.82.

**What was wrong with the bridge**

- **Serialisation:** every call and every event was converted to JSON, queued, and decoded on the other side.
- **Async only:** JS couldn't read a native value (a layout measurement, a stored setting) in the same tick. That caused visible jumps: render, measure asynchronously, render again.
- **Eager startup:** all native modules were created at launch, used or not.
- **No type safety:** JS and native agreed on method names and argument shapes by convention, and mismatches crashed at runtime.
- **A renderer that couldn't be interrupted,** so React 18 features such as transitions and Suspense for data had no proper support.

**The parts**

| Part | What it is | What it gives |
|---|---|---|
| **JSI** | a C++ API to the JS engine: JS can hold references to C++ objects and call their methods | direct calls, sync or async, no JSON; engine-independent |
| **Turbo Native Modules** | native modules exposed through JSI | loaded on first use; typed; sync methods possible |
| **Fabric** | the renderer: shadow tree and layout (Yoga) in shared C++ | the same core on iOS and Android, sync layout reads, concurrent rendering |
| **Codegen** | build-time generator that reads typed TS or Flow specs | C++, Kotlin and Objective-C interfaces that must match the spec |
| **Bridgeless mode** | the runtime without the bridge at all | less startup work, one initialisation path |

**What Fabric changes**

- The shadow tree is immutable and thread-safe, so React can prepare a new tree in the background and commit it when ready. That is what makes transitions, Suspense and automatic batching work as on the web.
- Layout can be read synchronously, so `useLayoutEffect` can measure a view and reposition a tooltip before the frame is shown, without a flicker.
- Urgent updates from user input can be rendered synchronously on the UI thread.
- The event loop follows the web model more closely (microtasks, well-defined ordering).

**What it means in practice**

- Libraries can do things that were impossible before: synchronous storage (MMKV, #681), UI-thread worklets (#678), camera frame processing, fast list recycling (#673).
- For application code the change is mostly invisible. You write the same React components.
- It isn't automatically faster everywhere. The big wins are startup (lazy modules), responsiveness under concurrent rendering, and removing bridge traffic in gesture- and scroll-heavy screens.

**Migration**

- **Timeline:** default in 0.76, the legacy architecture frozen in 0.80, removed as an option in 0.82, and its code deleted from builds after that.
- **Apps:** upgrade React Native, then check every dependency with native code. Most are ready; the rest must be replaced or patched.
- **Interop layers** let many old-style modules and view managers keep working unchanged, but they are a transition tool, not a place to stay.
- **Your own native modules:** write a typed spec and move to a Turbo Native Module or the Expo Modules API (#700).

**Follow-up:** a native module method was asynchronous under the bridge, and now it could be synchronous. When should it stay async? (When it does I/O or any slow work. A synchronous call blocks the JS thread for its whole duration, so keep sync methods for fast in-memory reads.)
