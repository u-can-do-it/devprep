## Hints

- What happens to the database when a very hot key expires and 5,000 requests miss at the same moment?
- How can you make sure only one request recomputes a value while the others wait or get slightly stale data?
- Which is safer under concurrent writes: updating cache entries or deleting them, and in what order relative to the DB write?

## Answer

### Invalidation

Strategies, often combined:

- **TTL expiry** – simple, bounds staleness; pick TTLs per data type.
- **Explicit invalidation on write** – after committing to the DB, **delete** the key (not set it), so the next read repopulates from the source of truth.
- **Event-driven** – publish change events (CDC with Debezium, outbox, pub/sub) so all services/nodes invalidate their caches.
- **Versioned keys** – `user:42:v7`; bump the version to invalidate a whole group instantly.

Race to be aware of: reader misses, reads old value from DB, writer updates DB and deletes the key, reader then writes the stale value into cache. Mitigations: short TTLs as a safety net, **delayed double delete**, or versioned/compare-and-set writes. For multi-level caches (in-process + Redis), use pub/sub to clear local copies.

### Stampede (thundering herd / dogpile)

When a hot key expires, many concurrent misses hit the DB at once, potentially causing a cascading failure.

- **Request coalescing / locking** – only one caller recomputes; others wait or serve stale.

```python
async def get_with_lock(key, loader, ttl=300):
    if (v := await redis.get(key)) is not None:
        return v
    if await redis.set(f"lock:{key}", "1", nx=True, ex=10):   # winner rebuilds
        try:
            v = await loader()
            await redis.set(key, v, ex=ttl + random.randint(0, 30))  # jittered TTL
            return v
        finally:
            await redis.delete(f"lock:{key}")
    await asyncio.sleep(0.05)
    return await get_with_lock(key, loader, ttl)              # bound retries in real code
```

- **Stale-while-revalidate** – store a soft expiry inside the value; serve stale and refresh in the background.
- **Probabilistic early expiration** (XFetch) – each request may refresh early with probability rising near expiry.
- **TTL jitter** – avoid many keys expiring simultaneously (e.g. after a cache warm-up).
- **Pre-warming / never-expire hot keys** refreshed by a background job.
- Protect the DB anyway: connection pool limits, circuit breakers, rate limiting.
