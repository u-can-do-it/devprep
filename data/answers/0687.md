## Hints

- A production stack trace says `at anonymous (address at index.android.bundle:1:482913)`. What do you need to read it?
- Does a React error boundary catch a crash inside a Swift or Kotlin library?
- What is an ANR, and which thread causes it?

## Answer

> A mobile app fails in three ways: a JavaScript error, a native crash, and a freeze (an ANR on Android, a hang or watchdog kill on iOS). You need a crash reporting tool that captures all three on both layers, plus uploaded source maps and native symbol files, so that stack traces are readable. Then you watch release health: the share of crash-free users per version, and you gate rollouts on it.

**Three kinds of failure**

| Kind | Example | Where it shows |
|---|---|---|
| JS error | `undefined is not a function` in render or a handler | error boundary, JS error handler; fatal in release if unhandled |
| Native crash | null pointer in a Kotlin module, bad memory access, out of memory | native crash report only; JS never hears about it |
| Freeze | main thread blocked for 5 seconds (ANR), slow start killed by the iOS watchdog | Play Console vitals, crash tool's ANR and hang detection |

An error boundary (#205) catches render errors in JS and lets you show a fallback screen. It doesn't catch errors in event handlers or async code, or anything native.

**Tooling**

Sentry, Firebase Crashlytics, Bugsnag and Datadog have React Native SDKs that install both a JS handler and native crash handlers. One report shows the JS stack, the native stack, and the context:

- App version, build number and over-the-air update id (#699).
- Device model, OS version, free memory, whether the app was in the foreground.
- Breadcrumbs: the screens visited, requests, and taps before the crash.
- The user id (not personal data) and feature flags.

**Readable stack traces**

Production code is minified and compiled to Hermes bytecode (#677), and native code is stripped. Per release, upload:

- **JS source maps**, composed from the Metro and Hermes maps.
- **iOS dSYM files.**
- **Android R8/ProGuard mapping files** and native debug symbols.

The release name and build number in the SDK must match the uploaded files. Every over-the-air update has its own bundle and needs its own source maps. Build tools (the Sentry Expo plugin, EAS, Gradle and Xcode steps) automate this; verify it by throwing a test error in a release build.

**What to monitor**

- **Crash-free users and sessions** per version. This is the main release health number.
- **ANR rate** and crash rate in Play Console's Android vitals. Bad values reduce the app's visibility in the store.
- **App start time,** slow and frozen frames (#695).
- **JS errors by screen,** and failed requests by endpoint.
- **Store consoles:** Xcode Organizer and App Store Connect for iOS, Play Console for Android. They see crashes even when your SDK failed to start.

Alert on a new issue in the latest version and on a drop in the crash-free rate. Assign issues to the owning team.

**Investigating one crash**

1. Read the symbolicated stack: JS or native? Which library?
2. Look for a pattern: one OS version, one device vendor, one app version, low memory, a specific screen.
3. Reproduce in a **release** build on a similar device, and read the native logs (#671).
4. If it started with a release, compare what changed: a dependency upgrade is the usual suspect for native crashes.
5. Fix, ship, and confirm in the next version's data. Use an over-the-air update for a JS fix and a store release for a native one.

**Privacy**

Scrub personal data from events and breadcrumbs, don't record request bodies, and declare the SDK in the store privacy forms.

**Follow-up:** crash-free users dropped from 99.8% to 97% an hour after a staged rollout reached 10%. What do you do? (Halt the rollout, check whether the crash is JS or native, roll back or fix with an over-the-air update if it is JS, and submit a fixed build if it is native.)
