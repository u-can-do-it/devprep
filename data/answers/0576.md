## Hints

- What is a delegate at runtime: a function pointer, or an object? What does it hold besides the method?
- What does the `event` keyword forbid that a public delegate field allows?
- If a short-lived object subscribes to an event on a long-lived one, who references whom?

## Answer

**Delegates** are type-safe references to methods. A delegate is an object that holds a target (the instance, or `null` for static methods) and a method, and it can be **multicast** (a list of methods called in order).

```csharp
public delegate decimal PriceRule(decimal price);           // custom delegate type

Func<int, int, int> add = (a, b) => a + b;                  // returns a value
Action<string> log = msg => Console.WriteLine(msg);          // returns void
Predicate<int> isEven = n => n % 2 == 0;                    // older; Func<int, bool> is more common
```

`Func<...>` and `Action<...>` cover almost every case; define a custom delegate type when the name documents intent or you need `ref`/`out` parameters. Lambdas are just a short way to create a delegate (or an expression tree, when the target type is `Expression<Func<...>>`, which is how EF Core translates LINQ to SQL, see #579).

**Closures**

A lambda that uses a local variable **captures the variable, not its value**. The compiler moves the variable into a hidden class shared by the method and the lambda:

```csharp
var counter = 0;
Action inc = () => counter++;
inc(); inc();
Console.WriteLine(counter);          // 2: the lambda changed the same variable
```

The classic bug was capturing a `for` loop variable: every lambda saw the final value. Since C# 5, `foreach` creates a new variable per iteration, but `for` still shares one, so copy it into a local inside the loop. Captures also allocate, so on hot paths use `static` lambdas (`static x => x * 2`), which the compiler stops from capturing anything.

**Events**

An event is a delegate with restricted access: outside code can only `+=` and `-=`; only the declaring class can raise it or replace the list.

```csharp
public class OrderService
{
    public event EventHandler<OrderPlacedEventArgs>? OrderPlaced;

    public void Place(Order o)
    {
        // ...
        OrderPlaced?.Invoke(this, new OrderPlacedEventArgs(o));   // ?. copies the delegate, safe if a handler unsubscribes concurrently
    }
}
```

With a public delegate field, any caller could do `OrderPlaced = null` and remove everyone else's handlers, or invoke it from outside.

**How event handlers leak memory**

The publisher's delegate list references each subscriber (the delegate's target). If a short-lived object subscribes to a long-lived publisher (a singleton, a static event, an app-wide message bus) and never unsubscribes, the publisher keeps it alive forever, along with everything it references:

```csharp
public class PriceWidget : IDisposable
{
    private readonly PriceFeed _feed;                    // singleton
    public PriceWidget(PriceFeed feed) { _feed = feed; _feed.Updated += OnUpdated; }
    private void OnUpdated(object? s, EventArgs e) { /* ... */ }
    public void Dispose() => _feed.Updated -= OnUpdated;  // without this, every widget ever created stays in memory
}
```

Fixes: unsubscribe in `Dispose`, return an `IDisposable` subscription token from your own APIs, or use weak events (WPF's `WeakEventManager`). An anonymous lambda can't be unsubscribed unless you keep a reference to it.

**Follow-up:** what happens when one handler of a multicast event throws? (The exception stops the invocation; later handlers don't run. If every handler must run, iterate `GetInvocationList()` and call each one in its own `try`/`catch`.)
