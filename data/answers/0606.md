## Hints

- When do you answer the client with success: after the event is in memory, in a durable log, or committed in PostgreSQL? What do you lose with each?
- Why is one `INSERT` per event the wrong shape, and what does PostgreSQL offer for loading many rows at once?
- What should happen when the database slows down: should requests queue in memory, wait, or be rejected?

## Answer

Start with the numbers and the guarantees, then design the path from socket to disk.

**1. Clarify and size it**

- **Durability:** may an acknowledged event be lost? This decides almost everything below.
- **Event size and peaks:** 50k/s × 1 KB ≈ 50 MB/s, about **4.3 billion rows and 4 TB a day** before indexes. Retention and query patterns matter more than the HTTP layer.
- **Idempotency and ordering:** clients will retry, so events need a client-generated ID (a UUIDv7 keeps inserts roughly time-ordered). Is ordering needed per device or tenant, or not at all?
- Can clients send **batches**? 500 requests of 100 events are far cheaper than 50,000 requests.

**2. Architecture**

```text
clients → load balancer → N stateless ingest instances (Kestrel)
            → bounded Channel<T> → batch writer → PostgreSQL (partitioned, COPY)
   (or)     → Kafka → consumer group → batch writer → PostgreSQL
```

| Acknowledge after | Pros | Cons |
|---|---|---|
| in-memory queue | lowest latency | a crash or deploy loses acknowledged events |
| **database commit (group commit)** | durable, no extra infrastructure | latency = batch interval; a DB outage turns into 503s |
| durable log (Kafka) | durable, absorbs DB outages and spikes, replayable | another system to run; the DB is eventually consistent |

For a hard "no loss" requirement without Kafka, use **group commit**: each request waits until the batch that contains its events is committed.

**3. The ingest instance**

```csharp
app.MapPost("/events", async (EventDto[] events, IngestQueue queue, CancellationToken ct) =>
{
    if (!Validate(events, out var error)) return Results.Problem(error, statusCode: 400);
    var pending = new PendingBatch(events);                                  // holds a TaskCompletionSource
    if (!queue.Writer.TryWrite(pending))                                     // bounded channel is full
        return Results.StatusCode(503);                                      // fail fast + Retry-After header
    await pending.Completion.Task.WaitAsync(TimeSpan.FromSeconds(5), ct);    // completes after the DB commit
    return Results.Accepted();
});

// BackgroundService: a few of these per instance
while (await reader.WaitToReadAsync(ct))
{
    var batch = new List<PendingBatch>();
    int rows = 0;
    while (rows < 5_000 && reader.TryRead(out var item)) { batch.Add(item); rows += item.Events.Length; }
    try   { await WriteBatchAsync(batch, ct); batch.ForEach(b => b.Completion.TrySetResult()); }
    catch (Exception ex) { batch.ForEach(b => b.Completion.TrySetException(ex)); }    // clients get an error and retry
}
```

- `Channel.CreateBounded<PendingBatch>(capacity)` gives **back-pressure** for free (#600). Rejecting with 503/429 and `Retry-After` is better than unbounded memory growth; an idempotent retry from the client is safe.
- Create the `TaskCompletionSource` with `TaskCreationOptions.RunContinuationsAsynchronously` so completing it doesn't run every request's continuation on the writer loop.
- Keep the hot path allocation-light: System.Text.Json source generation, no per-event logging, metrics instead. Server GC (the ASP.NET Core default) and request size limits in Kestrel.
- **Graceful shutdown:** fail the readiness probe, stop accepting, drain the channel within `HostOptions.ShutdownTimeout` (#595).

**4. Writing to PostgreSQL**

`COPY ... FROM STDIN (FORMAT BINARY)` through Npgsql is an order of magnitude faster than row-by-row `INSERT`s. `COPY` has no `ON CONFLICT`, so copy into a temporary staging table and move rows in the same transaction:

```csharp
await using var tx = await conn.BeginTransactionAsync(ct);
await using (var cmd = new NpgsqlCommand("CREATE TEMP TABLE staging (LIKE events INCLUDING DEFAULTS) ON COMMIT DROP", conn, tx))
    await cmd.ExecuteNonQueryAsync(ct);
await using (var copy = await conn.BeginBinaryImportAsync("COPY staging (id, tenant_id, ts, payload) FROM STDIN (FORMAT BINARY)", ct))
{
    foreach (var e in batch.SelectMany(b => b.Events))
    {
        await copy.StartRowAsync(ct);
        await copy.WriteAsync(e.Id, NpgsqlDbType.Uuid, ct);
        await copy.WriteAsync(e.TenantId, NpgsqlDbType.Uuid, ct);
        await copy.WriteAsync(e.Timestamp, NpgsqlDbType.TimestampTz, ct);
        await copy.WriteAsync(e.Payload, NpgsqlDbType.Jsonb, ct);
    }
    await copy.CompleteAsync(ct);
}
await using (var cmd = new NpgsqlCommand("INSERT INTO events SELECT * FROM staging ON CONFLICT DO NOTHING", conn, tx))
    await cmd.ExecuteNonQueryAsync(ct);                                       // retries become no-ops
await tx.CommitAsync(ct);
```

Schema choices matter more than code: **partition by time** (daily) so retention is `DROP` of a partition instead of a huge `DELETE`; keep **few indexes** (each one is extra write work), a BRIN index on time works well for append-only data; the uniqueness check for idempotency must include the partition key. Watch WAL volume, checkpoints, replica lag and autovacuum. Batches of a few thousand rows in a handful of parallel writers usually beat both tiny batches and one giant one: measure.

**5. Scaling and failure**

- Ingest instances are stateless: scale them horizontally on CPU. PostgreSQL is the bottleneck: scale up, tune, then shard by tenant (e.g. Citus) or move analytics to a columnar store (ClickHouse, TimescaleDB) if the queries are aggregations.
- With Kafka in front, a DB outage only grows consumer lag, and partitioning by device or tenant key keeps per-key order.
- Monitor queue depth, batch size, flush latency, rejection rate and consumer lag; alert on the trend, not single spikes.

**Follow-up:** why not acknowledge from memory and write asynchronously? (Every deploy, crash or OOM loses acknowledged events, and the client won't retry. If that's acceptable, say so explicitly; otherwise acknowledge after a durable write.)
