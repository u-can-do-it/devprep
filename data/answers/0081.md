## Hints

- When does a FastAPI background task run relative to sending the response?
- What happens to a queued background task if the server process restarts or crashes?
- What do Celery, RQ, Dramatiq or arq give you that `BackgroundTasks` doesn't?

## Answer

`BackgroundTasks` lets you schedule a function to run **after the response has been sent**, in the same process. The client gets a fast response while small follow-up work happens.

```python
from fastapi import BackgroundTasks, FastAPI

app = FastAPI()

def send_welcome_email(email: str) -> None:
    ...

@app.post("/signup", status_code=201)
async def signup(user: UserCreate, background: BackgroundTasks):
    created = await create_user(user)
    background.add_task(send_welcome_email, created.email)
    return created
```

Details: sync task functions run in the threadpool, async ones on the event loop; tasks run sequentially in the order added; you can also add them from dependencies.

**Limitations:**

- **No durability** – if the process crashes or is redeployed, pending tasks are lost.
- **No retries, scheduling, rate limiting or monitoring.**
- Runs on the **same server resources** as your API; heavy work hurts latency.
- No result tracking for the client.

**Use a real task queue** (Celery, RQ, Dramatiq, arq, or cloud queues like SQS + workers) when work is long-running or CPU-heavy, must not be lost, needs retries/backoff, needs scheduling (cron-like), or must scale independently of the API. Typical pattern: endpoint enqueues a job, returns `202 Accepted` with a job id, client polls or gets a webhook/websocket notification.

Rule of thumb: fire-and-forget, short, losable tasks (logging, cache warm-up, a non-critical email) → `BackgroundTasks`; everything else → a queue.

**Follow-up:** How would you guarantee that an email is sent exactly when the DB transaction commits? (Transactional outbox pattern.)
