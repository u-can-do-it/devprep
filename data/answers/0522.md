## Hints

- If the frontend hides the "Delete user" button, what stops a user from calling `DELETE /users/5` from DevTools?
- Where do roles come from on page load: a decoded JWT, a `/me` endpoint, or both? What if the role changes while the user is logged in?
- Would you check roles (`admin`) or permissions (`users:delete`) in components, and why does it matter as the product grows?

## Answer

Frontend authorization is **UX, not security**. It keeps users from seeing actions they can't perform and from running into `403`s; the server still checks every request (#117, #371). With that framing, the pattern is:

**1. Where permissions come from**

- After login, fetch a `/me` (or `/session`) endpoint that returns the user, their roles and **effective permissions** for the current tenant. Don't decode an access token in the browser as the source of truth: with `HttpOnly` cookies (#115) you can't read it anyway, and claims go stale.
- Prefer **permissions** (`"invoices:approve"`) over role names in the UI. Roles change meaning over time; mapping roles to permissions on the server lets you change that without a frontend release.
- Keep it in one place (an auth context, or the session entry of your query cache), refresh it on window focus or on a push event, and handle **`401`/`403` globally**: `401` clears the session and redirects to login, `403` shows "no access" and refetches `/me`, because the role probably changed.

**2. Route guards**

```tsx
function RequirePermission({ permission }: { permission: Permission }) {
  const { user, isLoading } = useSession();
  const location = useLocation();
  if (isLoading) return <Spinner />;                                  // don't flash the login page
  if (!user) return <Navigate to="/login" state={{ from: location }} replace />;
  if (!user.permissions.includes(permission)) return <Forbidden />;   // a 403 page, not a redirect loop
  return <Outlet />;
}

<Route element={<RequirePermission permission="users:manage" />}>
  <Route path="/admin/users" element={<Users />} />
</Route>
```

Combine with **lazy loading** so the admin bundle isn't shipped to regular users. That saves bytes, it doesn't hide anything: client code is always visible.

**3. Permission-based UI**

```tsx
const can = usePermission();
{can('invoices:approve') && <Button onClick={approve}>Approve</Button>}
```

Decide the UX per case: **hide** (the user shouldn't know the feature exists), **disable with an explanation** ("Ask your admin for approver rights"), or **show and let the server say no**. Being consistent matters more than which you pick.

**4. Data the user shouldn't see is filtered by the API**, never by the client: a list with "hidden" rows still ships the rows. Tenant isolation lives in the backend query (#379).

**5. Server rendering (Next.js):** check the session in the server component or in `proxy.ts`/middleware so protected HTML is never rendered, still backed by API-side checks.

**What it protects against:** confusing UX, accidental `403`s, support tickets, and shipping admin UI to everyone. **What it doesn't stop:** an attacker. Users can edit React state, replay requests or call the API directly. Authorization tests belong in the backend (user A tries to reach user B's resource, a customer calls an admin endpoint, #524), with E2E tests only for the UI states.

**Follow-up:** the `role` field in the user object can be edited in Redux DevTools. Does that matter? (Only for UX. If it unlocks anything real, the backend is broken.)
