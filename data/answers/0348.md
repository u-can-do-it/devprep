## Hints

- What's the difference between `no-cache` and `no-store`?
- How can the server answer "nothing changed" without resending the body?
- How would you cache a JavaScript bundle forever and still ship updates?

## Answer

**`Cache-Control`** tells browsers and shared caches (CDNs, proxies) whether and how long to store a response.

- `max-age=N` – fresh for N seconds; no request needed during that time.
- `s-maxage=N` – override for **shared** caches only (CDN).
- `public` / `private` – `private` means only the user's browser may store it (personalized data).
- `no-cache` – may store, but must **revalidate** with the server before each use.
- `no-store` – never store (sensitive data).
- `immutable` – content will never change at this URL; don't revalidate even on reload.
- `stale-while-revalidate=N` – after expiry, serve the stale copy for up to N seconds while fetching a fresh one in the background (fast responses, eventually fresh).
- `stale-if-error=N` – serve stale if the origin is failing.

**Validators – conditional requests:** when a cached response expires, the client asks "has it changed?"

```http
HTTP/1.1 200 OK
Cache-Control: max-age=60, stale-while-revalidate=300
ETag: "v42-a1b2c3"

GET /api/products/7 HTTP/1.1
If-None-Match: "v42-a1b2c3"

HTTP/1.1 304 Not Modified
```

`304` has no body, saving bandwidth (though still a round trip). `Last-Modified` + `If-Modified-Since` is the older, second-precision alternative.

**Typical policy:**

- Fingerprinted static assets (`app.3f9c1.js`): `public, max-age=31536000, immutable` – a new deploy produces a new URL.
- HTML: `no-cache` (always revalidate) or a short `s-maxage` at the CDN.
- Public API reads: short `max-age` + `stale-while-revalidate`.
- Authenticated/personal responses: `private, no-cache` or `no-store`.

`Vary` lists request headers that change the response (e.g. `Accept-Encoding`, `Accept-Language`) so caches store separate variants.
