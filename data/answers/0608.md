## Hints

- What does `0.1 + 0.2 == 0.3` return for `double`, and for `decimal`? Why?
- What is `7 / 2` in C#, and what is `int.MaxValue + 1` at run time?
- What does `Math.Round(2.5)` return?

## Answer

**The three floating-point types**

| | `float` | `double` | `decimal` |
|---|---|---|---|
| Size | 32 bit | 64 bit | 128 bit |
| Base | binary (IEEE 754) | binary (IEEE 754) | **decimal** (base 10) |
| Precision | about 7 digits | about 15 to 16 digits | 28 to 29 digits |
| Range | ±3.4e38 | ±1.8e308 | ±7.9e28 |
| Speed | hardware | hardware | software arithmetic, much slower |
| Literal | `1.5f` | `1.5` | `1.5m` |
| Use for | graphics, ML, large arrays | science, statistics, geometry | **money**, anything a human checks on a calculator |

Binary floating point can't represent most decimal fractions exactly: `0.1` is stored as 0.1000000000000000055…, and the errors add up.

```csharp
Console.WriteLine(0.1 + 0.2 == 0.3);          // False: 0.30000000000000004
Console.WriteLine(0.1m + 0.2m == 0.3m);       // True
double sum = 0;
for (int i = 0; i < 10; i++) sum += 0.1;      // 0.9999999999999999
decimal total = 19.99m * 3;                   // 59.97, exactly
```

`decimal` stores a 96-bit integer plus a scale (where the decimal point sits), so sums and products of prices are exact. It still can't represent `1m / 3m` and it rounds at 28 digits, but it rounds the way an accountant expects.

**Money rules:** `decimal` in C#, DTOs and the database (`numeric(19,4)` or `decimal(18,2)`, never `float`/`real`); round once, at the end, with a stated rule; or store minor units in a `long` (cents) when you must match another system exactly. EF Core warns when a `decimal` property has no precision (SQL Server would truncate to `decimal(18,2)`): set `HasPrecision(18, 2)`.

**`Math.Round` is banker's rounding.** The default `MidpointRounding.ToEven` rounds .5 to the nearest **even** digit, which avoids bias in statistics but is not what an invoice expects:

```csharp
Math.Round(2.5);                                        // 2
Math.Round(3.5);                                        // 4
Math.Round(2.5, MidpointRounding.AwayFromZero);         // 3
Math.Round(1.005m, 2, MidpointRounding.AwayFromZero);   // 1.01; as a double 1.005 is really 1.00499… and gives 1.00
```

**Integers**

- Division **truncates toward zero**: `7 / 2 == 3`, `-7 / 2 == -3`, `-7 % 2 == -1`. Make one operand floating for a fraction: `7 / 2.0 == 3.5`.
- Overflow **wraps silently** by default: `int.MaxValue + 1` is `int.MinValue` at run time (the compiler only catches it in constant expressions). `checked { … }` or `<CheckForOverflowUnderflow>true</CheckForOverflowUnderflow>` throws `OverflowException`; `unchecked` marks places where wrapping is intended (hash codes). `decimal` always throws on overflow; `double` goes to `Infinity`.
- `int` for counts and ids, `long` for anything that can grow (file sizes, timestamps, ids of a big table), `byte` and `short` only for storage and interop. `Int128`, `BigInteger` and `Half` exist for special cases, and generic math (`INumber<T>`, #577) lets one method accept all of them.

```csharp
int a = int.MaxValue;
int b = a + 1;                   // -2147483648, no error
int c = checked(a + 1);          // OverflowException
```

**Comparing floating-point values**

Never `==` on computed values. Compare with a tolerance that fits the magnitude of the data; `double.Epsilon` is **not** a tolerance (it's the smallest positive value, about 4.9e-324):

```csharp
static bool AlmostEqual(double a, double b, double relative = 1e-9) =>
    Math.Abs(a - b) <= relative * Math.Max(1, Math.Max(Math.Abs(a), Math.Abs(b)));

Console.WriteLine(double.NaN == double.NaN);    // False: use double.IsNaN(x)
```

**Parsing and formatting depend on culture.** `double.Parse("1,5")` is 1.5 on a Polish machine and 15 on an American one (the comma becomes a thousands separator). Parse and format data with `CultureInfo.InvariantCulture`; use the user's culture only for display (#563).

**Follow-up:** `(int)3.99` and `Convert.ToInt32(3.99)` give different results. Why? (The cast truncates toward zero to 3; `Convert.ToInt32` rounds, with banker's rounding, to 4. Casting a value out of `int` range or `NaN` saturates since .NET 9; before that the result depended on the CPU.)
