## Hints

- Which parts of .NET Framework have no direct equivalent in modern .NET (`System.Web`, Web Forms, WCF server, AppDomains, Remoting)?
- In which order do you migrate the projects in a solution, and how can a library serve the old app and the new app at the same time?
- How can a new ASP.NET Core app take over routes one by one while users keep a single site, session and login?

## Answer

A big-bang rewrite of a large app usually takes years, freezes features and ships new bugs. The goal is an **incremental** migration where the app keeps running and you move it piece by piece (strangler fig). Note that .NET Framework 4.8.x is still supported as part of Windows, so the motivation is business value: performance, Linux containers, hiring, modern libraries, not a deadline.

**1. Assess first**

- Inventory projects, NuGet packages and their dependency graph. For each package: is there a modern .NET version or a replacement?
- Find blockers: `System.Web`/`HttpContext.Current` everywhere, Web Forms pages, WCF services, AppDomains, .NET Remoting, Code Access Security, COM, Windows-only APIs (registry, Event Log, WMI).
- Use Microsoft's upgrade tooling (GitHub Copilot app modernization in Visual Studio, which replaced the deprecated .NET Upgrade Assistant in late 2025 and needs a Copilot licence; the legacy tool can still be enabled) to analyse the solution and convert projects, and review every change it makes.
- Add **characterization tests** around the critical flows before changing anything.

**2. Migrate bottom-up**

1. Convert projects to **SDK-style** `.csproj` and `PackageReference` (this works on .NET Framework too).
2. Move class libraries first: multi-target them (`<TargetFrameworks>net48;net10.0</TargetFrameworks>`) or target `netstandard2.0`, so the old app and the new one share the same code.
3. Replace or wrap dependencies on `System.Web` in those libraries.
4. The web app's host migrates last.

```xml
<PropertyGroup>
  <TargetFrameworks>net48;net10.0</TargetFrameworks>
</PropertyGroup>
<ItemGroup Condition="'$(TargetFramework)' == 'net48'">
  <Reference Include="System.Web" />
</ItemGroup>
```

**3. Run old and new side by side**

Create a new ASP.NET Core app and put it **in front** of the old one. It handles migrated routes and forwards everything else to the legacy app with **YARP**:

```csharp
builder.Services.AddReverseProxy().LoadFromConfig(builder.Configuration.GetSection("ReverseProxy"));
var app = builder.Build();
app.MapControllers();                           // routes already migrated
app.MapReverseProxy();                          // everything else goes to the .NET Framework app
```

- The **System.Web adapters** (`Microsoft.AspNetCore.SystemWebAdapters`) provide a `System.Web.HttpContext`-like API so shared libraries work in both apps, and they can share **session and authentication** with the old app during the transition.
- Migrate route by route, starting with the most valuable or the easiest pages; measure each step and remove the old code when its traffic is gone.

**4. Typical replacements**

| .NET Framework | Modern .NET |
|---|---|
| ASP.NET MVC / Web API | ASP.NET Core MVC or Minimal APIs (similar concepts, new pipeline) |
| Web Forms | no port: rewrite pages in Razor Pages, Blazor or a SPA |
| WCF services | CoreWCF for existing SOAP clients, or gRPC/REST for new ones; WCF **client** packages exist |
| `Global.asax`, HTTP modules and handlers | `Program.cs`, middleware |
| `web.config`, `ConfigurationManager` | `IConfiguration` and options (#584) |
| Entity Framework 6 | EF6 runs on modern .NET; move to EF Core later as a separate step |
| Windows services | Worker Service with `BackgroundService` (#595) |
| Windows-only APIs | Windows Compatibility Pack, or keep that part on Windows |

**5. Risks to manage**

- Behaviour differences: culture and globalization (ICU vs NLS), default JSON serializer, `HttpClient` defaults. Integration tests catch these.
- Two apps to deploy and monitor during the transition: keep it time-boxed and visible.
- Don't combine the migration with a redesign of the domain; change the platform first, then refactor.

**How to say it:** "Assess and add tests, convert to SDK-style projects, move libraries to multi-targeting, put a new ASP.NET Core app with YARP in front, migrate route by route with shared session and auth, and delete legacy code as traffic moves."

**Follow-up:** the old app has a WCF service used by ten external partners you can't make change. What do you do? (Host it on CoreWCF, keeping the same contract and bindings, and test it against recorded partner requests. New consumers get a REST or gRPC API, and the SOAP endpoint is retired when partners move.)
