## Hints

- If the tool writes the code, what is left for the interviewer to evaluate?
- What do you do in the first two minutes, before you type a prompt?
- The generated code has a bug. Is that a problem for you or an opportunity?

## Answer

> When AI is allowed in an interview, the interviewer is assessing how you direct it and check it, not how fast it types. Confirm the rules first. Clarify the problem and outline your approach out loud before prompting, then work in small steps you can explain. Read the output critically, run it, and point out what you'd change. Own the design decisions and be ready to continue without the tool. For a take-home, say how you used AI and be able to explain and extend every line.

More companies now allow or even require AI tools in live coding and take-home tasks, because that is how the job is done. What they evaluate changes accordingly.

**What the interviewer is looking for**

| Signal | What it looks like |
|---|---|
| Problem decomposition | you split the task and decide the order before prompting |
| Communication with the tool | specific prompts with context, constraints and examples |
| Critical reading | you spot a flaw in the output without being told |
| Verification | you run it, write a test, try an edge case |
| Ownership | you can explain why each part is there and what the alternatives were |
| Judgement | you know when to stop prompting and write three lines yourself |
| Fundamentals | you can still reason about complexity, state, errors and types |

**How to work in a live session**

1. **Ask about the rules:** which tools, whether to share the screen with the assistant, whether full agent mode is fine or only completion.
2. **Clarify the problem out loud:** inputs, outputs, edge cases, constraints. The same as without AI.
3. **State your approach before prompting:** "a map from id to item, one pass, O(n); I'll handle duplicates by keeping the last". Now the design is visibly yours.
4. **Prompt in small steps** and say what you're asking for and why. One function or one component at a time.
5. **Read what comes back, aloud:** "this is fine, this handles the empty list, but it mutates the input, and I don't want that". Catching a real flaw is the strongest thing you can do in the session.
6. **Run it.** Add a quick test or try the edge cases you named in step 2.
7. **Fix small things by hand.** It shows you can, and it's faster than another prompt.
8. **Summarise:** what works, what you'd do with more time, what you'd check before production.

**Example of talking through a live session** (replace with your own)

> "Before I start: is it fine if I use the agent in the editor, or only completion? Good. Let me repeat the task: merge two lists of orders by id, the newer one wins, and the order of the first list is kept. I'll assume ids are unique within a list; tell me if they aren't. My plan is a map from id to order and a single pass, so O(n). I'll ask the assistant for that function and for tests with an empty list and with an id present in both lists." *(reads the output)* "This works, but it mutates the first array, which I don't want, and it types the order as `any`. I'll fix both by hand, that's quicker than another prompt. Now I'll run the tests. They pass, and I'll add one for an id that exists only in the second list. With more time I'd validate the input at the boundary and check how it behaves with very large lists."

**What goes wrong**

- Pasting the whole task and waiting in silence. The interviewer learns nothing about you.
- Accepting output without reading it, then being unable to explain a line.
- Prompting again and again in a loop when a two-line manual fix would do.
- Letting the tool pick the architecture and defending a choice you didn't make.
- Freezing when the tool is slow, wrong or switched off. Be ready to write the core yourself.

**Take-home tasks**

- **Follow the instructions** about AI use, and if they say nothing, state what you did. A short note in the README is enough: "Used an agent for scaffolding and test data; the data model, the reducer and the error handling are my design."
- **Understand all of it.** The follow-up interview is usually "walk me through this" and "now change it live". Anything you can't explain counts against you.
- **Make it yours:** trim generated extras you weren't asked for, keep the scope tight, write the trade-offs section yourself.
- **Leave evidence of how you worked:** meaningful commits, tests, a note on what you'd do next.
- Don't hide AI use. Reviewers recognise unedited generated code, and honesty is part of what is being assessed.

**If AI is not allowed,** respect that completely. Then the test is of fundamentals, and using a tool anyway is a failed interview regardless of the code.

**Follow-up:** the assistant produced a working solution in thirty seconds. How do you use the remaining time to show what you know? (Review it aloud, test edge cases, discuss complexity and trade-offs, improve naming and error handling, and say how you'd change it for production scale.)
