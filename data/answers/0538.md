## Hints

- What should you ask before drawing anything, and why does "who are the users and on what devices" change the architecture?
- Where does each piece of state live: server cache, URL, global store, component?
- Which trade-off would you state out loud for choosing infinite scroll over pagination?

## Answer

A frontend system design round ("design a product listing page", "design a chat app", "design a dashboard") is not about pixels. The interviewer wants to see that you can go from vague requirements to an architecture, state trade-offs, and stop at the right level of detail. A simple structure (often called RADIO) keeps you on track.

**1. Requirements (5 min).** Functional: core flows, must-have vs nice-to-have. Non-functional: users and devices (mobile-first? slow networks?), scale of data (100 products or 1 million?), SEO (public catalogue vs logged-in app), real-time needs, offline, accessibility (#285), i18n (#472), auth. Ask, then write the list where both of you can see it. Scope explicitly: "I'll focus on the listing and detail pages, not checkout."

**2. Architecture.** Rendering strategy first: SSR or SSG for public, SEO-relevant pages, a SPA for the authenticated app, streaming for slow data (#42, #492). Then the high-level boxes: component tree (page, layout, feature components, shared UI), data layer (API client, cache), state, routing, and where the boundary with the backend sits (BFF, #421). Draw it; a diagram beats prose.

**3. Data model.** The entities the UI needs (`Product`, `Filter`, `Cart`), normalised by id (#453), and the shape of a page in memory. Separate **server state** (products, cached, refetched, #212, #530) from **client state** (selected filters, open modal, #529) and **URL state** (filters, sort, page, so views are shareable and the back button works, #503).

**4. Interface (API).** Endpoint shape and pagination: cursor-based for feeds, offset for tables (#95); fields and sparse responses; error contract (#353); real-time via SSE or WebSockets where needed (#107); request dedup and caching headers (#348). Say what the client sends (filters, cursor, locale) and what it gets back (items, next cursor, total if cheap).

**5. Optimisations and the hard parts.** Pick the two or three that matter for this product:

- **Performance:** code splitting by route (#60), image strategy (`srcset`, lazy loading, #254), list virtualization for long lists (#218), prefetching on hover, optimistic updates (#530), Core Web Vitals targets (#59).
- **Resilience:** loading and error states, retries with backoff for idempotent requests (#521), stale-while-revalidate, request cancellation on navigation (#300).
- **Accessibility:** keyboard navigation, focus management, live regions for dynamic content (#287, #504).
- **Security:** XSS and CSP for user content (#108, #111), auth token storage (#115), no secrets in the bundle (#368).
- **Observability:** error tracking and RUM (#464); feature flags for rollout (#123).

**Worked example: product listing with filters.** Requirements: public, SEO matters, 500k products, mobile majority. Architecture: Next.js with SSR for the first page (SEO, fast LCP), client-side navigation for filter changes; filters and sort in the URL; results in TanStack Query keyed by the URL params; infinite scroll with cursor pagination (#539) and a "Load more" fallback for accessibility and SEO crawlers; images via `next/image` with explicit sizes to avoid CLS; a virtualized grid only if measurements show jank; facets fetched with the results to avoid a second round trip; debounce the search input and cancel stale requests (#502). Trade-off stated: infinite scroll is better for browsing, worse for reaching the footer and for returning to a position, so persist scroll position per URL.

**Common mistakes:** jumping into code or component names before requirements; silence instead of thinking out loud; designing for Google scale when the brief says internal tool; not stating trade-offs ("I'd use X because... the cost is..."); forgetting error and empty states; ignoring the interviewer's hints about where they want depth.

**Follow-up:** how would your design change if the page had to work offline? (Service worker with cache-first for the shell and stale-while-revalidate for data, #280; queue mutations and replay; show sync status.)
