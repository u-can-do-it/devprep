## Hints

- When you change a property on a loaded entity and call `SaveChangesAsync`, how does EF Core know what `UPDATE` to send?
- How many SQL queries run when you loop over 100 orders and touch `order.Customer` with lazy loading on?
- What happens to the row count when you `Include` two collections in one query?

## Answer

**Change tracking**

A `DbContext` is a **unit of work**, registered as scoped (one per request). Entities you load are tracked: EF keeps a snapshot of their original values, and `SaveChangesAsync` compares (`DetectChanges`) and sends only the changed columns in one transaction.

| State | Meaning on `SaveChanges` |
|---|---|
| `Added` | `INSERT` |
| `Modified` | `UPDATE` of changed columns |
| `Deleted` | `DELETE` |
| `Unchanged` / `Detached` | nothing |

Tracking costs memory and CPU, so read-only queries should skip it:

```csharp
var list = await db.Products.AsNoTracking().Where(p => p.IsActive).ToListAsync(ct);
```

A `DbContext` is **not thread-safe**: don't run two queries on it in parallel, and don't make it a singleton.

**N+1 and lazy loading**

```csharp
// N+1: one query for orders, then one per order for the customer (with lazy-loading proxies)
foreach (var o in await db.Orders.ToListAsync())
    Console.WriteLine(o.Customer.Name);

// One query with a JOIN
var orders = await db.Orders.Include(o => o.Customer).ToListAsync();

// Better for read endpoints: project only what you need (no tracking, fewer columns)
var rows = await db.Orders
    .Select(o => new OrderRow(o.Id, o.Total, o.Customer.Name))
    .ToListAsync();
```

Lazy loading is off by default in EF Core (it needs the proxies package and `virtual` navigations). Keep it off in web apps: it hides queries in property access. A projection with `Select` is usually the best choice for reads because it fetches only the needed columns and doesn't track.

**Cartesian explosion and split queries**

`Include(o => o.Lines).Include(o => o.Payments)` becomes one SQL query with two JOINs, so an order with 50 lines and 10 payments returns 500 rows. `AsSplitQuery()` sends one query per collection instead. The trade-off: more round trips, and the queries aren't one consistent snapshot unless you use a transaction. EF logs a warning when a query includes several collections without choosing a mode.

**Other common pitfalls**

- Calling `ToList()` too early and filtering in memory (#579).
- A method EF can't translate inside a query throws at runtime; move it after materialisation or rewrite it.
- Loading an entity just to delete or update many rows: use `ExecuteUpdateAsync`/`ExecuteDeleteAsync` (#596).
- Turn on SQL logging in development (`LogTo`, or `Microsoft.EntityFrameworkCore.Database.Command` at `Information`) and read what's generated.

**Migrations**

```bash
dotnet ef migrations add AddOrderStatus   # generates C# Up/Down from the model diff
dotnet ef database update                 # applies locally
dotnet ef migrations script --idempotent  # SQL script for production review
```

Each migration also updates a model snapshot; the database records applied migrations in `__EFMigrationsHistory`. In production prefer reviewed SQL scripts or a migration bundle (`dotnet ef migrations bundle`) run in the deploy pipeline, not `Database.Migrate()` at app startup with several replicas racing. Check generated migrations: renames can come out as drop + add, which loses data.

**Follow-up:** a list endpoint takes 3 seconds and runs 201 queries. How do you find and fix it? (Look at the SQL log or traces, spot the N+1, replace it with a projection or `Include`, add `AsNoTracking`, then check the query plan and indexes.)
