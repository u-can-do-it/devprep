## Hints

- Which OSI layers do these numbers refer to, and what can a load balancer "see" at each one?
- Can a balancer route `/api` and `/images` to different backends if it only sees IPs and ports?
- Which one has to terminate TLS to make its routing decisions?

## Answer

**L4 (transport layer)** load balancers route based on IP address, port, and protocol (TCP/UDP). They don't inspect the payload — they forward connections/packets.

- Very fast, low latency, handle millions of connections.
- Protocol-agnostic: works for databases, gRPC, game servers, any TCP/UDP traffic.
- Can pass TLS through untouched.
- Examples: AWS NLB, IPVS, HAProxy in TCP mode.

**L7 (application layer)** load balancers understand HTTP(S): they terminate TLS and read URLs, headers, cookies, and methods.

- Content-based routing (`/api/*` → API service, `Host: admin.*` → admin app).
- Sticky sessions via cookies, header rewriting, compression, caching, WAF rules, auth, rate limiting.
- Per-request balancing of HTTP/2 and gRPC streams over one connection.
- More CPU work per request, slightly higher latency.
- Examples: AWS ALB, NGINX, Envoy, Traefik, Cloudflare.

```nginx
location /api/ { proxy_pass http://api_backend; }
location /     { proxy_pass http://web_backend; }
```

Common setup: an L4 balancer at the edge for raw throughput feeding a fleet of L7 proxies (or an ingress controller / service mesh) that handle routing.

Both need **health checks**, and the algorithm matters: round robin, least connections, or consistent hashing.

**Follow-up:** "Why does L4 balancing work poorly for long-lived gRPC connections?" — one connection pins all its requests to one backend.
