## Hints

- Which layers of an app don't care whether they run in a browser or on a phone?
- What happens if a shared package imports `window.localStorage` or `react-native`?
- React Native components can render to the DOM. What is the cost of using that for the whole website?

## Answer

> Share the layers that don't depend on the platform: types and API contracts, the API client, validation, business logic, state and data-fetching hooks, translations and design tokens. Put them in packages in a monorepo. Share UI only when the product is truly the same on both platforms, with React Native for Web or a universal Expo app. Keep shared packages free of DOM and native APIs, and inject platform differences through small adapters or platform file extensions.

**What is worth sharing**

| Layer | Share? | Notes |
|---|---|---|
| Types, API schemas (OpenAPI, GraphQL, zod) | yes | the highest value for the lowest cost |
| API client, auth logic, error mapping | yes | inject storage and `fetch` |
| Validation and business rules | yes | pure functions |
| State stores, TanStack Query hooks and key factories | yes | platform-neutral (#636) |
| Translations, formatting, analytics event names | yes | |
| Design tokens (colours, spacing, type scale) | yes | generate CSS variables and RN theme objects from one source |
| UI components | sometimes | needs a cross-platform UI layer |
| Navigation and layout | rarely | interaction patterns differ |

**Monorepo layout**

```
apps/
  web/        Next.js or Vite
  mobile/     Expo
packages/
  api/        client, schemas, query hooks
  domain/     business logic
  tokens/     design tokens
  ui/         optional shared components
```

Use pnpm workspaces with Turborepo or Nx for task caching and affected-only builds (#419, #616). Expo detects monorepos and configures Metro for them.

**Rules for shared packages**

- **No platform APIs.** No `window`, `document` or `localStorage`, and no `react-native` imports, unless the package is explicitly a UI package.
- **Inject differences.** The core takes an interface, and each app provides the implementation:

```ts
// packages/api
export interface TokenStorage {
  get(): Promise<string | null>;
  set(token: string): Promise<void>;
  clear(): Promise<void>;
}
export function createApiClient(opts: { baseUrl: string; storage: TokenStorage }) { /* ... */ }

// apps/mobile: storage backed by SecureStore
// apps/web:    an httpOnly cookie handled by the server, or another web implementation
```

- **Or use platform files:** `storage.native.ts` and `storage.web.ts` (also `.ios`, `.android`). The bundler picks the right one (#670).
- **One version of React** and of each library with native code. Duplicates cause "invalid hook call" errors and native module conflicts. Enforce single versions with workspace overrides.
- **Ship compatible code.** Either let each app's bundler compile the package source, or build it. Check that `exports` conditions resolve in both Metro and the web bundler.
- **Enforce boundaries** with lint rules, so a web-only import can't reach a shared package.

**Sharing UI**

- **React Native for Web** renders `View`, `Text` and the other primitives to DOM elements. Expo uses it for its web target.
- **A universal Expo app** with Expo Router: one codebase and one set of routes for iOS, Android and the web, with static or server rendering (#675).
- **Cross-platform styling libraries** (NativeWind, Tamagui, Unistyles) give one styling API with responsive rules.
- **React Strict DOM** goes the other way: a web-first API that is mapped to native.
- **Expo DOM components** embed a web React component inside a native screen (#690).

**Trade-offs of shared UI**

- It works best for app-like products: dashboards, tools, the logged-in part of a product.
- A marketing site with heavy SEO, content and web-specific layouts is usually better as a separate web app that shares only logic.
- The risk is a lowest-common-denominator UI: a website that feels like a phone app, or an app that ignores platform conventions.
- Web bundle size and accessibility need attention, because the abstraction hides HTML semantics.

**A sensible path**

Start by sharing contracts, the API client and logic. That gives most of the benefit with little coupling. Add shared tokens next. Share components only where the design is intentionally the same, and measure whether it saves time.

**Follow-up:** the shared `api` package works on the web but crashes in the mobile app with "localStorage is not defined". How should it have been designed? (The package must not touch platform storage. It should accept a storage adapter, with the web and mobile apps passing their own implementations.)
