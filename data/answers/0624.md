## Hints

- Which Entra ID app registrations do you need for a React SPA calling your own Node API, and which OAuth flow does the SPA use?
- What exactly must the API check in an incoming access token, and why shouldn't it try to validate a Microsoft Graph token?
- Delegated vs application permissions in Microsoft Graph: which one does a nightly job that syncs all employees need?
- Which claim do you use as the stable user id: `email`, `upn`, `sub` or `oid`?
- How do app roles or group membership end up in the token, and what is the groups "overage" problem?

## Answer

Many companies already run Microsoft 365, so internal apps sign people in with their work account through **Microsoft Entra ID** (formerly Azure AD), using **MSAL** libraries, and read company data (users, groups, calendars, files, mail) through **Microsoft Graph**. Under the hood it's OAuth 2.0 + OpenID Connect (#116, #380).

**1. App registrations (one tenant, "single tenant"):**

- **API registration:** *Expose an API* with an Application ID URI (`api://<api-client-id>`) and a scope such as `access_as_user`. Define **app roles** (`Offers.Approver`, `Admin`) and assign them to users or groups in *Enterprise applications*.
- **SPA registration:** redirect URI of type *SPA* (authorization code flow with PKCE, no client secret), with permission to call the API scope.
- For server-to-server work (sync jobs, sending mail), a confidential client with a **certificate** or a federated credential/managed identity rather than a long-lived secret.

**2. Frontend with MSAL React:**

```tsx
const msal = new PublicClientApplication({
  auth: { clientId: SPA_ID, authority: `https://login.microsoftonline.com/${TENANT_ID}`, redirectUri: '/' },
  cache: { cacheLocation: 'sessionStorage' },
});

<MsalProvider instance={msal}><App /></MsalProvider>

async function getApiToken() {
  const account = msal.getActiveAccount()!;
  try {
    return (await msal.acquireTokenSilent({ account, scopes: [`api://${API_ID}/access_as_user`] })).accessToken;
  } catch (e) {
    if (e instanceof InteractionRequiredAuthError) return msal.acquireTokenRedirect({ scopes: [...] });
    throw e;
  }
}
// attach as `Authorization: Bearer <token>` in the API client (#469)
```

Request a token **for your API's scope**, not a Graph token, when calling your backend. Tokens live in browser storage, so XSS protection matters (#108); the alternative is a **BFF** (#421): the backend is a confidential client, does the code exchange and keeps tokens server-side behind an `HttpOnly` session cookie (#523).

**3. Validating the token in the Node API:**

```ts
import { createRemoteJWKSet, jwtVerify } from 'jose';
const JWKS = createRemoteJWKSet(new URL(`https://login.microsoftonline.com/${TENANT_ID}/discovery/v2.0/keys`));

const { payload } = await jwtVerify(token, JWKS, {
  issuer: `https://login.microsoftonline.com/${TENANT_ID}/v2.0`,
  audience: API_ID,                                  // or the api:// URI, depending on the token version
});
if (!String(payload.scp ?? '').split(' ').includes('access_as_user')) throw forbidden();
const user = { id: payload.oid, tenant: payload.tid, roles: (payload.roles as string[]) ?? [] };
```

- Set `requestedAccessTokenVersion: 2` in the API registration's manifest, or Entra issues v1 tokens with a different issuer (`https://sts.windows.net/<tenant>/`) and the `api://` URI as audience.
- Check **signature, issuer (your tenant), audience (your API), expiry**, then the **scope** (`scp`, delegated) or **roles** (app roles, or `roles` in app-only tokens).
- Identify users by **`oid`** (+ `tid`). `email` and `upn` can change (name change, domain migration); `sub` is different per application.
- Map Entra roles or groups to your own permissions (#379), and keep row-level rules in your app (#622).
- **Groups:** the `groups` claim only carries ids, and past ~200 groups the token has an *overage* marker instead, so you'd have to call Graph. App roles assigned to groups are usually cleaner.
- Never try to validate a token issued for Graph; it isn't meant for you.

**4. Microsoft Graph:**

- **Delegated permissions** act as the signed-in user (`User.Read`, `Calendars.Read`); the backend gets such a token with the **on-behalf-of** flow (`msal-node` `acquireTokenOnBehalfOf`) from the user's API token.
- **Application permissions** act as the app itself (`User.Read.All`, `Mail.Send`) via **client credentials**; they need admin consent and are powerful, so scope them down (e.g. an application access policy to restrict which mailboxes `Mail.Send` may use).
- Typical uses in an internal system: syncing employees and departments with `/users/delta` (#623), checking group membership, sending approval emails (`/users/{id}/sendMail`), reading files from SharePoint/OneDrive, Teams notifications (via a bot or a Workflows webhook, since posting chat messages as an app is restricted).
- Graph returns paged results (`@odata.nextLink`), throttles with `429` and `Retry-After` (#521), and supports `$select`/`$filter` to fetch less.

**5. Better Auth and similar libraries:** Better Auth is a self-hosted TypeScript auth library that stores sessions in your own database and supports Microsoft as an OIDC provider. It fits when the app should own its sessions (cookies, multiple providers, local accounts for external users) instead of relying on Entra tokens alone.

**Follow-up:** someone leaves the company and is disabled in Entra ID. How long can they still use your app? (Until their access token expires, usually 60-90 minutes, or for as long as your own session lives if you issued one. Shorten sessions, re-check the account on refresh, or react to Graph change notifications for disabled users.)
