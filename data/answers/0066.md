## Hints

- Does a `try/catch` around a call that returns a promise catch the rejection if you don't `await` it?
- What does Node do by default since v15 when a promise rejects and nobody handles it?
- Where in an Express app should errors end up, and what about errors thrown in async route handlers?

## Answer

Rules by async style:

- **async/await** – wrap awaited calls in `try/catch`; a `catch` only sees a rejection if you actually `await` the promise.
- **Promises** – always end chains with `.catch()` or return them to a caller that handles them.
- **Callbacks** – check the error-first argument (`(err, data)`); a `throw` inside an async callback cannot be caught by the outer `try`.
- **EventEmitters/streams** – listen for `'error'`; an unhandled `'error'` event throws and crashes the process.

```js
async function loadUser(id) {
  try {
    return await db.users.findById(id);
  } catch (err) {
    throw new Error(`Failed to load user ${id}`, { cause: err });
  }
}
```

**Unhandled rejections:** since Node 15 the default (`--unhandled-rejections=throw`) is to treat them like uncaught exceptions: the process **crashes** with a non-zero exit code. That's intentional: the app may be in an unknown state.

Global hooks (`process.on('unhandledRejection')`, `process.on('uncaughtException')`) should be used to **log and exit gracefully**, not to keep running as if nothing happened. Let a process manager or orchestrator (systemd, Kubernetes) restart it.

In Express 4, errors thrown in async handlers aren't forwarded to error middleware automatically (you need `next(err)` or a wrapper); **Express 5** forwards rejected promises for you.

Distinguish **operational errors** (timeout, invalid input: handle and respond) from **programmer errors** (bugs: crash and fix).
