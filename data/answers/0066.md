## Hints

- Does a `try/catch` around a call that returns a promise catch the rejection if you don't `await` it?
- Where should every error in an Express app end up, and how do you tell Express a function is the error handler?
- What does Node do by default since v15 when a promise rejects and nobody handles it, and should you override that?

## Answer

**Rules by async style:**

- **async/await** – wrap awaited calls in `try/catch`; a `catch` only sees a rejection if you actually `await` the promise.
- **Promises** – always end chains with `.catch()` or return them to a caller that handles them.
- **Callbacks** – check the error-first argument (`(err, data)`); a `throw` inside an async callback cannot be caught by the outer `try`.
- **EventEmitters/streams** – listen for `'error'`; an unhandled `'error'` event throws and crashes the process (#293).

**Express: one central error handler.** Express recognises the error middleware by its **four-argument signature** and skips to it when `next(err)` is called or a handler throws. In **Express 5** a rejected promise from an `async` handler is forwarded automatically; in Express 4 you had to `try/catch` and call `next(err)` or wrap handlers (`express-async-errors`).

```js
class HttpError extends Error {
  constructor(status, message, options) { super(message, options); this.status = status; }
}

app.get('/users/:id', async (req, res) => {
  const user = await db.users.findById(req.params.id);       // rejection -> error handler (Express 5)
  if (!user) throw new HttpError(404, 'User not found');
  res.json(user);
});

app.use((err, req, res, next) => {                           // 4 args = error handler; register it last
  const status = err.status ?? 500;
  req.log.error({ err, requestId: req.id }, 'request failed');  // log once, with the request id (#302)
  res.status(status).json({
    type: 'about:blank', title: status === 500 ? 'Internal Server Error' : err.message, status,   // #353
  });                                                           // never send err.stack to clients
});
```

**Fastify** handles `async` routes natively, has `reply.send(err)`/`throw` semantics, and a single `app.setErrorHandler((err, req, reply) => ...)`; validation errors already come with a `statusCode`. The principle is the same: throw typed errors in handlers, map them to responses in one place.

**Operational vs programmer errors.** Operational errors (invalid input, not found, timeout from a dependency, rate limited) are expected: map them to `4xx`/`503` and carry on. Programmer errors (`TypeError`, undefined variable, broken invariant) mean the process may be in a bad state: respond `500`, log, and prefer restarting over limping on.

**Unhandled rejections:** since Node 15 the default (`--unhandled-rejections=throw`) treats them like uncaught exceptions: the process **crashes** with a non-zero exit code. That is intentional. Global hooks (`process.on('unhandledRejection')`, `process.on('uncaughtException')`) should **log and exit gracefully** (close the server, finish in-flight responses, #301), not keep running as if nothing happened; let the orchestrator restart the process.

```js
async function loadUser(id) {
  try {
    return await db.users.findById(id);
  } catch (err) {
    throw new Error(`Failed to load user ${id}`, { cause: err });   // keep the original error
  }
}
```

**Follow-up:** why is `promise.catch()` attached later (e.g. after a `setTimeout`) a problem? (The rejection is already unhandled when the microtask queue drains; Node reports it before your late handler attaches.)
