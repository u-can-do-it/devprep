## Hints

- Does `await` start a new thread? What actually happens to the method when it reaches an `await` on an unfinished task?
- What does a caller get back from an `async void` method, and where does an exception thrown inside it go?
- What does `SynchronizationContext` capture, and what happens if the only thread that can run the continuation is blocked in `.Result`?

## Answer

**`async` doesn't create threads.** The compiler rewrites an `async` method into a state machine. It runs synchronously until the first `await` on an unfinished task, then returns a `Task` to the caller and registers the rest of the method as a continuation. When the awaited operation completes (often an I/O completion, with no thread waiting on it), the continuation runs, on the captured context or on a thread pool thread.

```csharp
public async Task<User> GetUserAsync(int id, CancellationToken ct)
{
    var json = await _http.GetStringAsync($"/users/{id}", ct);   // returns to the caller here
    return JsonSerializer.Deserialize<User>(json)!;              // continuation, later
}
```

**`Task` vs `ValueTask`**

| | `Task` / `Task<T>` | `ValueTask` / `ValueTask<T>` |
|---|---|---|
| Kind | class, always a heap object (cached for some results) | struct that wraps a result, a `Task` or an `IValueTaskSource` |
| Await it | as many times as you like, store it, `Task.WhenAll` | **once**, and don't block on it before it completes |
| Use for | the default for almost everything | hot paths that usually complete synchronously (e.g. a read served from a buffer or cache) |

If you need to await a `ValueTask` twice or combine it, call `.AsTask()` once. The internals are #603.

**Why avoid `async void`**

- The caller can't await it, so it can't know when it finished or whether it failed.
- An exception is raised on the captured `SynchronizationContext`, or on the thread pool if there is none, which **crashes the process** in ASP.NET Core and console apps.
- The only legitimate use is event handlers (`button.Click += async (s, e) => ...`), which must have a `void` signature. Wrap the body in `try`/`catch` there.

Watch out for lambdas: passing an `async` lambda to a parameter of type `Action` silently produces an `async void`.

**Why `.Result` and `.Wait()` can deadlock**

In an app with a single-threaded `SynchronizationContext` (WinForms, WPF, classic ASP.NET), `await` captures that context and posts the continuation back to the UI or request thread. If that thread is blocked in `.Result`, the continuation never runs and the task never completes:

```csharp
// WPF button handler
var user = GetUserAsync(1, default).Result;   // UI thread blocks; GetUserAsync's continuation waits for the UI thread
```

ASP.NET Core has no `SynchronizationContext`, so this exact deadlock doesn't happen there, but blocking still holds a thread pool thread for the whole wait. Under load that leads to **thread pool starvation** (#594). Also, `.Result` wraps exceptions in `AggregateException`, while `await` rethrows the original one.

**Rules of thumb**

- Async all the way up: make the caller `async` instead of blocking. If you truly must block (a `Main` before C# 7.1, a sync interface you can't change), use `.GetAwaiter().GetResult()` and know the risk.
- In libraries, `ConfigureAwait(false)` skips capturing the context, which avoids this deadlock for callers that block and saves a context switch. Application code in ASP.NET Core doesn't need it.
- Return the task directly (no `async`/`await`) only for trivial pass-through methods; with `using` or `try`, keep the `await` or the resource is disposed too early.
- Run independent operations concurrently with `Task.WhenAll`, not by awaiting them one by one.

**Follow-up:** is `Task.Run` a way to make a method async? (It moves CPU-bound work off the current thread, which helps a UI stay responsive. Wrapping I/O in `Task.Run` in ASP.NET Core only swaps one thread pool thread for another and adds overhead; use the real async API instead.)
