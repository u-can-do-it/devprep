## Hints

- When a modal opens, where should keyboard focus go, and where should it go when it closes?
- What should happen when the user presses Tab on the last focusable element inside the modal? And Escape?
- How do you stop a screen reader from wandering into the page behind the modal?

## Answer

A modal must behave like a separate, temporary page for keyboard and screen reader users:

1. **Move focus in on open** — to the first meaningful control or the dialog heading.
2. **Trap focus** — Tab/Shift+Tab cycle inside the dialog only.
3. **Escape closes** the dialog.
4. **Make the background inert** — not focusable, not readable by screen readers, not scrollable.
5. **Return focus** to the element that opened it when it closes.
6. **Label it** — `aria-labelledby` pointing at the title (and `aria-describedby` if useful).

**The modern way: native `<dialog>`** with `showModal()` gives you most of this for free — it renders in the top layer, makes the rest of the page inert, handles Escape, and restores focus on close in current browsers.

```jsx
function ConfirmDialog({ open, onClose, title, children }) {
  const ref = useRef(null);

  useEffect(() => {
    const dialog = ref.current;
    if (open && !dialog.open) dialog.showModal();
    if (!open && dialog.open) dialog.close();
  }, [open]);

  return (
    <dialog ref={ref} aria-labelledby="dlg-title" onClose={onClose}>
      <h2 id="dlg-title">{title}</h2>
      {children}
      <button autoFocus onClick={onClose}>Cancel</button>
    </dialog>
  );
}
```

If you build a custom modal, use the `inert` attribute on the rest of the page (e.g. the app root), handle Tab wrapping manually, and store `document.activeElement` before opening so you can restore it. Libraries like Radix UI and React Aria implement these patterns.

**General keyboard rules:** every interactive element must be reachable with Tab and operable with Enter/Space; keep DOM order = visual order; never remove focus outlines without a visible `:focus-visible` replacement; avoid positive `tabindex`; use `tabindex="-1"` to focus non-interactive targets programmatically (e.g. headings after route changes in an SPA).

**Follow-up:** for composite widgets (tabs, menus), use roving `tabindex` so Tab enters the widget once and arrow keys move within it.
