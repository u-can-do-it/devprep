## Hints

- What is the difference between the authentication middleware and the authorization middleware, and in which order must they run?
- Where do claims come from in a JWT, and how do they end up in `HttpContext.User`?
- How would you express "only the author of a document may edit it", which a role check can't?

## Answer

**Authentication** answers *who are you*: a handler (scheme) reads the request and builds a `ClaimsPrincipal` in `HttpContext.User`. **Authorization** answers *are you allowed*: it checks that principal against requirements.

```csharp
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(o =>
    {
        o.Authority = "https://login.example.com";   // downloads signing keys via OIDC discovery
        o.Audience = "orders-api";                    // the aud claim must match
    });

builder.Services.AddAuthorization(o =>
{
    o.AddPolicy("CanRefund", p => p.RequireClaim("scope", "orders.refund"));
    o.AddPolicy("Adult", p => p.Requirements.Add(new MinimumAgeRequirement(18)));
});

app.UseAuthentication();   // after routing/CORS, before authorization
app.UseAuthorization();
```

**Schemes**

| Scheme | Typical use |
|---|---|
| JWT bearer | APIs called by SPAs, mobile apps or other services; stateless, validates signature, issuer, audience and expiry |
| Cookies | server-rendered apps and BFFs; an encrypted cookie (Data Protection, #599) holds the identity |
| OpenID Connect | signs the user in at an identity provider, then usually stores the result in a cookie |

You can register several schemes and pick per endpoint (`[Authorize(AuthenticationSchemes = "...")]`).

**Claims, roles and policies**

- A **claim** is a key-value fact about the user (`sub`, `email`, `role`, `scope`).
- `[Authorize]` alone requires an authenticated user. `[Authorize(Roles = "Admin")]` checks role claims.
- **Policies** are named requirements and the recommended way: `[Authorize(Policy = "CanRefund")]` or `.RequireAuthorization("CanRefund")`. A custom requirement has an `IAuthorizationHandler` that calls `context.Succeed(requirement)`.
- Set a **fallback policy** (`o.FallbackPolicy = o.DefaultPolicy`) so endpoints are protected by default and you opt out with `[AllowAnonymous]`.

**Resource-based authorization**

Attribute checks run before your handler, so they can't see the document from the database. Load it, then ask `IAuthorizationService`:

```csharp
public sealed class DocumentAuthorHandler
    : AuthorizationHandler<OperationAuthorizationRequirement, Document>
{
    protected override Task HandleRequirementAsync(AuthorizationHandlerContext ctx,
        OperationAuthorizationRequirement req, Document doc)
    {
        if (req.Name == "Edit" && doc.AuthorId == ctx.User.FindFirstValue(ClaimTypes.NameIdentifier))
            ctx.Succeed(req);
        return Task.CompletedTask;
    }
}

var doc = await db.Documents.FindAsync([id], ct);
var result = await auth.AuthorizeAsync(User, doc, new OperationAuthorizationRequirement { Name = "Edit" });
if (!result.Succeeded) return TypedResults.Forbid();
```

This is what prevents IDOR: being logged in is not the same as being allowed to touch *this* record.

**401 vs 403:** 401 (challenge) means not authenticated or the token is invalid; 403 (forbid) means authenticated but not allowed.

**Follow-up:** the `role` claim is in the token but `[Authorize(Roles = "Admin")]` still fails. Why? (The handler maps claim types: the role claim name in the token must match `TokenValidationParameters.RoleClaimType`. Set `RoleClaimType = "role"` or turn off inbound claim mapping, then check `User.Claims` in a debugger.)
