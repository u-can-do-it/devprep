## Hints

- Why are "big bang" rewrites that replace everything on one cut-over date so risky?
- What component lets you send some requests to the new system and the rest to the old one?
- How do you handle the data that both systems need during the transition?

## Answer

The **strangler fig pattern** (named by Martin Fowler after a vine that slowly grows around a tree) replaces a legacy system **incrementally**: new functionality grows around the old system until the old system can be removed.

**How it works:**
1. **Put a facade or router in front** of the legacy app: a reverse proxy, API gateway, or edge routing (e.g. a Next.js app that proxies unknown routes to the old app).
2. **Pick a slice**: a route, page or bounded context with clear boundaries and real value, e.g. `/search` or the checkout flow.
3. **Build it in the new system** and route that traffic to it, gradually if possible: by percentage, internal users first, or behind a feature flag.
4. **Repeat** slice by slice. Remove legacy code as each part is replaced.
5. **Decommission** the old system when nothing routes to it.

```text
             +--> /search, /checkout --> new service
Client -> Router
             +--> everything else -----> legacy monolith
```

**Handling data:**
- Initially the new code may read and write the legacy DB through an **anti-corruption layer** that translates old models into clean new ones.
- Later, move ownership of data to the new service and synchronize with **change data capture** (Debezium) or events until the legacy side stops needing it.
- Avoid long periods of dual writes without reconciliation.

**Why it works:** value ships continuously, risk is small and reversible (route back to legacy), and the team learns as it goes.

**Pitfalls:** never finishing (two systems forever, double maintenance cost), choosing slices that are too entangled, and letting the router accumulate business logic. Track migration progress explicitly and plan the final shutdown.
