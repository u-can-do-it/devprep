## Hints

- Does "customer" mean the same thing to sales, billing and support?
- What's the boundary inside which a business rule must always be true, in one transaction?
- Why does DDD recommend that one aggregate references another by id rather than holding the object?

## Answer

**Domain-Driven Design** is an approach for complex business software: model the code on the business domain, built together with domain experts. It has two halves.

**Strategic design (the big picture):**

- **Ubiquitous language:** developers and domain experts use the same terms, and those terms appear in the code (`TimeOffRequest.approve()`, not `updateStatus(2)`). If the business says "accrual", the code says accrual.
- **Bounded contexts:** a model is only consistent within a boundary. "Customer" in Sales (a lead, a pipeline) differs from "Customer" in Billing (invoices, tax id). Each context has its own model, language and usually its own team or service. Microservice boundaries are best drawn along bounded contexts.
- **Context map:** how contexts relate (customer–supplier, shared kernel, an **anti-corruption layer** that translates a legacy or external model so it doesn't leak into yours).
- **Subdomains:** **core** (your competitive advantage, where you invest in modelling), **supporting**, and **generic** (buy or use a library: auth, payments).

**Tactical design (inside a context):**

- **Entities:** identity that persists over time (an `Employee`).
- **Value objects:** defined by their values, immutable, with validation (`Money`, `DateRange`, `Email`). They remove a lot of primitive-obsession bugs.
- **Aggregates:** a cluster of objects with one **root** that enforces **invariants** and is saved in **one transaction**. Outside code goes through the root only, and other aggregates are referenced **by id**.
- **Domain events:** facts that happened (`TimeOffApproved`), used to trigger work in other aggregates or contexts asynchronously, often published via an outbox.
- **Repositories** load and save aggregates; **domain services** hold logic that doesn't belong to one entity.

```ts
class TimeOffRequest {
  private constructor(readonly id: string, private status: 'pending' | 'approved' | 'rejected',
                      readonly period: DateRange, private events: DomainEvent[] = []) {}

  approve(by: ManagerId, balance: Balance) {
    if (this.status !== 'pending') throw new DomainError('Only pending requests can be approved');
    if (!balance.covers(this.period)) throw new DomainError('Insufficient balance');   // invariant
    this.status = 'approved';
    this.events.push({ type: 'TimeOffApproved', requestId: this.id, by });
  }
}
```

**When it's worth it:** rules-heavy domains (HR policies, insurance, logistics, finance) with real business complexity and access to domain experts. **Not worth it** for CRUD apps or simple integrations; the tactical patterns add ceremony without value there. Many teams use the strategic ideas (language, bounded contexts) everywhere and the tactical ones only in the core domain.
