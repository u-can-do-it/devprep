## Hints

- How would you express "editors can edit documents" vs "users can edit documents they own, during business hours, in their own region"?
- What happens to a role-based system when every customer wants slightly different permissions?
- How would you answer "who can see this folder?" when permissions are inherited from parents and teams?

## Answer

**RBAC (role-based)**: permissions are grouped into roles (`viewer`, `editor`, `admin`), and users get roles, often per tenant (`alice is admin in org 7`). Simple to understand, audit and display in a UI. Weakness: **role explosion** when you need fine-grained or contextual rules ("editor-but-only-EU-billing").

**ABAC (attribute-based)**: decisions come from policies over attributes of the **subject** (department, clearance), **resource** (owner, classification, tenant), **action**, and **environment** (time, IP, MFA used). Very expressive, but harder to reason about and audit ("why was this denied?"). Often implemented with a policy engine (OPA/Rego, Cedar).

**ReBAC (relationship-based)**: permissions come from a graph of relationships: "user is member of team, team is editor of folder, document is in folder". Popularized by Google Zanzibar (OpenFGA, SpiceDB). Great for sharing and nested structures like Google Drive or GitHub orgs.

For a typical multi-tenant SaaS:

- Start with **tenant-scoped RBAC**: `memberships(user_id, org_id, role)`. Every query is filtered by `org_id`.
- Add **ABAC-style conditions** for ownership and context ("members can edit their own drafts").
- Move to **ReBAC** if you get sharing, folders and inheritance.
- Keep authorization behind a single interface, so the model can change without touching every handler:

```ts
type Action = 'read' | 'update' | 'delete';
function can(user: User, action: Action, doc: Doc): boolean {
  const role = user.roles[doc.orgId];
  if (!role) return false;                       // tenant isolation
  if (role === 'admin') return true;
  if (action === 'read') return true;
  return role === 'editor' || doc.authorId === user.id;
}
```

Check permissions in the backend on every request; the frontend only hides buttons.

**Follow-up:** How do you support list endpoints efficiently? Turn the policy into query filters (or use the engine's "list objects" API) instead of loading everything and checking each row.
