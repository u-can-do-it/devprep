## Hints

- Which operation type is meant to read data, and which to change it?
- Why might the execution order of top-level fields differ between the two?
- What transport is usually needed for real-time updates?

## Answer

GraphQL has three operation types:

- **Query** – read-only fetch. Top-level fields may be resolved **in parallel**.
- **Mutation** – changes data and returns the updated result. Top-level fields run **sequentially**, in order, so `createUser` then `addToTeam` is predictable.
- **Subscription** – a long-lived operation where the server **pushes** results when an event happens (new message, order status change). Usually over WebSockets (`graphql-ws` protocol) or SSE.

```graphql
query GetPost($id: ID!) {
  post(id: $id) { title author { name } }
}

mutation AddComment($input: AddCommentInput!) {
  addComment(input: $input) { id text }
}

subscription OnComment($postId: ID!) {
  commentAdded(postId: $postId) { id text }
}
```

**Good practices:**

- Use **variables** instead of string interpolation (safer, cacheable, works with persisted queries).
- Mutations take a single `input` object and return a payload with the changed entity so clients can update their cache.
- Use subscriptions sparingly – for many cases, polling or refetching after a mutation is simpler and cheaper to scale.

**Follow-up:** Could you technically change data in a query resolver? Yes, but you break the contract – clients, caches and tooling assume queries are side-effect free.
