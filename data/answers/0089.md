## Hints

- Who is responsible for loading data into the cache on a miss: the application or the cache layer?
- Is the cache updated before, at the same time as, or after the database on writes?
- Which strategy risks losing writes if the cache node crashes?

## Answer

**Cache-aside (lazy loading)** – the most common. The app checks the cache; on a miss it reads the DB and populates the cache with a TTL. On writes, update the DB and **delete** the cache key.

```python
async def get_user(user_id: int) -> dict:
    key = f"user:{user_id}"
    if (cached := await redis.get(key)) is not None:
        return json.loads(cached)
    user = await db.fetch_user(user_id)
    await redis.set(key, json.dumps(user), ex=300)
    return user
```

Pros: only caches what's requested, cache failure isn't fatal. Cons: first request is slow, possible stale data, app code handles caching logic.

**Read-through** – like cache-aside, but the **cache layer/library** loads from the DB on a miss. Cleaner app code; needs a cache that supports loaders.

**Write-through** – writes go to the cache **and** the DB synchronously. Cache is always fresh for written data; adds write latency and may cache data that's never read.

**Write-behind (write-back)** – writes go to the cache and are **flushed to the DB asynchronously** in batches. Very fast writes and absorbs spikes, but risk of **data loss** and harder consistency.

**Refresh-ahead** – proactively refresh hot keys before they expire.

Choosing: read-heavy APIs → cache-aside with TTL; data that must be fresh right after writes → write-through; write-heavy counters/metrics where small loss is acceptable → write-behind.

Always consider: TTLs, eviction policy (LRU/LFU), what's safe to serve stale, and invalidating rather than updating on writes to avoid race conditions.
