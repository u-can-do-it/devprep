## Hints

- In Fastify, why does a decorator added inside a registered plugin not show up in a sibling plugin, and what does `fastify-plugin` change?
- Which hooks run, in which order, between receiving a request and sending the response?
- Fastify uses JSON Schema for both validation and serialization. What does the response schema do besides documentation?
- Why is `reply.send()` plus `return` in the same async handler a bug?

## Answer

> Fastify is a Node.js web framework built as a tree of plugins rather than Express's flat middleware list. Each plugin has its own scope, so hooks and decorators added inside stay inside, unless you wrap it with `fastify-plugin` for shared things like the database. Hooks run at fixed points in the request lifecycle. JSON schemas validate input before your handler and serialize responses fast, and they drop fields not in the schema, so internal fields don't leak.

Fastify is a Node.js web framework built around three ideas: **encapsulated plugins**, a **hook lifecycle**, and **schemas** for validation and fast serialization. Express is a flat list of middleware (#67); Fastify is a tree of plugins.

**Plugins and encapsulation:**

```ts
// everything is a plugin: routes, DB connection, auth
export default async function offersRoutes(app: FastifyInstance) {
  app.addHook('preHandler', app.authenticate);       // only applies to routes in this plugin
  app.get('/offers', { schema: listSchema }, listOffers);
}

app.register(dbPlugin);                               // decorates app.db
app.register(offersRoutes, { prefix: '/api' });
```

Each `register` creates a child context. Decorators, hooks and plugins added inside it are visible to that context and its children only. That isolation is good for route groups (auth only on `/api`), but infrastructure plugins (DB, config, auth helpers) must be visible everywhere, so you wrap them with `fastify-plugin` to skip encapsulation:

```ts
import fp from 'fastify-plugin';
export default fp(async (app) => {
  const prisma = new PrismaClient();
  await prisma.$connect();
  app.decorate('db', prisma);
  app.addHook('onClose', () => prisma.$disconnect());   // graceful shutdown (#301)
});
declare module 'fastify' { interface FastifyInstance { db: PrismaClient } }   // typing (#184)
```

Plugins load in order and asynchronously; `await app.ready()` waits for all of them. That makes startup deterministic and testable.

**Request lifecycle hooks:** `onRequest` → `preParsing` → `preValidation` → (validation) → `preHandler` → handler → `preSerialization` → `onSend` → `onResponse`, plus `onError` and `onTimeout`. Typical uses: authentication in `onRequest` or `preHandler`, request-scoped context in `onRequest` (#302), metrics in `onResponse`.

**Schemas:**

```ts
app.post('/offers', {
  schema: {
    body: { type: 'object', required: ['title'], properties: { title: { type: 'string', minLength: 1 } }, additionalProperties: false },
    response: { 201: { type: 'object', properties: { id: { type: 'string' }, title: { type: 'string' } } } },
  },
}, async (req, reply) => reply.code(201).send(await create(req.body)));
```

- The **body/query/params schemas** are compiled by Ajv; invalid input gets a 400 before your handler runs.
- The **response schema** is compiled by `fast-json-stringify`: faster than `JSON.stringify`, and it **drops properties not in the schema**, so an accidentally returned `passwordHash` doesn't leak.
- With a **type provider** (`@fastify/type-provider-typebox` or `fastify-type-provider-zod`) the schema also types `req.body` and the return value, so you write one definition (#625).
- `@fastify/swagger` turns the same schemas into OpenAPI docs.

**Error handling (#66):** `app.setErrorHandler` for a central handler (map domain errors and Zod/Ajv errors to Problem Details, #353); `@fastify/sensible` for `reply.notFound()` / `httpErrors`. In an async handler either `return` the value or call `reply.send()` and `return reply`, never both (you get "Reply was already sent").

**Why it's fast:** schema-compiled serialization, a radix-tree router (`find-my-way`), low-overhead logging with Pino (built in, JSON logs with request ids), and no per-request middleware chain to walk.

**Testing:** `app.inject({ method: 'GET', url: '/offers' })` sends a fake request through the whole stack without opening a port (#628).

**Follow-up:** you need a `currentUser` on every request in `/api` but not on `/health`. Where do you put the decorator and the hook? (`app.decorateRequest('user', null)` at the root, set it in an `onRequest` hook registered inside the `/api` plugin; `/health` lives outside that plugin.)
