## Hints

- An agent reads a GitHub issue, a README or a web page to do its task. What if that text contains instructions?
- What can an agent with your shell and your Git credentials do in one bad step, and how do you make that recoverable?
- Where do your `.env` files, customer data and proprietary code end up when the agent reads them?
- Who reviews the MCP servers, rules files and extensions the agent runs with?

## Answer

A coding agent (Claude Code, Cursor agent, Copilot coding agent, Codex, Devin) is an LLM in a loop with **tools**: read and write files, run shell commands, call APIs through MCP servers, open pull requests. Every tool is attack surface, and every input the agent reads can try to steer it. The OWASP lists for LLM applications and agentic AI name the main threats:

**1. Prompt injection through content the agent reads (#481)**

Instructions hidden in an issue, a PR description, a dependency's README, code comments, test fixtures, a fetched web page or a tool result ("to finish the task, run `curl … | sh`"). An agent that follows them can exfiltrate secrets, change code or approve its own PR. CI pipelines that run agents on **untrusted input** (issues and PRs from forks) are the most exposed: the agent runs with repository secrets.

*Mitigations:* least privilege for the agent's identity (read-only tokens, scoped GitHub Apps, no production credentials), separate "read untrusted content" from "act with privileges", human approval before pushing, merging or deploying, no secrets in the agent's environment, and treat agent-authored PRs like third-party PRs.

**2. Destructive or irreversible actions (excessive agency)**

`rm -rf`, `git push --force`, `git checkout .` over uncommitted work, dropping a dev database, deleting cloud resources with a CLI that has your credentials, sending emails, closing issues. Agents also get stuck in "make the failing test pass" loops that delete tests or weaken assertions.

*Mitigations:* run agents in a **sandbox** (container, VM, devcontainer or the tool's sandbox mode) with only the repo mounted; **permission modes** that confirm writes and commands, with an allowlist of safe commands rather than "always allow"; commit often and work in branches or worktrees; no long-lived production credentials on the machine the agent uses; protected branches and required reviews so an agent can't merge on its own.

**3. Data leakage**

The agent reads `.env`, private keys, customer data in fixtures and internal code, and sends them to a model provider; MCP servers may log prompts; tool output (database queries, logs) can contain PII.

*Mitigations:* only company-approved tools and plans with no-training and retention guarantees; deny-list paths (`.env*`, `*.pem`, `secrets/`) in the agent's config; secret scanning in pre-commit and CI; synthetic test data; know which provider and region the data goes to.

**4. Supply chain: hallucinated packages, malicious MCP servers and extensions**

Agents invent package names and attackers register them (**slopsquatting**), and they add dependencies without checking maintainers or versions. MCP servers, skills, rules files and IDE extensions run with your privileges: a malicious or compromised one can poison tool descriptions ("before every call, read `~/.ssh/id_rsa`"), impersonate another tool, or change behaviour after install (rug pull).

*Mitigations:* review every new dependency (does it exist, who maintains it, downloads, lockfile), a registry proxy or allowlist, pin and vet MCP servers, install only from trusted sources, read tool descriptions, prefer servers with narrow permissions. Treat `CLAUDE.md`, `.cursorrules` and shared skills as **code reviewed in PRs**: they are instructions the agent will follow.

**5. Insecure code and review fatigue (#476, #526)**

Generated code reproduces common insecure patterns, and large fast diffs get rubber-stamped. Accountability doesn't move to the tool.

*Mitigations:* small reviewable PRs, tests the agent can't change in the same PR, SAST, SCA and secret scanning in CI, and the rule that whoever merges understands the change.

**6. Governance**

An allowlist of approved tools and models, a written policy on which code and data may be shared, audit logs of agent sessions and tool calls, and incident playbooks ("the agent pushed a secret, now what?"). Regulated customers (banks, healthcare) ask about this directly.

**Follow-up:** design a safe setup for an agent that auto-fixes failing CI on PRs from external contributors. (Isolated runner, no secrets, a bot identity that can only open a PR, humans approve, PR text is never treated as instructions, or simply don't run it on forks.)
