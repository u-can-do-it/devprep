## Hints

- Where do you start: the code, the data model, the people or the running system?
- How can an agent speed up getting to know a codebase, and which of its claims do you still have to verify?
- What makes a good first change to ship?

## Answer

**Goal for the first week:** run the system, understand its main flows and its domain language, and ship one small change to production through the real pipeline.

**1. Run it and get access**

- Get the app running locally and run the tests. Note every gap in the README as you go; fixing it is a useful first PR.
- Get access to logs, APM, error tracking, CI and the issue tracker.

**2. Build a map, top-down**

- Ask someone for a 30-minute whiteboard tour: services, databases, queues, external providers, who owns what.
- Read the architecture docs and decision records (ADRs), even if outdated: they tell you why things are the way they are.
- **Read the data model:** the core tables and their relations explain the business better than controllers do.

**3. Follow real requests end to end**

- Pick the two or three most important flows (here: booking a consultation, joining a video call, issuing a prescription) and trace them from the UI through the API, database and queue consumers.
- Use real traces from the APM tool to see what actually happens, including the calls nobody documented.

**4. Learn the history and the risks**

- `git log` and blame on the most-changed files show where the complexity and the bugs live.
- Recent postmortems show how the system fails.
- Ask what everyone is afraid to touch.

**5. Learn the domain language** (#486): appointment vs consultation, referral, prescription, sick leave, the insurer's terms. Using the business's words makes conversations with stakeholders much easier.

**6. Map the stack onto what you know.** Frameworks share the same concepts: routing, middleware, dependency injection, an ORM with migrations, background jobs, configuration. Find where each lives in this stack and what the framework does under the hood. That's how you become productive in a new language within a week.

**With coding agents:**

- Ask them to explain a module, trace a flow, list where something is implemented, or draft a map of the repo. That's much faster than grepping alone.
- Ask them to write characterisation tests before you change legacy code.
- **Verify their claims** by reading the code and running it: in a large legacy codebase agents confidently describe structure that isn't there.
- Write what you learn into the repo's agent context and docs (#541), so the next person and the next agent start faster.

**7. Ship something small for real:** a bug fix, a missing log, a test, a small UX fix. The point is to go through review, CI, deploy and monitoring once, and to learn the team's standards.

**8. Keep a list of what surprised you.** Fresh eyes see friction the team no longer notices; after a few weeks, those notes turn into improvements (#558).

**On a trial day** they watch how you orient yourself, what you ask, how you use agents and whether you verify their output, and how you communicate what you did and didn't finish. Asking good questions early beats guessing silently.

**Follow-up:** after a month you think a core module should be rewritten. How do you approach it? (Gather evidence: bugs, change cost, incidents. Understand why it's built that way, propose incremental steps such as the strangler fig pattern (#425) instead of a big rewrite, and agree with the owners.)
