## Hints

- JS runs on one thread, so where do `setTimeout` callbacks wait until they can run?
- After a task finishes, which queue is drained completely before the next task starts?
- What will `setTimeout(..., 0)` vs `Promise.resolve().then(...)` print first?

## Answer

JavaScript runs code on a **single call stack**. Async work (timers, I/O, network) is handled by the host environment (browser or Node/libuv). When that work finishes, its callback is put in a queue. The **event loop** moves callbacks onto the stack whenever the stack is empty.

**Two kinds of queues:**

- **Macrotasks (tasks):** `setTimeout`, `setInterval`, I/O, UI events, `MessageChannel`, `setImmediate` (Node).
- **Microtasks:** promise callbacks (`then`/`catch`/`finally`, code after `await`), `queueMicrotask`, `MutationObserver`.

**Loop order:** run one macrotask, then **drain the whole microtask queue**, including microtasks added during draining. In the browser, the page may then render (`requestAnimationFrame`, then layout and paint). Then the next macrotask runs.

```js
console.log('1');
setTimeout(() => console.log('2'), 0);
Promise.resolve().then(() => console.log('3'));
queueMicrotask(() => console.log('4'));
console.log('5');
// 1 5 3 4 2
```

**Consequences:**

- Microtasks always run before the next timer, even a 0 ms one.
- A microtask that keeps scheduling more microtasks **starves** the loop. Rendering and timers never get a turn.
- Long synchronous work blocks everything. Split it into chunks, use `scheduler.yield()` where supported, or move it to a Web Worker.

**Node specifics:** the loop has phases (timers → poll → check → close). `process.nextTick` callbacks run before promise microtasks. Inside an I/O callback, `setImmediate` runs before `setTimeout(0)`.

**Follow-up:** predict the output of mixed `async`/`await` and `setTimeout` code. The code after an `await` runs as a microtask.
