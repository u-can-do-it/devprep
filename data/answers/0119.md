## Hints

- If the counter lives in each instance's memory, what happens behind a load balancer with 10 instances?
- Should you limit per IP, per account, or both – and what does each miss?
- How do you slow attackers down without letting them lock real users out?

## Answer

**Threats:** brute force on one account, **credential stuffing** (leaked password lists across many accounts, often from botnets with many IPs), and **password spraying** (one common password against many accounts).

**Where to enforce:** layered – edge/WAF/API gateway for coarse IP limits, plus application logic for account-aware limits. Counters must live in a **shared store** (Redis) so all instances see the same state.

**Algorithms:**

- **Fixed window** – simple, but bursty at window boundaries.
- **Sliding window log/counter** – smoother and accurate.
- **Token bucket** – allows bursts up to capacity, refills at a steady rate; common for APIs.

Use atomic operations (Lua script or `INCR` + `EXPIRE`) to avoid race conditions:

```python
async def allow(redis, key: str, limit: int, window_s: int) -> bool:
    count = await redis.incr(key)
    if count == 1:
        await redis.expire(key, window_s)
    return count <= limit

# per account and per IP, checked before verifying the password
ok = await allow(r, f"login:acct:{email_hash}", 10, 900) and \
     await allow(r, f"login:ip:{ip}", 100, 900)
```

**Login-specific controls:**

- Limit by **account** (stops targeted brute force) *and* by **IP / subnet / device fingerprint** (stops spraying).
- **Progressive delays / exponential backoff** rather than hard lockouts – hard lockouts let attackers DoS real users.
- **Step-up challenges** (CAPTCHA, proof-of-work) after suspicious signals.
- **MFA/passkeys** make stolen passwords far less valuable; check passwords against breach lists.
- Return the **same response and timing** for unknown user vs wrong password (prevent enumeration).
- Respond with `429 Too Many Requests` + `Retry-After` for API clients.
- **Monitor and alert** on spikes in failures; log for incident response.

**Trade-offs to mention:** NAT/corporate IPs share addresses (limits too strict hurt many users), IPv6 needs limiting per prefix, Redis outage handling (fail open vs closed), and the extra latency of a shared store.
