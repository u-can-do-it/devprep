## Hints

- What does `uses: some/action@v3` actually point to, and can its owner change what it points to?
- What can a malicious `postinstall` script in a transitive dependency access on a CI runner?
- How can a consumer verify that an artifact was built from a specific commit by your pipeline?

## Answer

The CI pipeline is a prime target: it has write access to registries, cloud credentials, and runs third-party code. The compromised `tj-actions/changed-files` action (2025) was retagged to malicious code that printed CI secrets into build logs, so every workflow referencing it by tag ran the attacker's code.

**1. Lock down third-party code that runs in the pipeline**
- Pin actions to a **full commit SHA**, not a mutable tag. Let Renovate or Dependabot update the pins.
- Restrict which actions are allowed (organization allowlist) and prefer official or verified ones. Vendor or fork rarely updated ones.
- Dependencies installed during builds are the other half of the problem: lockfiles, `npm ci`, and dependency scanning.

**2. Least privilege**
- Default `permissions: contents: read` on the `GITHUB_TOKEN`. Grant more per job.
- **OIDC** short-lived cloud credentials instead of stored keys. Protected environments for deploys.
- Never run untrusted PR code with secrets (`pull_request_target` combined with checking out the PR head is a classic hole). Watch for script injection from `${{ github.event.* }}` interpolated into `run:` blocks.
- Use ephemeral runners. Never reuse self-hosted runners for public repos.

**3. Integrity and provenance**
- Generate **SLSA provenance** and attestations (`actions/attest-build-provenance`, `npm publish --provenance`, npm trusted publishing via OIDC).
- **Sign images** (Sigstore cosign) and enforce signature verification at deploy time with an admission policy (Kyverno, Sigstore policy-controller).
- Produce an SBOM for each release.

**4. Protect the source**
- Branch protection or rulesets, required reviews (including on `.github/workflows/**` via CODEOWNERS), signed commits, and secret scanning with push protection.

```yaml
# pin to the full 40-character commit SHA; the comment records the version
- uses: actions/checkout@<full-commit-sha> # v4.x.y
```

**Follow-up:** "How would you respond to a compromised dependency?" Identify affected builds from SBOMs and logs, rotate every credential the runner could reach, rebuild from clean pins, and audit for published artifacts.
