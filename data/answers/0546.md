## Hints

- Can you explain in one sentence what problem it solved and for whom?
- What went wrong while you built it, and how did you find out?
- How do you know it works, beyond "I tried it a few times"?

## Answer

Companies hiring for agentic engineering ask you to **show** something you built: an MCP server, an agent workflow, a repo set up for agents, an automation that people really use. They're testing judgement, not the demo. Prepare a 5-minute version and be ready to go deep for 30.

**Structure**

1. **Problem and users:** what was slow, manual or error-prone, who had the problem, and why an agent or automation rather than a script or a plain API call.
2. **Architecture:** a simple diagram (trigger, model, tools or MCP servers, data sources, where it runs, where results go). Name the model and why you chose it.
3. **Key decisions and trade-offs:** workflow vs agent (#480), how tools are shaped (#542), how context is supplied, what's deterministic code and what's left to the model, cost per run.
4. **Guardrails:** permissions, read-only vs write tools, human approval, secrets handling, prompt-injection exposure (#525).
5. **Failure modes you hit and how you fixed them:** loops, wrong tool choice, hallucinated fields, context overflow, flaky external APIs. This is the most convincing part; nothing works on the first try.
6. **Evaluation:** a set of test cases, what "correct" means, success rate and how it changed with your fixes (#482, #543).
7. **Results:** usage and impact in numbers (time saved per week, tickets triaged, errors caught), and what people said.
8. **What you'd change** with more time, and what you'd never do again.

**Example outline:** "Our on-call engineers spent about 20 minutes per alert collecting context. I built a read-only MCP server over our logs, deploys and runbooks, plus an agent that posts a summary with links into the alert's Slack thread. First version: the agent pulled 30k log lines and ran out of context, so I changed the log tool to return grouped errors with counts. It also blamed every incident on the latest deploy, so I made it compare with the hour before and cite evidence. On 25 past incidents it found the right area in 19. Now it runs on every alert; on-call says triage takes about 5 minutes. Next I'd add a feedback button to collect more eval cases."

**Good projects for this kind of role:**

- An MCP server for an internal system or a narrower, safer wrapper over a vendor API.
- A repository prepared for agents (`CLAUDE.md`, skills, hooks, permissions) with a before/after measurement (#541).
- An agent that triages errors or alerts into tickets with evidence and a suggested fix.
- A CI agent: fix lint failures, update dependencies, review PRs, with guardrails.
- An n8n or code workflow that removed a manual business process (#547).
- An eval harness for prompts or agent setups.

**Questions to expect:** What did the agent get wrong most often? What does a run cost? What happens when the model or an API changes? How do you stop prompt injection? Why not just a script? Who maintains it now? Can you show the code and a real transcript?

**Pitfalls:** a demo with no users or no numbers, not knowing the cost, "the AI handles it" without explaining what code enforces, hiding failures, and code you can't explain because the agent wrote it.

**Follow-up:** if you had to rebuild it for 10× more users, or for patient data, what would change? (#548, #556)
