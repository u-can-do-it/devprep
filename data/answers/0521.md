## Hints

- What happens to a login form, a search endpoint or an LLM proxy if one client can call it a thousand times a second?
- Which status code and headers tell a client to slow down, and what should a well-behaved client do with them?
- Is a limit per IP enough when a whole office shares one address, or when one attacker has thousands of them?

## Answer

**Rate limiting** caps how many requests a client may make in a time window (e.g. 100 requests/min per API key). It protects against brute force and credential stuffing, scraping, abuse of expensive endpoints (search, exports, LLM calls, email/SMS sending), noisy neighbours in a multi-tenant system, and accidental overload from a buggy client stuck in a retry loop. It is not a full DDoS defence (that's the CDN/WAF's job), but it limits the damage.

**Related terms:** *throttling* slows or queues requests instead of rejecting them; *quotas* are long-window limits (10k requests per month per plan); *circuit breakers* protect your own outgoing calls to a failing dependency.

**What to limit by:** per user/API key (fair, but needs auth), per IP (works before login, but offices and mobile carriers share IPs and attackers rotate them), per endpoint (login, password reset and checkout get tighter limits), and per tenant. Usually layered: coarse IP limits at the edge, fine-grained per-identity limits in the gateway or app.

**Algorithms, one line each:** fixed window (simple, bursty at window boundaries), sliding window (smoother), token bucket (steady rate with controlled bursts, the usual default), leaky bucket (constant output rate). With more than one instance, counters must live in a shared store (Redis) and be incremented atomically (#119, #142).

**Server response:**

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 30
RateLimit-Limit: 100
RateLimit-Remaining: 0
RateLimit-Reset: 30
```

Return `429` (not `403` or `503`), say when to retry, keep the body small. The `RateLimit-*` headers follow an IETF draft whose newer revisions fold them into `RateLimit: limit=100, remaining=0, reset=30` plus `RateLimit-Policy: 100;w=60`; many APIs still send `X-RateLimit-*`. For browser clients on another origin, expose them with `Access-Control-Expose-Headers: Retry-After, RateLimit`, otherwise `res.headers.get()` returns `null` (#110). On login endpoints don't reveal which rule fired or whether the account exists. Log and alert on spikes.

**Client behaviour (frontend or a calling service):**

- Respect `Retry-After`; otherwise retry with **exponential backoff and jitter** (1 s, 2 s, 4 s… plus a random offset) and a cap on attempts, so many clients don't retry in lockstep (thundering herd).
- Only retry **idempotent** requests automatically. For a `POST` payment, use an idempotency key (#356) or ask the user.
- Reduce the request rate at the source: debounce search inputs, batch requests, cache responses, don't poll when SSE/WebSockets are available.
- Show a clear message ("Too many attempts, try again in 30 s") instead of a generic error, and never retry a login silently.

```ts
async function fetchWithBackoff(url: string, init?: RequestInit, attempts = 4): Promise<Response> {
  for (let i = 0; ; i++) {
    const res = await fetch(url, init);
    if (res.status !== 429 || i === attempts - 1) return res;
    const retryAfter = Number(res.headers.get('Retry-After'));
    const delay = retryAfter ? retryAfter * 1000 : 2 ** i * 1000 + Math.random() * 500;
    await new Promise((r) => setTimeout(r, delay));
  }
}
```

**Pitfalls:** limiting per IP only (locks out an office, misses botnets), hard account lockouts that let attackers lock out real users, counters kept in process memory behind a load balancer, and forgetting expensive-but-rare endpoints (export, report generation).

**Follow-up:** your frontend calls a third-party API limited to 10 requests/s. How do you stay under it? (Move the calls behind your backend and queue/throttle there, or a client-side token bucket plus caching.)
