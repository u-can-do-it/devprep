## Hints

- What is the event loop doing while a synchronous file read is waiting on the disk?
- At what point in a program's life does blocking not matter?
- How would you read a 5 GB log file?

## Answer

All three read a file, but they behave differently on the event loop:

- **`fs.readFileSync`** blocks the main thread until the read finishes. No other request, timer or callback runs meanwhile.
- **`fs.readFile(path, cb)`** hands the work to libuv's thread pool and calls the callback later. This is the classic callback style.
- **`fs/promises`** (`import { readFile } from 'node:fs/promises'`) is the same non-blocking work with a promise API. It's the modern default with `async`/`await`.

```js
import { readFile } from 'node:fs/promises';
import { readFileSync, createReadStream } from 'node:fs';

const config = JSON.parse(readFileSync('./config.json', 'utf8')); // OK: startup

app.get('/report', async (req, res) => {
  const data = await readFile('./report.csv', 'utf8');   // non-blocking
  res.send(data);
});

createReadStream('./huge.log').pipe(res);                  // big files: stream
```

**Sync is acceptable** at startup (loading config or certificates before the server listens), in CLI tools and build scripts, and in one-off scripts. It's a bug inside request handlers in a server, where one slow disk read stalls every user.

Pitfalls:

- `readFile` loads the **whole file into memory**. Use streams for large files.
- Don't check `fs.exists`/`access` and then open the file: that's a race (TOCTOU). Just open it and handle `ENOENT`.

**Follow-up:** Why can heavy `fs` use slow down DNS lookups or `crypto.pbkdf2`? (They share libuv's thread pool, 4 threads by default.)
