## Hints

- Can you still do the task when the tool is unavailable or wrong, and how would you know?
- What is the difference between asking AI to do something and asking it to teach you?
- What does a junior miss if the agent writes every first version for them?

## Answer

> Interviewers want to hear that you choose when to use AI, not that you use it for everything or refuse it. Skip it when you can't verify the result, when the data may not leave the company, when you're learning a fundamental for the first time, or when typing the change is faster than describing it. Keep your skills by understanding every diff you ship, forming your own hypothesis before you ask, and sometimes working without it. With juniors, use AI as a tutor and make them explain their own PRs.

**When not to use it, or only as an assistant**

| Situation | Why |
|---|---|
| You can't verify the output | you'd be shipping something you can't judge (#476) |
| Secrets, customer data, client code outside approved tools | policy and law, not preference (#664) |
| Learning a fundamental for the first time | struggling with it is how it sticks; ask for explanations, write it yourself |
| Architecture and trade-off decisions | use it to list options and attack your idea; the decision and the responsibility are yours |
| Security-critical or money logic | only with a line-by-line read and tests you designed |
| A three-line change you already see | typing is faster than prompting and reviewing |
| The agent is looping | after two failed attempts, stop and think or debug by hand (#545) |
| The task is vague | AI will fill the gaps with confident guesses; clarify first |

**How skills erode:** you stop reading diffs closely because they usually work. You lose the mental model of the system because you never traced it yourself. You can't debug without the tool. And you may not notice: in a 2025 randomized study by METR, experienced open-source developers were slower with AI tools on their own repositories while believing they were faster. Feeling productive is not a measurement.

**Habits that keep you sharp**

- **Understand what you ship.** For every diff, be able to explain why it's correct and what would break it. If you can't, you aren't done.
- **Think first.** Write your own hypothesis or design in two or three lines before asking. Then compare. You keep the skill, and you catch the tool when it's wrong.
- **Ask it to teach:** "explain why this works", "what are the alternatives", "quiz me on this module", not just "fix it".
- **Read the code and the docs,** not only the summary.
- **Do some things by hand on purpose:** a bug now and then without the agent, a kata, the first version of something in a technology you're learning.
- **Review seriously.** Reviewing other people's and agents' code is now the main way most developers exercise judgement.

**Juniors and teams**

- A junior with an agent can produce a senior-looking diff without understanding it. Ask them to **explain the PR**: why this approach, what was rejected, what happens on failure.
- Encourage **tutor mode**: ask for hints and explanations before solutions.
- Pair on debugging and design, where judgement is learned.
- Agree on team norms: disclose significant AI use, the author is accountable for the code, and there are tasks where people are expected to work it out themselves.
- Don't give juniors only the leftovers the agents can't do. They still need a path through progressively harder work.

**Example answer** (replace with your own)

> "I use an agent every day, mostly for implementation with tests and for exploring code I don't know. I don't use it for the decision itself: on our last feature I wrote the data model on paper first and then asked the agent to find problems with it. I also don't use it when I'm learning. When we adopted a new state library I built the first slice by hand and only then delegated the rest. And once a week or so I debug something without it, because I noticed I was reaching for the agent before reading the stack trace. With the junior on my team, the rule is that he explains every PR to me before I review it."

**What not to say:** "I use it for everything" (who checks it?), "I don't trust it, so I don't use it" (that reads as not keeping up), or "skills don't matter any more" (they matter most when the tool is wrong).

**Follow-up:** you notice a colleague merging agent-written code they can't explain. What do you do?
