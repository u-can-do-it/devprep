## Hints

- An installed app has two layers. Which one can be replaced without the store?
- What happens if new JavaScript calls a native module that the installed binary doesn't contain?
- What do the store rules say about changing an app after review?

## Answer

> An app is a native binary plus a JavaScript bundle and assets. An over-the-air update replaces only the bundle and assets: the app downloads a newer compatible bundle from your update server and runs it on the next launch. It can't change native code, native dependencies or permissions. Each update targets a runtime version, so it reaches only binaries it is compatible with. Roll it out in stages, watch crash rates, keep a rollback ready, and use it for fixes and small changes, which is what the stores allow.

**How it works** (EAS Update with `expo-updates`)

1. You publish an update: the JS bundle and assets are uploaded, with metadata.
2. On launch (or on your trigger), the app asks the server: is there a newer update for my **runtime version** and **channel**?
3. It downloads the new bundle and only the assets it doesn't have yet.
4. The update is applied on the next cold start, or immediately if you reload the app from code.
5. If the new bundle crashes at launch, the library falls back to the previous working one.

**What it can and can't change**

| Can | Can't |
|---|---|
| JavaScript and TypeScript code | native code (Swift, Kotlin, C++) |
| styles, texts, navigation | adding or upgrading a library with native code |
| images and other bundled assets | permissions, app icon, app name, splash screen |
| | the React Native or Expo SDK version |

**Runtime version: the compatibility contract**

An update must only reach binaries with the same native side. If JS calls a native method that isn't in the installed binary, the app crashes.

- Every build has a runtime version, and every update is published for one.
- Policies: tie it to the app version, or to a **fingerprint**, a hash of everything that affects native code. With a fingerprint, any native change produces a new runtime version automatically.
- After a native change you need a store release. Updates for the old runtime still go to old binaries.

**Channels**

Builds point to a channel (`production`, `staging`, `preview`). You publish to a branch and map channels to branches, so the same tested update can be promoted from staging to production without rebuilding.

```bash
eas update --channel production --message "Fix checkout total rounding"
```

**Rolling out safely**

- Test the update on a **release build with the same runtime**, not only in development.
- Start with a percentage of users and increase it.
- Tag crash reports with the update id, and compare crash-free rates (#687).
- Roll back by republishing the previous update or returning to the bundle embedded in the binary.
- Sign updates (code signing), and restrict who can publish to production.
- Upload source maps for each update.

**When the update is applied**

- Default: download in the background, apply on the next launch. Simple, but a fix takes two launches to arrive.
- Check when the app returns to the foreground, for long-lived sessions.
- For a critical fix: download, then show "Updating…" and reload, or block with a short update screen. Don't reload under a user in the middle of a form.

**Store rules**

Apple and Google allow apps to download interpreted code, as long as it doesn't change the app's main purpose or add features that would bypass review. Bug fixes, text and layout changes and small improvements are fine. Shipping a different product through an update risks removal.

**Limits to be honest about**

- It doesn't replace store releases: native changes still go through review.
- You now have a matrix: several binaries in the wild, each with its own latest update.
- Not every user gets it. People with no connection at launch keep running the old bundle.
- A bad update reaches users faster than a bad store release. Treat it like a production deploy, with the same care.

**Services**

EAS Update is the common choice, and `expo-updates` can also talk to a self-hosted server that implements its protocol. Microsoft's hosted CodePush ended with App Center in 2025; self-hosted versions exist.

**Follow-up:** you published an update that calls a new native module, and old binaries crash on launch. What went wrong, and how do you prevent it? (The update was published for a runtime that doesn't contain the module. Use a fingerprint-based runtime version so native changes can't share a runtime, and let the automatic fallback and a rollback limit the damage.)
