## Hints

- Is the effect synchronizing with something *outside* React, or just shuffling React state around?
- If a value can be computed from props and state, why store it and update it in an effect?
- Should "send analytics when the user clicks Buy" run because a render happened, or because the user clicked?

## Answer

Effects are an escape hatch for **synchronizing with external systems**: the DOM, subscriptions, timers, network connections, non-React widgets. Many effects in real codebases don't need to exist. They cause extra renders, flicker, and bugs.

**Common misuses and fixes:**

1. **Derived state in an effect.** Compute it during render instead, with `useMemo` if it's expensive:
   ```jsx
   // bad: useEffect(() => setFullName(first + ' ' + last), [first, last]);
   const fullName = `${first} ${last}`; // good
   ```
2. **Event logic in an effect** (a POST or toast triggered by a state flag). Put it in the **event handler** that caused it.
3. **Resetting state when a prop changes.** Use a `key` on the component instead.
4. **Chains of effects** that set state, which triggers another effect. Calculate everything in one handler or one reducer.
5. **Notifying the parent** (`useEffect(() => onChange(value), [value])`). Call `onChange` in the same handler that updates the value, or lift the state up.
6. **Fetching in effects without cleanup.** This causes race conditions (an old response overwrites a new one) and request waterfalls. If you must fetch in an effect, use an `ignore` flag or an `AbortController`. Better, use TanStack Query, framework loaders, or Server Components.
7. **Lying about dependencies** to "run once." Fix the cause, for example with `useEffectEvent` for non-reactive logic. Don't disable the lint rule.

```jsx
useEffect(() => {
  const ctrl = new AbortController();
  fetch(`/api/user/${id}`, { signal: ctrl.signal }).then(r => r.json()).then(setUser);
  return () => ctrl.abort();
}, [id]);
```

**Rule of thumb:** if no external system is involved, you probably don't need an effect.
