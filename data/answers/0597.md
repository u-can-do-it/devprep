## Hints

- In which direction do project references point in Clean Architecture, and where do the interfaces for the database or email sender live?
- If a feature changes, how many folders or projects do you touch in a layered solution compared with a vertical slice?
- What does a repository wrapped around EF Core's `DbContext` add, given that `DbContext` already is a unit of work with `DbSet`s?

## Answer

There is no single right structure. The interviewer wants to hear the **trade-offs** and that you pick the simplest structure that keeps the code changeable.

**1. The common options**

| Style | How code is organised | Good at | Cost |
|---|---|---|---|
| **Layered (N-tier)** | `Controllers` → `Services` → `Repositories` → DB | familiar, easy to start | a feature is spread over every layer; services become huge "god" classes |
| **Clean / Onion / Hexagonal** | `Domain` ← `Application` ← `Infrastructure`, `Web`; dependencies point **inward** | domain logic free of EF, HTTP and vendors; easy to unit test | many projects, interfaces and mappings, even for simple CRUD |
| **Vertical slices** | one folder per use case (`Orders/PlaceOrder`) with endpoint, request, handler, validator | a change touches one place; each slice can be as simple or rich as it needs | shared logic needs discipline, or it gets duplicated |
| **Modular monolith** | modules (Billing, Scheduling) with their own data and a small public API | clear boundaries, can later become services | needs rules about what modules may reference |

They combine well: a modular monolith whose modules are built from vertical slices, with a rich domain model only in the modules that have real business rules.

**2. Clean Architecture in .NET**

- `Domain`: entities, value objects, domain rules. No references to EF Core or ASP.NET Core.
- `Application`: use cases, and the interfaces they need (`IEmailSender`, `IPaymentGateway`).
- `Infrastructure`: EF Core `DbContext`, HTTP clients, implementations of those interfaces.
- `Web`: endpoints, DI registration (the composition root, #581).

The rule is enforced by project references, and you can add architecture tests (NetArchTest, ArchUnitNET) so nobody adds `using Microsoft.EntityFrameworkCore` in `Domain`.

**3. A vertical slice**

```csharp
// Features/Appointments/Cancel.cs: everything for one use case in one file
public static class CancelAppointment
{
    public record Request(string Reason);

    public static void Map(IEndpointRouteBuilder app) =>
        app.MapPost("/appointments/{id:guid}/cancel", Handle).RequireAuthorization();

    static async Task<Results<NoContent, NotFound, Conflict<string>>> Handle(
        Guid id, Request req, AppDbContext db, TimeProvider clock, CancellationToken ct)
    {
        var appt = await db.Appointments.FindAsync([id], ct);
        if (appt is null) return TypedResults.NotFound();
        if (!appt.TryCancel(req.Reason, clock.GetUtcNow())) return TypedResults.Conflict("Already started");
        await db.SaveChangesAsync(ct);
        return TypedResults.NoContent();
    }
}
```

The slice uses `DbContext` directly. The business rule (`TryCancel`) still lives on the entity, so it's testable without a database.

**4. CQRS and MediatR**

- **CQRS** here usually means: **commands** go through the domain model and change state; **queries** skip it and project straight to DTOs (`Select`, `AsNoTracking`, or Dapper). You don't need separate databases for that.
- **MediatR** sends a request object to its handler in-process. Its real value is **pipeline behaviours**: validation, logging, transactions around every handler.
- Costs: an extra hop that makes "go to definition" land on an interface, more ceremony per feature, and MediatR moved to a commercial licence in 2025. Plain handler classes injected into endpoints, plus endpoint filters or decorators for cross-cutting concerns, often do the same job.

**5. When it's overkill**

- A CRUD service or a small team: four projects and an interface per class slow you down without protecting anything.
- A **generic repository over EF Core** (`IRepository<T>` with `GetAll`, `Add`): `DbContext` already is a unit of work and `DbSet<T>` a repository. The wrapper hides `Include`, projections and `AsNoTracking`, and usually leaks `IQueryable` anyway. Add a specific abstraction only where you need to swap or fake something.
- Mapping the same object through four DTO types with AutoMapper "for decoupling" that nobody needs.

**How to say it:** "I start with vertical slices in a single project, put business rules on the domain model where there are real invariants, and introduce module boundaries or separate projects when the team or the domain grows. I add layers when they protect something, not by default."

**Follow-up:** your Clean Architecture solution has a `Domain` project that is just anemic entities with getters and setters, and all logic sits in services. What went wrong? (You paid for the layers without getting a domain model. Either move the rules and invariants onto the entities, or admit the app is CRUD and simplify to slices.)
