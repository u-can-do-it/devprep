## Hints

- How does the client know it's talking to the real server and not an attacker?
- How do two parties agree on a shared key over a network someone is listening to?
- What can an observer still see even when the connection uses HTTPS?

## Answer

HTTPS is HTTP over **TLS**, which provides **confidentiality** (encryption), **integrity** (tamper detection) and **server authentication** (certificates).

**TLS 1.3 handshake (1 round trip):**

1. **ClientHello** – supported versions, cipher suites, a random value, **key share** (ephemeral ECDHE public key), and **SNI** (target hostname).
2. **ServerHello** – chosen cipher and its own key share. Both sides now compute the same shared secret via (EC)Diffie-Hellman and derive session keys.
3. Server sends (already encrypted) its **certificate**, a **CertificateVerify** signature proving it owns the private key, and **Finished**.
4. Client **validates the certificate**: chain up to a trusted root CA, hostname matches, not expired, not revoked. Sends **Finished**. Application data flows.

Key points:

- **Asymmetric crypto** is used for authentication and key exchange; **symmetric crypto** (AES-GCM, ChaCha20-Poly1305) encrypts the bulk data.
- **Forward secrecy** – ephemeral keys mean a stolen server private key can't decrypt past traffic. TLS 1.3 requires it and removed RSA key exchange.
- TLS 1.2 needed 2 round trips; TLS 1.3 needs 1, and resumption can use **0-RTT** (replayable, so only for idempotent requests).

```bash
openssl s_client -connect example.com:443 -servername example.com
```

**What HTTPS does not hide:** destination IP, often the hostname (SNI, unless Encrypted Client Hello is used), traffic size and timing. It also doesn't make the server itself trustworthy or secure.

**Related:** HSTS (`Strict-Transport-Security`) forces HTTPS and blocks SSL-stripping downgrades; mTLS adds client certificates for service-to-service auth.
