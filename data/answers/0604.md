## Hints

- Why would the runtime compile the same method twice, and what does it learn in between?
- What stops the JIT from inlining a call through an interface, and how can it still do it?
- How would you see the machine code for a method instead of guessing?

## Answer

The JIT trades compile time against code quality, so modern .NET compiles hot code **more than once** and uses what it observed at run time.

**1. Tiered compilation (default since .NET Core 3.0)**

| Tier | What it is | Purpose |
|---|---|---|
| **ReadyToRun** | precompiled native code shipped inside the assembly | fast startup, no JIT for cold code |
| **Tier 0** | quick JIT with almost no optimization | fast startup for code with no R2R image |
| **Tier 0 instrumented** | Tier 0 plus probes | collect profile data for hot methods (dynamic PGO) |
| **Tier 1** | fully optimized JIT, compiled in the background | steady-state performance |

A method is promoted after it has been called about 30 times (after a short startup delay). Methods with hot loops would be stuck in slow Tier 0 code, so **On-Stack Replacement** (OSR, default since .NET 7) switches a running loop to optimized code mid-execution. Static `readonly` fields of an already-initialized class are treated as **constants** at Tier 1, so `if (Config.Enabled)` branches can disappear entirely.

**2. Dynamic PGO (on by default since .NET 8)**

Instrumented code records which types actually show up at virtual and interface call sites and which branches are taken. Tier 1 then uses it:

- **Guarded devirtualization:** `if (obj.GetType() == typeof(List<int>)) { inlined List<int> code } else { normal interface call }`.
- **Hot/cold block layout:** frequently taken paths are laid out sequentially, rare ones (error handling) moved out of the way.

This is why .NET 8+ code often got faster with no source change, and why benchmarks must warm up.

**3. Inlining and devirtualization**

Inlining removes call overhead and, more importantly, lets other optimizations see through the call. The JIT inlines small, non-virtual methods by heuristics; `[MethodImpl(MethodImplOptions.AggressiveInlining)]` raises the budget. Large methods, recursion, and (historically) methods with exception handling blocks are usually not inlined.

A virtual or interface call can only be inlined after **devirtualization**: the JIT must know the exact type. It can when the class or method is `sealed`, when the object was just created with `new`, from generic instantiation over structs, or by guessing with PGO.

```csharp
public sealed class Circle : Shape { public override double Area() => Math.PI * R * R; }
double Sum(Circle[] shapes) { double s = 0; foreach (var c in shapes) s += c.Area(); return s; }
// Circle is sealed → Area() is devirtualized and inlined; no PGO guess needed
```

Generic methods over **value types** get a specialized copy per struct type (so `T` calls devirtualize), while all reference types share one copy using `__Canon`.

**4. Bounds-check elimination and other optimizations**

Every array or span access is checked, unless the JIT can prove the index is in range:

```csharp
for (int i = 0; i < arr.Length; i++) sum += arr[i];      // check removed: i < arr.Length is proven
for (int i = 0; i < count; i++) sum += arr[i];            // check stays: count may exceed Length
var span = arr.AsSpan(0, count);                          // one check here...
foreach (var x in span) sum += x;                         // ...none in the loop
```

Other passes include loop cloning (a fast version without checks plus a slow fallback), struct promotion (keeping struct fields in registers), hoisting invariant code, vectorization helpers in the base library (`Vector128/256/512`), and, in recent versions, stack allocation of some objects that never escape the method.

**5. ReadyToRun and Native AOT**

ReadyToRun (`<PublishReadyToRun>true</PublishReadyToRun>`) cuts startup, but its code is version-resilient and less optimized, so hot R2R methods are rejitted at Tier 1 anyway. Native AOT (#601) has no JIT at all: great startup and memory, but no tiering and no dynamic PGO, so peak throughput can be lower.

**6. Seeing what the JIT did**

```bash
DOTNET_JitDisasm="Sum" dotnet run -c Release          # print the assembly for Sum at each tier (.NET 7+)
DOTNET_JitDisasmSummary=1 dotnet run -c Release       # list every jitted method and its tier
DOTNET_TieredPGO=0 dotnet run -c Release              # compare with dynamic PGO off
```

BenchmarkDotNet's `[DisassemblyDiagnoser]` dumps the code that was actually measured, and sharplab.io is handy for quick experiments. Always look at the final Tier 1 output in Release, never at Debug or Tier 0 code.
