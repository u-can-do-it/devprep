## Hints

- Should a URL describe a thing or an action?
- How deep should nesting like `/users/1/orders/5/items` go?
- Where do optional criteria like status or date range belong: in the path or the query string?

## Answer

**Resources are nouns**, HTTP methods are the verbs.

```http
GET    /orders            # list
POST   /orders            # create
GET    /orders/123        # read one
PATCH  /orders/123        # partial update
DELETE /orders/123        # delete
```

**Conventions:**

- Plural nouns, lowercase, hyphens in paths (`/shipping-addresses`); pick one JSON field casing (`camelCase` or `snake_case`) and stick to it.
- **Path = identity, query = options.** Use the path to identify a resource and the query string for filtering, sorting, pagination and field selection.
- **Shallow nesting** – nest only to express ownership one level deep: `GET /customers/42/orders`. Once a child has its own id, address it directly: `/orders/123`, not `/customers/42/orders/123/items/7`.

**Filtering, sorting, pagination:**

```http
GET /orders?status=paid&created_after=2026-09-01&sort=-created_at,total&limit=50&cursor=eyJpZCI6...
GET /orders?fields=id,total,status
```

`-` prefix for descending is a common convention; document allowed filter/sort fields and validate them (never pass them straight into SQL). For complex search, `POST /orders/search` with a JSON body is acceptable.

**Non-CRUD actions:** model them as a sub-resource or as creating a resource:

- `POST /orders/123/cancel` – pragmatic "controller" resource.
- `POST /orders/123/refunds` – a refund is a real resource with its own id and status (often the better design).
- Avoid `GET /cancelOrder?id=123` – GETs must be safe.

Consistency matters more than any specific rule – publish a style guide (or adopt one like Google's AIP or Zalando's guidelines) and lint the OpenAPI spec (e.g. Spectral).

**Follow-up:** How would you return related data (e.g. order + customer) without N extra requests? (`?include=customer`, compound documents, or a BFF.)
