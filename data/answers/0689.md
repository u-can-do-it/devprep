## Hints

- There are no `<button>` or `<h1>` elements. How does a screen reader know what a `Pressable` is?
- What happens to your layout when the user sets the system font size to 200%?
- How does a blind user move through a screen on a phone without a keyboard?

## Answer

> Core components map to native views, so they use the platform's own accessibility APIs, but you must supply the meaning: a label, a role and a state for every interactive element. Screen reader users swipe from element to element and double-tap to activate, so grouping and order matter. Let text scale with the system font setting, keep touch targets at least 44 to 48 points, and test with VoiceOver and TalkBack on real devices.

**The props**

```tsx
<Pressable
  onPress={toggleFavourite}
  accessibilityRole="button"
  accessibilityLabel="Add to favourites"
  accessibilityState={{ selected: isFavourite }}
  accessibilityHint="Saves this product to your list"
  hitSlop={10}
>
  <HeartIcon filled={isFavourite} />
</Pressable>
```

| Prop | Purpose |
|---|---|
| `accessible` | makes a view one focusable element, and groups its children |
| `accessibilityLabel` | what is read; required for icon-only controls |
| `accessibilityRole` / `role` | `button`, `link`, `header`, `image`, `checkbox`, `switch`, `tab`... |
| `accessibilityState` | `disabled`, `selected`, `checked`, `expanded`, `busy` |
| `accessibilityValue` | for sliders and progress |
| `accessibilityHint` | extra explanation, read after a pause |
| `accessibilityActions` | custom actions, such as "delete" on a swipeable row |

React Native also accepts web-style `aria-*` props and `role`, which helps when code is shared with the web (#57).

**Grouping and hiding**

- A card with a title, a price and an image should usually be **one** element with a combined label, so the user doesn't swipe three times per card.
- Hide decorative content with `aria-hidden` (or `importantForAccessibility="no-hide-descendants"` on Android and `accessibilityElementsHidden` on iOS).
- A modal must trap the screen reader inside it: `aria-modal` (`accessibilityViewIsModal` on iOS). The built-in `Modal` and navigation libraries handle this.

**Announcements and focus**

- Announce changes that aren't visible to a screen reader user: `AccessibilityInfo.announceForAccessibility('Added to cart')`, or a live region (`aria-live="polite"`).
- After navigation, the navigator moves focus to the new screen. For your own overlays and for validation errors, move focus yourself (`AccessibilityInfo.setAccessibilityFocus`, or focus the first invalid input).
- Mark screen titles with the `header` role, so users can jump between headings.

**Font scaling**

`Text` follows the system font size by default. Don't turn it off with `allowFontScaling={false}`.

- Build layouts that grow: no fixed heights on text containers, allow wrapping, scroll when needed.
- `maxFontSizeMultiplier` can cap extreme sizes on elements that truly can't grow, such as a tab bar label.
- Test at the largest setting. This finds more bugs than any other accessibility check.

**Touch and vision**

- Touch targets: at least 44×44 points on iOS and 48×48 dp on Android. Use padding or `hitSlop` for small icons.
- Contrast: 4.5:1 for normal text, in both light and dark mode.
- Don't use colour alone to show state or errors.
- Respect "reduce motion" (`AccessibilityInfo.isReduceMotionEnabled`, or `useReducedMotion` in Reanimated).
- Gestures such as swipe-to-delete need an alternative that a screen reader can reach.

**Testing**

- Use **VoiceOver** (iOS) and **TalkBack** (Android) on a real device. Swipe through every screen: is everything reachable, in a sensible order, with a meaningful label?
- Xcode's Accessibility Inspector and Android's Accessibility Scanner find missing labels and small targets.
- In component tests, `getByRole` and `getByLabelText` queries (#686) fail when the semantics are missing, so they protect accessibility as a side effect.

**Why it matters in an interview:** accessibility is a legal requirement for many consumer apps (the European Accessibility Act applies from June 2025), and both stores describe it in their guidelines.

**Follow-up:** a custom checkbox is a `Pressable` with an icon. What does TalkBack read, and how do you fix it? (Without props it reads nothing useful. Add `accessibilityRole="checkbox"`, a label, and `accessibilityState={{ checked }}`.)
