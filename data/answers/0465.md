## Hints

- Browsers support ES modules natively. Why do we still bundle for production?
- Why does a large webpack project take a while to start the dev server, while Vite starts almost instantly?
- What does Vite use for production builds, and why did that change?

## Answer

A **bundler** starts from entry points, follows every `import` to build a **module graph**, and produces optimised files for the browser:

- **Transforms:** TypeScript, JSX, CSS modules, Sass, images and fonts through loaders or plugins.
- **Bundling and code splitting:** combines modules into chunks and splits at dynamic `import()` and route boundaries so users download only what they need.
- **Optimisation:** tree shaking, minification, scope hoisting, CSS extraction.
- **Content hashing** (`app.3f9a1c.js`) so files can be cached for a year and changed files get new names.
- **Dev experience:** a dev server with **Hot Module Replacement (HMR)** that swaps changed modules without a reload and keeps state.

We still bundle for production because hundreds of separate module requests (a deep import waterfall) are slow even over HTTP/2, and minification and tree shaking need the whole graph.

**webpack vs Vite:**

| | webpack 5 | Vite |
|---|---|---|
| dev server | **bundles the whole app** before serving; cold start grows with app size | serves **native ES modules on demand**; only the modules a page imports get transformed |
| dependencies | bundled with the app | pre-bundled once (CommonJS → ESM, many files → one) and cached |
| HMR | rebuilds affected chunks | replaces just the changed module; stays fast as the app grows |
| production | webpack itself | **Rolldown** in Vite 8 (Rust); Rollup with esbuild in earlier versions |
| config | very flexible, verbose: loaders, plugins | convention-based, small config, Rollup-compatible plugin API |
| strengths | mature ecosystem, **Module Federation**, unusual legacy setups | speed, simplicity, the default for React, Vue and Svelte apps and Vitest |

A long-standing Vite caveat was that dev (unbundled ESM) and production (bundled) used different pipelines, so a few bugs only showed up in production builds. Moving to Rolldown for both reduces that gap.

**Other tools you'll hear about:** **Rspack/Rsbuild** (a Rust, webpack-compatible bundler, an easy migration path for big webpack apps), **Turbopack** (the Next.js default since Next 16), **esbuild** (very fast transforms and bundling for libraries and tools), and **tsup/tsdown** for building npm packages.

**Follow-up:** a webpack app takes 90 seconds to start in dev. What are your options, short of a full migration?
