## Hints

- What is the difference between Firebase Hosting, Cloud Functions (2nd gen) and Cloud Run, and how can Hosting route `/api/**` to one of them?
- How does a function or Cloud Run service get the database password without it being in the code or the image?
- What do the Firebase emulators let you run locally and in CI, and how do you seed them with data?
- 50 Cloud Run instances each open a Prisma pool of 10 connections to Cloud SQL. What happens?
- How does a GitHub Actions workflow deploy to GCP without a service account key file?

## Answer

**Firebase vs GCP:** Firebase is a developer-friendly layer on top of Google Cloud. A Firebase project *is* a GCP project, so Firebase Hosting, Functions and Firestore sit next to Cloud Run, Cloud SQL and Secret Manager and share IAM, billing and logs.

**Main pieces for a TypeScript web app:**

| service | what it is | typical use |
|---|---|---|
| **Firebase Hosting** | static files on a global CDN, free TLS, rewrites | the React SPA build; `/api/**` rewritten to Cloud Run or a function |
| **Cloud Functions for Firebase (2nd gen)** | functions as code; 2nd gen runs on Cloud Run | `onRequest` HTTP endpoints, `onCall`, triggers (Firestore, Storage, Pub/Sub), `onSchedule` cron jobs |
| **Cloud Run** | any container, scales by requests, scale to zero | the Node API (Fastify/Nest), workers, Cloud Run **jobs** for batch/ETL (#629) |
| **Cloud SQL for PostgreSQL** | managed Postgres | the main database |
| **Secret Manager** | versioned secrets with IAM | DB passwords, API keys |
| **Cloud Storage** | object storage | documents, signed URLs (#410) |
| **Cloud Scheduler / Cloud Tasks / Pub/Sub** | cron, task queues, messaging | reminders, sync jobs (#623), async work |
| **Artifact Registry, Cloud Build** | images, builds | CI/CD |
| **Cloud Logging / Error Reporting / Trace** | observability | structured JSON logs from stdout |

**Firebase Hosting config:**

```json
{
  "hosting": {
    "public": "dist/apps/web",
    "rewrites": [
      { "source": "/api/**", "run": { "serviceId": "rms-api", "region": "europe-central2" } },
      { "source": "**", "destination": "/index.html" }
    ],
    "headers": [{ "source": "/assets/**", "headers": [{ "key": "Cache-Control", "value": "public, max-age=31536000, immutable" }] }]
  }
}
```

Same origin for SPA and API means no CORS (#110) and first-party cookies. `firebase hosting:channel:deploy pr-123` gives a **preview URL** per pull request (#405).

**Functions (2nd gen) essentials:**

```ts
import { onRequest } from 'firebase-functions/v2/https';
import { onSchedule } from 'firebase-functions/v2/scheduler';
import { defineSecret } from 'firebase-functions/params';

const dbUrl = defineSecret('DATABASE_URL');                  // stored in Secret Manager

export const api = onRequest({ region: 'europe-central2', secrets: [dbUrl], concurrency: 80, minInstances: 1 }, app);
export const reminders = onSchedule({ schedule: 'every day 08:00', timeZone: 'Europe/Warsaw' }, sendApprovalReminders);
```

- 2nd gen handles many concurrent requests per instance (1st gen handled one), so module-level state such as a DB pool is shared between requests.
- **Cold starts** (#128): keep bundles small, lazy-load heavy modules, use `minInstances` for latency-sensitive endpoints.
- Region close to users and the database (`europe-central2` is Warsaw).

**Emulator Suite:** `firebase emulators:start` runs Auth, Firestore, Functions, Hosting, Storage and Pub/Sub locally. `--import ./seed --export-on-exit` keeps seed data; `firebase emulators:exec "pnpm test"` starts them, runs the tests and stops them, which is handy in CI. The emulators don't cover Cloud SQL, so run Postgres in Docker for that (#399, #628).

**Connecting to Cloud SQL:**

- Use the **Cloud SQL connector** or Auth Proxy (IAM-authenticated, encrypted), or private IP through a VPC connector.
- **Connection limits:** total connections = instances × pool size. With autoscaling, cap `max-instances`, keep pools small (e.g. 2-5 per instance), or put a pooler in front (#338, #620).

**Configuration and secrets** (#68, #400): environment variables for non-secret config; Secret Manager mounted as env vars or files for secrets; each service runs as its **own service account** with least-privilege IAM roles (`roles/cloudsql.client`, `roles/secretmanager.secretAccessor` on specific secrets).

**CI/CD** (#403): GitHub Actions authenticates with **Workload Identity Federation** (OIDC, no JSON key), builds the image, pushes to Artifact Registry, runs `prisma migrate deploy`, then `gcloud run deploy` and `firebase deploy --only hosting`. With Nx, deploy only affected apps (#616).

**Logging:** write JSON lines to stdout with a `severity` field (`INFO`, `ERROR`) and `message`; Cloud Logging parses them, Error Reporting groups errors with stack traces (#304).

**Follow-up:** Cloud Functions or Cloud Run for the main API? (Cloud Run: you control the container and runtime, run Fastify as-is, test it the same way locally, and avoid vendor-specific function wrappers. Functions are great for triggers, small webhooks and scheduled jobs.)
