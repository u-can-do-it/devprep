## Hints

- Who are the three parties in an SSO login, and which one does the app actually trust?
- What format is the identity assertion in each protocol, and how does it get back to the app?
- Which one would you pick for a new mobile app, and which one does an enterprise customer's old IdP probably speak?

## Answer

**Single sign-on**: users authenticate once at an **Identity Provider** (IdP: Okta, Entra ID, Google Workspace), and many apps (**Service Providers / Relying Parties**) trust the IdP's signed statement about who the user is. Benefits: one place for MFA and password policy, central offboarding, fewer passwords.

Typical flow (both protocols): user opens the app, the app redirects to the IdP, the user authenticates (if no IdP session yet), the IdP sends a **signed assertion** back to the app, the app validates it and creates **its own session**.

| | SAML 2.0 | OpenID Connect |
|---|---|---|
| Built on | XML, SOAP-era standards | OAuth 2.0, JSON, REST |
| Identity token | Signed XML **assertion** | Signed **ID token** (JWT) |
| Typical transport | Browser POSTs the assertion to the app's ACS URL | Authorization code flow (+ PKCE); app exchanges code for tokens |
| API access | Not covered | Same flow also yields OAuth access tokens |
| Mobile / SPA | Awkward | Designed for it |
| Where you see it | Enterprise/B2B, legacy IdPs | Consumer logins, modern SaaS, B2B too |

Security notes:

- **SAML**: XML signature validation is notoriously tricky (signature wrapping attacks, parser differences). Always use a well-maintained library, validate audience, recipient, `NotOnOrAfter`, and keep it patched.
- **OIDC**: validate the ID token's signature (via the IdP's JWKS), `iss`, `aud`, `exp`, and `nonce`; use PKCE and the `state` parameter.
- Both: match users on a stable IdP subject ID, not email alone; support IdP-initiated logout/deprovisioning (**SCIM** for user lifecycle).

For a B2B SaaS in 2026 you usually support **both**: OIDC as default, SAML because enterprise customers ask for it. Many teams use a broker (Auth0, WorkOS, Keycloak) to normalize them.

**Follow-up:** Why is IdP-initiated SAML riskier? There's no request from the app to tie the response to, so it's more exposed to replay and login CSRF.
