## Hints

- Which signal tells you *that* something is wrong, and which tells you *where* in a chain of services it went wrong?
- How does a request ID travel from the frontend through three backend services?
- What happens to your metrics bill if you add `user_id` as a label?

## Answer

> When production misbehaves, you need to see what the system is doing from the outside. Logs record individual events, metrics are cheap numbers over time for dashboards and alerts, and traces follow one request across services to show where time went. They're most useful together: an alert leads to slow traces, and a trace ID leads to the exact logs. OpenTelemetry is the vendor-neutral standard for producing all three, so you instrument once and can switch backends without changing code.

**Observability** is being able to understand what your system is doing from its outputs, including for failures you didn't predict. Three main signals:

- **Logs:** discrete events with context. Use **structured (JSON) logs** with a level, message, request or trace ID, and relevant fields. Best for "what exactly happened in this request?"
- **Metrics:** numeric time series aggregated over time (request rate, error rate, latency percentiles, CPU, queue depth). Cheap to store, ideal for **dashboards, alerts and SLOs**. Common methods: RED (Rate, Errors, Duration) for services and USE (Utilization, Saturation, Errors) for resources.
- **Traces:** the path of one request across services as a tree of **spans** with timings. Best for "which service or query made this request slow?"

Their power comes from **correlation**: a latency alert (metric) leads to slow traces, and a trace ID leads to the exact logs.

**OpenTelemetry (OTel)** is the vendor-neutral CNCF standard for producing telemetry:
- SDKs and **auto-instrumentation** for HTTP, DB and queue libraries in Node, Python, Java and other languages,
- **context propagation** through the W3C `traceparent` header,
- the **OTLP** protocol and the **Collector**, which receives, processes (sampling, PII scrubbing) and exports data to any backend (Grafana stack, Datadog, Honeycomb, Jaeger, and others).

You instrument once and can switch vendors without touching code.

```ts
import { trace } from "@opentelemetry/api";
const tracer = trace.getTracer("checkout");

await tracer.startActiveSpan("charge-card", async (span) => {
  span.setAttribute("order.id", orderId);
  try { await chargeCard(orderId); } finally { span.end(); }
});
```

**Pitfalls:** high-cardinality metric labels (user IDs) blow up costs, logging secrets or PII, and alerting on causes (CPU) instead of user-facing symptoms (error rate, latency SLOs).
