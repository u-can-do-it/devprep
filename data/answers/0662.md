## Hints

- What does a failed attempt by a cheap model cost, compared with one good attempt by an expensive one?
- In a long agent session, which grows faster: the output you asked for, or the context that is sent again on every turn?
- Which is the more useful number for a team: cost per token or cost per merged change?

## Answer

> Match the tool and the model to the task. Use inline completion for small edits, chat for questions and design, and an agent for multi-file work it can verify. Use a small, fast model for simple, high-volume or latency-sensitive steps, and the strongest model for planning, hard debugging and large changes. Cost is driven by context size multiplied by the number of turns, so keep tasks scoped and contexts clean. Set budgets and track cost per outcome, and remember that engineer time usually costs more than tokens.

**Choosing the tool**

| Task | Tool | Why |
|---|---|---|
| Finish a line, a small function, a repetitive edit | inline completion | instant, you see every character |
| Understand code, compare options, sketch a design | chat | nothing changes in the repository |
| A change across files with tests to run | agent in the editor or terminal | it runs commands and iterates |
| A well-specified chore | background or cloud agent | you review a PR later (#659) |
| A fixed, repeated job (triage, review) | a script or CI job calling the model | no interactive session needed (#661) |

**Choosing the model**

- **Small, fast, cheap:** completion, classification, extraction, summaries, searches by subagents, simple edits with a clear pattern. Latency matters here more than depth.
- **Mid-range:** everyday implementation with good context and tests.
- **Frontier:** planning a larger change, debugging something subtle, unfamiliar or legacy code, long autonomous tasks, security-sensitive review.
- **Reasoning effort** (extended thinking) is a second dial: more thinking helps hard problems and makes easy ones slower and more expensive.
- **Mix them:** a strong model plans and reviews, a cheaper one executes mechanical steps or runs as a subagent.
- Decide with **evidence**: run the same handful of real tasks on two models and compare how often the result merges without rework (#543). Model names and prices change every few months; the method stays.

**What drives the cost**

- **Subscription or usage-based.** Seats have a flat price with limits; API usage is billed per token. Heavy agent use can make either one the better deal, so look at real usage.
- **Input:** each turn sends the conversation again, so a long session costs roughly context size × number of turns. Big files read whole, long logs and many MCP tool definitions all add to every turn.
- **Output** tokens cost several times more than input, and thinking tokens count as output.
- **Prompt caching** makes a repeated prefix much cheaper, which is why agent sessions are affordable at all (#483).
- **Parallel agents and retries** multiply everything.

**Keeping it under control**

- One task per session, clear the context between tasks, delegate searching to subagents on a cheaper model (#658).
- Scope the task: point to the files, don't make the agent rediscover the repository every time.
- Turn off tools and MCP servers you don't use in a project.
- For CI and scripts: caps on turns and output tokens, batch processing for offline work, a spending limit per key.
- For a team: usage dashboards, a budget per person or team, and a look at outliers, which are usually a runaway loop or a huge context, not real work.
- Report **cost per merged PR or per resolved ticket**, next to the time saved.

**Don't over-optimise:** an hour of an engineer's time usually costs more than a day of tokens. A weak model that needs three attempts and a longer review is more expensive than a strong one that gets it right. Save money where the volume is (automation, CI, subagents), not on the hard problem in front of you.

**Follow-up:** your team's AI bill doubled last month. How do you find out why and what to change? (Break usage down by person, tool and job; look for long sessions with big contexts, new CI automations and parallel runs; then fix the largest source and compare it with what it delivered.)
