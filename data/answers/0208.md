## Hints

- Should a test know about a component's internal state, or only what the user can see and do?
- Which query would also fail if the button weren't accessible to a screen reader?
- What's the difference between `getBy`, `queryBy` and `findBy`?

## Answer

React Testing Library (RTL) renders components into a DOM (jsdom or happy-dom, or a real browser with Vitest browser mode) and encourages testing **behavior from the user's point of view**: find elements the way users do, interact with them, and check the visible outcome. You never touch state, props or internal methods. That makes tests survive refactors.

```tsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';

test('adds a todo', async () => {
  const user = userEvent.setup();
  render(<TodoApp />);

  await user.type(screen.getByRole('textbox', { name: /new todo/i }), 'Buy milk');
  await user.click(screen.getByRole('button', { name: /add/i }));

  expect(await screen.findByRole('listitem')).toHaveTextContent('Buy milk');
  expect(screen.queryByText(/no todos/i)).not.toBeInTheDocument();
});
```

**Why `getByRole` first:** it queries the **accessibility tree** by role and accessible name, the same way assistive technology does. If a "button" is a `<div>` with no label, the test fails, so you get free a11y checks. Priority: `ByRole` → `ByLabelText` → `ByPlaceholderText`/`ByText` → `ByTestId` as a last resort.

**Query variants:**

- `getBy`: element must exist, otherwise the test throws.
- `queryBy`: returns `null`. Use it to assert absence.
- `findBy`: returns a promise. Use it for async UI.

**Best practices:** use `user-event`, which simulates real event sequences, rather than `fireEvent`. Mock the network at the boundary with MSW instead of mocking hooks. Avoid testing implementation details or snapshotting large trees. RTL replaced Enzyme, which doesn't support modern React.

**Follow-up:** use Playwright for end-to-end flows. Keep RTL for component and integration tests.
