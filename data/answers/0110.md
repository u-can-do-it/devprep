## Hints

- Which policy normally prevents JavaScript on one origin from reading responses from another?
- Is CORS enforced by the server or by the browser?
- Why would a `PUT` with JSON trigger an extra request but a simple form `POST` doesn't?

## Answer

The **Same-Origin Policy** stops scripts on `https://app.com` from reading responses from `https://api.other.com` (origin = scheme + host + port). **CORS (Cross-Origin Resource Sharing)** is a mechanism for a server to **relax** that policy by telling the browser which origins may read its responses.

Key point: CORS is **enforced by the browser**. It doesn't protect your server from curl or other servers – it protects users' data from being read by other sites' scripts.

**Simple requests** (`GET`/`HEAD`/`POST` with only safelisted headers and form/text content types) are sent directly; the browser checks the response:

```http
Access-Control-Allow-Origin: https://app.com
```

**Preflight** – for other methods (`PUT`, `DELETE`), custom headers (`Authorization`), or `Content-Type: application/json`, the browser first sends:

```http
OPTIONS /orders/1
Origin: https://app.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: authorization, content-type
```

The server must reply with:

```http
Access-Control-Allow-Origin: https://app.com
Access-Control-Allow-Methods: GET, PUT, DELETE
Access-Control-Allow-Headers: authorization, content-type
Access-Control-Max-Age: 600
```

**Credentials:** for cookies, the client uses `credentials: "include"` and the server must send `Access-Control-Allow-Credentials: true` with an **explicit** origin – `*` is not allowed.

**Common mistakes:**

- Reflecting any `Origin` back with credentials allowed – effectively disables the protection.
- Thinking CORS errors are server bugs – the request often reached the server; the browser just hid the response.
- Forgetting `Vary: Origin` when the allowed origin is dynamic (cache poisoning).
- Using CORS as authorization – it isn't.
