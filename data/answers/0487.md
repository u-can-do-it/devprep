## Hints

- Where is the schema defined in Prisma, and where in Drizzle?
- What SQL does your ORM actually run when you load 50 posts with their authors?
- What happens to database connections when 500 serverless functions start at once?

## Answer

There are three common levels of abstraction for Postgres or MySQL in Node:

| | Prisma | Drizzle (or Kysely) | raw SQL (`pg`, `postgres.js`) |
|---|---|---|---|
| schema | its own `schema.prisma` DSL, generated client | TypeScript schema, a typed query builder close to SQL | your migrations; types written by hand or generated |
| queries | high-level object API (`findMany({ include })`) | SQL-shaped (`select().from().where()`), relational queries optional | full SQL control |
| type safety | excellent | excellent | none unless you add it (pgtyped, Kysely types, Zod) |
| migrations | `prisma migrate` from the schema | `drizzle-kit` generate/migrate | a tool of your choice (node-pg-migrate, dbmate) |
| complex SQL | `$queryRaw` escape hatch, typed SQL | natural: CTEs, window functions | natural |
| weight | heavier (recent versions dropped the Rust engine, which helped) | thin, serverless and edge friendly | thinnest |

**How to choose:**

- **Prisma:** fastest start, great DX and docs, good for CRUD-heavy apps and teams less comfortable with SQL.
- **Drizzle or Kysely:** you think in SQL and want types without hiding it; fits serverless and edge runtimes and complex queries.
- **Raw SQL:** performance-critical or SQL-heavy services (reporting), or teams with strong SQL skills. Always use parameters (`$1` placeholders with `pg`, or the `` sql`… WHERE id = ${id}` `` tagged template in postgres.js), never string concatenation.
- Mixing is fine: an ORM for CRUD plus raw SQL for reports.

**ORM pitfalls:**

- **N+1 queries:** loading a list and then lazily fetching each relation. Use `include`/joins, check the query log, and count queries in tests.
- **Over-fetching:** selecting every column (including large JSON or text) when you need three. Select explicitly.
- **Hidden expensive queries:** a harmless-looking call that generates a huge join, or a filter that can't use an index. Read the generated SQL and run `EXPLAIN ANALYZE`.
- **Transactions:** forgetting to pass the transaction client (`tx`) to inner calls, which then run outside the transaction; long transactions holding locks during slow API calls.
- **Connection pooling:** each serverless instance opens its own pool and can exhaust Postgres. Use a pooler (PgBouncer, Supabase's pooler, Prisma Accelerate) and small per-instance pools.
- **Migrations:** schema drift between environments, and destructive migrations run without an expand/contract plan.
- **Leaky models:** returning database rows straight from the API exposes internal fields. Map to DTOs.
- The ORM doesn't replace knowing SQL: indexes, isolation levels and locking still matter.
