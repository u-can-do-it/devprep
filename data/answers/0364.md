## Hints

- Why can't a CDN cache by URL when every request goes to `POST /graphql`?
- How does a client cache know that the `User:42` in two different queries is the same object?
- What could you send instead of the full query text so a `GET` request stays short?

## Answer

HTTP caching relies on URL-addressed `GET` requests, which GraphQL doesn't naturally use. So caching happens at several other layers.

**1. Normalized client cache** (Apollo Client, Relay, urql Graphcache)

The client splits responses into objects keyed by `__typename` + `id` (`User:42`) and stores them in a flat map. A different query or a mutation that returns `User:42` updates the same entry, so every component showing that user re-renders with fresh data – no refetch needed.

- Requires stable ids (`id` or custom `keyFields`).
- List changes after mutations (adding/removing items) need manual cache updates or refetches.

**2. Persisted queries + `GET` + CDN**

The client sends a **hash** of a known query instead of the full text, which makes `GET` requests short and cacheable:

```http
GET /graphql?operationName=Product&variables=%7B%22id%22%3A%227%22%7D&extensions=%7B%22persistedQuery%22%3A%7B%22version%22%3A1%2C%22sha256Hash%22%3A%22ecf4...%22%7D%7D
```

- **Automatic Persisted Queries (APQ)** register hashes on first miss.
- **Trusted documents** register them at build time – also a security win (only known operations run).
- The server sets `Cache-Control` from **cache hints** (e.g. `@cacheControl(maxAge: 60)` per type/field; the response gets the minimum across all fields, and `PRIVATE` if any field is per-user).

**3. Server-side caching**

- **Full response cache** keyed by operation + variables + user/role (e.g. GraphQL Yoga/Envelop response cache, Apollo Router entity caching), invalidated by entity type/id on mutations.
- **Resolver/data-level caching** – DataLoader dedupes within a request; Redis caches expensive resolver results across requests.

Pitfalls:

- Mutations must never be cacheable or sent as `GET`.
- Per-user fields make a whole response private – split personalized data into separate operations to keep public ones CDN-cacheable.
- Normalized caches can serve stale lists; choose fetch policies (`cache-and-network`) deliberately.
