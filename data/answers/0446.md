## Hints

- What file does a remote produce, and what two functions does it give the host?
- How do the host and remote agree on a single copy of React at runtime, and what does `singleton` change?
- Why does a federated app's entry usually just call `import('./bootstrap')`?

## Answer

**Module Federation** (webpack 5, now also Rspack, Rsbuild and Vite via `@module-federation/vite`) lets separately built and deployed applications **load code from each other at runtime** and **share dependencies**.

- **Remote:** a build that **exposes** modules. It emits a container entry (`remoteEntry.js`, or `mf-manifest.json` in Module Federation 2.0) with `init(shareScope)` and `get(moduleName)`.
- **Host (consumer):** a build that declares **remotes** and imports their modules as if they were local packages. An app can be both host and remote.
- **Shared:** dependencies both sides agree to share, negotiated at runtime instead of bundled twice.

```js
// checkout (remote): rspack.config.js / webpack.config.js
const { ModuleFederationPlugin } = require('@module-federation/enhanced/webpack');

new ModuleFederationPlugin({
  name: 'checkout',
  filename: 'remoteEntry.js',
  exposes: { './CheckoutPage': './src/CheckoutPage' },
  shared: {
    react: { singleton: true, requiredVersion: '^19.0.0' },
    'react-dom': { singleton: true, requiredVersion: '^19.0.0' },
  },
});

// shell (host)
new ModuleFederationPlugin({
  name: 'shell',
  remotes: { checkout: 'checkout@https://cdn.example.com/checkout/remoteEntry.js' },
  shared: { react: { singleton: true }, 'react-dom': { singleton: true } },
});
```

```jsx
// in the shell
const CheckoutPage = React.lazy(() => import('checkout/CheckoutPage'));
```

**At runtime:** the host loads `remoteEntry.js` and calls `init()` with the share scope, which is a registry where every container lists the shared versions it can provide. It then calls `get('./CheckoutPage')`, and the remote's chunks are loaded from its own origin (`publicPath: 'auto'`). For each shared package the runtime picks the **highest version that satisfies** every `requiredVersion`. With `singleton: true` only **one** instance is ever loaded.

**Async boundary:** shared modules are resolved asynchronously, so the entry file is just `import('./bootstrap')` and the real app lives in `bootstrap.js`. Without it you get *"Shared module is not available for eager consumption"*. `eager: true` avoids this but puts the dependency in the initial chunk.

**What breaks when shared versions don't match:**

- **Not a singleton and versions differ:** two copies of React load. Hooks throw *"Invalid hook call"*, a context provided by the host is invisible to the remote (two different `createContext` registries), and the payload grows.
- **Singleton with an unsatisfied range:** a console warning (*"Unsatisfied version … of shared singleton module"*), then the already loaded version is used anyway. A remote built for React 19 running on the host's React 18 fails at runtime (`use` is undefined, for example).
- **`strictVersion: true`:** the load throws instead of warning. That's louder and safer, but the remote then needs a fallback UI.
- Libraries with **module-level state** must be singletons: `react`, `react-dom`, routers, state stores, CSS-in-JS runtimes, i18n, design systems that use context. Stateless utilities (lodash, date-fns) can safely be duplicated.

**Module Federation 2.0** (`@module-federation/enhanced`) adds a bundler-independent runtime (`loadRemote`, `registerRemotes`), `mf-manifest.json` with preloading metadata, generated TypeScript types for remotes, runtime plugins (error fallback, retries) and Chrome devtools.

**Limits:** it's mostly a client-side, same-framework solution. SSR support is more limited. For Next.js the native route-level option is **Multi-Zones**.
