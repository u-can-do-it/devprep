## Hints

- At what point in the event loop does the browser get a chance to render a new frame?
- Why does an animation driven by `setTimeout(fn, 16)` stutter, even on a fast machine?
- What happens to these callbacks when the tab is in the background?

## Answer

**One frame of the event loop (simplified):**

1. Run **one task** (an event handler, a timer, a message).
2. Run **all microtasks** (promise callbacks, `queueMicrotask`, MutationObserver).
3. If it's time for a frame (usually every 16.7 ms at 60 Hz, faster on 120 Hz screens), do the **rendering steps**:
   - Handle scroll and resize events, and media queries.
   - **Run `requestAnimationFrame` callbacks.**
   - Style → Layout → **ResizeObserver** callbacks → Paint → Composite. IntersectionObserver is also updated as part of this step.
4. If there's spare time before the next frame: **`requestIdleCallback`** callbacks.

**`requestAnimationFrame(cb)`**

- Runs **right before the next paint**, once per frame, in sync with the display's refresh rate.
- `cb` receives a high-resolution timestamp. Animate by **elapsed time**, not by counting frames, so speed is the same at 60 Hz and 120 Hz.
- **Paused in background tabs** and hidden iframes, which saves battery.
- Right for JS-driven animations, and for batching DOM writes so they land in the next frame.

```js
function animate(el, start, now = start) {
  const progress = Math.min((now - start) / 300, 1);
  el.style.transform = `translateX(${progress * 200}px)`;
  if (progress < 1) requestAnimationFrame((t) => animate(el, start, t));
}
requestAnimationFrame((t) => animate(box, t));
```

**`setTimeout(fn, 16)`** isn't aligned to frames. It can fire twice in one frame or skip a frame, causing jank. It's clamped to at least 4 ms after nesting and throttled to about 1 s or more in background tabs. Use it for **delays**, and for **yielding** long work back to the event loop. The newer `scheduler.yield()` does that yielding job better where it's supported.

**`requestIdleCallback(cb, { timeout })`** runs low-priority work (analytics, prefetching, cache warming) when the browser is idle. It gets a `deadline.timeRemaining()` budget. It isn't available in Safari, so use a fallback.

**Common mistakes:**

- Heavy work inside rAF delays the frame. Keep it short and move computation elsewhere.
- Reading layout (`offsetHeight`) after writing inside rAF still forces a synchronous layout.
- A recursive rAF loop that never stops.

**Follow-up:** where you can, CSS animations or the Web Animations API on `transform`/`opacity` beat rAF, because they run on the compositor even when the main thread is busy.
