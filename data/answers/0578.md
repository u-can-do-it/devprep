## Hints

- For two instances of an ordinary class with the same field values, what do `==` and `Equals` return? And for two records?
- What does `with` do to the original object?
- If two objects are equal but have different hash codes, what goes wrong when you put them in a `Dictionary` or `HashSet`?

## Answer

**Records** are types whose identity is their data. The compiler generates value-based equality, `ToString`, deconstruction and support for `with` expressions.

```csharp
public record Money(decimal Amount, string Currency);          // positional record: a class with init-only properties

var a = new Money(10m, "EUR");
var b = new Money(10m, "EUR");
Console.WriteLine(a == b);                    // True: compares Amount and Currency
Console.WriteLine(ReferenceEquals(a, b));     // False: still two objects
Console.WriteLine(a);                         // Money { Amount = 10, Currency = EUR }

var c = a with { Amount = 20m };              // a copy with one property changed; a is untouched
var (amount, currency) = c;                   // deconstruction
```

| | `class` | `record` (`record class`) | `record struct` | `struct` |
|---|---|---|---|---|
| Kind | reference | reference | value | value |
| `==` / `Equals` | reference equality | value equality (generated) | value equality (generated) | default `Equals` compares fields, often via reflection (slow); no `==` unless you define it |
| Positional properties | - | `init`-only | **mutable** (`readonly record struct` makes them init-only) | - |
| `with` | - | yes | yes | yes (C# 10) |

**When to use them:** DTOs and API contracts, value objects (`Money`, `DateRange`), messages and events, immutable state. Avoid records for EF Core entities that are tracked and mutated by identity: value equality conflicts with "same row = same entity" semantics.

**Pitfalls**

- Immutability is **shallow**: `record Order(List<Item> Items)` can't reassign `Items`, but anyone can `Add` to the list. And equality on a list property compares **references**, so two orders with equal items aren't equal. Use `ImmutableArray<T>` or override `Equals`.
- Record equality also compares `EqualityContract` (the runtime type), so a base record and a derived record with the same values are not equal.

**The `Equals` / `GetHashCode` contract**

If you override equality yourself (for a class or a plain struct):

1. **Equal objects must have equal hash codes.** Unequal objects may collide.
2. The hash code must not change while the object is used as a key, so base it on immutable fields.
3. `Equals` must be reflexive, symmetric and transitive, and `Equals(null)` returns `false`.

```csharp
public sealed class Sku : IEquatable<Sku>
{
    public Sku(string code) => Code = code.ToUpperInvariant();
    public string Code { get; }

    public bool Equals(Sku? other) => other is not null && Code == other.Code;
    public override bool Equals(object? obj) => Equals(obj as Sku);
    public override int GetHashCode() => Code.GetHashCode();          // for several fields: HashCode.Combine(a, b)
    public static bool operator ==(Sku? l, Sku? r) => Equals(l, r);
    public static bool operator !=(Sku? l, Sku? r) => !Equals(l, r);
}
```

Break rule 1 and a `Dictionary` or `HashSet` looks in the wrong bucket: `set.Contains(equalItem)` returns `false`. Mutate a key after inserting it and you can't find it again. Implementing `IEquatable<T>` also avoids boxing for structs in generic collections.

**Follow-up:** can you customize a record's equality? (Yes: declare `public virtual bool Equals(Money? other)` and `GetHashCode()` yourself in a `record class`, or `public bool Equals(...)` in a `record struct`; the compiler uses yours instead of generating them, and `==` follows.)
