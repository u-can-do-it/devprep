## Hints

- For each thing you configured: what kept going wrong before you added it?
- Which of your rules are advice to the model, and which are enforced?
- What did you try and then remove because it didn't help?

## Answer

> Interviewers ask this to see whether you shape your tools or only type prompts. Don't list features. Pick three or four things you built, and for each say what problem kept repeating, which mechanism you chose and why, and what changed. Show that you know the difference between advice (`CLAUDE.md`, skills) and enforcement (hooks, permissions), that you share the setup with the team, and that you removed what didn't work.

A good answer is a short tour of **your** setup with reasons. Each item follows the same pattern: **recurring problem → mechanism → result**.

**What a realistic setup contains**

| Layer | Example | Problem it solved |
|---|---|---|
| `CLAUDE.md` | build, test and lint commands, "money is in cents", "don't edit `src/gen`" | the agent guessed commands and broke generated files |
| Permissions | allow `pnpm test *` and `git diff *`; deny reading `.env` and `git push` | constant permission prompts, and risk around secrets |
| Hook: format on edit | `PostToolUse` on `Edit\|Write` runs Prettier on the file | diffs full of formatting noise |
| Hook: protect files | `PreToolUse` blocks edits to lockfiles and migrations already on `main` | the agent "fixed" a merged migration |
| Hook: `Stop` check | runs the type check and sends errors back | "done" while the build was red |
| Hook: notification | desktop notification when the agent waits for input | you came back to a session that had been idle for ten minutes |
| Skill: `/add-migration` | steps, the backfill pattern, a check script | every migration needed the same three corrections |
| Skill: `/release` | changelog, version bump, tag; only you can invoke it | a manual checklist people skipped |
| Subagent: reviewer | read-only tools, a review checklist, fresh context | self-review in the same context missed things |
| MCP servers | issue tracker, read-only database schema, browser for UI checks | copying tickets and schemas into prompts by hand |

**What the interviewer listens for**

- **A reason for each item.** "I added a hook because the agent forgot to format in about one session in five" beats "I use hooks".
- **The right mechanism:** facts in `CLAUDE.md`, procedures in skills, guarantees in hooks and permissions (#653).
- **Team thinking:** `.claude/` is committed and reviewed, personal preferences stay in `~/.claude` or `settings.local.json`, and bigger setups are shared as a plugin (#541).
- **Safety:** read-only tools by default, no production credentials, secrets denied, hooks reviewed like scripts (#525).
- **Pruning:** what you removed. Too many MCP servers eat context; a long `CLAUDE.md` gets ignored; a skill that never triggers is dead weight.
- **Evidence:** fewer corrections per task, fewer review comments about formatting, agent PRs that merge without rework (#543).

**Example answer** (replace with your own)

> "Three things made the biggest difference. First, a short `CLAUDE.md` with the commands and four traps specific to our repo; before that the agent kept running the whole test suite instead of one file. Second, two hooks: one formats each edited file, one blocks edits to migrations that are already merged, because the agent once rewrote one to make a test pass. I chose hooks there because a line in `CLAUDE.md` had been ignored twice. Third, a skill for adding an API endpoint that points to our best existing module and ends with the contract tests; new endpoints now pass review with one or two comments instead of ten. I also removed things: I had six MCP servers enabled and kept two, the issue tracker and a read-only schema server, because the rest were just taking context."

**If your setup is small, say so and reason about it:** "I use a `CLAUDE.md` and permission rules. The next thing I'd automate is formatting, with a hook, because I fix it by hand in most sessions." An honest small setup with clear reasoning is better than a list of installed packs.

**Red flags:** "I installed a pack of 50 skills" (you don't know what they do), auto-approving everything with no sandbox, rules repeated in capitals in a prompt instead of enforced, and not being able to say what any single item improved.

**Follow-up:** which of these would you set up first in a new team, and how would you get colleagues to adopt it?
