## Hints

- Which kind of test is cheapest to write and fastest to run?
- What does a unit test deliberately not exercise that an integration test does?
- Why shouldn't most of your tests drive a real browser?

## Answer

The test pyramid says you should have **many fast, cheap tests at the bottom and few slow, expensive ones at the top**.

- **Unit tests (base):** test a single function, class, or component in isolation. Milliseconds each, precise failures, no network or DB. Example: a price-calculation function.
- **Integration tests (middle):** check that pieces work together — an API route with a real test database, a React component with its hooks and context, a service calling a mocked external API. Slower but catch wiring and contract bugs that unit tests miss.
- **End-to-end tests (top):** drive the whole system like a user would (Playwright, Cypress): browser → frontend → backend → DB. Highest confidence, but slow, brittle, and hard to debug. Keep them for critical journeys like login and checkout.

```ts
// unit (Vitest)
test('applies 10% discount', () => {
  expect(applyDiscount(100, 0.1)).toBe(90);
});

// e2e (Playwright)
test('user can log in', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill('a@b.com');
  await page.getByLabel('Password').fill('pw');
  await page.getByRole('button', { name: 'Sign in' }).click();
  await expect(page.getByText('Dashboard')).toBeVisible();
});
```

Anti-pattern: the **ice-cream cone** — mostly manual and E2E tests, few unit tests. Some frontend teams prefer the "testing trophy", which emphasizes integration tests; the underlying goal is the same — maximum confidence per unit of cost.
