## Hints

- What would a reviewer prefer to read: "fix typo", "wip", "fix again", or three logical commits?
- How can you mark a commit as a fix for an earlier commit so it's merged in automatically?
- Why is rewriting history on a shared branch dangerous, and what's the safer way to force-push?

## Answer

`git rebase -i <base>` opens an editor listing your commits, oldest first. You change the command in front of each one:

- `pick`: keep as is
- `reword`: change the message
- `squash`: merge into the previous commit and combine messages
- `fixup`: merge into the previous commit and discard this message
- `edit`: stop to amend or split the commit
- `drop`: remove the commit
- reorder lines to reorder commits

```bash
git fetch origin
git rebase -i origin/main      # everything on my branch since main

# while working: mark a fix for an earlier commit
git commit --fixup=a1b2c3d
git rebase -i --autosquash origin/main   # fixups move into place automatically

git push --force-with-lease    # update the PR branch safely
```

**Why clean up:** small logical commits ("add user model", "add signup endpoint", "add tests") make review, `git bisect`, reverts and changelogs much easier.

**Rules:**
- Only rewrite commits **that no one else has built on**, typically your own feature branch.
- Use `--force-with-lease`, which refuses to overwrite remote commits you haven't seen, instead of `--force`.
- If things go wrong: `git rebase --abort` during the rebase, or `git reflog` afterwards.
- `--update-refs` keeps stacked branches in sync when you rebase the bottom one.

**Follow-up:** "Why not just squash-merge every PR?" That's fine for small PRs and very common. Interactive rebase matters when a PR should keep several meaningful commits, or for cleaning up before review.
