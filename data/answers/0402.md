## Hints

- What triggers a workflow to run in the first place?
- Do two jobs in the same workflow run one after another or at the same time by default?
- How would you test your code on Node 22 and Node 24 without copying the job?

## Answer

A **workflow** is a YAML file in `.github/workflows/`. It is made of:

- **Events (`on`)**: what triggers it: `push`, `pull_request`, `schedule` (cron), `workflow_dispatch` (manual), `release`, and others.
- **Jobs**: units of work that each run on a fresh **runner** (a GitHub-hosted or self-hosted VM). Jobs run **in parallel by default**. Use `needs` to order them. Jobs don't share a filesystem, so pass files with artifacts.
- **Steps**: sequential commands inside a job. They share the job's workspace. A step is either a shell command (`run`) or a reusable **action** (`uses`).
- **Actions**: reusable packaged steps, e.g. `actions/checkout`, `actions/setup-node`.

```yaml
name: CI
on:
  pull_request:
  push: { branches: [main] }
permissions: { contents: read }
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix: { node: [22, 24] }
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: "${{ matrix.node }}", cache: npm }
      - run: npm ci
      - run: npm test
  deploy:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production
    steps:
      - run: echo "deploying..."
```

Other concepts worth naming: **matrix** builds, **caching** dependencies, **secrets** and **environments** (with required reviewers), **reusable workflows** (`workflow_call`), and `concurrency` groups to cancel outdated runs.

**Follow-up:** "How do you share a build output between jobs?" Upload it with `actions/upload-artifact` and download it in the dependent job.
