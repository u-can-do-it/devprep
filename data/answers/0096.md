## Hints

- Where in an HTTP request can a version number live?
- What counts as a breaking change versus an additive one?
- How do you get clients off an old version?

## Answer

**Common strategies:**

1. **URI path** – `/v1/orders`. Very explicit, easy to route, cache and test in a browser. Most common choice.
2. **Query parameter** – `/orders?version=2`. Easy but messy; easy to forget.
3. **Custom header** – `Api-Version: 2024-10-01`. Keeps URIs clean. Stripe uses date-based versions pinned per account.
4. **Media type / content negotiation** – `Accept: application/vnd.acme.v2+json`. Most "pure REST" but harder for clients and tooling.

**What matters more than the mechanism:**

- **Avoid breaking changes** where possible. Adding optional fields or new endpoints is non-breaking; renaming/removing fields, changing types or semantics is breaking.
- Clients should be **tolerant readers** (ignore unknown fields).
- Version only for breaking changes, and keep the number of live versions small.
- Have a **deprecation policy**: announce, add `Deprecation` and `Sunset` headers, monitor usage per version, then remove.

```http
HTTP/1.1 200 OK
Deprecation: true
Sunset: Wed, 01 Apr 2027 00:00:00 GMT
Link: </v2/orders>; rel="successor-version"
```

**My default:** URI major version (`/v1`) for public APIs because it's obvious and cache-friendly, plus additive evolution within a version. For internal APIs with controlled clients, often no versioning – just evolve compatibly.

**Follow-up:** How does GraphQL avoid versioning? (Additive schema evolution plus `@deprecated` fields.)
