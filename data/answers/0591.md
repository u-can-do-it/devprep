## Hints

- Why is collecting only the youngest objects most of the time cheap, and what does a gen2 collection cost?
- What is special about objects of 85,000 bytes or more?
- Why is a finalizer a bad way to close a file handle, and what does `SafeHandle` do instead?

## Answer

.NET uses a **tracing, generational, compacting** garbage collector. It starts from **roots** (static fields, locals on thread stacks, CPU registers, GC handles), marks every reachable object, then frees or compacts the rest. There's no reference counting, so cycles aren't a problem.

**Generations**

| Heap | Holds | Collected |
|---|---|---|
| Gen 0 | new allocations | very often, cheap |
| Gen 1 | objects that survived one GC; a buffer between young and old | often |
| Gen 2 | long-lived objects (caches, singletons) | rarely; a **full GC**, expensive |
| LOH | objects ≥ 85,000 bytes (mostly large arrays and strings) | only with gen 2, not compacted by default |
| POH | pinned arrays from `GC.AllocateArray(..., pinned: true)` | with gen 2 |

The idea is that **most objects die young**. Allocating is just bumping a pointer; the cost is in what **survives**, because survivors get copied and promoted. The worst pattern is "mid-life" objects that live just long enough to reach gen 2 and then die, which leads to frequent full GCs. Large temporary buffers hit the LOH and fragment it: pool them with `ArrayPool<T>` (#593).

**Workstation vs server GC**

| | Workstation | Server |
|---|---|---|
| Heaps | one | one per core |
| GC work | on the thread that triggered it | dedicated GC threads, in parallel |
| Optimized for | low memory, UI responsiveness | throughput |
| Default for | console and desktop apps | ASP.NET Core apps (the Web SDK turns it on) |

Since .NET 9, server GC uses **DATAS** (dynamic adaptation to application size) by default: it starts with fewer heaps and grows with the load, so small containers don't reserve memory as if they ran on a 64-core box. The GC respects container memory limits; you can cap it further with `GCHeapHardLimit`.

**Background GC** (on by default) collects gen 2 concurrently with your threads, and gen 0/1 collections can still happen meanwhile. There are still short pauses, just not one long stop-the-world for the whole heap. For latency-sensitive sections there are `GCSettings.LatencyMode = GCLatencyMode.SustainedLowLatency` and `GC.TryStartNoGCRegion`. Calling `GC.Collect()` yourself is almost always wrong.

**Finalizers are expensive and unreliable**

An object with a finalizer (`~MyType()`) is tracked from the moment it is allocated. When it becomes unreachable it **survives that GC**, waits for the single finalizer thread to run its finalizer, and is only freed by a later GC. The order isn't defined, other managed objects it references may already be finalized, and .NET (Core) doesn't run finalizers on process exit. A finalizer is a safety net, never the cleanup mechanism.

**Deterministic cleanup: `IDisposable` and `SafeHandle`**

If you hold an unmanaged resource, wrap the raw handle in a `SafeHandle` subclass. It owns the (critical) finalizer and protects the handle from being released or recycled while a P/Invoke call is still using it. Your class then just implements `IDisposable`, with no finalizer of its own:

```csharp
public sealed class NativeBuffer : IDisposable
{
    private readonly MyNativeHandle _handle = NativeMethods.CreateBuffer();  // a SafeHandle
    public void Dispose() => _handle.Dispose();
}

// The full pattern, for unsealed base classes that derived classes may extend
public class ResourceBase : IDisposable
{
    private bool _disposed;

    public void Dispose()
    {
        Dispose(disposing: true);
        GC.SuppressFinalize(this);          // a derived class might add a finalizer
    }

    protected virtual void Dispose(bool disposing)
    {
        if (_disposed) return;
        if (disposing) { /* dispose managed IDisposable fields */ }
        /* release raw unmanaged resources here, if you hold any */
        _disposed = true;
    }
}
```

Use `IAsyncDisposable` and `await using` when cleanup does I/O (flushing a stream, closing a connection).

**"Memory leaks" in a GC'd runtime** are references that keep objects alive: static or singleton caches without eviction, event handlers on long-lived publishers (#576), captive dependencies (#581), timers, an unbounded `IMemoryCache` (#598). Check `dotnet-counters` for GC heap size, % time in GC and gen 2 counts, and compare heap dumps to find the root (#594).

**Follow-up:** p99 latency spikes every few minutes. How do you check whether it's the GC? (Watch gen 2 count, % time in GC and the allocation rate with `dotnet-counters` and line them up with the spikes. Usual causes are large temporary allocations on the LOH or mid-life objects; reduce allocations, pool buffers, and only then tune GC settings.)
