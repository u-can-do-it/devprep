## Hints

- What can a malicious package do the moment you run `npm install`, before you ever import it?
- How do you stop a brand-new compromised release of a dependency from reaching production?
- If a dependency is compromised at runtime, what limits what it can read, write or spawn?

## Answer

Supply-chain attacks (typosquatting, hijacked maintainer accounts, self-spreading worms that steal npm and cloud tokens) target the install step and the runtime. Defend both.

**Install time**

- **Commit the lockfile** and use frozen installs in CI (`npm ci`, `pnpm install --frozen-lockfile`) so only reviewed versions install.
- **Block lifecycle scripts**: `npm ci --ignore-scripts`, or pnpm 10+, which doesn't run dependency `postinstall` scripts unless you allow-list them.
- **Delay brand-new versions** (pnpm `minimumReleaseAge`, Renovate's minimum release age). Most malicious releases are found and pulled within days.
- Run `npm audit` / Dependabot / Socket, and check provenance with `npm audit signatures`. Publish your own packages with `--provenance` or trusted publishing, and use 2FA.
- Keep dependencies few and well-maintained. Remove unused ones.

**Runtime: the permission model**

```bash
node --permission \
  --allow-fs-read=/app --allow-fs-write=/app/tmp \
  server.js
```

With `--permission`, file system access outside the allowed paths, child processes, worker threads, native addons and WASI are **denied by default** and throw `ERR_ACCESS_DENIED`. You opt in with `--allow-child-process`, `--allow-worker` and similar flags. Code can check `process.permission.has('fs.write', path)`.

Its limits: Node's docs describe it as a **seat belt, not a sandbox**. It applies to the whole process (not per package) and doesn't stop malicious code that is already running from abusing what you allowed. Combine it with OS-level isolation: non-root containers, read-only filesystems, no secrets in the build environment, and egress restrictions.
