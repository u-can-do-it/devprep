## Hints

- How does the iterator protocol change when `next()` returns a promise?
- How would you go through a paginated API one page at a time, without loading every page first?
- What runs when you `break` out of a `for await` loop early?

## Answer

An **async iterator** is an object whose `next()` returns a **promise** of `{ value, done }`. An object is **async iterable** if it has a `[Symbol.asyncIterator]()` method. `for await...of` consumes it, awaiting each step.

An **async generator** (`async function*`) is the easy way to write one. Inside it you can both `await` and `yield`:

```js
async function* fetchAllPages(url) {
  let next = url;
  while (next) {
    const res = await fetch(next);
    const { items, nextPage } = await res.json();
    yield* items;                   // hand out items one by one
    next = nextPage;
  }
}

for await (const order of fetchAllPages('/api/orders')) {
  if (order.total > 1000) break;   // stops fetching further pages
}
```

**Why it's useful:**

- **Pull-based and lazy:** the next page is fetched only when the consumer asks for it, which gives you natural backpressure.
- **Streams:** Node readable streams and web `ReadableStream`s (in Node and most modern browsers) are async iterable, so you can process data chunk by chunk.
- **Event sources:** you can wrap WebSocket messages or server-sent events in a clean loop.
- **Cleanup:** `break`, `return` or a thrown error calls the iterator's `return()`, which runs the generator's `finally` block. That's where you close connections.

**Helpers:** `Array.fromAsync(iterable)` collects everything into an array.

**Pitfalls:**

- `for await` processes items **one at a time**. For parallelism, use a concurrency-limited pool instead.
- `for await (const x of arrayOfPromises)` is risky. If a later promise rejects while you are still waiting for an earlier one, that rejection may be reported as unhandled.
- Don't use async generators for CPU-heavy work. They only help with things you wait on.
