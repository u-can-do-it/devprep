## Hints

- Where should a database container store its data so it survives a restart or recreation?
- What's the difference between letting Docker manage storage and mounting a host folder?
- How does one container find another — by IP or by name?

## Answer

**Storage options:**

- **Named volumes:** managed by Docker, persist independently of containers. Best for databases and production data.
- **Bind mounts:** map a host path into the container. Great for local development (live code reload), but tied to the host's file layout and permissions.
- **tmpfs:** in-memory, for sensitive or temporary data.

**Networking:**

- The default `bridge` network gives containers private IPs, but on a **user-defined bridge network** Docker provides built-in DNS, so containers reach each other by **service/container name**.
- `-p 8080:3000` publishes container port 3000 on host port 8080 — needed only for access from outside Docker.
- `host` network shares the host's network stack (no isolation); `none` disables networking.

```yaml
# compose.yaml
services:
  api:
    build: .
    ports: ["8080:3000"]
    environment:
      DATABASE_URL: postgres://app:secret@db:5432/app   # "db" resolves via DNS
    depends_on: [db]
  db:
    image: postgres:17
    volumes: [pgdata:/var/lib/postgresql/data]
volumes:
  pgdata:
```

Compose creates a shared network automatically, so `api` connects to `db` by name; the database doesn't need a published port at all.

**Pitfall:** using `localhost` inside a container to reach another container — `localhost` refers to the container itself.
