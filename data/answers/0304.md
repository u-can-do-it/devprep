## Hints

- Why is `console.log('user created ' + id)` hard to search across 50 instances?
- Which signals tell you *that* something is wrong, and which tell you *where*?
- How do you connect one slow request's log lines to the trace of the downstream calls it made?

## Answer

The three pillars, all correlated by a request or trace ID:

**Logs: structured JSON**

- Use a fast structured logger such as **pino**. Write one JSON object per line to stdout and let the platform ship it (Fluent Bit, Datadog agent, CloudWatch).
- Use levels (`debug` only when needed), **child loggers** with `requestId`, `userId` and `traceId`, and **redaction** of secrets and PII.
- Log events with context, not prose: `log.info({ orderId, ms }, 'order placed')`.

```js
import pino from 'pino';
export const logger = pino({
  level: process.env.LOG_LEVEL ?? 'info',
  redact: ['req.headers.authorization', '*.password'],
});
```

**Metrics: is it healthy?**

- RED per endpoint: **R**ate, **E**rrors, **D**uration (histograms, so you get p95/p99).
- Node-specific: **event loop delay** (`perf_hooks.monitorEventLoopDelay`), heap usage, GC time, active handles. Pool saturation for the DB and HTTP clients.
- Expose them via Prometheus (`prom-client`) or OpenTelemetry metrics. Alert on SLOs, not on every error.

**Traces: where did the time go?**

- **OpenTelemetry** auto-instrumentation for http, undici/fetch, pg, redis and Express/Fastify. Load it before the app (`node --import ./otel.js server.js`) so modules get patched.
- Propagate W3C `traceparent` headers across services. Inject `trace_id` into logs so you can jump from a log line to the trace.

Practices: sample traces (keep all errors and slow ones), keep label cardinality low (never `userId` as a metric label), don't log full request bodies, and make health and readiness endpoints cheap.

**Follow-up:** Why can heavy synchronous logging hurt latency? (Writes to files and pipes can be synchronous, so pino uses transports in worker threads.)
