## Hints

- Before PPR, what happened to a whole route if one small component read `cookies()`?
- During `next build`, what does Next.js do when rendering reaches a component that needs request data or uncached I/O?
- Why would the build insist that this component be either cached or wrapped in `<Suspense>`?

## Answer

**The problem.** In the classic model, rendering was decided **per route**: one runtime API call (`cookies()`, `headers()`, `searchParams`) or one uncached fetch made the *whole* page dynamic, even if 95% of it was the same for everyone.

**Partial Prerendering (PPR)** splits a route into a **static shell** and **dynamic holes**. In Next.js 16 it's the default rendering model once you enable **Cache Components** (`cacheComponents: true`).

**How the shell is built.** At build time, Next.js renders the tree and looks at what each component does:

- Synchronous or pure work, module imports → **included** in the shell.
- **`'use cache'`** functions or components → executed, cached, **included** (unless the `cacheLife` is too short to be useful).
- **Runtime APIs** (`cookies`, `headers`, `searchParams`, unknown `params`), **uncached I/O** (fetch, DB), or `connection()` → prerendering can't finish there. If that component sits under a **`<Suspense>`** boundary, the **fallback** goes into the shell and the content is rendered at request time.

```tsx
export default function ProductPage() {
  return (
    <>
      <ProductDetails />                    {/* 'use cache' + cacheTag -> in shell */}
      <Suspense fallback={<CartSkeleton />}>
        <Cart />                            {/* reads cookies() -> streamed per request */}
      </Suspense>
    </>
  );
}
```

On a request, the shell (HTML + RSC payload) is sent immediately, possibly from a CDN, and the holes **stream in the same HTTP response**.

**Why it forces you to choose.** If dynamic or uncached access happens **outside** any Suspense boundary, there's no valid fallback, so the route can't produce a shell. Next.js reports a "blocking route" error in dev and at build time. You must explicitly:

1. **cache it** (`'use cache'`, with `cacheLife`/`cacheTag`), or
2. **defer it** (wrap it in `<Suspense>`, and use `connection()` for random or time-based values), or
3. pass runtime values **as arguments** into a cached function. `cookies()` inside `'use cache'` is an error.

**Design implications:** read runtime data as **deep** in the tree as possible (pass the `params` promise down instead of awaiting it in a layout); `Math.random()`/`Date.now()` need `connection()` or caching; streaming must work end to end through your proxies.

**Follow-up:** compare this with ISR: ISR caches whole pages. PPR caches per component and keeps personalization without giving up a CDN-served first byte.
