## Hints

- What's the ratio of reads (redirects) to writes (new links), and how should that shape the design?
- How would you generate short codes that are unique without a slow coordination step?
- Should the redirect be a 301 or a 302 — and how does that affect analytics?

## Answer

**Clarify requirements:** create short link (optional custom alias, expiry), redirect fast, basic click analytics. Scale assumption: ~100M new links/month, reads ~100x writes. Redirect latency should be low; availability matters more than strict consistency.

**API:**

```http
POST /api/links   { "url": "https://...", "alias": "optional" }  -> 201 { "code": "aZ3kP9q" }
GET  /aZ3kP9q     -> 302 Location: https://...
```

**Short code generation:** 7 base62 characters give 62^7, about 3.5 trillion codes.

- **Counter + base62 encoding:** unique by construction. Use a distributed ID generator or hand out ID ranges to each app server to avoid a single bottleneck. Downside: sequential codes are guessable — shuffle/obfuscate if that matters.
- **Random code** with a uniqueness check (unique index; retry on collision).
- Hashing the URL causes collisions and must handle duplicates — usually not preferred.

**Storage:** a key-value lookup `code → {url, owner, created_at, expires_at}`. A sharded SQL table or a NoSQL store (DynamoDB/Cassandra) keyed by code both work; a unique constraint protects against duplicates.

**Read path:** CDN/edge → app → **Redis cache** (hot links, LRU) → DB. Most traffic should be served from cache.

**301 vs 302:** a 301 is cached by browsers (less load, but you lose click tracking and can't change the target); 302/307 keeps every click hitting your service.

**Analytics:** don't write to the DB synchronously on each redirect — emit a click event to a queue/stream and aggregate asynchronously.

**Extras:** rate limiting and malicious-URL scanning for abuse, expiry cleanup jobs, multi-region read replicas.

**Follow-up:** "What if one link goes viral?" — it's a hot key; cache it at the edge/CDN and in local in-memory caches.
