## Hints

- If a refresh token is stolen and both the attacker and the real client keep using it, how could the server notice?
- What does the server need to store to tell an old refresh token from the current one?
- Once an access token is issued, how long can a stolen one be used, and what are your options to shorten that?

## Answer

**Setup:** short-lived **access tokens** (5–15 min, often JWTs, verified statelessly) and long-lived **refresh tokens** (days/weeks, opaque, stored server-side as a hash). For browsers, keep the refresh token in an `HttpOnly; Secure; SameSite=Strict` cookie scoped to the refresh path, or better, use a backend-for-frontend so tokens never reach JS.

**Rotation:** every refresh returns a **new refresh token** and invalidates the old one. All tokens from one login share a **family ID**.

**Reuse detection:** if a refresh token that was **already used** shows up again, two parties hold it, and one is an attacker. Revoke the **whole family** and force re-login.

```sql
CREATE TABLE refresh_tokens (
  id          uuid PRIMARY KEY,
  family_id   uuid NOT NULL,
  user_id     uuid NOT NULL,
  token_hash  bytea NOT NULL UNIQUE,
  used_at     timestamptz,
  revoked_at  timestamptz,
  expires_at  timestamptz NOT NULL
);
```

Refresh endpoint logic (in one transaction, row locked):

1. Look up by hash. Unknown, expired or revoked: reject.
2. If `used_at` is set: **reuse** detected, revoke all tokens with that `family_id`, alert, reject.
3. Otherwise mark it used, insert a new token in the same family, issue a new access token.

Edge case: a client legitimately retries after a network failure. Allow a short **grace window** (a few seconds) where the previous token returns the same new pair instead of triggering revocation.

**Fast revocation of access tokens:**

- Keep them short-lived, so revoking the family stops access within minutes.
- For instant cut-off (fired employee, compromised account): a denylist of token IDs (`jti`) or a per-user "tokens issued before" timestamp in Redis, checked at the gateway; or use opaque tokens with introspection for high-risk APIs.
- **Sender-constrain** tokens (DPoP, mTLS) so a stolen token is useless without the client's private key. The OAuth 2.0 Security BCP (RFC 9700) requires public clients' refresh tokens to be either rotated or sender-constrained.

**Follow-up:** Also revoke families on logout, password change and suspicious activity, and set an absolute family lifetime so rotation can't extend a session forever.
