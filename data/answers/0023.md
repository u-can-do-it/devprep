## Hints

- What happens if you declare the same `interface` name twice? And the same `type` name?
- Can an `interface` describe a union or a tuple?
- How do `extends` and `&` differ when properties conflict?

## Answer

Both can describe the shape of an object, and in most code they are interchangeable. The differences:

**Only `type` can:**

- Name **unions**, primitives, tuples, and function types: `type Id = string | number`, `type Pair = [number, number]`.
- Use **mapped and conditional types**: `type ReadonlyUser = { readonly [K in keyof User]: User[K] }`.
- Be built from template literal types and other type expressions.

**Only `interface` can:**

- Use **declaration merging**. Two declarations with the same name are combined into one type:

```ts
interface User { name: string }
interface User { age: number }

const u: User = { name: 'Ann' };       // ❌ Property 'age' is missing — User now has both fields
const ok: User = { name: 'Ann', age: 30 }; // ✅

type Point = { x: number }
type Point = { y: number }             // ❌ Duplicate identifier 'Point'
```

This is how you add fields to types you don't own, such as globals or library types:

```ts
window.analytics.track('signup');      // ❌ Property 'analytics' does not exist on type 'Window'

// globals.d.ts
declare global {
  interface Window { analytics: Analytics }            // merges into the built-in Window
  namespace Express { interface Request { user?: User } } // merges into Express's Request
}
export {};

window.analytics.track('signup');      // ✅
app.get('/me', (req, res) => res.json(req.user));      // ✅ req.user is typed
```

**Extending:** the difference shows up when a property conflicts.

```ts
interface Animal { name: string }

interface Dog extends Animal { name: number }
// ❌ error right here: Interface 'Dog' incorrectly extends interface 'Animal'.
//    Types of property 'name' are incompatible.

type Cat = Animal & { name: number }   // no error here...
// Cat['name'] is string & number, which is `never`

const c: Cat = { name: 'Tom' };        // ❌ ...only here: Type 'string' is not assignable to type 'never'
```

`interface extends` reports incompatible properties right where you declare them. An intersection accepts the conflict, and you only find out later when no value fits. Interfaces are also cached by name, so the compiler often checks them faster than large intersections.

**Classes** can `implements` either one, as long as the type is an object type.

**Practical guidance:**

- Many teams use `interface` for public object shapes and contracts, especially in libraries, because consumers can extend them.
- Use `type` for unions, utility compositions and everything else.
- Being consistent matters more than which rule you pick. The official handbook leans toward `interface` until you need a feature only `type` has.

**Follow-up:** "Why might accidental declaration merging be a problem?" Two files can silently add to the same global interface.
