## Hints

- Is `fastapi dev` / `uvicorn --reload` suitable for production? Why not?
- In Kubernetes, should one container run several worker processes or just one?
- How does the app learn the real client IP and scheme when it sits behind a load balancer?

## Answer

FastAPI is an ASGI app. In production it runs under an **ASGI server (Uvicorn)**, usually in a **container** behind a **reverse proxy or load balancer** that terminates TLS.

**Processes: use multiple cores.** One Uvicorn process uses one core for Python code.

- **On Kubernetes/ECS**: usually **one process per container**, and scale by **replicas**. The orchestrator handles restarts, health checks and load balancing, and memory and CPU limits stay predictable.
- **On a single VM**: run several workers in one place: `fastapi run --workers 4`, `uvicorn app.main:app --workers 4`, or Gunicorn as a process manager with Uvicorn workers (the `uvicorn-worker` package). Workers ≈ CPU cores is a starting point.

```dockerfile
FROM python:3.13-slim
COPY --from=ghcr.io/astral-sh/uv:latest /uv /bin/uv
WORKDIR /app
COPY pyproject.toml uv.lock ./
RUN uv sync --locked --no-dev
COPY app ./app
USER 1000
CMD ["/app/.venv/bin/fastapi", "run", "app/main.py", "--port", "8000", "--proxy-headers"]
```

Checklist:

- **Exec-form `CMD`** so `SIGTERM` reaches Uvicorn for a graceful shutdown. Lifespan cleanup runs then.
- **Proxy headers**: `--proxy-headers` plus trusted proxy IPs (Uvicorn's `--forwarded-allow-ips` or the `FORWARDED_ALLOW_IPS` env var), so `request.client` and `https` URLs are correct. Use `root_path` if the app is served under a path prefix.
- **Health endpoints** for liveness and readiness. Readiness should check dependencies cheaply.
- **No `--reload`** and no debug mode. Disable or protect `/docs` if needed.
- **Each worker is a separate process**: in-memory caches, rate limiters and WebSocket connections aren't shared. Use Redis for shared state. The DB pool is per worker, so size it accordingly.
- Timeouts at the proxy, request size limits, structured logs to stdout, and OpenTelemetry instrumentation.
- Run CPU-heavy or long jobs in a task queue (Celery, arq, Dramatiq), not in request workers.

**Follow-up:** Why can `--workers 8` in a container limited to 1 CPU make things worse? (Workers compete for one core, add memory per process and context switching, and CPU throttling worsens tail latency.)
