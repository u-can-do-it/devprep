## Hints

- When does the `else` block of a `try` statement run, and when does `finally` run?
- Why is a bare `except:` or `except Exception: pass` dangerous?
- How do you raise a domain error but keep the original low-level error for debugging?

## Answer

> Errors need to be caught at the right place and passed on with useful context. Python wraps the risky call in `try` and catches specific types with `except`, ordered from specific to general. `else` runs only on success, which keeps the `try` small, and `finally` always runs for cleanup. Define custom exceptions under one app-level base class. Use `raise NewError(...) from e` to keep the original cause visible, and avoid a bare `except:`.

```python
class AppError(Exception):
    """Base for all errors raised by this app."""

class PaymentDeclined(AppError):
    def __init__(self, order_id: int, reason: str):
        super().__init__(f"order {order_id} declined: {reason}")
        self.order_id = order_id
        self.reason = reason

def charge(order):
    try:
        resp = gateway.charge(order.total)          # only the risky call
    except gateway.CardError as e:
        raise PaymentDeclined(order.id, e.code) from e   # chain the cause
    except (TimeoutError, ConnectionError):
        log.warning("gateway unavailable")
        raise                                        # re-raise unchanged
    else:
        order.mark_paid(resp.id)                     # runs only if no exception
    finally:
        metrics.incr("charge.attempt")               # always runs
```

- **`except`** catches matching types. Order from specific to general.
- **`else`** runs only if the `try` succeeded. It keeps the `try` small, so you don't accidentally catch errors from the success path.
- **`finally`** always runs, for cleanup. Prefer `with` context managers for resources.
- **`raise X from e`** sets `__cause__`, and the traceback shows both errors. `from None` hides the original when it's irrelevant.

**Custom exceptions**: subclass `Exception` (never `BaseException`), build a small hierarchy with an app-level base class, and add useful attributes. Callers can then catch `AppError` broadly or `PaymentDeclined` precisely, and an API layer can map them to HTTP status codes.

Pitfalls: bare `except:` also catches `KeyboardInterrupt` and `SystemExit`. Swallowing errors silently hides bugs. Using exceptions for normal control flow in hot loops is slow and unclear.

Modern additions: `e.add_note("context")` (3.11) and `ExceptionGroup` with `except*` for multiple concurrent failures, for example from `asyncio.TaskGroup`.

**Follow-up:** What's the difference between `raise` and `raise e` inside an `except` block? (Bare `raise` re-raises the active exception with its traceback intact. `raise e` adds the current line to the traceback.)
