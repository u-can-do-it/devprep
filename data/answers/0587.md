## Hints

- What should a client see when your code throws a `NullReferenceException`, and what should it never see?
- Which errors are expected (a duplicate email, an order that doesn't exist) and which are bugs?
- What does RFC 9457 ProblemDetails standardise, and why does that help frontends?

## Answer

Split errors into two kinds and handle them differently:

- **Expected failures** (validation, not found, conflict, business rule broken) are part of the API contract. Return a 4xx with details.
- **Unexpected failures** (bugs, database down) should be logged with full detail and returned as a generic 500, never with a stack trace.

**ProblemDetails everywhere**

ProblemDetails (RFC 9457, formerly 7807) is a standard JSON error body: `type`, `title`, `status`, `detail`, `instance`, plus extensions such as `errors` or `traceId`. One format means the frontend has one error parser.

```csharp
builder.Services.AddProblemDetails();                        // consistent bodies for 4xx/5xx
builder.Services.AddExceptionHandler<GlobalExceptionHandler>();

app.UseExceptionHandler();   // early in the pipeline, catches what later middleware throws
app.UseStatusCodePages();    // ProblemDetails for empty 404/405 responses too
```

**`IExceptionHandler`** (.NET 8+) is the clean place to map exceptions to responses:

```csharp
public sealed class GlobalExceptionHandler(ILogger<GlobalExceptionHandler> log,
    IProblemDetailsService problems) : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(HttpContext ctx, Exception ex, CancellationToken ct)
    {
        var status = ex switch
        {
            ConcurrencyConflictException => StatusCodes.Status409Conflict,
            _ => StatusCodes.Status500InternalServerError,
        };
        if (status == 500) log.LogError(ex, "Unhandled exception");   // details go to logs only

        ctx.Response.StatusCode = status;
        return await problems.TryWriteAsync(new() { HttpContext = ctx,
            ProblemDetails = { Status = status, Title = "Request failed" } });
    }
}
```

**Validation**

| Option | How |
|---|---|
| DataAnnotations | `[Required]`, `[Range]`, `[EmailAddress]` on the DTO. Controllers with `[ApiController]` return 400 automatically; Minimal APIs do too since .NET 10 with `builder.Services.AddValidation()` |
| FluentValidation | rules in an `AbstractValidator<T>` class, good for conditional or cross-field rules; call it from an endpoint filter or the handler |

Both should produce a `ValidationProblem` (400 with an `errors` dictionary keyed by field). Validation of the request shape belongs at the edge; business rules ("email already taken") belong in the domain or service and usually map to 409 or 422.

**Exceptions vs a Result type**

```csharp
public async Task<Result<Order>> PlaceAsync(PlaceOrder cmd) =>
    stock < cmd.Quantity ? Result.Fail(Errors.OutOfStock) : Result.Ok(order);
```

- Exceptions for expected outcomes are expensive-ish, invisible in method signatures, and easy to forget to catch.
- A `Result<T>` (hand-written, or a library like ErrorOr or FluentResults) makes failure explicit and the endpoint maps it to `TypedResults`.
- A common middle ground: `Result` for expected business failures, exceptions for truly exceptional ones, and the global handler as the safety net. Pick one convention per codebase.

**Follow-up:** a client gets a 500 in production and sends you the response. How do you find the cause? (ProblemDetails includes a `traceId`; search logs and traces by it. That's why the trace id is returned and the stack trace isn't.)
