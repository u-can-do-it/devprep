## Hints

- Can you add a library with custom native code to Expo Go?
- If the `ios/` and `android/` folders are generated, where does your native configuration live?
- Which parts of Expo are a free open-source framework, and which are a paid cloud service?

## Answer

> Expo is the framework the React Native team recommends for new apps. It is open-source libraries and tooling (Expo SDK, Expo Router, the CLI, prebuild) plus an optional cloud service, EAS. The old limit "no custom native code" is gone: a development build is your own app and can contain any native library. With Continuous Native Generation the native projects are generated from config, so you rarely edit Xcode or Gradle files by hand.

**Expo Go vs a development build**

| | Expo Go | Development build |
|---|---|---|
| What it is | a ready-made app from the store that loads your JS | your own app, built with `expo-dev-client` |
| Native modules | only those bundled in Expo Go | any library, plus your own native code |
| Good for | learning, quick prototypes | real projects |
| App name, icon, push setup, deep links | Expo's | yours |

Start a real project with a development build. You rebuild it only when native dependencies or config change; daily work is still Fast Refresh.

**Prebuild and Continuous Native Generation (CNG)**

- `npx expo prebuild` generates the `ios/` and `android/` projects from `app.json` / `app.config.ts`, your dependencies and their config plugins.
- With CNG you treat those folders as build output: they aren't committed and can be regenerated at any time.
- The benefit shows at upgrade time. Instead of merging template changes into native files by hand, you bump versions and regenerate (#701).

**Config plugins**

A config plugin is a function that changes the native project during prebuild: an `Info.plist` entry, an Android permission, a Gradle setting, an entitlement.

```json
{
  "expo": {
    "plugins": [
      ["expo-camera", { "cameraPermission": "Allow $(PRODUCT_NAME) to scan QR codes." }],
      "./plugins/with-custom-manifest.js"
    ]
  }
}
```

Most libraries ship one. For anything unusual you write your own, which keeps manual native edits reproducible.

**EAS (Expo Application Services)**

- **Build:** builds the iOS and Android binaries in the cloud, and manages certificates and keystores. You can build iOS without owning a Mac.
- **Submit:** uploads to App Store Connect and Google Play (#688).
- **Update:** over-the-air JS updates (#699).
- **Workflows:** CI pipelines for builds, tests and releases.

EAS is optional and has usage-based pricing. You can build locally (`npx expo run:ios`, `eas build --local`) or on your own CI.

**Also part of Expo**

- The **Expo SDK**: maintained modules for camera, notifications, file system, secure storage, images and more.
- The **Expo Modules API**: write native modules in Swift and Kotlin with little boilerplate (#700).
- **Expo Router** (#675).

**When a bare React Native CLI project still makes sense**

- A brownfield app, where React Native lives inside an existing native project (#705).
- A team with strong native skills and a heavily customised native build that doesn't fit generated projects.
- Company rules that exclude the tooling.

Even then you can install `expo` and use its modules. "Bare vs Expo" is no longer either-or, and "ejecting" is an outdated idea.

**Follow-up:** a library needs a line added to `AndroidManifest.xml` and has no config plugin. What do you do in a CNG project? (Write a small config plugin with `withAndroidManifest`. Don't edit the generated file, because the next prebuild overwrites it.)
