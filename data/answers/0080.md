## Hints

- Where does FastAPI run a plain `def` endpoint, and where does it run an `async def` one?
- What happens to every other request on the event loop if an `async def` endpoint calls `time.sleep(2)` or `requests.get()`?
- How can you safely call a blocking library from async code?

## Answer

- **`async def` endpoints** run directly **on the event loop**. Great for async I/O (`httpx.AsyncClient`, `asyncpg`, async SQLAlchemy) because the loop can serve other requests while awaiting.
- **`def` endpoints** run in a **threadpool** (AnyIO worker threads, default limit 40). Blocking calls there only block that thread. The same applies to sync dependencies.

The dangerous case: **blocking code inside `async def`**. The single event loop thread is stuck, so *all* concurrent requests in that worker freeze until it finishes.

```python
import asyncio, time, requests, httpx

@app.get("/bad")
async def bad():
    time.sleep(2)                       # blocks the whole loop
    return requests.get(URL).json()     # also blocking

@app.get("/ok-sync")
def ok_sync():
    return requests.get(URL).json()     # runs in threadpool

@app.get("/ok-async")
async def ok_async():
    async with httpx.AsyncClient() as client:
        r = await client.get(URL)
    report = await asyncio.to_thread(build_report)  # offload unavoidable blocking work
    return r.json()
```

Guidelines:

- Use `async def` only if everything inside is non-blocking; otherwise plain `def` is safer.
- Offload blocking calls with `asyncio.to_thread` / `run_in_threadpool`.
- CPU-heavy work belongs in a process pool or task queue; threads won't help much due to the GIL.
- The threadpool has a limit: many slow sync endpoints can exhaust it and queue requests.
- Scale across cores with multiple workers (e.g. `uvicorn --workers N` or `fastapi run --workers N`).
