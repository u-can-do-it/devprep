## Hints

- What do the `<<<<<<<`, `=======`, and `>>>>>>>` markers represent?
- How would you apply a single bug-fix commit to a release branch without merging everything else?
- If a bug appeared somewhere in the last 200 commits, how could you find the culprit in about 8 steps?

## Answer

**Resolving a merge conflict:** a conflict happens when both sides changed the same lines (or one deleted a file the other edited).

1. Run `git status` to see conflicted files.
2. Open each file, understand *both* changes, and edit to the correct combined result — not just "pick mine".
3. Remove the conflict markers, run the tests, `git add` the file, then `git commit` (or `git rebase --continue`).
4. If it goes badly: `git merge --abort` / `git rebase --abort`.

Small PRs and frequent syncing with main prevent most conflicts.

**`git cherry-pick`** copies a specific commit onto the current branch as a new commit — e.g. backporting a hotfix to a release branch.

```bash
git switch release/2.3
git cherry-pick 4f9e2ab        # use -x to record the original hash
```

**`git bisect`** binary-searches history to find the commit that introduced a bug.

```bash
git bisect start
git bisect bad                 # current commit is broken
git bisect good v2.1.0         # this version worked
# test each checkout, mark good/bad... or automate:
git bisect run npm test
git bisect reset
```

With 1,000 commits it takes about 10 steps.

**Pitfall:** cherry-picking many commits between branches creates duplicate commits with different hashes, which can cause confusing conflicts later.
