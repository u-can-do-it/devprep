## Hints

- On the web, leaving a page unmounts it. What happens to a screen when another one is pushed on top?
- A browser tab is closed within minutes or hours. How long can a mobile app stay alive in the background?
- You deployed a fix to the web five minutes ago. When do mobile users get a fix?

## Answer

> React itself transfers fully: components, hooks, state management, TanStack Query, TypeScript, Testing Library. The bugs come from assumptions about the platform under it. The big ones are: screens that stay mounted, an app that lives for days and loses its network, layout and text rules that aren't CSS, a JS thread that is easy to block on a slow phone, and releases that can't be rolled back or deployed instantly.

**1. Lifecycle assumptions**

- **"Leaving a screen unmounts it."** No: a covered screen stays mounted, and going back doesn't re-run `useEffect`. Use focus effects and query invalidation (#674).
- **"The app starts fresh each visit."** The app is suspended and resumed, sometimes after days. Data is stale, the token may have expired, the socket is dead. Refetch on app focus (#682).
- **"State in memory is safe."** The OS can kill a background app at any time. Persist what matters.

**2. Layout and styling**

- Text outside `<Text>`, including `{count && <Badge />}` rendering a bare `0`, crashes instead of just looking odd (#667, #195).
- No cascade, no inheritance, no `:hover`, no media queries. The default direction is a column (#668).
- Content doesn't scroll by default. A long form without a `ScrollView` is simply cut off.
- No `position: fixed`, no CSS Grid, no portals to `document.body`.
- Ignoring safe areas and the keyboard, so content sits under the notch or the submit button hides behind the keyboard (#679).

**3. Interaction**

- `onClick` thinking: there is no hover, targets need 44 to 48 points, and feedback on press matters.
- Ignoring platform conventions: the Android back button, swipe-back on iOS, native pickers (#670).
- Forgetting accessibility, because there is no semantic HTML to get it half-right for free (#689).

**4. Performance**

- `.map()` inside a `ScrollView` for long lists, instead of a virtualised list (#669).
- Animations driven by `setState`. They need the UI thread (#678).
- Heavy work on the JS thread: big JSON parsing, sorting large arrays in render, `console.log` left in production (#694).
- Full-size images in thumbnails (#672).
- Testing only on the iOS simulator on a fast laptop, in a debug build. Use a release build on a mid-range Android phone.

**5. Platform APIs**

- `localStorage`, cookies, `window`, `document` and most browser APIs don't exist. Libraries that touch the DOM don't work, and Node built-ins are missing.
- Tokens in AsyncStorage, the mobile version of tokens in `localStorage`. Use secure storage (#681).
- Assuming the network is there. Handle offline, timeouts and slow connections as normal states.
- Asking for all permissions at startup (#685).
- Adding a library without checking that it has native code, supports the New Architecture and is maintained. A native dependency is a long-term cost (#701).

**6. Navigation**

- Treating navigation as URL changes only, and passing whole objects as params instead of ids.
- Redirecting by hand after login instead of rendering screens based on the session.

**7. Release thinking**

- **No instant deploy and no rollback.** Store review takes time, and a bad build stays on users' phones (#688).
- **Old versions live for months,** so the API must stay backward compatible.
- **Feature flags and over-the-air updates** are the safety net, with limits (#699).
- Secrets in the bundle are as public as on the web (#698).

**What helps a web developer most**

Build one small feature end to end on a real device: a list, a details screen, a form with the keyboard, and a release build. Most of the points above show up in the first week.

**Follow-up:** which web skills give you an advantage on a React Native team? (State and data-fetching architecture, TypeScript, testing habits, performance profiling of React renders, accessibility thinking, and API design for clients that update slowly.)
