## Hints

- In a brownfield app, who owns the app's entry point and its navigation stack?
- Starting the JavaScript runtime takes time. When do you pay that cost?
- Do the native developers need Node and Metro on their machines to build the app?

## Answer

> In a brownfield setup the native app stays the host, and React Native renders some screens inside it. You embed a React Native root view in a view controller or fragment, start one shared runtime for all React Native screens, and let native code own navigation. Session, configuration and analytics come from the native side through a small native module. To keep the native team's workflow unchanged, the React Native part is delivered as a prebuilt framework with the JS bundle inside. The costs are two navigation systems, a boundary to debug across, and a larger app.

**Why do it**

- A large native app exists, and rewriting it isn't an option.
- New features should be built once for both platforms, or shared between several apps.
- It is a low-risk way to evaluate React Native: one self-contained feature, then decide.

**1. Embedding**

- **iOS:** a React Native factory creates a root view for a registered component name, and you put it in a `UIViewController`.
- **Android:** a `ReactFragment` or `ReactActivity` hosts the surface, managed by a `ReactHost`.
- JS registers each entry point: `AppRegistry.registerComponent('Checkout', () => Checkout)`. One bundle can contain many of them.
- Initial props carry what the screen needs to start: an id, the locale, the theme.

**2. One runtime, started at the right time**

- Create **one** React Native instance for the whole app, and attach many surfaces to it. One instance per screen wastes memory and startup time.
- Starting the runtime costs a noticeable fraction of a second. Either warm it up shortly after app launch, in the background, or lazily before the first React Native screen. Measure both (#695).
- Keep the instance alive between screens, so the second open is instant.

**3. Navigation**

Pick one owner. In brownfield it is almost always native.

- A React Native screen is pushed like any native screen, inside its own view controller or fragment.
- To open a native screen from JS, call a native module: `HostNavigation.open('profile', { userId })`.
- Flows that stay inside React Native can use a nested navigator, but the host must handle the back gesture and the Android back button consistently.
- Deep links and push notifications are routed by the host, which decides whether the target is native or React Native (#684).

**4. Sharing session and services**

- A host module exposes what already exists natively: the auth token and its refresh, user and feature flags, analytics, logging.
- Don't run a second login or a second token store in JS. One source of truth, on the native side (#697).
- Networking can go through the host's stack, to reuse its interceptors, certificate pinning and caching, or JS can use `fetch` with the host's token.
- Events go both ways: the host tells JS about logout or a theme change, and JS tells the host about a finished flow.

**5. Shipping the JS and the framework**

- Native developers shouldn't need Node, Metro or the JS repository to build the app.
- Package React Native, Hermes, the native modules and the **JS bundle** as a binary artifact: an XCFramework for iOS and an AAR for Android, published to internal package repositories.
- The host app adds a versioned dependency. Tooling for this exists in the community and in Expo.
- React Native developers work in a small test host app, with Metro and Fast Refresh.
- Over-the-air updates can still update the JS part (#699), within the usual runtime version limits.

**6. Costs and risks**

| Risk | Mitigation |
|---|---|
| Version conflicts with the host's own native dependencies | align versions; keep the React Native dependency list small |
| App size grows by several megabytes | measure; justify with the number of shared features |
| Two design systems | wrap native components as React Native views, or rebuild the tokens and components once |
| Debugging across the boundary | clear contracts, logging on both sides, crash reports with both stacks (#687) |
| Ownership | a platform team owns the integration; feature teams own screens |
| Every native module must be compiled into the host | review each addition with the native team |

**Where to start**

Choose a self-contained feature with few native integrations: onboarding, settings, a help centre, a new checkout step. Define success measures before starting: crash-free rate, screen load time, development time against the native estimate.

**Follow-up:** the first React Native screen takes 1.5 seconds to appear when opened, and later ones are instant. What do you do? (The runtime is created on first use. Prewarm the shared instance after app launch at low priority, preload the bundle, and keep the instance alive; show a native skeleton if a delay remains.)
