## Hints

- Each middleware gets the request and a `next` delegate. What can it do before calling `next`, after it, or instead of it?
- What happens if authorization runs before routing, or exception handling is registered after the endpoint that throws?
- Which information does an MVC filter have that a middleware doesn't (e.g. the action, its arguments, model state)?

## Answer

**The pipeline is a chain of middleware.** Each middleware receives the `HttpContext` and a `next` delegate. It can run code before calling `next` (on the way in), after it (on the way out), or not call it at all (**short-circuit**, e.g. return 401 or a cached response). The endpoint (controller action or Minimal API handler) sits at the end.

```csharp
app.Use(async (context, next) =>
{
    var sw = Stopwatch.StartNew();
    await next(context);                                  // the rest of the pipeline runs here
    app.Logger.LogInformation("{Path} took {Ms} ms", context.Request.Path, sw.ElapsedMilliseconds);
});
```

**`Use`, `Run`, `Map`**

| Method | What it does |
|---|---|
| `app.Use(...)` | adds middleware that can call `next` |
| `app.Run(...)` | adds **terminal** middleware: there is no `next` |
| `app.Map("/path", branch => ...)` | branches the pipeline by path prefix |
| `app.MapWhen(predicate, ...)` / `UseWhen` | branches on any condition; `UseWhen` rejoins the main pipeline |
| `app.MapGet(...)`, `MapControllers()` | register **endpoints** for routing (not middleware) |

For reusable middleware, write a class with `InvokeAsync(HttpContext context)` and register it with `app.UseMiddleware<T>()`. Such a class is created once (a singleton), so inject scoped services as `InvokeAsync` parameters, not in the constructor (#581).

**Why order matters**

Middleware runs in registration order on the way in, and in reverse on the way out. A typical order:

```csharp
app.UseExceptionHandler();          // first: catches exceptions from everything after it
app.UseHsts();
app.UseHttpsRedirection();
app.UseStaticFiles();               // short-circuits for files, before auth work (if they're public)
app.UseRouting();                   // picks the endpoint (implicit in minimal hosting if you don't call it)
app.UseCors();                      // after routing, before auth
app.UseAuthentication();            // who are you?
app.UseAuthorization();             // may you? needs the endpoint's [Authorize] metadata from routing
app.UseRateLimiter();
app.MapControllers();
```

Typical mistakes: `UseExceptionHandler` registered late doesn't see exceptions from earlier middleware; `UseAuthorization` before `UseAuthentication` sees an anonymous user; CORS after auth means preflight requests get rejected; response-modifying middleware placed after something that has already started writing the response can't change headers.

**Middleware vs filters**

| | Middleware | MVC filters / endpoint filters |
|---|---|---|
| Runs for | every request through that part of the pipeline, including static files and 404s | only requests that reached an MVC action (or a Minimal API endpoint, for endpoint filters) |
| Knows about | `HttpContext` (and the selected endpoint's metadata after routing) | the action, its arguments after model binding, model state, the action result |
| Good for | logging, exception handling, CORS, auth, compression, request IDs | validation of bound arguments, per-action authorization or caching, shaping results |

MVC filter types run in this order: authorization, resource, (model binding), action, exception, result. Minimal APIs use **endpoint filters** (`AddEndpointFilter`, #583), which can read and change the handler's arguments.

Rule of thumb: if the logic is about HTTP in general, write middleware; if it needs to know which action runs or its bound arguments, write a filter.

**Follow-up:** how do you make middleware run only for `/api` requests? (Put it in `app.UseWhen(ctx => ctx.Request.Path.StartsWithSegments("/api"), b => b.UseMiddleware<X>())`, or, if it depends on endpoint metadata, check `context.GetEndpoint()?.Metadata` after routing.)
