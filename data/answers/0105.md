## Hints

- Why did browsers open 6 connections per origin in HTTP/1.1?
- HTTP/2 multiplexes streams – so why can one lost packet still stall all of them?
- What does moving the transport to UDP make possible?

## Answer

**HTTP/1.1 (1997)**

- Text protocol, persistent connections (`keep-alive`).
- One request at a time per connection; pipelining exists but is broken in practice → **application-level head-of-line (HOL) blocking**.
- Browsers open ~6 TCP connections per origin; developers worked around it with bundling, sprites, domain sharding.

**HTTP/2 (2015)**

- **Binary framing** and **multiplexing**: many concurrent streams over one TCP connection.
- **HPACK** header compression (headers are repetitive and large).
- Stream prioritization; server push (now deprecated and removed in browsers).
- Fixes app-level HOL blocking, but still runs on TCP: a lost packet stalls **all** streams until retransmitted → **TCP-level HOL blocking**, worse on lossy mobile networks.

**HTTP/3 (2022)**

- Runs on **QUIC** over UDP. QUIC implements reliability, congestion control and streams itself, with **independent streams** – loss on one doesn't block others.
- **TLS 1.3 built in**: 1-RTT handshake for new connections, **0-RTT** resumption (replay risk – only for idempotent requests).
- **Connection migration** via connection IDs – survives switching Wi-Fi → 4G.
- QPACK header compression.

```http
Alt-Svc: h3=":443"; ma=86400
```

The server advertises HTTP/3 via `Alt-Svc` (or DNS HTTPS records); the browser upgrades on later requests.

**Practical implications:**

- With HTTP/2+, domain sharding and aggressive bundling are counter-productive; many small cacheable files are fine.
- Some networks block UDP, so HTTP/3 always needs a fallback to HTTP/2.
- Usually you enable these at the CDN/load balancer; the app behind often still speaks HTTP/1.1.
