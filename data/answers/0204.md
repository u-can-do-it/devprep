## Hints

- Why would a dropdown be clipped when its parent has `overflow: hidden` or creates a stacking context?
- If a click happens inside a portal, which ancestors' `onClick` handlers run: the DOM ancestors or the React ancestors?
- Do Context values reach content rendered through a portal?

## Answer

`createPortal(children, domNode)` renders children into a **different DOM node**, often a container at the end of `<body>`. The children stay at their **logical position in the React tree**.

```jsx
import { createPortal } from 'react-dom';

function Modal({ open, children }) {
  if (!open) return null;
  return createPortal(
    <div className="backdrop"><div role="dialog" aria-modal="true">{children}</div></div>,
    document.body
  );
}
```

**When you need them:** modals, tooltips, popovers, dropdowns and toasts that must escape a parent's `overflow: hidden`, `z-index` stacking context, or `transform`. Also for rendering React content into DOM nodes that non-React code manages, like a map widget.

**Behavior to know:**

- **Events bubble through the React tree, not the DOM tree.** A click inside the portal triggers `onClick` on React ancestors, even though they're nowhere near it in the DOM. This is useful, but it can surprise you. For example, a parent's "click outside" logic may treat a portal click as an inside click.
- **Context, state and error boundaries work normally**, because portal content is still a React descendant.
- **Accessibility is your job:** focus management, `Escape` to close, `aria-modal`, and making the background inert.

**Modern alternative:** the native `<dialog>` element with `showModal()` and the **Popover API** (`popover` attribute) render in the browser's **top layer**. That escapes clipping and stacking contexts without a portal, and gives you focus handling and `Esc` support for free. With CSS anchor positioning, many tooltips and popovers no longer need a portal at all.
