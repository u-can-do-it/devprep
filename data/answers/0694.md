## Hints

- While a 400 ms JavaScript loop runs, can the user still scroll a list? Can they press a button?
- How many milliseconds do you have per frame at 60 Hz, and at 120 Hz?
- The performance monitor shows two frame rates. What does each one tell you?

## Answer

> The two threads that matter are the UI (main) thread, which owns native views, touches and scrolling, and the JS thread, which runs React and your code. Other work (layout, images, networking) runs on background threads. When JS is blocked, native scrolling and UI-thread animations continue, but presses, state updates and new list rows wait. When the UI thread is blocked, everything freezes. So first find out which thread drops frames, in a release build, and then either do less work or move it off that thread.

**The threads**

| Thread | Runs | If it is blocked |
|---|---|---|
| **UI / main** | native views, touch handling, scrolling, native-driven animations | the whole app freezes; Android reports an ANR after about 5 s |
| **JS** | React rendering, event handlers, your logic, timers | taps aren't handled, JS animations stop, lists show blank rows |
| **Background** | layout calculation, image decoding, networking, storage | usually invisible; the result arrives late |
| **UI runtime (Reanimated)** | worklets: a second JS runtime on the UI thread | animations stutter if worklets are heavy (#678) |

With Fabric, rendering isn't fixed to one thread: an urgent update can be rendered and laid out synchronously on the UI thread, while a transition is prepared in the background (#693).

**The frame budget**

16.7 ms at 60 Hz and 8.3 ms at 120 Hz. A handler that takes 100 ms on the JS thread drops six or more frames of anything JS controls.

**What "JS is blocked" looks like**

- A press gives no feedback for a moment, then everything happens at once.
- A list scrolls smoothly but shows empty space, because new rows can't be rendered in time.
- A spinner driven by the native driver keeps spinning, while a JS-driven progress bar stops.
- A screen transition on the native stack is smooth, but the new screen's content appears late.

**Finding the cause**

1. **Release build, real mid-range device.** Debug builds mislead.
2. **Performance monitor:** JS frame rate vs UI frame rate tells you which thread to study.
3. **JS thread:** the React DevTools Profiler shows which components render and why (#216). The DevTools performance panel and the Hermes sampling profiler show where JS time goes outside React.
4. **UI thread:** Android Studio's profiler or Perfetto, and Xcode Instruments. Look for deep view trees, overdraw, big images and slow native modules.

**Fixes on the JS thread**

- **Render less:** memoise expensive components and stabilise props (#35), keep state close to where it's used, split contexts (#217), enable the React Compiler.
- **Virtualise** long lists (#673).
- **Defer:** mark non-urgent updates with `startTransition`, and schedule low-priority work with `requestIdleCallback` or after the transition ends. `InteractionManager`, the old tool for this, has been removed from current versions.
- **Chunk** long loops, so the thread can handle input between pieces.
- **Move work off the thread:** a native module or C++ for heavy computation (#700), a background JS runtime, or the server.
- **Remove waste:** `console.log` in production, synchronous reads of large values at startup, parsing huge JSON payloads.

**Fixes on the UI thread**

- Flatten the view hierarchy and avoid large transparent layers.
- Size images to their display size (#672).
- Run animations as `transform` and `opacity` changes, not layout changes.
- Check native modules that do slow work on the main thread.

**Follow-up:** a search screen filters 5,000 items on every key press and the input lags. What do you change? (Keep the input state urgent and the filtered list deferred with `useDeferredValue` or a transition, debounce, memoise the filtering, and virtualise the result list. If the data is larger, filter in SQLite or on the server.)
