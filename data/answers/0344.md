## Hints

- Which parts of your data have a stable shape and which vary per record?
- What do you lose when a field lives inside a JSON blob instead of its own column?
- How would you index a query that filters on a key inside the JSON?

## Answer

PostgreSQL's **`jsonb`** stores parsed, binary JSON that can be queried and indexed. It gives you document-style flexibility while keeping transactions, joins and constraints for the rest of the row – often removing the need for a separate document database.

**Good fits:**

- Sparse or variable attributes: product specs that differ per category, user preferences, feature settings.
- Storing external payloads as received: webhook bodies, third-party API responses, audit snapshots.
- Rapidly evolving data at the edges of a stable core schema.

```sql
CREATE TABLE products (
  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name  text NOT NULL,
  price numeric(10,2) NOT NULL,
  attrs jsonb NOT NULL DEFAULT '{}'
);
CREATE INDEX products_attrs_gin ON products USING gin (attrs jsonb_path_ops);

SELECT id, name, attrs->>'color' AS color
FROM products
WHERE attrs @> '{"brand": "Acme", "wireless": true}';   -- uses the GIN index
```

Use an **expression index** for one hot key: `CREATE INDEX ON products ((attrs->>'sku'));`. PostgreSQL 17 added SQL/JSON `JSON_TABLE` to turn JSON into rows.

**Keep as real columns** anything you filter, join, sort or aggregate on often, anything needing a foreign key, `NOT NULL` or type safety, and anything that's updated frequently (updating one key rewrites the whole value, and large values are TOASTed). The planner also has poor statistics for values inside JSON, which can lead to bad plans.

**Choose a document DB instead** when the whole domain is document-shaped, you need its horizontal scaling model, or the team's access patterns are naturally per-aggregate.

Pitfall: "schema-less" usually means the schema moved into application code. Validate the JSON (Pydantic/Zod, or a `CHECK` with `jsonb_typeof`/JSON Schema) to avoid drift.
