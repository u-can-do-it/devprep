## Hints

- Can code running in the browser read `process.env.DATABASE_URL`?
- When does the value of a public variable get decided: at build time or when the server starts?
- Which `.env` files should never be committed?

## Answer

Next.js loads variables from `.env` files into `process.env`:

- `.env` – defaults for all environments
- `.env.development`, `.env.production`, `.env.test` – per environment
- `.env.local` (and `.env.*.local`) – local overrides and secrets. They are **git-ignored** and win over the others. (`.env.local` is skipped in the test environment.)

**Server-only by default.** A variable like `DATABASE_URL` is available only in server code: Server Components, Route Handlers, Server Actions and `proxy.ts`. In a Client Component it is `undefined`.

**`NEXT_PUBLIC_` exposes a variable to the browser.** At **build time**, Next.js replaces every literal `process.env.NEXT_PUBLIC_X` with its value in the JS bundle:

```ts
// becomes "https://api.example.com" inside the client bundle
fetch(`${process.env.NEXT_PUBLIC_API_URL}/products`);
```

Consequences:

- **Never** put secrets (API keys with write access, DB URLs, signing keys) behind `NEXT_PUBLIC_`. Anyone can read them in DevTools.
- Public values are **frozen at build**. Changing them on the server later does nothing until you rebuild. That's a problem if you want "build once, deploy the same Docker image to staging and prod".
- Only literal access is replaced. `process.env[name]` with a computed key is not inlined.

To use runtime config in the browser, read the variable on the server during a dynamic render and pass it down as a prop. `publicRuntimeConfig` was removed in Next.js 16.

**Follow-up:** validate env vars at startup (e.g. a Zod schema in `env.ts`), so a missing variable fails the deploy and not the first request.
