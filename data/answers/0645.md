## Hints

- A column shows `amount` as `1 234,50 zł`, but sorting puts `9,00 zł` after `10,00 zł`. Which of `valueGetter`, `valueFormatter` and `cellRenderer` did someone misuse?
- The parent component re-renders and the grid loses its scroll position and selection. What wasn't memoized, and what is `getRowId` for?
- How do you get hold of the grid API in React?
- Users want their column order and widths to survive a reload. Which API saves and restores that?
- The PM asks for row grouping and Excel export. Can you do that with AG Grid Community?

## Answer

> AG Grid is configured with `columnDefs` (typed `ColDef<Row>[]`) plus a `defaultColDef` shared by every column. A `valueGetter` computes the value the grid sorts and filters on. A `valueFormatter` only changes how it's displayed. A `cellRenderer` is a React component for cells that need markup. Give every row a stable id with `getRowId`, so updates don't rebuild rows or lose selection, and use transactions for frequent changes. Keep `columnDefs` and callbacks stable, use the grid API through a ref, and save column state with `getColumnState`/`applyColumnState`. Community covers client-side data, editing, filtering and CSV. Enterprise adds the server-side row model, grouping, pivots, the Set Filter and Excel export.

**A typed grid**

```tsx
import { AgGridReact } from 'ag-grid-react';
import { AllCommunityModule, ModuleRegistry, type ColDef, themeQuartz } from 'ag-grid-community';

ModuleRegistry.registerModules([AllCommunityModule]);   // v33+: register only what you use to shrink the bundle

type Order = { id: string; number: string; customer: { name: string }; amount: number; status: 'open' | 'paid' };

const money = new Intl.NumberFormat('pl-PL', { style: 'currency', currency: 'PLN' });

const columnDefs: ColDef<Order>[] = [                     // outside the component, or useMemo
  { field: 'number', headerName: 'No.', pinned: 'left' },
  { headerName: 'Customer', valueGetter: (p) => p.data?.customer.name },           // computed, sortable
  { field: 'amount', type: 'numericColumn', valueFormatter: (p) => money.format(p.value) },  // display only
  { field: 'status', cellRenderer: StatusBadge },                                  // React component
];

export function OrdersGrid({ rows }: { rows: Order[] }) {
  const gridRef = useRef<AgGridReact<Order>>(null);
  const defaultColDef = useMemo<ColDef>(() => ({ sortable: true, filter: true, resizable: true, flex: 1, minWidth: 120 }), []);
  const getRowId = useCallback((p: { data: Order }) => p.data.id, []);

  return (
    <div style={{ height: 600 }}>                           {/* the grid needs a height */}
      <AgGridReact<Order>
        ref={gridRef}
        theme={themeQuartz}
        rowData={rows}
        columnDefs={columnDefs}
        defaultColDef={defaultColDef}
        getRowId={getRowId}
        rowSelection={{ mode: 'multiRow' }}
        onCellValueChanged={(e) => saveOrder(e.data)}
      />
    </div>
  );
}
```

`field` is type-checked against `Order` (including nested paths like `'customer.name'`). The grid only renders the rows and columns in view (DOM virtualization), which is why tens of thousands of client-side rows still scroll smoothly (#218).

**`valueGetter` vs `valueFormatter` vs `cellRenderer`**

| | Affects sort/filter/export | Use for |
|---|---|---|
| `field` | raw value | plain properties |
| `valueGetter` | yes, it **is** the value | computed or nested values (`a + b`, `customer.name`) |
| `valueFormatter` | no, display only (export can opt in) | numbers, dates, enum labels |
| `cellRenderer` | no | badges, links, buttons, icons |

Formatting money inside a `valueGetter` (returning a string) breaks numeric sorting and filtering. A `cellRenderer` creates a React component per visible cell, so prefer a formatter whenever plain text is enough. For editing, `valueParser` turns typed text back into a value, and `valueSetter` writes it into nested data.

**Row identity and updates.** With `getRowId`, a new `rowData` array is diffed by id: unchanged rows stay, changed ones re-render, and selection, expanded state and scroll survive. Without it, every new array rebuilds every row. For frequent updates (live prices, websockets) skip React state and push deltas:

```ts
gridRef.current?.api.applyTransactionAsync({ update: changedRows, add: newRows, remove: removedRows });
```

**Keeping React re-renders cheap.** Every prop you pass must be referentially stable: `columnDefs`, `defaultColDef` and callbacks in `useMemo`/`useCallback` or module scope. A new `columnDefs` array on each render makes the grid re-process its columns and can reset column state.

**The grid API.** `gridRef.current.api` (or `event.api` in `onGridReady`) gives `getSelectedRows()`, `setFilterModel()`, `exportDataAsCsv()`, `ensureIndexVisible()`, `refreshCells()` and more. Avoid copying grid state into React state "just in case"; ask the API when you need it.

**Saving the user's layout**

```ts
const onStateChange = useDebouncedCallback((e: { api: GridApi }) =>
  localStorage.setItem('orders.columns', JSON.stringify(e.api.getColumnState())), 500);

<AgGridReact
  onColumnMoved={onStateChange} onColumnResized={onStateChange}
  onColumnVisible={onStateChange} onSortChanged={onStateChange}
  onGridReady={(e) => {
    const saved = localStorage.getItem('orders.columns');
    if (saved) e.api.applyColumnState({ state: JSON.parse(saved), applyOrder: true });
  }}
/>
```

Newer versions also have `initialState` and `onStateUpdated` for the whole grid state (columns, filters, sort, pagination). Save it per user on the backend if layouts should follow people across machines. Version it, because a renamed column turns old saved state into junk.

**Community vs Enterprise**

- **Community (MIT):** client-side and infinite row models, sorting, text/number/date filters, editing, selection, pagination, CSV export, custom renderers.
- **Enterprise (licence key):** server-side and viewport row models, row grouping, aggregation, pivoting, the Set Filter, master/detail, Excel export, clipboard range selection, integrated charts.

Ask early which one the project pays for, because it decides whether "group by customer" is a config flag or a backend feature (#646).

**Other things worth knowing:** `localeText` translates the UI (there are ready-made locale packages, including Polish). The Theming API (`themeQuartz.withParams({ accentColor: 'var(--mantine-primary-color-filled)' })`) can reuse your design tokens (#643). `cellClassRules` colours cells conditionally, such as negative amounts or validation errors (#651).

**Follow-up:** "When would you not use AG Grid?" A list of 50 rows with no sorting is simpler as a plain `<Table>`. A headless library (TanStack Table) fits when you need full control over markup. AG Grid pays off when you need many grid features out of the box with large data.
