## Hints

- Who reads the column, event or endpoint you're changing, and how would you find out besides searching this one repo?
- At 10× traffic, which resource runs out first: CPU, database connections, row locks, a queue or a third-party rate limit?
- Can you undo the change in a minute without a deploy? What about the data it has already written or the messages it has already sent?

## Answer

These are three questions to answer **before** merging anything that touches a live system with history. Interviewers use them to see whether you think in systems or in files.

**1. Who depends on it (blast radius)**

- **Consumers you can't see from your repo:** other services, queue consumers, mobile apps still running old versions (you can't force patients to update), partner integrations and webhooks, reports and BI jobs reading the table directly, cron jobs, n8n workflows, support tools.
- **How to find them:** code search across all repositories, the APM service map and access logs (who actually calls this endpoint, with which client version), database query statistics by user (`performance_schema` in MySQL, `pg_stat_statements` in PostgreSQL), contract tests (#392), and asking the owners.
- **How to stay safe:** make the change backward compatible (add, don't rename or remove), use expand/contract for schema (#340) and versioning for APIs and events (#96), and add telemetry to deprecated paths so you know when the last caller is gone.

**2. What happens at 10× traffic (capacity)**

Do a back-of-the-envelope estimate. **Little's law** (concurrency = throughput × latency) is enough for most of it:

```
today:   200 req/s × 50 ms = 10 requests in flight → 10 DB connections busy
10×:   2,000 req/s × 50 ms = 100 in flight → pool of 20 per pod × 4 pods = 80: requests queue for connections,
                                              latency grows, so in-flight grows further
```

Things that usually break first, in roughly this order:

- **The database:** connection pools (#338), lock contention on hot rows, a query that was fine on 10k rows but scans 10M (#339), N+1 queries multiplied by traffic (#86).
- **Shared state and fan-out:** cache stampedes (#90), synchronous calls to other services, retry storms when a dependency slows down.
- **Queues:** consumers fall behind and lag grows without bound (#424).
- **External limits:** SMS, payment or video provider rate limits and quotas, and cost (log and APM volume is billed too).
- **Unbounded work:** queries without `LIMIT`, O(n²) loops over growing lists, jobs that load a whole table into memory.

Stateless app servers scale horizontally; the shared database and third parties don't. Verify with a load test on production-like data (#393) or a gradual rollout while watching saturation metrics.

**3. How do you roll it back (reversibility)**

- **Separate deploy from release:** put the behaviour behind a feature flag with a kill switch, so turning it off takes seconds and needs no deploy (#123).
- **Make code rollback possible:** the previous version must still work with the current schema and with data the new version wrote. That's why destructive migrations ship in a later deploy (#340).
- **Data and side effects don't roll back:** sent emails and SMS, charged payments, published events, backfilled rows. Make them idempotent, run backfills in batches with a dry-run mode, keep an audit trail and know how you'd repair data.
- **Decide rollback criteria before the rollout:** error rate, p99 latency and a business metric (bookings per minute) on a canary or a small percentage of users. Rolling back vs rolling forward: #406.

A useful framing is **one-way vs two-way doors**: move fast on changes that are cheap to reverse, and slow down (review, staged rollout, backups) on the ones that aren't.

**Follow-up:** you need to change the format of an event that three services owned by other teams consume. How do you ship it? (Add fields instead of changing them, or publish both versions for a while, agree on a contract, watch which consumers still read the old version, and only then remove it.)
