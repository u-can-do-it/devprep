## Hints

- Which packages does your app need at runtime in production, and which only while building or testing?
- What happens when a plugin library and the app each install their own copy of React?
- What does `npm install --omit=dev` leave out?

## Answer

All three list packages, but they differ in **who installs them and when**:

- **`dependencies`**: needed at runtime (`express`, `zod`, `pg`). They are installed for your app and for anyone who installs your package.
- **`devDependencies`**: needed only to develop, build or test (`typescript`, `vitest`, `eslint`). They are skipped by `npm install --omit=dev` (or `npm ci --omit=dev`) and are never installed for consumers of your package.
- **`peerDependencies`**: used by **libraries and plugins**. They say "I work with the host's copy of X, I don't bring my own". A React component library declares `react` as a peer, so the app and the library share one React instance. Two copies would break hooks and context.

```json
{
  "name": "@acme/ui",
  "peerDependencies": { "react": "^19.0.0" },
  "dependencies": { "clsx": "^2.1.0" },
  "devDependencies": { "react": "^19.1.0", "vitest": "^3.2.0" }
}
```

Notes:

- npm 7+ and pnpm install peers automatically, and they warn or fail when versions conflict.
- `optionalDependencies` may fail to install without failing the whole install. This is common for platform-specific binaries.
- For an app (not a library), the dev/runtime split mostly affects production image size and attack surface.

**Follow-up:** Why do libraries often list a peer in `devDependencies` as well? (So their own tests can run against it.)
