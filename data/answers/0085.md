## Hints

- What can go wrong when two transactions read and write the same rows concurrently: dirty reads, non-repeatable reads, phantoms, lost updates, write skew?
- What's the default isolation level in PostgreSQL vs MySQL InnoDB, and does "Repeatable Read" mean the same thing in both?
- What must application code do when running at Serializable?

## Answer

Transactions give **ACID** guarantees; the **I (isolation)** is tunable, trading correctness for concurrency. The SQL standard defines four levels by which anomalies they prevent:

| Level | Dirty read | Non-repeatable read | Phantom read |
|-------|-----------|---------------------|--------------|
| Read Uncommitted | possible | possible | possible |
| Read Committed | prevented | possible | possible |
| Repeatable Read | prevented | prevented | possible (standard) |
| Serializable | prevented | prevented | prevented |

- **Dirty read** – seeing another transaction's uncommitted changes.
- **Non-repeatable read** – the same row read twice returns different values.
- **Phantom** – re-running a range query returns new rows.
- **Lost update** – two read-modify-write cycles overwrite each other.
- **Write skew** – two transactions read overlapping data, each writes something different, and together they violate an invariant (e.g. two doctors both go off call).

Real implementations differ from the table. **PostgreSQL** uses MVCC snapshots: default **Read Committed**; Read Uncommitted behaves like Read Committed; **Repeatable Read** is snapshot isolation (no phantoms, aborts on concurrent updates of the same row, but allows write skew); **Serializable** (SSI) detects dangerous patterns and aborts with `40001` serialization failures. **MySQL InnoDB** defaults to **Repeatable Read** with consistent snapshots plus gap/next-key locks for locking reads.

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT count(*) FROM doctors WHERE on_call AND shift_id = 7;
UPDATE doctors SET on_call = false WHERE id = 1;
COMMIT;  -- may fail with a serialization error: retry the whole transaction
```

Practical tools at Read Committed: atomic updates (`SET balance = balance - 10`), `SELECT ... FOR UPDATE`, optimistic locking with a version column, unique constraints. Higher levels require **retry logic** and cost throughput.
