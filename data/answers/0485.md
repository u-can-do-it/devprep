## Hints

- Within a topic, where does Kafka guarantee order, and where doesn't it?
- A consumer group has 3 consumers and the topic has 2 partitions. What does the third consumer do?
- The handler charges a card and then crashes before committing the offset. What happens next, and how do you make that safe?

## Answer

**Partitions:** a Kafka topic is split into **partitions**, each an append-only log with increasing **offsets**. Producers choose a partition by hashing the message **key**, so all messages with the same key (e.g. `orderId`) go to the same partition. **Order is guaranteed only within a partition.**

**Consumer groups:** consumers with the same `groupId` share the work. Each partition is assigned to **exactly one consumer in the group**, so parallelism is limited by the partition count (a fourth consumer on a three-partition topic sits idle). Different groups each receive every message, which gives **fan-out**: billing and email services each have their own group. When consumers join or leave, partitions are **rebalanced**.

**Offsets and delivery semantics:** the consumer commits the offset it has processed.

- Commit **after** processing → **at-least-once**: a crash between processing and committing means the message is processed again. This is the usual choice.
- Commit before processing → at-most-once: messages can be lost.
- **Exactly-once** exists inside Kafka (idempotent producer plus transactions for read-process-write between topics), but side effects in other systems (databases, emails, payments) still need idempotency.

**Idempotent consumers:** record processed event ids **in the same transaction** as the side effect, and skip duplicates:

```ts
await consumer.run({
  eachMessage: async ({ message }) => {
    const event = JSON.parse(message.value!.toString());
    await db.transaction(async (tx) => {
      const inserted = await tx.insert(processedEvents).values({ id: event.id }).onConflictDoNothing().returning();
      if (inserted.length === 0) return;               // already handled
      await applyPayment(tx, event);
    });
  },
});
```

Natural idempotency also works: upserts, "set status to PAID" instead of "add 10", and version checks (optimistic locking).

**Retries and dead-letter queues:**

- **Transient errors** (timeouts, a dependency down): retry with backoff. Retrying in place blocks the whole partition, so after a few attempts move the message to a **retry topic** with a delay, then back.
- **Permanent errors** ("poison pills": invalid payload, a bug): after N attempts send the message to a **dead-letter topic (DLQ)** with the error and original metadata, alert, and keep the partition moving. Provide a tool to inspect and replay the DLQ.
- Retry topics break strict ordering for that key. If order matters, pause the key or partition instead of skipping ahead.

**Node.js clients:** KafkaJS has been the common choice, but it's no longer actively maintained; Confluent's `@confluentinc/kafka-javascript` (librdkafka-based, with a KafkaJS-compatible API) is the supported alternative.
