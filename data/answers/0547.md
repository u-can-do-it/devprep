## Hints

- Who will change the workflow next month: an engineer, or the operations person who asked for it?
- Step 4 of 7 fails for 12 of 300 items. What happens to the other 288, and how do you rerun only the failed ones?
- Where do the API credentials live, and who can see the data that passed through each execution?

## Answer

**n8n** is a workflow automation tool (self-hostable, under the fair-code Sustainable Use License) where you connect **nodes** in a visual graph: **triggers** (webhook, schedule, app events, forms, chat, an MCP Server Trigger), **integrations** (Slack, Jira, Google Sheets, HTTP Request, Postgres and MySQL), **logic** (IF, Switch, Merge, Loop Over Items, Wait, sub-workflows) and a **Code** node for JavaScript or Python. AI Agent nodes add an LLM with tools and memory.

**When n8n fits:**

- Glue between SaaS tools and internal APIs, where the process belongs to the business (sales, operations, support) and they should be able to see it and suggest changes.
- Low volume, latency-tolerant, fast to iterate together with the business owner.
- Examples: onboard a new B2B client (create accounts, a Jira epic, a Slack message); classify support tickets with an LLM and route them to Jira; post a daily report from the database to Slack; enrich a monitoring alert and open an incident.

**When to write code instead:**

- Core product logic, transactions, complex domain rules, high volume or low latency.
- Anything that needs real tests, type checking and code review.
- Heavy processing of sensitive data.

Watch for the moment a workflow becomes a hidden production system with no owner.

**Making workflows reliable:**

- **Errors:** set **Retry On Fail** (tries and wait time) on flaky nodes, route per-item failures through the node's error output instead of stopping everything, and set an **Error Workflow** (an Error Trigger node) that alerts Slack with a link to the failed execution. Failed executions can be retried from the failing node.
- **Idempotency:** webhooks get retried and executions get rerun, so dedupe by an external id, upsert instead of insert, and search before create ("does a Jira issue with this ticket id already exist?").
- **Rate limits and volume:** process items in batches (Loop Over Items plus Wait), and use the HTTP Request node's built-in pagination and batching.
- **Long processes:** a **Wait** node pauses an execution until a time or a webhook call (an approval, a callback) without holding a worker.
- **Scale:** in production run **queue mode** (a main instance plus workers, with Redis and Postgres) so a long execution doesn't block others.

**Security and data:**

- Credentials are stored encrypted with `N8N_ENCRYPTION_KEY`. Use a least-privilege service account per integration, control who may use which credential, and never paste tokens into Code nodes.
- **Execution data stores every payload.** With patient data (#556) that matters: self-host in the EU, limit access, save only failed executions (`EXECUTIONS_DATA_SAVE_ON_SUCCESS=none`) and prune old ones (`EXECUTIONS_DATA_PRUNE`, `EXECUTIONS_DATA_MAX_AGE`).

**Treat workflows as software:** keep them in Git (`n8n export:workflow`, or the Git-based source control feature in paid plans), review changes, use a staging instance, develop with pinned test data, document the owner, and monitor (`N8N_METRICS=true` exposes Prometheus metrics).

**n8n and agents:** n8n can expose workflows as tools through the **MCP Server Trigger** and call external MCP servers from its AI Agent node. A good pattern: the agent decides **what** to do, and a deterministic, permission-limited workflow does it (#480).

**Follow-up:** the sales team built an n8n workflow that has quietly become critical: it creates every new client's accounts. What do you do? (Agree on an owner, add error alerts and idempotency, move it to Git with review, document it, and decide whether its core should become a service with an API that the workflow calls.)
