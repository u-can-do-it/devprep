## Hints

- What does the commit history look like after each operation?
- Which one rewrites existing commits and creates new hashes?
- What could go wrong if you rewrite commits others have already pulled?

## Answer

Both integrate changes from one branch into another, but differently.

**`git merge`** creates a merge commit that joins the two histories. History is preserved exactly as it happened; it's non-destructive and safe on shared branches, but frequent merges can make the graph noisy.

**`git rebase`** replays your commits on top of the target branch, creating **new commits with new hashes**. The result is a clean, linear history, but it rewrites history.

```bash
# on feature branch: bring in latest main
git fetch origin
git rebase origin/main          # linear: your commits on top of main
# or
git merge origin/main           # adds a merge commit

# tidy up your own commits before opening a PR
git rebase -i origin/main
```

**Golden rule:** don't rebase commits that others have based work on (public/shared branches). If you must update your own pushed branch after a rebase, use `git push --force-with-lease`, which refuses to overwrite commits you haven't seen.

Typical team practice: rebase your local feature branch to stay current and clean up commits; integrate into `main` via merge or squash-merge through a PR.

**Follow-up:** "What's a squash merge?" — all branch commits are combined into one commit on main; clean history, but individual commit detail is lost.
