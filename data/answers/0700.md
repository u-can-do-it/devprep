## Hints

- Before writing native code, where do you check whether somebody already solved the problem?
- What is the single source of truth for a module's method names and types under the New Architecture?
- A synchronous native method takes 50 ms. Which thread waits?

## Answer

> Write a native module when you need a platform API or a vendor SDK that no maintained library covers, when existing native code must be reused, or when a computation is too heavy for JavaScript. First check the Expo SDK and reactnative.directory. There are two main ways to write one: a Turbo Native Module, where a typed TypeScript spec drives Codegen, or the Expo Modules API, a Swift and Kotlin DSL with less boilerplate. Keep the JS interface small, do slow work off the JS and UI threads, and remember that you now maintain code on two platforms.

**When you need one**

- A platform feature without a good library: a specific Bluetooth profile, a system setting, a new OS API.
- A vendor's native SDK: a payment terminal, an identity check, a device manufacturer's kit.
- Heavy work: image or audio processing, cryptography, parsing large files (#694).
- A custom native view: a map, a camera preview, a video player, a chart drawn natively.

**Option 1: Turbo Native Module**

```ts
// specs/NativeBattery.ts
import type { TurboModule } from 'react-native';
import { TurboModuleRegistry } from 'react-native';

export interface Spec extends TurboModule {
  getLevel(): Promise<number>;     // async: resolved from a native thread
  isCharging(): boolean;           // sync: blocks the JS thread, so it must be fast
}

export default TurboModuleRegistry.getEnforcing<Spec>('NativeBattery');
```

- Add a `codegenConfig` section to `package.json`. At build time **Codegen** generates the native interfaces from the spec (#693).
- Implement them in Kotlin for Android and Objective-C++ or Swift for iOS. A pure C++ module can serve both platforms.
- If the native code doesn't match the spec, the build fails, instead of the app crashing at runtime.
- A native **view** is a Fabric Native Component, with a spec made with `codegenNativeComponent`.

**Option 2: Expo Modules API**

```swift
public class BatteryModule: Module {
  public func definition() -> ModuleDefinition {
    Name("Battery")
    Events("onLevelChange")

    AsyncFunction("getLevel") { () -> Float in
      UIDevice.current.batteryLevel
    }
  }
}
```

- The same DSL exists in Kotlin, so the two implementations look alike.
- It handles argument conversion, events, views (`View`, `Prop`), autolinking and lifecycle hooks, and it runs on JSI.
- It works in any app that has the `expo` package, and a config plugin can apply the native setup the module needs (#676).
- You write the TypeScript types yourself.

**Choosing**

| | Turbo Native Module | Expo Modules API |
|---|---|---|
| Languages | Kotlin/Java, Objective-C++/Swift, C++ | Swift, Kotlin |
| Types | generated from the spec | written by hand |
| Boilerplate | more | less |
| Best for | libraries without an Expo dependency, shared C++ | app-local modules, most product teams |

Nitro Modules are a third option for performance-critical libraries, with generated, statically typed JSI bindings.

**Threads**

- A **synchronous** method runs on the JS thread and blocks it. Use it only for quick in-memory reads.
- An **async** method should do its work on a background queue and resolve a promise.
- Anything that touches views must run on the **main thread**. Never block it with I/O.
- Shared native state needs normal thread safety.

**Events**

For values that change (progress, sensor data, connection state), the module emits events and JS subscribes. Remove listeners on unmount, stop the native work when nobody listens, and don't send an event per sensor reading if ten per second is enough.

**Design advice**

- Expose a small, task-level API (`scan(): Promise<Result>`), not a mirror of the whole SDK.
- Return plain serialisable data, and reject promises with stable error codes.
- Wrap the module in a TypeScript file that the rest of the app imports, so tests can mock one place (#686).
- Handle permissions and lifecycle (the app going to the background) inside the module's contract.

**Cost of ownership**

You need the app's native build to test it, on both platforms. It must be updated when React Native, Xcode, Gradle or the vendor SDK change (#701). If the module is useful to others, publishing it as a library spreads that cost.

**Follow-up:** a module streams accelerometer data at 100 Hz to JS and the UI stutters. What do you change? (Don't send every sample to the JS thread. Aggregate or throttle natively, or process the stream in a worklet on the UI thread and send only the results to React.)
