## Hints

- What metrics would show you that memory is leaking rather than just high?
- How can you compare two heap snapshots to find which objects keep growing?
- What are the usual suspects that keep objects reachable forever in a long-lived Node process?

## Answer

> A memory leak in a long-running service shows up as a memory baseline that keeps rising after each garbage collection, until the process is killed. First confirm it's really a leak and whether it's in the JS heap or outside it. Then take heap snapshots over time and compare them to find objects whose count keeps growing. Follow their retainer path to see what keeps them alive. Common causes are unbounded caches, listeners added per request, and timers never cleared. Taking a snapshot pauses the process, so take the instance out of rotation first.

**1. Confirm it's a leak.** Watch `heapUsed` and RSS over time (APM, `process.memoryUsage()`, container metrics). A leak looks like a sawtooth whose baseline keeps rising after each GC, ending in OOM kills or `JavaScript heap out of memory`. Distinguish from legitimate growth (bigger cache) and from off-heap growth (Buffers, native addons) where RSS grows but `heapUsed` doesn't.

**2. Reproduce and capture.** Reproduce under load in staging if possible. Take **heap snapshots** at intervals:

```bash
node --inspect app.js                     # Chrome DevTools > Memory
node --heapsnapshot-signal=SIGUSR2 app.js # kill -USR2 <pid> writes a snapshot
```

In production, `v8.writeHeapSnapshot()` behind an admin endpoint works, but note it **pauses the process** and needs roughly heap-size of extra memory, so take it out of rotation first.

**3. Analyze.** Use the **Comparison** view between snapshots: sort by size delta, find constructors whose count keeps growing, then follow the **retainers** path to the GC root holding them. Allocation timeline / sampling profiler helps find the allocating code.

**4. Usual culprits:**

- Unbounded in-memory caches/maps keyed by user or request (use LRU with TTL, or `WeakMap`).
- Event listeners added per request and never removed (`MaxListenersExceededWarning` is a hint).
- Closures capturing large objects; timers/intervals never cleared.
- Globals or module-level arrays accumulating data.
- Unconsumed streams, unreleased DB connections, AsyncLocalStorage contexts kept alive.

**5. Fix and verify** with a load test showing a flat baseline. Add memory alerts, and set `--max-old-space-size` to fit the container limit so you fail predictably.

**Follow-up:** How would you debug memory growth that shows up in RSS but not in the JS heap?
