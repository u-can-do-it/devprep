## Hints

- Which of these options draws real platform UI components, which draws its own pixels, and which shows a web page?
- What does the team already know, and what code already exists?
- Which features appear in native SDKs first, and only later in cross-platform tools?

## Answer

> Choose from the product and the team, not from benchmarks. React Native fits a team that knows React and a product made of screens, lists, forms and media: one codebase, real native views, and code shared with the web. Fully native fits apps that live on the newest platform features or on heavy graphics. Flutter fits highly custom, identical UI on every platform. A PWA or Capacitor fits when you already have a web app and need reach quickly. React Native's costs are native dependencies, upgrades, and CPU-heavy work in JavaScript.

| | UI is drawn by | Language | Strong at | Weak at |
|---|---|---|---|---|
| **Native** (SwiftUI, Jetpack Compose) | the platform | Swift, Kotlin | newest OS features, performance, platform feel | two codebases and two teams |
| **React Native** | the platform's views, driven from JS | TypeScript | one team, native look and accessibility, web code sharing, over-the-air updates | heavy computation, dependency on native libraries, upgrades |
| **Flutter** | its own renderer | Dart | custom, identical UI everywhere; smooth graphics | not native widgets, little sharing with a React web app, new language |
| **Kotlin Multiplatform** | native UI (or Compose Multiplatform) | Kotlin | shared business logic under native UI | iOS team must accept Kotlin; younger ecosystem |
| **Capacitor / Ionic** | a WebView | TypeScript | reusing an existing web app, fastest start for a web team | WebView performance and feel |
| **PWA** | the browser | TypeScript | no store, instant updates, links and SEO | limited device APIs and background work, weaker on iOS, no store presence |

**Questions that decide**

1. **Team and code:** what skills and code exist? A React web team is productive in React Native in weeks.
2. **Product type:** content, commerce, banking, booking and internal tools are mostly lists and forms, where React Native is strong. A video editor, a game or an AR app is not.
3. **Platform depth:** how much depends on widgets, watch apps, Live Activities, CarPlay, background processing or new OS APIs on release day?
4. **Web:** do you also have, or need, a web app that could share logic or UI (#702)?
5. **Release speed:** is fixing JS bugs without a store release valuable (#699)?
6. **Lifetime and budget:** who will maintain it in three years?

**Where React Native struggles**

- **CPU-heavy work in JS:** no JIT (#677), one JS thread (#694). It needs native code or C++.
- **Heavy custom graphics and games.** Skia helps for custom drawing; a game engine is the right tool for games.
- **Low-end Android** with complex screens needs deliberate performance work (#673, #695).
- **Day-one OS features** and extensions (widgets, watch apps) need native code, written by you or by a library.
- **Third-party native libraries:** quality varies, and an abandoned one can block an upgrade (#701).
- **You still need native knowledge:** build systems, signing, crash analysis, store rules.
- **App size and startup** are somewhat worse than a lean native app.

**Where it is a clear win**

- One product team ships both platforms and reuses skills, tooling and code from the web.
- Platform look and accessibility come from real native components.
- A large ecosystem, with Expo removing most of the native build work (#676).
- It mixes with native: a native screen or module where needed, or React Native inside an existing native app (#705).

**Don't frame it as all or nothing**

Many large apps are hybrids: mostly React Native with a few native screens, or a native app with some React Native features. A PWA can be a good first version, and a store app can follow when the need is proven.

**In an interview,** show that you can argue for and against your own preferred tool, and that you would ask about the team and the product before answering.

**Follow-up:** a startup with three React developers needs iOS, Android and web versions of a booking product in four months. What do you recommend, and what risk do you flag? (React Native with Expo, sharing logic or a universal app with the web. Flag the need for some native and store-release knowledge, and for real-device testing from week one.)
