## Hints

- Can a single GraphQL response contain both data and errors?
- What happens to the parent object when a non-null field fails to resolve?
- Should "email already taken" be treated the same way as "database is down"?

## Answer

A GraphQL response can have **`data` and `errors` together** – partial success is normal. Each error has a `message`, `path` (which field failed), `locations`, and optional `extensions` (e.g. `code`).

```json
{
  "data": { "user": { "name": "Ana", "recommendations": null } },
  "errors": [{
    "message": "Recommendation service unavailable",
    "path": ["user", "recommendations"],
    "extensions": { "code": "SERVICE_UNAVAILABLE" }
  }]
}
```

**Null propagation:** if a field fails, it becomes `null`. If that field is **non-null** (`!`), the null bubbles up to the nearest nullable parent – one failing field can wipe out a large part of the response. That's why fields backed by unreliable dependencies should stay nullable.

**HTTP status:** with the GraphQL-over-HTTP spec (`application/graphql-response+json`), requests that fail before execution (parse/validation errors) get `4xx`; responses where execution produced data – even partial – are `200`. Monitoring must look at the `errors` array, not just status codes.

**Two categories of errors:**

1. **Unexpected / technical** (bugs, timeouts, auth failures) → top-level `errors`, with a stable `extensions.code`. Mask internal messages in production.
2. **Expected / domain** (validation, "email taken", "out of stock") → model them **in the schema**, so they're typed, documented and enforced by codegen:

```graphql
type Mutation { signUp(input: SignUpInput!): SignUpResult! }

union SignUpResult = SignUpSuccess | EmailTaken | InvalidInput

type SignUpSuccess { user: User! }
type EmailTaken { message: String!, suggestedEmail: String }
type InvalidInput { fieldErrors: [FieldError!]! }
```

Clients use `__typename` to branch, and the compiler warns when a new error type isn't handled. A lighter alternative is a payload with `userErrors: [UserError!]!` (Shopify's style).

Newer work on **semantic nullability** and client-side "throw on field error" (e.g. Relay's `@throwOnFieldError`, the `@semanticNonNull` proposal) lets schemas mark fields that are null only on error, so clients get stricter types without null-bubbling.
