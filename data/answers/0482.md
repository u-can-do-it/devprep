## Hints

- The same prompt gives a different answer each run. What does "the test passed" mean then?
- Which properties of an answer can be checked by plain code, without another model?
- How do you know an LLM judge agrees with your users?

## Answer

You can't assert `expect(answer).toBe(...)` on generated text, and every prompt or model change can silently improve one case and break another. LLM features need **evals**: automated, repeatable measurements of quality.

**1. Build a dataset**

- A **golden set** of realistic inputs: common cases, edge cases, known past failures, adversarial inputs (prompt injection, off-topic requests). Start with 30–100 and grow it from production feedback.
- For each input, the **expected outcome**: a reference answer, required facts, or criteria ("must cite the refund policy; must not promise a refund").

**2. Score with the cheapest reliable check**

- **Deterministic assertions** where possible: valid JSON matching a schema, the correct tool chosen with correct arguments, required keywords or citations present, length limits, no PII, the classification label exactly matching.
- **Reference-based metrics** for extraction and classification: accuracy, precision and recall.
- **LLM-as-judge** for open-ended quality (helpfulness, faithfulness to sources, tone), with a clear **rubric** and a pass/fail or 1–5 scale. Calibrate it against human labels on a sample; judges have biases (they favour longer answers, their own style, or the first option in pairwise comparisons).
- **For RAG:** score retrieval (was the right chunk in the top k?) and generation (is every claim supported by the retrieved context?) separately.

**3. Deal with non-determinism**

- Run each case several times and report a **pass rate**, not a single pass/fail. Set thresholds ("≥ 95% on the core set, no regressions on critical cases").
- Pin the model version and keep temperature low for tasks that need consistency.

**4. Run evals like tests**

- In CI on every prompt, model, tool or retrieval change, comparing against the baseline. Tools: promptfoo, Braintrust, LangSmith, Langfuse, or a plain test runner with a judge helper.
- Track **cost and latency** alongside quality, since a better model may be too slow or expensive.

**5. Monitor in production**

- Tracing of prompts, tool calls and outputs; user feedback (thumbs, edits, retries); sampled online evals with the same judges; alerts on drops.
- Feed failures back into the golden set.

**Also test the deterministic parts normally:** prompt templating, tool implementations, parsing and the UI, with the model mocked.

**Follow-up:** the product manager wants to switch to a cheaper model. How do you show whether quality stays acceptable?
