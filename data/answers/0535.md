## Hints

- What happens to a `setTimeout`-based job when the pod restarts, and to a cron job when there are three replicas?
- A job runs twice because the worker crashed after doing the work but before acknowledging it. Is that a bug in the queue or in your handler?
- Why should the API process and the worker process be deployed separately?

## Answer

Anything that is slower than a request should tolerate, must be retried, or runs on a schedule belongs in a **background job**: sending email, generating PDFs, resizing images, syncing with a third-party API, nightly reports, webhooks (#357), long-running operations (#355). Node has no built-in job system, so you pick one.

**Options, from simplest to heaviest:**

- **In-process** (`setTimeout`, `node-cron`, `setInterval`): fine for a single instance and work you can afford to lose. Jobs vanish on restart and run N times with N replicas.
- **Redis-backed queue: BullMQ** (the default choice in the Node world). Persistent jobs, retries with backoff, delayed and repeatable (cron) jobs, priorities, concurrency per worker, rate limiting, flows (parent waits for children), and a UI (Bull Board). Needs Redis (#342).
- **Postgres-backed queue** (pg-boss, Graphile Worker): one less piece of infrastructure, jobs enqueued **in the same transaction** as your business data, `SELECT ... FOR UPDATE SKIP LOCKED` under the hood. Great until throughput reaches tens of thousands of jobs per minute.
- **Cloud queues**: SQS + Lambda or ECS workers, Cloud Tasks, Pub/Sub (#424). Managed, scalable, less control over local dev.
- **Workflow engines** (Temporal, Inngest, Trigger.dev): for multi-step, long-lived processes with waits, timers and compensation (#427). Overkill for "send an email".

**BullMQ in practice:**

```ts
// queue.ts (API side)
import { Queue } from 'bullmq';
export const emailQueue = new Queue('email', { connection: redis });

await emailQueue.add('welcome', { userId }, {
  jobId: `welcome:${userId}`,                       // dedupe: same id = one job
  attempts: 5,
  backoff: { type: 'exponential', delay: 2_000 },   // 2 s, 4 s, 8 s...
  removeOnComplete: 1000, removeOnFail: 5000,
});

// worker.ts (separate process / deployment)
import { Worker } from 'bullmq';
const worker = new Worker('email', async (job) => {
  const user = await db.user.findUnique({ where: { id: job.data.userId } });   // reload, don't trust stale payload
  if (!user || user.welcomeSentAt) return;                                       // idempotent
  await mailer.send(welcome(user));
  await db.user.update({ where: { id: user.id }, data: { welcomeSentAt: new Date() } });
}, { connection: redis, concurrency: 10 });

worker.on('failed', (job, err) => log.error({ jobId: job?.id, attempts: job?.attemptsMade, err }));
process.on('SIGTERM', async () => { await worker.close(); process.exit(0); });  // finish in-flight jobs (#301)
```

**Design rules that interviewers listen for:**

- **Small payloads, ids not blobs.** The job carries `userId`, the worker reloads fresh data. Payloads are serialized to JSON (no `Date`, no class instances, #442).
- **At-least-once delivery means idempotent handlers.** A job can run twice (worker crash after the side effect, Redis failover, a retry after a timeout). Check a marker, use an idempotency key on outgoing calls (#356), or make the operation naturally repeatable.
- **Retries with exponential backoff and a cap**, then a **dead-letter** state (BullMQ's failed set, SQS DLQ) that someone monitors. Don't retry non-retryable errors (validation) at all.
- **Timeouts** per job so a hung HTTP call doesn't block a worker slot forever; `AbortSignal` for the call (#300).
- **Separate the worker from the API process**: different scaling, a worker crash doesn't take the API down, deploys don't drop in-flight jobs. Same codebase and image, different entrypoint (#301).
- **Transactional enqueue:** if you write to the database and then `queue.add`, a crash in between loses the job. Either use a Postgres-backed queue in the same transaction or the outbox pattern (#484).
- **Scheduling with replicas:** use the queue's repeatable jobs (one scheduler, locked in Redis) instead of `node-cron` in every pod.
- **Observability:** job counts per state, age of the oldest waiting job (lag), failure rate, duration percentiles (#304, #412); alert on lag, not just on failures.

**Python note:** the same roles are played by Celery or RQ with Redis, Dramatiq, arq for asyncio, and FastAPI's `BackgroundTasks` only for fire-and-forget work inside the request's process (#81).

**Follow-up:** 10,000 users must get a newsletter. One job or 10,000? (10,000 small jobs, enqueued in bulk with `addBulk`, rate-limited to what the email provider allows, so a failure retries one email and progress is visible.)
