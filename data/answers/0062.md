## Hints

- Which of these runs before the event loop moves on to the next phase?
- Which queue is drained between every callback, and could it starve I/O?
- Which event loop phase does `setImmediate` belong to?

## Answer

All three defer a callback, but to different places:

- **`process.nextTick(fn)`** – goes to the nextTick queue, drained **immediately after the current operation**, before promise microtasks and before the loop continues. Highest priority.
- **Promise callbacks** (`.then`, `await` continuation, `queueMicrotask`) – drained right after the nextTick queue.
- **`setTimeout(fn, 0)`** – a timer (actually clamped to 1 ms) run in the **timers** phase.
- **`setImmediate(fn)`** – runs in the **check** phase, right after the poll (I/O) phase.

```js
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));
Promise.resolve().then(() => console.log('promise'));
process.nextTick(() => console.log('nextTick'));
console.log('sync');
// sync, nextTick, promise, then timeout/immediate (order of the last two can vary in the main module)
```

Pitfall: recursively scheduling `process.nextTick` (or promises) **starves the event loop** – I/O never gets a turn. `setImmediate` is the safer way to yield, because it lets one full loop iteration pass.

Typical use of `nextTick`: emitting an event or calling a callback asynchronously *after* the constructor/function returns, so the caller can attach listeners first, while keeping it before any I/O.

**Follow-up:** Inside an I/O callback, which fires first: `setTimeout(0)` or `setImmediate`? (Always `setImmediate`.)
