## Hints

- What is the difference between an Nx *app* and a *library*, and why does Nx push you to keep most code in libraries?
- How does `nx affected` know which projects a pull request touched, and what does the cache key of a task contain?
- How do tags and the `@nx/enforce-module-boundaries` lint rule stop a feature library from importing another app's internals?
- Where do the shared types between a React frontend and a Node API live in an Nx workspace?

## Answer

> In a monorepo with a frontend, an API and shared code, rebuilding and retesting everything on every change gets slow. Nx builds a project graph from your imports, and `nx affected` runs tasks only for changed projects and the projects that depend on them. It caches results by hashing the inputs, and a remote cache shares them with CI. Apps stay thin and logic lives in libraries. Tags with lint rules stop the wrong imports, like a React component using the Prisma client.

Nx is a build system and toolkit for monorepos (#419). It builds a **project graph** from your imports and `project.json`/`package.json` files, then runs tasks (build, test, lint, typecheck) in dependency order, in parallel, **only for what changed**, and **caches** the results.

**Typical layout for a full-stack TypeScript product:**

```
apps/
  web/            React (Vite) frontend
  api/            Fastify / Nest API
  web-e2e/        Playwright
libs/
  shared/types/       DTOs and Zod schemas used by web and api (#625)
  shared/util/        pure helpers (dates, money)
  api/feature-offers/ business logic for one domain
  api/data-access/    Prisma client, repositories
  web/feature-offers/ pages and hooks for one domain
  web/ui/             design-system components
```

Apps are thin shells (bootstrapping, routing, config). Logic lives in libraries, so it is reusable, testable in isolation and gets its own cache entry.

**What Nx gives you:**

- **`nx affected -t lint test build`**: compares the branch with the base (`--base=origin/main`), maps changed files to projects, and runs the targets for those projects *and everything that depends on them*. A change in `shared/types` retests both apps; a change in `web/ui` doesn't touch the API.
- **Computation caching:** the cache key is a hash of the task's inputs: source files of the project and its dependencies, the target's options, configured env vars, lockfile and global config (`namedInputs` in `nx.json`). On a hit Nx replays the terminal output and restores the outputs (`dist/`, coverage). **Remote cache** (Nx Cloud or a self-hosted one) shares it between CI and developers.
- **Task pipeline:** `"build": { "dependsOn": ["^build"] }` means "build my dependencies first".
- **Module boundaries:** tag projects (`type:feature`, `type:ui`, `type:data-access`, `scope:web`, `scope:api`, `scope:shared`) and enforce rules with ESLint:

```json
"depConstraints": [
  { "sourceTag": "scope:web",  "onlyDependOnLibsWithTags": ["scope:web", "scope:shared"] },
  { "sourceTag": "type:ui",    "onlyDependOnLibsWithTags": ["type:ui", "type:util"] },
  { "sourceTag": "type:feature", "onlyDependOnLibsWithTags": ["type:feature", "type:ui", "type:data-access", "type:util"] }
]
```

  This catches a React component importing the Prisma client, or a deep import past a library's public `index.ts`.
- **Generators** (`nx g @nx/js:lib ...`) for consistent new projects, and **migrations** (`nx migrate latest`) that update Nx, plugins and your config together.
- **`nx graph`** to visualize dependencies and spot cycles.

**Refactoring in a monorepo** (the job mentions it):

- Extract code into a library with a small public API (`index.ts`), then move imports over; `nx g @nx/workspace:move` updates paths.
- Break cycles by moving the shared piece down into a lower-level library, or inverting the dependency (pass a callback, depend on an interface).
- Keep "shared" libraries small and specific. A giant `shared/utils` that everything imports invalidates every cache on every change.
- One version policy: a single root `package.json` (Nx's default) avoids version drift but means upgrading React or Prisma upgrades it everywhere.

**CI:** `npx nx affected -t lint test build typecheck --base=$BASE --head=$HEAD` plus a remote cache usually turns a 20-minute pipeline into a few minutes. `nx-set-shas` (GitHub Action) computes the base as the last successful run on `main`.

**Nx vs alternatives:** Turborepo does caching and task orchestration with less structure (no generators or boundary rules); pnpm workspaces alone give linking but no affected or caching.

**Follow-up:** a teammate changed a file in `libs/shared/util` and CI rebuilt everything. Is that wrong, and how would you make it cheaper? (It's correct if everything depends on it. Split the library so consumers depend only on what they use, and check that `namedInputs` exclude test files and docs from production inputs.)
