## Hints

- Before listing threats, what do you need to draw to understand the feature?
- Where does data cross from a less trusted zone into a more trusted one?
- For each threat you find, what are your options besides "fix it now"?

## Answer

Threat modeling is a structured way to find design-level security problems **before** code is written, when they are cheapest to fix. A common framing is four questions:

1. **What are we building?** Draw a data-flow diagram: actors, processes, data stores, external services, and **trust boundaries** (browser to API, API to third-party, service to DB, tenant to tenant).
2. **What can go wrong?** Walk each element and each boundary crossing with **STRIDE**.
3. **What are we going to do about it?** Mitigate, eliminate (drop the feature/data), transfer, or explicitly accept, with an owner.
4. **Did we do a good job?** Review the model, turn mitigations into tickets and tests, and revisit when the design changes.

**STRIDE**, each threat mapped to the property it breaks:

| Threat | Violates | Example / mitigation |
|---|---|---|
| **S**poofing | Authentication | Stolen session; MFA, secure cookies, mTLS between services |
| **T**ampering | Integrity | Modified webhook payload; HMAC signatures, server-side validation |
| **R**epudiation | Non-repudiation | "I never approved that payout"; audit logs that can't be altered |
| **I**nformation disclosure | Confidentiality | IDOR, verbose errors, PII in logs; authorization checks, encryption |
| **D**enial of service | Availability | Huge uploads, expensive queries; rate limits, quotas, timeouts |
| **E**levation of privilege | Authorization | Mass assignment to `role`; allow-listed DTOs, least privilege |

Example for "users can import contacts from a CSV URL": SSRF (fetching internal URLs), DoS (giant files), CSV/formula injection when exported to spreadsheets, cross-tenant data leaks, and PII retention.

Practical tips: keep it lightweight (a 45-minute session per significant feature with dev, product and security), store the diagram with the design doc, prioritize by likelihood and impact rather than trying to be exhaustive, and include abuse cases ("how would a fraudster use this?"), not only technical attacks.

**Follow-up:** Other approaches exist: attack trees, PASTA, LINDDUN for privacy threats. STRIDE is popular because it's easy to teach and applies per element.
