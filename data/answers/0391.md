## Hints

- Does the test code run inside the browser or in a separate process that controls it?
- Which browsers, tabs and origins can each tool handle?
- Why do E2E tests that use `sleep(2000)` or CSS-class selectors break so often?

## Answer

Both are popular modern E2E frameworks; the main difference is **architecture**.

**Playwright** (Microsoft) drives browsers **from outside** via a Node (or Python/Java/.NET) process over browser automation protocols.

- Chromium, Firefox and **WebKit** (Safari engine), plus mobile emulation.
- Multiple tabs, multiple origins, multiple users/contexts in one test.
- Parallel execution and sharding built in, free.
- Strong tooling: codegen, trace viewer (DOM snapshots, network, console per step), UI mode, API testing, component testing.

**Cypress** runs your test code **inside the browser**, next to the app.

- Excellent interactive DX: time-travel debugging, live reload.
- Easy network stubbing and direct access to the app's window.
- Limitations: one tab, cross-origin flows need `cy.origin()`, WebKit support is experimental, JS/TS only, and its chained command API isn't regular `async/await`. Parallelization and analytics mostly come through the paid Cypress Cloud.

In 2026 Playwright is the default choice for most new projects; Cypress remains common in existing codebases.

**Keeping E2E tests reliable:**

- **User-facing locators**: `getByRole('button', { name: 'Save' })`, `getByLabel`, or `data-testid`. Avoid CSS classes and XPath.
- **No fixed sleeps**: use auto-waiting actions and web-first assertions that retry.

```ts
await page.getByRole('button', { name: 'Place order' }).click();
await expect(page.getByText('Order confirmed')).toBeVisible();
```

- **Isolated state**: each test creates its own user/data via API or seeding; log in once and reuse `storageState`.
- **Stub third parties** (payments, email) but keep your own backend real.
- **Keep the suite small**: critical journeys only; push the rest down to unit/integration tests.
- Record **traces/videos on failure** in CI.

**Follow-up:** How do you test login with MFA or SSO in E2E? Use test-only IdP users, seed sessions via API, or a test TOTP secret, rather than automating a real third-party login.
