## Hints

- Which transport fits one-way server-to-client token streaming, and which fits two-way interaction?
- If a user's WebSocket is connected to instance A but the event is produced on instance B, how does it get delivered?
- What should happen to an expensive upstream generation when the client closes the tab?

## Answer

**Token streaming (request → stream of chunks): SSE over `StreamingResponse`.** It's plain HTTP, works through proxies, and the browser `EventSource` (or `fetch` with a stream reader) can consume it.

```python
from fastapi import Request
from fastapi.responses import StreamingResponse

@app.post("/chat")
async def chat(req: ChatIn, request: Request):
    async def events():
        async with llm.stream(req.messages) as stream:   # upstream async iterator
            async for token in stream:
                if await request.is_disconnected():
                    break                                 # stop paying for tokens
                yield f"data: {json.dumps({'t': token})}\n\n"
        yield "event: done\ndata: {}\n\n"
    return StreamingResponse(events(), media_type="text/event-stream",
                             headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"})
```

Key points: use an **async** generator so the event loop isn't blocked, disable proxy buffering, send heartbeats (`: ping`) to keep idle connections open, and cancel the upstream call on disconnect. Make long generations **resumable** by writing chunks to Redis Streams keyed by a generation ID, so a reconnect (`Last-Event-ID`) can replay what was missed, possibly on another instance.

**Live updates to many clients: WebSockets (or SSE) plus a pub/sub backbone.**

```python
@app.websocket("/ws/{room}")
async def ws(websocket: WebSocket, room: str, user: WsUser):
    await websocket.accept()
    async with broker.subscribe(f"room:{room}") as sub:   # Redis pub/sub, NATS, Kafka
        try:
            async for msg in sub:
                await websocket.send_text(msg)
        except WebSocketDisconnect:
            pass
```

Each instance holds only **its own** connections. Any instance publishes events to the broker, and every instance fans them out to its local subscribers. The load balancer needs WebSocket support and long idle timeouts. Sticky sessions aren't needed when state lives in the broker.

Scaling concerns:

- **Authenticate at handshake** (token in a cookie or the first message, not a logged query string). Re-check authorization per room.
- **Backpressure**: slow clients get bounded per-connection queues; drop or disconnect when full.
- **Connection limits**: file descriptors, memory per socket, and a cap per instance. Autoscale on connection count, not CPU.
- **Delivery semantics**: Redis pub/sub is at-most-once. Use Streams or Kafka with offsets when clients must catch up after reconnects.
- **Graceful deploys**: close with code 1001 so clients reconnect with jittered backoff.
