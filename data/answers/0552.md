## Hints

- Between `const slot = await findSlot()` and `await save(slot)`, what else can run?
- Your service runs on four pods. Which kind of lock still helps, and which doesn't?
- Which database features make "check, then act" a single atomic step?

## Answer

Node runs your JavaScript on one thread, so you don't get **data races** (two threads writing the same memory at once). You still get **race conditions**: the result depends on how operations interleave. Every `await` is a point where other requests run, and in production several processes and pods share one database.

**Classic check-then-act bug:**

```ts
async function book(slotId: string, patientId: string) {
  const slot = await db.slots.findById(slotId);
  if (slot.patientId) throw new ConflictError('Slot taken');   // both requests see a free slot...
  await db.slots.update(slotId, { patientId });                // ...and both "book" it; last write wins
}
```

Other forms of the same problem: read-modify-write (`balance = await get(); await set(balance - 10)`), a Redis counter done as `GET` then `SET` instead of `INCR`, a double-clicked submit or a client retry creating two orders, a cache refilled with stale data right after it was invalidated, and responses arriving out of order in the frontend (#496).

**Fixes, from most to least preferred:**

1. **One atomic statement** with the condition inside it, then check how many rows changed:

   ```sql
   UPDATE slots SET patient_id = ? WHERE id = ? AND patient_id IS NULL;   -- 0 rows → already taken
   ```

2. **Constraints** as the last line of defence: a unique index on `(doctor_id, starts_at)` or on the idempotency key (#356). Catch the duplicate-key error (`ER_DUP_ENTRY` 1062 in MySQL, `23505` in PostgreSQL) and turn it into `409 Conflict`. Constraints work across every pod and every code path.
3. **Row locks** in a short transaction: `SELECT ... FOR UPDATE`, then update (#337). Pitfalls: autocommit releases the lock immediately, an ORM may run the select and the update on different connections, and you can't lock a row that doesn't exist yet (that's what unique constraints are for).
4. **Optimistic concurrency** with a `version` column, retrying on conflict (#337).
5. **Distributed locks** to coordinate work outside the database (only one pod runs a job, only one refresh of a token): Redis `SET key token NX PX 30000` released by a compare-and-delete script, PostgreSQL advisory locks, or MySQL `GET_LOCK()`. A lock can expire while the holder is still working (a GC pause, a slow call), so protect the resource with a fencing token or a database condition too.
6. **In-process mutexes** only serialise work inside one process, which is fine for a local resource but useless across replicas:

   ```ts
   const tails = new Map<string, Promise<void>>();

   function withKeyLock<T>(key: string, fn: () => Promise<T>): Promise<T> {
     const prev = tails.get(key) ?? Promise.resolve();
     const result = prev.then(fn);
     const tail = result.then(() => {}, () => {});   // never rejects, so the next caller always runs
     tails.set(key, tail);
     tail.then(() => { if (tails.get(key) === tail) tails.delete(key); });
     return result;
   }
   ```

Real data races do exist in Node once you share memory between worker threads with `SharedArrayBuffer`; there you need `Atomics` (#281).

**Testing races:** fire many concurrent requests at a real database and assert the invariant, e.g. 20 parallel bookings of one slot give exactly one `201` and nineteen `409`s. Mocks won't show it.

**Vocabulary interviewers expect:** race condition vs data race, critical section, mutex vs semaphore (a concurrency limit, #168), deadlock (#337), livelock and starvation, atomicity, idempotency.

**Follow-up:** you added `SELECT ... FOR UPDATE`, yet double bookings still happen. Why? (The query ran outside a transaction, the update used another connection, or the row didn't exist yet, so there was nothing to lock: add a unique constraint.)
