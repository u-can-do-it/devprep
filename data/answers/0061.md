## Hints

- Which library gives Node its event loop and thread pool, and which operations use that pool?
- In what order are timers, I/O callbacks, `setImmediate` callbacks and close handlers processed in one loop iteration?
- Where do promise callbacks and `process.nextTick` fit relative to those phases?

## Answer

Node runs JavaScript on a single thread, but **libuv** (a C library) provides the event loop, OS-level async I/O (epoll, kqueue, IOCP) and a **thread pool** (default 4 threads, `UV_THREADPOOL_SIZE`) for work the OS can't do asynchronously: file system calls, `dns.lookup`, `crypto.pbkdf2`, zlib.

Each loop iteration ("tick") goes through phases, each with its own FIFO queue:

1. **timers** – run expired `setTimeout` / `setInterval` callbacks.
2. **pending callbacks** – some deferred system errors (e.g. TCP `ECONNREFUSED`).
3. **idle/prepare** – internal.
4. **poll** – fetch new I/O events and run their callbacks; blocks here waiting for I/O if nothing else is scheduled.
5. **check** – run `setImmediate` callbacks.
6. **close callbacks** – e.g. `socket.on('close')`.

Between every callback (not just between phases, since Node 11), Node drains the **microtask queues**: first `process.nextTick`, then promise reactions.

```js
const fs = require('node:fs');
fs.readFile(__filename, () => {
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate')); // always first here: check comes right after poll
});
```

Key takeaway: network I/O doesn't use the thread pool, but heavy fs/crypto work can saturate those 4 threads and cause latency even though the main thread is idle.
