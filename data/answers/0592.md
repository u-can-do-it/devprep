## Hints

- What does `_count++` compile to, and how can two threads lose an update?
- A `lock` is owned by a thread. Which thread runs your code after an `await`?
- Can the factory you pass to `ConcurrentDictionary.GetOrAdd` run twice for the same key?

## Answer

The best fix for shared mutable state is **not sharing it**: immutable objects, per-request state, message passing. When you must share, pick the cheapest tool that's correct.

| Tool | Use for |
|---|---|
| `Interlocked` | one atomic operation on a number or reference |
| `lock` (on a `Lock` or private object) | short critical sections in synchronous code |
| `SemaphoreSlim` | critical sections that `await`; limiting concurrency |
| `ReaderWriterLockSlim` | many readers, rare writers, synchronous only |
| `ConcurrentDictionary`, `ConcurrentQueue`, `Channel<T>` | shared collections, producer-consumer (#600) |
| Immutable or frozen collections | read-mostly data you rebuild and swap atomically |

**Races and `Interlocked`**

```csharp
private int _count;
public void Hit() => _count++;                          // read, add, write: two threads can lose an update
public void HitSafe() => Interlocked.Increment(ref _count);
```

**`lock` and the `Lock` type**

`lock` is a `Monitor.Enter`/`Exit` pair in a `try`/`finally`. Lock on a **private readonly** object, never on `this`, a `Type` or a string, which other code can also lock on. Since .NET 9 / C# 13 there's `System.Threading.Lock`; `lock` on it compiles to `EnterScope()`, which is faster and states the intent:

```csharp
private readonly Lock _gate = new();
private readonly Dictionary<string, int> _totals = new();

public void Add(string key, int value)
{
    lock (_gate)
    {
        _totals[key] = _totals.GetValueOrDefault(key) + value;
    }
}
```

Keep the critical section short, never call unknown code (callbacks, events) inside it, and when you need two locks, always take them in the same order to avoid deadlocks.

**Why no `await` inside `lock`**

A monitor is **thread-affine**: the thread that entered must exit. After an `await` the continuation can run on a different thread, so the exit would fail, and holding a lock across I/O invites contention and deadlocks. The compiler refuses it (CS1996). Use `SemaphoreSlim`:

```csharp
private readonly SemaphoreSlim _mutex = new(1, 1);

public async Task RefreshAsync(CancellationToken ct)
{
    await _mutex.WaitAsync(ct);
    try { await ReloadFromDatabaseAsync(ct); }
    finally { _mutex.Release(); }       // always release in finally
}
```

`SemaphoreSlim` isn't reentrant: calling `RefreshAsync` again from inside it deadlocks.

**`ConcurrentDictionary` traps**

- `GetOrAdd(key, factory)` runs the factory **outside** the lock. Under contention it can run several times for one key; only one result is stored. If the factory is expensive or has side effects, store a `Lazy<T>`:

```csharp
private readonly ConcurrentDictionary<string, Lazy<Task<TenantConfig>>> _configs = new();

public Task<TenantConfig> GetAsync(string tenant) =>
    _configs.GetOrAdd(tenant, t => new Lazy<Task<TenantConfig>>(() => LoadAsync(t))).Value;
// Lazy<T> runs LoadAsync once per key. A faulted task stays cached: remove the key on failure.
```

- Check-then-act isn't atomic: `if (!d.ContainsKey(k)) d[k] = v;` races. Use `TryAdd`, `AddOrUpdate`, `TryUpdate`, `TryRemove`. The update delegate of `AddOrUpdate` can also run more than once, so keep it pure.
- `Count`, `Keys`, `Values` and `ToArray()` take all internal locks; avoid them on hot paths. Enumeration is safe but isn't a snapshot.

**Other traps**

- Concurrent writes to a plain `Dictionary<,>` can corrupt its internals and leave a reader looping forever at 100% CPU.
- A singleton service in ASP.NET Core is shared by every request, so its fields must be thread-safe (#581).
- `volatile` gives ordering and visibility for one field, not atomicity of `x++` or check-then-act. It is rarely what you need (#605).

**Follow-up:** a singleton caches data in a `Dictionary`, and under load the CPU occasionally sticks at 100%. Why? (Concurrent writes corrupted the dictionary's buckets and a reader loops forever. Use `ConcurrentDictionary`, a lock, or build a new immutable/frozen dictionary and swap the reference atomically.)
