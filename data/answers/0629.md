## Hints

- Finance sends an XLSX export every month, with Polish characters, comma decimals and dates like `05.11.2026`. What can go wrong when loading it?
- If the script crashes halfway and you run it again, do you get duplicates?
- How do you load a 2 GB CSV into Postgres without loading it all into memory?
- pandas, Polars or the plain `csv` module: when does each make sense?
- Where does a script like this run every night, and how does anyone notice when it fails?

## Answer

ETL = **extract** (from an API, files or another database), **transform** (clean, validate, map), **load** (into your database). In an internal-systems team Python is often the glue: importing ERP exports, syncing with external APIs, preparing reports. Interviewers want to see a script that is **idempotent, validated, observable and memory-safe**, not a notebook.

**Example: load monthly cost invoices from a CSV/XLSX export into PostgreSQL**

```python
import csv, logging, os, sys
from datetime import datetime
from decimal import Decimal, InvalidOperation
from pydantic import BaseModel, field_validator, ValidationError
import psycopg

log = logging.getLogger("import_invoices")

class InvoiceRow(BaseModel):
    number: str
    nip: str
    issue_date: datetime
    net: Decimal
    currency: str = "PLN"

    @field_validator("issue_date", mode="before")
    @classmethod
    def parse_pl_date(cls, v: str) -> datetime:
        return datetime.strptime(v.strip(), "%d.%m.%Y")

    @field_validator("net", mode="before")
    @classmethod
    def parse_pl_decimal(cls, v: str) -> Decimal:
        return Decimal(v.replace(" ", "").replace(" ", "").replace(",", "."))   # "1 234,50" -> 1234.50

def extract(path: str):
    with open(path, encoding="cp1250", newline="") as f:          # Windows exports are often cp1250, not UTF-8
        yield from csv.DictReader(f, delimiter=";")                # Polish Excel uses ';' as the separator

def transform(rows):
    for i, raw in enumerate(rows, start=2):                        # line 1 is the header
        try:
            yield InvoiceRow(number=raw["Numer"], nip=raw["NIP"], issue_date=raw["Data"], net=raw["Netto"])
        except (ValidationError, InvalidOperation, KeyError) as e:
            log.warning("line %d skipped: %s", i, e)                  # report bad rows, don't stop the whole import

def load(conn, rows, batch_size=1000):
    sql = """INSERT INTO cost_invoice (number, nip, issue_date, net, currency)
             VALUES (%s, %s, %s, %s, %s)
             ON CONFLICT (nip, number) DO UPDATE
             SET issue_date = EXCLUDED.issue_date, net = EXCLUDED.net, updated_at = now()"""
    batch, total = [], 0
    with conn.cursor() as cur:
        for r in rows:
            batch.append((r.number, r.nip, r.issue_date.date(), r.net, r.currency))
            if len(batch) == batch_size:
                cur.executemany(sql, batch); total += len(batch); batch.clear()
        if batch:
            cur.executemany(sql, batch); total += len(batch)
    return total

if __name__ == "__main__":
    logging.basicConfig(level=logging.INFO, format="%(asctime)s %(levelname)s %(message)s")
    with psycopg.connect(os.environ["DATABASE_URL"]) as conn:      # commits on success, rolls back on exception
        n = load(conn, transform(extract(sys.argv[1])))
    log.info("imported %d rows", n)
```

**What makes it production-grade:**

- **Idempotent loads:** a natural unique key (`nip`, `number`) plus `INSERT ... ON CONFLICT DO UPDATE`, so re-running the import doesn't create duplicates (#623). Alternatively, load into a staging table and `MERGE` into the target in one transaction.
- **Streaming:** generators (#72) process row by row, so a 2 GB file uses constant memory. For big loads, `COPY` (`cur.copy("COPY staging FROM STDIN")`) is much faster than `INSERT`s.
- **Validation at the boundary:** Pydantic (#77, #79) for types and rules; invalid rows go to a report or an errors table with the line number, so finance can fix the source.
- **Locale traps:** encoding (`cp1250` vs UTF-8 with BOM, `utf-8-sig`), `;` separators, decimal commas, non-breaking spaces as thousand separators, `dd.mm.yyyy` dates, leading zeros in NIP or postal codes (read them as strings, never as numbers).
- **Money as `Decimal`,** never `float` (#630). pandas reads numbers as floats by default; use `dtype=str` and convert, or `decimal` converters.
- **Parameterized SQL** (`%s` placeholders), never f-strings (#113).
- **Configuration from environment** (#324), logs to stdout, a non-zero exit code on failure so the scheduler marks the run as failed.
- **Tests** (pytest, #315) for the transform functions with tricky sample rows: empty lines, a BOM, `1 234,50`, a date in the wrong format.

**Tool choice:**

- **`csv` / `openpyxl`:** small to medium files, simple mapping, no heavy dependency.
- **pandas:** exploratory work, joins and aggregations between several sources, `read_excel`, `read_csv(chunksize=...)` for large files. Watch dtypes (floats, NaN for empty cells, dates).
- **Polars:** the same kind of dataframe work, much faster and lazy (`scan_csv`), with stricter types.
- **Heavier orchestration** (Airflow, Prefect, Dagster) only when you have many pipelines with dependencies, backfills and retries to manage.

**Running and monitoring it:** cron or a Kubernetes CronJob on a server; on GCP a **Cloud Run job** triggered by Cloud Scheduler (#626). Record each run (start, end, rows read/loaded/rejected) in a table, alert when it fails or hasn't run, and keep a "last import" date visible to the business users.

**Follow-up:** the same invoice appears in two monthly files with a corrected amount. What should happen? (The upsert updates it, and an audit or history row records the old and new amount, so finance can see the correction instead of the value silently changing.)
