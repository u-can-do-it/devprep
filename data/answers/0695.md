## Hints

- What happens between the tap on the app icon and the first useful screen? Name the phases.
- Which code runs at startup even though the first screen doesn't need it?
- Each native library adds compiled code for several CPU architectures. Where does that show up?

## Answer

> Measure before changing anything, on a release build and a slow Android phone. Startup has phases: native start, loading the JS bundle, running module code, the first render, and the first data. Most wins come from running less JavaScript at startup (lazy screens, deferred SDK setup) and from showing cached content instead of waiting for the network. App size comes mainly from native libraries and assets, so analyse the binary, remove what you don't need, and let the stores deliver per-device builds.

**What to measure**

- **Cold start** (process not running) is the number that matters. Warm start is much faster.
- **Time to initial display** (first frame) and **time to full display** (content usable).
- Percentiles by device class from production, not one run on your phone: Play Console vitals, Xcode Organizer, or the app-start metrics of your monitoring tool (#687).
- In development: marks around each phase (`react-native-performance`, `performance.mark`), `adb shell am start -W`, and the App Launch template in Instruments.

**Startup phases and what helps**

| Phase | Cost | Improvements |
|---|---|---|
| Native start | process, native libraries, the runtime | fewer native dependencies, no heavy work in `Application` or `AppDelegate` |
| Bundle load | reading the bundle | Hermes bytecode is memory-mapped (#677); nothing to parse |
| Module execution | every imported file's top-level code runs | lazy routes and `React.lazy`, inline requires, no side-effect imports, no big barrel files |
| First render | provider tree, first screen | a light first screen; move optional providers lower |
| First data | network round trips | show persisted cache first (#682), prefetch in parallel, one request for the home screen |

**Typical findings**

- Analytics, crash reporting, feature flags, maps, payments and chat SDKs all initialised before the first frame. Keep crash reporting early and defer the rest until after the first screen is shown.
- A root file that imports every screen, so all code runs at launch. Load screens on first navigation.
- Large synchronous reads at startup, such as a multi-megabyte persisted store. Split it and load parts when they are needed.
- The splash screen hidden too early, so the user sees a white screen or a spinner, or hidden too late, after waiting for requests that could finish in the background.
- A login check that waits for the network before showing anything. Decide from the stored session and validate in the background.

Turbo Native Modules already load lazily (#693), and prebuilt framework binaries reduce build time, not startup time.

**App size: find out what is in it**

- **JS bundle:** Expo Atlas or `source-map-explorer` shows which modules are large.
- **Android:** the APK Analyzer in Android Studio. Look at `lib/` (native code per CPU architecture), `assets/` and resources.
- **iOS:** the App Store Connect size report per device.

**App size: reduce it**

- **Ship an AAB.** Google Play then delivers only the code for the device's CPU architecture and screen density.
- **R8** with code and resource shrinking on Android.
- **Remove unused native libraries.** Each one adds compiled code for every architecture, and often its own dependencies.
- **Assets:** convert images to WebP, use vector icons, subset fonts, and download large or rarely used content on demand instead of bundling it.
- **JS:** avoid importing whole libraries for one function (date, utility and icon libraries are the usual ones). Metro's tree shaking is limited, so imports matter.
- **Check both sizes:** download size (compressed) is what the store shows; install size is what the user's storage loses.

**Keep it from regressing**

- A size check in CI that fails a pull request above a budget.
- Startup time on a dashboard per release, with an alert on regressions.
- A review step for every new native dependency.

**Follow-up:** startup got 400 ms slower between two releases and nobody knows why. How do you find it? (Compare production start metrics per phase if you have marks; otherwise bisect the commits with an automated cold-start measurement on one device, and check new dependencies and new work in the root component first.)
