## Hints

- What two properties must every primary key value have?
- What should happen to a user's orders if the user row is deleted?
- Why enforce rules in the database when the application already validates input?

## Answer

**Primary key (PK)** – uniquely identifies a row; implies `UNIQUE` + `NOT NULL`. Usually a **surrogate** key (`bigint` identity or UUID) rather than a natural key like email, which can change. A PK can be composite, e.g. `(order_id, product_id)` in a join table.

**Foreign key (FK)** – a column referencing another table's key, guaranteeing **referential integrity**: you can't insert an order for a non-existent customer.

**Other constraints:** `NOT NULL`, `UNIQUE`, `CHECK` (row-level rule), `DEFAULT`, and in PostgreSQL `EXCLUDE` (e.g. no overlapping bookings).

```sql
CREATE TABLE orders (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id bigint NOT NULL REFERENCES customers(id) ON DELETE RESTRICT,
  total       numeric(12,2) NOT NULL CHECK (total >= 0),
  status      text NOT NULL DEFAULT 'pending'
);

CREATE TABLE order_items (
  order_id   bigint REFERENCES orders(id) ON DELETE CASCADE,
  product_id bigint REFERENCES products(id),
  qty        int NOT NULL CHECK (qty > 0),
  PRIMARY KEY (order_id, product_id)
);
```

**Referential actions** when the parent row is deleted/updated:

- `CASCADE` – delete/update children too (good for owned data like order items).
- `RESTRICT` / `NO ACTION` – refuse while children exist (default behaviour).
- `SET NULL` / `SET DEFAULT` – detach children.

Why in the DB: constraints hold for **every** writer (scripts, other services, race conditions between two app instances), and the planner can use them.

Pitfall: PostgreSQL does **not** auto-index FK columns – add an index on `orders.customer_id`, or joins and cascading deletes get slow.

**Follow-up:** Auto-increment ids vs UUIDs (and why time-ordered UUIDv7 is popular now).
