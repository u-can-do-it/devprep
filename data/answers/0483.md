## Hints

- Apart from the user's question, what else does the model see on every call?
- What happens to quality when you put 200 pages into the context "just in case"?
- Which costs more per token: input or output, and how does caching change that?

## Answer

**Prompt engineering** is writing the instructions well: a clear task, role and audience, constraints, output format, and examples. **Context engineering** is the broader job of deciding **everything** that goes into the model's context window for each call, and in what form:

- the system prompt and instructions
- **examples** (few-shot)
- **retrieved data** (RAG results, database records, files)
- **tool definitions** and tool results
- **conversation history** and memory
- the current state of the task

For agents and long conversations, most failures come from the context, not the wording: missing facts, outdated or contradictory information, too many irrelevant tools, or the important instruction buried in the middle.

**Prompt-writing basics that still matter:**

- Be specific: say what good output looks like, who it's for, and what to do when information is missing ("say you don't know").
- Separate instructions from data with clear sections or tags.
- Give 2–3 examples of the input and output you want, covering an edge case.
- Ask for **structured output** (a JSON schema) when code consumes the result.
- Let the model reason before answering on complex tasks (extended thinking or "plan first").

**Managing the context window:**

- **Tokens:** roughly 4 characters of English per token, more tokens for Polish and code. Context windows are large (hundreds of thousands to a million tokens), but quality and attention degrade with length; content in the middle of very long contexts is used less reliably.
- **Select, don't dump:** retrieve the few most relevant chunks, and expose only the tools needed for this step.
- **Compress history:** summarise older turns, drop finished tool outputs, keep key decisions in a structured state or memory file.
- **Order:** stable content first (instructions, tool definitions, documents), the changing question last.

**Cost and latency:**

- You pay per **input and output token**; output tokens are several times more expensive and also drive latency.
- **Prompt caching:** reusing an identical prefix (system prompt, documents) is much cheaper and faster, so keep that prefix stable and put variable content at the end.
- Use the **smallest model** that passes your evals for each step, cap `max_tokens`, batch offline work, and track cost per request.
