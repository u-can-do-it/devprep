## Hints

- Who reads your tool's name, description and output: a developer, or a model deciding what to call next?
- A log search returns 40,000 lines. What should the tool return instead?
- Which tools are safe to call without asking, and what must the server enforce no matter what the client allows?

## Answer

An MCP server exposes a system (logs, tickets, a database, CI) to any MCP client: Claude Code, Cursor, your own agent (#479). Datadog, Atlassian (Jira), Slack and GitHub now ship official remote MCP servers, so first check whether you need your own. You build one when the system is internal, or when you want a **narrower, safer, better-shaped** interface than the vendor's.

**Primitives:** **tools** (actions the model calls), **resources** (data the client can attach, such as a runbook or a schema) and **prompts** (reusable templates, often exposed as slash commands). In practice most value is in tools.

**Transports:** **stdio** (the client starts the server as a local process; credentials come from environment variables) or **Streamable HTTP** (a remote, shared server; authorization with OAuth 2.1, so each user acts with their own permissions).

**A minimal server** (TypeScript SDK v2; in v1 the package was `@modelcontextprotocol/sdk` and the schema a plain object of Zod fields):

```ts
import { McpServer } from '@modelcontextprotocol/server';
import { StdioServerTransport } from '@modelcontextprotocol/server/stdio';
import * as z from 'zod/v4';

const server = new McpServer({ name: 'ops', version: '1.0.0' });

server.registerTool(
  'search_error_logs',
  {
    description:
      'Search error logs of one service in a time window. Returns at most `limit` grouped errors ' +
      'with counts and one sample each, newest first. Use get_trace for details of a single request.',
    inputSchema: z.object({
      service: z.enum(['booking-api', 'payments', 'video']),
      from: z.string().describe('ISO 8601 start, e.g. 2026-10-26T14:00:00Z'),
      to: z.string().describe('ISO 8601 end, at most 24 h after from'),
      query: z.string().max(200).optional().describe('Free text, e.g. "timeout"'),
      limit: z.number().int().min(1).max(50).default(20),
    }),
    annotations: { readOnlyHint: true, openWorldHint: false },
  },
  async ({ service, from, to, query, limit }) => {
    const groups = await logs.searchGrouped({ service, from, to, query, limit });   // your API client
    if (groups.length === 0) {
      return { content: [{ type: 'text', text: 'No errors found. Try a wider window or no query.' }] };
    }
    return { content: [{ type: 'text', text: JSON.stringify(groups.map(redactPatientData)) }] };
  },
);

await server.connect(new StdioServerTransport());
```

Python is just as short: `FastMCP` (`mcp.server.fastmcp`) in SDK v1 or `MCPServer` in v2, with `@mcp.tool()` on a typed function.

**Designing tools for a model, not for a developer:**

- **Workflow-shaped, not endpoint-shaped:** `get_failing_ci_job_summary` beats wrapping 15 REST endpoints. Fewer, clearer tools mean better choices and less context.
- **Descriptions are prompts:** say what the tool does, when to use it instead of a sibling tool, units and formats, and the limits.
- **Constrained inputs:** enums, ranges and defaults stop the model from inventing values; validate everything anyway.
- **Token budget:** paginate, aggregate and truncate (group identical errors, return counts and one sample, cap sizes), and say what was cut and how to get more.
- **Actionable errors:** "window too large, max 24 h" lets the model recover; a stack trace doesn't. Tool failures return `isError: true` instead of crashing.
- **Stable identifiers** in outputs (trace ids, ticket keys) so the model can chain calls.

**Safety:**

- **Read-only by default.** Write tools (create a Jira ticket, post to Slack, rerun CI) are separate, clearly named, idempotent where possible, and confirmed by a human in the client. Annotations (`readOnlyHint`, `destructiveHint`, `idempotentHint`) help clients decide, but they're hints: **the server enforces permissions**.
- **Least-privilege credentials:** a scoped, read-only token, or the user's own OAuth identity on a remote server, never an admin key.
- **Redact sensitive data** before it reaches the model: patient data in logs (#556), secrets, tokens.
- **Tool output is untrusted:** a log line or ticket comment can contain prompt injection (#481, #525). Don't let one tool's output silently trigger another tool's side effects.
- **Audit and limits:** log every call with user, arguments and result size; rate-limit; time out slow backends.

**Testing and evaluating:** unit-test handlers like any API; use the MCP Inspector (`npx @modelcontextprotocol/inspector`) during development; and evaluate with real tasks ("why did bookings fail at 14:10?"): does the agent pick the right tools, how many calls and tokens does it need, does it reach the right answer? Improve descriptions and output shapes based on the transcripts (#543).

**Distribution:** commit a project `.mcp.json` so the whole team gets the server, version it, and document the required environment variables.

**Follow-up:** your Jira MCP server lets agents create tickets, and an agent created 40 duplicates overnight. How do you prevent it? (An idempotency key such as a fingerprint of the error, search before create, per-session rate limits, human approval for writes, and alerts on unusual volume.)
