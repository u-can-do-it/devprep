## Hints

- What do the three numbers in `MAJOR.MINOR.PATCH` promise?
- If two developers run `npm install` a month apart with the same `package.json`, will they get the same code?
- Which install command should CI use, and why?

## Answer

**Semver** is `MAJOR.MINOR.PATCH`: major for breaking changes, minor for new backward-compatible features, patch for fixes. Ranges in `package.json` say which versions are acceptable:

| Range | Means | Example matches |
|---|---|---|
| `1.2.3` | exactly that version | `1.2.3` |
| `^1.2.3` | same major | `>=1.2.3 <2.0.0` |
| `~1.2.3` | same minor | `>=1.2.3 <1.3.0` |
| `^0.2.3` | for 0.x, caret locks the minor | `>=0.2.3 <0.3.0` |

`npm install` writes `^` by default, so `package.json` alone doesn't pin anything: new installs pick up whatever matches today.

A **lockfile** (`package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`) records the exact resolved version and integrity hash of **every** package in the tree, including transitive ones. Committing it gives:

- reproducible installs on every machine and in CI;
- reviewable dependency changes in pull requests;
- protection against a compromised new release being pulled in silently.

In CI use the frozen install: `npm ci`, `pnpm install --frozen-lockfile` or `yarn install --immutable`. It fails if the lockfile and `package.json` disagree.

Use one package manager per repo (set the `packageManager` field). pnpm is popular because of its shared content-addressed store and strict `node_modules`, which blocks "phantom" imports of packages you never declared.

**Follow-up:** Should a published library ship its lockfile? (No. Consumers resolve their own tree, so the library's lockfile only affects its own development.)
