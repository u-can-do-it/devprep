## Hints

- How can two teams each own part of the `Product` type without one team owning the whole thing?
- What component plans and executes a query that touches several services?
- What organizational problems does federation solve, and what new ones does it create?

## Answer

**Federation** composes many independently owned GraphQL services (**subgraphs**) into one unified graph (the **supergraph**). Clients see a single schema; a **router/gateway** splits each operation into a query plan, calls the relevant subgraphs and merges the results.

**Entities** are types that several subgraphs contribute to, identified by a key:

```graphql
# products subgraph
type Product @key(fields: "id") {
  id: ID!
  name: String!
  price: Float!
}

# reviews subgraph
type Product @key(fields: "id") {
  id: ID!
  reviews(first: Int = 10): [Review!]!
  averageRating: Float
}
```

For a query asking `product { name reviews { body } }`, the router fetches `name` from products, then sends the `id` to reviews' `_entities` resolver (a reference resolver loads the product by key), and stitches the result.

**Ecosystem:** Apollo Federation 2 with Apollo Router (Rust) and GraphOS, WunderGraph Cosmo, The Guild's Hive Gateway; the GraphQL Foundation's **Composite Schemas** work is standardizing the approach. A **schema registry** composes subgraph schemas in CI and blocks breaking or non-composable changes.

**Benefits:**

- Teams own and deploy their part of the graph independently (matches microservice/domain boundaries).
- Clients keep one endpoint, one schema, one set of tools.
- Scales a large graph across many teams (Netflix, Expedia, and others run large federated graphs).

**Costs:**

- Operational complexity: router, registry, composition, distributed tracing.
- Extra latency from sequential subgraph hops; query planning must avoid entity N+1 (batch `_entities` calls).
- Cross-subgraph design governance: naming, nullability, ownership of shared types.
- Auth and caching must work consistently across subgraphs.

**When:** a single schema (a modular monolith or a BFF) is simpler and better for one or a few teams. Choose federation when **multiple teams** need to evolve one graph independently and coordination around a central schema has become the bottleneck. Older **schema stitching** is the gateway-owned alternative; federation moves ownership to the services.

**Follow-up:** How would you handle authorization for a field owned by one subgraph on an entity owned by another?
