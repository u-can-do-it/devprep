## Hints

- Does running a line of code mean you checked that it produced the right result?
- What's the difference between line coverage and branch coverage?
- How could someone reach 100% coverage with tests that would never fail?

## Answer

**Code coverage** measures which parts of the code were **executed** while tests ran. Common metrics:

- **Line/statement coverage**: which lines ran.
- **Branch coverage**: whether each side of every `if`, `?:`, `&&`, `??` was taken. More useful than line coverage.
- **Function coverage**: which functions were called.

Tools: Vitest/Jest (V8 or Istanbul), Node's built-in `node --test --experimental-test-coverage`, `coverage.py`/`pytest-cov`.

**What it's good for:** finding **untested code**. A file with 20% coverage clearly lacks tests, and a coverage diff on a PR shows new code that nobody exercised.

**Why 100% isn't "well tested":**

- Coverage measures **execution, not verification**. This test gives 100% coverage and checks nothing:

```ts
test('calculates total', () => {
  calculateTotal([{ price: 10, qty: 2 }]); // no assertion
});
```

- It can't see **missing code**: an unhandled edge case (empty list, negative quantity, time zones) doesn't show up as an uncovered line.
- Executing a branch with **one input** doesn't prove the logic is right for others (off-by-one errors, rounding).
- It says nothing about integration: components can each be fully covered and still not work together.
- Chasing the number produces brittle tests of trivial code and implementation details.

**Practical approach:** use coverage as a **signal, not a target**. Look at what's uncovered and decide if it matters; set a reasonable floor (e.g. 70–85%) or require that coverage doesn't drop on changed lines; focus thorough testing on business logic and risky code. To check that tests actually catch bugs, look at **mutation testing**.

**Follow-up:** Goodhart's law applies: once coverage becomes a KPI, people optimize the number instead of test quality.
