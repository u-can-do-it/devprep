## Hints

- Is a message deleted once it's consumed, or kept so that a new consumer can read history?
- How do you keep the order of events for one customer while still processing in parallel?
- What should happen upstream when the queue keeps growing faster than consumers drain it?

## Answer

| | **Kafka** | **RabbitMQ** | **Amazon SQS** |
|---|---|---|---|
| Model | distributed **append-only log** | **message broker** with exchanges and queues | fully managed **queue** |
| After consumption | retained (time or size based), **replayable** | removed once acked | removed once deleted |
| Ordering | per **partition** (by key) | per queue (single consumer) | FIFO queues only (per group ID) |
| Throughput | very high, horizontal via partitions | high, lower than Kafka | elastic, no capacity planning |
| Strengths | event streaming, many independent consumer groups, event sourcing, CDC, analytics | flexible routing (topic, fanout, headers), priorities, per-message acks, RPC-style work queues | zero ops, DLQs, visibility timeouts, great for background jobs on AWS |
| Costs | operational complexity (much less with managed Kafka or KRaft-only Kafka 4) | you run and cluster it (or use a managed one) | AWS lock-in, limited features, standard queues may duplicate or reorder |

**Rough rule:** Kafka for **event streams** many services read and replay. RabbitMQ for **rich routing and task distribution**. SQS (often with SNS for fan-out) for **simple, reliable job queues** on AWS. Redis Streams or a Postgres-based queue are fine for small systems.

**Back-pressure** means slowing producers, or shedding load, when consumers can't keep up, instead of letting memory or lag grow without limit.
- **Monitor lag:** queue depth, consumer lag, age of the oldest message. Alert on them.
- **Scale consumers** based on lag (KEDA, autoscaling on queue depth). In Kafka, parallelism is capped by the partition count.
- **Bound everything:** bounded in-memory buffers, RabbitMQ `prefetch` (QoS), max in-flight messages per consumer.
- **Push back:** producers block or get `429` with `Retry-After`. Rate-limit at the API edge.
- **Shed or degrade:** drop low-priority work, sample analytics, separate queues by priority.
- **Retries with exponential backoff and jitter** plus a **dead-letter queue**, so poison messages don't block the line.

**Pitfall:** "just add a queue" doesn't add capacity. It only buys time. If average production exceeds consumption, lag grows forever.
