## Hints

- When the user taps "save" offline, where does the UI read the new value from?
- A queued "create order" request is sent, the connection drops before the response, and it is retried. How do you avoid two orders?
- Two devices edit the same record while offline. Who wins?

## Answer

> Offline-first means the UI reads from and writes to a local database, and a sync process exchanges changes with the server in the background. Every write is saved locally and added to a persistent queue of pending changes. Sync pushes that queue with idempotent requests, and pulls server changes since the last cursor. Conflicts need an explicit rule: last write wins, server wins, a field-level merge, or asking the user. It is a lot of machinery, so first decide how much offline the product really needs.

**How much offline do you need?**

| Level | Behaviour | Typical tools |
|---|---|---|
| 1. Cached reads | last loaded data is visible offline | persisted TanStack Query cache (#682) |
| 2. Queued writes | simple actions made offline are sent later | paused mutations, persisted and resumed |
| 3. Local-first | full work offline for hours or days | SQLite + a sync engine |

Level 3 fits field work, inspections, notes, deliveries and travel apps. Many apps only need level 1 or 2.

**Architecture for level 3**

```
UI  ⇄  local DB (SQLite)  ⇄  sync engine  ⇄  API
            ↑ source of truth for the UI
```

- The UI never waits for the network. It subscribes to local queries and re-renders when the local data changes.
- Each record carries sync metadata: `updatedAt` or a version, a `deleted` flag, and a sync status.
- Records get **client-generated ids** (UUIDs), so they can be created and referenced offline, and no temporary-id mapping is needed.

**The queue of pending changes (outbox)**

Each local write also inserts an operation, in the same transaction:

```ts
type PendingOp = {
  id: string;            // UUID, also sent as the idempotency key
  entity: 'order';
  entityId: string;
  type: 'create' | 'update' | 'delete';
  payload: unknown;
  createdAt: number;
  attempts: number;
};
```

- Operations are sent in order, at least per entity.
- The server stores the operation id and ignores repeats, so a retry after a lost response is safe (#356).
- **Temporary failures** (network, 5xx): retry with backoff. **Permanent failures** (validation, permission, 409): stop retrying, mark the record as failed, and tell the user. One bad operation must not block the queue forever.

**Pulling changes**

- The client stores a cursor from the last sync (a server timestamp or change sequence), and asks for "changes since".
- Deletes are sent as **tombstones**; otherwise the client never learns that a row is gone.
- Apply a pulled batch in one transaction.
- Sync a subset the user needs (their region, the last 30 days), not the whole database.

**When to sync**

App start, return to the foreground, connectivity regained, pull-to-refresh, a silent push as a hint, and a periodic background task where the OS allows it (#704).

**Conflicts**

| Strategy | How | Fits |
|---|---|---|
| Last write wins | newest timestamp replaces the record | low-value data, single-user records |
| Field-level merge | merge changed fields; conflict only on the same field | forms edited by several people |
| Version check | send the base version; server returns 409; client merges or asks | important records (#337) |
| Domain operations | send "add 2 to quantity", not "quantity = 5" | counters, stock |
| CRDTs | data types that always merge | collaborative text and documents |

Client clocks are unreliable, so the server should assign the order. Whatever rule you pick, the user should never silently lose work.

**UI honesty**

Show the state: saved locally, syncing, synced, failed. Show when the data was last updated. Let the user retry or discard a failed change.

**Hard parts people forget**

- **Auth offline:** tokens expire. Queue the changes and re-authenticate on reconnect, without dropping the queue.
- **Schema changes:** local migrations, and an old app replaying old-format operations against a newer API.
- **Logout and account switch:** unsynced changes must be warned about, and local data wiped.
- **Attachments:** photos upload separately and resumably, linked by id.
- **Storage limits and encryption** of sensitive local data (#681).
- **Testing:** kill the app mid-sync, go offline mid-request, replay the queue twice.

**Build or buy**

Sync engines such as WatermelonDB, PowerSync, ElectricSQL and RxDB solve the generic parts. Writing your own is reasonable for a narrow model, and expensive for a broad one.

**Follow-up:** a user edits an order offline, and meanwhile the order is cancelled on the server. What happens on sync? (The push returns a conflict. The app marks the local change as failed, pulls the cancelled state, and tells the user what happened, keeping their text available to copy.)
