## Hints

- If you mock `fetch` with `jest.fn()`, what parts of your real code never run?
- At which layer does MSW intercept requests, in the browser and in Node?
- How do you make one test return a 500 without affecting the others?

## Answer

Components that fetch data need predictable responses in tests. Common options, from most coupled to least:

1. **Mock your own module:** `vi.mock('./api')` and return fixtures. Fast, but the API client, URL building, headers and error parsing are never tested, and the test knows implementation details.
2. **Mock `fetch` or axios directly:** `globalThis.fetch = vi.fn()`. You have to fake the whole `Response` shape, and switching from `fetch` to axios breaks every test.
3. **Intercept at the network level with Mock Service Worker (MSW).** Your real code runs unchanged, including the API client, and only the network is replaced.

**MSW** defines request handlers once and reuses them in unit tests (Node), in the browser during development, in Storybook and in Playwright:

```ts
// mocks/handlers.ts
import { http, HttpResponse } from 'msw';

export const handlers = [
  http.get('/api/orders', () => HttpResponse.json([{ id: '1', total: 99 }])),
  http.post('/api/orders/:id/cancel', ({ params }) => HttpResponse.json({ id: params.id, status: 'cancelled' })),
];

// test setup (Vitest/Jest)
import { setupServer } from 'msw/node';
export const server = setupServer(...handlers);
beforeAll(() => server.listen({ onUnhandledRequest: 'error' }));
afterEach(() => server.resetHandlers());
afterAll(() => server.close());
```

Override a handler for one test to cover error and edge cases:

```ts
test('shows an error when orders fail to load', async () => {
  server.use(http.get('/api/orders', () => new HttpResponse(null, { status: 500 })));
  render(<Orders />);
  expect(await screen.findByRole('alert')).toHaveTextContent(/couldn't load orders/i);
});
```

**Why it's often better:**

- Tests exercise the **real request code**, so a wrong URL, a missing header or a broken error parser fails the test.
- They're **independent of the HTTP library**, so refactoring `fetch` to axios or TanStack Query doesn't touch the tests.
- In the browser it runs as a **Service Worker**, so you can develop the UI before the backend exists and demo edge cases.
- `onUnhandledRequest: 'error'` catches requests you forgot about.

**Caveats:** handlers can drift from the real API, so generate them or the fixtures from the OpenAPI spec, or add contract tests. Don't build a second backend inside the handlers: keep them dumb and return fixtures.
