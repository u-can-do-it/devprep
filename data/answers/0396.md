## Hints

- Which of the two is replaced when you pass arguments to `docker run image ...`?
- What happens when you combine both instructions in one image?
- Which process becomes PID 1, and who receives `SIGTERM` when the container stops?

## Answer

Both define what runs when the container starts, but they play different roles:

- **`ENTRYPOINT`** is the fixed executable. Arguments passed to `docker run` are **appended** to it. You override it only with `--entrypoint`.
- **`CMD`** provides **default arguments** (or a default command if there is no entrypoint). Anything passed after the image name in `docker run` **replaces** it.

Used together, `ENTRYPOINT` is the program and `CMD` its default flags:

```dockerfile
ENTRYPOINT ["node", "dist/cli.js"]
CMD ["--help"]
# docker run my-cli            -> node dist/cli.js --help
# docker run my-cli migrate    -> node dist/cli.js migrate
```

**Exec form vs shell form:**

- Exec form (`["node", "server.js"]`) runs the binary directly, so it is **PID 1** and receives `SIGTERM` from `docker stop`, letting it shut down gracefully.
- Shell form (`CMD node server.js`) wraps it in `/bin/sh -c`. The shell becomes PID 1 and usually doesn't forward signals, so the app is killed with `SIGKILL` after the 10-second timeout: dropped requests, unclosed DB connections.

Rule of thumb: use exec form, `CMD` for a normal app, `ENTRYPOINT` + `CMD` for CLI-style images or a wrapper script that ends with `exec "$@"`.

**Follow-up:** "Why add `--init` or `tini`?" Because PID 1 also has to reap zombie processes and handle signals, and a small init process does both properly.
