## Hints

- What happens to the running time of `a.filter((x) => b.includes(x))` when both arrays double in size?
- Why is `arr.shift()` slower than `arr.pop()`?
- What does `[...acc, item]` inside `reduce` cost?

## Answer

**Big-O** describes how running time (or memory) **grows** with the input size `n`, ignoring constants and smaller terms. It's normally the worst case. In an interview, always state both **time and space** complexity.

| Complexity | Name | Example |
|---|---|---|
| O(1) | constant | `arr[i]`, `map.get(k)`, `set.has(x)` |
| O(log n) | logarithmic | binary search |
| O(n) | linear | one loop, `includes`, `indexOf` |
| O(n log n) | linearithmic | `sort` |
| O(n²) | quadratic | nested loops over the same data |
| O(2ⁿ) | exponential | naive recursive Fibonacci, all subsets |

**Common JavaScript operations:**

| Operation | Cost |
|---|---|
| `arr[i]`, `push`, `pop`, `arr.length` | O(1) (`push` is amortized) |
| `shift`, `unshift`, `splice` | O(n): every element has to move |
| `includes`, `indexOf`, `find`, `some`, `filter`, `map` | O(n) |
| `Set.has`/`add`/`delete`, `Map.get`/`set`, `obj[key]` | O(1) on average (hash table) |
| `sort` | O(n log n), stable since ES2019 |
| `slice`, spread `[...arr]`, `concat`, `Object.keys`, `JSON.stringify` | O(n) |
| `str.includes`, `str.indexOf` | O(n·m) in the worst case |

**The classic mistakes:**

```js
// O(n·m): includes scans b for every element of a
const common = a.filter((x) => b.includes(x));

// O(n + m): build a Set once, then O(1) lookups
const inB = new Set(b);
const common2 = a.filter((x) => inB.has(x));
```

```js
// O(n²): each spread copies the whole accumulator
const byId = users.reduce((acc, u) => ({ ...acc, [u.id]: u }), {});

// O(n)
const byId2 = new Map(users.map((u) => [u.id, u]));
```

A queue built with `shift()` is O(n) per dequeue. For BFS on big inputs, use an index pointer (`let head = 0; queue[head++]`).

**How to talk about it in an interview:**

1. Start with the brute force and its complexity ("two nested loops, so O(n²)").
2. Name the bottleneck ("the inner lookup") and the fix ("a hash map makes it O(1), so O(n) overall, at the cost of O(n) extra memory").
3. Mention space, including recursion depth (call stack).
4. Don't over-optimize: for n = 100, readable O(n²) code is fine. Say so.
