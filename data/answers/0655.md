## Hints

- What does the model see of your skill before it decides to load it?
- Which parts of the procedure should be prose for the model, and which should be a script it runs?
- How do you find out that a skill never triggers, or triggers when it shouldn't?

## Answer

> A skill is a folder with a `SKILL.md`: YAML frontmatter with a `name` and a `description`, then instructions in Markdown. The model sees only the description until the task matches, so the description has to say what the skill does and when to use it. Keep the body a short procedure with verification steps, move long reference material into separate files and deterministic steps into scripts. Test it in a fresh session: does it trigger on a realistic prompt, and does the agent then do the right thing?

**Layout and location**

```
.claude/skills/add-migration/
  SKILL.md          instructions (required)
  reference.md      naming rules, loaded only when the body points to it
  scripts/check.sh  run by the agent, not read into context
```

Project skills live in `.claude/skills/` and are committed, personal ones in `~/.claude/skills/`, and plugins ship their own, invoked as `/plugin:skill`. On a name clash, managed (enterprise) wins over personal and personal over project. The older `.claude/commands/*.md` files are the same thing in a single file and still work.

**`SKILL.md`**

```md
---
name: add-migration
description: Create and verify a database migration. Use when a task changes the schema, adds a column, index or table, or mentions migrations.
argument-hint: [short-name]
---

Create a migration named `$ARGUMENTS`.

1. Read `prisma/schema.prisma` and change only the models the task needs.
2. Run `pnpm prisma migrate dev --name $ARGUMENTS --create-only`, then read the generated SQL.
3. A new column on an existing table must be nullable or have a default. See `reference.md` for the backfill pattern.
4. Run `scripts/check.sh`. It fails on `DROP` statements and missing indexes on foreign keys.
5. Report the SQL and the result of the check. Never edit a migration that is already on `main`.
```

**Frontmatter that matters**

| Field | Effect |
|---|---|
| `name` | the command name (`/add-migration`); defaults to the folder name |
| `description` | what it does and when to use it; this is what triggers it |
| `argument-hint` | shown in autocomplete |
| `disable-model-invocation: true` | only you can run it with `/name`. Use for side effects: deploy, release, send |
| `user-invocable: false` | hidden from the `/` menu; background knowledge the model loads itself |
| `allowed-tools` | tools the skill may use without asking |
| `context: fork` + `agent` | run the skill in a subagent, so its work doesn't fill the main context |
| `paths` | glob patterns; the skill activates when matching files are touched |
| `model`, `hooks` | a model for this turn; hooks registered when the skill is used |

**How loading works** (progressive disclosure)

1. At session start only names and descriptions are in context, within a small budget (about 1% of the context window). Long descriptions get truncated, so put the trigger words first.
2. When the task matches or you type `/name`, the whole `SKILL.md` enters the conversation once and stays.
3. Supporting files load when the body refers to them; scripts are executed, and only their output costs tokens.
4. After compaction only the beginning of each used skill is kept, so the most important rules go at the top.

**Arguments and live data:** `$ARGUMENTS` is everything typed after the name, `$0`, `$1` are positional arguments. A line such as `` !`git diff HEAD` `` runs before the model sees the skill and is replaced by the command's output, which is how you inject current state.

**What makes a skill good**

- **The description is written for the model:** what and when, with the words a user would actually use ("migration", "add a column"). "Helps with databases" never triggers at the right time.
- **One job per skill.** "Backend stuff" is a `CLAUDE.md` section, not a skill.
- **A procedure with a way to verify** each step, and the reasons behind non-obvious rules. The model follows rules better when it knows why.
- **Scripts for anything deterministic** (validation, scaffolding): cheaper, repeatable and testable.
- **Short.** Keep `SKILL.md` to a few hundred lines at most, and don't explain what the model already knows.
- **No secrets**, and no destructive action without `disable-model-invocation`.

**Testing it**

- **Triggering:** in a fresh session, give a realistic prompt that doesn't name the skill. Did it load? Then an unrelated prompt. Did it stay out?
- **Behaviour:** run it on a real task two or three times. Where the agent deviates, the instructions are ambiguous; fix the text or move the step into a script.
- **Regression:** keep a few past tasks as test cases and rerun them when you change the skill or the model (#543).
- Review skills in pull requests like code, give them owners, and delete the ones nobody uses.

**Security:** a skill from the internet is a prompt plus scripts that run with your permissions. Read it before installing, the same as any dependency (#525).

**Follow-up:** the skill triggers, but the agent skips step 4. What are your options? (Make the step explicit and explain why, move it into a script the earlier step calls, or enforce it with a hook: see #653.)
