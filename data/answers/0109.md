## Hints

- When a browser sends a request to your site from another site's page, which cookies get attached?
- Can the attacker's page read the response, or only trigger the request?
- What can a legitimate page include in its request that an attacker's page cannot?

## Answer

**Cross-Site Request Forgery (CSRF)** tricks a logged-in user's browser into sending a state-changing request to your site. Because the browser attaches cookies automatically, the request looks authenticated.

```html
<!-- on evil.example -->
<form action="https://bank.example/transfer" method="POST">
  <input type="hidden" name="to" value="attacker" />
  <input type="hidden" name="amount" value="1000" />
</form>
<script>document.forms[0].submit()</script>
```

The attacker can't read the response – they just need the side effect.

**Defenses:**

**1. `SameSite` cookies**

- `Strict` – cookie never sent on cross-site requests (even following a link – can hurt UX).
- `Lax` – sent only on top-level `GET` navigations; blocks cross-site `POST`s, iframes, `fetch`. Default in modern browsers when unspecified.
- `None` – always sent; requires `Secure`. Needed for genuine cross-site embedding.

```http
Set-Cookie: session=abc; HttpOnly; Secure; SameSite=Lax; Path=/
```

Note: "site" means registrable domain, so `evil.example.com` and `app.example.com` are **same-site** – SameSite won't protect against a compromised sibling subdomain.

**2. CSRF tokens** – a random token tied to the session, included in forms or a header, and verified server-side (synchronizer token or double-submit cookie). Most frameworks provide this.

**3. Check `Origin` / `Sec-Fetch-Site` headers** for state-changing requests.

**4. Never change state with `GET`.**

APIs using `Authorization: Bearer` headers (not cookies) aren't vulnerable to classic CSRF, since browsers don't add that header automatically.

**Follow-up:** Does CORS prevent CSRF? (No – CORS restricts reading responses; simple cross-origin `POST`s are still sent.)
