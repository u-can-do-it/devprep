## Hints

- How would you know when an element scrolls into view without running code on every scroll event?
- What should a component do when its own size changes, but the window hasn't been resized?
- Why is reading `getBoundingClientRect()` inside a scroll handler a performance problem?

## Answer

All three are **asynchronous, browser-batched observers**. Instead of polling or listening to high-frequency events and measuring layout yourself, you register interest and the browser calls you **only when something relevant changes**, at a point in the frame where the data is already computed.

**`IntersectionObserver`** watches visibility relative to the viewport or a scroll container:

```js
const io = new IntersectionObserver((entries) => {
  for (const entry of entries) {
    if (entry.isIntersecting) {
      loadMore();
      io.unobserve(entry.target);
    }
  }
}, { rootMargin: '200px 0px', threshold: 0 }); // start 200px before it's visible

io.observe(document.querySelector('#sentinel'));
```

Use cases: infinite scroll, lazy-loading beyond what `loading="lazy"` covers, pausing videos or animations off screen, impression analytics, highlighting the "active section" in a table of contents.

**`ResizeObserver`** watches an **element's** size, not just the window. Use it for charts and canvases that redraw at their container's size, text truncation logic, and components that react to their own width (when container queries can't, because the logic is in JavaScript).

```js
new ResizeObserver(([entry]) => {
  const { inlineSize } = entry.contentBoxSize[0];
  chart.resize(inlineSize);
}).observe(container);
```

**`MutationObserver`** watches **DOM changes**: child nodes, attributes, text. Callbacks run as **microtasks**, batched. Use it for third-party widgets you don't control, editors, or reacting to injected content. Keep the observed subtree and options narrow.

**Why they beat polling and scroll handlers:**

- No forced synchronous layout. Scroll handlers that call `getBoundingClientRect()` cause layout thrashing and hurt INP.
- They don't run at all when nothing changes, and IntersectionObserver works across iframes.

**Pitfalls:**

- Always `disconnect()` or `unobserve()` when done (in React, in the `useEffect` cleanup).
- Changing an element's size inside its own ResizeObserver callback can cause the "ResizeObserver loop completed with undelivered notifications" warning.
- IntersectionObserver isn't pixel-accurate for animations. Use scroll-driven animations for those.

**Follow-up:** `PerformanceObserver` follows the same pattern for performance entries (LCP, long animation frames), and it's what the `web-vitals` library uses.
