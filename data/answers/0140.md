## Hints

- How does a producer's relationship to its consumers change when it publishes an event instead of calling an API?
- What happens to requests when a downstream service is slow or temporarily down?
- If a message can be delivered more than once, what must consumers guarantee?

## Answer

In **event-driven architecture**, services communicate by publishing events ("OrderPlaced") rather than calling each other directly. Other services subscribe and react. The producer doesn't know or care who consumes the event.

**Message queues/brokers** (RabbitMQ, SQS, Kafka, NATS) sit in between and provide:

- **Decoupling:** add new consumers without touching the producer.
- **Buffering / load leveling:** absorb traffic spikes; consumers process at their own pace.
- **Resilience:** if a consumer is down, messages wait instead of failing the user request.
- **Async work:** move slow tasks (emails, video processing) out of the request path.
- **Fan-out** to many subscribers; Kafka-style logs also allow **replay**.

**Problems they introduce:**

- **Delivery semantics:** most systems are *at-least-once*, so consumers must be **idempotent** (dedupe by event ID).
- **Ordering:** guaranteed only within a partition/key.
- **Eventual consistency:** the UI may briefly show stale state.
- **Poison messages:** need retries with backoff and a dead-letter queue.
- **Dual writes:** saving to the DB and publishing can diverge — use the **transactional outbox** pattern.
- Harder debugging: need correlation IDs and distributed tracing; event schemas need versioning.

```python
def handle_order_placed(event):
    if processed_events.exists(event["id"]):  # idempotency
        return
    reserve_stock(event["order_id"])
    processed_events.add(event["id"])
```

**Follow-up:** "Queue vs pub/sub vs log?" — a queue delivers each message to one worker; pub/sub to all subscribers; a log (Kafka) retains messages for replay by independent consumer groups.
