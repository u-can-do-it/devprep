## Hints

- How is a JavaScript `number` stored in memory, and can `0.1` be represented exactly in binary?
- What is the largest integer you can store without losing precision?
- How would you safely handle money or 64-bit IDs?

## Answer

Every `number` in JavaScript is an **IEEE 754 double-precision float** (64 bits). Fractions like `0.1` and `0.2` have no exact binary form, so they are stored as the closest approximation. The small errors add up:

```js
0.1 + 0.2;              // 0.30000000000000004
0.1 + 0.2 === 0.3;      // false
Math.abs(0.1 + 0.2 - 0.3) < Number.EPSILON; // true, compare with a tolerance
```

`Number.EPSILON` works as a tolerance for values around 1. For larger values, scale the tolerance to their size.

**Practical rules:**

- **Money:** store integer minor units (cents), or use a decimal library. Format for display with `Intl.NumberFormat`.
- **Rounding:** `toFixed` returns a string and can surprise you (`(1.005).toFixed(2)` is `'1.00'`).
- **Special values:** `NaN !== NaN` (use `Number.isNaN`), and `-0` exists (`Object.is(-0, 0)` is `false`).

**Safe integers:** a double can represent every integer exactly only up to `Number.MAX_SAFE_INTEGER` (2^53 − 1). Beyond that, precision is lost: `2 ** 53 + 1 === 2 ** 53` is `true`.

**`BigInt`** stores integers of any size:

```js
const big = 9007199254740993n;
big + 1n;          // 9007199254740994n
// big + 1;        // TypeError: can't mix BigInt and Number
```

BigInt limits: it can't mix with `number` without explicit conversion, it doesn't work with `Math`, `JSON.stringify` throws on it, and it is slower. Use it for 64-bit IDs, cryptography or exact large counters. A common real bug: an API returns 64-bit IDs as JSON numbers and the client silently corrupts them. Send them as strings instead.
