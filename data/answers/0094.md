## Hints

- What happens to fields you omit in the request body for each method?
- Is each of them idempotent?
- How would you express "remove this field" in a partial update?

## Answer

- **`PUT`** replaces the whole resource with the representation you send. Omitted fields are reset/removed. It is **idempotent** – sending the same body twice gives the same result. It can also create a resource at a client-chosen URI.
- **`PATCH`** applies a **partial** modification. Only the fields you send change. It is **not guaranteed idempotent** (depends on the patch format).

```http
PUT /users/42
{"name": "Ana", "email": "ana@example.com", "role": "admin"}

PATCH /users/42
{"role": "admin"}
```

Two common `PATCH` formats:

- **JSON Merge Patch** (RFC 7396, `application/merge-patch+json`) – send the changed fields; `null` means delete the field.
- **JSON Patch** (RFC 6902, `application/json-patch+json`) – a list of operations:

```json
[
  { "op": "replace", "path": "/role", "value": "admin" },
  { "op": "remove", "path": "/nickname" }
]
```

In practice most APIs use `PATCH` with merge semantics for forms that edit a few fields, and `PUT` when the client owns the full document (e.g. a settings object).

**Pitfall:** implementing `PUT` as a partial update confuses clients and can silently keep stale fields. Also consider concurrent edits – use `ETag` + `If-Match` to avoid lost updates.
