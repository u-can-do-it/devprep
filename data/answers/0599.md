## Hints

- What happens if an endpoint binds the request body straight to an EF Core entity that has an `IsAdmin` or `Price` property?
- Which of `FromSql($"...{id}")` and `FromSqlRaw("..." + id)` sends a parameter, and why does the C# type of the argument matter?
- Your app runs on three instances behind a load balancer and users get logged out or see antiforgery errors at random. Which keys are involved?

## Answer

ASP.NET Core has good defaults, but most real vulnerabilities come from how the app uses them. Go through the request path: binding, data access, cookies, cross-origin access, keys and secrets.

**1. Overposting (mass assignment)**

Binding the body to an entity lets clients set fields you never meant to expose:

```csharp
// BAD: client sends { "name": "x", "isAdmin": true } and it gets saved
app.MapPut("/users/{id}", async (int id, User input, AppDbContext db) => { ... });

// GOOD: a DTO with only the editable fields, copied explicitly
public record UpdateProfile(string DisplayName, string? Bio);
app.MapPut("/users/{id}", async (int id, UpdateProfile dto, AppDbContext db, ClaimsPrincipal user) =>
{
    var u = await db.Users.FindAsync(id);
    if (u is null || u.Id != user.GetUserId()) return Results.NotFound(); // also check ownership (IDOR)
    u.DisplayName = dto.DisplayName;
    u.Bio = dto.Bio;
    await db.SaveChangesAsync();
    return Results.NoContent();
});
```

The same applies to responses: return DTOs, not entities, so you don't leak password hashes or internal fields.

**2. SQL injection with EF Core**

LINQ queries are always parameterized. Raw SQL depends on the method:

```csharp
db.Users.FromSql($"SELECT * FROM users WHERE email = {email}");      // safe: FormattableString → parameter
db.Users.FromSqlRaw("SELECT * FROM users WHERE email = '" + email + "'"); // injectable
db.Users.FromSqlRaw("SELECT * FROM users WHERE email = {0}", email);   // safe: positional parameter
```

The trap: `FromSql` and `ExecuteSql` are safe only while the argument is an interpolated string literal. Build the string into a `string` variable first and pass it to `FromSqlRaw`, and the protection is gone. Identifiers (column names for sorting) can't be parameters: map them from an allow-list. The same rules apply to Dapper.

**3. CSRF and antiforgery**

- CSRF matters when the browser sends credentials automatically: **cookie authentication**. An API that only accepts a bearer token in the `Authorization` header isn't CSRF-prone (but then the token must be stored safely on the client).
- MVC: `[ValidateAntiForgeryToken]` or the global `AutoValidateAntiforgeryTokenAttribute`. Razor Pages validate by default. Minimal APIs (.NET 8+): `app.UseAntiforgery()` validates endpoints that bind form data.
- Also set cookies `HttpOnly`, `Secure` and `SameSite=Lax` or `Strict`.

**4. CORS**

CORS relaxes the browser's same-origin policy; it is not an authorization mechanism. List exact origins, and never combine credentials with any origin (`AllowAnyOrigin()` with `AllowCredentials()` is rejected by the framework, so people "fix" it with `SetIsOriginAllowed(_ => true)`, which is just as bad).

```csharp
builder.Services.AddCors(o => o.AddPolicy("web", p => p
    .WithOrigins("https://app.example.com").AllowCredentials()
    .WithMethods("GET", "POST", "PUT", "DELETE").WithHeaders("Content-Type", "Authorization")));
```

**5. Data Protection keys**

Data Protection encrypts auth cookies, antiforgery tokens and TempData. By default each instance generates its **own key ring** locally, so a cookie issued by instance A can't be read by instance B, and in a container the keys vanish on restart. Persist the keys to shared storage and encrypt them at rest:

```csharp
builder.Services.AddDataProtection()
    .SetApplicationName("clinic-portal")                       // same name on every instance
    .PersistKeysToAzureBlobStorage(blobUri, credential)        // or Redis, a DbContext, a file share
    .ProtectKeysWithAzureKeyVault(keyUri, credential);
```

**6. Secrets**

- User secrets (`dotnet user-secrets`) are for local development only; they're plain JSON on disk.
- In production, load secrets from a vault (Azure Key Vault, AWS Secrets Manager) through a configuration provider, authenticate with a managed identity rather than a stored key, and never commit them to `appsettings.json`.
- Keep secrets out of logs (#589) and exception details out of responses (#587).

**7. The rest of the checklist**

HTTPS redirection and HSTS, a fallback authorization policy so new endpoints are protected by default (#586), rate limiting on login and expensive endpoints (`AddRateLimiter`), request size limits, and dependency scanning (`dotnet list package --vulnerable`).

**Follow-up:** after moving to Kubernetes, users are logged out on every deployment. Why? (The Data Protection key ring lived in the pod's file system and was lost on restart, so old cookies can't be decrypted. Persist the keys to shared, durable storage.)
