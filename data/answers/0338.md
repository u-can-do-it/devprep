## Hints

- What work happens each time a new PostgreSQL connection is opened?
- What happens to the database when 200 serverless function instances each open their own connections?
- Why might a smaller pool give higher throughput than a bigger one?

## Answer

Opening a DB connection is expensive: TCP + TLS handshake, authentication, and in PostgreSQL a **dedicated backend process** per connection (several MB of memory). A **pool** keeps a set of open connections and lends them to requests, so you pay that cost once and cap how many connections hit the database.

**Where pools live:**

- **In the app** – the driver/ORM pool (`pg.Pool`, SQLAlchemy, HikariCP, Prisma). Per process.
- **External pooler** – PgBouncer, Supavisor, RDS Proxy, Neon's pooler. Needed when you have many app instances or **serverless** functions, which would otherwise exhaust `max_connections`.

PgBouncer modes: **session** (one server connection per client session), **transaction** (connection returned after each transaction – most efficient, but session state like `SET`, advisory locks, `LISTEN` doesn't survive; prepared statements need PgBouncer 1.21+ support), **statement** (rare).

```ts
import { Pool } from "pg";
const pool = new Pool({ max: 10, idleTimeoutMillis: 30_000, connectionTimeoutMillis: 2_000 });
const { rows } = await pool.query("SELECT * FROM users WHERE id = $1", [id]);
```

**Sizing:** more is not better. The DB can only run roughly as many queries in parallel as it has CPU cores (plus some for I/O waits); beyond that, connections fight over CPU, locks and memory, and latency rises. A common starting point is around `cores * 2` per database server, then **measure**. Remember the total: `instances × pool size` must stay below `max_connections` minus headroom for migrations and admin.

Pitfalls:

- Leaked connections (not released on error) → pool exhaustion and timeouts; always release in `finally`.
- Long transactions hold connections; set statement and idle-in-transaction timeouts.
- Set a **connection acquire timeout** so requests fail fast instead of queueing forever.
