## Hints

- `services/orders.py` does `from payments import charge`. If you `patch('payments.charge')`, does `orders.py` see the mock?
- What happens when you replace an `async def` function with a plain `Mock` and the code `await`s it?
- How does `spec`/`autospec` catch a test that calls the mock with the wrong arguments?

## Answer

Mocking replaces a dependency (HTTP call, database, clock, email) with a controllable stand-in so the test is fast, deterministic and focused (#135). Python's tools are `unittest.mock` from the standard library, pytest's `monkeypatch` fixture, and the `mocker` fixture from `pytest-mock`.

**`patch`: where it is looked up, not where it is defined.** `patch` swaps a name in a module's namespace at test time. If `orders.py` imported `charge` into its own namespace, patching `payments.charge` changes nothing for it.

```python
# services/orders.py
from payments import charge

def place_order(order):
    return charge(order.total)

# tests/test_orders.py
from unittest.mock import patch

def test_place_order_charges_total(order):
    with patch("services.orders.charge", autospec=True) as charge:   # the name orders.py uses
        charge.return_value = {"status": "ok"}
        result = place_order(order)
    charge.assert_called_once_with(order.total)
    assert result["status"] == "ok"
```

Alternatives: `@patch(...)` as a decorator (mocks arrive as arguments, bottom-up), `patch.object(module, "name")`, `patch.dict(os.environ, {...})`. Pass a dependency explicitly instead of patching when the design allows it; patching is for code you can't inject into.

**`Mock`, `MagicMock`, `AsyncMock`, `spec`:**

- `MagicMock` also implements dunder methods (`__len__`, `__iter__`, context managers); `Mock` doesn't.
- `AsyncMock` returns an awaitable. Replacing an `async def` with a plain `Mock` yields `TypeError: object Mock can't be used in 'await' expression`, or worse, a coroutine that is never awaited. `patch` picks `AsyncMock` automatically when the target is a coroutine function.
- `spec=Class` / `autospec=True` makes the mock reject attributes and call signatures the real object doesn't have, so a renamed method fails the test instead of passing silently. Default to `autospec=True`.
- `side_effect` raises an exception, returns successive values from an iterable, or calls a function: `charge.side_effect = [TimeoutError(), {"status": "ok"}]` tests a retry.
- Assertions: `assert_called_once_with`, `assert_any_call`, `call_args_list`, `assert_not_called`.

**`monkeypatch`** is pytest's fixture for the same job, undone automatically after the test: `monkeypatch.setattr(orders, "charge", fake_charge)`, `monkeypatch.setenv("API_KEY", "x")`, `monkeypatch.delattr`, `monkeypatch.chdir`. Good for simple replacements with a real function or a fake class; use `Mock` when you need call assertions.

**Boundary helpers:** `respx` or `httpx.MockTransport` for HTTP clients, `time-machine` or `freezegun` for time, `pytest-asyncio`/`anyio` for async tests, and for FastAPI `app.dependency_overrides[get_db] = lambda: test_session` instead of patching (#326). Prefer a **fake** (an in-memory repository implementing the same interface) at architectural boundaries; mocks for one-off collaborators.

**Pitfalls interviewers ask about:**

- **Over-mocking:** when every collaborator is mocked, the test asserts the implementation's call sequence, not behaviour; it passes while production breaks. Mock only the slow, non-deterministic or external edge.
- **Mocking what you don't own:** patching `requests.get` ties tests to a library's API; wrap third-party clients in your own adapter and fake that.
- **Wrong patch target** (the `from x import y` trap above) and patches that leak because the `with`/decorator scope was wrong.
- **`Mock()` accepting anything:** without `spec`, `mock.chrage()` is a valid call. Use `autospec`.
- **Forgetting `AsyncMock`** for coroutines and async context managers (`__aenter__`).
- **Time and randomness:** inject a clock or `random.Random(seed)`, or patch them, so tests don't flake (#137).

**Follow-up:** how do you test that an exception from the payment provider is logged and the order is marked `failed` without actually failing anything real? (`side_effect=PaymentError(...)`, then assert on the order state and on `caplog.records`.)
