## Hints

- How do you send a request through your Fastify or Express app in a test without starting a server on a port?
- Why might mocking the Prisma client give you green tests and a broken production query?
- Tests run in parallel and share one database. How do you stop them from seeing each other's data?
- How does a test call a protected endpoint without a real Entra ID login?
- What should an authorization test for "user B can't approve user A's offer" assert?

## Answer

For a CRUD-heavy business API, most bugs live in the seams: SQL, validation, authorization, transactions. So the bulk of backend tests should be **integration tests through HTTP against a real PostgreSQL**, with fast unit tests for pure logic (state machines, calculations) and few end-to-end tests (#134).

**1. Build the app without listening:**

```ts
// app.ts
export async function buildApp(deps: { db: PrismaClient; clock?: () => Date; mailer?: Mailer }) {
  const app = Fastify({ logger: false });
  app.decorate('deps', deps);
  await app.register(routes);
  return app;
}
// server.ts calls buildApp(...) and app.listen(); tests never do
```

Dependencies (database, clock, mailer, HTTP clients) are passed in, so tests can replace the ones that cross the system boundary.

**2. Send requests:**

```ts
const res = await app.inject({
  method: 'POST', url: '/api/offers/123/approve',
  headers: { authorization: `Bearer ${await tokenFor(manager)}` },
});
expect(res.statusCode).toBe(200);
expect(await db.offer.findUnique({ where: { id: '123' } })).toMatchObject({ status: 'APPROVED' });
```

Fastify's `inject` (#618) or `supertest(app.server)` for Express and NestJS (#619) run the full pipeline: routing, hooks, validation, serialization, error handler.

**3. A real database:**

- **Testcontainers** (`@testcontainers/postgresql`) starts a throwaway Postgres in Docker from the test setup; or a `services: postgres` container in GitHub Actions plus Docker Compose locally (#399).
- Run **`prisma migrate deploy`** once in global setup, so tests also verify the migrations.
- Same major Postgres version as production, so `jsonb`, constraints and locking behave the same.

**4. Isolation between tests:**

| strategy | how | trade-off |
|---|---|---|
| truncate between tests | `TRUNCATE offer, ... RESTART IDENTITY CASCADE` in `beforeEach` | simple; tests in one file run sequentially |
| database per worker | create `test_${process.env.VITEST_POOL_ID}` from a migrated template DB (`CREATE DATABASE ... TEMPLATE`) | parallel and fast; a bit of setup |
| transaction per test, rolled back | wrap each test in a transaction | fast, but awkward when the code under test opens its own transactions |
| unique data per test | random ids/emails, no cleanup | easy, but data grows and counts are unreliable |

**5. Test data:** small **factories** (`createUser({ roles: ['manager'] })`, `createOffer({ owner })`) that insert valid rows with sensible defaults. Each test creates exactly what it needs and states the important values explicitly. Avoid one giant shared seed that every test silently depends on.

**6. Auth in tests:** don't call Entra ID (#624). Either sign test JWTs with a test key pair that the app trusts in the test environment, or inject an `authenticate` dependency that reads a test header. Then cover the matrix: no token → 401, wrong role → 403, other user's record → 404/403 (#371, #622), happy path → 200.

**7. External systems:** mock HTTP at the network level with MSW for Node or `nock` (#461), including failures (timeouts, 429, 500) to check retries. Use fakes for the mailer and queue and assert on what was "sent". Use a fixed clock for deadlines and reminders.

**8. What to assert:** the status code, the response body shape (snapshot only small, stable parts), **and the database state and side effects** (audit row written, notification enqueued, nothing written on validation error).

**9. Tricky cases worth a test:** two concurrent approvals (`Promise.all` of two requests, expect one success and one conflict, #621); unique-constraint violations mapped to 409; pagination boundaries; transactions rolled back when a later step fails.

**Why not mock Prisma everywhere:** a mocked `db.offer.findMany` returns whatever you told it to, so wrong `where` clauses, missing `include`s, constraint violations and transaction bugs pass. Mock Prisma only in unit tests of logic that isn't about the query.

**Speed:** Vitest with a reused container and per-worker databases runs hundreds of HTTP-level tests in seconds. In CI with Nx, only affected projects run their tests (#616).

**Follow-up:** a test passes alone but fails when the whole suite runs. What do you look for? (Shared state: leftover rows from another test, a module-level cache or singleton, mocks not restored, fake timers left on, or an order dependency on auto-increment ids.)
