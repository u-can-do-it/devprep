## Hints

- What's the difference between what the planner estimated and what actually happened, and where do you see both?
- When is a sequential scan actually the right choice?
- What does it suggest if a node says it sorted on disk?

## Answer

`EXPLAIN` shows the planner's chosen plan with **estimates**; `EXPLAIN ANALYZE` actually runs the query and adds **real timings and row counts**. Add `BUFFERS` to see cache hits vs disk reads (PostgreSQL 18 includes buffers by default with `ANALYZE`). Run it on a copy for writes, or wrap in `BEGIN ... ROLLBACK`.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE customer_id = 42 ORDER BY created_at DESC LIMIT 20;
```

Read the tree **inside-out** (deepest nodes run first). For each node check:

- **Scan type** – `Seq Scan` (whole table), `Index Scan`, `Index Only Scan` (no heap visits), `Bitmap Heap Scan` (many matching rows). A seq scan on a big table with a selective filter suggests a missing or unusable index.
- **Estimated vs actual rows** – `rows=10` vs `actual rows=500000` means stale or insufficient statistics; run `ANALYZE`, raise the statistics target, or add extended statistics for correlated columns. Bad estimates lead to bad join choices.
- **Join type** – `Nested Loop` (good for few outer rows with an index on the inner side), `Hash Join` (large unsorted sets), `Merge Join` (both inputs sorted).
- **loops** – actual time is per loop; a cheap inner node executed 100,000 times is the real cost.
- **Rows Removed by Filter** – lots of rows read then discarded → better index or composite index.
- **Sort Method: external merge Disk** – sort spilled to disk; add an index matching `ORDER BY` or raise `work_mem` for that query.

Workflow: find the node where most time goes, form a hypothesis (index, rewrite, statistics), change one thing, re-run. Tools like explain.dalibo.com visualize plans; `pg_stat_statements` tells you *which* queries are worth optimizing in the first place.
