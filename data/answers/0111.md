## Hints

- If an attacker injects a `<script>` tag, what could tell the browser not to run it?
- How can you allow your own inline scripts without allowing injected ones?
- How do you deploy a strict policy without breaking production on day one?

## Answer

**Content Security Policy (CSP)** is a response header that tells the browser which sources of scripts, styles, images, frames, etc. are allowed. It's a **defense-in-depth** layer that mitigates XSS and data injection when other defenses fail.

**Strict, nonce-based policy (recommended):**

```http
Content-Security-Policy:
  script-src 'nonce-r4nd0m' 'strict-dynamic';
  object-src 'none';
  base-uri 'none';
  frame-ancestors 'self';
  report-to csp-endpoint
```

```html
<script nonce="r4nd0m" src="/app.js"></script>
```

- A fresh random **nonce** per response; only scripts carrying it run. Injected `<script>` tags don't know the nonce.
- **`'strict-dynamic'`** lets trusted scripts load further scripts, so you don't maintain huge domain allowlists (which are often bypassable via JSONP or open CDNs).
- Avoid `'unsafe-inline'` and `'unsafe-eval'` – they largely defeat the purpose.
- `frame-ancestors` replaces `X-Frame-Options` for clickjacking protection.
- Hashes (`'sha256-...'`) work for static inline scripts on cached/static pages where nonces aren't possible.

**Rollout plan:**

1. Start with **`Content-Security-Policy-Report-Only`** and a reporting endpoint.
2. Analyze violations; refactor inline event handlers (`onclick=`) and `eval` usage.
3. Add nonces via your framework (Next.js middleware can generate a nonce per request; note this forces dynamic rendering).
4. Enforce, keep monitoring reports, and consider **Trusted Types** (`require-trusted-types-for 'script'`) to lock down DOM sinks.

**Pitfalls:** third-party tags (analytics, tag managers) that inject inline scripts, nonces cached by a CDN (must be per response), and believing CSP replaces output encoding – it doesn't.
