## Hints

- During a rolling deploy, which versions of the app are talking to the database at the same time?
- Which DDL statements take locks that block reads or writes on a big table?
- How would you rename a column without breaking the old code that's still running?

## Answer

During a rolling or blue-green deploy, **old and new app versions run simultaneously** against one database. So every migration must be compatible with both. The core technique is **expand / contract** (parallel change):

1. **Expand** – add new structures in a backward-compatible way (new nullable column, new table, new index).
2. **Migrate** – deploy code that writes to both old and new; **backfill** existing rows in small batches.
3. **Switch reads** to the new structure.
4. **Contract** – once no running code uses the old column, drop it in a later deploy.

Renaming `name` → `full_name` is therefore 3–4 deploys, not one `ALTER ... RENAME`.

**Avoid long locks (PostgreSQL examples):**

```sql
SET lock_timeout = '3s';   -- fail fast instead of queueing behind a long query and blocking everyone

CREATE INDEX CONCURRENTLY idx_orders_status ON orders (status);

ALTER TABLE orders ADD CONSTRAINT fk_orders_customer
  FOREIGN KEY (customer_id) REFERENCES customers(id) NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT fk_orders_customer;  -- doesn't block writes

-- NOT NULL on an existing column without a long exclusive scan:
ALTER TABLE users ADD CONSTRAINT email_nn CHECK (email IS NOT NULL) NOT VALID;
ALTER TABLE users VALIDATE CONSTRAINT email_nn;
ALTER TABLE users ALTER COLUMN email SET NOT NULL;  -- uses the validated check (PG 12+)
```

Also: adding a column with a constant default is instant since PG 11, but changing a column type usually rewrites the table – do it via a new column + backfill.

**Process:**

- Migrations are versioned and run by a tool (Flyway, Liquibase, Alembic, Prisma Migrate, Atlas) as a separate CI/CD step, **before** the code that needs them.
- Backfills run as batched background jobs, throttled and resumable, not inside the migration transaction.
- Prefer **roll-forward** over down-migrations; destructive steps happen only after the new code is proven.
- Lint migrations in CI (e.g. squawk, strong_migrations-style checks) and test on a production-sized copy.
