## Hints

- Is the stutter on the JS thread or the UI thread? How can you tell?
- What makes every visible row re-render when one thing changes?
- `FlatList` unmounts rows that leave the window. What does FlashList do with them instead?

## Answer

> First measure in a release build on the slow phone, and find out which thread drops frames. Blank areas during fast scrolling mean JS can't render rows fast enough. Stutter with rows present usually means heavy views or large images. Typical fixes: memoised, cheap rows, images sized for the row, `getItemLayout`, and tuned window props. FlashList recycles row views instead of destroying them, which often removes the problem at once.

**1. Measure**

- Use a **release build**. Debug builds are several times slower.
- Open the performance monitor: it shows **JS** and **UI** frame rates separately (#694).
- Record with the React DevTools Profiler while scrolling: which components render, how often and why (#216).

**2. Make rows cheap and stable**

```tsx
const Row = memo(function Row({ item, onOpen }: RowProps) {
  return (
    <Pressable onPress={() => onOpen(item.id)} style={styles.row}>
      <Image source={item.thumbUrl} style={styles.thumb} recyclingKey={item.id} />
      <Text numberOfLines={1}>{item.title}</Text>
    </Pressable>
  );
});

const renderItem = useCallback(
  ({ item }: { item: Product }) => <Row item={item} onOpen={openProduct} />,
  [openProduct],
);
```

- `memo` on the row, with stable props: no new objects, arrays or inline functions created per render (#35). The React Compiler does much of this for you.
- Don't keep state high up that changes on scroll or on every keystroke and re-renders the whole list.
- Keep the row's view tree shallow. Avoid heavy work in render (date formatting libraries, big style calculations).
- Use stable ids as keys, never the index (#32).

**3. Fix images**

Images are the usual cause on Android. Load thumbnails at the displayed size, not the originals, and use a caching component (`expo-image`) (#672).

**4. Tune `FlatList`**

| Prop | Effect |
|---|---|
| `getItemLayout` | for fixed-height rows: skips measuring, makes `scrollToIndex` instant |
| `initialNumToRender` | rows in the first render; just enough to fill the screen |
| `maxToRenderPerBatch` | rows rendered per batch; lower means more responsive, more blank areas |
| `windowSize` | how many screens of rows stay mounted (default 21); lower saves memory |
| `removeClippedSubviews` | detaches off-screen native views; can help on Android |

These are trade-offs between blank areas, memory and responsiveness, so change one and measure.

**5. Consider FlashList**

`FlatList` **virtualises**: rows outside the window are unmounted, and new rows are created from nothing, which costs JS time and memory allocations. FlashList (Shopify) **recycles**: a row that scrolls out is reused for the next item, with new props. Fewer views are created, so scrolling is smoother on slow devices.

```tsx
<FlashList
  data={products}
  renderItem={renderItem}
  keyExtractor={(p) => p.id}
  getItemType={(p) => (p.isAd ? 'ad' : 'product')}   // separate recycling pools
/>
```

- FlashList v2 is built for the New Architecture and no longer needs size estimates.
- **Recycling pitfall:** the component instance is reused, so `useState` inside a row keeps the previous item's value. Derive state from props, key it by item id, or use the library's recycling-aware state hook.
- Legend List is a newer alternative with a similar goal.

**6. If it's still slow**

- Paginate and don't hold thousands of heavy objects in one render path.
- Move animation work to the UI thread (#678).
- Check for JS work happening during scroll: `onScroll` handlers calling `setState`, analytics, logging.
