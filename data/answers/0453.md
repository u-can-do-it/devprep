## Hints

- If the same user appears in ten posts and you rename them, how many places must you update?
- What's the cost of finding one item in an array of 5,000 versus looking it up in an object by id?
- Why does updating a deeply nested object cause more components to re-render?

## Answer

**Normalizing** means storing client data like a small database: each entity type in its own table, **keyed by id**, and other records referencing it by **id** instead of embedding a copy.

```ts
// Nested (as the API returns it)
posts: [
  { id: 'p1', author: { id: 'u1', name: 'Ana' }, comments: [{ id: 'c1', author: { id: 'u1', name: 'Ana' } }] },
]

// Normalized
users:    { ids: ['u1'],  entities: { u1: { id: 'u1', name: 'Ana' } } }
posts:    { ids: ['p1'],  entities: { p1: { id: 'p1', authorId: 'u1', commentIds: ['c1'] } } }
comments: { ids: ['c1'],  entities: { c1: { id: 'c1', authorId: 'u1' } } }
```

**Why nested state causes bugs:**

- **Duplicates drift apart:** rename Ana in one place and the copy inside a comment still shows the old name.
- **Updates are awkward:** changing one comment means copying the post, its comments array and the comment, which is easy to get wrong without Immer.
- **Extra re-renders:** a new reference for a deep object changes every ancestor, so every component selecting the parent re-renders.
- **Lookups are O(n):** `posts.find(p => p.id === id)` versus `entities[id]`.

**Redux Toolkit's `createEntityAdapter`** gives you this shape and the CRUD reducers:

```ts
const usersAdapter = createEntityAdapter<User>();   // { ids: [], entities: {} }

const usersSlice = createSlice({
  name: 'users',
  initialState: usersAdapter.getInitialState({ status: 'idle' }),
  reducers: {
    userAdded: usersAdapter.addOne,
    usersReceived: usersAdapter.upsertMany,
    userUpdated: usersAdapter.updateOne,   // payload: { id, changes }
  },
});

export const { selectById: selectUserById, selectAll: selectAllUsers } =
  usersAdapter.getSelectors((s: RootState) => s.users);
```

It also supports a `sortComparer` that keeps `ids` sorted. A list component renders `ids` and each row selects its own entity by id, so editing one row re-renders only that row.

**When not to bother:** small, read-only data you replace wholesale, or server data held by a cache library. Apollo Client normalizes automatically, while RTK Query and TanStack Query cache per request and invalidate instead.

**Follow-up:** the API returns nested posts. Where do you normalize them: in the API layer, in the reducer, or with a schema library like `normalizr`?
