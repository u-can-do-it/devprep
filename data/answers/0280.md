## Hints

- What sits between your page and the network, and keeps working after the tab is closed?
- If you deploy a new service worker, why don't users get it right away?
- Should HTML, hashed JS bundles and API responses all be cached the same way?

## Answer

A **Service Worker** is a script that runs in its own thread, separate from the page. It acts as a **programmable network proxy** for its origin and **scope**. It can intercept requests, serve them from the Cache API, and handle push notifications and background sync. It has no DOM access, requires **HTTPS** (localhost is allowed), and is event-driven: the browser stops it when idle.

**Lifecycle:**

1. **Register:** `navigator.serviceWorker.register('/sw.js')`. Its scope defaults to the script's directory.
2. **Install:** usually precache the app shell. `event.waitUntil(...)` keeps it alive until done.
3. **Waiting:** if an old worker still controls open tabs, the new one **waits** until all those tabs close. This prevents two versions running at once.
4. **Activate:** clean up old caches. Use `clients.claim()` to control open pages straight away.
5. **Fetch / push / sync events** from then on.

`self.skipWaiting()` skips the waiting step. Do it carefully, because the old page may now load assets from the new version. A common UX is a "New version available, reload?" prompt.

```js
self.addEventListener('fetch', (event) => {
  if (event.request.mode === 'navigate') {
    // network-first for HTML, falling back to the cached shell when offline
    event.respondWith(fetch(event.request).catch(() => caches.match('/offline.html')));
  }
});
```

**Caching strategies:**

| Strategy | Use for |
|---|---|
| **Cache-first** | Hashed, immutable assets (JS, CSS, fonts) |
| **Network-first** | HTML and frequently changing API data, so it's fresh when online and still works offline |
| **Stale-while-revalidate** | Avatars, non-critical API data. Instant response, refreshed in the background |
| **Network-only / cache-only** | Payments and auth / precached shell |

Use **Workbox** (or your framework's plugin) rather than writing routing and cache versioning by hand.

**PWA basics:** a web app manifest (name, icons, `display: standalone`), HTTPS and a service worker with offline support make the app installable.

**Pitfalls:**

- Caching HTML cache-first can leave users stuck on an old version for good.
- Version your caches and delete the old ones on activate.
- Never cache authenticated responses in a shared way.

**Follow-up:** HTTP caching (`Cache-Control`) already covers many needs. Add a service worker when you need **offline** support, push or fine-grained control.
