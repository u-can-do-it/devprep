## Hints

- Why is an in-memory store with single-threaded command execution so fast and free of race conditions per command?
- Which structure would you pick for a leaderboard sorted by score?
- What happens to the data if the Redis server restarts?

## Answer

**Redis** is an in-memory data structure server. Commands execute one at a time (I/O is multi-threaded in recent versions), so each command is **atomic** and typically sub-millisecond. It's used as a cache, but its data types make it much more. **Valkey** is the Linux Foundation fork created after Redis's 2024 license change and is API-compatible.

| Type | Use case |
|------|----------|
| **String** | cache entries, counters (`INCR`), distributed locks (`SET key val NX EX 10`) |
| **Hash** | objects / sessions with fields (`HSET user:42 name Ana`) |
| **List** | simple queues, recent items (`LPUSH` + `LTRIM`) |
| **Set** | unique members, tags, "who liked this" (`SADD`, `SINTER`) |
| **Sorted set** | leaderboards, priority queues, sliding-window rate limiting (`ZADD`, `ZRANGE ... REV`) |
| **Stream** | append-only log with consumer groups – lightweight event streaming |
| **Bitmap / HyperLogLog** | daily active flags, approximate unique counts with tiny memory |
| **Geo** | "find stores within 5 km" |
| **JSON, vector sets, search** | document storage and similarity search (built into Redis 8) |

```bash
ZADD leaderboard 1500 "ana" 1320 "bo"
ZINCRBY leaderboard 50 "bo"
ZRANGE leaderboard 0 9 REV WITHSCORES   # top 10
```

Also: **pub/sub**, **TTL** on any key, `MULTI`/`EXEC` transactions and Lua/functions for atomic multi-step logic.

**Durability:** data lives in RAM. Persistence is optional – RDB snapshots and/or the AOF log – and replication is asynchronous, so a failover can lose recent writes. Treat Redis as a cache or for data you can rebuild, unless you've configured and accepted its durability limits.
