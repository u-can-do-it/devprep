## Hints

- What does the browser need to build before it can paint the first pixel?
- Why is CSS considered render-blocking, and why can a script block parsing?
- How could you get the first screen to show before every stylesheet and script has loaded?

## Answer

The **critical rendering path** is the sequence of steps the browser takes to turn HTML, CSS and JS into pixels:

1. **Parse HTML → DOM.** The parser builds the tree incrementally as bytes arrive.
2. **Parse CSS → CSSOM.**
3. **Run JavaScript** that the parser encounters.
4. **Render tree** — combine DOM + CSSOM, keeping only visible nodes (no `display: none`, no `<head>`).
5. **Layout** — compute the size and position of every box.
6. **Paint** — fill in pixels (text, colors, borders, images) into layers.
7. **Composite** — the GPU combines layers into the final frame.

**What blocks the first render:**

- **CSS is render-blocking:** the browser won't paint without the CSSOM, to avoid a flash of unstyled content.
- **Classic `<script>` is parser-blocking**, and it also waits for preceding CSS (the script might read styles).
- **Web fonts** can hide text until loaded (FOIT).
- A slow server response (TTFB) delays everything.

**Optimizing it:**

```html
<link rel="preconnect" href="https://cdn.example.com">
<link rel="preload" href="/hero.avif" as="image" fetchpriority="high">
<style>/* small inlined critical CSS for above-the-fold */</style>
<link rel="stylesheet" href="/print.css" media="print">
<script src="/app.js" defer></script>
```

- Minimize, compress and split CSS; inline critical CSS; use `media` attributes on non-critical stylesheets.
- `defer`/`async`/`type="module"` for scripts.
- `font-display: swap` and preloading key fonts.
- Reduce request count and bytes on the critical path; use HTTP/2+, a CDN, and server rendering or streaming for fast first HTML.

**Follow-up:** these steps map directly onto metrics — TTFB, First Contentful Paint and LCP — which you can inspect in the Chrome DevTools Performance panel.
