## Hints

- Which methods should never change server state?
- If a client retries the same request three times because of a timeout, what should the end state be?
- Why is `POST` the odd one out?

## Answer

- **Safe** methods don't modify server state (read-only semantics): `GET`, `HEAD`, `OPTIONS`, `TRACE`.
- **Idempotent** methods produce the same server state whether called once or many times: all safe methods plus `PUT` and `DELETE`.
- **Neither**: `POST` (creating an order twice creates two orders) and `PATCH` (not guaranteed – e.g. `{"op": "increment"}`).

| Method | Safe | Idempotent |
|--------|------|------------|
| GET    | yes  | yes        |
| PUT    | no   | yes        |
| DELETE | no   | yes        |
| POST   | no   | no         |
| PATCH  | no   | not guaranteed |

**Why it matters:**

- **Retries** – clients, proxies and load balancers can safely retry idempotent requests after a network failure.
- **Caching & prefetching** – browsers and CDNs cache and prefetch `GET`s assuming they're harmless. A `GET /delete-user?id=1` link is a bug waiting to happen (crawlers will click it).
- **Correct API design** – idempotency refers to state, not the response: a second `DELETE` may return `404` instead of `204`, and that's fine.

To make `POST` safe to retry (e.g. payments), use an **idempotency key**:

```http
POST /payments HTTP/1.1
Idempotency-Key: 7f3c9a2e-...
```

The server stores the key and returns the original result on duplicates.
