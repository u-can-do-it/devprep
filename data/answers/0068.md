## Hints

- Why shouldn't a database password be hard-coded or committed to git?
- What is a good way to fail fast if a required variable is missing or malformed?
- Where do secrets come from in production versus on a developer laptop?

## Answer

Follow the **12-factor** principle: configuration that varies between environments lives in **environment variables**, not code.

- Read values from `process.env`. Node 20.6+ can load a file natively with `node --env-file=.env app.js`, so `dotenv` is often unnecessary.
- Commit a `.env.example` with keys but no real values; add `.env` to `.gitignore`.
- **Validate config at startup** and fail fast with a clear message. Everything in `process.env` is a string, so parse and coerce.

```ts
import { z } from 'zod';

const Env = z.object({
  NODE_ENV: z.enum(['development', 'test', 'production']),
  PORT: z.coerce.number().default(3000),
  DATABASE_URL: z.string().url(),
});
export const config = Env.parse(process.env); // throws on startup if invalid
```

- Centralize config in one module; don't sprinkle `process.env.X` throughout the code.

**Secrets** in production should come from a secret manager (AWS Secrets Manager, GCP Secret Manager, Vault, Kubernetes Secrets) injected at deploy/runtime, never baked into Docker images or logged. Rotate them, scope them with least privilege, and use separate credentials per environment.

Pitfalls: logging the full config object, exposing server env vars to frontend bundles, and relying on `NODE_ENV` for anything other than dev/prod behavior toggles.
