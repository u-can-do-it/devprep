## Hints

- What does each of the three numbers in `2.4.1` promise to users of a library?
- How could a tool decide the next version number just by reading commit messages?
- Where do the changelog and the Git tag come from in an automated release?

## Answer

**Semantic Versioning (SemVer)**: `MAJOR.MINOR.PATCH`
- **MAJOR** for breaking changes,
- **MINOR** for new backward-compatible features,
- **PATCH** for backward-compatible bug fixes.
- Pre-releases look like `3.0.0-beta.2`. Ranges like `^2.4.1` rely on these promises.

**Conventional Commits** is a commit-message convention that machines can parse:

```text
feat(auth): add passkey login            -> minor
fix(api): handle empty cart on checkout  -> patch
feat!: drop support for Node 20          -> major
  (or a footer: "BREAKING CHANGE: ...")
chore, docs, refactor, test, ci, ...     -> no release by default
```

**Automating releases:** tools like **semantic-release**, **release-please** or **Changesets** (popular in monorepos, using change files instead of commit parsing) run in CI on `main` and:
1. analyze commits since the last tag,
2. compute the next version,
3. generate a **changelog**,
4. create a Git **tag** (`v2.5.0`) and a GitHub release,
5. publish the package or image.

```bash
git tag -a v2.5.0 -m "Release 2.5.0"   # annotated tag: author, date, message
git push origin v2.5.0
```

Enforce the format with commitlint in a commit hook or CI, or apply it only to squash-merge PR titles.

**For apps** (not libraries), SemVer matters less. Many teams version deploy artifacts by **commit SHA** or date, and still use conventional commits for changelogs.

**Pitfall:** marking breaking changes as `fix:`. Automation is only as honest as the commit messages.
