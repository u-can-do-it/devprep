## Hints

- Once a secret is pushed, does deleting it in a new commit make it safe?
- What's the very first thing you should do with the leaked credential itself?
- Why doesn't adding a file to `.gitignore` stop Git from tracking it?

## Answer

**1. Treat the secret as compromised and rotate it immediately.** Revoke the API key, change the DB password, issue new tokens. If it was pushed, bots scanning public repos can find it within minutes. Rewriting history doesn't help with clones, forks or caches that already have it. Then check provider logs for misuse.

**2. Stop tracking the file and ignore it:**

```bash
echo ".env" >> .gitignore
git rm --cached .env          # untrack, but keep the local file
git commit -m "chore: stop tracking .env"
```

`.gitignore` only affects **untracked** files. A file that's already committed stays tracked until you `git rm --cached` it.

**3. Clean history if needed:**
- **Not pushed yet:** amend the commit or use an interactive rebase to drop the file.
- **Pushed:** rewrite history with `git filter-repo --path .env --invert-paths` (or BFG), force-push with `--force-with-lease`, and have teammates re-clone. On GitHub, cached views and PR refs may need support to purge. That's why rotation comes first.

**Prevention:**
- Commit a `.env.example` with placeholder values. Keep real values in a secret manager or a local `.env`.
- Pre-commit secret scanning (gitleaks, detect-secrets) and **GitHub secret scanning with push protection**, which blocks pushes containing known token formats.
- Short-lived credentials (OIDC, SSO) so leaks are less damaging.

**Red flag in an interview:** "I'd just delete it in the next commit." The secret is still in history.
