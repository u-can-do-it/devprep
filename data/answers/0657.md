## Hints

- At which steps between a ticket and a merged PR do you use AI, and with which tool at each step?
- Where in that flow do you check the work, and how?
- Which tasks do you keep for yourself, and why?

## Answer

> Describe a real flow, step by step, not a list of tools. A solid one: let the agent explore the code and explain it, agree a plan before any code, implement in small verified steps, review the diff yourself, get a second review from a fresh context, then open the PR. Name the tool you use for each kind of task and what you keep for yourself: decisions, anything you can't verify and data you may not share. End with how you know it helps.

"How do you work with AI?" is now a standard question. The weak answer is "I use Copilot and ChatGPT". The strong one walks through one feature and shows **where you think and where the tool types**.

**From ticket to merged PR**

1. **Understand.** Ask the agent to find the relevant code and explain the current behaviour, read-only. You read the key files yourself; a summary is a map, not the territory (#559).
2. **Plan.** For anything beyond a small fix, ask for a plan (plan mode) and correct it: right layer, existing helpers reused, edge cases listed. This is the cheapest place to catch a wrong approach (#545).
3. **Specify the checks.** Write or dictate the test cases from the requirements before the implementation, so "done" is something the agent can verify (#660).
4. **Implement in small steps.** One step, run the tests, commit. Small commits make it cheap to throw a bad step away.
5. **Review the diff yourself,** every line, as if a colleague had written it: edge cases, error handling, security, fit with the codebase (#476).
6. **Second opinion.** A review by an agent with fresh context (it hasn't seen the reasoning, so it doesn't share the blind spots). Useful, and not a replacement for step 5.
7. **PR.** A draft description from the diff, which you edit so it says why. Then the normal pipeline: CI and human review.

**Which tool for which task**

| Task | Tool | Why |
|---|---|---|
| Finishing a line or a small function | inline completion | you stay in flow and see every character |
| "How does this work?", comparing options | chat | no changes to the code, quick back and forth |
| A change across several files with tests | agent in the editor or terminal | it can run commands and iterate |
| A well-specified chore (bump a dependency, add tests) | background or cloud agent | you review a PR instead of watching (#659) |
| Repeated procedures | skills, hooks, MCP tools | the setup carries the knowledge (#656) |

**What you keep for yourself**

- **Decisions:** architecture, data model, trade-offs. Use AI to list options and attack your idea, then decide and own it.
- **Anything you can't verify.** If you can't tell whether the output is right, you can't ship it.
- **Security-critical and money logic** without a line-by-line read.
- **Data you may not share:** secrets, customer data, client code outside approved tools (#664).
- **Learning something for the first time:** ask for an explanation and write it yourself (#663).

**How you know it helps:** lead time for a change, how often agent output merges without rework, review comments per PR, defects that escape. Not lines of code or number of prompts. Be honest about where it doesn't help: vague problems, unfamiliar domains with no tests, large legacy modules without a feedback loop.

**Example answer** (replace with your own)

> "Last sprint I added bulk export to an admin table. I first asked the agent to trace how the single export works and read those three files myself. Then I asked for a plan; it wanted a new endpoint, and I pointed it to the existing job queue instead. I wrote the test cases, including an empty selection and 50,000 rows, let it implement the job and the UI in three commits, and ran each. That took about a day and a half instead of the three I'd have estimated. What I didn't delegate was the decision to reuse the queue and the permission model."
