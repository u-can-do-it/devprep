## Hints

- How would you avoid repeating the same list of user fields in five different queries?
- How do you select fields that exist only on one member of a union or interface?
- Which component should decide which fields it needs?

## Answer

A **fragment** is a reusable selection of fields on a specific type.

**Named fragments** remove duplication and let each UI component declare its own data needs (**colocation**):

```graphql
fragment UserAvatar on User {
  id
  name
  avatarUrl(size: 64)
}

query PostPage($id: ID!) {
  post(id: $id) {
    title
    author { ...UserAvatar }
    comments(first: 10) {
      nodes { body author { ...UserAvatar } }
    }
  }
}
```

**Inline fragments** (`... on Type`) select type-specific fields on **interfaces and unions**:

```graphql
query Search($q: String!) {
  search(query: $q) {
    __typename
    ... on Product { name price }
    ... on Article { title publishedAt }
  }
}
```

They're also used with directives on a group of fields: `... @include(if: $withStats) { views likes }`.

**Why they matter in real apps:**

- With colocation, an `<Avatar>` component exports its fragment and the page query spreads it, so adding a field means editing one file, and the page fetches everything in **one request**.
- **Fragment masking** (Relay, GraphQL Code Generator's client preset) means a component can only read the fields declared in its own fragment – preventing hidden coupling between components.
- Fragments are purely a client-side query-composition feature; the server merges them into a single selection set.

Pitfall: requesting `__typename` and `id` is important for normalized caches to identify objects; most clients add `__typename` automatically.
