## Hints

- What runs on your machine or CI the moment you `npm install` a package?
- How do you make sure CI installs exactly the same versions you reviewed?
- How can you tell whether a published package was really built from its claimed source repo?

## Answer

> Your app runs hundreds of third-party packages with full access, so one compromised package can steal secrets or ship malware. Commit lockfiles and install from them exactly, and update through bot PRs with a short cooldown, because most malicious versions get caught within days. Disable install scripts by default and give CI only short-lived, minimal tokens. Prefer packages with provenance, run audit tools in CI, and keep an SBOM so you can quickly check whether you're affected. Question every new dependency.

Your app runs hundreds of transitive dependencies with full privileges. Recent incidents show the attack patterns: maintainer accounts phished and popular packages republished with malware, self-spreading worms that steal npm/GitHub tokens from CI, typosquatting, dependency confusion between private and public names, and malicious `postinstall` scripts.

**Pin and reproduce**

- Commit **lockfiles** (`package-lock.json`, `pnpm-lock.yaml`, `uv.lock`, `poetry.lock`) and install with `npm ci` / `pnpm install --frozen-lockfile` / `uv sync --locked`. Python can also enforce hashes (`pip install --require-hashes`).
- Update deliberately through **Dependabot or Renovate** PRs, with a **cooldown** so you don't pick up a version minutes after release (pnpm's `minimumReleaseAge`, Renovate's `minimumReleaseAge`). Most malicious versions are caught within hours or days.

**Limit what packages can do**

- Disable install scripts by default (`ignore-scripts=true` in `.npmrc`; pnpm 10 runs dependency lifecycle scripts only for packages you approve).
- Run CI with **least-privilege, short-lived tokens** (OIDC instead of long-lived secrets) so a compromised build can't steal much.

**Verify origin and integrity**

- Prefer packages published with **provenance/attestations** via trusted publishing (npm provenance, PyPI attestations), and check them with `npm audit signatures`.
- Use scoped/private registries correctly to prevent dependency confusion.
- For third-party scripts loaded from a CDN, use **Subresource Integrity**:

```html
<script src="https://cdn.example.com/lib@3.2.1/lib.min.js"
        integrity="sha384-..." crossorigin="anonymous"></script>
```

**Monitor**

- `npm audit` / `pip-audit` / OSV-Scanner in CI, plus a dependency-review step on PRs, and generate an **SBOM** (CycloneDX/SPDX) so you can answer "are we affected?" quickly.
- Keep the dependency tree small: question every new package.

**Follow-up:** You learn a dependency was compromised yesterday. What do you do? Check lockfiles and SBOMs for the affected versions, rotate any secrets the build could reach, and pin to a known-good version.
