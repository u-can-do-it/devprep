## Hints

- How does your build know which browsers it has to support?
- What's the difference between transpiling syntax and polyfilling an API?
- Which browser engine does every browser on an iPhone use?

## Answer

**1. Decide which browsers you support.** Write it down with product, based on your analytics, and put it in a **Browserslist** config (`package.json` → `"browserslist"`, or `.browserslistrc`), for example `> 0.5%, last 2 versions, not dead`, or a **Baseline** target such as "Baseline widely available": features supported by all major engines for at least 30 months. Babel, SWC, Autoprefixer, Lightning CSS and Vite (default target `baseline-widely-available` since Vite 7) all read it.

**2. Let the toolchain do the mechanical work**

- **Syntax** (optional chaining, class fields) is **transpiled** down to the target.
- **APIs** (`Array.prototype.findLast`, `structuredClone`) need **polyfills**, which a transpiler can't add by itself. Use `core-js` with usage-based injection (`useBuiltIns: 'usage'`), and only for the APIs your targets lack.
- **CSS** prefixes and fallbacks come from Autoprefixer or Lightning CSS.
- **Lint for compatibility:** `eslint-plugin-compat` and Stylelint's `no-unsupported-browser-features` flag APIs your targets don't support. MDN and caniuse show Baseline status.

**3. Write resilient code**

- **Feature detection**, not user-agent sniffing: `if ('IntersectionObserver' in window)`, `CSS.supports('container-type: inline-size')`, `@supports (display: grid) { … }`.
- **Progressive enhancement:** the core task works with basic features, and newer ones (View Transitions, `:has()`, anchor positioning) improve it where available.
- Prefer standard platform behaviour over custom hacks: real `<button>`, `<input type="date">` with a fallback, `dvh` units instead of fixed `100vh` on mobile.

**4. Test on real engines**

- Run end-to-end tests on all three engines: Playwright projects for **Chromium, Firefox and WebKit**.
- Use real devices or cloud labs (BrowserStack, Sauce Labs) for iOS Safari and Android, especially for touch, the on-screen keyboard and `position: fixed`.
- Remember that on iOS **every browser uses WebKit** (outside the EU's alternative-engine option), so "works in Chrome on iPhone" means "works in Safari".
- Visual regression tests per browser catch layout differences.

**Common trouble spots:** Safari date and input styling, `100vh` with dynamic toolbars, `gap` and sticky positioning in older versions, scrollbar width differences, fonts rendering at different widths, `Intl` and `Date` parsing of non-ISO strings, and autoplay or audio policies.

**Follow-up:** a feature you want is supported in 92% of your users' browsers. How do you decide whether to use it, polyfill it, or skip it?
