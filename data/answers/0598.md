## Hints

- What happens when 500 requests miss the cache for the same key at the same moment, and does `IMemoryCache.GetOrCreateAsync` stop it?
- What does a second app instance see in an `IMemoryCache` on the first instance, and what do you have to do with objects before putting them into `IDistributedCache`?
- Who decides whether a response is served from cache with response caching, and who decides with output caching?

## Answer

ASP.NET Core has caching at two levels: **data caching** (you cache objects in your code) and **HTTP caching** (the framework caches whole responses).

**1. Data caching**

| | `IMemoryCache` | `IDistributedCache` | `HybridCache` (package, since .NET 9) |
|---|---|---|---|
| Where | process memory | Redis, SQL Server, etc. | L1 memory **plus** optional L2 distributed |
| Values | any object, no serialization | `byte[]`, you serialize | any object, serialization handled |
| Shared between instances | no | yes | L2 yes, L1 per instance |
| Stampede protection | no | no | yes, one factory call per key |
| Tag invalidation | no | no | yes (`RemoveByTagAsync`) |

```csharp
builder.Services.AddStackExchangeRedisCache(o => o.Configuration = redisConn); // becomes the L2
builder.Services.AddHybridCache(o => o.DefaultEntryOptions = new HybridCacheEntryOptions
{
    Expiration = TimeSpan.FromMinutes(10),          // L2 lifetime
    LocalCacheExpiration = TimeSpan.FromMinutes(1), // shorter L1, limits staleness across instances
});

app.MapGet("/doctors/{id:int}", async (int id, HybridCache cache, AppDbContext db, CancellationToken ct) =>
    await cache.GetOrCreateAsync(
        $"doctor:{id}",
        async token => await db.Doctors.AsNoTracking()
            .Where(d => d.Id == id).Select(d => new DoctorDto(d.Id, d.Name)).FirstOrDefaultAsync(token),
        tags: ["doctors"],
        cancellationToken: ct));

// after an update
await cache.RemoveAsync($"doctor:{id}");
// or: await cache.RemoveByTagAsync("doctors");
```

**2. Cache stampede**

When a hot key expires, every concurrent request misses and runs the expensive query at once. `IMemoryCache.GetOrCreateAsync` doesn't lock, so the factory can run many times. `HybridCache` makes concurrent callers for the same key **wait for one factory call** in that process. Across instances you can add jittered expirations, early refresh, or a distributed lock for very expensive values.

**3. `IMemoryCache` pitfalls**

- Unbounded by default. If you set `SizeLimit`, every entry **must** set `Size`, or adding it throws.
- Cached objects are shared references: mutating one changes it for every request. Cache immutable DTOs or records.
- Per instance: after a write, other instances keep serving the old value until it expires.
- Never use user input as an unbounded key space without limits (memory exhaustion).

**4. HTTP caching: output vs response caching**

| | Response caching (`UseResponseCaching`) | Output caching (`UseOutputCache`, .NET 7+) |
|---|---|---|
| Driven by | HTTP headers (`Cache-Control`, `Vary`) | server-side policies you configure |
| Client can bypass | yes, `Cache-Control: no-cache` skips it | no, the server decides |
| Invalidation | only expiry | by tag (`EvictByTagAsync`) |
| Storage | memory | memory, or Redis for multiple instances |
| Stampede | no | yes, concurrent requests for the same entry wait (resource locking) |

```csharp
builder.Services.AddOutputCache(o => o.AddPolicy("Catalog", p => p.Expire(TimeSpan.FromMinutes(5)).Tag("catalog")));
app.UseOutputCache();
app.MapGet("/catalog", GetCatalog).CacheOutput("Catalog");
// after a catalog change: await outputCacheStore.EvictByTagAsync("catalog", ct);
```

Output caching skips authenticated requests and responses that set cookies by default, so you don't leak one user's page to another. Response caching is mostly about setting correct headers for browsers and CDNs; for caching in your own server, prefer output caching.

**5. What to decide for any cache**

- Key design (include tenant, culture, version), TTL and how stale a value may be.
- Invalidation on write, or short TTLs where invalidation is hard.
- What happens when Redis is down: `HybridCache` and most setups should fall back to the database rather than fail the request.

**Follow-up:** you scaled from one to four instances and users now see old prices for up to ten minutes after an update. Why? (Each instance has its own `IMemoryCache`, and you only invalidated on the instance that handled the write. Use a distributed L2 with a short L1 expiry, or broadcast invalidations, e.g. via Redis pub/sub.)
