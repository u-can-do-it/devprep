## Hints

- If the same key is in `appsettings.json` and in an environment variable, which one wins, and why is that order useful in containers?
- How do you write a nested key like `Database:ConnectionString` as an environment variable?
- Which options interface sees a changed value without restarting the app, and which one can't be injected into a singleton?

## Answer

**Configuration sources and precedence**

`WebApplication.CreateBuilder` loads these providers in order; **later sources override earlier ones**:

1. `appsettings.json`
2. `appsettings.{Environment}.json` (environment from `ASPNETCORE_ENVIRONMENT` or `DOTNET_ENVIRONMENT`: `Development`, `Staging`, `Production`)
3. User secrets (only in `Development`)
4. Environment variables
5. Command-line arguments

So the JSON files hold defaults and the deployment overrides them, which is exactly what you want in Docker and Kubernetes (one image, config from the environment). Nested keys use `:` in code and `__` in environment variables: `Database__ConnectionString=...`.

**Secrets**

- Never commit them to `appsettings.json`.
- Locally: `dotnet user-secrets set "Stripe:ApiKey" "sk_test_..."`, stored outside the repo in your user profile (not encrypted, just not in Git).
- In production: environment variables from the orchestrator's secret store, or a provider like Azure Key Vault (`AddAzureKeyVault`).

**The options pattern**

Bind a section to a class instead of reading strings with `IConfiguration["..."]` everywhere:

```csharp
public sealed class SmtpOptions
{
    public const string Section = "Smtp";
    [Required] public string Host { get; init; } = "";
    [Range(1, 65535)] public int Port { get; init; } = 587;
}

builder.Services.AddOptions<SmtpOptions>()
    .BindConfiguration(SmtpOptions.Section)
    .ValidateDataAnnotations()
    .ValidateOnStart();          // fail at startup, not on the first email

public sealed class EmailSender(IOptions<SmtpOptions> options)
{
    private readonly SmtpOptions _smtp = options.Value;
}
```

**`IOptions` vs `IOptionsSnapshot` vs `IOptionsMonitor`**

| Interface | Lifetime | Sees changes after startup | Use in |
|---|---|---|---|
| `IOptions<T>` | singleton | no, read once | most code |
| `IOptionsSnapshot<T>` | scoped | yes, recomputed per request | request-scoped services; can't be injected into singletons |
| `IOptionsMonitor<T>` | singleton | yes, `CurrentValue` plus `OnChange` callback | singletons and background services that need live values |

Live reload only happens if the source supports it (JSON files with `reloadOnChange: true`, which is the default; some remote providers). Environment variables don't change while the process runs.

**Named options** let you bind the same type twice (`Configure<HttpOptions>("github", ...)`, read with `IOptionsMonitor<T>.Get("github")`).

**Follow-up:** your app works locally but in Kubernetes the connection string is empty. How do you debug it? (Check the environment variable name uses `__`, that `ASPNETCORE_ENVIRONMENT` loads the file you expect, and that the section name matches; print `((IConfigurationRoot)config).GetDebugView()` in a non-production environment to see which provider supplied each key.)
