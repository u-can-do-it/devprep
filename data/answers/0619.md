## Hints

- Which NestJS building block would you use to check a JWT, to turn a string id into a number, and to wrap every response in `{ data }`?
- In which order do middleware, guards, interceptors and pipes run for a request?
- What is a provider's default scope, and what does `Scope.REQUEST` cost you?
- Can NestJS run on Fastify instead of Express?

## Answer

NestJS is an opinionated Node.js framework in the style of Angular and ASP.NET Core: **modules**, **dependency injection** and **decorators** on classes. It sits on top of Express by default or Fastify (`@nestjs/platform-fastify`), so it's a structure layer, not a different HTTP engine.

**Building blocks:**

| piece | what it is | example |
|---|---|---|
| **Module** (`@Module`) | groups controllers and providers, declares `imports`/`exports` | `OffersModule`, `PrismaModule` |
| **Controller** | routes, maps HTTP to service calls | `@Get(':id') findOne(@Param('id') id: string)` |
| **Provider / service** (`@Injectable`) | business logic, injected by constructor | `OffersService`, `PrismaService` |
| **Middleware** | Express-style `(req, res, next)`, before routing | request logging, raw body |
| **Guard** (`CanActivate`) | yes/no: may this request proceed? | `JwtAuthGuard`, `RolesGuard` |
| **Interceptor** | wraps the handler (RxJS) before and after | timing, response mapping, caching, transactions |
| **Pipe** | transforms and validates arguments | `ParseUUIDPipe`, `ValidationPipe`, a Zod pipe |
| **Exception filter** | turns thrown errors into responses | map `Prisma.NotFoundError` to 404 |

**Order:** middleware → guards → interceptors (before) → pipes → handler → interceptors (after) → exception filters (if something threw).

```ts
@Controller('offers')
@UseGuards(JwtAuthGuard, RolesGuard)
export class OffersController {
  constructor(private readonly offers: OffersService) {}

  @Post(':id/approve')
  @Roles('manager')
  approve(@Param('id', ParseUUIDPipe) id: string, @CurrentUser() user: User) {
    return this.offers.approve(id, user);
  }
}

@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private reflector: Reflector) {}
  canActivate(ctx: ExecutionContext) {
    const roles = this.reflector.getAllAndOverride<string[]>('roles', [ctx.getHandler(), ctx.getClass()]);
    if (!roles) return true;
    const { user } = ctx.switchToHttp().getRequest();
    return roles.some((r) => user.roles.includes(r));
  }
}
```

**Dependency injection:** providers are **singletons** by default (one instance per app), the same as a singleton in ASP.NET Core (#581). `Scope.REQUEST` creates a new instance per request and *bubbles up*: everything that injects it becomes request-scoped too, which costs performance. For per-request data prefer `AsyncLocalStorage` (`nestjs-cls`, #302). Circular dependencies between modules need `forwardRef` and are usually a design smell.

**Validation:** the classic stack is `class-validator` + `class-transformer` DTOs with a global `ValidationPipe({ whitelist: true, forbidNonWhitelisted: true, transform: true })`. `whitelist` strips unknown properties, which stops mass assignment (#372). Zod-based alternatives (`nestjs-zod`) let you share schemas with the frontend.

**Testing:** `Test.createTestingModule({ providers: [...] }).overrideProvider(PrismaService).useValue(mock)` for unit tests; boot the app and use `supertest` for e2e (#628).

**Nest vs Fastify/Express alone:**

- **Nest:** large teams, many modules, people from Java/.NET or Angular, built-in patterns for queues, microservices, GraphQL, Swagger. Cost: boilerplate, decorators and reflection metadata, more "magic" to learn, slower startup.
- **Plain Fastify (or with tRPC):** small team, explicit code, less ceremony; you choose your own structure (#467) and DI is just function arguments or a small container.

For a two-person team on an internal system, either works; what matters is a consistent structure. Saying that in an interview shows judgement.

**Follow-up:** where would you put "wrap the approve operation in a database transaction and write an audit entry": a guard, an interceptor or the service? (The service: it's business logic. An interceptor can measure or log around it, but the transaction must cover the business writes, and a guard runs before anything is loaded.)
