## Hints

- What happens to a fire-and-forget `Task.Run` from a controller when the pod is stopped or the job throws?
- A `BackgroundService` is a singleton. How do you use a scoped `DbContext` inside it?
- What do you lose if the process crashes with 10,000 items in an in-memory queue, and what do you do about it when the work must happen?

## Answer

**Pick by how durable the work must be**

| Option | Survives a crash or deploy | Good for |
|---|---|---|
| `Task.Run` fire-and-forget from a request | no; exceptions get lost, no shutdown handling | avoid it |
| `BackgroundService` (+ `Channel<T>`) | no, the queue is in memory | periodic refreshes, best-effort side work |
| Hangfire / Quartz.NET | yes, jobs persisted in a database, retries, dashboard; Quartz adds cron schedules and clustering | scheduled and recurring jobs, jobs that must survive restarts |
| Message broker (RabbitMQ, Azure Service Bus, SQS, Kafka) + a worker service | yes, at-least-once delivery | cross-service work, high volume, scaling workers separately |

**`IHostedService` and `BackgroundService`**

`IHostedService` has `StartAsync` and `StopAsync`. `BackgroundService` implements it and gives you one long-running `ExecuteAsync(stoppingToken)`. Hosted services are singletons registered with `AddHostedService`. Before .NET 10, synchronous work before the first `await` in `ExecuteAsync` blocked the startup of the whole host; .NET 10 starts it on a background thread, but keeping it asynchronous from the start is still the safe habit. Since .NET 6, an unhandled exception in `ExecuteAsync` **stops the host** by default, so catch per item.

**An in-process queue with `Channel<T>`**

```csharp
public sealed class EmailQueue
{
    private readonly Channel<EmailJob> _channel = Channel.CreateBounded<EmailJob>(
        new BoundedChannelOptions(1_000) { FullMode = BoundedChannelFullMode.Wait });   // back-pressure

    public ValueTask EnqueueAsync(EmailJob job, CancellationToken ct) => _channel.Writer.WriteAsync(job, ct);
    public IAsyncEnumerable<EmailJob> ReadAllAsync(CancellationToken ct) => _channel.Reader.ReadAllAsync(ct);
}

public sealed class EmailWorker(EmailQueue queue, IServiceScopeFactory scopes, ILogger<EmailWorker> log)
    : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await foreach (var job in queue.ReadAllAsync(stoppingToken))
        {
            try
            {
                await using var scope = scopes.CreateAsyncScope();      // a fresh scope (and DbContext) per job
                var sender = scope.ServiceProvider.GetRequiredService<IEmailSender>();
                await sender.SendAsync(job, stoppingToken);
            }
            catch (Exception ex) when (ex is not OperationCanceledException)
            {
                log.LogError(ex, "Email job {JobId} failed", job.Id);   // one bad job must not stop the loop
            }
        }
    }
}

builder.Services.AddSingleton<EmailQueue>();
builder.Services.AddHostedService<EmailWorker>();
```

Injecting a scoped service straight into the worker's constructor is a captive dependency (#581): one `DbContext` for the app's whole lifetime. Create a scope per unit of work instead. Channels are covered in more depth in #600.

**Periodic work**

```csharp
using var timer = new PeriodicTimer(TimeSpan.FromMinutes(5));
while (await timer.WaitForNextTickAsync(stoppingToken))
    await RefreshPricesAsync(stoppingToken);       // runs never overlap, unlike System.Threading.Timer
```

**Graceful shutdown**

On `SIGTERM` (Kubernetes) the host cancels `stoppingToken`, calls `StopAsync` on hosted services and waits up to `HostOptions.ShutdownTimeout` (30 seconds by default). Pass the token to every call, finish or hand back the in-flight item, and keep the timeout below the pod's `terminationGracePeriodSeconds`. Whatever is still in an in-memory channel at that point is gone.

**When the work must happen**

If an email must go out after an order is saved, an in-memory queue isn't enough. Write an **outbox** row in the same database transaction as the order (#596), and let a worker (or a broker) process it with retries and idempotency. The work then survives crashes and deploys.

**Several instances**

Every replica runs its own copy of each `BackgroundService`. That's fine for consuming a shared queue, but a "nightly cleanup" job then runs N times. Use a distributed lock (for example a PostgreSQL advisory lock), Quartz in clustered mode, Hangfire, or a Kubernetes `CronJob`.

**Follow-up:** the cleanup job runs three times every night after scaling to three replicas. How do you fix it? (Make only one instance run it: a distributed lock or leader election, a clustered scheduler like Quartz or Hangfire, or move it out of the web app into a `CronJob` or a single-replica worker. Also make the job idempotent so an accidental second run is harmless.)
