## Hints

- If the agent writes tests by reading the implementation, what do those tests prove?
- Tests fail after a change. What is the cheapest way for an agent to make them pass?
- How can you tell whether a test would catch a bug, without waiting for one?

## Answer

> Tests generated from the implementation only confirm what the code already does, including its bugs. Start from behaviour instead: you list the cases from the requirements, the agent writes the tests first, you check that they fail for the right reason, and then it implements without touching them. Review tests more carefully than code, because they are the specification the agent works against. Check their strength by breaking the code on purpose or with mutation testing.

AI makes tests cheap to write, so the risk moves from "too few tests" to **many tests that verify nothing**.

**How AI-written tests go wrong**

| Problem | Example |
|---|---|
| Mirrors the implementation | the test repeats the formula from the code, so both are wrong together |
| Cements a bug | generated from buggy code, it asserts the buggy output as expected |
| Over-mocking | everything around the unit is mocked, and the assertions check the mocks |
| Weak assertions | `toBeDefined()`, `not.toThrow()`, or a snapshot of a whole component |
| Happy path only | no empty input, no error from the API, no concurrency, no time zones |
| Coverage without verification | lines are executed, nothing meaningful is asserted |
| Tests bent to pass | assertions loosened, `.skip` added, snapshots updated, expected values edited |

```ts
// Mirrors the implementation: this passes even if the rule itself is wrong
expect(priceWithVat(100)).toBe(100 * 1.23);

// States the behaviour from the requirement, with boundaries
expect(priceWithVat(100)).toBe(123);
expect(priceWithVat(0)).toBe(0);
expect(priceWithVat(0.1 + 0.2)).toBe(0.37);   // rounding to cents
expect(() => priceWithVat(-1)).toThrow();
```

**A workflow that works (TDD with an agent)**

1. **You own the cases.** List behaviours and edge cases from the ticket. Ask the agent to add cases you missed; it is good at that.
2. **Tests first, no implementation.** Tell the agent not to write production code yet.
3. **See them fail for the right reason:** an assertion failure, not an import error.
4. **Commit the tests.** The specification is now fixed and any later change to it shows in the diff.
5. **Implement until green, without editing the tests.** If the agent thinks a test is wrong, it has to say so and stop.
6. **Refactor** with the tests as a safety net.

TDD suits agents well because it gives them an objective target and a feedback loop they can run themselves. What changes compared with classic TDD: the cycles are bigger (a group of cases at once), and your attention moves from writing code to reviewing tests.

**Checking that tests have teeth**

- **Break the code on purpose:** flip a condition, remove a check, and see whether a test fails. Ask the agent to do it and report which changes survived.
- **Mutation testing** (Stryker, mutmut) on critical modules does this systematically (#395).
- **Property-based tests** for logic with many inputs: state the invariant and let the tool search for counterexamples.
- Read each test name as a sentence. If it doesn't describe a behaviour a user or caller cares about, question it.

**Guardrails**

- In review, treat changes to test files in the same PR as the implementation as a signal. Was the test wrong, or was it weakened?
- CI or a hook that flags new `.skip`, `.only`, deleted assertions and updated snapshots (#654).
- Keep a few high-value end-to-end or contract tests that the agent may not edit (#543).

**Where AI helps most with tests**

- **Characterisation tests** for legacy code before a refactor: capture current behaviour, then change the structure safely.
- Edge-case brainstorming, test data and fixtures, table-driven cases.
- Turning a bug report into a failing reproduction, then fixing it.
- Migrating tests between frameworks.

**Follow-up:** the agent reports "all 40 tests pass", and you see one test file in the diff. What do you check? (What changed in it and why, whether the tests actually ran, and whether a deliberate bug makes any of them fail.)
