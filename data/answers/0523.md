## Hints

- Which flag stops `document.cookie` from reading the cookie, and which attack does that blunt?
- What's the difference between a cookie with no `Domain` attribute and one with `Domain=example.com`?
- Why would you want a cookie that *cannot* be set by a subdomain?

## Answer

A reasonable session cookie:

```http
Set-Cookie: __Host-session=5f1c9…; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=1800
```

| Attribute | Meaning | Defends against |
|---|---|---|
| `HttpOnly` | Not readable from JavaScript (`document.cookie`, Cookie Store API) | Session **theft** via XSS. Injected script can still call the API as the user while the page is open, but can't exfiltrate the cookie |
| `Secure` | Sent only over HTTPS (`localhost` is exempt) | Sniffing and downgrade attacks on plain HTTP |
| `SameSite=Strict` / `Lax` / `None` | Whether cross-site requests carry the cookie (#109) | CSRF. `Lax` is the modern default; `None` requires `Secure` and is for genuine cross-site embedding |
| `Domain` | Omitted = **host-only** (exactly `app.example.com`). `Domain=example.com` = sent to all subdomains | A broad `Domain` means one compromised subdomain can read or plant session cookies |
| `Path` | URL path prefix the cookie is sent to | Not a security boundary (pages on the same origin can still read it); only scoping |
| `Expires` / `Max-Age` | Persistent cookie with a lifetime. Without them it's a *session cookie* removed when the browser closes (though browsers often restore sessions) | Limits how long a stolen cookie is useful. The server must enforce expiry too (#378) |
| `__Host-` prefix | Browser accepts it only if `Secure`, `Path=/` and **no `Domain`** | Subdomains and HTTP pages can't set or override it (session fixation, "cookie tossing") |
| `__Secure-` prefix | Requires `Secure` | A weaker version of the above |

Also worth knowing:

- About 4 KB per cookie and a few dozen per domain; every request to that domain carries them, so keep them small and serve static assets from a cookieless domain or CDN.
- `Partitioned` (CHIPS) cookies for third-party embeds now that third-party cookies are restricted.
- The **browser** enforces these flags, not the server. Set them in one place (framework session config, Helmet, the reverse proxy) and check them in DevTools → Application → Cookies.
- Cookies vs `localStorage` for tokens: #56, #115.

**Follow-up:** can an XSS payload still harm the user if the session cookie is `HttpOnly`? (Yes: it can call the API from the page while the user is there. `HttpOnly` limits theft, not misuse, so CSP (#111) and output encoding are still needed.)
