## Hints

- Where does the state live, and what is the only way to change it?
- What must a reducer never do, and why does that make time-travel debugging possible?
- Which boilerplate did people complain about in classic Redux, and which RTK function removes each piece?

## Answer

**Redux** keeps app state in a single **store** and changes it through a strict one-way loop:

1. The UI **dispatches an action**: a plain object describing what happened, e.g. `{ type: 'cart/itemAdded', payload: { id: 7 } }`.
2. The store calls the **reducer** with `(currentState, action)`. A reducer is a **pure function** that returns the next state. It never mutates, never calls APIs, never uses `Date.now()` or random values.
3. The store saves the new state and notifies subscribers. Components read data through **selectors** (`useSelector`) and re-render when their slice changes.

Because every change is an action and reducers are pure, you get predictable updates, easy unit tests (`reducer(state, action)`), and Redux DevTools with action logs and time-travel.

**Middleware** sits between `dispatch` and the reducer. It's where side effects live (thunks, logging, analytics, RTK Query).

**Redux Toolkit (RTK)** is the official way to write Redux today. Hand-written action types, action creators, `switch` reducers and spread-heavy immutable updates are gone:

```ts
import { createSlice, configureStore, type PayloadAction } from '@reduxjs/toolkit';

const cartSlice = createSlice({
  name: 'cart',
  initialState: { items: [] as { id: number; qty: number }[] },
  reducers: {
    itemAdded(state, action: PayloadAction<{ id: number }>) {
      const item = state.items.find((i) => i.id === action.payload.id);
      if (item) item.qty++;            // "mutation" is safe: Immer makes an immutable copy
      else state.items.push({ id: action.payload.id, qty: 1 });
    },
  },
});

export const { itemAdded } = cartSlice.actions;   // action creators generated
export const store = configureStore({ reducer: { cart: cartSlice.reducer } });
export type RootState = ReturnType<typeof store.getState>;
export type AppDispatch = typeof store.dispatch;
```

What RTK gives you:

- **`createSlice`**: action types and creators generated from reducer names.
- **Immer**: write "mutating" code that produces immutable updates.
- **`configureStore`**: DevTools and thunk set up, plus dev-only checks that catch accidental mutations and non-serializable values.
- **`createAsyncThunk`, listener middleware and RTK Query** for async work and server data.
- Good TypeScript inference: you type the initial state and payloads, not every action.

**When Redux is worth it:** lots of shared client state that many components update, complex update logic, and a need for traceability (dev tools, middleware). For server data, RTK Query or TanStack Query fits better. For small apps, `useState`, Context or Zustand are often enough.
