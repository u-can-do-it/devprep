## Hints

- What happens if `id` changes from 1 to 2 and the response for 1 arrives last?
- Does `fetch` reject on a 404 or 500?
- What type does `r.json()` return, and does `(u: User)` check anything?
- What does the user see while loading, and if the request fails?

## Answer

It works on the happy path, which is why it looks fine in a quick review. Problems, most severe first:

1. **Race condition.** If `id` changes quickly, two requests are in flight. Whichever resolves *last* wins, so the screen can show user 1 while the URL says user 2. The effect has no cleanup to cancel or ignore the stale request.
2. **HTTP errors are treated as success.** `fetch` only rejects on network failure. A 404 or 500 resolves normally, so the error body is parsed and stored as a `User`.
3. **The type annotation is an unchecked cast.** `r.json()` returns `Promise<any>`, so `(u: User)` accepts anything. TypeScript can't help here; the shape has to be checked at runtime (Zod, Valibot, or a type guard) if the data matters.
4. **No error handling.** A network failure or invalid JSON becomes an unhandled promise rejection, and the UI has no error or loading state.
5. **Minor:** `id` isn't encoded in the URL (`encodeURIComponent`), and there's no loading state, so the previous user stays on screen while the next one loads.

**Fixed version:**

```tsx
async function fetchUser(id: string, signal: AbortSignal): Promise<User> {
  const res = await fetch(`/api/users/${encodeURIComponent(id)}`, { signal });
  if (!res.ok) throw new Error(`Failed to load user: HTTP ${res.status}`);
  return UserSchema.parse(await res.json()); // runtime validation
}

useEffect(() => {
  const controller = new AbortController();
  setState({ status: 'loading' });
  fetchUser(id, controller.signal)
    .then((user) => setState({ status: 'success', user }))
    .catch((error: unknown) => {
      if (controller.signal.aborted) return; // stale request, ignore
      setState({ status: 'error', error });
    });
  return () => controller.abort();
}, [id]);
```

`state` is a discriminated union (`{ status: 'loading' } | { status: 'success'; user: User } | { status: 'error'; error: unknown }`), so the component can't read `user` without checking `status` first.

**Better still:** in a real app, use TanStack Query, SWR or your framework's data loading. They handle cancellation, caching, deduplication and retries, and the React docs recommend them over hand-written fetching effects.

**How to write this up in a review:** start with the race condition (it ships wrong data silently), explain the exact sequence that triggers it, then give the fix. Mention the minor points last.
