## Hints

- If a test fails, how quickly can you tell what broke from its name and output alone?
- What happens to your tests when you refactor the internals without changing behavior?
- Can the test pass or fail depending on the order it runs in, or on the time of day?

## Answer

A good unit test is **fast, deterministic, readable, and tests behavior, not implementation**.

**Structure: Arrange, Act, Assert (or Given/When/Then)**

```ts
test('applies free shipping for orders over 100', () => {
  // Arrange
  const cart = makeCart({ items: [{ price: 120, qty: 1 }] });
  // Act
  const total = checkout(cart);
  // Assert
  expect(total.shipping).toBe(0);
});
```

**Qualities interviewers look for:**

- **One behavior per test**, with a name that describes it ("rejects expired coupons", not "test2"). A failure should tell you what's broken without reading the code.
- **Tests the public behavior**: inputs and outputs, not private methods or the order of internal calls. Refactoring shouldn't break tests unless behavior changes.
- **Isolated and independent**: no shared mutable state, works in any order and in parallel. Each test sets up its own data.
- **Deterministic**: no real time, randomness, network, or file system dependencies. Inject a clock or seed, and use fakes at boundaries.
- **Fast**: milliseconds, so people run them constantly.
- **Readable over DRY**: some duplication is fine if it makes each test self-explanatory. Use small factory helpers (`makeCart`) for noisy setup.
- **Meaningful assertions**: assert the specific outcome; avoid asserting everything (brittle) or nothing.
- **Mock only at boundaries** (HTTP, DB, clock). Heavy mocking of your own modules couples tests to implementation.
- **Covers edge cases**: empty input, boundaries (99, 100, 101), invalid input, error paths.

The FIRST acronym sums it up: Fast, Isolated, Repeatable, Self-validating, Timely.

**Follow-up:** How do you know a test is good? Break the code on purpose; the test should fail with a clear message.
