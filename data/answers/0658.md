## Hints

- What happens to the quality of answers as the context window fills up, long before it is full?
- After the context is compacted, which instructions survive and which can be lost?
- If you had to close the session now, what would a new session need in order to continue?

## Answer

> An agent's context window is finite, and quality drops as it fills with old tool output and abandoned attempts. Keep one task per session, clear the context between unrelated tasks, compact at natural breakpoints, and send context-heavy work such as searching to subagents so only a summary comes back. Keep the state of the work in files and commits, not in the conversation, so a fresh session can pick it up. After two failed corrections, start again with a better brief.

**Why it matters:** everything the agent has read, run and said stays in the context window: file contents, command output, failed attempts. Long before the window is full, the model pays less attention to early instructions and starts repeating mistakes ("context rot"). When it does fill up, the harness **compacts**: it replaces the history with a summary, and details are lost. Managing that is your job (#483 covers the same idea for LLM features).

Commands are Claude Code's; other agents have equivalents.

**Habits**

- **One task per session.** Finished the bug, starting a feature: `/clear`. Old context is not neutral; it steers the model toward the previous problem.
- **Compact on your terms.** Run `/compact` at a natural breakpoint (a step is done and committed) and say what to keep: "keep the API contract and the list of files still to migrate". Auto-compaction in the middle of a step picks worse moments.
- **Look at what fills the context** (`/context`): large files read whole, long test output, MCP tool definitions. Disable servers you don't use in this project.
- **Delegate reading to subagents.** "Find every place that calls the pricing service" may read fifty files. In a subagent that happens in a separate context and you get back a list (#653).
- **Don't paste big logs.** Save them to a file and let the agent search them.
- **Use plan mode for exploration:** the agent reads and proposes without changing anything, and you correct the plan while it is cheap (#545).
- **Rewind instead of arguing.** If a step went wrong, go back to the checkpoint before it (`/rewind`) and re-prompt with what you learned. Corrections stacked on a bad attempt leave the bad attempt in context.
- **After two failed corrections, restart.** A fresh session with a better brief beats a long session full of wrong turns.

**What survives**

- **Survives compaction and restarts:** files. `CLAUDE.md` is read again from disk, and the code, commits, a plan file and test results are still there.
- **Can be lost:** anything said only in the conversation: "use the new client, not the old one", a decision made twenty turns ago, the reason an approach was rejected.

So **durable state goes in files**: a short `PLAN.md` or task list with done and to-do, decisions with reasons, and small commits. Conventions that should hold in every session go in `CLAUDE.md` (#541).

**Continuing later:** `claude --continue` or `/resume` reopens a session with its history. For a clean handover (to tomorrow, a colleague or a parallel agent), ask the agent to write a note:

```md
## Goal
Migrate the orders module from Moment to date-fns without changing API output.
## Done
- utils/date.ts, OrderList, OrderFilters (tests green, commit a1b2c3)
## Decisions
- Keep ISO strings in the API; format only in the UI. Time zone stays Europe/Warsaw.
## Next
- OrderExport (uses `moment.tz`, needs date-fns-tz), then remove the dependency
## Verify
pnpm test orders && pnpm tsc --noEmit
```

A new session started from that note often performs better than the old one continued, because the note has the conclusions without the noise.

**Signs you waited too long:** the agent re-reads files it has already read, forgets a constraint from the start, proposes a fix it already tried, or contradicts an earlier decision.

**Follow-up:** you are migrating 200 files and the context can't hold the work. How do you organise it? (A list of files in a tracking file, a fixed procedure in a skill, batches run by subagents or parallel sessions that each read the procedure and report back, a commit per batch, and CI as the check: #659.)
