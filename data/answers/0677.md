## Hints

- What does a browser engine do with JavaScript source at startup that costs time on a phone?
- When is the JS bundle compiled with Hermes: on the device or at build time?
- Why can't a third-party engine on iOS rely on a JIT compiler?

## Answer

> Hermes is a JavaScript engine built by Meta for React Native. It compiles your bundle to bytecode at build time, so the phone doesn't parse or compile JavaScript at startup. That gives a faster start, lower memory use and a smaller download. It has no JIT, so long CPU-heavy JavaScript is slower than in V8. It has been the default engine since 0.70, and Hermes V1, a newer generation of it, is the default from 0.84.

**Why startup is faster**

| | V8 / JavaScriptCore (typical) | Hermes |
|---|---|---|
| Ships in the app | JS source (minified) | bytecode |
| At startup | parse, compile, then run | memory-map the bytecode and run |
| Hot code | JIT-compiled to machine code | interpreted |
| Memory | higher (JIT, compiled code caches) | lower |

On a phone, parsing a multi-megabyte bundle is a large part of time-to-interactive. Hermes moves that work to the build machine. The bytecode file is memory-mapped, so pages are loaded as they are needed, and code that never runs costs little.

**Why no JIT**

- iOS doesn't let third-party apps create executable memory, so a JIT isn't available there anyway.
- A JIT costs memory and warm-up time. Most app code is short UI logic that runs a few times, where an interpreter with precompiled bytecode wins.

The price: tight loops and heavy computation (parsing big files, image processing, cryptography) are slower than in a JIT engine. Move such work to native code or C++ (#700).

**Other properties**

- **Garbage collector:** generational and mostly concurrent on 64-bit devices, so pauses are short.
- **Built for React Native:** integrates through JSI (#693), and supports the Chrome DevTools Protocol, which React Native DevTools uses for breakpoints and profiling (#671).
- **Sampling profiler** and heap snapshots for performance and memory work.
- **Hermes V1:** a new compiler and VM with better performance and broader support for modern JavaScript.

**Differences you may notice**

- Language support follows its own schedule. Babel still transforms some syntax for it, and the `Intl` implementation relies on platform libraries, so details can differ from a browser.
- `Function.prototype.toString()` doesn't return source code, which breaks the rare library that depends on it.
- Stack traces in production point into bytecode. You need source maps that combine the Metro and Hermes maps to read them (#687).
- A bytecode bundle is tied to a Hermes bytecode version, which is one reason an over-the-air update must match the app's native runtime (#699).

**Other engines**

JavaScriptCore support moved out of the core into a community package, and V8 is available through community packages. Almost all apps use Hermes; you would switch only for a specific compatibility or performance reason.

**How to check:** `global.HermesInternal != null` is true when the app runs on Hermes.

**Follow-up:** an app must parse a 30 MB JSON file on the device and freezes for seconds. What are the options? (Don't do it on the JS thread: stream and parse natively, store data in SQLite and query it, paginate on the server, or run the work in a background runtime; see #694.)
