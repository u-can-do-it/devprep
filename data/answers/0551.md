## Hints

- The `ALTER TABLE` itself is quick, but it waits for a lock. What happens to every query that arrives after it?
- What's the difference between `ALGORITHM=INSTANT`, `INPLACE` and `COPY`, and why would you write the algorithm explicitly?
- How do gh-ost and pt-online-schema-change change a table without blocking writes, and what do they still need at the end?

## Answer

Two separate things can take production down: the **metadata lock queue** and **operations that copy the table**.

**1. Metadata locks (MDL): the classic outage**

Every query takes a shared metadata lock on the tables it touches and holds it **until its transaction ends**. DDL needs an exclusive metadata lock, at least briefly at the start and end. If one long transaction (a slow report, or a session that ran a `SELECT` and never committed) holds the shared lock, the `ALTER` waits, and **every new query on that table queues behind the `ALTER`**. The app sees "Waiting for table metadata lock", connection pools fill up and the service goes down, even for a change that would take milliseconds. PostgreSQL has the same lock-queue problem (#340).

```sql
SET SESSION lock_wait_timeout = 5;   -- the default is one year: fail fast and retry later instead
```

Before running DDL, look for long transactions (`information_schema.innodb_trx`, `performance_schema.metadata_locks`, the process list) and run migrations through a tool that sets a short timeout and retries.

**2. Online DDL algorithms**

| Algorithm | What happens | Typical operations (MySQL 8.0+) |
|---|---|---|
| `INSTANT` | only metadata changes | add a column, drop a column (8.0.29+), rename a column, set or drop a default, add values to the end of an `ENUM` |
| `INPLACE` | works inside InnoDB, concurrent reads and writes allowed (`LOCK=NONE`), may rebuild the table | add or drop a secondary index, make a column `NOT NULL` (rebuild), extend a `VARCHAR` while the length prefix stays 1 byte |
| `COPY` | builds a new copy of the table and **blocks writes** for the whole time | change a column's data type, convert the character set, add a foreign key with `foreign_key_checks` on |

**Write the algorithm explicitly.** If MySQL can't do it that way, it fails immediately instead of silently falling back to a blocking copy:

```sql
ALTER TABLE appointments
  ADD COLUMN cancellation_reason VARCHAR(255) NULL,
  ALGORITHM=INSTANT;

ALTER TABLE appointments
  ADD INDEX idx_doctor_starts (doctor_id, starts_at),
  ALGORITHM=INPLACE, LOCK=NONE;
```

Even "online" `INPLACE` changes have costs on a big table: hours of I/O, a log of concurrent changes that can overflow (`innodb_online_alter_log_max_size`), and **replica lag**, because replicas apply the `ALTER` only after it finishes on the primary. A table also allows only a limited number of instant column changes (64 row versions) before it needs a rebuild. Extending `VARCHAR(60)` to `VARCHAR(100)` in `utf8mb4` crosses 255 bytes, needs a 2-byte length prefix and therefore a table copy.

**3. Online schema change tools for big tables**

- **gh-ost** (GitHub): creates a ghost table with the new schema, copies rows in small chunks, and applies ongoing changes by **reading the binlog** (no triggers). It throttles on replica lag or load, can be paused, and lets you postpone the final cut-over.
- **pt-online-schema-change** (Percona): the same idea, but uses **triggers** on the original table to mirror writes, which adds write overhead and complicates foreign keys.
- Both need free disk space for a full copy and a short exclusive lock at **cut-over** (rename), so the MDL rule still applies.

```bash
gh-ost --host=replica-1 --database=app --table=appointments \
  --alter="MODIFY status VARCHAR(32) NOT NULL" \
  --chunk-size=1000 --max-lag-millis=1500 \
  --postpone-cut-over-flag-file=/tmp/ghost.postpone --execute
```

**4. Process**

- Expand/contract so old and new code both work during the deploy (#340).
- Backfill in batches by primary key range with short transactions and pauses, watching replica lag. Never one huge `UPDATE`: it holds locks, bloats the undo log and stalls replicas.
- MySQL DDL isn't transactional (each statement commits implicitly), so put one DDL per migration and make migrations safe to re-run.
- Test on a production-sized copy and check the table size first (`information_schema.tables`).

**Follow-up:** an `ALTER TABLE` that took 2 seconds on staging froze production for 10 minutes. What happened? (It waited for a metadata lock held by a long transaction, and all queries queued behind it. Use `lock_wait_timeout`, find and end long transactions, and retry outside peak hours.)
