## Hints

- What happens automatically every time someone pushes to the main branch?
- Is a human still involved before code reaches production?
- How often does each practice expect developers to integrate their work?

## Answer

These are three stages of automation, each building on the previous one.

- **Continuous Integration (CI):** developers merge small changes into a shared branch frequently (at least daily). Every push triggers an automated build plus tests and linters, so integration problems surface within minutes rather than at the end of a sprint.
- **Continuous Delivery:** every change that passes CI produces a release-ready artifact (e.g. a Docker image) and is automatically deployed to staging. Releasing to production is a **manual business decision** — one click, but a human presses it.
- **Continuous Deployment:** removes that last manual gate. Every change that passes the pipeline goes to production automatically.

```yaml
# simplified GitHub Actions flow
on: push
jobs:
  test:   # CI
    runs-on: ubuntu-latest
    steps: [ { uses: actions/checkout@v4 }, { run: npm ci && npm test } ]
  deploy: # Continuous deployment if this runs on every main push
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps: [ { run: ./deploy.sh production } ]
```

Continuous deployment only works with strong test coverage, monitoring, fast rollback, and usually feature flags to hide unfinished work.

**Follow-up:** "Why might a regulated company (banking, medical) stop at continuous delivery?" — audit, approvals, and release windows.
