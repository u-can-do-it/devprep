## Hints

- Why is a cursor more robust than a page number when new items are inserted at the top?
- Where would you put data that belongs to the relationship rather than to the node itself?
- How does the client know whether to show a "Load more" button?

## Answer

> Offset pagination slows down on deep pages and can skip or repeat rows when data changes. GraphQL's Relay-style connections use cursors instead. A list returns `edges`, each with a `node` and an opaque `cursor`, plus `pageInfo` with `hasNextPage` and `endCursor`. The client asks for `first: 20, after: <endCursor>` to get the next page. The server turns the cursor into a keyset `WHERE` condition, so pages stay stable and deep pages are as fast as the first. Cap `first` at a maximum.

The **Connection** pattern (from the Relay cursor connections spec, used far beyond Relay) standardizes pagination so clients and tooling can handle any list the same way.

```graphql
type Query {
  products(first: Int, after: String, last: Int, before: String,
           filter: ProductFilter): ProductConnection!
}

type ProductConnection {
  edges: [ProductEdge!]!
  pageInfo: PageInfo!
  totalCount: Int          # optional; can be expensive
}

type ProductEdge {
  cursor: String!
  node: Product!
  # edge-level data, e.g. addedAt for a "wishlist" relation
}

type PageInfo {
  hasNextPage: Boolean!
  hasPreviousPage: Boolean!
  startCursor: String
  endCursor: String
}
```

```graphql
query { products(first: 20, after: "Y3Vyc29yOjQw") {
  edges { node { id name } }
  pageInfo { hasNextPage endCursor }
} }
```

**How it works:**

- `first`/`after` page forward, `last`/`before` page backward.
- A **cursor** is an opaque string (often base64 of the sort key + id). The server decodes it into a keyset condition: `WHERE (created_at, id) < ($1, $2) ORDER BY created_at DESC, id DESC LIMIT 21` – fetch one extra row to compute `hasNextPage`.
- Results stay stable when rows are inserted, and deep pages are as fast as the first.

**Practical points:**

- Enforce a maximum `first` (e.g. 100) – it's also part of query-cost limits.
- Many schemas add a `nodes` shortcut field alongside `edges` for simpler clients.
- Client caches (Apollo `relayStylePagination`, Relay `@connection`, urql) merge pages for infinite scroll.
- `totalCount` can need a full `COUNT(*)`; make it optional or approximate.
- Offset pagination is still fine for small admin tables that need page numbers.
