## Hints

- How does code learn at runtime which platform it runs on?
- What does the bundler do with `Button.ios.tsx` and `Button.android.tsx` when you import `./Button`?
- Which hardware or system control exists on Android but not on iOS?

## Answer

> Most code is shared. For small differences, branch on `Platform.OS` or use `Platform.select`. For bigger ones, create two files with `.ios.tsx` and `.android.tsx` extensions, and the bundler picks the right one. Keep the branches small and at the edges, and test on both platforms, because behaviour differs in more places than the code shows.

**Small differences: the `Platform` module**

```tsx
import { Platform, StyleSheet } from 'react-native';

const styles = StyleSheet.create({
  header: {
    paddingTop: Platform.OS === 'ios' ? 12 : 8,
    ...Platform.select({
      ios: { fontFamily: 'Avenir' },
      android: { fontFamily: 'Roboto' },
      default: {},                        // web and others
    }),
  },
});

if (Platform.OS === 'android' && Platform.Version >= 33) {
  // Android 13+: Platform.Version is the API level (a number). On iOS it is a string like "18.2".
}
```

**Bigger differences: platform files**

```
DatePicker.ios.tsx
DatePicker.android.tsx
DatePicker.tsx          // optional fallback
```

`import { DatePicker } from './DatePicker'` resolves to the right file per platform. `.native.tsx` covers both mobile platforms and `.web.tsx` covers the web, which is how code is shared with React Native for Web (#702). Both files must export the same API, and TypeScript checks only the one it resolves, so keep a shared type.

**Differences you meet most often**

| Area | iOS | Android |
|---|---|---|
| Back | swipe from the left edge, a back button in the header | system back button or gesture; handle with `BackHandler` or the navigator |
| Press feedback | opacity change | ripple (`android_ripple`) |
| Shadows | `shadow*` props | `elevation`; `boxShadow` now works on both |
| System bars | status bar, home indicator | status bar and navigation bar, drawn edge-to-edge (#679) |
| Keyboard | covers the content; you must move it | resize behaviour differs, so test each form (#679) |
| Permissions | one system prompt, then Settings | can ask again once, then blocked (#685) |
| Fonts | San Francisco | Roboto; custom font weights need separate files |
| Text | tighter line boxes | extra font padding (`includeFontPadding`) |
| Pickers and alerts | wheels and action sheets | dialogs and bottom sheets |
| Push | APNs, explicit permission | FCM, channels (#683) |

Devices differ too. Android has a huge range of screen sizes, OS versions and slow phones, so a list that is smooth on a new iPhone can stutter on a mid-range Android (#673).

**Good practice**

- Follow each platform's conventions instead of forcing one design on both. Navigation libraries already do this for headers, transitions and tab bars.
- Hide the difference behind a component or hook (`useHaptics`, `<DatePicker>`), so screens don't fill up with `Platform.OS` checks.
- Test on both platforms, on a real device and in a release build, before you call a feature done.
- Don't check the platform when you mean a capability. Ask "is this API available?" where you can.

**Follow-up:** on Android the hardware back button closes the app while a custom modal is open. How do you fix it? (Subscribe with `BackHandler.addEventListener('hardwareBackPress', ...)` while the modal is open and return `true` after closing it, or use `Modal`'s `onRequestClose`.)
