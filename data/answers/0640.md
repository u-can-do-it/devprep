## Hints

- Which files tell you the truth about how the app runs in production, even when the README is wrong?
- How do you find the code behind one button in a large app you've never seen?
- Which git commands tell you *why* a strange piece of code exists?
- How do you change behaviour safely when you don't know what the current behaviour is?
- How do you mark what you've verified versus what you only assume?

## Answer

Software archaeology means reconstructing how a system works from the code, its history and its runtime behaviour, because the documentation is missing or wrong. A good answer is a **method** plus a short story from your own experience (#559 covers the first week in a new codebase in general).

**1. Start from questions, not from reading everything.** "How does login work?", "Where does the order list come from?", "What happens when a payment fails?" Each question gets a trace and a note.

**2. Get it running, and read what production actually runs.**

- Deployment config is the most honest documentation: Helm charts, Kubernetes manifests, Dockerfiles, CI pipelines and environment variables show which services exist, which URLs they use and which feature flags are on.
- `package.json` dates the code and its conventions: Next.js version, Pages or App Router, `next-auth` v4 or v5, TanStack Query v4 or v5, MUI version.
- Entry points: `next.config.*` (rewrites, redirects, `basePath`), `middleware.ts`/`proxy.ts`, `_app.tsx` or `app/layout.tsx` (providers), `pages/api/auth/[...nextauth].ts` or `auth.ts`.

**3. Trace one user journey end to end.**

- Browser DevTools, Network tab: which endpoints, which services, which headers and tokens.
- React DevTools (component tree) and TanStack Query Devtools (query keys) take you from the screen to the code.
- Grep for the URL or UI text, then follow the path: component → hook → API client → BFF route → backend service → its OpenAPI spec.
- Add temporary logging or set breakpoints; look at traces (OpenTelemetry, Jaeger) if they exist.

**4. Use history to recover the *why*.**

```bash
git log --follow -p -- src/features/billing/Invoice.tsx   # how the file evolved
git blame -w -C -C src/lib/api.ts                          # who and when, ignoring moves and whitespace
git log -S 'legacyCustomerId' --oneline                    # commits that added or removed a string
git log --grep 'SELF-1234'                                 # commits for one ticket
git log --format= --name-only | sort | uniq -c | sort -rn | head -20   # hotspots: most-changed files
```

Commit messages lead to tickets, tickets lead to the business reason. Files that change often *and* are complex are where bugs and knowledge concentrate, so start there.

**5. Use tools for the big picture.** IDE "find all references" and call hierarchy; dependency graphs with `madge` or `dependency-cruiser`; `knip` for unused files and exports; TypeScript errors with `strict` turned on locally to see where the types lie. Coding agents are good at "summarize this module" or "find every place that calls X", but **verify** their claims against the code.

**6. Ask people.** Ops knows how it's deployed, testers know the edge cases, support tickets show the real behaviour, the product owner knows the rules. One short call can save a day of reading.

**7. Build a safety net before changing anything.** **Characterization tests** (Michael Feathers, *Working Effectively with Legacy Code*) record what the system does today, even if it looks wrong, so a refactor can't change it by accident: Playwright tests on key flows, or component tests with MSW-mocked APIs (#461).

**Documenting what you learn**

- **Next to the code**, in the repo (`docs/`, README, Markdown with Mermaid), reviewed in pull requests like code. A wiki goes stale faster.
- **What's worth writing:**
  - How to run, configure and deploy it (the env vars and their meaning).
  - An architecture overview: a C4 context and container diagram showing which services the frontend talks to.
  - Sequence diagrams for critical flows, especially authentication (#632).
  - A glossary of domain terms.
  - Decision records (ADRs), including reconstructed ones ("we believe X was chosen because Y; source: ticket SELF-1234").
  - A list of known unknowns and risks.
- **Mark confidence:** *verified* (traced or tested) vs *assumed*. A wrong document is worse than none.
- **Keep it small and alive:** update the docs in the same PR as the change. In a project paid per deliverable, these documents are often part of what gets formally accepted.

**Follow-up:** "Tell me about a time you did this." Use STAR: the system, the question you had to answer, the techniques you used (tracing, git history, asking people), and what you produced (a diagram, a runbook, a fixed bug) that others still use.
