## Hints

- How long do branches live in each model?
- How does each model handle releases and hotfixes?
- What practices do you need in place before everyone can commit to main daily?

## Answer

**Git Flow** uses long-lived branches: `main` (released code), `develop` (integration), plus `feature/*`, `release/*`, and `hotfix/*` branches. It suits software with scheduled, versioned releases (mobile apps, libraries, on-prem products) or multiple supported versions. Downsides: long-lived branches drift, causing painful merges, and slow feedback.

**Trunk-based development:** everyone integrates into `main` (the trunk) at least daily, via very short-lived branches (hours to a day or two) and small PRs. `main` is always releasable. It relies on:

- strong automated tests and fast CI,
- feature flags to hide unfinished work,
- code review that keeps pace with small PRs.

Releases are cut from trunk (tags or short release branches if needed).

**For a team shipping daily**, trunk-based is the better fit: fewer merge conflicts, continuous integration in the true sense, and it enables continuous delivery. Research such as the DORA reports links trunk-based development with higher delivery performance.

GitHub Flow sits in between: `main` plus short-lived feature branches merged via PR — effectively trunk-based for most web teams.

**Follow-up:** "How do you ship a half-built feature with trunk-based development?" — behind a feature flag, or with branch-by-abstraction.
