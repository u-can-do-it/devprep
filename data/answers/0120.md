## Hints

- If your server fetches a URL the user provides, what internal addresses could it reach that the user can't?
- What lives at `169.254.169.254` in most cloud environments?
- Why is validating the hostname string before fetching not enough?

## Answer

**Server-Side Request Forgery (SSRF)** happens when an attacker makes your server send requests to destinations of their choosing – via features like "import from URL", webhooks, link previews, PDF/image renderers, or URL-based file processing. The server sits inside your network, so it can reach things the attacker can't:

- **Cloud metadata endpoints** (`http://169.254.169.254/...`) that hand out **temporary IAM credentials** – the classic path from SSRF to full cloud compromise.
- Internal admin panels, databases, Redis, Kubernetes APIs, other microservices without auth.

**Defenses (layered):**

1. **Avoid arbitrary URLs** where possible – use allowlists of domains, or have users upload files instead.
2. **Validate the resolved IP, not the string.** Resolve DNS, reject private, loopback, link-local, and metadata ranges (IPv4 and IPv6, including mapped forms), then **connect to that exact IP** to defeat **DNS rebinding**.
3. **Disable or re-validate redirects** – an allowed URL can redirect to `http://127.0.0.1`.
4. Allow only `http`/`https`; block `file://`, `gopher://`, etc.
5. **Network egress controls** – run fetchers in an isolated service/subnet with an egress proxy that only allows the public internet. This is the strongest control because it doesn't depend on app code.
6. **Harden metadata access** – enforce IMDSv2 on AWS (session token required, hop limit 1), or block metadata from workloads that don't need it.

```python
import ipaddress, socket

def is_public(host: str) -> bool:
    for info in socket.getaddrinfo(host, None):
        ip = ipaddress.ip_address(info[4][0])
        if not ip.is_global:
            return False
    return True
# then connect to the vetted IP, with redirects disabled
```

**Secrets management (limit the blast radius):**

- Never hard-code secrets or commit `.env` files; scan repos and CI (gitleaks, push protection).
- Store them in a **secrets manager** (AWS Secrets Manager, GCP Secret Manager, Vault) and inject at runtime.
- Prefer **short-lived, workload identity credentials** (IAM roles, OIDC federation for CI) over long-lived keys.
- **Least privilege** per service, rotation, and audit logging of secret access.

**Follow-up:** How does an attacker exploit blind SSRF where they never see the response? (Timing, out-of-band callbacks, hitting internal endpoints with side effects.)
