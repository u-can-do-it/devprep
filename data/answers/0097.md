## Hints

- How many endpoints does a GraphQL API typically expose, and who decides the response shape?
- What are over-fetching and under-fetching?
- What becomes harder in GraphQL that HTTP gives you for free in REST?

## Answer

**REST** exposes many resource endpoints (`/users/1`, `/users/1/posts`); the server decides the shape of each response. **GraphQL** exposes a single endpoint with a strongly typed schema; the **client** asks for exactly the fields it needs.

```graphql
query {
  user(id: "1") {
    name
    posts(first: 5) { title }
  }
}
```

**GraphQL strengths:**

- No over-fetching (unused fields) or under-fetching (multiple round trips) – great for mobile and complex UIs.
- Strongly typed schema = self-documenting, enables codegen for TypeScript clients.
- Evolves without versioning (add fields, deprecate old ones).
- Aggregates many backends behind one graph (BFF, federation).

**GraphQL costs:**

- **HTTP caching** is harder – everything is `POST /graphql`; you need client caches (Apollo, urql, Relay) or persisted queries over `GET`.
- **Performance pitfalls** like N+1 resolvers; arbitrary queries can be expensive.
- **Security** needs extra work: depth/cost limits, field-level authorization.
- Errors usually come back as `200` with an `errors` array, so monitoring differs.
- More tooling and learning curve.

**When to choose:**

- REST: simple CRUD, public APIs, file uploads, heavy reliance on CDN caching, webhooks.
- GraphQL: many client types with different data needs, deeply related data, fast-moving frontends.

They can coexist – e.g. REST for public/partner APIs, GraphQL as a BFF for your own apps.

**Follow-up:** How would you cache GraphQL responses? (Normalized client cache, persisted queries with `GET` + CDN, response caching with cache hints.)
