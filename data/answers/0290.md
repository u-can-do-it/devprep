## Hints

- When one widget changes size, how does the browser know the rest of the page isn't affected?
- Why should the browser lay out and paint a long article's comments section the user hasn't scrolled to?
- If off-screen content isn't rendered, what happens to the scrollbar and to find-in-page?

## Answer

Both let you tell the browser that part of the page is **independent**, so it can skip or limit style, layout and paint work.

**`contain`** is a promise about an element's subtree:

| Value | Promise | Benefit |
|---|---|---|
| `layout` | Inner layout doesn't affect the outside (and vice versa) | Relayout stays inside the box |
| `paint` | Children never paint outside its bounds (they're clipped) | Paint can be skipped when it's off screen |
| `size` | Its size doesn't depend on its children | Can be sized without laying out the children |
| `inline-size` | Like `size`, on the inline axis only | Required for container queries |
| `content` | `layout paint style` | **A safe default** for widgets, cards, list items |
| `strict` | `content` + `size` | Needs an explicit size |

```css
.feed-item { contain: content; }
```

Side effects: `contain: paint/layout` creates a stacking context and a containing block for absolute and fixed children, and clips overflow. That can break dropdowns that should overflow the box.

**`content-visibility`** goes further:

- **`auto`**: when the element is **off screen**, the browser **skips its rendering work entirely** (style, layout, paint) and applies size containment. When it nears the viewport, it renders as normal. The content **stays in the DOM and the accessibility tree**, and find-in-page and anchor links still work.
- **`hidden`**: like `display: none` for rendering, but keeps the rendering state cached, so showing it again is cheap. Good for tab panels.

Because skipped content has no size, give it a placeholder size, or the scrollbar jumps:

```css
.article-section {
  content-visibility: auto;
  contain-intrinsic-size: auto 600px; /* estimate; "auto" remembers the last rendered size */
}
```

**When it helps:** long, content-heavy pages (docs, feeds, comment threads, dashboards with many panels), where initial rendering time can drop a lot.

**When it doesn't:** small or mostly above-the-fold pages, and elements you measure from JavaScript. For very large lists, virtualization (TanStack Virtual) is still better, because it keeps the DOM nodes out entirely. A bad `contain-intrinsic-size` estimate causes scroll jumps. Measure before and after in a DevTools Performance recording.

**Follow-up:** the `contentvisibilityautostatechange` event lets you pause expensive work, such as canvas rendering, while an element is skipped.
