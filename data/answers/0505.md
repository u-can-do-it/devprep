## Hints

- A customer walks away from a shared computer with their account open. What should happen?
- Where can an account number end up besides the screen?
- Which third-party scripts run on the page, and what can they read?
- Does hiding a button in the UI stop a user from performing that action?

## Answer

The frontend can't *enforce* security: the server must. But in a banking portal it decides a lot about what leaks and how sessions behave.

**1. Tokens and sessions**

- Keep tokens out of JavaScript. Use `HttpOnly; Secure; SameSite` cookies, or a Backend-for-Frontend that holds the tokens (#421). Don't store them in `localStorage`, because any XSS can read it (#115).
- **Idle timeout:** after inactivity, show a warning dialog with a countdown and an "I'm still here" button (WCAG 2.2.1 Timing Adjustable), then log out. The **server also expires the session**: the client timer is only UX. Banks typically also set an absolute session limit.
- **Logout everywhere in the browser:** clear in-memory state and query caches, and tell other tabs with `BroadcastChannel` so they log out too.
- Send `Cache-Control: no-store` on pages and API responses with personal data, so the back button or a shared computer doesn't show cached account details after logout.

**2. Sensitive data**

- **Mask by default:** show account numbers, IBANs and card numbers as the last 4 digits. "Show full number" can require re-authentication and is audit-logged on the server.
- **Never put sensitive data in URLs.** URLs end up in browser history, proxy and server logs, and `Referer` headers. Use opaque ids, and set `Referrer-Policy: strict-origin-when-cross-origin` or stricter.
- **Keep it out of telemetry:** scrub error-tracking events (Sentry `beforeSend`), mask inputs in session replay, don't send PII in analytics events, and don't `console.log` API responses. Don't publish source maps publicly.
- Use the right `autocomplete` values (`one-time-code` for OTPs) and don't block password managers.

**3. Step-up authentication for risky actions**

Making a payment, adding a payee, or changing a phone number or email requires fresh MFA or transaction signing (PSD2 Strong Customer Authentication in the EU). The UI handles the flow: challenge, retry, timeout, and returning to the action. The server decides when step-up is required. Prevent double submits with a disabled button and an idempotency key (#356).

**4. XSS and third-party code**

- A strict **CSP** (#111), and ideally **Trusted Types**. No `dangerouslySetInnerHTML` without DOMPurify.
- **Every third-party script can read the whole page**, including what the user types (Magecart-style skimming). Keep tag managers and widgets to a minimum, pin them with Subresource Integrity, and load payment card fields from the provider's iframe (hosted fields), which also keeps you out of most PCI DSS scope.
- **Clickjacking:** `frame-ancestors 'none'` (#112).

**5. Authorization stays on the server**

Hiding a "Approve payment" button for users without the role is UX, not security. The API must check every request (#371 IDOR). Fetch permissions from the server, and don't trust role claims the client can edit.

**6. Supply chain**

Commit the lockfile, run SCA scanning (Snyk, `npm audit`, Dependabot), use an internal registry proxy, and review new dependencies (#375). Banks usually have strict policies on this, so expect questions about it.

**Good closing line:** "The frontend's job is to avoid leaking data and to make secure flows usable. The backend's job is to enforce them."
