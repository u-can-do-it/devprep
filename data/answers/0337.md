## Hints

- What happens when two users load the same record, both edit it and both save?
- Would you rather block a competing writer or detect the conflict at save time, and what does that depend on?
- If transaction A locks row 1 then row 2 while B locks row 2 then row 1, what happens?

## Answer

Both prevent **lost updates** when concurrent writers modify the same data.

**Pessimistic locking** – lock the row when reading, so others wait.

```sql
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;   -- others block here
UPDATE accounts SET balance = balance - 50 WHERE id = 1;
COMMIT;
```

Good for short, high-contention critical sections (inventory, balances). Costs: blocking, lower throughput, deadlock risk. Variants: `NOWAIT` (fail fast) and `SKIP LOCKED` (great for job queues: each worker grabs unlocked rows).

**Optimistic locking** – no lock; detect conflicts on write with a version column (or timestamp).

```sql
UPDATE documents
SET body = $1, version = version + 1
WHERE id = $2 AND version = $3;   -- 0 rows updated => someone else won
```

Good when conflicts are rare and edits are long-lived (user forms, documents across HTTP requests – you can't hold a DB lock while a user types). On conflict: retry, merge, or show "this record changed". In REST this maps to `ETag` + `If-Match`, returning `412 Precondition Failed`.

**Deadlocks** – two transactions each hold a lock the other needs, so neither can proceed. PostgreSQL detects this (after `deadlock_timeout`) and aborts one with error `40P01`; MySQL InnoDB does the same.

Prevention:

- Acquire locks in a **consistent order** (e.g. sort ids before updating).
- Keep transactions **short**; no network calls inside them.
- Lock everything needed up front (`SELECT ... FOR UPDATE` on all rows at once).
- Use atomic single statements (`SET stock = stock - 1 WHERE stock > 0`) where possible.
- Always have **retry logic** for deadlock and serialization errors.
