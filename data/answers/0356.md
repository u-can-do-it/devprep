## Hints

- What should the server do when the same key arrives twice at the same moment?
- What if a client reuses a key with a different request body?
- Where does the record of the original response live, and for how long?

## Answer

Network failures leave clients unsure whether a `POST /payments` succeeded. An **idempotency key** (a client-generated UUID sent in the `Idempotency-Key` header) lets them retry safely: the server performs the operation **at most once** and returns the **same response** for every retry.

**Storage** – a table (or Redis with persistence) keyed by `(client_id, key)`:

```sql
CREATE TABLE idempotency_keys (
  client_id     bigint NOT NULL,
  key           text   NOT NULL,
  request_hash  text   NOT NULL,          -- hash of method + path + body
  status        text   NOT NULL,          -- 'in_progress' | 'completed'
  response_code int,
  response_body jsonb,
  created_at    timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (client_id, key)
);
```

**Flow:**

1. `INSERT ... ON CONFLICT DO NOTHING` with `status = 'in_progress'`. The unique key makes concurrent duplicates race-safe.
2. If the row already existed:
   - different `request_hash` → `422` (key reused for another request);
   - `in_progress` → `409 Conflict` (tell the client to retry later);
   - `completed` → replay the stored status code and body.
3. Otherwise perform the operation. Ideally write the business change **and** mark the key `completed` with the response **in the same DB transaction**.
4. Expire keys after a documented window (e.g. 24 hours).

**The hard part: external side effects.** If you charge a card via a provider and crash before saving, a retry might charge twice. Solutions:

- Pass your own idempotency key **downstream** (Stripe and most payment providers accept one).
- Break the work into **recovery points** stored on the key row (`started` → `charge_created` → `finished`) so a retry resumes from the last completed step.
- Push follow-up effects (emails, webhooks) through a transactional **outbox**.

Don't cache failures caused by transient server errors (`5xx`) as final – let the client retry them; do cache deterministic `4xx` results.
