## Hints

- Who should handle cross-cutting concerns like authentication, rate limiting and TLS, so each service doesn't reimplement them?
- Does a mobile app on a slow network want the same payload as a desktop dashboard?
- Which team should own an API that exists to serve one specific frontend?

## Answer

**API Gateway:** a single entry point in front of many backend services. It handles **cross-cutting concerns**:
- routing (`/orders/*` goes to the order service),
- authentication and token validation, rate limiting, quotas,
- TLS termination, CORS, request size limits,
- logging, metrics, tracing headers, and sometimes caching and request transformation.

Examples: AWS API Gateway, Kong, Envoy-based gateways, Kubernetes Gateway API implementations, Cloudflare. It's generic and usually owned by a platform team.

**Backend-for-Frontend (BFF):** a backend built **for one specific client** (web, iOS, partner API), usually owned by that frontend team. It:
- **aggregates** calls to several services into one response tailored to a screen (fewer round trips on mobile),
- shapes data (trims fields, formats for the UI),
- holds client-specific logic, such as keeping OAuth tokens **server-side** and giving the browser an HTTP-only session cookie (a strong security pattern for SPAs).

```text
Browser -> Web BFF (Next.js server) --+
Mobile  -> Mobile BFF ----------------+--> API Gateway --> users / orders / catalog
```

In the React world, **Next.js route handlers and Server Components often act as the web BFF**.

**When to use:**
- **Gateway:** almost always with several services exposed externally.
- **BFF:** when clients have clearly different needs, or frontends are making many chatty calls. Alternatives are GraphQL (one flexible API) or a single shared API if clients are similar.

**Pitfalls:** putting business logic in the gateway (it becomes a bottleneck monolith), and duplicating domain logic across several BFFs.
