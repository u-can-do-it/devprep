## Hints

- Is it easier to buy a bigger server or to add more servers?
- What's the upper limit of making a single machine more powerful?
- What must be true about your application before you can run many copies of it behind a load balancer?

## Answer

- **Vertical scaling (scale up):** give a single machine more CPU, RAM, or faster disks. Simple — no code changes — but there's a hardware ceiling, cost grows steeply, it usually requires downtime, and the machine remains a single point of failure.
- **Horizontal scaling (scale out):** add more machines/instances and spread load across them with a load balancer. Nearly unlimited capacity, better fault tolerance, and works well with autoscaling — but adds complexity.

To scale horizontally, services should be **stateless**: no sessions or uploads stored in local memory/disk. Move state to shared stores:

- sessions → Redis or signed tokens,
- files → object storage (S3),
- data → a database that itself can scale (read replicas, sharding).

Typical practice: scale stateless app servers horizontally (e.g. Kubernetes HPA or cloud autoscaling groups), while databases often start with vertical scaling and add read replicas, caching, or sharding later because scaling writes horizontally is hard.

**Follow-up:** "What would you check before adding more instances?" — whether the bottleneck is actually the database, an external API, or a lock; more app servers won't fix those.
