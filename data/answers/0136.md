## Hints

- In TDD, what do you write before the production code?
- What are the three steps of the TDD cycle?
- In what situations might writing tests first slow you down?

## Answer

Test-driven development is a workflow where you write a failing test **before** the code that makes it pass, in a short loop:

1. **Red** — write a small test for the next bit of behavior; watch it fail.
2. **Green** — write the simplest code that makes it pass.
3. **Refactor** — clean up code and tests while keeping everything green.

```python
# 1. red
def test_slugify_lowercases_and_replaces_spaces():
    assert slugify("Hello World") == "hello-world"

# 2. green
def slugify(text: str) -> str:
    return text.lower().replace(" ", "-")
```

**Pros:**

- Forces you to define behavior and API from the caller's perspective first.
- Leads to testable, loosely coupled design.
- Produces a regression suite as a by-product; safe refactoring.
- Small steps and fast feedback.

**Cons / limitations:**

- Slower initially; requires discipline and practice.
- Awkward for exploratory work, prototypes, or UI layout where requirements are unclear.
- Can produce over-specified tests tied to implementation if done mechanically.

Many teams apply TDD selectively — for business logic, algorithms, and bug fixes (write a test reproducing the bug first) — rather than for everything.

**Follow-up:** "Is TDD the same as having high test coverage?" — no; coverage measures executed lines, TDD is a design practice.
