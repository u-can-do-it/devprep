## Hints

- Which app opens `myapp://orders/42` if two installed apps declare the `myapp` scheme?
- How do Apple and Google check that your app is allowed to open links to `example.com`?
- Where does the URL come from when the link started the app, and where when the app was already running?

## Answer

> A deep link is a URL that opens a specific screen. A custom scheme (`myapp://`) is easy but unverified: any app can claim it, and it does nothing when the app isn't installed. Universal Links (iOS) and App Links (Android) are normal `https://` URLs tied to your domain by a verification file, so they open the app when it's installed and the website when it isn't. In the app you read the initial URL on a cold start, listen for later ones, and map paths to screens.

| | Custom scheme | Universal Links / App Links |
|---|---|---|
| Example | `myapp://orders/42` | `https://example.com/orders/42` |
| Verified owner | no | yes, through your domain |
| App not installed | error or nothing | the website opens |
| Use for | OAuth redirects, development, app-to-app | links in emails, SMS, the web, ads |

**Verification files**

Both live on your domain under `/.well-known/`, are served over HTTPS without redirects, and list which app may open which paths.

```json
// https://example.com/.well-known/apple-app-site-association
{ "applinks": { "details": [{ "appIDs": ["TEAMID.com.example.shop"], "components": [{ "/": "/orders/*" }] }] } }
```

```json
// https://example.com/.well-known/assetlinks.json
[{ "relation": ["delegate_permission/common.handle_all_urls"],
   "target": { "namespace": "android_app", "package_name": "com.example.shop",
               "sha256_cert_fingerprints": ["AB:CD:..."] } }]
```

The app side: an Associated Domains entitlement (`applinks:example.com`) on iOS, and an intent filter with `android:autoVerify="true"` on Android. With Expo, both come from `app.json`.

Common mistakes: the wrong signing fingerprint (with Play App Signing, use Google's key, not your upload key), a redirect or wrong content type on the file, and forgetting that the OS caches the file.

**Handling links in the app**

```ts
const initial = await Linking.getInitialURL();              // the app was started by a link
const sub = Linking.addEventListener('url', ({ url }) => handle(url));   // already running
```

You rarely write this yourself. React Navigation takes a `linking` config that maps paths to screens (#674), and Expo Router does it automatically, because every screen already has a URL (#675).

**The hard cases**

- **Cold start:** wait until navigation is mounted and the session is restored before navigating.
- **Logged out:** save the target URL, show sign-in, then continue to it.
- **Back stack:** a link straight to an order should still let the user go back to the list. Define an initial route under the target.
- **Unknown or old paths:** show a fallback screen, don't crash. Old app versions receive links made for new ones.
- **Untrusted input:** anyone can craft a link. Validate parameters, never put tokens in links, and don't perform an action (pay, delete, add a friend) just because a link was opened. Ask the user to confirm.

**Deferred deep links**

"Install the app, then land on the order" doesn't work by itself, because the link is lost during installation. It needs an attribution service or the platform's install referrer.

**Testing**

```bash
npx uri-scheme open "myapp://orders/42" --ios
```

```bash
adb shell am start -a android.intent.action.VIEW -d "https://example.com/orders/42"
```

```bash
xcrun simctl openurl booted "https://example.com/orders/42"
```

Universal Links open the app from another app (Mail, Notes, Messages), not when you type the URL into the browser's address bar.

**Follow-up:** why is a custom scheme risky as an OAuth redirect URI, and what makes it acceptable? (Another app can register the same scheme and receive the authorization code. PKCE makes the stolen code useless, and a verified `https` redirect removes the problem; see #697.)
