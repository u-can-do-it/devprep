## Hints

- In development, where does the JavaScript come from: the app binary or your computer?
- Which changes need only a refresh, and which need a new native build?
- A crash shows nothing in the JS console. Where else do you look?

## Answer

> In development the app is a native shell that loads JavaScript from Metro, the bundler running on your computer. Editing JS triggers Fast Refresh in under a second. Changing native code or adding a native library needs a new native build. You debug JS with React Native DevTools, and native problems with Xcode and Logcat. Always check performance in a release build on a real device.

**The moving parts**

- **Metro** bundles your JS and assets and serves them to the app over the local network. Start it with `npx expo start` (or `npx react-native start`).
- **The native app** is installed on a simulator, emulator or device. It is either Expo Go, or your own development build made with `npx expo run:ios`, `npx expo run:android` or EAS Build (#676).
- **Fast Refresh** re-runs changed modules and keeps component state for function components. Press `r` in the terminal for a full reload.

Run the native build again only when native code changes: a new library with native code, a config plugin, permissions, the app icon.

**The dev menu**

Open it by shaking the device, with `Cmd+D` on the iOS simulator, `Cmd+M` (or `Ctrl+M`) on the Android emulator, or `m` in the terminal. It has reload, the element inspector, the performance monitor and the DevTools entry.

**React Native DevTools** (press `j` in the terminal)

- **Console and Sources:** logs, breakpoints, stepping through code on Hermes.
- **Components and Profiler:** the React tree, props and state, and why a component rendered (#216).
- **Network and Performance:** request inspection and performance traces in recent versions.

It replaced Flipper and the old "remote debugging in Chrome" mode. Errors and warnings also show in the app through LogBox.

**Simulator vs real device**

| | Simulator / emulator | Real device |
|---|---|---|
| Speed of iteration | fastest | needs a cable or the same Wi-Fi |
| Camera, sensors, biometrics | limited or faked | real |
| Push notifications | limited | real (#683) |
| Performance | misleading: it uses your computer's CPU | the truth, especially on a mid-range Android |

The iOS Simulator needs a Mac with Xcode. The Android Emulator runs anywhere. From the emulator, your computer's `localhost` is `10.0.2.2`.

**Native logs**

When the app crashes or a native module misbehaves, the JS console is often silent:

- **iOS:** Xcode's console, or the Console app for a device.
- **Android:** Logcat in Android Studio, or `adb logcat`.

A native stack trace usually names the library at fault.

**Common fixes when things act strange**

- Clear Metro's cache: `npx expo start --clear`.
- Rebuild the native app after changing dependencies.
- Check that the device and the computer are on the same network.
- Check whether the bug exists only in debug or only in release.

**Debug vs release**

A debug build is much slower: extra checks, no minification, dev warnings. Never judge performance in it. Build a release variant (`npx expo run:android --variant release`) before you measure or demo.

**Follow-up:** the app works in development but crashes on start in the release build. Where do you look first? (Native logs for the crash reason. Typical causes: a missing environment variable, code that depends on dev-only behaviour, or code removed by minification.)
