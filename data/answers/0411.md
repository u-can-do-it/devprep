## Hints

- How would you recreate your production environment exactly if the account were wiped?
- How does Terraform know which real resources it created earlier?
- What should happen if two engineers run `apply` at the same moment?

## Answer

**Infrastructure as Code (IaC)** means defining infrastructure (networks, databases, buckets, DNS, IAM) in versioned files instead of clicking in a console. Benefits: reproducible environments, code review for infra changes, history and rollback through Git, and automation in CI.

Tools: **Terraform / OpenTofu** (declarative HCL, multi-cloud), Pulumi and AWS CDK (general-purpose languages), CloudFormation and Bicep (cloud-specific).

**How Terraform works:**
- You declare the **desired state** in `.tf` files.
- **State** (`terraform.tfstate`) maps your resources to real cloud IDs and stores their last-known attributes. It's how Terraform knows what exists.
- **`terraform plan`** compares config, state and reality, then shows the diff: create, update in place, or **destroy/replace**.
- **`terraform apply`** executes that plan.

```hcl
terraform {
  backend "s3" {
    bucket       = "acme-tf-state"
    key          = "prod/app.tfstate"
    region       = "eu-central-1"
    use_lockfile = true   # native S3 state locking
  }
}

resource "aws_s3_bucket" "uploads" {
  bucket = "acme-prod-uploads"
}
```

**Best practices:**
- Keep state in a **remote, encrypted, locked backend**. It often contains secrets, so never commit it.
- Run `plan` on every PR (posted as a comment) and `apply` from CI after merge, with OIDC credentials.
- Use reusable **modules** and separate state per environment or component to limit the blast radius.
- Detect **drift** (manual console changes) with scheduled plans. Use `prevent_destroy` for critical resources like databases.

**Pitfall:** renaming a resource in code can make Terraform plan to destroy and recreate it. Read the plan, and use `moved` blocks for refactors.
