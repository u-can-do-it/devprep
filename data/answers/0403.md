## Hints

- What happens if a static AWS access key stored in CI leaks through a log or a malicious dependency?
- How could a cloud provider trust a CI job without any stored password?
- Should a workflow triggered by a pull request from a fork see your deploy secrets?

## Answer

**Basics of CI secrets:**
- Store them in the CI secret store (repository, organization or **environment** secrets), never in the repo. They're masked in logs, but masking is best effort, so never echo or transform them.
- Use **environment protection** (required reviewers, branch rules) so production secrets are only available to deploy jobs from `main`.
- Least privilege: set `permissions:` on the `GITHUB_TOKEN` (default to `contents: read`). Fork PRs don't get secrets, so don't work around that with `pull_request_target` plus checking out untrusted code.

**Why OIDC:** long-lived cloud keys never expire on their own, are hard to rotate, and work from anywhere once leaked. With **OpenID Connect**, the CI job asks GitHub for a signed, short-lived JWT describing *who* it is (repo, branch, environment). The cloud provider is configured to trust GitHub's issuer and **exchanges the token for temporary credentials** for a specific role, but only if claims like `sub = repo:acme/api:environment:production` match.

```yaml
permissions:
  id-token: write   # allow requesting the OIDC token
  contents: read
steps:
  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::123456789012:role/gha-deploy
      aws-region: eu-central-1
  - run: aws s3 sync dist/ s3://my-site
```

Benefits: no stored secret, credentials expire in minutes, access is scoped to exactly that repo and branch, and audit logs show which workflow assumed the role. The same pattern works for GCP (Workload Identity Federation), Azure, and npm trusted publishing.

**Pitfall:** a trust policy that only checks the organization (`repo:acme/*`) lets any repo or branch assume the production role.
