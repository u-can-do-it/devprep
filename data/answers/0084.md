## Hints

- What data structure do most relational indexes use, and why does it make lookups O(log n)?
- Why might the database ignore an index on `lower(email)` when you query `WHERE email = ...`, or vice versa?
- What extra work does every `INSERT` or `UPDATE` do for each index on the table?

## Answer

> Without an index, the database has to scan every row to find matches. An index is a separate sorted structure, usually a B-tree, that lets it jump straight to the right rows and also gives sorted order for free. Indexes are not free, though: every write has to update them, they use storage and memory, and they don't help on low-selectivity columns or predicates like `lower(email)` or `LIKE '%foo'`. Add them based on real queries and check with `EXPLAIN ANALYZE`.

An index is a separate, sorted data structure (usually a **B-tree**) mapping column values to row locations. Instead of a full table scan, the DB walks the tree in O(log n) and also gets sorted order for free, which helps `ORDER BY`, range queries and joins. Other types: hash, GIN (arrays/JSONB/full text), GiST, BRIN (in PostgreSQL).

```sql
CREATE INDEX idx_orders_customer_created ON orders (customer_id, created_at DESC);

-- uses the index (leftmost prefix)
SELECT * FROM orders WHERE customer_id = 42 ORDER BY created_at DESC LIMIT 20;

-- check the plan
EXPLAIN ANALYZE SELECT * FROM orders WHERE customer_id = 42;
```

Concepts: **composite indexes** follow the leftmost-prefix rule; **covering indexes** (`INCLUDE`) avoid table lookups; **partial indexes** index a subset (`WHERE deleted_at IS NULL`); **unique** indexes enforce constraints.

**When indexes hurt or don't help:**

- **Write overhead** – every INSERT/UPDATE/DELETE must update each index; write-heavy tables suffer.
- **Storage and memory** – indexes compete for cache.
- **Low selectivity** – an index on a boolean or `status` with 3 values often isn't used; a scan is cheaper.
- **Unusable predicates** – functions on the column (`WHERE lower(email) = ...`) without an expression index, leading wildcards (`LIKE '%foo'`), implicit type casts, wrong column order in composite indexes.
- **Redundant/unused indexes** – pure cost; find them via `pg_stat_user_indexes`.

Index based on real query patterns and verify with `EXPLAIN ANALYZE`.
