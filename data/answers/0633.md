## Hints

- Behind a proxy, what host and protocol does the Next.js process see in the request, and which URL does it then send to the IdP as `redirect_uri`?
- When does the browser refuse to store a cookie with the `Secure` flag or a `__Secure-` prefix?
- What happens when two replicas have different `AUTH_SECRET` values?
- Which errors appear when the Node process calls the IdP through a corporate proxy with an internal certificate authority?

## Answer

Start with facts, not guesses: set `debug: true` (or a custom `logger`) in the auth config, read the server logs, and look at the error code in the URL (`/api/auth/error?error=Configuration`, `OAuthCallback`, `AccessDenied`…). Then check `/api/auth/providers`, `/api/auth/csrf` and `/api/auth/session` directly, and inspect the cookies and redirects in DevTools (Network with "Preserve log" on).

**Typical causes, by symptom:**

| Symptom | Likely cause | Fix |
|---|---|---|
| Redirects to `http://localhost:3000/...`, or the IdP says *invalid redirect_uri* | The app builds URLs from the internal host | v4: set `NEXTAUTH_URL` to the **public** URL. v5: `AUTH_URL`, or `AUTH_TRUST_HOST=true` so it trusts `X-Forwarded-Host`/`X-Forwarded-Proto`; make the proxy send those headers. Register the exact callback URL in the IdP. |
| Login loop: IdP succeeds, app shows the login page again | The session cookie isn't stored or sent: `Secure`/`__Secure-` cookie on plain HTTP, wrong cookie `Path` under a sub-path, or cookie domain mismatch | Terminate TLS correctly and forward `X-Forwarded-Proto: https`; with a `basePath`, configure it in Next.js **and** in Auth.js (v4: `NEXTAUTH_URL=https://host/app/api/auth`, `SessionProvider basePath`; v5: `basePath` option) |
| Random logouts, `JWTSessionError` / *decryption operation failed* | Replicas or deploys use **different secrets**, or the secret was rotated | One `AUTH_SECRET` (`NEXTAUTH_SECRET` in v4) for all replicas, from a secret store, never generated at startup |
| `400 Request Header Or Cookie Too Large` / `431` | Session cookie with access, refresh and ID tokens is several KB (split into `.0`, `.1` chunks) | Store fewer claims in the JWT, drop `id_token` if not needed, use database sessions, or raise the proxy limits (nginx `large_client_header_buffers`) as a stopgap |
| `OAuthCallback` / *outgoing request timed out after 3500ms* (v4) | The server-to-IdP call is slow or blocked | Check egress from the pod to the IdP; in v4 raise `httpOptions.timeout` |
| *unable to verify the first certificate*, `UNABLE_TO_GET_ISSUER_CERT_LOCALLY` | IdP certificate signed by an internal CA that Node doesn't trust | `NODE_EXTRA_CA_CERTS=/etc/ssl/corp-ca.pem`; never `NODE_TLS_REJECT_UNAUTHORIZED=0` in production |
| Calls to the IdP hang, but `curl` from the pod works | An outbound HTTP proxy is required, and Node doesn't read `HTTP(S)_PROXY` by default | Configure a proxy agent, or on recent Node versions set `NODE_USE_ENV_PROXY=1`; add the IdP to `NO_PROXY` if it's internal |
| `iat`/`exp` validation errors right after login | Clock skew between servers | NTP on all hosts; a small clock tolerance |
| `CLIENT_FETCH_ERROR` in the browser console | `useSession` can't reach `/api/auth/session` (wrong base path, the proxy blocks it, or HTML returned instead of JSON) | Open that URL in the browser and fix routing |

**The method behind it**

1. **Reproduce** with the deployed config (same env vars, same proxy) and compare the redirect chain with what the IdP expects.
2. **Draw the hops**: browser → load balancer → ingress → Next.js pod, then pod → IdP. Each hop can rewrite the host, protocol, path or headers.
3. **Check headers at each hop**: what does the pod actually receive? Log `x-forwarded-*` temporarily.
4. **Write it down**: the working config (env vars, IdP client settings, proxy headers) goes into the repo's docs, because this is exactly the knowledge that gets lost.

**Follow-up:** "Do I need sticky sessions with several replicas?" Not with JWT sessions, as long as every replica has the same secret. With database sessions every replica needs the same database. Sticky sessions only hide a misconfiguration.
