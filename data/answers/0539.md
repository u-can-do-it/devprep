## Hints

- How does the page know the user reached the bottom without listening to every scroll event?
- The sentinel is visible on first render because the first page is short. What stops that from fetching every page in a loop?
- What does a keyboard or screen-reader user get instead of "scroll to load more"?

## Answer

A standard 30-minute task: a list that loads the next page when the user nears the end. The interviewer checks that you avoid scroll listeners, handle races and cleanup, and don't forget users who don't scroll with a mouse.

**Ingredients:** cursor pagination from the API (#95), an `IntersectionObserver` on a sentinel element (#278), and state for `items`, `cursor`, `status` and `hasMore`.

```tsx
type Page = { items: Item[]; nextCursor: string | null };

function useInfiniteItems() {
  const [items, setItems] = useState<Item[]>([]);
  const [cursor, setCursor] = useState<string | null>(null);
  const [hasMore, setHasMore] = useState(true);
  const [status, setStatus] = useState<'idle' | 'loading' | 'error'>('idle');
  const inFlight = useRef(false);                       // guard across renders

  const loadMore = useCallback(async (signal?: AbortSignal) => {
    if (inFlight.current || !hasMore) return;
    inFlight.current = true;
    setStatus('loading');
    try {
      const res = await fetch(`/api/items?limit=20${cursor ? `&cursor=${cursor}` : ''}`, { signal });
      if (!res.ok) throw new Error(`HTTP ${res.status}`);
      const page: Page = await res.json();
      setItems((prev) => [...prev, ...page.items]);
      setCursor(page.nextCursor);
      setHasMore(page.nextCursor !== null);
      setStatus('idle');
    } catch (err) {
      if ((err as Error).name !== 'AbortError') setStatus('error');
    } finally {
      inFlight.current = false;
    }
  }, [cursor, hasMore]);

  return { items, hasMore, status, loadMore };
}

export function ItemList() {
  const { items, hasMore, status, loadMore } = useInfiniteItems();
  const sentinel = useRef<HTMLDivElement>(null);

  useEffect(() => {                                     // first page
    const ac = new AbortController();
    loadMore(ac.signal);
    return () => ac.abort();
  }, []);                                               // eslint-disable-line react-hooks/exhaustive-deps

  useEffect(() => {
    const el = sentinel.current;
    if (!el || !hasMore) return;
    const io = new IntersectionObserver(
      ([entry]) => { if (entry.isIntersecting) loadMore(); },
      { rootMargin: '400px' },                          // start loading before the user hits the bottom
    );
    io.observe(el);
    return () => io.disconnect();
  }, [loadMore, hasMore]);                              // re-created when cursor changes, so the callback is never stale

  return (
    <section aria-busy={status === 'loading'}>
      <ul>{items.map((it) => <li key={it.id}>{it.name}</li>)}</ul>
      {status === 'error' && <button onClick={() => loadMore()}>Retry</button>}
      {hasMore
        ? <button ref={sentinel as any} onClick={() => loadMore()} disabled={status === 'loading'}>
            {status === 'loading' ? 'Loading…' : 'Load more'}
          </button>
        : <p role="status">No more items</p>}
    </section>
  );
}
```

**What to say while coding:**

- **Why `IntersectionObserver`:** a scroll listener fires dozens of times per second and forces layout reads; the observer is asynchronous and cheap. `rootMargin` prefetches before the sentinel is visible.
- **The loop bug:** if the first page is shorter than the viewport, the sentinel is visible immediately and the observer fires again after each page. That is correct behaviour **as long as** `hasMore` stops it and the in-flight guard prevents double requests. Without the guard you get duplicated items.
- **Stale closures:** the observer callback captures `loadMore`; recreating the observer when `loadMore` changes (its deps are `cursor` and `hasMore`) keeps it current. A `useRef` holding the latest function is the alternative.
- **Race conditions:** append with a functional update; a response for an old cursor can't arrive after a newer one because the guard serialises requests. If filters can change, reset state and abort the in-flight request when they do (#518).
- **Keys:** `item.id`, never the index, since the list grows (#32).
- **Accessibility:** the sentinel is a real **"Load more" button**, so keyboard and screen-reader users have an explicit control; `aria-busy` and a `role="status"` message announce progress and the end (#287). Infinite scroll also makes the footer unreachable, so keep the button or cap auto-loading after a few pages.
- **Scroll position restoration:** on back navigation the browser can't restore a list that is no longer there; cache the pages (TanStack Query keeps them, #530) or store the cursor and scroll offset in `sessionStorage`.
- **Very long sessions:** thousands of DOM nodes slow the page; combine with virtualization (#218) or drop pages far above the viewport.

**With TanStack Query** the hook collapses to `useInfiniteQuery({ queryKey: ['items'], queryFn: ({ pageParam }) => fetchPage(pageParam), initialPageParam: null, getNextPageParam: (last) => last.nextCursor })`, which gives `fetchNextPage`, `hasNextPage`, `isFetchingNextPage` and caching for free; the observer and the accessibility work stay the same.

**Follow-up:** why cursor pagination rather than `page=3`? (Items inserted at the top shift offsets and produce duplicates or gaps; a cursor is stable, #95.)
