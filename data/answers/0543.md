## Hints

- Which rules can you leave to the model's judgement, and which must hold even when the model is wrong or manipulated?
- Where can you put a check so that it applies to agent-written and human-written code alike?
- You changed `CLAUDE.md`, a skill or the model version. How do you know the agent got better and not worse?

## Answer

Two separate problems: **guardrails** keep a wrong or manipulated agent from doing damage, and **evaluation** tells you whether agents produce good code and whether your changes to their setup help.

**Guardrails, in layers**

| Layer | Examples | Protects against |
|---|---|---|
| Instructions | `CLAUDE.md`, skills, review checklists (#541) | honest mistakes (advisory only) |
| Harness permissions | allow/ask/deny rules, read-only tools, no `git push`, deny `.env` | destructive or unwanted actions |
| Hooks | block dangerous commands, run formatters and linters after every edit, refuse to stop while tests fail | rules the model forgets |
| Isolation | sandboxed shell, containers or worktrees, no production credentials, network allowlist | prompt injection and exfiltration (#525) |
| Repository gates | branch protection, required human review, CODEOWNERS for sensitive paths, CI | anything that got past the agent |
| CI checks | tests, type checks, lint, SAST, dependency and secret scanning, migration linting | insecure or broken code (#526) |
| Production | feature flags, canaries, alerts (#548) | what review missed |

Principles:

- **Enforce, don't ask.** A rule that matters becomes a deterministic check (a lint rule, a hook, a CI job), not a line in a prompt. The prompt explains why; the check guarantees it.
- **The same gates for humans and agents.** Agent PRs go through the normal pipeline; nobody merges code they don't understand.
- **Protect the tests.** Agents under pressure weaken assertions, skip tests or update snapshots. Flag PRs that change tests and implementation together in risky areas, run mutation testing on critical modules (#395), keep golden tests the agent can't edit.
- **Scale review to risk.** Payments, auth, migrations and patient data get a human expert; a copy change gets a lighter look.
- **Least privilege for agents in CI:** read-only tokens, a bot identity that can only open PRs, no secrets on runs triggered by untrusted input.

**Evaluating agent-written code**

- **Per change:** does it pass CI, how many review comments and fix-up commits, was it merged as is, rewritten or abandoned.
- **Over time:** revert and hotfix rate of agent-authored PRs vs human ones, bugs traced back to them, time from task to merge, and the share of tasks delegated successfully. Track them, but don't turn them into targets.
- **An eval suite for your agent setup.** Collect 20-50 real past tasks from your repo (closed tickets with known good solutions and tests): "add a field to the booking API", "fix this flaky test", "find why this query is slow". Run the agent on each in a clean worktree and grade automatically (hidden tests pass, lint and types pass, no forbidden files touched) plus a rubric graded by a person or an LLM judge (follows conventions, minimal diff, no new dependencies) (#482).
- **Run the suite on every change to the setup:** a new `CLAUDE.md`, skill, MCP tool, model or tool version. Compare pass rate, cost and time per task with the previous run. Agents are non-deterministic, so run each task several times and look at the rate, not one result.
- **Read transcripts**, not only scores: where did the agent waste turns, which instruction did it misread, which tool output confused it. That's where the fixes come from.

**Example:** after adding a "database migrations" skill, the migration tasks in the suite went from 3/10 to 8/10 passing, and no other category dropped. Ship it. If another category dropped, the skill's description was probably triggering too broadly.

**Follow-up:** your team's agents start merging more code, and incidents go up. What would you look at first? (Which changes caused them, whether review is scaled to risk, missing tests in those areas, PR size, and whether reviewers are rubber-stamping large diffs.)
