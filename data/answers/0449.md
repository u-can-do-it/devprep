## Hints

- If the remote's URL is hardcoded in the host's build, what has to happen to roll back a bad remote?
- What's the contract between a host and a remote, and how do you change it without a lockstep release?
- A user opened the app an hour ago and you just deployed a new remote. What happens when they open a lazy route?

## Answer

Host and remotes ship on their own schedules, so the problem is **version skew**. The contract between them is: the exposed module names, their props and types, the shared dependency ranges, and the events they emit. Treat it like a public API.

**Resolve remote URLs at runtime, not build time**

- Each remote deploy uploads **immutable, content-hashed** assets to a versioned path (`/checkout/1.14.2/…`).
- The host loads a small **manifest** that maps remote name → URL. Releasing means flipping that pointer, and **rollback means flipping it back**. Neither needs a host rebuild.
- **Caching:** the manifest and `remoteEntry.js` get `no-cache` or a short TTL. Hashed chunks get `Cache-Control: immutable` with a long max-age.
- **Keep old versions online** for a while. Users with an open tab still lazy-load chunks from the version they started with. Deleting them causes `ChunkLoadError`.

```ts
// shell: load the manifest, register remotes, render with a fallback
import { registerRemotes, loadRemote } from '@module-federation/enhanced/runtime';

const manifest: Record<string, string> =
  await fetch('/mfe-manifest.json', { cache: 'no-store' }).then((r) => r.json());
// { "checkout": "https://cdn.example.com/checkout/1.14.2/mf-manifest.json" }

registerRemotes(Object.entries(manifest).map(([name, entry]) => ({ name, entry })));

const Checkout = lazy(async () => {
  const mod = await loadRemote<{ default: ComponentType<CheckoutProps> }>('checkout/CheckoutPage');
  if (!mod) throw new Error('checkout unavailable');
  return mod;
});

// <ErrorBoundary fallback={<CheckoutUnavailable />}>
//   <Suspense fallback={<Spinner />}><Checkout cartId={id} /></Suspense>
// </ErrorBoundary>
```

**Evolve the contract without lockstep releases**

- **Additive changes only:** new optional props, new exposed modules.
- **Breaking change → expand and contract:** expose `./CheckoutV2` next to `./CheckoutPage`, migrate the host, then remove the old one once no host uses it.
- **Share types:** Module Federation 2.0 generates and downloads remote types, or publish a versioned `@acme/checkout-contract` package.

**Test the integration**

- **Consumer-driven contract tests:** the host states what it needs (module names, props, events). The remote's CI checks it still provides them before it can deploy.
- **Composed e2e smoke tests** (Playwright) against staging with the latest remotes, run on every remote deploy as well as host deploys.
- **Preview overrides:** load a PR build of one remote into an otherwise production composition, via a cookie or query param. Only allow your own CDN origins, otherwise this becomes an XSS vector.

**Fail safely at runtime**

- Wrap every remote in an **error boundary plus `Suspense`** with a useful fallback. A network failure or a crash must not blank the shell.
- Retry chunk loads once, then show the fallback. MF 2.0 runtime plugins (`errorLoadRemote`) can return a fallback module centrally.
- Use **`strictVersion`** for critical singletons so a mismatch fails loudly and visibly instead of breaking subtly.

**Roll out gradually and observe**

- **Canary** through the manifest service (5% of users get the new remote version), or behind feature flags.
- Tag errors and RUM metrics with the **remote name and version** (Sentry tags or releases), so you know which deploy caused a spike.
- **Singleton upgrades** (a new React major) are the one thing that still needs coordination. Plan them as a platform-wide migration.

**Follow-up:** a remote deploy breaks checkout for 10% of users, but only for those who had the app open before the deploy. What's happening, and how do you fix it?
