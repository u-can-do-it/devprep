## Hints

- Why should you always throw `Error` objects instead of strings?
- How can calling code tell a "not found" error apart from a network failure?
- When you catch a low-level error and throw a higher-level one, how do you keep the original?

## Answer

Throw `Error` instances (or subclasses), never strings or plain objects. They carry a **stack trace**, and tools and loggers know how to handle them.

**Custom error classes** let callers branch on the type of error and carry structured data:

```js
class HttpError extends Error {
  constructor(status, message, options) {
    super(message, options);          // options may contain { cause }
    this.name = 'HttpError';          // shows up in stack traces and logs
    this.status = status;
  }
}
class NotFoundError extends HttpError {
  constructor(resource, options) { super(404, `${resource} not found`, options); this.name = 'NotFoundError'; }
}
```

**`cause` (ES2022)** chains errors without losing the original:

```js
try {
  await db.query(sql);
} catch (err) {
  throw new Error('Failed to load user profile', { cause: err });
}
```

Loggers, Node's `util.inspect` and browser devtools print the cause chain, so you keep both the business context and the low-level reason.

**Handling them:**

```js
try { await loadUser(id); }
catch (err) {
  if (err instanceof NotFoundError) return showEmpty();
  if (err instanceof HttpError && err.status >= 500) return retryLater();
  throw err;   // never swallow errors you don't understand
}
```

**Good practices:**

- Add a stable `code` property (for example `'E_RATE_LIMIT'`). Messages change; codes can be relied on.
- Use `AggregateError` for multiple failures (`Promise.any` throws one).
- At API boundaries, map internal errors to safe client messages. Don't leak stack traces.
- In TypeScript, `catch (err)` is `unknown`, so narrow with `instanceof` before reading properties.

**Pitfall:** `instanceof` can fail across realms or across duplicated package copies. Checking `err.name` or `err.code` is more robust there.
