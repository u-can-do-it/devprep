## Hints

- Models learn from millions of public repos. Which security practices are common in public code, and which are rare?
- An agent suggests `npm install fast-json-validate`. What do you check before running it?
- Which CI tooling catches the mistakes a tired reviewer won't?

## Answer

Generated code is roughly as secure as the **average of its training data** plus the context you gave it. Studies and vendor reports keep finding a sizeable share of AI-suggested snippets with known weakness classes (CWEs), and developers using assistants tend to be *more* confident in insecure code. Expect these patterns:

**1. Missing authorization and validation.** Handlers that check "logged in" but not ownership (#371) or role (#524); no input validation at the boundary; trusting `req.body` wholesale (mass assignment, #372). The model doesn't know your permission model unless you tell it.

**2. Classic injection.** String-concatenated SQL and shell commands (``exec(`git log ${branch}`)``), `innerHTML`/`dangerouslySetInnerHTML` with user data, `eval`, template injection in emails, path traversal in file endpoints (`path.join(uploads, req.query.name)`).

**3. Insecure defaults copied from tutorials.** `cors({ origin: '*' })` with credentials, `verify=False` / `rejectUnauthorized: false`, `jwt.decode` where `jwt.verify` was needed, MD5 or SHA-1 for passwords instead of bcrypt/argon2, `Math.random()` for tokens, debug mode left on, and in generated infrastructure code overly broad IAM policies and public buckets.

**4. Secrets and PII.** Hard-coded API keys "for now", `.env.example` values that are real, logging whole request bodies, test fixtures built from real customer data the agent found in the repo.

**5. Hallucinated and outdated dependencies.** Packages that don't exist (**slopsquatting**: attackers register those names), real packages at wrong versions or with deprecated APIs, old pins with known CVEs, and reimplementing a library's internals instead of using it.

**6. Licensing and provenance.** Large verbatim snippets from GPL/AGPL code; unclear ownership of generated code in some jurisdictions. Company policy usually requires public-code matching filters and attribution checks.

**7. Tests that prove nothing.** Tests that mirror the implementation, mock the thing under test, or were edited by the agent until they passed. Security behaviour (`403` for the wrong user) rarely gets a test unless you ask for it.

**How a team catches it before merge**

- **Prompt for security:** project instructions (`CLAUDE.md`, rules files) that state the auth model, the validation library, logging rules and banned APIs; ask for a "what can go wrong with this endpoint?" section in the plan.
- **Review as untrusted input (#476):** read the whole diff, start at trust boundaries (network, files, database, shell), grep for `as any`, `eval`, `exec`, `innerHTML`, `verify`, `origin: '*'` and strings that look like keys.
- **Automate in CI:** SAST (Semgrep, CodeQL), dependency scanning (`npm audit`, `pip-audit`, Snyk, Dependabot/Renovate), **secret scanning** (gitleaks, GitHub push protection), a committed lockfile and registry allowlist, IaC scanning (Checkov, tfsec), and a rule that new dependencies need a reviewer's label.
- **Verify dependencies exist** and are what you think: registry page, maintainers, download counts, and the edit distance to a popular name, before installing.
- **Authorization tests as a template:** every new endpoint gets a "user A can't touch user B" test. Agents follow existing patterns well, so give them one.
- **Keep PRs small**, and don't merge what you couldn't explain in the review. Accountability stays with the human (#525).

**Follow-up:** the agent's PR passes all checks and the tests it wrote itself. What's still missing? (A test the agent didn't write, a reviewer who understands the change, and a check that the tests test behaviour rather than the implementation.)
