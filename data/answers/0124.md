## Hints

- Which one is a read-only template and which one is a running process?
- Does a container ship its own operating system kernel?
- Why does a container start in milliseconds while a VM takes much longer?

## Answer

- **Image:** a read-only, layered template containing the filesystem (app code, runtime, libraries) plus metadata like the default command. Built from a Dockerfile and stored in a registry.
- **Container:** a running (or stopped) instance of an image. Docker adds a thin writable layer on top of the image layers; many containers can run from the same image. Think class vs object.
- **Virtual machine:** emulates whole hardware via a hypervisor, and each VM runs its **own full OS kernel**.

Containers share the host's kernel and are isolated using Linux namespaces (process, network, filesystem views) and cgroups (CPU/memory limits). As a result they:

- start in milliseconds, use megabytes rather than gigabytes,
- allow much higher density per host,
- but provide weaker isolation than VMs (a kernel exploit can affect all containers).

```bash
docker build -t myapp:1.0 .          # create an image
docker run -d --name web myapp:1.0   # start a container from it
docker ps                            # list running containers
```

In practice they're complementary: cloud providers run containers *inside* VMs, and tools like Firecracker or gVisor add VM-like isolation to containers.

**Follow-up:** "What happens to data written inside a container when it's removed?" — it's lost unless stored in a volume.
