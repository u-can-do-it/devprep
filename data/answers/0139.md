## Hints

- What does each letter of SOLID stand for?
- If adding a new payment method forces you to edit a big `switch` statement, which principle is violated?
- Why does depending on an interface instead of a concrete class make code easier to test?

## Answer

SOLID is a set of five object-oriented design principles that make code easier to change.

- **S — Single Responsibility:** a module should have one reason to change. Split an `InvoiceService` that calculates totals, renders PDFs, and sends emails.
- **O — Open/Closed:** open for extension, closed for modification. Add new behavior by adding code (a new strategy class), not by editing existing `if/else` chains.
- **L — Liskov Substitution:** subtypes must be usable wherever the base type is expected without surprises. A `ReadOnlyList` that throws on `add()` breaks callers expecting a `List`.
- **I — Interface Segregation:** prefer small, focused interfaces over one fat interface that forces implementers to stub unused methods.
- **D — Dependency Inversion:** high-level code depends on abstractions; concrete details are injected.

```ts
interface PaymentProvider { charge(amount: number): Promise<string>; }

class StripeProvider implements PaymentProvider { /* ... */ }
class PayPalProvider implements PaymentProvider { /* ... */ }

class CheckoutService {
  constructor(private payments: PaymentProvider) {} // D: injected abstraction
  pay(total: number) { return this.payments.charge(total); } // O: new provider = new class
}
```

Strong candidates also mention balance: applying SOLID dogmatically leads to over-abstraction. In functional or TypeScript codebases the same ideas appear as small functions, composition, and passing dependencies as parameters.
