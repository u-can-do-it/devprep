## Hints

- In InnoDB, what does a secondary index store to find the row, and what does that mean for a random UUID primary key?
- When PostgreSQL updates a row, what happens to the old version, and who cleans it up?
- Which isolation level is the default in each database, and what extra locks does InnoDB take under it?

## Answer

Both are MVCC relational databases with B-tree indexes, but they store rows and old versions differently, and that changes how you design tables and transactions.

| | **MySQL (InnoDB)** | **PostgreSQL** |
|---|---|---|
| Table storage | **clustered index**: rows live in the primary key B-tree, in PK order | **heap**: rows in no particular order; every index, PK included, points to a tuple location |
| Secondary index entry | the **primary key value** → a lookup walks two B-trees | a pointer to the heap tuple |
| `UPDATE` | in place; the old version goes to the **undo log** | writes a **new tuple version**; the old one stays in the table as a dead tuple |
| Cleanup | purge thread trims undo history | **VACUUM** / autovacuum removes dead tuples |
| Default isolation | **REPEATABLE READ** | **READ COMMITTED** |
| Phantom protection | **gap and next-key locks** on locking reads and writes | no gap locks; SERIALIZABLE uses non-blocking predicate locks (SSI) |
| DDL in a transaction | causes an implicit commit | **transactional DDL** (can be rolled back) |
| Connections | thread per connection | process per connection → use a pooler (PgBouncer, #338) |

**What it means in practice:**

- **Primary keys in InnoDB:** every secondary index carries the PK, and inserts land in PK order. A random UUIDv4 PK makes all indexes bigger and inserts scatter across pages (page splits, poor cache use). Prefer `BIGINT AUTO_INCREMENT` or a time-ordered id (UUIDv7, ULID) stored as `BINARY(16)`. A covering index (all needed columns in the index) avoids the second lookup.
- **Updates in PostgreSQL:** each update creates a new version and, unless it's a **HOT** update (no indexed column changed and there's room on the page), new entries in **every** index. Frequently updated rows on a heavily indexed table cause write amplification and **bloat**. Keep hot counters in narrow tables and watch autovacuum.
- **Long transactions hurt both:** in PostgreSQL they stop VACUUM from removing dead tuples (bloat, and in the extreme, transaction ID wraparound); in InnoDB the undo history list grows and reads slow down. Watch out for "idle in transaction" sessions and transactions that wait on HTTP calls.
- **Isolation surprises:** a plain `SELECT` in InnoDB under REPEATABLE READ reads from a snapshot, but `UPDATE` and `SELECT ... FOR UPDATE` see the **latest committed** row. PostgreSQL's REPEATABLE READ is snapshot isolation and aborts a concurrent update with a serialization error (`40001`) that your code must retry (#85).
- **InnoDB gap locks cause surprising deadlocks.** Under REPEATABLE READ a locking statement on a range or a non-unique index locks the matching index records **and the gaps between them**, so concurrent `INSERT`s into that range wait. Two transactions that each lock a gap and then insert into it deadlock. Without a usable index, an `UPDATE ... WHERE status = 'x'` locks every row it scans. Fixes: index the columns you filter on in locking statements, lock by unique key where possible, keep transactions short, consider READ COMMITTED (which mostly disables gap locking), and retry on deadlock (#337).
- **Diagnosing locks:** MySQL: `SHOW ENGINE INNODB STATUS` (latest detected deadlock), `innodb_print_all_deadlocks`, `performance_schema.data_locks`, `information_schema.innodb_trx`. PostgreSQL: `pg_locks` joined with `pg_stat_activity`, `log_lock_waits`, deadlock details in the server log.
- **Smaller gotchas:** MySQL's default collations are case- and accent-insensitive, so `'Anna' = 'anna'` and a unique index on `email` is case-insensitive; PostgreSQL compares case-sensitively (use `lower()` indexes or `citext`). In MySQL use `utf8mb4` (the old `utf8` is 3-byte and can't store emoji). PostgreSQL has partial indexes, exclusion constraints and richer types (`jsonb` with GIN, arrays, ranges). MySQL has functional and multi-valued JSON indexes but no partial indexes.

**Follow-up:** two transactions run `SELECT ... FOR UPDATE` on a doctor's free slots in a time range, then both `INSERT` an appointment, and MySQL reports a deadlock. Why, and what would you change? (Both hold next-key locks on the same gap, and each insert waits for the other's gap lock. Lock a specific row by unique key, rely on a unique constraint, or use a conditional `UPDATE` on a pre-created slot row instead, #552.)
