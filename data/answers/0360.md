## Hints

- Where does the source of truth for your types live in each approach?
- How do you keep SDL and resolver signatures in sync without a compiler noticing a mismatch?
- Which approach makes the schema easier for frontend teams to review in a pull request?

## Answer

**Schema-first (SDL-first):** write the schema in GraphQL SDL, then implement resolvers that match it.

```graphql
type Query { product(id: ID!): Product }
type Product { id: ID!, name: String!, price: Float! }
```

```ts
const resolvers: Resolvers = {           // types generated from the SDL
  Query: { product: (_, { id }, ctx) => ctx.db.product.find(id) },
};
```

- **Pro:** The schema is a readable **contract**; easy design reviews and parallel frontend/backend work.
- **Pro:** Language-agnostic; works well with federation and schema registries.
- **Con:** Two sources of truth – resolvers can drift from SDL. Mitigate with codegen (GraphQL Code Generator's resolver types) so TypeScript catches mismatches.
- Tools: Apollo Server, GraphQL Yoga with `graphql-tools`, gqlgen (Go), Ariadne (Python).

**Code-first:** define types in the programming language; the SDL is generated.

```ts
builder.objectType("Product", {
  fields: (t) => ({
    id: t.exposeID("id"),
    name: t.exposeString("name"),
    price: t.exposeFloat("price"),
  }),
});
```

- **Pro:** Single source of truth, full type inference, refactoring support; easy to build reusable abstractions (pagination helpers, auth plugins).
- **Con:** The schema is less visible – commit the generated `schema.graphql` and review its diff in CI.
- Tools: Pothos (TS), Grats (TS, from annotated functions), Nest.js code-first, Strawberry (Python dataclass-style), Hot Chocolate (.NET).

**How to choose:** schema-first suits API-design-led teams and polyglot services; code-first suits TypeScript/Python teams wanting maximum type safety with less glue. Either way: **generate types**, commit the printed schema, and run breaking-change checks (GraphQL Inspector, schema registry) in CI.
