## Hints

- What does the database have to do to serve `OFFSET 100000`?
- What happens to page 3 if a new row is inserted while the user is on page 2?
- Which approach lets a user jump directly to page 50?

## Answer

**Offset pagination** – `?page=3&limit=20` → `LIMIT 20 OFFSET 40`.

- Pros: simple, supports jumping to any page and showing total pages.
- Cons: the DB still scans and discards all skipped rows, so deep pages get slow. Results **shift** when rows are inserted/deleted, causing duplicates or skipped items.

**Cursor (keyset) pagination** – the client sends an opaque cursor pointing at the last item seen:

```sql
SELECT id, created_at, title
FROM posts
WHERE (created_at, id) < ($1, $2)   -- values from the cursor
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

- Pros: uses an index seek, so performance is constant at any depth; stable under concurrent writes.
- Cons: no random page access, harder to show "page 7 of 120", requires a unique, stable sort key (add `id` as a tie-breaker).

Response shape:

```json
{ "data": [ ... ], "next_cursor": "eyJjcmVhdGVkX2F0Ijoi..." }
```

Encode the cursor (e.g. base64 JSON) so clients treat it as opaque and you can change it later.

**When to use:**

- Offset: admin tables, small datasets, UIs that need page numbers.
- Cursor: infinite scroll, feeds, large or fast-changing tables, public APIs (GitHub, Stripe, GraphQL Relay connections all use cursors).

**Follow-up:** How do you support sorting by a non-unique column? (Composite key with `id`, and a matching composite index.)
