## Hints

- What's wrong with concatenating a user's search term directly into the query string?
- Why can't a mutation argument be an ordinary output type like `User`?
- What does the `!` mean on a variable definition?

## Answer

**Variables** keep the operation document static and pass dynamic values separately as JSON:

```graphql
mutation CreateOrder($input: CreateOrderInput!, $notify: Boolean = true) {
  createOrder(input: $input, notify: $notify) {
    order { id status total }
    errors { field message }
  }
}
```

```json
{
  "query": "mutation CreateOrder(...) { ... }",
  "variables": {
    "input": { "customerId": "42", "items": [{ "productId": "7", "quantity": 2 }] }
  }
}
```

- Declared with a type (`$input: CreateOrderInput!`); `!` means required; defaults are allowed.
- The server **validates** variable values against the schema before execution.

**Why not string interpolation:**

- **Injection** – user input could change the query structure (add fields, aliases, mutations).
- **Escaping bugs** with quotes and special characters.
- A static document can be **cached, parsed once, persisted/allow-listed** and type-checked by codegen; interpolated strings defeat all of that.

**Input types** are special object types used only for arguments:

```graphql
input CreateOrderInput {
  customerId: ID!
  items: [OrderItemInput!]!
  couponCode: String
}
input OrderItemInput { productId: ID!, quantity: Int! }
```

Output types can have arguments, resolvers, interfaces and cycles; input types can contain only scalars, enums and other input types, so they're always serializable from JSON. The common convention is **one `input` argument per mutation**, which is easy to evolve by adding optional fields. For "exactly one of these fields" inputs, `@oneOf` input objects are now supported by the spec and major servers.
