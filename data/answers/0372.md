## Hints

- What happens if your update endpoint does `user.update(req.body)` and the client adds `"role": "admin"`?
- Which fields should a client ever be able to set on a user record?
- How can your validation library help, rather than you filtering fields by hand?

## Answer

**Mass assignment** (also called auto-binding or over-posting) happens when a framework or ORM copies **all** fields from the request body onto a model. An attacker adds fields the UI never shows, such as `isAdmin`, `role`, `balance`, `ownerId` or `emailVerified`, and the server saves them.

```js
// Vulnerable
app.patch('/me', async (req, res) => {
  await db.user.update({ where: { id: req.user.id }, data: req.body });
});
```

Prevention:

- **Use explicit input schemas (DTOs) per operation**: one for "create", one for "update profile", one for admin actions. Only allow-listed fields get through.
- **Reject or strip unknown fields.** In Pydantic v2, `extra="forbid"` turns surprise fields into a 422; Zod objects strip unknown keys by default, and `z.strictObject()` rejects them.
- **Never bind directly to ORM entities** from request bodies; map validated DTOs onto models explicitly.
- **Keep sensitive fields on separate, authorized endpoints** (e.g. `POST /admin/users/{id}/role`).
- Do the same for **output**: use response models so you don't leak `password_hash` or internal flags (excessive data exposure).

```python
from pydantic import BaseModel, ConfigDict

class ProfileUpdate(BaseModel):
    model_config = ConfigDict(extra="forbid")
    display_name: str | None = None
    bio: str | None = None

@app.patch("/me")
async def update_me(body: ProfileUpdate, user=Depends(current_user)):
    await users.update(user.id, body.model_dump(exclude_unset=True))
```

**Follow-up:** Mass assignment is in the OWASP API Security Top 10 under "Broken Object Property Level Authorization", together with excessive data exposure.
