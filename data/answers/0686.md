## Hints

- When Jest renders a React Native component, is a phone or simulator involved?
- What happens in Jest when your code imports a module that calls native code?
- Which bugs can only an end-to-end test on a real build catch?

## Answer

> Use the same pyramid as on the web. Types and lint catch the cheap mistakes. Jest tests logic and hooks. React Native Testing Library tests screens the way a user uses them, but in Node, with native modules mocked. End-to-end tools (Maestro, Detox) drive a real build on a simulator or device, and cover what Jest can't: native code, navigation, the keyboard, permissions. Keep many fast component tests and a few end-to-end tests for the critical flows.

| Level | Tool | Runs on | Catches |
|---|---|---|---|
| Static | TypeScript, ESLint | your machine, CI | wrong props, typos, hook rules |
| Unit | Jest | Node | pure logic, reducers, formatters, hooks |
| Component / screen | Jest + React Native Testing Library | Node | rendering, interaction, states, a11y labels |
| End-to-end | Maestro, Detox | simulator, emulator, device | real builds: native modules, navigation, startup |
| Manual | people | real devices | feel, performance, odd devices |

**Component tests**

```tsx
test('shows an error for a wrong password', async () => {
  const user = userEvent.setup();
  render(<SignInScreen />, { wrapper: Providers });

  await user.type(screen.getByLabelText('Email'), 'a@b.co');
  await user.type(screen.getByLabelText('Password'), 'wrong-pass');
  await user.press(screen.getByRole('button', { name: 'Sign in' }));

  expect(await screen.findByText('Wrong email or password')).toBeOnTheScreen();
});
```

- The philosophy is the same as React Testing Library (#208): query by role, label and text, not by `testID` or implementation details.
- The preset is `jest-expo` or `react-native`. Nothing native runs: components render to a JS tree.
- Mock the network at the HTTP level with MSW (#461), not by mocking your own hooks.

**Mocking native modules**

Native code doesn't exist in Node, so anything that calls it must be mocked.

- Many libraries ship a Jest setup or mock (Reanimated, Safe Area Context, AsyncStorage, Gesture Handler). Add them to the Jest setup file.
- For the rest, `jest.mock('expo-camera', () => ...)`, or better, wrap the module in your own small function and mock that.
- A typical failure, "SyntaxError: Cannot use import statement", means a dependency isn't transpiled. Add it to `transformIgnorePatterns`.

**What Jest can't tell you**

Whether the layout looks right, whether a gesture works, whether the keyboard covers the button, whether the app starts, whether a native module is linked. Those need a real build.

**End-to-end**

Maestro flows are YAML and treat the app as a black box:

```yaml
appId: com.example.shop
---
- launchApp
- tapOn: "Email"
- inputText: "a@b.co"
- tapOn: "Password"
- inputText: "correct-pass"
- tapOn: "Sign in"
- assertVisible: "Your orders"
```

- **Maestro:** quick to write, tolerant of timing, works with any app.
- **Detox:** tests in JavaScript, grey-box. It knows when the app is idle, so it waits correctly, at the cost of more setup.
- Run against a release-like build and a seeded test backend. Cover login, the main purchase or booking flow, and anything that has broken before.
- CI: Android emulators run on Linux runners, iOS simulators need macOS. Device clouds add real devices.

**What I test where**

- Business rules and formatting: unit tests.
- Each screen's states (loading, empty, error, success) and form validation: component tests.
- "A user can sign in and place an order": two or three end-to-end flows.
- Before a release: a manual pass on a real low-end Android phone and an iPhone.

**Follow-up:** your end-to-end tests fail randomly about one run in ten. What do you do? (Find out why before adding retries: wait for visible elements instead of sleeping, make the backend data deterministic, disable animations, and isolate tests from each other.)
