## Hints

- Where does the session live by default when you don't configure a database adapter?
- Which callback runs first, `jwt` or `session`, and which one decides what the browser can see?
- How do you read the session in a Server Component, a Route Handler, `proxy.ts` and a Client Component?
- What did `getServerSession(authOptions)` become in v5, and why did existing users get logged out after the upgrade?

## Answer

> NextAuth.js, renamed Auth.js in v5, handles sign-in with OAuth providers, CSRF protection and the session cookie in Next.js. By default the session is an encrypted JWT in an HttpOnly cookie, or a database row when you use an adapter. The `jwt` callback puts data like roles into the token, and the `session` callback decides what the browser can see, so expose only what the UI needs. v5 replaces `getServerSession` with one `auth()` function. Always check the session next to the data, not just in middleware.

NextAuth.js (renamed **Auth.js** from v5) is the de facto auth library for Next.js. It handles the OAuth/OIDC dance, sign-in pages, CSRF protection and the session cookie, and gives you hooks to shape the session. In September 2025 the project joined Better Auth: Auth.js is still maintained (security fixes), but new greenfield projects are pointed to Better Auth. Existing apps, like most enterprise self-service portals, run v4 or v5.

**Building blocks**

- **Providers**: OAuth/OIDC (Keycloak, Entra ID, Google, GitHub…), `Credentials` (your own login form) and email magic links.
- **Session strategy**:
  - `jwt` (default without an adapter): the session is an **encrypted JWT (JWE) in an HttpOnly cookie**. Stateless, no database, scales across replicas as long as they share the secret. Can't be revoked before it expires.
  - `database` (default with an adapter such as Prisma): the cookie holds only a session ID; the session row can be deleted to log someone out. `Credentials` works only with `jwt` by default.
- **Callbacks** run in this order:
  - `signIn` – allow or deny (e.g. only users from one domain).
  - `jwt({ token, user, account, profile, trigger })` – runs at sign-in (`account` and `user` are set only then) and every time the session is read. Put tokens and roles **into the JWT** here.
  - `session({ session, token })` – builds what `auth()`, `useSession()` and `/api/auth/session` return. **Expose only what the UI needs**: everything here is readable from the browser.
  - `redirect` – restrict where the user can be sent after sign-in.

**v5 (Auth.js) setup in the App Router**

```ts
// auth.ts
import NextAuth from 'next-auth';
import Keycloak from 'next-auth/providers/keycloak';

export const { handlers, auth, signIn, signOut } = NextAuth({
  providers: [Keycloak],                  // reads AUTH_KEYCLOAK_ID / _SECRET / _ISSUER
  session: { strategy: 'jwt', maxAge: 8 * 60 * 60 },
  callbacks: {
    jwt({ token, profile }) {
      if (profile) token.roles = (profile as any).realm_access?.roles ?? [];
      return token;
    },
    session({ session, token }) {
      session.user.roles = token.roles as string[];
      return session;
    },
  },
});

// app/api/auth/[...nextauth]/route.ts
import { handlers } from '@/auth';
export const { GET, POST } = handlers;
```

Reading the session:

| Where | v5 | v4 |
|---|---|---|
| Server Component, Route Handler, Server Action | `await auth()` | `await getServerSession(authOptions)` |
| `getServerSideProps` / API route (Pages) | `await auth(req, res)` | `getServerSession(req, res, authOptions)` |
| `proxy.ts` / `middleware.ts` | `export default auth((req) => …)`, `req.auth` | `withAuth` from `next-auth/middleware` |
| Client Component | `useSession()` inside `<SessionProvider>` | same |

**Protecting routes:** an optimistic redirect in `proxy.ts` (cookie present?) for UX, plus the **real check** next to the data: `auth()` in every page, Server Action and Route Handler that touches data, and authorization on the backend (#245). Hiding buttons with `useSession()` is UX, not security.

**v4 → v5 differences worth knowing**

- One `auth.ts` exporting `auth`, `handlers`, `signIn`, `signOut` instead of `authOptions` passed around.
- `getServerSession`, `getSession`, `withAuth` → `auth()` everywhere.
- Env vars: `NEXTAUTH_SECRET`/`NEXTAUTH_URL` → `AUTH_SECRET`/`AUTH_URL` (the URL is usually inferred), provider credentials auto-read from `AUTH_<PROVIDER>_ID`, and `AUTH_TRUST_HOST` when self-hosting behind a proxy.
- Cookie prefix `next-auth.` → `authjs.`, so **everyone is logged out once** after the upgrade.
- Edge-compatible core; adapters moved to `@auth/*-adapter`.
- v5 stayed a long-running beta, so many production apps are still on v4. Check `package.json` first.

**Follow-up:** "Why not put the access token straight into the session?" Because `useSession()` and `/api/auth/session` hand it to JavaScript in the browser, so an XSS can steal it. Keep it in the encrypted JWT and call APIs from the server (#632).
