## Hints

- Where does Node look when you `require('lodash')` versus `require('./utils')`?
- If two files require the same module, does its top-level code run twice?
- What does a `"exports"` field in a dependency's `package.json` change?

## Answer

**Resolution** for `require(X)` from a file in directory `D`:

1. **Built-in modules** first: `fs`, `http`, or explicitly `node:fs`. The `node:` prefix can never be shadowed by an npm package.
2. **Relative or absolute paths** (`./`, `../`, `/`): try the exact file, then `.js`, `.json`, `.node`. If it's a directory, use `package.json` `"main"` or fall back to `index.js`.
3. **Bare names** (`lodash`): look in `D/node_modules`, then each parent's `node_modules` up to the root. Inside the package, the `"exports"` field (if present) decides which entry points exist. Unlisted subpaths throw `ERR_PACKAGE_PATH_NOT_EXPORTED`. Otherwise `"main"` is used.

`require.resolve('x')` shows the resolved path without loading it.

**Caching**: after the first load, the module object is stored in `require.cache` keyed by its **resolved absolute filename**. Later `require` calls return the same `module.exports` without running the code again.

```js
// counter.js
let n = 0;
module.exports = { inc: () => ++n };

// a.js and b.js both require('./counter') -> they share one n
```

Consequences:

- Modules behave like **singletons**. That's handy for a DB pool and dangerous for hidden global state in tests.
- Two different resolved paths (e.g. two copies of a package in nested `node_modules`) mean two instances. That's a common cause of `instanceof` failures.
- Deleting from `require.cache` forces a reload, but it's a hack mostly used by old hot-reload tools.
- Each module is wrapped in a function `(exports, require, module, __filename, __dirname)`, which is where those "globals" come from.
