## Hints

- Does `fetch` reject when the server returns 404 or 500?
- The user types fast in a search box. What happens when responses arrive out of order?
- How do you know at runtime that the API actually returned what your TypeScript type says?

## Answer

Don't call `fetch` from components. Put a thin **API layer** between the UI and the network, and a **server-state cache** on top of it.

**1. A small HTTP client** that centralises the base URL, auth, JSON and errors:

```ts
export class ApiError extends Error {
  constructor(public status: number, public body: unknown) { super(`HTTP ${status}`); }
}

export async function http<T>(path: string, init: RequestInit & { schema?: z.ZodType<T> } = {}): Promise<T> {
  const res = await fetch(`${API_URL}${path}`, {
    ...init,
    headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${getToken()}`, ...init.headers },
  });
  if (!res.ok) throw new ApiError(res.status, await res.json().catch(() => null));   // fetch doesn't reject on 4xx/5xx
  const data = res.status === 204 ? undefined : await res.json();
  return init.schema ? init.schema.parse(data) : (data as T);
}
```

**2. Types that match reality**

- **Generate types and clients from the OpenAPI spec** (`openapi-typescript` with `openapi-fetch`, Orval, Hey API), so a backend change shows up as a compile error instead of a production bug.
- **Validate at the boundary** (Zod, Valibot) where data is critical or the API is outside your control. TypeScript types are erased at runtime.
- **Map DTOs to UI models** in the API layer (dates as `Date`, `snake_case` → `camelCase`) so components don't depend on the wire format.

**3. Caching and request state with TanStack Query, RTK Query or SWR:** loading, error and empty states, deduplication, caching, background refetching, retries and invalidation after mutations, without hand-written `useEffect` fetching.

**4. Cancellation and race conditions:** pass an `AbortSignal` (query libraries pass one for you) so unmounting or a new search cancels the old request. Otherwise a slow, stale response can overwrite a newer one. Debounce search input.

**5. Errors and retries**

- Retry **network errors and 5xx/429** with exponential backoff, and only for **idempotent** requests (GET, PUT, DELETE, or POST with an idempotency key).
- Show useful messages: field errors from a 400/422 next to the inputs, "not found" for 404, "you don't have access" for 403.
- **401:** refresh the token once (single-flight: concurrent requests wait for the same refresh), then retry, or redirect to login.

**6. UX:** skeletons instead of spinners for page loads, optimistic updates with rollback for quick actions, disabling double submits, and keeping previous data visible while the next page loads.

**Follow-up:** five components on a page need the current user. How do you make sure there's only one request?
