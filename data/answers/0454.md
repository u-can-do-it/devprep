## Hints

- Who uses the library, and what happens to them when you rename a prop?
- How does a consumer change a button's colour for a dark theme without editing the button's code?
- Where would a designer, a developer and a QA engineer look to see every state of a component?

## Answer

A component library is a **product whose users are other developers**. The hard parts are API design, theming, documentation and releases, not the JSX.

**1. API design**

- **Consistent, predictable props** across components: `size="sm|md|lg"`, `variant="primary|secondary|ghost"`, `disabled`, `onChange(value)`. Names that describe *intent*, not appearance (`variant="danger"`, not `red`).
- **Extend native props** so consumers can pass `aria-*`, `data-*`, `type` and handlers, and forward `ref` (a regular prop in React 19):

```tsx
type ButtonProps = React.ComponentPropsWithRef<'button'> & {
  variant?: 'primary' | 'secondary' | 'ghost';
  size?: 'sm' | 'md';
};

export function Button({ variant = 'primary', size = 'md', className, ...rest }: ButtonProps) {
  return <button className={cn(button({ variant, size }), className)} {...rest} />;
}
```

- **Composition over configuration:** a `<Select>` with 30 props becomes compound components (`<Select.Trigger>`, `<Select.Item>`) or `asChild` slots.
- Support **controlled and uncontrolled** use (`value`/`defaultValue`/`onValueChange`).
- **Accessibility built in:** keyboard support, focus management and ARIA come with the component, so every team gets them for free.

**2. Theming:** components read **design tokens** as CSS custom properties (`var(--color-bg-primary)`), never hard-coded hex values. A theme or brand swaps the token values (`[data-theme="dark"]`) without touching components.

**3. Documentation and testing with Storybook**

- A story per state (default, hover, disabled, loading, error, long text, RTL), which also serves as the visual spec for design review.
- Interaction tests (`play` functions), accessibility checks (axe addon) and **visual regression** tests (Chromatic, Playwright screenshots) catch unintended changes.
- Link stories to the Figma components (Code Connect, design addon) so both sides use the same names.

**4. Packaging and versioning**

- Publish as a package (internal npm registry or a monorepo workspace), ship ESM with types, mark `"sideEffects": ["*.css"]` so unused components tree-shake, and keep React as a **peer dependency**.
- **Semantic versioning** with Changesets: a breaking prop change is a major release, with a migration note and ideally a codemod. Deprecate first (console warning in dev, `@deprecated` JSDoc), remove later.

**5. Governance:** a contribution process, an owner team, adoption metrics, and a rule for when a product team may build a one-off component instead of extending the library.
