## Hints

- What happens if a client asks for `friends { friends { friends { ... } } }` 20 levels deep?
- Why is counting requests per minute not enough for GraphQL?
- Should production clients be able to explore your entire schema?

## Answer

Because clients compose queries freely, one request can be enormously expensive. Defenses work in layers:

**1. Limit query shape**

- **Max depth** (e.g. 8–10) to block deeply nested cyclic queries.
- **Max aliases / fields / tokens** – aliases can repeat an expensive field 1000 times in one query.
- **Pagination limits** – require `first`/`last` arguments with a max (e.g. 100).

**2. Query cost analysis**

Assign a cost to each field (lists multiply by their `first` argument) and reject queries above a budget before execution. Rate-limit by **cost points** per client rather than request count (GitHub's API does this).

```graphql
query {
  users(first: 100) {         # 100
    posts(first: 50) {        # 100 * 50 = 5000 -> over budget
      title
    }
  }
}
```

**3. Persisted / trusted documents**

For first-party apps, allow only queries registered at build time (by hash). This eliminates arbitrary queries entirely and is the strongest control.

**4. Introspection and errors**

- Disable introspection in production for private APIs (it's not a security boundary on its own, but reduces reconnaissance).
- Disable field "did you mean" suggestions, and mask internal error messages.

**5. Classic API security still applies**

- **Authorization per field/resolver** (or in the business layer) – not just at the endpoint, since one endpoint serves everything.
- Timeouts, batching limits (array of operations in one HTTP request), input validation, CSRF protection if cookies are used (require `Content-Type: application/json` or a custom header, block `GET` mutations).
