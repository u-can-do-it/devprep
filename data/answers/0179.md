## Hints

- Does `readonly` produce any runtime check in the emitted JavaScript?
- Is `Readonly<T>` deep or shallow?
- Why would a function take `readonly string[]` instead of `string[]`?

## Answer

TypeScript has several **compile-time** tools for immutability:

- **`readonly` modifier** on properties: they can be assigned only at declaration or in the constructor.
- **`Readonly<T>`**: a mapped type that makes all top-level properties readonly.
- **`readonly T[]`** / **`ReadonlyArray<T>`**: removes mutating methods (`push`, `sort`, `splice`) from the type. `ReadonlyMap` and `ReadonlySet` do the same for collections.
- **`as const`**: deeply readonly literal types.

```ts
interface User { readonly id: string; name: string }
const u: User = { id: '1', name: 'Ann' };
// u.id = '2';  // error

function total(prices: readonly number[]) {
  // prices.push(1);  // error: this function promises not to mutate its input
  return prices.reduce((a, b) => a + b, 0);
}

type Frozen = Readonly<{ tags: string[] }>;
declare const f: Frozen;
// f.tags = [];     // error
f.tags.push('x');   // allowed: Readonly is shallow
```

**Compared with `Object.freeze`:**

| | TS `readonly` | `Object.freeze` |
|---|---|---|
| When checked | compile time only, erased | at runtime |
| Depth | shallow (`Readonly<T>`) | shallow |
| Cost | none | small runtime call |
| Protects against JS callers / `any` | no | yes |

`Object.freeze(obj)` returns `Readonly<T>`, so you get both kinds of protection.

**Gotchas:**

- Readonly isn't fully sound. An object with a readonly property can be assigned to a type where the same property is mutable, and then changed through that alias.
- `readonly string[]` isn't assignable to `string[]`. Mark your parameters readonly so callers can pass either.
- Deep immutability needs a recursive `DeepReadonly<T>` type or `as const`.
