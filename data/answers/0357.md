## Hints

- What should happen when a customer's endpoint is down for six hours?
- How does a receiver verify that a webhook really came from you and isn't a replay?
- Can you guarantee exactly-once, in-order delivery over HTTP, and if not, what do you promise instead?

## Answer

**Requirements:** at-least-once delivery, retries with backoff, authenticity, observability, isolation between customers, and no impact on the core request path.

**Architecture:**

1. **Capture events reliably** – the business transaction writes an event to an **outbox** table in the same DB transaction; a relay publishes it to a queue/stream. No "commit then hope the HTTP call works".
2. **Fan-out** – a dispatcher looks up subscriptions (endpoint URL, event types, secret) and creates one **delivery** record per endpoint.
3. **Delivery workers** POST the payload with a short timeout (e.g. 10 s). `2xx` = success; anything else = retry.
4. **Retries** with exponential backoff + jitter over a long window (e.g. ~3 days); after that, mark failed, alert the customer, and **auto-disable** endpoints failing persistently.
5. **Isolation** – per-endpoint queues or concurrency limits so one slow customer doesn't block everyone (avoid head-of-line blocking).
6. **Self-service** – dashboard of attempts with request/response, manual **replay**, and an API to list missed events.

**Payload and headers** (the Standard Webhooks spec is a good reference):

```http
POST /hooks/acme HTTP/1.1
Content-Type: application/json
webhook-id: msg_2Kt8...
webhook-timestamp: 1791100800
webhook-signature: v1,K5oZfzN95Z9UVu1EsfQmfVNQhnkZ2pj9o9NDN/H/pI4=

{ "type": "invoice.paid", "data": { "id": "inv_123", "amount": 4200 } }
```

- **Signature:** HMAC-SHA256 over `id.timestamp.body` with a per-endpoint secret; receivers verify with a constant-time compare and reject old timestamps (replay protection). Support **secret rotation** with two active secrets.
- **Thin vs fat payloads:** sending only ids ("invoice.paid, id=inv_123") forces a fetch of current state – avoids stale or out-of-order data issues and leaks less.

**Contract for receivers:** delivery is **at least once and not ordered** – dedupe by `webhook-id`, use timestamps/versions to ignore stale updates, respond `2xx` fast and process asynchronously.

**Security on the sender side:** customer URLs are untrusted → **SSRF protection** (block private IP ranges after DNS resolution, egress through a dedicated proxy), HTTPS only, cap response sizes.

**Follow-up:** How would you migrate customers to a new payload version without breaking them?
