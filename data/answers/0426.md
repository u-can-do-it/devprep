## Hints

- Do your reads and writes really need the same data model, scaling and storage?
- What if, instead of storing the current balance, you stored every deposit and withdrawal?
- How do you change an event's schema once millions of them are stored and immutable?

## Answer

> In some systems, the way data is written and the way it's read are very different. CQRS separates them: commands go to a write model that enforces business rules, and queries read from views built for specific screens. Event sourcing stores every change as an immutable event and rebuilds current state by replaying them, which gives a full history. Both add real complexity, like eventual consistency and evolving event formats, so use them only where history or very different loads matter, not for CRUD apps.

**CQRS (Command Query Responsibility Segregation)** separates the **write model** (commands that change state and enforce business rules) from the **read model** (queries optimized for display).
- Writes go to a normalized model or aggregate that validates invariants.
- Reads come from one or more **projections**: denormalized views, search indexes, caches, built for specific screens.
- They can share a database (logical CQRS) or use separate stores updated asynchronously, which brings **eventual consistency** between write and read.

**Event sourcing** stores **state changes as an immutable, append-only sequence of events** (`OrderPlaced`, `ItemAdded`, `OrderShipped`) instead of only the current state. Current state is derived by replaying events, using snapshots for speed.

```ts
function apply(state: Account, e: AccountEvent): Account {
  switch (e.type) {
    case "Deposited": return { ...state, balance: state.balance + e.amount };
    case "Withdrawn": return { ...state, balance: state.balance - e.amount };
  }
}
const account = events.reduce(apply, { balance: 0 });
```

The two fit together naturally: events from the write side feed the read-side projections. But each can be used alone.

**Benefits:**
- full **audit trail** and history (finance, compliance), and "time travel" debugging,
- new read models can be built later by replaying history,
- reads and writes scale independently, and read models fit their use cases,
- natural integration with event-driven systems.

**Costs:**
- eventual consistency in the UI ("I saved it but don't see it yet"),
- **event schema evolution** (upcasting, versioned events), and correcting mistakes with compensating events instead of updates,
- rebuilding projections, snapshots, idempotent handlers, ordering per aggregate,
- GDPR "right to be forgotten" with immutable logs (crypto-shredding),
- a steep learning curve and many more moving parts.

**When it's worth it:** complex, collaborative domains where history matters (ledgers, bookings, logistics), or very different read and write loads. **Not** for CRUD apps. Applying it system-wide "because microservices" is a classic over-engineering mistake. Use it per bounded context.
