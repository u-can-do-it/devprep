## Hints

- What is the difference between data that is *stale* and data that has been *garbage collected*?
- Two components mount at the same time and ask for the same user. How many requests go out?
- What has to happen in `onMutate`, `onError` and `onSettled` for an optimistic update to be safe?

## Answer

TanStack Query is a **cache keyed by query keys** plus rules for when to refetch (#212). Knowing the rules is what separates "I used it" from "I understand it".

**Query keys** are arrays, hashed deterministically (object key order doesn't matter). Make them hierarchical and include **every input** the fetcher uses, otherwise two different requests share one cache entry:

```ts
['todos']                                  // all todo lists
['todos', { status: 'done', page: 2 }]     // one filtered page
['todos', 'detail', id]
```

Keep keys in a factory (`todoKeys.detail(id)`) so invalidation can target a prefix.

**Freshness: `staleTime` vs `gcTime`.**

- `staleTime` (default `0`): how long data is considered fresh. Fresh data is served from cache with **no** request. Stale data is still shown immediately, but a background refetch is triggered on mount, window focus, reconnect or `refetchInterval`.
- `gcTime` (default 5 minutes, formerly `cacheTime`): how long an **unused** query stays in memory after its last observer unmounts. After that it is deleted and the next mount shows a loading state.

Setting `staleTime: 60_000` for rarely changing data removes most "why does it refetch on every tab switch" surprises.

**Deduplication:** concurrent `useQuery` calls with the same key share one in-flight request. The same mechanism makes prefetching cheap: `queryClient.prefetchQuery` on hover, then the page mounts with data already present.

**Invalidation:** after a mutation, `invalidateQueries({ queryKey: ['todos'] })` marks every query with that prefix stale and refetches the **active** ones. `setQueryData` writes the cache directly when the mutation response already contains the new entity, saving a round trip. `removeQueries` deletes.

**Optimistic update, the safe way:**

```ts
const toggle = useMutation({
  mutationFn: (todo: Todo) => api.patch(`/todos/${todo.id}`, { done: !todo.done }),
  onMutate: async (todo) => {
    await qc.cancelQueries({ queryKey: ['todos'] });              // 1. stop refetches from overwriting us
    const previous = qc.getQueryData<Todo[]>(['todos']);          // 2. snapshot
    qc.setQueryData<Todo[]>(['todos'], (old) =>                   // 3. write optimistic value
      old?.map((t) => (t.id === todo.id ? { ...t, done: !t.done } : t)));
    return { previous };
  },
  onError: (_err, _todo, ctx) => qc.setQueryData(['todos'], ctx?.previous),   // 4. roll back
  onSettled: () => qc.invalidateQueries({ queryKey: ['todos'] }),              // 5. sync with server
});
```

Skipping step 1 is the classic bug: an in-flight refetch lands after your optimistic write and reverts it. In React 19 projects, `useOptimistic` (#39) covers the simple "pending state in one component" case; the mutation pattern above is for shared cache state.

**Other knobs worth knowing:** `enabled: !!userId` for dependent queries; `select` to derive or slice data without re-rendering on unrelated changes; `placeholderData: keepPreviousData` to avoid flashing while paginating (#95); `useInfiniteQuery` with `getNextPageParam` for cursor pagination (#539); `useSuspenseQuery` to use Suspense boundaries; `retry` defaults to 3 with exponential backoff, which you usually turn off for 4xx errors; `networkMode` for offline behaviour; `queryClient.setDefaultOptions` to set `staleTime` globally.

**Pitfalls:** a key missing an input (filters) shows the wrong data; mutations with no invalidation leave stale lists; using the query cache as a global client-state store (use #529 for that); calling `useQuery` in a loop instead of `useQueries`; and in SSR, creating one `QueryClient` at module scope shared by all requests (#244).
