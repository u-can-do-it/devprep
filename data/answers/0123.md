## Hints

- How many full copies of the production environment does each strategy need?
- How quickly can you roll back if the new version is broken?
- Is "deploying code" the same thing as "releasing a feature to users"?

## Answer

**Blue-green:** run two identical environments. Blue serves traffic; deploy to green, test it, then switch the router/load balancer. Rollback = switch back instantly. Cost: double infrastructure, and database schema changes must be compatible with both versions.

**Canary:** release the new version to a small share of traffic (1% → 10% → 50% → 100%), watching error rates and latency at each step. Limits blast radius and catches issues that only appear with real traffic. Needs good observability and ideally automated rollback.

**Rolling:** replace instances gradually (e.g. Kubernetes' default `RollingUpdate`). No extra environment needed, but old and new versions run side by side for a while, and rollback is another rolling update — slower.

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }
```

**Feature flags** decouple *deploy* from *release*. Code ships to production switched off, then is enabled per user, per percentage, or per tenant — without redeploying. They enable trunk-based development, A/B tests, and an instant kill switch. Downsides: extra code paths to test and **flag debt** — remove flags once a rollout is finished.

**Follow-up:** "How do you handle a DB migration during these deployments?" — expand/contract migrations so both versions work against the schema.
