## Hints

- When a field becomes invalid, how does a screen reader user find out, and which field it was?
- Why might adding an `aria-live` region at the same moment you insert the message not get announced?
- Is it better to show errors on every keystroke, on blur, or on submit?

## Answer

**Field-level errors**

```html
<label for="email">Email</label>
<input id="email" type="email" autocomplete="email"
       aria-invalid="true" aria-describedby="email-hint email-error">
<p id="email-hint">We'll send the receipt here.</p>
<p id="email-error" class="error">
  <svg aria-hidden="true">...</svg> Enter an email address like name@example.com
</p>
```

- **`aria-invalid="true"`** marks the field invalid. Set it only after validation, not on an empty form.
- **`aria-describedby`** links the message, so it's read when the field is focused. (`aria-errormessage` exists, but screen reader support is weaker.)
- Message text should say **what's wrong and how to fix it**, not just "Invalid".
- **Don't rely on color alone.** Add an icon or text, and keep the label visible.

**On submit**

- Move focus to the **first invalid field**, or to an **error summary** at the top. A summary has a heading such as "2 errors" and links to each field. This is best for long forms.
- Update `document.title` ("Error: Checkout") so the change is obvious.
- Validate on **blur or submit**, not on every keystroke. Announcing errors while the user is still typing is noisy. Use `:user-invalid` for styling that waits for interaction.

**Live regions for dynamic updates** (toasts, "Saved", search result counts, async validation):

```html
<!-- present in the DOM from the start, initially empty -->
<div role="status" aria-live="polite" class="sr-only" id="announcer"></div>
```

```js
announcer.textContent = '12 results found';
```

- **`polite`** (`role="status"`) waits until the screen reader finishes speaking. Use it for most updates.
- **`assertive`** (`role="alert"`) interrupts. Keep it for urgent, time-sensitive errors.
- The region **must exist before** its content changes. Inserting a new element that already contains text often isn't announced. Changing the text of an existing region is.
- Keep messages short and don't announce every small change. Clear and re-set the text to repeat an identical message.

**In React:** keep one app-level announcer (or use React Aria's `announce`) instead of scattering live regions around. With React 19 Actions, announce `useActionState` errors through it and set focus once the server response arrives.

**Follow-up:** test with real screen readers. Live region behavior differs a lot between NVDA, JAWS and VoiceOver.
