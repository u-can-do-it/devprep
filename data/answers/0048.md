## Hints

- Which attributes can you put on an `<input>` to make the browser check it for you?
- How would you style an invalid field or show a custom message?
- Who controls the code running in the browser — you or the user?

## Answer

HTML has **constraint validation** built in. Use the right input `type` and attributes and the browser blocks submission and shows a message:

```html
<form>
  <input type="email" name="email" required>
  <input type="password" name="pw" minlength="12" required>
  <input type="text" name="zip" pattern="[0-9]{5}" title="5 digits">
  <input type="number" name="age" min="18" max="120">
  <button>Sign up</button>
</form>
```

Useful pieces:

- Attributes: `required`, `type` (`email`, `url`, `number`, `date`), `min`/`max`, `minlength`/`maxlength`, `pattern`, `step`.
- CSS: `:invalid`, `:valid`, and **`:user-invalid`** (only after the user has interacted — avoids red fields on page load).
- JS API: `input.validity`, `form.checkValidity()`, `reportValidity()`, and `setCustomValidity('message')` for custom rules (e.g. "passwords must match").
- `novalidate` on the form disables native UI when you render your own errors.
- Correct `type`, `autocomplete` and `inputmode` also give better mobile keyboards and autofill.

**Why you still need server-side validation:** client validation is a **UX feature, not a security control**. Anyone can disable JS, edit the DOM in DevTools, or send a request directly with `curl`. The server must re-validate everything — types, lengths, formats, business rules and authorization — using a schema validator (Zod, Pydantic). Sharing one schema between client and server avoids drift.

**Follow-up:** for accessible errors, link the message with `aria-describedby`, set `aria-invalid="true"`, and move focus to the first invalid field on submit.
