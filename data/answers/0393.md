## Hints

- What question does each type of test answer: "is it fast enough?", "where does it break?", "does it survive a spike?", "does it degrade over hours?"
- Why is the average response time a misleading metric?
- What environment and data would make your results meaningful?

## Answer

Performance tests answer different questions:

- **Load test**: expected production traffic (e.g. peak hour). Do we meet our SLOs?
- **Stress test**: push beyond expected load until something breaks. Where's the limit, which component fails first, and does it fail gracefully (429/503) rather than corrupting data?
- **Spike test**: sudden jump (0 to 10× in seconds), like a marketing push. Do autoscaling, queues and rate limiting react in time?
- **Soak (endurance) test**: moderate load for hours. Finds memory leaks, connection pool exhaustion, growing queues, log or disk fill-up.

**Example with k6** (JS/TS scripts, run from CLI or CI):

```js
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [
    { duration: '2m', target: 200 },  // ramp up to 200 virtual users
    { duration: '10m', target: 200 }, // hold
    { duration: '2m', target: 0 },
  ],
  thresholds: {
    http_req_failed: ['rate<0.01'],
    http_req_duration: ['p(95)<300', 'p(99)<800'],
  },
};

export default function () {
  const res = http.get(`${__ENV.BASE_URL}/api/products?page=1`);
  check(res, { 'status 200': (r) => r.status === 200 });
  sleep(1);
}
```

Thresholds make the run **fail** if SLOs are missed, so it can gate CI. Alternatives: Locust (Python), Gatling, Artillery.

**Doing it well:**

- Model **realistic scenarios**: a mix of endpoints, think time, realistic data volumes (a query fast on 1,000 rows may be slow on 10 million).
- Watch **percentiles (p95/p99) and error rate**, not averages. Measure throughput (RPS) too.
- Test in a **production-like environment**, and monitor the system under test (CPU, DB connections, GC, queue depth) to find the bottleneck, not only the client-side numbers.
- Make sure the load generator itself isn't the bottleneck; use distributed runners for big loads.
- Run a smaller version regularly to catch regressions, not just once before launch.

**Follow-up:** Open vs closed models: fixed virtual users slow down when the system slows (hiding problems); arrival-rate executors keep sending requests at a fixed rate.
