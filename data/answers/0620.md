## Hints

- What is the difference between `prisma migrate dev`, `prisma migrate deploy` and `prisma db push`, and which one runs in production?
- How do you make two writes atomic with Prisma, and what goes wrong if you call an external API inside the transaction?
- `$queryRaw` and `$queryRawUnsafe` both run SQL. Which one is safe with user input, and why?
- What does Prisma return for a `Decimal` column, and what do you see after it goes through `JSON.stringify`?

## Answer

> Prisma makes database code typed and simple, but using it well takes a few habits. Use `migrate dev` only in development and `migrate deploy` in CI/CD, and review the generated SQL, because a rename can come out as drop and add. Inside `$transaction`, use `tx` and keep the transaction short. `$queryRaw` with a tagged template is parameterized, while `$queryRawUnsafe` with string building allows injection. Map `P2002` to 409, and keep one `PrismaClient` per process.

#487 covers *choosing* Prisma. This is about using it well day to day.

**Schema and relations:**

```prisma
model Offer {
  id         String      @id @default(uuid()) @db.Uuid
  number     String      @unique
  status     OfferStatus @default(DRAFT)
  total      Decimal     @db.Decimal(12, 2)
  ownerId    String      @db.Uuid
  owner      User        @relation(fields: [ownerId], references: [id])
  items      OfferItem[]
  version    Int         @default(0)
  createdAt  DateTime    @default(now()) @db.Timestamptz(3)
  updatedAt  DateTime    @updatedAt @db.Timestamptz(3)
  deletedAt  DateTime?   @db.Timestamptz(3)

  @@index([ownerId, status])
}
enum OfferStatus { DRAFT SUBMITTED APPROVED REJECTED }
```

Prisma does **not** create indexes on foreign keys for PostgreSQL by itself; add `@@index` for columns you filter or join on (#84).

**Migrations:**

- `prisma migrate dev`: development only. Diffs the schema against the migration history, writes a new SQL migration, applies it, regenerates the client. It may offer to **reset** the database when it detects drift.
- `prisma migrate dev --create-only`: generate the SQL and edit it before applying (data backfills, `CREATE INDEX CONCURRENTLY`, renaming a column instead of drop + add).
- `prisma migrate deploy`: applies pending migrations, never generates or resets. This is what CI/CD runs before (or as a step of) the deploy.
- `prisma db push`: syncs the schema without migration files. Prototyping only.
- Destructive changes need expand/contract (#340): add the new column, backfill, switch the code, drop the old one later.

**Queries:**

- `select` only what you need; `include` loads relations. Returning a model straight to the client leaks internal fields (#372).
- Watch for N+1 (#86): a loop that calls `findUnique` per row. Use `include`, `where: { id: { in: ids } }`, or a single `findMany`. Turn on query logging (`log: ['query']`) in dev.
- Pagination: `take` + `cursor` + `skip: 1` for cursor pagination (#95).
- Upserts and unique constraints: catch `Prisma.PrismaClientKnownRequestError` with code `P2002` (unique violation) and map it to 409; `P2025` (record to update not found) to 404.

**Transactions:**

```ts
// interactive: all queries on `tx` run in one DB transaction
await prisma.$transaction(async (tx) => {
  const offer = await tx.offer.update({
    where: { id, version },                  // optimistic concurrency (#337): fails with P2025 if someone else changed it
    data: { status: 'APPROVED', version: { increment: 1 } },
  });
  await tx.auditLog.create({ data: { entity: 'offer', entityId: id, action: 'approve', userId } });
}, { isolationLevel: 'Serializable', timeout: 10_000 });
```

- Use `tx`, not `prisma`, inside the callback, or the query runs outside the transaction.
- Keep it short: no emails, no HTTP calls, no waiting for users inside it. It holds a connection and locks; the default timeout is 5 s. Send side effects after commit or through an outbox (#484).
- For a fixed list of independent writes, the batch form `prisma.$transaction([a, b])` is enough.

**Raw SQL:**

```ts
const rows = await prisma.$queryRaw<{ month: Date; total: Prisma.Decimal }[]>`
  SELECT date_trunc('month', "createdAt") AS month, sum(total) AS total
  FROM "Offer" WHERE "ownerId" = ${userId}::uuid GROUP BY 1 ORDER BY 1`;
```

The tagged template turns `${userId}` into a bind parameter. `$queryRawUnsafe(\`... ${userId}\`)` concatenates strings and is SQL injection (#113). Use `Prisma.sql` and `Prisma.join` to build dynamic fragments safely; newer versions also offer TypedSQL (`.sql` files with generated types).

**Practical gotchas:**

- **One `PrismaClient` per process.** In dev with hot reload, store it on `globalThis` so each reload doesn't open a new pool. In serverless, keep pools small or use a pooler (#338, #626).
- **`Decimal` columns** come back as `Prisma.Decimal` objects, not numbers (#630). **`DateTime`** comes back as a JS `Date` in UTC.
- **Soft delete and tenant/owner filters:** a client extension (`prisma.$extends({ query: { offer: { findMany({ args, query }) { ... } } } })`) can add `deletedAt: null` or an owner filter everywhere, but don't rely on it alone for security (#622).
- **`prisma generate`** must run after install and in the Docker build; the generated client lives in your build output or `node_modules`, so forgetting it gives "Prisma Client did not initialize".
- Prefer `updateMany`/`deleteMany` with a `where` that includes the owner for authorization in one query, and check the returned `count`.
