## Hints

- In GitOps, who applies changes to the cluster: your CI pipeline or something running inside the cluster?
- During a rolling update, how does Kubernetes know a new pod is ready to receive traffic?
- What's the difference between a CPU limit and a memory limit when a pod exceeds it?

## Answer

**GitOps with Argo CD**

- The desired state of each environment lives in **Git**: plain manifests, Kustomize overlays or Helm charts, often in a separate config repository.
- **Argo CD** runs in the cluster. An `Application` points at a repo, path and revision; Argo CD keeps comparing the live state with Git (**Synced / OutOfSync**, **Healthy / Progressing / Degraded**) and syncs, automatically or on demand.
- It's a **pull model**: CI builds and tests, pushes an image tagged with the commit SHA to the registry (Artifact Registry on GCP) and updates the tag in the config repo with a commit or PR. CI never holds cluster credentials.
- **Rollback = `git revert`** of the tag bump, so every change is reviewed and auditable. Argo CD can also roll back to an earlier sync, but auto-sync must be off for that, or Git would win again.
- `selfHeal` reverts manual `kubectl edit` drift; `prune` deletes resources removed from Git. **Sync waves** order resources, and a `PreSync` hook Job can run database migrations before the new pods start.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata: { name: booking-api, namespace: argocd }
spec:
  project: default
  source:
    repoURL: https://github.com/acme/k8s-config
    path: apps/booking-api/overlays/production
    targetRevision: main
  destination: { server: https://kubernetes.default.svc, namespace: booking }
  syncPolicy:
    automated: { prune: true, selfHeal: true }
```

**What happens in the cluster: a rolling update of a Deployment**

```yaml
spec:
  replicas: 4
  strategy:
    rollingUpdate: { maxSurge: 25%, maxUnavailable: 0 }    # add new pods before removing old ones
  template:
    spec:
      terminationGracePeriodSeconds: 40
      containers:
        - name: api
          image: europe-docker.pkg.dev/acme/apps/booking-api:3f9c2e1
          resources:
            requests: { cpu: 250m, memory: 512Mi }
            limits: { memory: 512Mi }
          readinessProbe: { httpGet: { path: /ready, port: 3000 }, periodSeconds: 5 }
          livenessProbe: { httpGet: { path: /live, port: 3000 }, periodSeconds: 10, failureThreshold: 3 }
          lifecycle:
            preStop: { sleep: { seconds: 5 } }   # Kubernetes 1.30+; let endpoints update before SIGTERM
```

- New pods receive traffic only once the **readiness probe** passes; an old pod is removed only when its replacement is ready. If new pods never become ready, the rollout stalls instead of taking the service down (`progressDeadlineSeconds` marks it failed).
- **Liveness** restarts a stuck process. Don't check the database in liveness: a database blip would restart every pod at once. Use a **startup probe** for slow boots.
- **Graceful shutdown:** on SIGTERM stop accepting new connections, finish in-flight requests, close pools (#301).

**Resources and scaling**

- **Requests** reserve capacity and drive scheduling; **limits** cap usage. Over the **CPU** limit a container is **throttled** (latency spikes with no errors); over the **memory** limit it's **OOMKilled**. A common setup is memory request = limit and CPU requests without a CPU limit. Size the Node heap to the container's memory.
- **HPA** scales on CPU utilisation (relative to requests) or custom metrics (queue depth via KEDA, external metrics such as Datadog's). A **PodDisruptionBudget** keeps enough replicas during node upgrades.
- **Progressive delivery:** Argo Rollouts adds canary and blue-green with automated analysis of metrics (it can query Datadog or Prometheus) and automatic abort.

**Config and secrets:** ConfigMaps and Secrets, but **no plaintext secrets in the GitOps repo**: use External Secrets Operator with GCP Secret Manager, Sealed Secrets or SOPS. Give pods cloud access with **Workload Identity** instead of key files.

**Environments:** a Kustomize base with `staging` and `production` overlays (or Helm values per environment), promotion by PR, and ApplicationSets to generate Applications for many services or clusters.

**Follow-up:** a deploy is Synced and Healthy in Argo CD, but users see errors. How is that possible? (Health only means pods are running and ready; readiness may not check the real dependency, the bug may be in logic, or a migration may have broken the old pods. That's why you also watch error rates and business metrics, and use canaries with analysis.)
